SPA Loading Model

The browser downloads the app shell once. Subsequent navigations are instant — JavaScript intercepts the URL change and renders the new view client-side. No full page reload.

First load
HTML shell
JS bundle (500KB)
API data
Total: ~3s (slow 3G)
Subsequent navigation
API data
Total: ~200ms ⚡

✅ SPA Strengths

Fast navigation after first load
Rich app-like interactions
Offline capability (PWA)
Shared app state between routes
Modern framework support

❌ SPA Weaknesses

Slow initial load
Poor SEO out-of-box
JS required — no JS = broken
Memory leaks accumulate
TTFB depends on API

Navigation timing — SPA vs MPA

SPA
First page: 2,800ms (full bundle + render)
Nav #2: 80ms
Nav #3: 40ms (cached)
MPA (traditional)
Page 1: 800ms
Page 2: 750ms (new request)
Page 3: 820ms (another request)
SPA loses on first load, wins on every subsequent navigation. For dashboards and internal tools (authenticated apps with many routes), SPA is the right choice.

Code Splitting in SPAs (React lazy / Vite)

// Without code splitting: one 1.5MB bundle loads on first visit
// With code splitting: only load what's needed

import { lazy, Suspense } from 'react';

// Each route is its own chunk — loaded on demand
const Dashboard = lazy(() => import('./pages/Dashboard'));
const Orders = lazy(() => import('./pages/Orders'));
const Analytics = lazy(() => import('./pages/Analytics'));

const App = () => (
  <Router>
    <Suspense fallback={<PageSkeleton />}>
      <Routes>
        <Route path="/" element={<Dashboard />} />
        <Route path="/orders" element={<Orders />} />
        <Route path="/analytics" element={<Analytics />} />
      </Routes>
    </Suspense>
  </Router>
);

// Result: Main bundle 200KB → chunks 80KB each
// SAP Fiori: first load 1.8s → 0.9s after route-level splitting
