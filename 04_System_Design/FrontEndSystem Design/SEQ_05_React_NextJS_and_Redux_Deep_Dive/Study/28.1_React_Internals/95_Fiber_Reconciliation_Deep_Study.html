1. What Is React Fiber?

// Fiber is React's internal reconciliation engine (React 16+)
// It replaced the old "Stack Reconciler" with an incremental, interruptible architecture
//
// The Problem Fiber Solves:
// ─────────────────────────────────────────────────────
// Old Stack Reconciler (React ≤15):
//   - Recursive, synchronous tree diffing
//   - Once started, CANNOT be interrupted
//   - Long component trees → blocks main thread for 100ms+
//   - User interactions (typing, clicking) FREEZE during render
//   - Animations stutter at 60fps (16ms budget exceeded)
//
// Fiber Architecture (React 16+):
//   - Units of work (fibers) processed incrementally
//   - Can PAUSE work, do higher-priority updates, then RESUME
//   - Uses requestIdleCallback / MessageChannel for scheduling
//   - Enables: Concurrent Mode, Suspense, Transitions, Streaming SSR
//
// Key Insight: Fiber turns the call stack into a linked list
//   Stack: function calls → can't pause mid-execution
//   Fiber: linked list → can save position and resume later

2. Fiber Node Structure

// Every React element gets a corresponding Fiber node
// A Fiber is a JS object with these key fields:

FiberNode {
  // ── Identity ──
  tag: 0,              // FunctionComponent=0, ClassComponent=1, HostComponent=5, etc.
  type: App,            // The component function/class or 'div', 'span', etc.
  key: 'item-1',        // Reconciliation key for list diffing

  // ── Tree Links (Linked List) ──
  return: parentFiber,  // Parent node (up)
  child: firstChild,    // First child (down)
  sibling: nextSibling, // Next sibling (right)

  // ── State & Props ──
  pendingProps: {},     // New props from parent (incoming)
  memoizedProps: {},    // Props from last render (current)
  memoizedState: {},    // State from last render (hooks linked list)
  updateQueue: {},      // Pending state updates queue

  // ── Effects ──
  flags: 0,             // Placement=2, Update=4, Deletion=8, etc. (bitmask)
  subtreeFlags: 0,      // Aggregated flags from children
  effectTag: 0,         // Side effects to commit (DOM updates, refs, lifecycles)

  // ── Double Buffering ──
  alternate: otherFiber // Points to the "other" version of this fiber
                        // current ↔ workInProgress (swap on commit)
}
Double Buffering: React maintains TWO fiber trees. The "current" tree reflects what's on screen. The "workInProgress" tree is being built during render. On commit, React swaps them — the workInProgress becomes current. This enables interruptible rendering without visual corruption.

3. Reconciliation Algorithm (Diffing)

// React's diffing is O(n) thanks to two heuristics:
//
// Heuristic 1: Different element types → destroy old tree, build new
//   <div> → <span> = unmount entire subtree, mount fresh
//   <ComponentA> → <ComponentB> = unmount A, mount B (even if similar)
//
// Heuristic 2: Keys identify stable elements across renders
//   <li key="a"> stays matched to <li key="a"> even if position changes
//   Without keys: React matches by index (wrong! causes bugs)
//
// Diffing Steps:
// 1. Compare root elements (same type? → update props; diff type? → replace)
// 2. Recurse into children
// 3. For lists: match by key, detect insertions/deletions/moves
//
// List Diffing (Key Algorithm):
// ─────────────────────────────────
// Old: [A, B, C, D]
// New: [A, C, D, B]
//
// Without keys (by index):
//   index 0: A→A ✓ (keep)
//   index 1: B→C ✗ (update B→C, re-render subtree!)
//   index 2: C→D ✗ (update C→D, re-render subtree!)
//   index 3: D→B ✗ (update D→B, re-render subtree!)
//   = 3 unnecessary re-renders
//
// With keys:
//   key="A" matched → keep
//   key="B" moved to index 3 → move DOM node
//   key="C" matched → keep
//   key="D" matched → keep
//   = 1 DOM move (optimal!)

4. Two Phases: Render & Commit

// ═══════════════════════════════════════════════
// PHASE 1: RENDER (Interruptible, Pure)
// ═══════════════════════════════════════════════
// Work: Build workInProgress tree, compute diffs
// Can be: Paused, aborted, restarted
// Calls: render(), constructor(), getDerivedStateFromProps()
// Must be: Pure (no side effects!)
//
// Traversal Order (like DFS):
//   1. beginWork(fiber) → process fiber, return child
//   2. If child exists → beginWork(child)
//   3. If no child → completeWork(fiber), go to sibling
//   4. If no sibling → completeWork(parent), go up
//
// ═══════════════════════════════════════════════
// PHASE 2: COMMIT (Synchronous, Side Effects)
// ═══════════════════════════════════════════════
// Work: Apply all collected changes to the DOM
// Cannot be: Interrupted (must complete atomically)
// Three sub-phases:
//   a) beforeMutation: read DOM (getSnapshotBeforeUpdate)
//   b) mutation: write DOM (insertions, updates, deletions)
//   c) layout: read DOM after mutation (useLayoutEffect, componentDidMount)
//
// After commit: current tree pointer swaps to workInProgress
// useEffect callbacks are scheduled asynchronously (after paint)

Fiber Traversal: The Work Loop

// Simplified React work loop (performUnitOfWork)
// This is what makes Fiber interruptible

function workLoopConcurrent() {
  // Process fibers one at a time, checking for interruptions
  while (workInProgress !== null && !shouldYield()) {
    workInProgress = performUnitOfWork(workInProgress);
  }
}

function performUnitOfWork(unitOfWork) {
  // Step 1: Process this fiber (call component, compute diff)
  const next = beginWork(unitOfWork);

  if (next !== null) {
    // Has children → go deeper
    return next;
  }

  // No children → complete this fiber and find next work
  let completedWork = unitOfWork;
  while (completedWork !== null) {
    completeWork(completedWork); // Collect effects

    if (completedWork.sibling !== null) {
      return completedWork.sibling; // Process sibling next
    }
    completedWork = completedWork.return; // Go up to parent
  }
  return null; // All work done
}

// shouldYield() checks:
//   - Has 5ms elapsed since this time slice started?
//   - Are there higher-priority updates waiting?
//   - Is there pending user input?
// If yes → pause, yield to browser, resume later

Priority Lanes (React 18)

// React uses "Lanes" to assign priority to updates
// Lanes are bitmasks — can combine multiple priorities

// Lane priorities (highest to lowest):
SyncLane          = 0b0000000000000000000000000000010  // Discrete events (click, keydown)
InputContinuousLane = 0b0000000000000000000000000001000 // Continuous events (scroll, mousemove)
DefaultLane       = 0b0000000000000000000000000100000  // Normal setState
TransitionLane1   = 0b0000000000000000000000010000000  // startTransition updates
IdleLane          = 0b0100000000000000000000000000000  // Offscreen, low priority

// How Lanes work in practice:
//
// 1. User types in search box → SyncLane (show keystroke ASAP)
// 2. Search results filter → TransitionLane (can wait)
//
// React processes SyncLane first, interrupting TransitionLane work
// This is why useTransition makes UIs feel responsive:
//   - Urgent update (input value) renders immediately
//   - Transition (filtered list) renders when idle

function SearchWithTransition() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);
  const [isPending, startTransition] = useTransition();

  function handleChange(e) {
    setQuery(e.target.value);           // SyncLane → immediate

    });
  }
}

Effect Flags & Commit Phase Internals

// During render phase, fibers accumulate effect flags:
const Placement    = 0b00000010;  // New node → insert into DOM
const Update       = 0b00000100;  // Props/state changed → update DOM
const Deletion     = 0b00001000;  // Removed → delete from DOM
const ChildDeletion= 0b00010000;  // Child was deleted
const Ref          = 0b00100000;  // Ref needs attaching/detaching
const Passive      = 0b01000000;  // useEffect callback needs running
const Layout       = 0b10000000;  // useLayoutEffect callback

// Commit phase walks the fiber tree and processes flags:
//
// Sub-phase 1: beforeMutation
//   → getSnapshotBeforeUpdate (class components)
//   → Read DOM before changes
//
// Sub-phase 2: mutation
//   → Placement: parentNode.appendChild(newChild)
//   → Update: node.setAttribute(), node.textContent = ...
//   → Deletion: parentNode.removeChild(child)
//   → Ref detach: ref.current = null
//
// Sub-phase 3: layout (after DOM mutation, before paint)
//   → useLayoutEffect callbacks fire synchronously
//   → componentDidMount / componentDidUpdate
//   → Ref attach: ref.current = domNode
//
// After paint (async):
//   → useEffect callbacks fire asynchronously
//   → Passive effects scheduled via flushPassiveEffects()

FAANG Interview Questions

Q1: Explain React Fiber architecture and why it was introduced.
React Fiber is the complete rewrite of React's reconciliation engine, introduced in React 16. The old Stack Reconciler used recursive, synchronous tree diffing — once it started processing a large component tree, it couldn't stop until done. This blocked the main thread for 50-100ms+, causing dropped frames and unresponsive UIs. Fiber solves this by representing each component as a "fiber node" linked in a tree via child/sibling/return pointers (linked list instead of call stack). The key innovation is the work loop: React processes one fiber at a time, and after each unit of work, checks shouldYield() — if 5ms has elapsed or higher-priority input is pending, it yields to the browser. This enables time-slicing (splitting rendering across frames), prioritized updates (user clicks processed before background data), and the foundation for Concurrent Mode, Suspense, and Transitions. The double-buffering technique (current vs workInProgress trees) ensures the UI never shows partial updates.
Follow-up: What happens when React "interrupts" a render? Does work get lost?
Q2: How does React's diffing algorithm achieve O(n) complexity?
Generic tree diff is O(n³). React achieves O(n) through two heuristics. First: elements of different types produce different trees — if a <div> becomes a <span>, React destroys the entire subtree and rebuilds, skipping deep comparison. Second: developers provide keys to hint at stable identity across renders. For lists, React builds a Map of old keys → fiber nodes, then iterates the new list: if a key matches, it reuses the fiber (potentially moving it); if not, it creates a new one; leftover old fibers are deleted. Without keys, React matches by index, which causes unnecessary unmount/remount when items are reordered — this is the classic "don't use array index as key" interview point. The trade-off: React may do extra work if keys are wrong (like using Math.random()), but in practice O(n) diffing with keys handles 99% of real-world UI updates efficiently.
Follow-up: When would React's O(n) heuristic produce suboptimal results?
Q3: Explain the render phase vs commit phase. Why does it matter?
The render phase is where React calls your component functions, computes the virtual DOM diff, and builds the workInProgress fiber tree. It's pure computation — no DOM mutations, no side effects. Critically, it can be paused, aborted, and restarted (this is how Concurrent Mode works). The commit phase takes the completed workInProgress tree and applies all DOM mutations synchronously in three sub-phases: beforeMutation (read DOM snapshots), mutation (actual DOM writes — insert, update, delete), and layout (useLayoutEffect, ref attachment). The commit phase CANNOT be interrupted — once it starts, it runs to completion to avoid showing partial UI states. This separation matters because: (1) render functions must be pure since they may run multiple times, (2) useLayoutEffect runs synchronously before paint (blocking), while useEffect runs after paint (non-blocking), and (3) side effects in render phase cause bugs in Concurrent Mode — a component might render twice but only commit once.
Follow-up: How does this affect where you should put data fetching logic?
Q4: What are React priority lanes and how do they enable concurrent rendering?
Lanes are React's priority system, replacing the older "expiration time" model. Each update is assigned a lane (a bitmask) based on its origin: SyncLane for discrete events like clicks (highest), InputContinuousLane for scroll/mousemove, DefaultLane for normal setState, TransitionLane for startTransition, and IdleLane for offscreen work. When React enters the work loop, it picks the highest-priority pending lane and processes only updates in that lane. If a higher-priority update arrives mid-render, React can interrupt the current work and switch. For example: user types in a search box — the input value update gets SyncLane (renders immediately), while the filtered results list uses startTransition → TransitionLane (interruptible). The user sees their keystroke instantly, and the list updates when the browser is idle. Bitmask design allows batching: if 3 transitions are pending, they share TransitionLanes and process together. This is the core mechanism behind useTransition, useDeferredValue, and why React 18 feels responsive with large component trees.
Follow-up: How would you debug a case where transitions aren't improving perceived performance?

//
// Step 3: Delete remaining (none)
//
// Result: 1 DOM move (c moved to front) instead of 3 DOM updates
//

    • 3. Concurrent Rendering: useTransition Example

    import { useState, useTransition, memo } from 'react';

// 10,000 items — heavy to filter
const allItems = Array.from({ length: 10000 }, (_, i) => ({
  id: i,
  name: `Item ${i}`
}));

function SearchApp() {
  const [query, setQuery] = useState('');
  const [filtered, setFiltered] = useState(allItems);
  const [isPending, startTransition] = useTransition();

  function handleSearch(e) {
    const value = e.target.value;

    // Urgent: update input immediately (SyncLane)
    setQuery(value);

    // Non-urgent: filter list in background (TransitionLane)
    startTransition(() => {
      const results = allItems.filter(item =>
        item.name.toLowerCase().includes(value.toLowerCase())
      );
      setFiltered(results);
    });
  }

  return (
    <div>
      <input value={query} onChange={handleSearch} />
      {isPending && <span>Filtering...</span>}
      <ul style={{ opacity: isPending ? 0.7 : 1 }}>
        {filtered.map(item => (
          <li key={item.id}>{item.name}</li>
        ))}
      </ul>
    </div>
  );
}

// What Fiber does:
// 1. User types 'a' → SyncLane update: query='a' renders IMMEDIATELY
// 2. TransitionLane update: filter 10K items starts in background
// 3. User types 'ab' before filter completes → SyncLane interrupts!
// 4. React ABORTS the 'a' filter, starts fresh with 'ab'
// 5. Input stays responsive throughout (never blocks for >5ms)
