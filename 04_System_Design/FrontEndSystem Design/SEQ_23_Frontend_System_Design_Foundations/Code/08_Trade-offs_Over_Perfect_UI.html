Scenario: Should the hero section of a marketing page have a full-screen 4K background video?
4K Background Video
✅ Option A — No video, use CSS animations
+ LCP stays under 2.5s
+ Saves 5–15 MB per page load
+ Works on all connections
+ Lighthouse score unaffected
- Less visually wow-factor on desktop
✓ Recommended for SEO-critical pages
Option B — Full 4K video
+ Stunning visual impact
+ Strong brand impression on high-end devices
- LCP >6s on mobile
- 15MB download on 3G = 60s load
- Poor CLS if video layout shifts
- Battery drain on mobile
Use only with lazy-load + poster fallback
Scenario: Build a news aggregator app (public content, SEO critical, 20M monthly users)
Rendering Strategy
Option A — Pure CSR (React SPA)
+ Simple deployment (static hosting)
+ Fast subsequent page navigations
+ Lower server costs
- Googlebot may not index JS content
- Blank screen until JS loads (FCP ~3s)
- Bad for news SEO ranking
Only valid for authenticated apps
✅ Option B — SSR or Hybrid (Next.js)
+ Full HTML on first request → instant FCP
+ Googlebot reads actual content
+ LCP from CDN cache with ISR
+ Core Web Vitals green
- Server costs (mitigated with edge caching)
- Hydration complexity
✓ Recommended: ISR with 60s revalidate
Scenario: A dashboard with theme (dark/light), user profile, and a complex multi-step form with 30 fields
State Management
✅ Option A — Context for theme/profile + local state for form
+ Zero extra dependencies
+ Form state stays co-located with form
+ Context re-renders limited to subtree
+ Simple, predictable
- Form logic can get verbose without a form library (use react-hook-form)
✓ Right for most SPAs without complex shared derived state
Option B — Redux Toolkit for everything
+ DevTools time-travel debugging
+ Predictable global state
- RTK boilerplate for simple use case
- 15KB bundle weight
- Over-engineering for theme + profile
- Form in Redux = re-render on each keystroke
Use when: multiple teams, complex derived state, undo history
Scenario: Stock price dashboard — prices update every 5 seconds for 50 symbols
Update Strategy
✅ Option A — SSE (Server-Sent Events)
+ Single persistent HTTP connection
+ Automatic reconnection built-in
+ Works through standard proxies/firewalls
+ Server pushes only when data changes
- Uni-directional (client→server needs REST)
- Max 6 connections per domain (HTTP/1.1)
✓ Best for one-directional broadcast at regular intervals
Option B — WebSocket
+ Bi-directional: subscribe/unsubscribe messages
+ Lower latency for truly real-time (trading apps)
- More complex infrastructure (sticky sessions or Redis pub/sub)
- Overkill if client never sends data
- Proxy/firewall issues in enterprise (SAP context!)
Use when: chat, collaborative editing, gaming
Scenario: Enterprise form needs a date-picker with keyboard navigation
Component Approach
Option A — Custom pixel-perfect date picker
+ Total visual control
+ Matches design system exactly
- Must implement ALL keyboard nav: arrow keys, Home/End, Page Up/Down
- Must add ARIA role="dialog", aria-label, aria-live
- Must test with NVDA/JAWS/VoiceOver
- 2–4 weeks to certify WCAG AA
Only if design system doesn't exist
✅ Option B — React Aria / Radix / Headless UI datepicker
+ WCAG AA keyboard nav out of box
+ Screen-reader tested
+ Styled via CSS classes (design system compatible)
+ Ship in 2 days, not 2 weeks
- Slight style coupling to library conventions
- Bundle weight (~5–10KB)
✓ Always prefer battle-tested accessible primitives

📐 The 5 Rules of Trade-off Thinking

1
There is no universally correct answer. The correct answer depends on your constraints: scale, team size, timeline, user environment.
2
Name both options explicitly. "I chose A over B because…" — not just "I chose A." Interviewers want to see you considered alternatives.
3
Quantify the trade-off. Not "slower" — "LCP increases by ~1.5 seconds on 3G." Not "heavier bundle" — "adds 15KB gzip."
4
Know when to flip the decision. "I'd reconsider this if: user base grows beyond 50M, or if requirements change to include real-time collaboration."
5
Perfect is the enemy of shipped. A working accessible component shipped now beats a pixel-perfect inaccessible one shipped in 6 weeks.

🗂️ Hruday's Proven Trade-offs (SAP/Bosch/Oracle)

⚡
Chose lazy-loading + video poster over full 4K hero video → LCP dropped from 6s to 1.8s, bounced design-system requirement to use CSS animation fallback
♿
Chose SAP Fiori web components (native a11y) over custom date pickers → WCAG AA achieved in 3 days, custom picker would have taken 3 weeks
🔌
Chose REST + React Query caching over WebSockets for a 5-minute polling dashboard at SAP → simpler infrastructure, saved 2 weeks of backend work
🧩
Chose Module Federation micro-frontends over monolith → teams deployed independently, but added SharedScope complexity — documented the trade-off in ADR
