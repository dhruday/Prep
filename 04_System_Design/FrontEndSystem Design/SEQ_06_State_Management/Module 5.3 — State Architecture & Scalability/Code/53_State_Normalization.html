Why normalize state?

Nested state structures cause two critical problems: stale duplicates (same entity appears in multiple places and gets out of sync) and O(n) lookups (must search arrays to find by id). Normalisation flattens data into a dictionary keyed by id.

❌ Nested (problematic)
orders: [
 {id:'1', product:{id:'P1', name:'License'}},
 {id:'2', product:{id:'P1', name:'License'}},
]
→ P1 appears twice! Update one = inconsistency
✅ Normalised (O(1) lookup)
orders:  { ids:['1','2'], entities:{1:{productId:'P1'}, 2:{productId:'P1'}} }
products: { ids:['P1'], entities:{P1:{name:'License'}} }
→ One source of truth. O(1) update.

normalizr + EntityAdapter patterns

// ─── normalizr (normalize API response) ───
import { schema, normalize } from 'normalizr';

const product = new schema.Entity('products');
const order   = new schema.Entity('orders', { product });
const result  = normalize(apiResponse, [order]);

// result.entities → { orders: {...}, products: {...} }
// result.result   → ['1', '2']  (ids)

// ─── NgRx EntityAdapter (built-in normalisation) ───
const ordersAdapter = createEntityAdapter<Order>({
  selectId: o => o.id,
  sortComparer: (a, b) => a.date.localeCompare(b.date),
});
const initialState = ordersAdapter.getInitialState();
// { ids: [], entities: {} }

// Reducer operations:
ordersAdapter.addOne(state, order);         // O(1)
ordersAdapter.updateOne(state, { id, changes }); // O(1)
ordersAdapter.removeOne(state, id);         // O(1)
ordersAdapter.upsertMany(state, orders);    // batch O(1)

// Selectors:
const { selectAll, selectById, selectTotal } = ordersAdapter.getSelectors();
