1. What Is Memoization?

// Memoization = caching the result of expensive computations
// If the same inputs are provided, return the cached result
// instead of recalculating.
//
// In React, there are THREE memoization tools:
//
// 1. React.memo(Component)
//    → Memoizes the COMPONENT RENDER
//    → Skips re-rendering if props haven't changed (shallow compare)
//
// 2. useMemo(computeFn, deps)
//    → Memoizes a COMPUTED VALUE
//    → Recalculates only when deps change
//
// 3. useCallback(fn, deps)
//    → Memoizes a FUNCTION REFERENCE
//    → Returns same function object unless deps change
//    → Syntactic sugar: useCallback(fn, deps) === useMemo(() => fn, deps)
//
// WHY this matters:
// React re-renders a component when its parent re-renders
// This can cascade: 1 state change → 100+ component re-renders
// Memoization breaks the cascade by skipping unchanged subtrees

2. React's Reconciliation & Why Memo Helps

// React's rendering pipeline:
// 1. Trigger: state/context change → component re-renders
// 2. Render: component function executes → returns new JSX
// 3. Reconcile: React diffs old and new virtual DOM (fiber tree)
// 4. Commit: React applies minimal DOM changes
//
// IMPORTANT: Step 2 (render) is the expensive part for CPU
// Not step 4 (DOM commit) — React is already efficient there
//
// Without memo:
// Parent re-renders → ALL children re-render (even unchanged ones)
// Each child runs its function body, creates JSX objects, diffs
//
// With React.memo:
// Parent re-renders → React checks child props (shallow compare)
// If props unchanged → SKIP rendering entirely (no function call)
//
// The catch: "unchanged" means shallow equality
// Objects/arrays create NEW references every render:
// { name: 'John' } !== { name: 'John' }  // Different reference!
// [1, 2, 3] !== [1, 2, 3]                 // Different reference!
// () => {} !== () => {}                    // Different reference!
//
// This is why useMemo/useCallback exist:
// They preserve references across renders when deps don't change

3. React 19's Automatic Memoization (React Compiler)

// React Compiler (formerly React Forget) — automatic memoization
// Available in React 19+ (experimental, Meta production since 2024)
//
// What it does:
// Compiler analyzes your component code at BUILD TIME
// Automatically inserts useMemo/useCallback where beneficial
// No manual memoization needed!
//
// Before (manual):
function Product({ item }) {
  const price = useMemo(() => formatPrice(item.price), [item.price]);
  const handleClick = useCallback(() => addToCart(item.id), [item.id]);
  return <div onClick={handleClick}>{price}</div>;
}

// After (compiler does it for you):
function Product({ item }) {
  const price = formatPrice(item.price);
  const handleClick = () => addToCart(item.id);
  return <div onClick={handleClick}>{price}</div>;
}
// Compiler output: same as the "before" version but auto-generated
//
// Current status (2026): Stable in React 19
// Instagram.com fully compiled — 12% improvement in INP

Pattern 1: React.memo for Component Memoization

// ✅ GOOD: Expensive component that receives stable props
const ExpensiveList = React.memo(function ExpensiveList({ items, onSelect }) {
  return (
    <ul>
      {items.map(item => (
        <li key={item.id} onClick={() => onSelect(item.id)}>
          {expensiveRender(item)}
        </li>
      ))}
    </ul>
  );
});

// Custom comparison for complex props:
const Chart = React.memo(ChartComponent, (prevProps, nextProps) => {
  // Return true if props are "equal" (skip re-render)
  return prevProps.data.length === nextProps.data.length
    && prevProps.data.every((d, i) => d.id === nextProps.data[i].id);
});

// ❌ BAD: Memoizing a simple component
const Label = React.memo(({ text }) => <span>{text}</span>);
// Cost of memo check ≈ cost of re-rendering — no benefit

Pattern 2: useMemo for Expensive Computations

// ✅ GOOD: Filtering/sorting large datasets
function ProductList({ products, filter }) {
  const filtered = useMemo(() => {
    return products
      .filter(p => p.category === filter)
      .sort((a, b) => b.rating - a.rating);
  }, [products, filter]);

  return filtered.map(p => <Product key={p.id} product={p} />);
}

// ✅ GOOD: Creating stable object/array references for memo'd children
function Dashboard({ userId }) {
  const config = useMemo(() => ({
    userId,
    theme: 'dark',
    features: ['analytics', 'charts'],
  }), [userId]);

  return <MemoizedPanel config={config} />;
}

// ❌ BAD: Trivial computation
const fullName = useMemo(() => `${first} ${last}`, [first, last]);
// String concatenation is cheaper than useMemo's overhead

Pattern 3: useCallback for Stable Function References

// useCallback prevents creating new function on every render
// ONLY useful when passed to a React.memo'd child

// ✅ GOOD: Handler passed to memo'd list item
function TodoList({ todos }) {
  const handleToggle = useCallback((id) => {
    setTodos(prev => prev.map(t =>
      t.id === id ? { ...t, done: !t.done } : t
    ));
  }, []); // No deps because we use updater function

  return todos.map(todo =>
    <MemoizedTodoItem key={todo.id} todo={todo} onToggle={handleToggle} />
  );
}

// ✅ GOOD: Dependency of useEffect
const fetchData = useCallback(async () => {
  const res = await fetch(`/api/user/${userId}`);
  setData(await res.json());
}, [userId]);

useEffect(() => { fetchData(); }, [fetchData]);

// ❌ BAD: useCallback without React.memo recipient
const handleClick = useCallback(() => setCount(c => c + 1), []);
return <button onClick={handleClick}>+</button>;
// <button> is a native element — it ALWAYS re-renders with parent
// useCallback adds overhead with zero benefit here

FAANG Interview Questions

Q1: When should you use React.memo vs useMemo vs useCallback?
React.memo wraps a component to skip re-rendering when props are shallowly equal — use it for components that are expensive to render AND receive the same props frequently (e.g., list items, charts, data grids). useMemo caches a computed value — use it for expensive calculations (filtering 10K items, complex transformations) or to create stable object/array references passed to memo'd children. useCallback caches a function reference — it's essentially useMemo(() => fn, deps). Use it when passing callbacks to React.memo'd children, otherwise the new function reference defeats memo. Key rule: useCallback is only useful if the receiving component is wrapped in React.memo or uses the callback in a useEffect dependency array. Without that, you're adding memoization overhead with no benefit.
Follow-up: How does React Compiler change the memoization strategy?
Q2: What are the costs of excessive memoization?
Memoization has real costs that are often overlooked: (1) Memory — every useMemo/useCallback stores the cached value plus the dependency array in the fiber. For a component rendering 1000 list items each with 3 memoized values, that's 3000 cached objects in memory. (2) Comparison cost — on every render, React must shallow-compare all dependencies. If there are many deps or deps are deep objects, comparison can approach the cost of just recalculating. (3) Code complexity — developers wrap everything in useMemo "just in case," making code harder to read and maintain. (4) Stale closures — useCallback with missing dependencies returns a stale function that references old state, causing bugs. The rule: profile first, then memoize. Don't memoize computations that take less than ~1ms. Use React DevTools Profiler to identify actual bottlenecks before adding memo.
Follow-up: How would you profile to determine if memoization is actually helping?
Q3: Explain how useMemo and useCallback work internally in React's fiber architecture.
In React's fiber tree, each component instance has a "hooks" linked list attached to its fiber node. useMemo creates a hook node that stores [memoizedValue, deps]. On subsequent renders, React walks the hooks list in order. For useMemo, it compares current deps with stored deps using Object.is() for each element. If all deps are identical, it returns the cached value (skips executing the compute function). If any dep changed, it runs the compute function, stores the new value and new deps. useCallback is identical internally — it stores the function itself as the memoized value. The key implementation detail: hooks MUST be called in the same order every render because React uses the call order to map hooks to fiber nodes. That's why hooks can't be inside conditionals. Memory-wise, each hook adds ~40 bytes to the fiber, so thousands of hooks across many components have measurable memory impact.
Follow-up: What happens to memoized values when a component unmounts?

Memoization Anti-Patterns

// ❌ Anti-Pattern 1: Memoizing everything "just in case"
const name = useMemo(() => user.name, [user.name]); // NO! Property access is free
const onClick = useCallback(() => setOpen(true), []); // NO! button isn't memo'd

// ❌ Anti-Pattern 2: Unstable deps defeating memoization
function Parent() {
  const config = { theme: 'dark' }; // New object every render!
  return <MemoChild config={config} />; // Memo is useless — new ref each time
}
// Fix: const config = useMemo(() => ({ theme: 'dark' }), []);

// ❌ Anti-Pattern 3: Missing deps in useCallback
const [count, setCount] = useState(0);
const handleClick = useCallback(() => {
  console.log(count); // Always logs 0! Stale closure
}, []); // Missing dep: count
// Fix: use updater: setCount(c => c + 1) → no dep needed

// ❌ Anti-Pattern 4: React.memo on components with children prop
const Layout = React.memo(({ children }) => <div>{children}</div>);
// children is JSX — new object every render → memo never skips

// ✅ Better pattern: composition over memo
function Parent() {
  const [count, setCount] = useState(0);
  return (
    <div>
      <Counter count={count} setCount={setCount} />
      <ExpensiveTree /> {/* Doesn't re-render! Not a child of Counter */}
    </div>
  );
}

Production Checklist

✅ Profile with React DevTools before adding memo
✅ React.memo on list items in large lists (>50 items)
✅ React.memo on components receiving context (they re-render on ANY context change)
✅ useMemo for expensive computations (>1ms with React Profiler)
✅ useCallback for functions passed to memo'd children
✅ Stable references for objects/arrays passed as props
✅ No missing dependencies in useMemo/useCallback
✅ Consider composition (lifting state) before memoization
✅ Monitor React Compiler compatibility for auto-memo
✅ Track re-render counts in dev with React.Profiler
