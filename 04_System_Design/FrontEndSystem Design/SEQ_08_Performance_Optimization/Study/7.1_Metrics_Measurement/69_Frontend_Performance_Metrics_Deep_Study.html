1. Why Performance Metrics Matter at Google Scale

// Google's research (2020):
// - 53% of mobile users abandon sites that take >3s to load
// - A 100ms improvement in LCP → +0.7% conversion at eBay
// - Pinterest: 40% reduction in wait time → 15% increase in SEO traffic
// - Google Search: Core Web Vitals are a ranking signal since 2021
//
// Performance metrics answer THREE questions:
// 1. "Is it happening?"  → FCP (First Contentful Paint)
// 2. "Is it useful?"     → LCP (Largest Contentful Paint)
// 3. "Is it usable?"     → INP (Interaction to Next Paint)
// 4. "Is it stable?"     → CLS (Cumulative Layout Shift)

3. Core Web Vitals (CWV) — The Google Ranking Trio

// Core Web Vitals are the THREE metrics Google uses for ranking:
// 1. LCP  — Loading performance
// 2. INP  — Interactivity (replaced FID in March 2024)
// 3. CLS  — Visual stability
//
// Assessment: A page "passes" CWV if 75th percentile of ALL three metrics
// are in the "Good" threshold across real user data (CrUX).
//
// Why 75th percentile (not median)?
// The p75 ensures MOST users (not just half) have a good experience.
// Outliers (top 25%) may be on very slow devices/networks — acceptable.
// But if your p75 is poor, a significant portion of users are suffering.
//
// CrUX (Chrome UX Report):
// Real-user data collected from opted-in Chrome users (billions of page loads)
// Updated monthly, powers PageSpeed Insights, Search Console
// Origin-level AND URL-level data available

5. The Browser Rendering Pipeline & Metrics

// Request → TTFB → FCP → LCP → TTI → INP (ongoing)
//                                        └── CLS (ongoing)
//
// Timeline of a page load:
//
// [0ms]  Navigation starts
//   ├── DNS lookup, TCP connect, TLS handshake
//   ├── Request sent to server
// [~200ms] TTFB — first byte of response arrives
//   ├── HTML parsing begins (incremental)
//   ├── CSS/JS discovered → fetched in parallel
// [~800ms] FCP — first text/image rendered
//   ├── Render-blocking CSS resolved
//   ├── Above-the-fold content painted
// [~1500ms] LCP — hero image/heading fully rendered
//   ├── Largest content element visible
//   ├── LCP can change until user interacts
// [~2500ms] TTI — main thread idle, handlers attached
//   ├── No long tasks blocking for 5s window
// [ongoing] INP — measured on every user interaction
// [ongoing] CLS — measured on every layout shift

LCP — Largest Contentful Paint (Deep Dive)

// LCP measures when the largest visible content element finishes rendering
//
// What counts as LCP element:
// ✓ <img> elements
// ✓ <image> inside <svg>
// ✓ <video> poster image (or first frame)
// ✓ CSS background-image (via url())
// ✓ Block-level text elements (<h1>, <p>, <div> with text)
//
// What does NOT count:
// ✗ Elements with opacity: 0
// ✗ Elements outside viewport
// ✗ Placeholder images (low intrinsic size)
//
// LCP keeps updating until:
// - User interacts (click, tap, keydown)
// - A larger element renders
//
// Common LCP killers:
// 1. Slow server response (TTFB > 800ms)
// 2. Render-blocking CSS/JS
// 3. Slow resource load (hero image not optimized)
// 4. Client-side rendering (content waits for JS)
// Optimizing LCP at Google scale:

// 1. Preload the LCP resource
<link rel="preload" as="image" href="/hero.webp" fetchpriority="high">

// 2. Use fetchpriority to boost LCP image
<img src="/hero.webp" fetchpriority="high" alt="Hero">

// 3. Inline critical CSS (eliminate render-blocking)
<style>/* critical above-the-fold CSS inlined */</style>
<link rel="preload" as="style" href="/full.css" onload="this.rel='stylesheet'">

// 4. Server-side render critical content (don't wait for JS)
// SSR/SSG ensures HTML contains content, not empty <div id="root">

INP — Interaction to Next Paint

// INP replaced FID in March 2024 as a Core Web Vital
//
// FID only measured INPUT DELAY of the FIRST interaction
// INP measures the FULL LATENCY of ALL interactions, reports worst (p98)
//
// INP = Input Delay + Processing Time + Presentation Delay
//
// Input Delay:        Time between user action and handler start
//                     (main thread busy with other tasks)
// Processing Time:    Time to run event handlers
//                     (your onClick, onChange code)
// Presentation Delay: Time from handler complete to next frame painted
//                     (style calc, layout, paint, composite)
//
// Why p98 (not worst)?
// If a page has 100 interactions, INP = 98th worst
// Filters out single-interaction anomalies
// But catches consistently slow interactions
//
// Common INP killers:
// 1. Heavy event handlers (data processing in onClick)
// 2. Synchronous layout (forced reflow in handler)
// 3. Long hydration blocking main thread
// 4. Third-party scripts monopolizing main thread

CLS — Cumulative Layout Shift

// CLS measures visual stability — unexpected element movements
//
// Layout Shift Score = Impact Fraction × Distance Fraction
//
// Impact Fraction: % of viewport affected by the shift
// Distance Fraction: How far elements moved (as % of viewport)
//
// Example: A 400px tall element shifts down by 100px
// Viewport = 800px
// Impact = (400 + 100) / 800 = 0.625
// Distance = 100 / 800 = 0.125
// Score = 0.625 × 0.125 = 0.078
//
// "Session window" approach (since 2021):
// CLS = worst session window (max 5s, 1s gap between shifts)
// Not the sum of ALL shifts over page lifetime
// Fairer for long-lived SPAs with many interactions
//
// Only UNEXPECTED shifts count. Excluded:
// ✓ Shifts within 500ms of user interaction (click, tap, keypress)
// ✓ Shifts from scroll (if using scroll-anchoring)
// ✗ Ads loading and pushing content down → counts!
// ✗ Images loading without dimensions → counts!
// ✗ Dynamic content injected above viewport → counts!

FAANG Interview Questions

Q1: Explain Core Web Vitals and why they matter for Google ranking.
Core Web Vitals are three metrics Google uses as a ranking signal: LCP (loading — largest content painted under 2.5s), INP (interactivity — interaction latency under 200ms), and CLS (stability — layout shift score under 0.1). Google evaluates these at the 75th percentile using real user data from CrUX (Chrome UX Report). They became a ranking factor in 2021 because Google found strong correlation between these metrics and user satisfaction. A page must pass all three at p75 to get the ranking boost — it's pass/fail per metric. The data comes from real Chrome users, not Lighthouse — so optimizing Lighthouse score alone doesn't guarantee ranking improvement. You need real-user monitoring to track what Google actually sees.
Follow-up: Why did Google replace FID with INP? What's the fundamental difference?
Q2: How would you design a performance monitoring system for a large-scale web app?
I'd implement a three-layer system. Layer 1: Real User Monitoring (RUM) using the web-vitals library to capture CWV from every user session. Each metric (LCP, INP, CLS) is sent to an analytics endpoint with metadata — device type, connection speed, geo, page URL. Layer 2: Synthetic monitoring using Lighthouse CI in our CI/CD pipeline, running against staging on every PR. We set performance budgets (LCP < 2.5s, bundle size < 200KB) that block merges if exceeded. Layer 3: Alerting — we aggregate RUM data in a dashboard (Grafana/Datadog), set p75 thresholds, and alert when metrics regress. The key insight: lab and field tell different stories. Lab catches regressions before deploy, field tells you what users actually experience. At Google scale, I'd also segment by geography and device — p75 LCP for users in India on 3G is very different from US on fiber.
Follow-up: How do you handle performance budgets when different teams own different parts of the page?
Q3: Your LCP is 4.2 seconds. Walk me through how you'd diagnose and fix it.
Step 1: Identify the LCP element — use Chrome DevTools Performance panel or web-vitals attribution build. Common LCP elements: hero images, large headings, video posters. Step 2: Break down the 4.2s into sub-parts. TTFB (server response time) — if TTFB is >1s, optimize server first (CDN, edge rendering, caching). Resource discovery time — if the LCP image isn't in the HTML (loaded via JS or CSS), the browser discovers it late. Fix: add preload hint with fetchpriority="high". Resource load time — if image is large, use modern formats (WebP/AVIF), responsive srcset, and CDN. Render blocking — if CSS/JS blocks rendering, inline critical CSS, defer non-critical JS. Client rendering — if content waits for JS hydration, switch to SSR/SSG for the critical path. I'd start with a Lighthouse trace, identify the biggest bottleneck in the LCP waterfall, fix it, measure again. Usually TTFB + render-blocking resources account for 70% of LCP issues.
Follow-up: How does fetchpriority="high" work at the browser level?
Q4: Explain the difference between TTFB, FCP, LCP, and TTI.
These metrics represent progressive milestones in the loading journey. TTFB (Time to First Byte) — measures server responsiveness. Timer starts at navigation, stops when the first byte of the HTML response arrives. Includes DNS, TCP, TLS, and server processing time. FCP (First Contentful Paint) — the first moment any content (text, image, canvas) is painted on screen. Tells the user "something is happening." LCP (Largest Contentful Paint) — when the largest visible content element (hero image, main heading) finishes rendering. This is what the user perceives as "the page loaded." TTI (Time to Interactive) — when the page is fully interactive — main thread is idle for 5+ seconds with no long tasks (>50ms). Deprecated from CWV but still useful for debugging. The progression: TTFB ≤ FCP ≤ LCP ≤ TTI. Each has different optimization levers: TTFB → server/CDN, FCP → critical CSS/fonts, LCP → resource loading priority, TTI → JavaScript execution cost.
Follow-up: Why was TTI replaced? What's wrong with the "5-second quiet window" definition?

1. Measuring Core Web Vitals with web-vitals Library

// The official Google library for measuring CWV
import { onLCP, onINP, onCLS, onFCP, onTTFB } from 'web-vitals';

// Each callback fires once with the final metric value
onLCP((metric) => {
  console.log('LCP:', metric.value, 'ms');
  console.log('Element:', metric.entries[0]?.element); // The LCP element
  console.log('Rating:', metric.rating); // 'good' | 'needs-improvement' | 'poor'
  sendToAnalytics(metric);
});

onINP((metric) => {
  console.log('INP:', metric.value, 'ms');
  // Attribution tells you WHICH interaction was slowest
  console.log('Target:', metric.entries[0]?.target);
  sendToAnalytics(metric);
});

onCLS((metric) => {
  console.log('CLS:', metric.value);
  // Entries show which elements shifted
  metric.entries.forEach(e => {
    e.sources?.forEach(s => console.log('Shifted:', s.node));
  });
  sendToAnalytics(metric);
});

function sendToAnalytics(metric) {
  // Beacon API — reliable even on page unload
  navigator.sendBeacon('/analytics', JSON.stringify({
    name: metric.name,
    value: metric.value,
    rating: metric.rating,
    delta: metric.delta,
    id: metric.id,
    navigationType: metric.navigationType,
    url: location.href,
    deviceType: /Mobile/.test(navigator.userAgent) ? 'mobile' : 'desktop',
    connection: navigator.connection?.effectiveType,
  }));
}

2. PerformanceObserver API — Low-Level Measurement

// PerformanceObserver is the browser API under web-vitals

// Observe LCP entries
const lcpObserver = new PerformanceObserver((list) => {
  const entries = list.getEntries();
  const last = entries[entries.length - 1]; // Latest LCP candidate
  console.log('LCP candidate:', last.startTime, last.element);
});
lcpObserver.observe({ type: 'largest-contentful-paint', buffered: true });

// Observe layout shifts for CLS
let clsValue = 0;
const clsObserver = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (!entry.hadRecentInput) { // Only unexpected shifts
      clsValue += entry.value;
      console.log('Shift:', entry.value, 'Total CLS:', clsValue);
      entry.sources?.forEach(s =>
        console.log('  Element:', s.node, 'moved from', s.previousRect, 'to', s.currentRect)
      );
    }
  }
});
clsObserver.observe({ type: 'layout-shift', buffered: true });

// Observe long tasks (>50ms main thread blocks)
const longTaskObserver = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log('Long task:', entry.duration, 'ms', entry.attribution);
  }
});
longTaskObserver.observe({ type: 'longtask', buffered: true });

3. Resource Timing — Network-Level Performance

// Get timing for every resource loaded on the page
const resources = performance.getEntriesByType('resource');

resources.forEach(r => {
  console.log({
    name: r.name,
    type: r.initiatorType, // 'script', 'img', 'css', 'fetch'
    duration: r.duration,
    size: r.transferSize,   // Bytes over network (0 if cached)
    protocol: r.nextHopProtocol, // 'h2', 'h3', 'http/1.1'
    cached: r.transferSize === 0,
    dns: r.domainLookupEnd - r.domainLookupStart,
    tcp: r.connectEnd - r.connectStart,
    ttfb: r.responseStart - r.requestStart,
    download: r.responseEnd - r.responseStart,
  });
});

// Find the LCP resource's network timing
new PerformanceObserver((list) => {
  const lcp = list.getEntries().at(-1);
  if (lcp?.url) {
    const res = performance.getEntriesByName(lcp.url)[0];
    console.log('LCP resource breakdown:', {
      discoveryTime: res.startTime,
      ttfb: res.responseStart - res.requestStart,
      downloadTime: res.responseEnd - res.responseStart,
      renderDelay: lcp.startTime - res.responseEnd,
    });
  }
}).observe({ type: 'largest-contentful-paint', buffered: true });
