1. The Browser Rendering Pipeline

// Normal rendering pipeline (optimal):
//
// JS → Style → Layout → Paint → Composite
//
// 1. JS: Your code runs, modifies DOM/CSSOM
// 2. Style: Browser recalculates computed styles
// 3. Layout: Browser calculates geometry (position, size)
// 4. Paint: Browser fills in pixels (colors, images, text)
// 5. Composite: Browser composites layers onto screen
//
// Normally: browser BATCHES all DOM changes
// You can do 1000 writes → browser does ONE layout pass
//
// Example (optimal — browser batches both writes):
el1.style.width = '100px';  // write (queued)
el2.style.height = '50px';  // write (queued)
// → ONE layout calculation at end of frame ✅
//
// Layout is "lazy" — only computed when NEEDED
// The browser invalidates layout on DOM write
// But doesn't recalculate until a read forces it

2. What Is a Forced Reflow?

// A "forced reflow" (forced synchronous layout) happens when:
// 1. You WRITE to the DOM (invalidates layout)
// 2. Then immediately READ a layout property
// → Browser MUST recalculate layout synchronously
//   to give you an accurate value
//
// Properties that TRIGGER forced reflow when READ:
//
// Element geometry:
//   offsetWidth, offsetHeight, offsetTop, offsetLeft
//   clientWidth, clientHeight, clientTop, clientLeft
//   scrollWidth, scrollHeight, scrollTop, scrollLeft
//   getBoundingClientRect()
//   getComputedStyle()
//
// Window properties:
//   window.innerWidth, window.innerHeight
//   window.scrollX, window.scrollY
//
// Other:
//   elem.focus() (needs layout to determine visibility)
//   elem.scrollIntoView()
//
// Example of forced reflow:
el.style.width = '100px';    // WRITE → invalidates layout
const h = el.offsetHeight;    // READ → forces synchronous layout!

Layout Thrashing: The Write-Read Loop

// Layout THRASHING = forced reflow in a LOOP
// Each iteration: write → read → browser recalculates layout
// N iterations = N layout recalculations (should be 1)

// ❌ THRASHING: O(n) layout calculations
const items = document.querySelectorAll('.item');
for (const item of items) {
  item.style.width = box.offsetWidth + 'px';  // READ → forced layout!
  item.style.height = box.offsetHeight + 'px'; // READ → forced layout!
}
// With 100 items: 200 forced layouts instead of 1!
// Can take 100ms+ instead of 2ms

// Real-world example: Responsive table resize
// ❌ This is O(n²) in layout cost:
columns.forEach(col => {
  col.style.width = (col.offsetWidth / totalWidth * 100) + '%';
  // Every iteration: read offsetWidth (forces layout)
  // then write width (invalidates layout for next read)
});

// Another common one: Animating position with JS
// ❌ Reading position after setting it, every frame:
function animate() {
  el.style.left = el.offsetLeft + 1 + 'px'; // read + write
  requestAnimationFrame(animate);
}

Fix: Read-then-Write Pattern

// Golden Rule: Batch all READS, then batch all WRITES
// Never interleave reads and writes

// ✅ FIXED: O(1) layout calculation
const items = document.querySelectorAll('.item');

// Phase 1: READ all values (one layout calculation)
const width = box.offsetWidth;
const height = box.offsetHeight;

// Phase 2: WRITE all values (batched, no forced layout)
for (const item of items) {
  item.style.width = width + 'px';
  item.style.height = height + 'px';
}
// → ONE layout at end of frame ✅

Fix: requestAnimationFrame for Writes

// Defer writes to the next frame
// Reads happen now, writes happen in rAF callback

const measurements = [];

// Read phase (current frame)
items.forEach((item, i) => {
  measurements[i] = item.getBoundingClientRect();
});

// Write phase (next frame boundary)
requestAnimationFrame(() => {
  items.forEach((item, i) => {
    item.style.transform = `translateY(${measurements[i].top}px)`;
  });
});

Fix: FastDOM Library

// FastDOM batches reads and writes automatically
import fastdom from 'fastdom';

items.forEach(item => {
  fastdom.measure(() => {                    // READ phase
    const width = item.offsetWidth;
    fastdom.mutate(() => {                   // WRITE phase
      item.style.height = width + 'px';
    });
  });
});
// FastDOM schedules all measures first, then all mutates
// Uses requestAnimationFrame internally

// Modern alternative: CSS containment
.item {
  contain: layout style;
  /* Changes inside don't trigger layout of siblings/parents */
  /* Limits the "blast radius" of layout recalculation */
}

FAANG Interview Questions

Q1: What is layout thrashing and how do you fix it?
Layout thrashing occurs when JavaScript alternates between reading layout properties (offsetWidth, getBoundingClientRect) and writing to the DOM in a loop. After a DOM write, the browser's layout is invalidated. When the next read occurs, the browser must perform a synchronous layout recalculation to return accurate values. In a loop of n elements, this causes n forced layouts instead of 1, turning an O(1) operation into O(n) or worse. The fix is the "read-then-write" pattern: first batch all reads (measure all elements into variables), then batch all writes (apply all changes). The browser then only needs one layout pass at the end of the frame. For complex scenarios, use requestAnimationFrame to defer writes to the next frame boundary, or use libraries like FastDOM that automatically batch reads and writes. Modern CSS containment (`contain: layout`) also helps by isolating layout recalculations to a subtree, reducing the cost of forced reflows.

Q2: How would you detect layout thrashing in a production app?
In Chrome DevTools Performance tab: record the interaction, look for long purple bars labeled "Layout" or "Recalculate Style" in the Main thread. If you see many small purple bars in rapid succession (rather than one at the end of the frame), that's thrashing. Click on a Layout entry — it shows "Layout Forced" with a warning triangle and points to the JavaScript line that caused the forced reflow. In the Summary tab, the "Forced reflow is a likely performance bottleneck" warning appears. For automated detection: Chrome's Lighthouse flags "Avoid large layout shifts" and "Avoid forced reflows." Custom approach: use Performance Observer to monitor long tasks, then use Chrome's --enable-blink-features=LayoutInstabilityAPI to detect layout instability. For code review: search for the pattern of reading offsetWidth/clientHeight/getBoundingClientRect inside loops that also write to style properties — this is the classic thrashing signature.

Quick Reference

LAYOUT THRASHING = read ↔ write DOM in a loop

Properties that force layout (when read after a write):
  offsetWidth/Height/Top/Left, clientWidth/Height/Top/Left,
  scrollWidth/Height/Top/Left, getBoundingClientRect(),
  getComputedStyle(), focus(), scrollIntoView()

Fix patterns:
1. Read-then-Write: batch reads → batch writes
2. requestAnimationFrame: defer writes to next frame
3. FastDOM library: auto-batches reads/writes
4. CSS containment: contain: layout style
5. CSS transforms: use transform instead of top/left
   (transforms don't trigger layout, only composite)

Detection:
• Chrome Performance → purple "Layout" bars (forced)
• Lighthouse → "Avoid forced reflows" warning
• Code review → offsetWidth/clientHeight in loops

Render pipeline cost:
  JS only:              cheapest
  JS + Style:           style-only changes
  JS + Style + Layout:  geometry changes
  JS + Style + Layout + Paint: visual changes
  JS + Style + Layout + Paint + Composite: full pipeline
