# 477. gRPC in Frontend Systems

────────────────────────────────────
## 1. High-Level Explanation (Frontend Interview Level)
────────────────────────────────────

**What it is:**
**gRPC** (Google Remote Procedure Call) is a high-performance, contract-first RPC framework that uses HTTP/2 transport and Protocol Buffers (protobuf) for binary serialisation. While traditionally a backend-to-backend protocol, it's increasingly relevant to frontend engineers through **gRPC-Web** — a compatibility layer that lets browser clients call gRPC services via an Envoy proxy. Compared to REST, gRPC delivers ~30-50% smaller payloads (binary vs JSON), strict compile-time type safety via `.proto` files, and native server-streaming support.

**Why it exists:**
REST APIs suffer from three problems at scale: (1) JSON serialisation is slow and verbose, (2) API contracts are loosely enforced (OpenAPI is optional), and (3) streaming requires bolting on WebSockets or SSE. gRPC solves all three: binary protobuf is fast and compact, `.proto` files enforce contracts at compile time, and HTTP/2 framing enables native streaming. For frontend teams consuming microservice backends that already speak gRPC, going through a REST translation layer adds latency and loses type safety.

**When and where it's used:**
- Internal dashboards (Cisco network monitoring, Google Cloud Console)
- Microservice-heavy backends already using gRPC (no REST gateway needed)
- High-throughput data transfer (financial data, telemetry streams)
- Monorepo setups where frontend + backend share `.proto` definitions

**Role in large-scale applications:**
At FAANG scale, gRPC powers inter-service communication (Google uses it for virtually all internal services). gRPC-Web bridges this to the browser — the frontend gets the same type-safe, binary-efficient transport that backend services use. Netflix, Uber, and Dropbox all use gRPC extensively; their frontend teams increasingly consume gRPC directly rather than through REST wrappers.

## 2. Deep-Dive Explanation (Senior / Staff Level)
────────────────────────────────────

### **A. Architecture — How gRPC-Web Works**

```
┌──────────────────────┐         ┌──────────────────────┐         ┌──────────────────────┐
│                      │  HTTP/  │                      │  HTTP/2  │                      │
│   Browser Client     │  1.1 or│   Envoy Proxy        │  native  │   gRPC Server        │
│   (gRPC-Web)         │  HTTP/2│   (gRPC-Web filter)  │  gRPC    │   (Go/Java/Node)     │
│                      │ ──────▶│                      │ ────────▶│                      │
│  Generated TS client │        │  Translates:         │          │  Protobuf            │
│  from .proto files   │        │  - HTTP/1.1 → HTTP/2 │          │  Server handlers     │
│                      │◀────── │  - gRPC-Web framing  │◀──────── │                      │
│                      │        │    → native gRPC     │          │                      │
└──────────────────────┘        └──────────────────────┘         └──────────────────────┘
```

**Why the proxy is required:**
Browsers cannot make raw HTTP/2 frames or use gRPC's binary framing directly. The `fetch()` and `XMLHttpRequest` APIs don't expose the low-level HTTP/2 primitives that gRPC needs. The Envoy proxy (or a gRPC-Web compatible proxy) translates browser-compatible HTTP requests into full gRPC binary calls.

### **B. Protocol Buffers — The Contract**

```protobuf
// user.proto
syntax = "proto3";

package user.v1;

// Service definition — becomes the TypeScript client interface
service UserService {
  // Unary: request → response
  rpc GetUser (GetUserRequest) returns (User);
  
  // Server streaming: request → stream of responses
  rpc ListUsers (ListUsersRequest) returns (stream User);
  
  // Client streaming (NOT supported in gRPC-Web)
  rpc UploadAvatar (stream AvatarChunk) returns (UploadResponse);
  
  // Bidirectional streaming (NOT supported in gRPC-Web)
  rpc Chat (stream ChatMessage) returns (stream ChatMessage);
}

message GetUserRequest {
  string id = 1;          // Field number 1 in binary encoding
}

message ListUsersRequest {
  int32 page_size = 1;
  string page_token = 2;
  UserFilter filter = 3;
}

message UserFilter {
  string department = 1;
  UserRole role = 2;
}

enum UserRole {
  USER_ROLE_UNSPECIFIED = 0;
  USER_ROLE_ADMIN = 1;
  USER_ROLE_MEMBER = 2;
  USER_ROLE_VIEWER = 3;
}

message User {
  string id = 1;
  string name = 2;
  string email = 3;
  UserRole role = 4;
  google.protobuf.Timestamp created_at = 5;
  repeated string tags = 6;
}
```

### **C. Generated TypeScript Client Usage**

```typescript
// Auto-generated by protoc-gen-ts (or buf generate)
// DO NOT EDIT — regenerated from user.proto

// ──── Unary call ────
import { UserServiceClient } from './generated/user_grpc_web_pb';
import { GetUserRequest, User } from './generated/user_pb';
import { grpc } from '@improbable-eng/grpc-web';

const client = new UserServiceClient('https://api.example.com', {
  transport: grpc.WebsocketTransport(),  // or grpc.CrossBrowserHttpTransport
});

// Type-safe request creation
const request = new GetUserRequest();
request.setId('user-123');

// Unary call — request → single response
client.getUser(request, new grpc.Metadata(), (err, response) => {
  if (err) {
    console.error(`gRPC error: ${err.code} - ${err.message}`);
    return;
  }
  
  // response is fully typed — change server return type and TS compiler flags it
  console.log(response.getName());   // string
  console.log(response.getEmail());  // string
  console.log(response.getRole());   // UserRole enum
  console.log(response.getTagsList()); // string[]
});

// ──── Server streaming ────
const listRequest = new ListUsersRequest();
listRequest.setPageSize(50);

const stream = client.listUsers(listRequest);

stream.on('data', (user: User) => {
  console.log(`Received user: ${user.getName()}`);
  appendUserToUI(user);
});

stream.on('status', (status: grpc.Code) => {
  if (status.code !== grpc.Code.OK) {
    console.error(`Stream error: ${status.details}`);
  }
});

stream.on('end', () => {
  console.log('Stream complete');
});

// Cancel stream (e.g., user navigates away)
stream.cancel();
```

### **D. Modern Approach — Connect-Web (Buf)**

```typescript
// connect-web — modern alternative to grpc-web
// Smaller bundle, better DX, supports both gRPC-Web and Connect protocol
import { createPromiseClient } from '@connectrpc/connect';
import { createGrpcWebTransport } from '@connectrpc/connect-web';
import { UserService } from './generated/user_connect';

const transport = createGrpcWebTransport({
  baseUrl: 'https://api.example.com',
});

const client = createPromiseClient(UserService, transport);

// ──── Unary — async/await (much cleaner than callbacks) ────
async function getUser(id: string) {
  try {
    const user = await client.getUser({ id });
    // user is fully typed from .proto definition
    console.log(user.name, user.email, user.role);
    return user;
  } catch (err) {
    // ConnectError with gRPC status codes
    if (err instanceof ConnectError) {
      if (err.code === Code.NotFound) {
        console.log('User not found');
      }
    }
    throw err;
  }
}

// ──── Server streaming — async iterator ────
async function listUsers() {
  const stream = client.listUsers({ pageSize: 50 });
  
  for await (const user of stream) {
    console.log(`${user.name} — ${user.email}`);
    appendUserToUI(user);
  }
}

// ──── React Query integration ────
import { useQuery } from '@tanstack/react-query';

function useUser(id: string) {
  return useQuery({
    queryKey: ['user', id],
    queryFn: () => client.getUser({ id }),
    // Response is automatically typed as User
  });
}

function UserProfile({ id }: { id: string }) {
  const { data: user, isLoading, error } = useUser(id);
  
  if (isLoading) return <Skeleton />;
  if (error) return <ErrorBanner error={error} />;
  
  return (
    <div>
      <h1>{user.name}</h1>
      <p>{user.email}</p>
      <Badge role={user.role} />
    </div>
  );
}
```

### **E. gRPC Communication Patterns**

| **Pattern** | **Browser (gRPC-Web)** | **Use Case** | **Alternative if Unsupported** |
|-------------|----------------------|--------------|-------------------------------|
| **Unary** (1 req → 1 res) | ✅ Fully supported | Standard CRUD, data fetching | — |
| **Server streaming** (1 req → N res) | ✅ Supported | Live feeds, log tailing, search results | SSE as fallback |
| **Client streaming** (N req → 1 res) | ❌ Not supported | File upload chunks | REST multipart or tus protocol |
| **Bidirectional streaming** (N ↔ N) | ❌ Not supported | Chat, collaboration | WebSocket |

### **F. Comparison: REST vs GraphQL vs gRPC-Web vs tRPC**

| **Aspect** | **REST** | **GraphQL** | **gRPC-Web** | **tRPC** |
|------------|----------|-------------|--------------|----------|
| **Serialisation** | JSON (text) | JSON (text) | Protobuf (binary) | JSON (text) |
| **Payload size** | Large | Medium (no over-fetching) | Small (~30-50% of JSON) | Large |
| **Contract** | OpenAPI (optional) | Schema (required) | .proto (required) | TypeScript (inferred) |
| **Code generation** | Optional (openapi-codegen) | Optional (graphql-codegen) | Required (protoc / buf) | None (inference) |
| **Type safety** | Weak (runtime) | Medium (schema) | Strong (compile-time) | Strongest (same language) |
| **Streaming** | SSE / WebSocket | Subscriptions | Native server streaming | None |
| **Browser support** | Full (native fetch) | Full (fetch + library) | Via Envoy proxy | Full (fetch) |
| **Backend language** | Any | Any | Any (.proto is language-agnostic) | TypeScript only |
| **Infrastructure** | Standard | Standard | Needs Envoy proxy | Standard |
| **Learning curve** | Low | Medium | High | Low (if already TS) |
| **Cache-friendly** | ✅ (HTTP caching) | ❌ (POST requests) | ❌ (binary, POST) | ❌ (POST-based) |
| **Best for** | Public APIs, simple apps | Flexible queries, BFF | Internal high-throughput, polyglot | Full-stack TS monorepo |


### **H. Production Considerations**

#### **Error Handling**

```typescript
import { ConnectError, Code } from '@connectrpc/connect';

async function safeGetUser(id: string) {
  try {
    return await client.getUser({ id });
  } catch (err) {
    if (err instanceof ConnectError) {
      switch (err.code) {
        case Code.NotFound:
          return null;  // Expected — user doesn't exist
        case Code.PermissionDenied:
          redirectToLogin();
          return null;
        case Code.Unavailable:
          // Server down — show retry UI
          showRetryBanner();
          return null;
        case Code.DeadlineExceeded:
          // Timeout — try again
          return safeGetUser(id);
        default:
          // Unknown error — report to Sentry
          captureException(err);
          throw err;
      }
    }
    throw err;
  }
}
```

#### **Interceptors (Middleware)**

```typescript
import { Interceptor } from '@connectrpc/connect';

// Auth interceptor — adds JWT to every request
const authInterceptor: Interceptor = (next) => async (req) => {
  const token = getAuthToken();
  if (token) {
    req.header.set('Authorization', `Bearer ${token}`);
  }
  
  try {
    return await next(req);
  } catch (err) {
    if (err instanceof ConnectError && err.code === Code.Unauthenticated) {
      await refreshToken();
      req.header.set('Authorization', `Bearer ${getAuthToken()}`);
      return next(req);
    }
    throw err;
  }
};

// Logging interceptor
const loggingInterceptor: Interceptor = (next) => async (req) => {
  const start = performance.now();
  console.log(`→ ${req.method.name}`);
  
  const response = await next(req);
  
  const duration = performance.now() - start;
  console.log(`← ${req.method.name} (${duration.toFixed(1)}ms)`);
  
  return response;
};

// Apply interceptors
const transport = createGrpcWebTransport({
  baseUrl: 'https://api.example.com',
  interceptors: [authInterceptor, loggingInterceptor],
});
```

### **I. When to Use gRPC in Frontend**

**✅ Good fit:**
- Backend is already gRPC (no REST translation layer needed)
- High-throughput binary data (metrics, telemetry, financial data)
- Need strict compile-time type safety across frontend/backend boundary
- Server streaming for real-time data (log viewer, live metrics)
- Polyglot backend (Go + Java + Python all speak gRPC natively)

**❌ Poor fit:**
- Public-facing APIs (REST is universally understood, cacheable)
- Simple CRUD app (protobuf toolchain overhead not justified)
- Backend is TypeScript only (tRPC gives same type safety with zero overhead)
- Team lacks gRPC infrastructure (Envoy setup, protobuf CI)
- Need HTTP caching (gRPC uses POST — not cacheable by CDN)

### **J. Anti-Patterns & Pitfalls**

1. **Using gRPC-Web without a proxy** → Browsers can't speak native gRPC. Always deploy Envoy with `envoy.filters.http.grpc_web` filter.
2. **Stale generated code** → Protobuf codegen MUST run in CI. Stale TypeScript clients cause runtime proto deserialization failures that TypeScript can't catch.
3. **Ignoring backward compatibility** → Removing or renumbering proto fields breaks old clients. Use `buf breaking` in CI to catch this.
4. **Choosing gRPC for public APIs** → External developers expect REST + OpenAPI. gRPC adds infrastructure requirements (Envoy proxy) that external consumers can't control.
5. **Not handling gRPC status codes** → gRPC has its own status code system (NOT HTTP status codes). `Code.Unavailable` ≠ 503. Map them explicitly.
6. **Large unary payloads** → gRPC messages have a default 4MB size limit. For large data, use server streaming to chunk responses.

## 3. Clear Real-World Examples
────────────────────────────────────

### **Example 1: Google Cloud Console**
Google's Cloud Console uses gRPC-Web to communicate with all Google Cloud services. The `.proto` files define every API surface. The browser-based dashboard gets the same type-safe, binary-efficient transport as `gcloud` CLI. Server streaming powers live log tailing in Cloud Logging.

### **Example 2: Cisco Network Monitoring**
Cisco's internal dashboards consume gRPC streams from network telemetry services. Each switch/router pushes metrics via gRPC streaming → Envoy proxy → gRPC-Web → React dashboard. Binary protobuf is critical here — JSON encoding of million-point telemetry data would be 3x larger and 5x slower to parse.

### **Example 3: Hruday @ SAP / Bosch Context**
At Bosch, the WebSocket dashboard could have used gRPC server streaming as an alternative transport. gRPC-Web server streaming provides the same real-time push as WebSocket, with the addition of type-safe contracts (`.proto` defines exactly what each message looks like). At SAP, if the microservice backend spoke gRPC, the micro-frontend architecture could consume gRPC-Web directly instead of going through a BFF REST translation layer — eliminating one hop and getting compile-time contract validation.

### **Scale Evolution:**
- **1K users**: REST is fine. No need for gRPC complexity.
- **100K users**: If backend is microservices speaking gRPC, adding a REST gateway becomes a bottleneck. gRPC-Web eliminates the translation layer, reducing latency by 15-30ms per request.
- **10M users**: Binary protobuf reduces bandwidth by 30-50%. Server streaming replaces polling for real-time data. `buf breaking` in CI prevents API contract violations across hundreds of frontend/backend teams.

## 4. Interview-Oriented Explanation
────────────────────────────────────

### **Sample Answer (7+ years level):**

> *"gRPC is Google's RPC framework using HTTP/2 and Protocol Buffers. In the browser, we use gRPC-Web — a compatibility layer that sends gRPC calls through an Envoy proxy, since browsers can't make raw HTTP/2 frames.*
>
> *The advantages over REST are threefold. First, protobuf is binary — payloads are 30-50% smaller than JSON and faster to parse. Second, .proto files enforce contracts at compile time — change a server field type and the TypeScript compiler immediately flags every broken client call. Third, native server streaming — for live metrics or log tailing, the server pushes data through a single HTTP/2 connection, no WebSocket needed.*
>
> *The trade-offs: you need an Envoy proxy (infrastructure cost), a protobuf build pipeline (CI complexity), and gRPC-Web only supports unary and server streaming — not client or bidirectional streaming. For those, you still need WebSocket.*
>
> *I'd use gRPC-Web when the backend is already gRPC-native and the frontend needs type-safe, high-throughput communication — internal dashboards, monitoring tools. For public APIs, I'd stick with REST for cacheability and universal tooling. For a full-stack TypeScript monorepo, tRPC gives the same type safety with zero protobuf overhead."*

### **Likely Follow-up Questions:**

1. **"Why can't browsers use native gRPC?"** → The browser's `fetch()` API doesn't expose HTTP/2 framing primitives. gRPC requires low-level control over HTTP/2 streams that browsers don't provide. The Envoy proxy translates gRPC-Web's browser-compatible framing into native gRPC.

2. **"How does protobuf compare to JSON in size and speed?"** → Protobuf is typically 30-50% smaller (binary vs text). Parsing is ~5x faster because protobuf uses field numbers (not string keys) and doesn't need JSON parsing. For a 1KB JSON payload, protobuf equivalent is ~600 bytes.

3. **"When would you choose gRPC-Web over tRPC?"** → When the backend isn't TypeScript. tRPC requires both frontend and backend to be TypeScript in a shared monorepo. gRPC works with any language — Go, Java, Python, Rust. If the backend team uses Go, gRPC-Web is the type-safe option.

4. **"How do you handle streaming in the browser with gRPC?"** → Server streaming works natively in gRPC-Web. For bidirectional streaming, gRPC-Web can't help — fall back to WebSocket or consider the newer WebTransport API. Some teams use gRPC for data fetching and WebSocket for real-time bidirectional communication.

5. **"What about caching?"** → gRPC uses POST requests (binary body) — HTTP caching doesn't work. For cacheable data, either use REST, or implement application-level caching (React Query / TanStack Query wrapping gRPC calls).

6. **"How do you ensure proto changes don't break the frontend?"** → Run `buf breaking --against main` in CI. This detects backward-incompatible changes (removed fields, type changes, renumbered fields) before they reach production.

## 6. Why & How Summary
────────────────────────────────────

### **Why It Matters**
- **Performance**: 30-50% smaller payloads, faster serialization. Critical for high-throughput dashboards.
- **Type safety**: .proto contracts catch API drift at compile time. No runtime "field name changed" bugs.
- **Streaming**: Native server streaming replaces polling/SSE for real-time data.
- **Microservice interop**: Frontend speaks the same protocol as backend services — no REST translation layer.

### **How It Works**
`.proto` files define service contracts → `protoc` (or `buf generate`) produces TypeScript client stubs → Browser gRPC-Web client sends requests through an Envoy proxy → Proxy translates gRPC-Web framing to native gRPC over HTTP/2 → Backend gRPC server processes the request and returns protobuf-encoded responses.

### **Company Relevance**
- **Cisco** — Internal network monitoring dashboards consume gRPC telemetry streams directly. Binary efficiency matters for high-frequency metrics.
- **Microsoft** — Azure services expose gRPC endpoints. VS Code Remote uses gRPC for extension host communication. Teams backend is microservices.
- **Adobe** — Internal pipeline tools and Creative Cloud developer platform use gRPC for high-throughput asset processing APIs.
- **Salesforce** — Less directly relevant (Apex/REST-centric), but showing awareness of gRPC demonstrates breadth. Salesforce's internal platform services (Hyperforce) use gRPC.
