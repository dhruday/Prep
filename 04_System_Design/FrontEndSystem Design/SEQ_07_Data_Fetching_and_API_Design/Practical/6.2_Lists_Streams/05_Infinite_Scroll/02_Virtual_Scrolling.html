Why Virtual Scrolling?

Rendering 10,000 DOM elements kills performance. Virtual scrolling renders only the ~20 items visible in the viewport, creating a spacer element to simulate full scroll height.

// Core idea: only render visible window
const ITEM_HEIGHT = 40;          // fixed row height
const VIEWPORT_HEIGHT = 400;     // visible area
const TOTAL_ITEMS = 10000;
const OVERSCAN = 5;             // extra items above/below

// Total scrollable height (the spacer)
spacer.style.height = TOTAL_ITEMS * ITEM_HEIGHT + 'px';

viewport.addEventListener('scroll', () => {
  const scrollTop = viewport.scrollTop;
  const startIdx = Math.floor(scrollTop / ITEM_HEIGHT) - OVERSCAN;
  const endIdx = startIdx + Math.ceil(VIEWPORT_HEIGHT / ITEM_HEIGHT) + OVERSCAN * 2;
  renderItems(Math.max(0, startIdx), Math.min(TOTAL_ITEMS, endIdx));
});
Key insight: A spacer <div> with height = totalItems × itemHeight creates the scrollbar. A positioned window renders only visible rows, translated to their correct Y offset.

How TanStack Virtual Works

// TanStack Virtual (formerly react-virtual) pipeline:

// 1. MEASURE — determine item sizes
//    Fixed: all items same height (fastest)
//    Variable: measureElement() with ResizeObserver

// 2. VIRTUALIZE — calculate visible range
const virtualizer = useVirtualizer({
  count: items.length,
  getScrollElement: () => parentRef.current,
  estimateSize: () => 40,   // estimated row height
  overscan: 5,              // extra items to render
});

// 3. RENDER — only visible items
virtualizer.getVirtualItems().map(vItem => (
  <div style={{
    position: 'absolute',
    top: 0,
    transform: `translateY(${vItem.start}px)`,
    height: vItem.size
  }} />
))

Overscan Strategy

Overscan renders extra rows above and below the visible window. This prevents blank flashes during fast scrolling. Typical overscan: 3–5 items. Too high defeats the purpose of virtualization.

Variable-height items: Use measureElement callback + ResizeObserver. TanStack Virtual maintains a size cache and recalculates offsets when sizes change.

Q: When is virtual scrolling necessary?

Rule of thumb: Beyond ~500-1000 DOM elements, rendering becomes sluggish (especially with complex row components). At 5,000+ items, browsers may freeze during initial render.

Signals you need it:
• First Contentful Paint > 2s due to list rendering
• Scrolling jank (frames dropping below 60fps)
• Memory usage growing linearly with list size
• Mobile devices struggling with the list

When NOT to use: Simple lists under 200 items, items that need to be searchable by Ctrl+F (virtual items are not in DOM), accessibility-critical lists where all items must be screen-reader accessible.
