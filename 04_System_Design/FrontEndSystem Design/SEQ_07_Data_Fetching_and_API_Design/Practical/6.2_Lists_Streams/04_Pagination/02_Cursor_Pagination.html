How Cursor Pagination Works

Instead of skipping N rows, the server uses a cursor — an opaque token that encodes the position of the last seen item.

-- Traditional offset (slow at depth):
SELECT * FROM items ORDER BY id LIMIT 10 OFFSET 10000;

-- Cursor-based (O(1) regardless of position):
SELECT * FROM items
WHERE id > 10000   -- cursor decoded to last_id
ORDER BY id
LIMIT 10;

Cursor Encoding

Cursors are typically base64-encoded to be opaque to clients:

// Server creates cursor
const cursor = btoa(JSON.stringify({ id: 1050 }));
// → "eyJpZCI6MTA1MH0="

// Server decodes cursor
const decoded = JSON.parse(atob(cursor));
// → { id: 1050 }

// Then: WHERE id > 1050 LIMIT 10
Opaque cursors let the server change the underlying encoding without breaking clients.

Response Shape

B-Tree Index Seek — O(1) Lookup

When the query uses WHERE id > cursor, the database performs an index seek, not a scan.

-- B-Tree for "id" column:
--
--        [500]
--       /     \
--    [250]   [750]
--    / \     / \
--  [100][400][600][900]
--
-- WHERE id > 600: seek to 600 in O(log N), scan forward 10
-- Total: O(log N + limit) ≈ O(1) for fixed limit

Keyset Condition Internals

-- The cursor WHERE clause enables index-only access:
EXPLAIN ANALYZE
SELECT * FROM items
WHERE id > 50000
ORDER BY id LIMIT 10;

-- → Index Scan using items_pkey
--   Index Cond: (id > 50000)
--   Rows: 10
--   Time: 0.04ms  ← constant regardless of position!
Offset: O(offset + limit) — scans all skipped rows
Cursor: O(log N + limit) — seeks directly via B-tree

Why Twitter/Instagram Use Cursors

  • Billions of tweets/posts — offset would scan millions of rows
  • Real-time inserts — 6,000+ tweets/sec; offset causes ghost records
  • Infinite scroll UX — "Load more" maps perfectly to cursors
  • Consistent reads — cursor guarantees no duplicates/skips

Interview Key Points

✅ O(1) seek via B-tree index — scales to billions of rows
✅ No ghost records — cursor is a stable pointer
❌ Cannot jump to arbitrary page N
❌ Only forward/backward traversal
