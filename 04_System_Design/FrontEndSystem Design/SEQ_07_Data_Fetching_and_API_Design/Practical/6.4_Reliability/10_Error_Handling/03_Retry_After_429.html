429 Too Many Requests

The server sets Retry-After header (seconds or HTTP-date) telling the client exactly how long to wait before the next request.

Always prefer the server's Retry-After over your own backoff — the server knows its capacity best.

Header Format

HTTP/1.1 429 Too Many Requests
Retry-After: 5          ← seconds
Retry-After: Thu, 01 Jan 2026 00:00:00 GMT  ← date

Burst 6 Requests (limit = 3)

Sends 6 sequential requests to /api/unreliable/rate-limited?max=3. After hitting the limit, reads Retry-After, shows countdown, then resumes.

Browser Behavior on 429

• Browsers do not auto-retry on 429 — the app must handle it.
• fetch() resolves normally; check res.status === 429.
• The Retry-After header is accessible via res.headers.get('Retry-After').

Rate-Limit Headers (Common)

X-RateLimit-Limit: 100       ← max per window
X-RateLimit-Remaining: 0     ← left in window
X-RateLimit-Reset: 1700000000← epoch reset time
Retry-After: 5               ← wait seconds

Q: Should you use Retry-After or your own backoff?

Prefer Retry-After when present — the server knows its capacity. Fall back to exponential backoff only if the header is missing.

Q: How do you prevent 429 in the first place?

Client-side rate limiting (token bucket / leaky bucket), request batching, and caching reduce outbound request rate below the server's threshold.

Q: What's the difference between 429 and 503?

429 = client sending too fast (rate-limit). 503 = server overloaded/down (capacity). Both are transient & retryable, but 429 is client-triggered.
