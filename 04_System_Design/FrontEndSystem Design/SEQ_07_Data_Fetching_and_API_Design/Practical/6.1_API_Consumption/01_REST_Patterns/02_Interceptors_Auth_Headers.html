Request Interceptors

Interceptors sit between your application code and the network layer. Request interceptors modify outgoing requests before they hit fetch():

  • Inject Authorization: Bearer <token> header
  • Add X-Request-ID (correlation ID) for distributed tracing
  • Stamp X-Request-Timestamp for timing measurement

Response Interceptors

Response interceptors process responses before your app sees them:

  • Check for 401 → trigger token refresh → replay request
  • Unwrap data envelopes: { data, meta } → return just data
  • Log timing: compare X-Request-Timestamp with now

Interceptor Pipeline Flow

Request→Auth Interceptor→ Logging Interceptor→fetch()→ Response Logger→Error Transformer→Result

Pipeline Pattern (reduce/compose)

function createClient(interceptors) {
  return async (url, options = {}) => {
    // Apply request interceptors (left to right)
    let config = { url, ...options };
    for (const i of interceptors) {
      if (i.request) config = await i.request(config);
    }
    let response = await fetch(config.url, config);
    // Apply response interceptors (right to left)
    for (const i of [...interceptors].reverse()) {
      if (i.response) response = await i.response(response, config);
    }
    return response;
  };
}

Headers API in fetch()

The Headers object is an iterable map. Some headers are forbidden and silently ignored by the browser:

// Forbidden headers (browser-controlled, cannot set via JS):
Cookie, Host, Origin, Referer, Content-Length
// You CAN set:
Authorization, X-Request-ID, Accept, Content-Type

CORS Preflight & Custom Headers

Adding Authorization or any custom header (e.g. X-Request-ID) makes the request "not simple", triggering an OPTIONS preflight:

OPTIONS /api/products→Server checks CORS→ 204 OK + Access-Control-Allow-Headers→Actual GET
The server responds with Access-Control-Max-Age: 86400. The browser caches the preflight result for 24 hours, so subsequent requests skip the OPTIONS call.

Preflight Caching

// Server CORS response headers:
Access-Control-Allow-Origin: *
Access-Control-Allow-Headers: Authorization, X-Request-ID
Access-Control-Max-Age: 86400 // cache preflight 24h

Q: How do you handle token refresh in interceptors?

When a 401 is received: (1) Queue all pending requests. (2) Call the refresh-token endpoint. (3) On success, update the stored token and replay all queued requests with the new token. (4) On failure, redirect to login.

Q: What's the difference between request and response interceptors?

Request interceptors modify outgoing config (headers, body, URL) before the network call. Response interceptors transform or inspect the returned response (unwrap envelopes, handle errors, log timing). They run in reverse order for a clean pipeline.

Q: How do you prevent infinite loops in auth refresh interceptors?

Use a flag like _isRetry: true on the config object. If a 401 response comes from a request already marked _isRetry, do NOT attempt another refresh — instead, reject immediately and redirect to login. Also, use a single shared Promise for concurrent refresh attempts (mutex pattern).

Q: How do interceptors in Axios differ from a custom fetch wrapper?

Axios provides a built-in axios.interceptors.request.use() / response.use() API with eject support. A custom fetch wrapper gives more control (compose, middleware pattern) but requires manual implementation of features like automatic JSON parsing, timeout, and request cancellation that Axios includes out-of-the-box.
