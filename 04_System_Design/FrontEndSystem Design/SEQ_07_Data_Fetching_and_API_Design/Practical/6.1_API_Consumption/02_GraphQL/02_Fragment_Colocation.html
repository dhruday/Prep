📐 What is Fragment Colocation?

Each component declares exactly what data it needs as a GraphQL fragment, colocated next to the component code. The parent page composes fragments into one query.

UserAvatar.fragment+ PostCard.fragment+ CommentList.fragment= PageQuery

❌ Without Colocation

// Parent fetches everything — components silently depend on shape
const GET_PAGE = gql`
  query { user(id:1) { id name email avatar bio phone posts { id title body createdAt comments { id body author { name } } } } }
`;
// If PostCard stops using `createdAt`, nobody removes it → over-fetching
// If CommentList needs `author.avatar`, parent must know → tight coupling

✅ With Colocation

// UserAvatar.tsx — owns its data needs
export const USER_AVATAR_FRAGMENT = gql`
  fragment UserAvatarFields on User { id name avatar }
`;

// PostCard.tsx — owns its data needs
export const POST_CARD_FRAGMENT = gql`
  fragment PostCardFields on Post { id title body }
`;

// Page.tsx — composes fragments
const PAGE_QUERY = gql`
  query ProfilePage($id: ID!) {
    user(id: $id) { ...UserAvatarFields posts { ...PostCardFields } }
  }
  ${USER_AVATAR_FRAGMENT}
  ${POST_CARD_FRAGMENT}
`;

🔗 Fragment Spread Mechanics

// Fragments get inlined at build time (Relay compiler / GraphQL codegen)

// Before compilation:
query { user(id:1) { ...UserAvatarFields } }

// After compilation (what the server sees):
query { user(id:1) { id name avatar } }

// Duplicate fields across fragments are deduplicated:
fragment A on User { id name }
fragment B on User { id email }
// Merged: { id name email } — `id` appears once

🛡️ Fragment Masking (Relay-style)

Relay hides parent data from child components. PostCard can ONLY access fields in its own fragment — even if the parent fetched user.email. This enforces strict data boundaries.
// Relay useFragment — component only sees its own fields
function PostCard({ post }) {
  const data = useFragment(POST_CARD_FRAGMENT, post);
  // data.title ✅ data.body ✅
  // data.createdAt ❌ — not in fragment, even if fetched
}

💬 "Why colocate fragments with components?"

Benefits: 1) Components own their data contract 2) Removing a component auto-removes its fields 3) Adding a field = edit one file 4) TypeScript types auto-generated per fragment 5) No over-fetching — each component declares minimum needs.
Risk without it: "God queries" in parent pages that nobody dares touch. Dead fields accumulate. One developer's change breaks another component silently.

💬 "How do fragments prevent over-fetching?"

// Scenario: PostCard redesign removes "body" preview

// With colocation:
// 1. Dev edits PostCard.fragment → removes `body`
// 2. Composed query auto-excludes `body`
// 3. Codegen updates types → build error if `body` still used

// Without colocation:
// 1. Dev removes body from JSX… but forgets the query
// 2. `body` still fetched → transferred but never rendered
// 3. Over-fetching grows silently over months

💬 "Fragment vs inline selection — when no fragment?"

Skip fragments for: leaf components with 1-2 fields, one-off admin pages, prototyping. Use fragments when: component is reused, team > 2 developers, data shape may evolve, you want typed props from codegen.
