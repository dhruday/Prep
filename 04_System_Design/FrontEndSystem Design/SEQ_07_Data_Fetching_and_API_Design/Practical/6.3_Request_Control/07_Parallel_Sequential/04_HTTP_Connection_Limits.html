The 6-Connection Limit

Browsers enforce a maximum of 6 simultaneous TCP connections per origin (HTTP/1.1). If you fire 12 requests, only 6 start immediately — the remaining 6 are queued and wait for a connection to free up.

This limit exists in Chrome, Firefox, Safari, and Edge. It applies per origin (scheme + host + port).

HTTP/1.1 vs HTTP/2

// HTTP/1.1: 6 parallel TCP connections per origin
//   → 12 requests = 2 batches of 6
//   → Queuing delay for requests 7-12

// HTTP/2: 1 TCP connection, multiplexed streams
//   → 12 requests = all on 1 connection
//   → No queuing (but server may limit concurrency)
Our localhost server uses HTTP/1.1, so you'll see the 6-connection limit clearly in the waterfall.

Workarounds (Historical)

Domain sharding: split assets across img1.cdn.com, img2.cdn.com to get 6 connections each. Now obsolete with HTTP/2.
Bundling: combine multiple resources into one request. Still relevant for reducing total requests.
Priority hints: fetchpriority="high" to reorder the queue.

Network Stack Queue

When you call fetch(), the request enters the browser's network service:

1. Request enters the pending queue per origin.
2. If fewer than 6 connections are active, a TCP socket is allocated immediately.
3. If 6 are in use, the request waits in the queue (shown as "Queueing" in DevTools).
4. When a connection completes, the next queued request gets that socket.

DevTools Evidence

In the Network tab waterfall, queued requests show a gray bar (Queueing) before the green TTFB bar. Requests 7+ will have visible queueing time.

Chrome DevTools → Network → right-click header → enable "Connection ID" column to see which requests share TCP connections.

HTTP/2 Multiplexing

HTTP/2 uses a single TCP connection with multiplexed streams. Each request/response is a stream — no head-of-line blocking at the HTTP level. The 6-connection browser limit doesn't apply.

HTTP/2 has its own concurrency limit: SETTINGS_MAX_CONCURRENT_STREAMS (server-configured, typically 100-256). Exceeding it still causes queueing.

Q: Why do browsers limit connections per origin?

A: To prevent a single page from overwhelming a server and to be a good network citizen. The HTTP/1.1 spec recommended 2 connections; browsers relaxed it to 6. It also limits resource consumption on the client (each TCP connection uses memory and kernel resources).

Q: How does HTTP/2 solve the connection limit problem?

A: HTTP/2 multiplexes multiple streams over a single TCP connection. Hundreds of requests can be in-flight simultaneously without the 6-connection limit. However, TCP-level head-of-line blocking remains — a dropped packet stalls all streams (solved by HTTP/3 + QUIC).

Q: What is domain sharding and is it still relevant?

A: Splitting resources across subdomains (img1.cdn.com, img2.cdn.com) to get 6 connections per subdomain. It was a key optimization for HTTP/1.1 but is anti-pattern for HTTP/2 — it prevents multiplexing and wastes connections.

Q: If I fire 100 fetch() calls, what happens?

A: All 100 promises are created instantly (JS is non-blocking). The browser's network layer queues them — only 6 active at a time over HTTP/1.1. As each completes, the next queued request fires. Total time ≈ (100/6) × average_request_time. Over HTTP/2, all 100 could be concurrent.
