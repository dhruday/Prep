1. The Deduplication Problem

// Scenario: 5 React components mount simultaneously
// Each calls useUser() which fetches GET /api/users/me
//
// WITHOUT deduplication:
//   Component A → fetch(/api/users/me) → Network request #1
//   Component B → fetch(/api/users/me) → Network request #2
//   Component C → fetch(/api/users/me) → Network request #3
//   Component D → fetch(/api/users/me) → Network request #4
//   Component E → fetch(/api/users/me) → Network request #5
//   Result: 5 identical requests → 5× server load, 0 UX benefit
//
// WITH deduplication:
//   Component A → fetch starts → Network request #1
//   Component B → joins in-flight promise ────┘
//   Component C → joins in-flight promise ────┘
//   Component D → joins in-flight promise ────┘
//   Component E → joins in-flight promise ────┘
//   Result: 1 request → all 5 components get the same data

2. Two Levels of Deduplication

// Level 1: IN-FLIGHT deduplication (request coalescing)
// → Multiple callers during the SAME request share ONE network call
// → Promise is the dedup mechanism — all callers await same promise
// → Cleaned up when promise resolves/rejects
//
// Level 2: CACHE deduplication (stale-while-revalidate)
// → Data that was fetched recently is served from cache
// → No network call at all if data is "fresh" (within staleTime)
// → Cache has TTL; expired entries trigger new fetch
//
// React Query provides BOTH levels automatically:
// - Same queryKey during in-flight fetch → promise shared (Level 1)
// - Same queryKey within staleTime → cache hit, no fetch (Level 2)
// - Same queryKey after staleTime → background refetch (SWR)

3. How React Query Deduplicates Internally

// Simplified internal mechanism:

class QueryCache {
  queries = new Map();  // key → Query instance

  fetchQuery(key, fetchFn, staleTime) {
    const cacheKey = JSON.stringify(key);
    let query = this.queries.get(cacheKey);

    // Case 1: Currently fetching → return SAME promise (dedup!)
    if (query?.state === 'loading') {
      return query.promise;  // All callers share this
    }

    // Case 2: Fresh cache → return data, no network call
    if (query?.state === 'fresh' && Date.now() - query.dataUpdatedAt < staleTime) {
      return Promise.resolve(query.data);
    }

    // Case 3: Stale or missing → start new fetch
    const promise = fetchFn().then(data => {
      this.queries.set(cacheKey, {
        state: 'fresh', data, dataUpdatedAt: Date.now()
      });
      return data;
    });

    this.queries.set(cacheKey, { state: 'loading', promise });
    return promise;
  }
}

4. Cache Invalidation — The Hard Part

// "There are only two hard things in CS: cache invalidation and naming things"

// When cached data becomes stale (mutation happened):
// Option 1: Invalidate — mark cache as stale, trigger refetch
queryClient.invalidateQueries({ queryKey: ['products'] });

// Option 2: Update directly — modify cache without refetch
queryClient.setQueryData(['products', id], newProduct);

// Option 3: Optimistic update — update cache immediately, revert on error
useMutation({
  mutationFn: updateProduct,
  onMutate: async (newData) => {
    await queryClient.cancelQueries(['products', newData.id]);
    const previous = queryClient.getQueryData(['products', newData.id]);
    queryClient.setQueryData(['products', newData.id], newData);
    return { previous };
  },
  onError: (err, newData, context) => {
    queryClient.setQueryData(['products', newData.id], context.previous);
  },
});

1. Manual Promise Map Deduplicator

// When NOT using React Query — build your own dedup layer

class RequestDeduplicator {
  pending = new Map();  // key → Promise

  async dedupe(key, fetchFn) {
    // If same request is already in-flight → return same promise
    if (this.pending.has(key)) {
      return this.pending.get(key);
    }

    // Start new request, store promise
    const promise = fetchFn().finally(() => {
      this.pending.delete(key);  // Clean up after resolve/reject
    });

    this.pending.set(key, promise);
    return promise;
  }
}

const dedup = new RequestDeduplicator();

// 10 simultaneous calls → 1 fetch request
const results = await Promise.all([
  dedup.dedupe('user:me', () => fetch('/api/users/me')),
  dedup.dedupe('user:me', () => fetch('/api/users/me')),
  dedup.dedupe('user:me', () => fetch('/api/users/me')),
]);

2. Service Worker Deduplication

// Service Worker can intercept ALL fetch calls centrally
// Even across multiple tabs!

// sw.js
const inflight = new Map();

self.addEventListener('fetch', (event) => {
  const url = event.request.url;

  // Only dedup GET requests
  if (event.request.method !== 'GET') return;

  if (inflight.has(url)) {
    // Clone the in-flight response for this requester
    event.respondWith(
      inflight.get(url).then(res => res.clone())
    );
    return;
  }

  const responsePromise = fetch(event.request).then(res => {
    inflight.delete(url);
    return res;
  });

  inflight.set(url, responsePromise);
  event.respondWith(responsePromise.then(res => res.clone()));
});
Service Worker deduplication works across tabs — if Tab A and Tab B both request /api/users/me within the same time window, only one network request fires. This is invisible to application code.

3. Dedup + Cache Two-Layer Architecture

// Layer 1: Cache (prevents fetch for fresh data)
// Layer 2: Dedup (prevents duplicate in-flight requests)

class ApiCache {
  inflight = new Map();
  cache = new Map();

  async get(key, fetcher, ttl = 60000) {
    // Level 1: Fresh cache hit → no network call
    const cached = this.cache.get(key);
    if (cached && Date.now() < cached.expiresAt) {
      return cached.data;
    }

    // Level 2: In-flight dedup → join existing request
    if (this.inflight.has(key)) {
      return this.inflight.get(key);
    }

    // Level 3: New request
    const promise = fetcher().then(data => {
      this.cache.set(key, { data, expiresAt: Date.now() + ttl });
      this.inflight.delete(key);
      return data;
    }).catch(err => {
      this.inflight.delete(key);
      throw err;
    });

    this.inflight.set(key, promise);
    return promise;
  }
}

FAANG Interview Questions

Q1: How does React Query handle request deduplication and when would you need to implement your own?
React Query deduplicates automatically at the queryKey level. When multiple useQuery hooks share the same queryKey during a render cycle, the first hook triggers the network request and subsequent hooks receive the same in-flight promise — one HTTP call serves all consumers. Combined with staleTime, cached data prevents fetches entirely for fresh data. You'd implement your own dedup when: 1) you're not using React Query (vanilla fetch, Angular, Vue), 2) you need cross-tab deduplication (Service Worker), 3) you need dedup at the network layer regardless of framework (API middleware), or 4) you need custom key generation logic beyond what queryKey provides.
Follow-up: How does React Query's dedup interact with Suspense mode?
Q2: Explain the Promise Map pattern for request deduplication.
The Promise Map pattern uses a Map<string, Promise> where the key is the request identifier (URL + params serialized) and the value is the in-flight Promise. When a request comes in, check if the Map already has an entry for that key. If yes, return the existing Promise (all callers await the same one). If no, start the fetch, store the Promise in the Map, and clean up with .finally() when it resolves. The critical detail is the .finally() cleanup — without it, the Map grows indefinitely. Also, errors should NOT be cached in the Map — if a request fails, the next caller should try again, not get the cached rejection.
Follow-up: How would you handle deduplication for POST requests?
Q3: How can a Service Worker deduplicate requests across browser tabs?
A Service Worker intercepts all fetch events from every tab in its scope. By maintaining an in-flight Map inside the Service Worker, when Tab A requests /api/users/me and Tab B requests the same URL 50ms later, the Service Worker returns a clone of Tab A's in-flight response to Tab B. This is transparent to application code — both tabs think they made independent requests. The key is using response.clone() because a Response body can only be consumed once. Limitations: only works for GET requests, doesn't handle POST dedup, and the Service Worker must be registered and active before the requests fire.
Follow-up: What happens if the Service Worker crashes while requests are in-flight?
Q4: What's the relationship between deduplication and caching?
They're complementary but solve different problems. Deduplication prevents duplicate in-flight requests — it only matters when the same request fires multiple times simultaneously. Caching prevents unnecessary requests by serving previously-fetched data. Think of it as: cache = "I already have this data," dedup = "I'm already fetching this data." In a well-designed system, the check order is: 1) Is data in cache and fresh? → return (no network call). 2) Is the same request already in-flight? → join (one network call). 3) Neither → start new request. React Query handles both levels automatically with queryKey + staleTime. Without a library, you build both layers yourself.
Follow-up: How does stale-while-revalidate fit into this picture?

2. Full Dedup + Cache + TTL Utility

class SmartFetcher {
  constructor() {
    this.cache = new Map();
    this.inflight = new Map();
  }

  key(url, params) {
    return url + '?' + new URLSearchParams(params).toString();
  }

  async fetch(url, params = {}, ttl = 30000) {
    const k = this.key(url, params);

    // 1. Cache hit
    const cached = this.cache.get(k);
    if (cached && Date.now() < cached.exp) return cached.data;

    // 2. Dedup — join in-flight
    if (this.inflight.has(k)) return this.inflight.get(k);

    // 3. New request
    const p = fetch(`${url}?${new URLSearchParams(params)}`)
      .then(r => r.json())
      .then(data => {
        this.cache.set(k, { data, exp: Date.now() + ttl });
        this.inflight.delete(k);
        return data;
      })
      .catch(err => { this.inflight.delete(k); throw err; });

    this.inflight.set(k, p);
    return p;
  }

  invalidate(url, params) {
    this.cache.delete(this.key(url, params));
  }
}

Key Lifecycle

Request arrives
  │
  ├─ Cache fresh? → Return cached data (no network)
  │
  ├─ In-flight for same key? → Return same Promise (dedup)
  │
  └─ Neither → Start fetch
       │
       ├─ Store Promise in inflight Map
       │
       ├─ On resolve → Store in cache, delete from inflight
       │
       └─ On reject → Delete from inflight (don't cache errors)

Production Checklist

✅ Use React Query/SWR — built-in dedup + cache + SWR
✅ Key generation must be deterministic (same input → same key)
✅ NEVER cache error responses in the dedup layer
✅ Use .finally() to clean up inflight Map entries
✅ Set appropriate staleTime (not just cacheTime)
✅ Only dedup GET requests (never POST/PUT/DELETE)
✅ Consider Service Worker for cross-tab dedup
✅ Invalidate cache after mutations (queryClient.invalidateQueries)
✅ Use response.clone() in Service Worker (body can only be read once)
✅ Monitor cache hit rates (are we actually saving requests?)
