1. The Latency Problem

// Without optimistic update (pessimistic):
// User clicks "Like" → [spinner 200-2000ms] → UI updates
// Perceived latency: 200-2000ms

// With optimistic update:
// User clicks "Like" → UI updates IMMEDIATELY → [API call in background]
// Perceived latency: ~0ms

// Research: Users perceive delays > 100ms as noticeable
// Jakob Nielsen's response time limits:
//   0.1s: Feels instant (optimistic territory)
//   1.0s: Flow maintained but delay noticed
//   10s:  User loses focus

// Mobile networks add 100-500ms latency overhead
// Without optimistic: every interaction feels sluggish on mobile

2. Consistency Guarantees

// Optimistic updates create TEMPORARY inconsistency:
// Client state: liked=true, count=43
// Server state: liked=false, count=42 (API not processed yet)

// Timeline:
// t=0:    Client: liked=true (optimistic)
// t=0:    API call starts
// t=200:  Server processes: liked=true, count=43
// t=400:  API response arrives → client confirms or syncs

// Failure scenarios:
// 1. Network error → rollback to liked=false, count=42
// 2. Business rule violation → rollback + show error
// 3. Conflict (someone else unliked) → server wins
// 4. Timeout → show "pending" state, retry

// Eventual consistency: client and server converge
// Strong consistency: wait for server response (pessimistic)

3. Rollback Mechanics

// Snapshot before mutation (the "undo" data):
const previousState = queryClient.getQueryData(['todos']);
// ^ Deep clone of current cache state

// Apply optimistic update:
queryClient.setQueryData(['todos'], (old) =>
  old.map(todo => todo.id === id ? {...todo, done: true} : todo)
);

// On error — rollback:
queryClient.setQueryData(['todos'], previousState);
// ^ Restores exact pre-mutation state

// Race condition: what if another query updated cache between
// our optimistic update and rollback?
// Solution: React Query's onMutate returns context
// onError receives context → precise rollback target
// Plus: onSettled triggers refetch for fresh data

4. Multi-Query Optimistic Updates

// Problem: "Like" affects MULTIPLE cached queries
// 1. Post detail: ['post', 123] → update likeCount
// 2. Feed list:   ['feed'] → update likeCount in list
// 3. User likes:  ['user-likes'] → add post to list

// All three must be optimistically updated atomically!

// Strategy: Update all affected queries in onMutate
onMutate: () => {
  const snapshots = {
    post: queryClient.getQueryData(['post', 123]),
    feed: queryClient.getQueryData(['feed']),
    likes: queryClient.getQueryData(['user-likes']),
  };
  
  // Update all three
  queryClient.setQueryData(['post', 123], ...);
  queryClient.setQueryData(['feed'], ...);
  queryClient.setQueryData(['user-likes'], ...);
  
  return snapshots; // All snapshots for rollback
}

// On error: rollback ALL three from snapshots

5. CRDT-Based Optimistic Updates

// Advanced: Use CRDTs for conflict-free concurrent updates
// G-Counter (Grow-only Counter) for likes:

// Each client has a local counter:
// Client A: likes = { A: 1, B: 0 } → total = 1
// Client B: likes = { A: 0, B: 1 } → total = 1

// After merge (max per client):
// Server:   likes = { A: 1, B: 1 } → total = 2
// No conflicts! Convergent without coordination!

// Used by: Figma (CRDT for collaborative editing)
// Google Docs (OT, not CRDT, but similar principle)
// Linear (task board drag-and-drop)

// For most apps: simple snapshot rollback is sufficient
// CRDTs are for real-time multi-user collaboration

3. Conflict Resolution Strategies

// When optimistic update conflicts with server state:

// Strategy 1: Last Write Wins (LWW)
// Server response always overwrites client state
// Simple but can lose data
onSettled: () => queryClient.invalidateQueries(['todos'])
// ^ Refetch fresh data from server after every mutation

// Strategy 2: Version Vector
// Each update has a version: { data, version: 5 }
// Server rejects if client version !== server version
// Client must refetch and re-apply

// Strategy 3: Operational Transform (Google Docs)
// Transform concurrent operations to converge
// Complex but preserves all user intentions

// Strategy 4: Server Reconciliation
// Server returns authoritative state after mutation
// Client REPLACES optimistic state with server response
onSuccess: (serverData) => {
  queryClient.setQueryData(['todos'], serverData);
}
Q1: Implement a "Like" button with optimistic update. Handle all edge cases.
See Code Walkthrough for full implementation. Key edge cases:
1. Double-click: Debounce or disable button during mutation
2. Rapid toggle: Like→Unlike→Like in 100ms — each must correctly snapshot and rollback
3. Network failure: Rollback + toast notification "Couldn't save like"
4. Server error: 409 Conflict (already liked) → sync with server state
5. Stale cache: Another user's like changed count → refetch on settle
6. Offline: Queue mutation, apply optimistically, retry when online
7. Animation: Heart animation should complete even on rollback (CSS not tied to state)
Follow-up: What if the user likes, then navigates away before API responds?
With React Query: the mutation continues in background (attached to mutation cache, not component). On return, cache reflects final state. If it failed, next visit refetches (staleTime expired). For critical mutations: use mutationKey for persistence.
Q2: How does Facebook/Meta handle optimistic updates at scale for reactions?
1. Immediate UI: Reaction appears instantly with optimistic state
2. Debounced API: If user changes reaction 3 times in 500ms, only the final one is sent
3. Request deduplication: Multiple components showing same post share one inflight mutation
4. Partial failure: Reaction saved but notification failed → reaction still shows (not atomic)
5. Counter estimation: "1.2K likes" is approximate, so ±1 optimistic change is unnoticeable
6. Conflict resolution: Server response is source of truth, overwrites on settle
7. Cross-device: WebSocket push updates counter from other devices
Follow-up: How do they handle like counts that are approximate?
Facebook uses eventual consistency for like counts. The number shown is an estimate (cached, aggregated periodically). Optimistic +1/-1 on the displayed number is fine because the base is already approximate. Exact count is never guaranteed in real-time.
Q3: Design optimistic drag-and-drop reordering for a task board (like Trello/Linear).
Architecture:
1. On drag end: immediately update local list order (optimistic)
2. Calculate new position: { id: taskId, position: newIndex, column: "in-progress" }
3. Send PATCH /api/tasks/reorder with new position
4. Snapshot entire board state before move (for rollback)

Challenges:
- Multiple users moving simultaneously → use fractional indexing (0.5 between 0 and 1) to avoid reindexing
- Rapid moves → debounce API calls, but update UI immediately each time
- Rollback on error → snap card back to original position with animation
- Cross-column moves update TWO columns optimistically

Fractional indexing: Instead of integer positions (1,2,3), use strings ("a","am","b"). Moving between "a" and "b" → "am". No need to renumber other items.
Follow-up: What is fractional indexing and how does Linear use it?
Fractional indexing uses lexicographically sortable strings as positions. Moving item between positions "a" and "b" creates position "an" (midpoint). No other items need updating. Linear uses this for their issue ordering — allows O(1) position updates without touching other rows.
Q4: When should you NOT use optimistic updates?
1. Financial transactions: $500 transfer must be confirmed by server before showing
2. Irreversible actions: Delete account, send email (can't unsend)
3. Complex validation: Server-side rules client can't replicate
4. High-conflict data: Inventory (2 users buying last item simultaneously)
5. External side effects: Triggering SMS, webhook, printing
6. Audit-critical: Medical records, legal documents — must confirm persistence
7. Low-confidence mutations: If server rejects >5% of the time, optimistic creates bad UX (frequent rollbacks)
Follow-up: What about adding to cart in e-commerce?
Adding to cart is a good optimistic candidate — it's reversible (remove from cart), low conflict (cart is per-user), and frequent. However, if inventory is limited ("only 2 left"), you might want to confirm availability first (pessimistic) to avoid "Sorry, out of stock" after user thinks they added it.
Q5: Explain the onMutate → onError → onSettled lifecycle in React Query.
Lifecycle:
1. onMutate(variables): BEFORE mutation fires. Cancel outgoing queries, snapshot cache, apply optimistic update. Return context (snapshot data).
2. mutationFn(variables): The actual API call.
3a. onSuccess(data, variables, context): Server confirmed. Update cache with server response or just let invalidation handle it.
3b. onError(error, variables, context): Server rejected. Use context to rollback. Show error toast.
4. onSettled(data, error, variables, context): ALWAYS runs (like finally). Invalidate queries to refetch fresh data. Ensures eventual consistency.

Critical: cancelQueries in onMutate prevents a background refetch from overwriting your optimistic data before the mutation responds.

1. Complete Like Button — React Query

function useLikeMutation(postId) {
  const queryClient = useQueryClient();
  
  return useMutation({
    mutationFn: () => fetch(`/api/posts/${postId}/like`, { method: 'POST' }),
    
    onMutate: async () => {
      // 1. Cancel any outgoing refetches (prevent overwrite)
      await queryClient.cancelQueries({ queryKey: ['post', postId] });
      
      // 2. Snapshot current state (for rollback)
      const previous = queryClient.getQueryData(['post', postId]);
      
      // 3. Optimistically update cache
      queryClient.setQueryData(['post', postId], (old) => ({
        ...old,
        isLiked: !old.isLiked,
        likeCount: old.isLiked ? old.likeCount - 1 : old.likeCount + 1,
      }));
      
      // 4. Return snapshot as context
      return { previous };
    },
    
    onError: (err, vars, context) => {
      // 5. Rollback on failure
      queryClient.setQueryData(['post', postId], context.previous);
      toast.error('Failed to update like');
    },
    
    onSettled: () => {
      // 6. Always refetch for ground truth
      queryClient.invalidateQueries({ queryKey: ['post', postId] });
    },
  });
}

2. Todo Toggle with Multi-Query Update

function useToggleTodo() {
  const queryClient = useQueryClient();
  
  return useMutation({
    mutationFn: ({ id, done }) =>
      fetch(`/api/todos/${id}`, {
        method: 'PATCH',
        body: JSON.stringify({ done }),
      }),
    
    onMutate: async ({ id, done }) => {
      // Cancel ALL affected queries
      await queryClient.cancelQueries({ queryKey: ['todos'] });
      
      // Snapshot both list and detail
      const prevList = queryClient.getQueryData(['todos']);
      const prevDetail = queryClient.getQueryData(['todo', id]);
      
      // Update list
      queryClient.setQueryData(['todos'], (old) =>
        old.map(t => t.id === id ? { ...t, done } : t)
      );
      
      // Update detail (if cached)
      if (prevDetail) {
        queryClient.setQueryData(['todo', id], { ...prevDetail, done });
      }
      
      return { prevList, prevDetail };
    },
    
    onError: (err, { id }, ctx) => {
      queryClient.setQueryData(['todos'], ctx.prevList);
      if (ctx.prevDetail) {
        queryClient.setQueryData(['todo', id], ctx.prevDetail);
      }
    },
    
    onSettled: () => {
      queryClient.invalidateQueries({ queryKey: ['todos'] });
    },
  });
}

3. Vanilla JS Optimistic Pattern (No Library)

class OptimisticStore {
  #state;
  #listeners = new Set();
  
  constructor(initialState) { this.#state = initialState; }
  
  getState() { return this.#state; }
  
  subscribe(fn) {
    this.#listeners.add(fn);
    return () => this.#listeners.delete(fn);
  }
  
  #notify() { this.#listeners.forEach(fn => fn(this.#state)); }
  
  async mutate(optimisticUpdate, apiCall) {
    // 1. Snapshot
    const snapshot = structuredClone(this.#state);
    
    // 2. Apply optimistic
    this.#state = optimisticUpdate(this.#state);
    this.#notify();
    
    try {
      // 3. API call
      const serverState = await apiCall();
      // 4. Reconcile with server response
      this.#state = serverState;
      this.#notify();
    } catch (err) {
      // 5. Rollback
      this.#state = snapshot;
      this.#notify();
      throw err; // Re-throw for error handling
    }
  }
}

Rollback Checklist

✅ cancelQueries before optimistic update (prevent overwrite)
✅ Snapshot ALL affected query caches (not just primary)
✅ structuredClone for deep snapshot (avoid reference issues)
✅ Return context from onMutate for onError access
✅ invalidateQueries in onSettled (always, not just onError)
✅ Show user feedback on rollback (toast, shake animation)
✅ Handle rapid mutations (each gets its own snapshot)
✅ Test with 100% failure rate to verify rollback works
