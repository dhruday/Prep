HTTP/1.1 vs HTTP/2 vs HTTP/3 — Transport Layer Deep Dive

HTTP/1.1 — The 6-Connection Bottleneck

HTTP/1.1 operates on a strict request-response model over TCP. Browsers enforce a 6 concurrent TCP connections per origin limit (Chrome, Firefox). Each connection handles one request at a time — a phenomenon called head-of-line (HOL) blocking at the HTTP layer.

// HTTP/1.1 waterfall — sequential on same connection
Connection 1: [GET /api/users ─────────] [GET /api/posts ─────────]
Connection 2: [GET /api/comments ──────] [GET /api/likes ──────────]
Connection 3: [GET /style.css ─────────] [GET /bundle.js ──────────]
Connection 4: idle...
Connection 5: idle...
Connection 6: idle...

// With 20 API calls, connections 7-20 QUEUE behind 1-6
// This is why domain sharding was a HTTP/1.1 optimization

TCP + TLS Handshake Cost per Connection:

// TCP 3-way handshake: ~1 RTT (Round Trip Time)
Client ──SYN──▶ Server          // ~50ms on typical CDN
Client ◀──SYN-ACK── Server
Client ──ACK──▶ Server

// TLS 1.2 adds 2 more RTTs
Client ──ClientHello──▶ Server
Client ◀──ServerHello+Cert── Server
Client ──KeyExchange──▶ Server
Client ◀──Finished── Server

// TLS 1.3 optimizes to 1 RTT (0-RTT for resumption)
Client ──ClientHello+KeyShare──▶ Server
Client ◀──ServerHello+Finished── Server

// Total cost per new HTTP/1.1+TLS1.2 connection: ~3 RTTs
// At 100ms RTT = 300ms before first byte even sends

HTTP/2 — Binary Framing & Multiplexing

HTTP/2 introduces a binary framing layer that breaks messages into independent frames, interleaved on a single TCP connection. Key concepts:

  • Stream: A bidirectional flow of frames within a connection (each request/response pair is a stream)
  • Frame: The smallest unit — HEADERS frame, DATA frame, PRIORITY frame, etc.
  • Multiplexing: Multiple streams share one TCP connection — no HTTP-level HOL blocking
// HTTP/2 single TCP connection — interleaved frames
┌─────────────────────────────────────────────────────┐
│ TCP Connection                                       │
│  [HEADERS stream:1] [DATA stream:3] [DATA stream:1] │
│  [HEADERS stream:5] [DATA stream:1] [DATA stream:5] │
│  [HEADERS stream:3] [DATA stream:3] [DATA stream:5] │
└─────────────────────────────────────────────────────┘

// Stream IDs: odd = client-initiated, even = server-push
// HPACK header compression eliminates redundant headers
⚠️ HTTP/2 still has TCP-level HOL blocking: if a single TCP packet is lost, ALL streams on that connection stall until retransmission. This is the fundamental problem HTTP/3 solves.

HTTP/3 — QUIC (UDP-Based Transport)

HTTP/3 replaces TCP+TLS with QUIC, which runs over UDP. Key differences:

  • Streams are independent at the transport layer — packet loss on stream 1 doesn't block stream 3
  • 0-RTT connection establishment — QUIC integrates the crypto handshake into the connection setup
  • Connection migration — identified by Connection ID, not IP:port tuple. Survives network changes (WiFi→cellular)
// HTTP/3 over QUIC — independent stream loss recovery
┌──────────────────────────────────────────┐
│ QUIC Connection (UDP)                     │
│  Stream 1: [pkt lost] ← only stream 1    │
│            waits for retransmit           │
│  Stream 3: [data flowing normally ──────] │
│  Stream 5: [data flowing normally ──────] │
└──────────────────────────────────────────┘

Richardson Maturity Model (Level 0–3)

Leonard Richardson's model classifies REST API maturity. Most production APIs are Level 2; Level 3 (HATEOAS) is rare but important for interviews.

LevelDescriptionExample
Level 0 — The Swamp of POX Single URI, single HTTP method (usually POST). RPC-style tunneling over HTTP. POST /api with {"action":"getUser","id":5}
Level 1 — Resources Individual URIs per resource, but still only POST. POST /users/5 with {"action":"get"}
Level 2 — HTTP Verbs Proper use of GET, POST, PUT, DELETE, PATCH + status codes. GET /users/5 → 200, DELETE /users/5 → 204
Level 3 — HATEOAS Responses include hypermedia links to discover API affordances dynamically. Response includes {"_links":{"self":"/users/5","orders":"/users/5/orders"}}
💡 HATEOAS (Hypermedia as the Engine of Application State): The client doesn't hardcode URIs. It discovers them from responses. GitHub API is a real-world example — the root endpoint returns links to all resources. This makes API evolution possible without breaking clients.

Idempotency of HTTP Methods

Idempotent: Making the same request N times produces the same server state as making it once. This is about server-side state, not response body.

MethodSafe?Idempotent?Why
GET✅✅No side effects — always reads
HEAD✅✅Same as GET without body
OPTIONS✅✅Metadata only
PUT❌✅Full replacement — PUT same data 10× = same state
DELETE❌✅Delete resource once or 10× = resource gone
POST❌❌Creates new resources — POST 10× = 10 resources
PATCH❌❌*Depends on operation — {"op":"replace"} is, {"op":"increment"} isn't
⚠️ PATCH idempotency is nuanced. JSON Merge Patch (RFC 7396) is idempotent since it's a partial PUT. JSON Patch (RFC 6902) with "add" or "move" operations may not be. Google interviews ask this distinction.

Conditional Requests — ETag / If-None-Match / If-Match

Conditional requests avoid transferring unchanged data and prevent lost-update problems.

Validation for Caching (If-None-Match)

// First request
GET /api/users/42
→ 200 OK
   ETag: "a1b2c3d4"
   Cache-Control: max-age=0, must-revalidate

// Subsequent request — browser sends ETag back
GET /api/users/42
If-None-Match: "a1b2c3d4"
→ 304 Not Modified  // No body transferred, use cached version

// Strong vs Weak ETags
ETag: "a1b2c3d4"        // Strong — byte-for-byte identical
ETag: W/"a1b2c3d4"      // Weak — semantically equivalent

Optimistic Concurrency (If-Match)

// Alice reads the resource
GET /api/docs/99 → ETag: "v5"

// Bob reads the same resource
GET /api/docs/99 → ETag: "v5"

// Alice updates (succeeds — ETag matches)
PUT /api/docs/99
If-Match: "v5"
→ 200 OK, ETag: "v6"

// Bob tries to update (FAILS — stale ETag)
PUT /api/docs/99
If-Match: "v5"
→ 412 Precondition Failed  // Must re-fetch and retry

Cache-Control Deep Dive

Cache-Control is the most misunderstood HTTP header. Here's what each directive actually does:

DirectiveWhere CachedBehavior
max-age=300Browser + CDNResponse is fresh for 300s. No network request during this window.
s-maxage=600CDN/proxy onlyOverrides max-age for shared caches. Browser ignores this.
no-cacheBothStore response BUT must revalidate (If-None-Match) before every use. Not "don't cache."
no-storeNeitherNever store the response anywhere. For sensitive data (bank balances).
must-revalidateBothOnce stale, MUST revalidate — cannot serve stale even if offline.
stale-while-revalidate=60BothServe stale for 60s while revalidating in background. Instant UX.
stale-if-error=300BothIf origin returns 5xx, serve stale for 300s instead of error.
privateBrowser onlyCDN/proxy must not cache. For user-specific data.
publicBothEven authenticated responses can be cached by CDN.
immutableBothNever revalidate — used for fingerprinted assets like bundle.a1b2.js.

Production Cache Strategy Pattern

// Static assets with content hash → cache forever
Cache-Control: public, max-age=31536000, immutable
// File: /static/app.c3f8a2.js

// HTML pages → always revalidate
Cache-Control: no-cache
// (stores but checks freshness via ETag every time)

// API responses → stale-while-revalidate for speed
Cache-Control: public, max-age=10, stale-while-revalidate=60
// Fresh for 10s, then serves stale for 60s while fetching

// User-specific data → private, short TTL
Cache-Control: private, max-age=0, must-revalidate
// Always revalidates, but can use 304 for bandwidth savings

// Sensitive data (auth tokens, PII) → never cache
Cache-Control: no-store
Pragma: no-cache  // HTTP/1.0 fallback
💡 stale-while-revalidate is the key to perceived performance in modern apps. The browser immediately serves the cached (possibly stale) version, then does a background fetch. React Query and SWR implement this pattern at the application layer. The HTTP-level directive does it at the browser/CDN layer.

Content Negotiation

The client and server negotiate the best representation via Accept headers:

// Client requests JSON, falls back to XML
GET /api/users/42
Accept: application/json, application/xml;q=0.9, */*;q=0.1

// Server responds with best match
200 OK
Content-Type: application/json; charset=utf-8
Vary: Accept  // CDN must cache separately per Accept value

// Language negotiation
Accept-Language: en-US, en;q=0.9, de;q=0.5

// Encoding negotiation
Accept-Encoding: br, gzip, deflate
// Server: Content-Encoding: br (Brotli — 20% smaller than gzip)
💡 The Vary header is critical for CDN caching. Vary: Accept-Encoding tells the CDN to cache gzip and br versions separately. Forgetting Vary can serve gzip content to a br-requesting client.

Backend for Frontend (BFF) Pattern

Each frontend platform (Web, iOS, Android) gets its own lightweight backend that orchestrates microservice calls, tailored to that platform's needs.

│  Web App │  │ iOS App  │  │ Android  │
└────┬─────┘  └────┬─────┘  └────┬─────┘
     │             │             │
     ▼             ▼             ▼
┌─────────┐  ┌─────────┐  ┌─────────┐
│ Web BFF │  │ iOS BFF │  │ Droid   │
│         │  │         │  │ BFF     │
└────┬────┘  └────┬────┘  └────┬────┘
     │             │             │
     └─────────────┼─────────────┘
                   ▼
          ┌────────────────┐
          │  API Gateway   │
          │  (Auth, Rate   │
          │   Limit, Log)  │
          └───────┬────────┘
                  │
     ┌────────────┼────────────┐
     ▼            ▼            ▼
┌─────────┐ ┌─────────┐ ┌─────────┐
│ User    │ │ Order   │ │ Product │
│ Service │ │ Service │ │ Service │
└─────────┘ └─────────┘ └─────────┘

Why BFF?

  • Response shaping: Web needs 20 fields, mobile needs 8. BFF filters so mobile doesn't over-fetch.
  • Orchestration: Single BFF call replaces 4 microservice calls on the client → fewer round trips.
  • Platform-specific logic: Push notification registration, WebSocket vs SSE decisions.
  • Security: Auth tokens stay server-side in the BFF. Client uses session cookies.
⚠️ Risk: BFF can become a "god service" with business logic. Keep it thin — only aggregation, transformation, and auth. Business rules stay in domain services.

FAANG Interview Q&A — Senior Engineer Level

Q1: How does HTTP/2 multiplexing work internally?
HTTP/2 introduces a binary framing layer between the socket and the HTTP semantics. Every HTTP message (request or response) is split into one or more frames — HEADERS frames carry metadata, DATA frames carry payload. Each request/response pair is assigned a stream ID (odd for client-initiated, even for server push).

On a single TCP connection, frames from different streams are interleaved. The receiver reassembles frames by stream ID. This eliminates HTTP-level HOL blocking — if stream 3's response is 2MB and stream 7's is 200 bytes, the server can interleave frames so stream 7 finishes quickly.

Key internals:
• HPACK compression: Headers are encoded via a static table (61 common headers) and a dynamic table (connection-specific). Repeated headers (like Authorization) are sent as single-byte index references instead of full strings — ~85% header size reduction.
• Flow control: Per-stream and per-connection flow control via WINDOW_UPDATE frames. A slow consumer can throttle a specific stream without affecting others.
• Stream prioritization: Clients signal dependency trees (stream 3 depends on stream 1) and weights. Server uses these to allocate bandwidth. Chrome removed priority trees in favor of PRIORITY_UPDATE in HTTP/3.

Limitation: All streams share one TCP connection. A single TCP packet loss triggers TCP retransmission, stalling ALL streams — this is TCP-level HOL blocking, which HTTP/3 (QUIC over UDP) solves.
Follow-up: "How does HPACK prevent CRIME-style compression attacks?" → HPACK uses Huffman encoding but not DEFLATE. The static table is fixed; the dynamic table is bounded. Unlike DEFLATE, an attacker can't probe secret header values by measuring compression ratios.
Follow-up: "Why not just open more TCP connections in HTTP/2?" → Defeats the purpose. Multiplexing reduces connection count to 1, saving memory (each TCP connection = kernel buffer ~128KB). Also, HPACK dynamic table is per-connection — more connections = worse compression.
Q2: Design a resilient REST API client for a mobile app
A resilient mobile API client must handle: unreliable networks, token expiry mid-flight, duplicate requests, and graceful degradation. Here's the architecture:

1. Request Queue with Priority: Offline mutations (POST, PUT) queue persistently (IndexedDB/SQLite). Foreground reads get priority. Background syncs are lowest priority.

2. Retry with Exponential Backoff + Jitter: Retry only idempotent requests (GET, PUT, DELETE) or POST with idempotency keys. Backoff: min(baseDelay × 2^attempt + random(0, baseDelay), maxDelay). Max 3 retries. Never retry 4xx (client errors).

3. Token Refresh Interception: On 401, pause all in-flight requests, refresh the token, replay paused requests with the new token. Use a mutex/promise to prevent concurrent refresh attempts.

4. Request Deduplication: If GET /users/42 is already in-flight, return the same promise to all callers. Key by method + url + serialized params.

5. Circuit Breaker: Track failure rate per endpoint. After 5 consecutive failures, "open" the circuit — immediately reject/return cached data for 30s before allowing a "half-open" probe request.

6. Timeout Strategy: Connection timeout: 10s (give up connecting). Read timeout: 30s (give up waiting for response). Total timeout: 60s (absolute cap). Use AbortController on the client.

7. Idempotency Keys: Every POST request sends Idempotency-Key: <uuid> header. Server stores this key with the response. If the same key is sent again (retry), server returns the stored response without re-executing.
Follow-up: "How do you handle the thundering herd problem when a token refresh completes?" → Use a single promise holder. First 401 triggers refresh, all subsequent 401s await the same promise. When it resolves, all replay simultaneously — but that's fine because they have a valid token now. Alternatively, stagger replays with 50ms intervals.
Follow-up: "What if the refresh token itself is expired?" → The refresh call returns 401. Detect this (avoid infinite loop) by checking if the failing request IS the refresh endpoint. If so, force logout and redirect to login. Also set a max refresh retry count of 1.
Q3: Explain stale-while-revalidate in detail
stale-while-revalidate is a Cache-Control extension (RFC 5861) that defines a window after max-age expires during which the cache can serve a stale response immediately while fetching a fresh one in the background.

Timeline with Cache-Control: max-age=60, stale-while-revalidate=120:
• 0–60s: Response is fresh. Serve from cache, no network request.
• 60–180s: Response is stale but within SWR window. Serve stale immediately (instant UX), trigger background revalidation. The background fetch updates the cache for the next request.
• 180s+: Response is stale and SWR window expired. Cache must wait for network response before serving (blocks like no-cache).

Why it matters: The user perceives zero latency during the SWR window because the browser serves cached data synchronously. The tradeoff: data might be up to max-age + stale-while-revalidate seconds old in the worst case.

Application-level equivalent: Libraries like SWR (Vercel) and React Query implement this at the JavaScript level: show cached data instantly, fetch in background, re-render when fresh data arrives. The HTTP-level directive does it at the browser cache/CDN level.
Follow-up: "What about stale-if-error?" → Same concept but triggered by 5xx/network errors instead of staleness. If the origin is down, stale-if-error=300 allows serving stale data for 300s rather than showing an error. This is your resilience layer at the cache level.
Follow-up: "Does this work with CDNs?" → Yes, CDNs like Cloudflare, Fastly, and Vercel Edge support it. CDN serves stale to user instantly, then revalidates with origin. But be careful: without Vary header, CDN might serve wrong variant.
Q4: Compare REST vs RPC vs GraphQL — when each?
REST (Resource-Oriented):
• Model: Resources with URIs, manipulated via HTTP verbs. State transferred as representations.
• Strengths: HTTP native (caching, CDN, proxies work out of the box). Stateless. Widely understood.
• Weaknesses: Over-fetching (GET /user returns 50 fields, you need 3). Under-fetching (need user + orders = 2 requests). No schema by default.
• Use when: Public APIs, CRUD-heavy apps, when HTTP caching is critical, when you want CDN optimization.

RPC (Action-Oriented — gRPC, tRPC):
• Model: Call remote procedures. gRPC uses Protobuf (binary) over HTTP/2. tRPC generates TypeScript types end-to-end.
• Strengths: Fast (binary serialization, HTTP/2 streaming). Type-safe. Bi-directional streaming.
• Weaknesses: Not browser-native (gRPC needs grpc-web proxy). Hard to cache. Not human-readable.
• Use when: Internal microservice communication, low-latency requirements, streaming (chat, live data), when both ends are owned by the same team.

GraphQL (Query-Oriented):
• Model: Single endpoint, client specifies exact data shape via query language.
• Strengths: No over/under-fetching. Strong schema (introspection). Frontend autonomy (no waiting for backend to add fields).
• Weaknesses: No HTTP caching (everything is POST). N+1 query problem on server. Complexity (resolvers, dataloaders, persisted queries). Security: malicious deep queries (query cost analysis needed).
• Use when: Complex UIs with varied data needs, multiple frontend platforms, rapid iteration where frontend/backend teams move independently.
Follow-up: "Can you cache GraphQL?" → Not at HTTP layer (POST requests). But: persisted queries (hash query → GET with hash = cacheable), @cacheControl directive, CDN-level (Stellate/GraphCDN), application-level (Apollo Client normalized cache).
Q5: What happens when the browser makes a fetch() call?
Complete lifecycle from fetch('https://api.example.com/data'):

1. URL Parsing & Scheme Check: Parse URL. Check if scheme is https. Apply CORS preflight rules — if cross-origin with non-simple headers, browser first sends OPTIONS request.

2. Service Worker Intercept: If a Service Worker is registered, the fetch event fires. SW can respond from cache, modify the request, or pass through to network.

3. HTTP Cache Check: Browser checks disk/memory cache. If a fresh cached response exists (per Cache-Control), return it without network. If stale but within SWR window, return stale and revalidate.

4. DNS Resolution: Check browser DNS cache → OS DNS cache → Recursive DNS resolver → Root → TLD → Authoritative nameserver. Returns IP address. Chrome pre-resolves DNS for links on the page (dns-prefetch).

5. TCP Connection: Check if an existing connection exists (HTTP/2 connection reuse, connection pooling). If not, TCP 3-way handshake (1 RTT). TLS handshake (1-2 RTTs for TLS 1.2, 1 RTT for TLS 1.3, 0-RTT for TLS 1.3 resumption).

6. HTTP Request: Serialize headers + body into HTTP/2 frames. Send via the connection. The request includes cookies (if same-origin or credentials: 'include'), auth headers, Content-Type.

7. Server Processing: Server receives request, routes to handler, executes logic, returns response with status code and headers.

8. Response Processing: Browser receives headers → fires response promise. Decompresses body (br/gzip). Parses body based on Content-Type. If response.json() is called, deserialization happens.

9. Cache Storage: If response is cacheable (GET + 200 + Cache-Control allows), store in HTTP cache with metadata (ETag, expiry). HSTS header stored for future upgrade-insecure.

10. JavaScript Promise Resolution: The Promise returned by fetch() resolves with the Response object. Note: fetch() only rejects on network failure, NOT on 4xx/5xx — you must check response.ok.
Follow-up: "At which step does CORS enforcement happen?" → CORS is enforced in two places: (1) Before the request: browser checks if preflight (OPTIONS) is needed. (2) After the response: browser checks Access-Control-Allow-Origin header. If missing or mismatched, JS cannot read the response body — but the request was already made and processed by the server.
Q6: How would you implement API versioning at scale?
Four strategies with tradeoffs:

1. URI Path Versioning: /v1/users, /v2/users
Pros: Explicit, easy to route at gateway/CDN level, easy to deprecate. Cons: URI pollution, breaks REST purist principles (URI should identify resource, not representation).

2. Header Versioning: Accept: application/vnd.company.v2+json
Pros: Clean URIs, follows content negotiation. Cons: Harder to test (can't paste URL in browser), CDN caching requires Vary: Accept which reduces cache hit ratio.

3. Query Parameter: /users?version=2
Pros: Easy to add. Cons: Not semantically correct, clutters URLs, optional parameter = ambiguity.

4. No Versioning (Additive Changes Only): Never remove fields, only add. Use feature flags for new behaviors.
Pros: Simplest, no version management. Cons: Response bloat over time, can't change field types.

At Google/Microsoft scale: Use URI versioning for major breaking changes (v1→v2), additive changes within a version, sunset headers (Sunset: Sat, 01 Jan 2025 00:00:00 GMT) for deprecation, and Deprecation: true header with Link: </v2/users>; rel="successor-version".
Follow-up: "How do you handle backward compatibility in a microservices environment?" → Use Consumer-Driven Contract Testing (Pact). Each consumer defines expected request/response. Provider test suite verifies all contracts. If a change breaks any consumer contract, CI fails.

  retries: number;                     // Max retry attempts for idempotent requests
  retryDelay: number;                  // Base delay for exponential backoff (ms)
}

// Interceptor pattern — each transforms and passes to next
type RequestInterceptor = (
  config: RequestInit & { url: string }
) => Promise<RequestInit & { url: string }>;

type ResponseInterceptor = (
  response: Response,
  config: RequestInit & { url: string }
) => Promise<Response>;

// Normalized error — every error from the API layer has this shape
// This decouples UI error handling from HTTP specifics
class ApiError extends Error {
  constructor(
    public status: number,            // HTTP status code (0 for network errors)
    public code: string,              // Machine-readable: 'NETWORK_ERROR', 'AUTH_EXPIRED'
    public body: unknown,             // Raw response body for downstream handling
    public retryable: boolean,        // Can this request be safely retried?
  ) {
    super(`API Error: ${status} ${code}`);
    this.name = 'ApiError';
  }
}

API Client Class — Core Engine

class ApiClient {
  private requestInterceptors: RequestInterceptor[] = [];
  private responseInterceptors: ResponseInterceptor[] = [];
  private inflightRequests = new Map<string, Promise<Response>>();
  // ^ Deduplication map: key = 'GET:/users/42' → shared promise
  // Multiple components requesting same data share ONE network call

  private refreshPromise: Promise<string> | null = null;
  // ^ Mutex for token refresh — only one refresh at a time
  // All 401s await this same promise instead of triggering N refreshes

  constructor(private config: ApiConfig) {}

  // --- Interceptor Registration ---
  addRequestInterceptor(fn: RequestInterceptor) {
    this.requestInterceptors.push(fn);
    return this; // Fluent API for chaining: client.addReq(...).addRes(...)
  }

  addResponseInterceptor(fn: ResponseInterceptor) {
    this.responseInterceptors.push(fn);
    return this;
  }

  // --- Main Request Method ---
  async request<T>(
    method: string,
    path: string,
    options: { body?: unknown; headers?: Record<string, string>; signal?: AbortSignal } = {}
  ): Promise<T> {
    const url = `${this.config.baseURL}${path}`;

    // Build initial request config
    let config: RequestInit & { url: string } = {
      url,
      method,
      headers: {
        'Content-Type': 'application/json',
        'X-Request-ID': crypto.randomUUID(),
        // ^ Correlation ID for distributed tracing across services
        ...options.headers,
      },
      body: options.body ? JSON.stringify(options.body) : undefined,
    };

    // Run request interceptors sequentially (order matters!)
    // Auth interceptor must run AFTER logging interceptor
    for (const interceptor of this.requestInterceptors) {
      config = await interceptor(config);
    }

    // --- Deduplication for GET requests ---
    const dedupeKey = `${method}:${url}`;
    if (method === 'GET' && this.inflightRequests.has(dedupeKey)) {
      // Another caller already issued this exact GET — reuse its promise
      // This prevents 10 components mounting simultaneously from firing
      // 10 identical API calls
      const response = await this.inflightRequests.get(dedupeKey)!;
      return response.clone().json() as Promise<T>;
      // ^ .clone() because Response body can only be consumed once
    }

    // --- Execute with retry logic ---
    const responsePromise = this.executeWithRetry(config, 0);

    // Register in dedup map (only GETs — mutations must never be deduped)
    if (method === 'GET') {
      this.inflightRequests.set(dedupeKey, responsePromise);
    }

    try {
      const response = await responsePromise;

      // Run response interceptors (logging, error transform, etc.)
      let processed = response;
      for (const interceptor of this.responseInterceptors) {
        processed = await interceptor(processed.clone(), config);
      }

      if (!processed.ok) {
        throw await this.buildError(processed);
      }

      return processed.json() as Promise<T>;
    } finally {
      // Always clean up dedup map — whether success or failure
      this.inflightRequests.delete(dedupeKey);
    }
  }

Retry Engine with Exponential Backoff + Jitter

  private async executeWithRetry(
    config: RequestInit & { url: string },
    attempt: number
  ): Promise<Response> {
    try {
      // Create AbortController for timeout enforcement
      const controller = new AbortController();
      const timeoutId = setTimeout(
        () => controller.abort(),
        this.config.timeout
      );
      // ^ AbortController is the ONLY correct way to timeout fetch()
      // Do NOT race with Promise.race — that leaks the connection

      const response = await fetch(config.url, {
        ...config,
        signal: controller.signal,
      });

      clearTimeout(timeoutId);

      // --- Auth Token Refresh on 401 ---
      if (response.status === 401 && !config.url.includes('/auth/refresh')) {
        // ^ Guard: don't retry refresh endpoint itself (infinite loop)
        const newToken = await this.refreshAuthToken();
        // Replace the Authorization header and replay
        config.headers = {
          ...(typeof config.headers === 'object' ? config.headers : {}),
          Authorization: `Bearer ${newToken}`,
        } as Record<string, string>;
        return this.executeWithRetry(config, 0);
        // ^ Reset attempt counter — auth retry is separate from network retry
      }

      // Retry only on server errors and rate limiting
      if (this.isRetryable(response.status, config.method!) && attempt < this.config.retries) {
        const delay = this.calculateBackoff(attempt, response);
        await new Promise(r => setTimeout(r, delay));
        return this.executeWithRetry(config, attempt + 1);
      }

      return response;

    } catch (error) {
      // Network errors (DNS failure, connection refused, offline)
      if (error instanceof TypeError && attempt < this.config.retries) {
        // TypeError = network failure in fetch() spec
        const delay = this.calculateBackoff(attempt);
        await new Promise(r => setTimeout(r, delay));
        return this.executeWithRetry(config, attempt + 1);
      }

      if (error instanceof DOMException && error.name === 'AbortError') {
        throw new ApiError(0, 'TIMEOUT', null, true);
      }

      throw new ApiError(0, 'NETWORK_ERROR', null, true);
    }
  }

  // --- Backoff Calculation ---
  private calculateBackoff(attempt: number, response?: Response): number {
    // Respect Retry-After header if server provides it (e.g., 429)
    if (response?.headers.has('Retry-After')) {
      const retryAfter = response.headers.get('Retry-After')!;
      const seconds = parseInt(retryAfter, 10);
      if (!isNaN(seconds)) return seconds * 1000;
      // Could also be a date: 'Wed, 21 Oct 2025 07:28:00 GMT'
      return new Date(retryAfter).getTime() - Date.now();
    }

    // Exponential backoff with full jitter (AWS recommended)
    // Formula: random(0, min(cap, base × 2^attempt))
    // Jitter prevents thundering herd when many clients retry simultaneously
    const cap = 30000; // Max 30 seconds
    const base = this.config.retryDelay; // e.g., 1000ms
    const expDelay = Math.min(cap, base * Math.pow(2, attempt));
    return Math.random() * expDelay;
    // ^ Full jitter: random between 0 and expDelay
    // Equal jitter alternative: expDelay/2 + random(0, expDelay/2)
  }

  // --- Retryability Check ---
  private isRetryable(status: number, method: string): boolean {
    // Only retry idempotent methods — POST creates duplicates!
    const idempotent = ['GET', 'PUT', 'DELETE', 'HEAD', 'OPTIONS'];
    if (!idempotent.includes(method)) return false;

    // 429 = rate limited, 502/503/504 = upstream issues (transient)
    // Never retry 400/401/403/404/409 — these are deterministic
    return [429, 502, 503, 504].includes(status);
  }

Token Refresh with Mutex Pattern

  // --- Token Refresh (Singleton Promise Pattern) ---
  private async refreshAuthToken(): Promise<string> {
    // If a refresh is already in-flight, ALL 401s share this promise
    // This prevents: 5 concurrent requests → 5 concurrent refreshes
    if (this.refreshPromise) {
      return this.refreshPromise;
    }

    this.refreshPromise = (async () => {
      try {
        const refreshToken = getStoredRefreshToken();
        const response = await fetch(
          `${this.config.baseURL}/auth/refresh`,
          {
            method: 'POST',
            headers: { 'Content-Type': 'application/json' },
            body: JSON.stringify({ refreshToken }),
          }
        );

        if (!response.ok) {
          // Refresh token expired — force logout
          clearAuthState();
          window.location.href = '/login';
          throw new ApiError(401, 'REFRESH_FAILED', null, false);
        }

        const { accessToken, refreshToken: newRefresh } = await response.json();
        storeTokens(accessToken, newRefresh);
        return accessToken;
      } finally {
        // Clear the singleton promise so next 401 triggers a new refresh
        this.refreshPromise = null;
      }
    })();

    return this.refreshPromise;
  }

  // --- Error Transformation ---
  private async buildError(response: Response): Promise<ApiError> {
    let body: unknown;
    try {
      body = await response.json();
    } catch {
      body = await response.text();
      // ^ Some error responses aren't JSON (502 from nginx)
    }

    const retryable = this.isRetryable(response.status, 'GET');
    const code = this.statusToCode(response.status);
    return new ApiError(response.status, code, body, retryable);
  }

  private statusToCode(status: number): string {
    const map: Record<number, string> = {
      400: 'BAD_REQUEST',
      401: 'UNAUTHORIZED',
      403: 'FORBIDDEN',
      404: 'NOT_FOUND',
      409: 'CONFLICT',
      422: 'VALIDATION_ERROR',
      429: 'RATE_LIMITED',
      500: 'INTERNAL_ERROR',
      502: 'BAD_GATEWAY',
      503: 'SERVICE_UNAVAILABLE',
    };
    return map[status] || `HTTP_${status}`;
  }

  // --- Convenience Methods ---
  get<T>(path: string, headers?: Record<string, string>) {
    return this.request<T>('GET', path, { headers });
  }
  post<T>(path: string, body: unknown) {
    return this.request<T>('POST', path, { body });
  }
  put<T>(path: string, body: unknown) {
    return this.request<T>('PUT', path, { body });
  }
  delete<T>(path: string) {
    return this.request<T>('DELETE', path);
  }
}

Usage — Wiring It All Together

// --- Instantiate with interceptors ---
const api = new ApiClient({
  baseURL: 'https://api.example.com/v1',
  timeout: 30000,
  retries: 3,
  retryDelay: 1000,
})
  .addRequestInterceptor(async (config) => {
    // Auth interceptor — attach Bearer token to every request
    const token = getStoredAccessToken();
    if (token) {
      (config.headers as Record<string, string>)['Authorization'] =
        `Bearer ${token}`;
    }
    return config;
  })
  .addResponseInterceptor(async (response, config) => {
    // Metrics interceptor — track latency per endpoint
    const duration = performance.now() - (config as any).__startTime;
    trackMetric('api_latency', { path: config.url, ms: duration });
    return response;
  });

// --- Use in components with full type safety ---
const users = await api.get<User[]>('/users');
const created = await api.post<User>('/users', { name: 'Alice' });
