1. Session-Based Authentication

// Traditional: server-side sessions
//
// 1. User sends credentials (POST /login)
// 2. Server validates, creates session in store (Redis/DB)
// 3. Server sets Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax
// 4. Every subsequent request: browser auto-sends cookie
// 5. Server looks up sessionId in store → gets user data
//
// Pros: Easy revocation (delete from store), no client-side secrets
// Cons: Server must store state, horizontal scaling needs shared store
//       Vulnerable to CSRF (cookies sent automatically)
//
// Perfect for: server-rendered apps (Next.js SSR, Rails, Django)

2. Token-Based Authentication (JWT)

// Stateless: server encodes user info in a signed token
//
// 1. User sends credentials (POST /login)
// 2. Server creates JWT: { sub: "user123", role: "admin", exp: ... }
// 3. Server signs with secret (HS256) or private key (RS256)
// 4. Client stores token (memory, cookie, or localStorage)
// 5. Client sends: Authorization: Bearer <token>
// 6. Server verifies signature + expiry → trusts claims
//
// Pros: Stateless, scales horizontally, works across domains
// Cons: Can't revoke until expiry (unless blacklist), payload readable
//       Larger than session ID, clock skew issues
//
// Perfect for: SPAs, mobile apps, microservices

4. Access + Refresh Token Pattern

// Modern standard: short-lived access + long-lived refresh
//
// Access Token: JWT, 5-15 min expiry, stored in memory
//   → Sent in Authorization header on every API call
//   → If stolen, limited damage window (5 min)
//
// Refresh Token: opaque string, 7-30 days, stored in HttpOnly cookie
//   → Sent only to /auth/refresh endpoint
//   → Server validates, issues new access token
//   → Can be revoked server-side (stored in DB)
//
// On page load: call /auth/refresh → get new access token
// On 401: silently refresh → retry original request
// On refresh failure: redirect to login
//
// Why this is optimal:
//   Access token (memory) → immune to CSRF, lost on refresh
//   Refresh token (HttpOnly cookie) → immune to XSS
//   Combined → minimal attack surface for both XSS and CSRF

Best practice: Access token in memory + refresh token in HttpOnly SameSite cookie. Service Worker is emerging as a secure alternative — it can intercept requests and attach tokens from an isolated context that XSS can't directly access.

Silent Refresh Race Condition

// Problem: Multiple tabs call /auth/refresh simultaneously
// If refresh token is single-use (rotated), only first tab succeeds
// Other tabs get 401 → user logged out in those tabs
//
// Solutions:
// 1. BroadcastChannel: one tab refreshes, broadcasts new token to others
// 2. Refresh token reuse window: allow same refresh token for 10s
// 3. Token family: server tracks refresh token chains per family
//    If old token reused → all tokens in family revoked (theft detected)

FAANG Interview Questions

Q1: Design the authentication architecture for a large-scale SPA with multiple microservices.
I'd use OAuth 2.0 Authorization Code flow with PKCE through an Identity Provider (Auth0/Keycloak). The SPA redirects to the IdP for login, receives an authorization code, then exchanges it (with PKCE verifier) at the BFF for tokens. The BFF (Backend-for-Frontend) is critical: it keeps the client_secret server-side, stores the refresh token in an HttpOnly SameSite cookie, and returns a short-lived access token. The SPA stores the access token in memory only. For API calls: SPA → BFF → microservices. The BFF attaches the access token. Microservices validate the JWT signature (RS256 with public key from IdP's JWKS endpoint) — no need to call the IdP on every request. Token refresh: when the access token expires (5 min), the BFF uses the refresh token cookie to get a new one. Multi-tab: BroadcastChannel syncs the new access token across tabs. Logout: BFF revokes refresh token at IdP, clears cookies, SPA clears memory.
Follow-up: How do you handle token revocation across microservices without a shared session store?
Q2: Explain the security trade-offs of storing JWT in localStorage vs HttpOnly cookie vs memory.
localStorage: Persistent, easy to use, but any XSS can steal the token with document.cookie or localStorage.getItem. An attacker can exfiltrate it to their server and replay it from anywhere. Never use for sensitive tokens. HttpOnly cookie: Immune to XSS reading (JavaScript can't access it), but vulnerable to CSRF because browsers auto-send cookies. Mitigate with SameSite=Lax/Strict, CSRF tokens, and Origin validation. Also sent on every request to the domain — wasteful for non-API requests. Memory (JavaScript variable): Immune to CSRF (not auto-sent), and while technically accessible to XSS, the attacker's window is limited to the current page session — the token is lost on refresh/navigate. The downside: user must re-authenticate on page refresh. Solution: pair with a refresh token in HttpOnly cookie. This is the recommended approach: access token in memory for day-to-day API calls, refresh token in HttpOnly SameSite cookie for silent refresh.
Follow-up: What about using a Service Worker to store and attach tokens?
Q3: How does the BFF (Backend-for-Frontend) pattern improve security?
The BFF is a thin server-side proxy that sits between the SPA and the auth provider. Security benefits: (1) Client secret never reaches the browser — the BFF holds it server-side and exchanges the auth code for tokens. (2) Refresh tokens stay in HttpOnly cookies — the SPA never sees them. (3) Token validation happens server-side — the BFF can check token blacklists, enforce rate limits, and add security headers. (4) Reduces CORS complexity — SPA talks to same-origin BFF, BFF talks to microservices. (5) Can implement token downscoping — the BFF gets a powerful token from the IdP but issues a limited-scope token to the SPA. Trade-offs: adds a server to maintain, adds latency (extra hop), and the BFF becomes a single point of failure (but it's simple enough to be highly available). At scale, I'd deploy the BFF as a lightweight edge function (Cloudflare Workers, Lambda@Edge) to minimize latency.
Follow-up: How would you handle SSR with authentication — where should tokens live?

1. Access + Refresh Token Implementation

// Auth module — stores access token in memory
let accessToken = null;
let refreshPromise = null; // Prevent parallel refreshes

async function getAccessToken() {
  if (accessToken && !isExpired(accessToken)) {
    return accessToken;
  }
  return refreshAccessToken();
}

async function refreshAccessToken() {
  // Deduplicate: if refresh already in-flight, reuse it
  if (refreshPromise) return refreshPromise;

  refreshPromise = fetch('/auth/refresh', {
    method: 'POST',
    credentials: 'include', // Send HttpOnly refresh cookie
  })
  .then(res => {
    if (!res.ok) throw new Error('Refresh failed');
    return res.json();
  })
  .then(data => {
    accessToken = data.accessToken;
    broadcastToken(accessToken); // Sync to other tabs
    return accessToken;
  })
  .finally(() => { refreshPromise = null; });

  return refreshPromise;
}

// Axios interceptor: auto-refresh on 401
api.interceptors.response.use(
  res => res,
  async error => {
    if (error.response?.status === 401 && !error.config._retry) {
      error.config._retry = true;
      const token = await refreshAccessToken();
      error.config.headers.Authorization = `Bearer ${token}`;
      return api(error.config);
    }
    return Promise.reject(error);
  }
);

2. Multi-Tab Token Sync

const channel = new BroadcastChannel('auth');

channel.addEventListener('message', (event) => {
  if (event.data.type === 'TOKEN_UPDATE') {
    accessToken = event.data.token;
  }
  if (event.data.type === 'LOGOUT') {
    accessToken = null;
    window.location.href = '/login';
  }
});

function broadcastToken(token) {
  channel.postMessage({ type: 'TOKEN_UPDATE', token });
}
function broadcastLogout() {
  channel.postMessage({ type: 'LOGOUT' });
}

Security Checklist

✅ Use HTTPS everywhere (tokens in transit)
✅ Short-lived access tokens (5-15 minutes)
✅ Refresh tokens: HttpOnly, Secure, SameSite=Strict cookie
✅ Rotate refresh tokens on every use (detect theft)
✅ Token family tracking (revoke all if reuse detected)
✅ BroadcastChannel for multi-tab sync
✅ Deduplicate concurrent refresh requests
✅ PKCE for all public clients (SPAs, mobile)
✅ Never store tokens in localStorage for production
✅ Implement idle timeout (10-30 min no activity → logout)
✅ Revoke all tokens on password change
✅ Rate-limit /auth/refresh endpoint
