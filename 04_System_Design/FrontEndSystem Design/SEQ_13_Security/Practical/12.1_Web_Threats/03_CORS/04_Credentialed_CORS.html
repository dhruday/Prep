Credentialed Cross-Origin Requests

By default, fetch() does NOT send cookies on cross-origin requests. To include cookies (needed for auth), you must set credentials: 'include'. But the server must also opt in with specific headers.

// Client-side:
const res = await fetch('https://api.example.com/profile', {
  credentials: 'include'  // sends cookies + accepts Set-Cookie
});

// Server must respond with ALL of these:
Access-Control-Allow-Origin: https://app.example.com  // exact origin (NOT *)
Access-Control-Allow-Credentials: true

// THREE STRICT RULES (browser enforces):
// 1. ACAO cannot be * with credentials → must be exact origin
// 2. ACAH (Allow-Headers) cannot be * with credentials
// 3. ACAM (Allow-Methods) cannot be * with credentials
// Violating any of these → browser blocks the response

Credentialed CORS Rules Summary

// With credentials: 'include', the browser enforces:

// ❌ WILL NOT WORK:
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
// Browser: "The value of ACAO header must not be the wildcard '*'"

// ❌ WILL NOT WORK (since Chrome 108):
Access-Control-Allow-Headers: *
Access-Control-Allow-Credentials: true
// Must list specific headers

// ✅ CORRECT:
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Access-Control-Allow-Headers: Content-Type, Authorization
Vary: Origin

// Credentials include:
// - Cookies (most common)
// - HTTP Basic/Digest auth
// - TLS client certificates

// BUT NOT:
// - Authorization header (that's just a header, not a "credential")
// - Bearer tokens sent manually

Google Senior Frontend — Credentialed CORS

Q: Your SPA on app.com needs to call api.app.com. Should you use credentials?

If using cookie-based auth: yes, credentials: 'include' + exact ACAO. But consider: these are different origins but same-site. Use SameSite=Lax cookies and the cookies will be sent without explicit CORS credentialing for top-level navigations. For API calls via fetch, you still need credentials: 'include' and CORS setup. Alternative: use an API gateway on app.com to proxy requests → eliminates CORS entirely.

Q: What's the architectural trade-off between cookie auth and token auth for CORS?

Cookies: automatic, HttpOnly (XSS-safe), but require CORS credentialing + CSRF protection. Tokens (Authorization header): explicit, works across any origin without credential concerns, but stored in JS memory (XSS-vulnerable). Google's approach for internal tools: cookie auth with strict CORS (simpler DX). For public APIs: token auth (avoids CORS credential complexity). For mobile: token auth (no cookie support).
