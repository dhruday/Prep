What is CSRF?

CSRF (Cross-Site Request Forgery) tricks a victim's browser into making an authenticated request to a target site. The browser automatically attaches cookies for the target domain — including auth session cookies. The attacker doesn't see the response; they just trigger the action (transfer money, change email, etc.).

1. Victim logged into bank.com → 2. Victim visits evil.com → 3. evil.com auto-submits form to bank.com/transfer → 4. Browser sends bank.com cookies → 5. Bank processes transfer!

<!-- Hosted on evil.com — auto-submits when visited -->

  <input type="hidden" name="amount" value="10000">

<script>document.getElementById('csrf-form').submit();</script>

<!-- Or via image tag (GET-based CSRF): -->
<img src="https://bank.com/transfer?to=attacker&amount=10000" style="display:none">

🔬 Why Browsers Send Cookies Cross-Origin

Cookie Origin Model: Cookies are sent based on the destination domain, not the source page. When evil.com submits a form to bank.com, the browser attaches bank.com's cookies because the REQUEST goes to bank.com.

SameSite Cookie Attribute: Modern defense. SameSite=Strict blocks cookies on all cross-site requests. SameSite=Lax (Chrome default since 2020) allows cookies on top-level GET navigations but blocks them on POST from cross-origin forms.

CORS doesn't help: CORS only applies to fetch/XHR. Form submissions and image loads bypass CORS entirely — the browser just sends the request with cookies attached.

Google Senior Frontend — CSRF Questions

Q: Is CSRF still relevant with SameSite=Lax default?

Mostly mitigated for POST-based CSRF, but still relevant: (1) GET-based state changes are still vulnerable with Lax, (2) Some browsers don't default to Lax, (3) Subdomains with SameSite=None can be exploited, (4) Within 2 minutes of cookie creation, Chrome temporarily sends Lax cookies on POST for compatibility ("Lax+POST"). Defense-in-depth with CSRF tokens is still recommended.

Q: Synchronizer token vs double-submit cookie — which is better?

Synchronizer pattern (server stores token in session, client sends in form) is more secure because the server validates against its session state. Double-submit cookie (token in cookie + header) is stateless and easier to scale, but vulnerable if attacker can set cookies (via subdomain XSS). At Google: use synchronizer tokens for critical actions, double-submit for APIs behind auth.
