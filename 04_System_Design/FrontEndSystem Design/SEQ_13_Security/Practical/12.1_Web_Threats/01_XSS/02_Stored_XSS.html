What is Stored XSS?

Stored (Persistent) XSS is the most dangerous XSS type. The attacker's payload is saved in the server's database (e.g., comment, profile bio, forum post) and served to every visitor who views that content. Unlike reflected XSS, no social engineering is needed — every user who visits the page is attacked.

Real-World: TweetDeck (2014)
Self-retweeting XSS worm spread across 40K+ accounts in minutes via stored XSS in tweet rendering.
Real-World: British Airways (2018)
Magecart injected stored XSS that stole 380,000 credit card numbers from payment pages.

🔬 How Stored XSS Executes in the Browser

1. Storage: Server receives POST with malicious HTML. If no sanitization, it's stored raw in the database (SQLite xss_comments table in our lab).

2. Retrieval: When ANY user requests the comments page, server queries DB and includes raw HTML in the response body.

3. Parsing: Browser's HTML parser tokenizes the response. Malicious <script> tags are parsed and executed during DOM construction. Event handlers (onerror, onload) are scheduled.

4. Client-Side Rendering (SPA): In React/Angular apps, if you set innerHTML or use dangerouslySetInnerHTML with unsanitized data from API, the same attack works — the browser parses the injected HTML.

5. Defense layers:
① Sanitize on write (DOMPurify server-side) — strips dangerous tags/attrs before storing
② Sanitize on read (DOMPurify client-side) — defense in depth for legacy data
③ Use textContent/innerText instead of innerHTML when HTML rendering isn't needed
④ CSP nonce to block inline scripts even if they reach the DOM

Google Senior Frontend — Stored XSS Questions

Q: You inherit a codebase with stored XSS in user comments. How do you remediate?

Immediate: Add server-side DOMPurify sanitization on the output path (when serving comments). Then: sanitize existing DB data with a migration script. Then: add input sanitization on write. Deploy CSP with nonces as a safety net. Long term: migrate to a framework with auto-escaping (React) and use textContent for non-HTML fields.

Q: Should you sanitize on input or output?

Both, but output sanitization is more important. Input sanitization can mangle valid data (e.g., a math formula with < symbols). Output encoding is context-aware — you encode differently for HTML body, attributes, JavaScript, and URLs. At Google, the principle is "render safely at the boundary where data meets HTML."

Q: How does Stored XSS interact with CSP?

CSP with nonce-based script-src blocks stored XSS scripts that don't have the correct nonce. However, CSP doesn't prevent all XSS — event handler attributes (onerror, onload) can bypass some CSP configurations unless you also set 'unsafe-inline' to be blocked. Strict CSP + DOMPurify is the gold standard.
