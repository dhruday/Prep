ESLint Rules for Prototype Pollution

// .eslintrc.json
{
  "rules": {
    "no-proto": "error",                   // ban __proto__
    "no-extend-native": "error",          // ban Array.prototype.x = ...
    "guard-for-in": "error",              // require hasOwnProperty in for-in
    "no-restricted-syntax": [
      "error",
      {
        "selector": "MemberExpression[property.name='__proto__']",
        "message": "Don't use __proto__. Use Object.getPrototypeOf."
      },
      {
        "selector": "ForInStatement",
        "message": "Use Object.keys/entries instead of for...in"
      }
    ]
  }
}

Google Senior Frontend — Detection

Q: Design a prototype pollution detection system for a large monorepo.

Pre-commit: ESLint rules (no-proto, guard-for-in, no-restricted-syntax for __proto__ access). PR review: Semgrep/CodeQL rules that detect merge/extend patterns with user input flowing to them (taint analysis). CI: npm audit with --audit-level=critical for every build. Runtime: Lightweight canary in the health check endpoint — create {}, check for unexpected properties. Monitoring: Datadog/Prometheus metric for "prototype pollution detected" — alert on first trigger. Google's approach: Presubmit checks in Critique (code review system) flag any for...in without hasOwnProperty, similar to their Tricorder static analysis tool.
