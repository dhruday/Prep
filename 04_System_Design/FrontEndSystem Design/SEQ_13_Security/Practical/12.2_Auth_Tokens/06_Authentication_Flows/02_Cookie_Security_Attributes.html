Cookie Prefixes (__Host-, __Secure-)

// Cookie prefixes enforce security at the browser level
// Browsers REJECT cookies with prefixes that don't meet requirements

// __Host- prefix requirements:
// ✅ Must have Secure flag
// ✅ Must NOT have Domain attribute
// ✅ Must have Path=/
// ✅ Must be set over HTTPS
Set-Cookie: __Host-session=abc123; Secure; Path=/

// Why? Prevents:
// 1. Cookie injection from subdomains (no Domain = exact match)
// 2. HTTP downgrade attacks (Secure required)
// 3. Path-based cookie shadowing (Path=/ required)

// __Secure- prefix requirements:
// ✅ Must have Secure flag (only requirement)
Set-Cookie: __Secure-token=xyz; Secure; SameSite=Strict

// Google uses __Host- for their auth cookies!
// Check: DevTools → Application → Cookies → google.com

Google Senior Frontend — Cookie Security

Q: What's the most secure cookie configuration for an auth session?

Set-Cookie: __Host-session=token; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=3600. Breakdown: __Host- prefix enforces Secure + no Domain + Path=/ at the browser level. HttpOnly blocks JavaScript access. SameSite=Strict prevents CSRF completely. Max-Age=3600 limits to 1 hour. This combination defends against: XSS (HttpOnly), CSRF (SameSite=Strict), MitM (Secure), cookie injection (__Host-), prolonged sessions (Max-Age).

Q: SameSite=Strict breaks OAuth redirects. How do you handle this?

OAuth redirects from the IdP back to your site are cross-site navigations — SameSite=Strict cookies won't be sent. Solutions: (1) Use SameSite=Lax for the initial auth check, then upgrade to a Strict session after the redirect. (2) Use a landing page pattern: OAuth callback → landing page (same-site) → redirect to app (now Strict cookie is sent). (3) Google's approach: Use a combination of Lax session cookie + a separate Strict CSRF cookie for state-changing operations.
