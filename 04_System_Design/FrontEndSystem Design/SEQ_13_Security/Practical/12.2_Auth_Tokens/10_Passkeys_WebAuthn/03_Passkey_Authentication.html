Authentication Ceremony

// navigator.credentials.get() — the authentication flow

// Step 1: Get challenge from server
const options = await fetch('/webauthn/auth-options').then(r => r.json());

// Step 2: Browser prompts authenticator
const assertion = await navigator.credentials.get({
  publicKey: {
    challenge: options.challenge,
    rpId: "example.com",
    allowCredentials: [],  // empty = discoverable (passkey)
    userVerification: "preferred",
    timeout: 60000
  }
});

// Step 3: assertion.response contains:
assertion.response.authenticatorData  // rpIdHash + flags + counter
assertion.response.clientDataJSON     // type + challenge + origin
assertion.response.signature          // signed(authData + hash(clientData))
assertion.response.userHandle         // user.id from registration

// Step 4: Server verifies
// 1. Look up public key by credential ID
// 2. Verify origin, rpIdHash, challenge
// 3. Verify signature with stored public key
// 4. Check sign count (anti-cloning)
// 5. Issue session token

Q: How does the sign counter protect against credential cloning?

Each time the authenticator creates a signature, it increments an internal counter (signCount). The server stores the last known sign count. On each authentication: if the incoming signCount ≤ stored signCount, it indicates the credential may have been cloned (two devices using the same credential, but the counter diverged). This is a heuristic, not a guarantee — some authenticators always return 0 (especially passkeys synced via cloud). For synced passkeys, Google recommends not relying on sign count for cloning detection; instead, use device-bound credentials for high-security scenarios (hardware security keys). The sign count was designed for single-device authenticators like YubiKeys, where cloning is a real threat.
