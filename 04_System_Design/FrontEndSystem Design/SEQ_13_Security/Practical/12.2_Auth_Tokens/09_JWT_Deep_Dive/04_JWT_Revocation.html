Recommended: Short-Lived JWT + Refresh Token

// The industry standard approach:

// Access token: JWT, 5-15 min expiry
// Refresh token: opaque, stored server-side, 7-30 days

// Normal flow:
// 1. Login → get access_token (JWT) + refresh_token
// 2. API calls use access_token in Authorization header
// 3. Access token expires after 5 min
// 4. Client calls /refresh with refresh_token
// 5. Server validates refresh_token, issues new access_token

// Revocation:
// Delete refresh_token from server → no more renewals
// Max 5 min window where old access_token still works
// For instant revocation: add token to blacklist (Redis)
// Blacklist only needs entries for 5 min (until token expires)

// This is a great balance of stateless (JWT) + revocable (refresh)

Google Senior Frontend — JWT Revocation

Q: Your product has a "Sign out from all devices" feature. How do you implement it with JWTs?

Approach: (1) Each user has a token_version (integer) in the database. (2) JWT includes the token_version at issue time. (3) On "sign out all": increment token_version in DB, delete all refresh tokens for the user from Redis/DB. (4) On every API request: JWT middleware checks token_version in JWT against DB. If mismatch → reject (user must re-login). (5) To avoid DB lookup on every request: use short-lived JWTs (5 min). Only check token_version during refresh. Old access tokens expire naturally within 5 min. (6) For immediate revocation: broadcast a "revoke user X" event via pub/sub. Each service adds user X to an in-memory deny list (TTL = max token lifetime). No DB lookup needed.
