CSP Challenges in SPAs

// SPAs have unique CSP challenges:

// 1. CSS-in-JS (styled-components, emotion)
//    Injects <style> tags at runtime → needs 'unsafe-inline' for styles
//    Or: configure library to use nonces

// 2. Dynamic script loading
//    Webpack code splitting: creates <script> tags dynamically
//    Solution: 'strict-dynamic' propagates trust

// 3. eval() usage
//    Some libraries use eval() or new Function()
//    Source maps, template compilers, JSON parsing
//    Solution: Use production builds (no eval), audit deps

// 4. Inline event handlers
//    <div onclick="handler()"> blocked by CSP
//    React: Uses synthetic events (addEventListener) → OK
//    Angular: Uses template binding → needs compilation mode

// 5. Web Workers & Service Workers
//    worker-src directive needed
//    Blob URLs for inline workers need blob: in worker-src

// 6. Hot Module Replacement (HMR)
//    Dev server uses eval/inline scripts
//    CSP must be relaxed in development

React CSP Configuration

// ═══ Next.js with CSP ═══
// next.config.js
const cspHeader = `
  default-src 'self';
  script-src 'self' 'nonce-\${nonce}' 'strict-dynamic';
  style-src 'self' 'nonce-\${nonce}';
  img-src 'self' blob: data:;
  font-src 'self';
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  base-uri 'self';
  form-action 'self';
  object-src 'none';
`;

// middleware.ts (Next.js)
export function middleware(request) {
  const nonce = Buffer.from(crypto.randomUUID()).toString('base64');
  const csp = cspHeader.replace(/\$\{nonce\}/g, nonce);
  
  const headers = new Headers(request.headers);
  headers.set('Content-Security-Policy', csp);
  headers.set('x-nonce', nonce);
  
  return NextResponse.next({ request: { headers } });
}

// In _document.tsx — pass nonce to scripts:
<script nonce={nonce} src="/_next/static/chunks/main.js" />

// styled-components with nonce:
<StyleSheetManager nonce={nonce}>
  <App />
</StyleSheetManager>

Angular & Vue CSP

// ═══ Angular CSP ═══
// Angular AOT compilation is CSP-compatible
// JIT compilation uses eval() → NOT CSP-safe

// Always use AOT in production:
ng build --configuration=production
// This compiles templates ahead of time

// Angular CSP nonce support (v16+):
// In index.html:
<app-root ngCspNonce="random-nonce-value"></app-root>

// Or via environment:
import { CSP_NONCE } from '@angular/core';
providers: [{ provide: CSP_NONCE, useValue: 'your-nonce' }]

// ═══ Vue.js CSP ═══
// Vue compiler uses new Function() in runtime build
// Solution: Use pre-compiled templates (vue-loader)

// vue.config.js
module.exports = {
  runtimeCompiler: false  // ensures no eval()
}

// Nuxt.js CSP:
// nuxt.config.ts
export default defineNuxtConfig({
  nitro: {
    routeRules: {
      '/**': {
        headers: {
          'Content-Security-Policy': "script-src 'self' 'nonce-{{nonce}}'"
        }
      }
    }
  }
})

Google Senior Frontend — SPA CSP

Q: How do you handle CSS-in-JS libraries with CSP?

CSS-in-JS (styled-components, emotion, MUI) inject <style> tags at runtime, which CSP's style-src blocks without 'unsafe-inline'. Solutions ranked by security: (1) Nonce injection: Pass nonce to the CSS-in-JS provider. styled-components: <StyleSheetManager nonce={nonce}>. Emotion: <CacheProvider value={createCache({key:'css',nonce})}>. MUI: createCache({key:'css',nonce}). Best option — no unsafe-inline needed. (2) Static extraction: Use compile-time CSS extraction (Linaria, vanilla-extract, Tailwind). No runtime <style> injection — generates .css files at build time. Most CSP-friendly but less dynamic. (3) 'unsafe-inline' for styles only: style-src 'self' 'unsafe-inline'. While not ideal, style injection XSS is much harder to exploit than script injection. Acceptable tradeoff for some apps. (4) Hash-based: Pre-compute hashes of critical styles. Impractical for CSS-in-JS (styles are dynamic). At Google: Closure Stylesheets (static extraction) + nonces for SSR-injected styles.
