Nonce-Based CSP

// Nonce = "Number used ONCE"
// Random value generated per request, shared between header and script tags

// Server generates nonce:
const crypto = require('crypto');
const nonce = crypto.randomBytes(16).toString('base64');
// e.g., "YTk5NmI3ZmQ2NjhiMzA0ZQ=="

// Set in CSP header:
Content-Security-Policy: script-src 'nonce-YTk5NmI3ZmQ2NjhiMzA0ZQ=='

// Add to allowed script tags:
<script nonce="YTk5NmI3ZmQ2NjhiMzA0ZQ==">
  console.log('This runs!');  // ✅ nonce matches
</script>

<script>
  console.log('This is blocked!');  // ❌ no nonce
</script>

// XSS payload injected by attacker:
<script>steal(cookies)</script>  // ❌ no nonce → BLOCKED

// Critical requirements:
// 1. Nonce must be random (not predictable)
// 2. Nonce must be unique per response (not cached/reused)
// 3. Use cryptographic randomness (not Math.random)
// 4. At least 128 bits (16 bytes)

Hash-Based CSP

// Hash = SHA-256/384/512 of the script content
// No dynamic generation needed — good for static scripts

// For this inline script:
<script>alert('Hello')</script>

// Generate hash (must match EXACTLY — whitespace matters!):
// echo -n "alert('Hello')" | openssl dgst -sha256 -binary | base64
// → "qznLcsROx4GACP2dm0UCKCzCG+HiZ1guq6ZZDob/Tng="

// CSP header:
Content-Security-Policy: script-src 'sha256-qznLcsROx4GACP2dm0UCKCzCG+HiZ1guq6ZZDob/Tng='

// ✅ Pros of hashes:
// - No per-request generation (cacheable)
// - Precise: only EXACT matching content runs
// - Good for static inline scripts (analytics, config)

// ❌ Cons:
// - Any content change = new hash
// - Whitespace matters (trailing newline changes hash)
// - Doesn't work for external scripts (use nonce instead)
// - Hard to maintain for frequently changing code

strict-dynamic

// strict-dynamic: Trust scripts loaded BY trusted scripts
// Solves the "widget loading" problem

Content-Security-Policy: script-src 'nonce-abc123' 'strict-dynamic'

// With strict-dynamic:
<script nonce="abc123">
  // ✅ This script is trusted (has nonce)
  const s = document.createElement('script');
  s.src = 'https://analytics.google.com/analytics.js';
  document.head.appendChild(s);
  // ✅ This dynamically loaded script is ALSO trusted!
  // Because it was loaded by a trusted (nonced) script
</script>

// Without strict-dynamic, you'd need:
// script-src 'nonce-abc123' https://analytics.google.com
// And every third-party CDN, and their dependencies...

// How strict-dynamic works:
// 1. Ignores URL-based allowlists (https://cdn.com)
// 2. Ignores 'unsafe-inline'
// 3. Only trusts: nonce'd scripts + scripts they load
// 4. Propagates trust through dynamic createElement

// Google's recommended strict CSP:
Content-Security-Policy:
  script-src 'nonce-{random}' 'strict-dynamic';
  object-src 'none';
  base-uri 'self'

Google Senior Frontend — Nonces vs Hashes

Q: When would you use nonces vs hashes for CSP?

Nonces: (1) SSR apps (Next.js, Nuxt) where server generates HTML per request. Each response gets a fresh nonce. (2) Dynamic inline scripts that change per user/request. (3) Combined with strict-dynamic for automatic trust chain. Hashes: (1) Static sites (SSG) where HTML is pre-built and cached by CDN. Can't inject per-request nonces. (2) Fixed inline scripts that never change (analytics snippet, config). (3) When you can't modify the server (static hosting). Key gotcha: Nonces break with full-page caching. If CDN caches the HTML, all users get the same nonce — but each response needs a unique CSP header. Solutions: (a) Edge computing (Cloudflare Workers) to inject nonce at CDN edge. (b) Use hashes for static content, nonces for dynamic. (c) 'strict-dynamic' + nonce on the entry script, all dynamic loads inherit trust. Google uses nonces + strict-dynamic for most properties.
