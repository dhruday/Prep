SRI for Dynamically Loaded Scripts

// Setting integrity on dynamically created script tags:

function loadScriptWithSRI(src, integrity) {
  return new Promise((resolve, reject) => {
    const script = document.createElement('script');
    script.src = src;
    script.integrity = integrity;
    script.crossOrigin = 'anonymous';
    script.onload = resolve;
    script.onerror = reject;
    document.head.appendChild(script);
  });
}

// Usage:
await loadScriptWithSRI(
  'https://cdn.example.com/lib.js',
  'sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8w'
);

// ═══ Challenges with dynamic imports ═══

// 1. import() doesn't support integrity attribute natively
const module = await import('https://cdn.example.com/lib.mjs');
// ❌ No way to specify integrity hash here

// 2. Code-split chunks (Webpack/Vite)
// Each lazy chunk is loaded dynamically
// Webpack can inject integrity via __webpack_require__.sri
// But requires Webpack SRI plugin

// 3. Service Worker verification (advanced):
// Intercept fetch, verify hash, then serve
self.addEventListener('fetch', (event) => {
  if (isThirdPartyScript(event.request.url)) {
    event.respondWith(verifyAndServe(event.request));
  }
});

Import Maps with Integrity

// Import Maps can specify integrity for ES modules
// (Chrome 89+, Firefox 108+)

<script type="importmap">
{
  "imports": {
    "lodash": "https://cdn.jsdelivr.net/npm/lodash-es@4.17.21/lodash.js",
    "react": "https://esm.sh/react@18.2.0"
  },
  "integrity": {
    "https://cdn.jsdelivr.net/npm/lodash-es@4.17.21/lodash.js":
      "sha384-HASH_HERE",
    "https://esm.sh/react@18.2.0":
      "sha384-HASH_HERE"
  }
}
</script>

// Now import statements are integrity-checked:
<script type="module">
import { debounce } from 'lodash';  // ✅ SRI verified!
import React from 'react';          // ✅ SRI verified!
</script>

// Import maps integrity limitations:
// - Only applies to bare specifiers mapped in the import map
// - Doesn't cover transitive dependencies
// - Browser support still evolving
// - Integrity field in import maps is still a proposal in some browsers

Q: How do you handle SRI for code-split chunks in a modern SPA?

Code-split SRI is one of the hardest problems: (1) Webpack approach: Use webpack-subresource-integrity plugin. It computes hashes at build time and injects them into the runtime. __webpack_require__.sri maps chunk IDs to integrity hashes. (2) Vite approach: @vitejs/plugin-sri or manual postbuild. Vite generates content-hashed filenames (app.a1b2c3.js) which provides some integrity via immutable naming. But doesn't prevent CDN tampering. (3) Self-hosting: If you host your own chunks, SRI adds less value (but still defense-in-depth). Content-hash in filename + Cache-Control: immutable provides strong caching. (4) Service Worker verification: For maximum security, a Service Worker can compute hashes of fetched chunks against a manifest. More flexible than browser SRI. Can verify any resource type. (5) CSP hash alternative: Instead of SRI per-chunk, use CSP: script-src 'sha384-...' for critical inline scripts. (6) Signed exchanges: Emerging standard. Server signs entire HTTP response. Browser verifies signature. Works with any resource type.
