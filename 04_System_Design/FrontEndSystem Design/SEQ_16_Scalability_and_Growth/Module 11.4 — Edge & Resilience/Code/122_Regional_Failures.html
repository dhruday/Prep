Regional failures: when us-east-1 goes down, your frontend must survive — automatically

Regional failures happen. AWS us-east-1 has had multiple major outages. The frontend must be designed to (1) detect regional API unavailability, (2) auto-failover to a secondary region, (3) show meaningful degraded UI rather than a blank screen, (4) recover gracefully as the primary region comes back. Key techniques: multi-region API endpoints, health checks at the client level, fallback manifests, and Service Worker offline-first caching as a last resort.

Resilience layers
Layer 1: Service Worker cache (offline)
Layer 2: CDN edge cache (stale-while-revalidate)
Layer 3: Multi-region API failover
Layer 4: Degraded mode UI (show cached data)
Layer 5: Status page + real-time incident
Common mistakes
Single API endpoint hardcoded
Crash on 5xx with no fallback
Auth service in only one region
No health check endpoint
SPA serves 200 but loads nothing

Multi-region API client with automatic failover

// ─── Multi-region fetch with failover ───
const ENDPOINTS = [
  'https://us-east.api.app.com',
  'https://eu-west.api.app.com',
  'https://ap-south.api.app.com'
];

async function resilientFetch(path: string, opts?: RequestInit) {
  for (const base of ENDPOINTS) {
    try {
      const res = await fetch(`${base}${path}`, {
        signal: AbortSignal.timeout(3000), // 3s per region
        ...opts
      });
      if (res.ok) return res;
    } catch { /* next region */ }
  }
  throw new Error('All regions unavailable');
}

// ─── React query with stale data fallback ───
const { data } = useQuery({
  queryKey: ['dashboard'],
  queryFn: () => resilientFetch('/api/dashboard'),
  staleTime: 60_000,
  // Keep showing stale data if refetch fails
  placeholderData: (prev) => prev,
  retry: 1
});
