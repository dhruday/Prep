Multi-tenant UI: one deployment, N customers — each with their own branding, features, data

Multi-tenancy in the frontend means: (1) tenants cannot see each other's data (isolation), (2) each tenant can have different theming, feature sets, and routing configs, (3) all tenants share the same deployed bundle. The tenant is identified at boot time (subdomain, header, JWT claim) and governs everything. SAP BTP is fully multi-tenant — CustomerA.btp.cloud.sap runs the same code as CustomerB.btp.cloud.sap but sees personalized dashboards, features, and themes.

What multi-tenant UI controls
Branding (logo, colors, fonts)
Feature gates (modules enabled per plan)
Navigation items
Data scoping (tenant ID in all API calls)
Locale defaults
Custom domain routing
Isolation requirements
No cross-tenant data in local/session storage
Auth token must contain tenant claim
API gateway enforces tenant scoping
No shared global state across tenant sessions
CSP headers per tenant

Tenant context bootstrap + Axios interceptor

// ─── Tenant config type ───
interface TenantConfig {
  id: string;
  name: string;
  theme: { primary: string; logo: string };
  features: string[];
  locale: string;
}

// ─── Bootstrap on app start ───
async function bootstrapTenant(): Promise<TenantConfig> {
  const subdomain = location.hostname.split('.')[0];
  const config = await fetch(`/api/tenant/${subdomain}`).then(r => r.json());
  applyTheme(config.theme);  // inject CSS vars
  i18n.changeLanguage(config.locale);
  return config;
}

// ─── Axios interceptor adds tenant ID to every request ───
axios.interceptors.request.use(cfg => {
  cfg.headers['X-Tenant-ID'] = tenantStore.getState().tenantId;
  return cfg;
});

// ─── Storage helper with namespace ───
const tenantStorage = (tenantId: string) => ({
  set: (k: string, v: string) => localStorage.setItem(`${tenantId}:${k}`, v),
  get: (k: string) => localStorage.getItem(`${tenantId}:${k}`),
});
