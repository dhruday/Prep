# 195. DRY (Don't Repeat Yourself)

## ────────────────────────────────────
## 1️⃣ High-Level Explanation (Interview-Level Overview)
## ────────────────────────────────────

**DRY** stands for *Don't Repeat Yourself* — a principle stating that every piece of knowledge or logic should have a **single, authoritative representation** in a system. Duplication of logic leads to inconsistencies, bugs, and maintenance nightmares.

**What it is:**
- Every discrete piece of behavior, rule, or data definition exists in exactly one place
- An instruction to extract repeated logic into reusable, testable units
- A guard against "shotgun surgery" — a single business rule change requiring modifications in 10 places

**Why it exists:**
- Duplication means changes must be made in multiple places — and humans forget some
- Inconsistencies between copies lead to subtle, hard-to-find bugs
- Testing becomes exponential — every copy needs its own test
- Knowledge about the system becomes fragmented

**The problem it solves:**
- Prevents divergent duplicates: two copies of the same logic that evolve independently
- Reduces the risk of partial updates (update one copy, forget another)
- Centralizes business rules so they are enforced consistently

**Where and when it is used:**
- Code duplication: utility functions, business logic, validation rules
- Data duplication: caching (controlled redundancy), or redundant fields in DB
- Configuration duplication: avoid defining the same constant in 10 files
- Test duplication: shared fixtures and test helpers

**Role in large-scale distributed systems:**
- DRY logic in shared libraries prevents rule drift across microservices
- **Note:** DRY must be balanced against service autonomy — don't create a shared library that couples 50 services

## 2️⃣ Deep-Dive Explanation (Senior / Staff Engineer Level)
## ────────────────────────────────────

### The Two Types of Duplication

**1. Accidental Duplication** (BAD — eliminate this)
- Two pieces of code that do the same thing, written independently
- No shared abstraction, no single point of change
- Example: email validation logic written 4 times across 4 services

**2. Intentional Redundancy** (GOOD — controlled for reasons)
- Denormalized database columns for query performance
- Cached copies of data for low latency reads
- CQRS read models built from event streams
- These are deliberate choices, not DRY violations

### DRY in Code: Practical Examples

**Violation:**
```java
// OrderService.java
if (user.getAge() < 18) throw new UnauthorizedException("Must be 18+");

// ProductService.java
if (user.getAge() < 18) throw new ForbiddenException("Age restriction");

// CheckoutService.java
if (user.getAge() < 18) return Response.forbidden("Age gate");
```

**DRY Compliant:**
```java
// AgeVerificationPolicy.java
public class AgeVerificationPolicy {
    public void enforce(User user, int minimumAge) {
        if (user.getAge() < minimumAge) {
            throw new AgeRestrictionException(
                "User must be at least " + minimumAge + " years old"
            );
        }
    }
}

// Used everywhere uniformly:
ageVerificationPolicy.enforce(user, 18);
```

### DRY in Configuration

```yaml
# ❌ Same value repeated in 12 config files
max-retries: 3
retry-delay-ms: 500

# ✅ Single source of truth — shared config or environment variable
RETRY_CONFIG_MAX: 3
RETRY_CONFIG_DELAY_MS: 500
```

### DRY in Database Design

```sql
-- ❌ Tax rate calculation duplicated in application code AND stored procedure AND trigger
-- Three places to update when tax rates change

-- ✅ Single tax_rates table, single lookup function
-- All business logic reads from one authoritative source
SELECT calculate_tax(order_total, country_code) FROM orders;
```

### DRY in Microservices: The Shared Library Problem

DRY is powerful but dangerous in distributed systems:

**Scenario:** 5 microservices each implement `UserPermissionCheck` independently.
- **Bad DRY fix:** Extract to `common-permissions.jar` that all 5 import
  - Changing the library requires coordinating releases of all 5 services
  - A build failure in the library blocks all services
  - Creates **deployment coupling** — not just code coupling

**Better approaches:**
1. **Shared service:** Permission check becomes an API call to an `AuthorizationService`
2. **Copied code with explicit ownership:** Each service owns its copy; acknowledge duplication with a comment
3. **Contract-based sharing:** Share just the contract (proto/OpenAPI), not the implementation

**The rule for microservices DRY:**
> Prefer **duplication** over the wrong **abstraction** at service boundaries.

### DRY vs AHA (Avoid Hasty Abstractions)

Sandi Metz's rule: *"Duplication is far cheaper than the wrong abstraction."*

```
Phase 1: Two pieces of similar code — WAIT, don't abstract yet
Phase 2: Three pieces — look for the pattern
Phase 3: Clear pattern emerges — extract the abstraction
```

Premature DRY creates the wrong abstraction:
```java
// processX and processY share 80% logic but the 20% difference is fundamentally different behavior
// ❌ Extracting them creates a messy method with boolean flags:
public void process(Entity e, boolean isX, boolean isY, boolean skipStep3) { ... }

// ✅ Two clear, separate methods that happen to look similar are better
```

### Trade-offs

| Scenario | Apply DRY? |
|---|---|
| Same validation in 3+ places | ✅ Yes — extract |
| Same 3-line utility in 2 places | ⚠️ Maybe — wait for a third |
| Same data model in 2 microservices | ❌ No — accept autonomy |
| Same constant string in 10 files | ✅ Yes — centralize |
| Same algorithm, different contexts | ⚠️ Evaluate carefully |

## 3️⃣ Capacity Planning & Estimation (When Applicable)
## ────────────────────────────────────

DRY has indirect capacity implications:
- **Duplicate cache entries:** Multiple services caching the same user object wastes memory. A shared cache with a single key space is DRY-compliant and more memory-efficient.
- **Duplicate API calls:** If 3 services independently fetch the same user data, a shared user service or cache reduces 3× load to 1×.
- **Duplicate index maintenance:** Computed fields duplicated and indexed separately add write amplification.

## ────────────────────────────────────
## 4️⃣ Data & Storage Design
## ────────────────────────────────────

**DRY in schema design:**
- Avoid storing derivable data: `total_price = quantity × unit_price` — compute it unless read performance demands storage
- Lookup tables for repeated values: store `country_id` not `country_name` string everywhere
- Reference data tables (tax rates, fee schedules) are the DRY answer to rule ownership

**Controlled redundancy (not a DRY violation):**
- Denormalized columns for performance: documented, justified deviation
- CQRS read models: deliberate copies for query performance
- These are documented choices, not accidents

## ────────────────────────────────────
## 5️⃣ Scalability, Reliability & Fault Tolerance
## ────────────────────────────────────

**DRY at scale:**
- A single shared validation library means a bug fix is deployed once, not 20 times
- Shared retry logic prevents inconsistent retry storms
- Centralized rate limit configuration avoids services having different thresholds

**Risk of over-DRY at scale:**
- A shared library with a breaking change can cascade across 50 services simultaneously
- Shared config services become SPOFs if all services read config from one place at startup
- **Mitigation:** Libraries are versioned; services pin versions; migrations are gradual

## 6️⃣ Security, APIs & Governance
## ────────────────────────────────────

- **Authorization logic should be DRY** — a single implementation prevents gaps between services applying rules differently
- **Encryption utilities** should be a shared, audited library — not reimplemented per service
- **Input validation schemas** should be DRY: define once, reuse in all entry points
- **Audit logging format** should be standardized to simplify SIEM ingestion

## 7️⃣ Real-World Examples & Case Studies
## ────────────────────────────────────

### Stripe's Validation Layer
- All API input validation runs through a single declarative schema system
- Business rules for card validation, currency checks, and amount limits are defined once
- Any change to a rule propagates instantly — no risk of 3 copies of a constraint being out of sync

### Netflix Hystrix → Resilience4j Migration
- Circuit breaker logic was duplicated per-team in many services
- Netflix extracted it into Hystrix (community later moved to Resilience4j)
- Single library: one config format, one dashboard, one mental model

### The "Distributed Monolith" Anti-Pattern
- Teams DRY their microservices too aggressively into a shared domain model library
- All 20 services import `core-domain.jar`
- Now all 20 services must deploy together when the domain changes
- DRY violated the service autonomy principle

## 8️⃣ Interview-Oriented Answer & Follow-Ups
## ────────────────────────────────────

### Sample Interview Answer

> "DRY is the principle that every piece of knowledge — business rules, validation logic, configuration — should have a single authoritative representation. In practice, this means extracting shared validation into a common class, centralizing configuration in one place, and not duplicating business rules across services. However, I'm careful not to over-apply DRY at microservice boundaries — sharing the wrong abstraction creates deployment coupling that hurts autonomy. I prefer a deliberate copy over the wrong shared abstraction."

### Common Follow-Up Questions

1. **"Isn't caching a DRY violation?"** → No. Caching is intentional, controlled redundancy. A DRY violation is accidental duplication.
2. **"How do you handle DRY across microservices?"** → Share APIs (not code) for behavior. Versioned libraries for utilities. Never share domain logic.
3. **"What happens when you extract too early?"** → You create the wrong abstraction — a "god utility" with boolean flags and edge cases. Wait for the third repetition.
4. **"DRY in tests?"** → Balance with readability. Over-DRY tests become hard to read. A test should be understandable in isolation.

### DRY Extraction Decision Tree

```
Is logic duplicated in 2+ places?
         |
        YES
         |
         v
Is it in the same service/module? ──YES──> Extract to shared utility
         |
        NO
         |
         v
Is it behavior (a process)?  ──YES──> Consider a shared service (API)
         |
        NO (it's a data model / contract)
         |
         v
Share the CONTRACT (OpenAPI/proto), not the implementation
```

### DRY Compliant Code Structure
```
src/
  domain/
    rules/
      AgeVerificationRule.java       ← Single place for age logic
      CurrencyValidationRule.java    ← Single place for currency logic
  api/
    OrderController.java             ← uses AgeVerificationRule
    UserController.java              ← uses AgeVerificationRule
  service/
    CheckoutService.java             ← uses both rules
```

## 🔟 Why & How Summary (Executive-Level Wrap-Up)
## ────────────────────────────────────

**Why DRY matters:**
- A single source of truth means bug fixes, rule changes, and improvements propagate once — not N times
- Reduces the "where is this defined?" cognitive overhead
- Dramatically reduces regression risk during refactors

**How it works:**
- Extract repeated logic into named, tested functions or classes
- Centralize configuration in one canonical location
- Treat business rules as first-class code artifacts with single ownership
- In distributed systems: share contracts, not code

**Key trade-offs:**
- Too little DRY: inconsistency, shotgun surgery, regression bugs
- Too much DRY: wrong abstractions, deployment coupling, overly clever code
- Sweet spot: abstract at the third repetition, within service boundaries, for clearly identical semantics
