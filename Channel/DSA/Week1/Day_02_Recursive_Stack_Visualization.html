Section 2: Anatomy of a Stack Frame

Every time a function is called, the system creates a stack frame — a private workspace for that specific invocation.

┌───────────────────────────────────────────┐ │ STACK FRAME for factorial(4) │ ├───────────────────────────────────────────┤ │ │ │ Return Address: line 7 in main() │ │ → "Where do I go back when I'm done?" │ │ │ │ Parameters: n = 4 │ │ → "What arguments was I given?" │ │ │ │ Local Variables: result = ??? │ │ → "My private workspace" │ │ │ │ Saved State: CPU registers │ │ → "What was happening before I was called?"│ │ │ └───────────────────────────────────────────┘
Key Understanding

Each recursive call gets its OWN frame with its OWN copy of variables. When factorial(4) calls factorial(3), the n=4 doesn't get overwritten. It's safely stored in its own frame, waiting.

The Stack is LIFO (Last-In, First-Out)

Think of it as a stack of plates: You can only add to the TOP → PUSH (new function call) You can only remove from TOP → POP (function returns) ┌─────────────┐ │ factorial(1) │ ← TOP (most recent, will finish first) ├─────────────┤ │ factorial(2) │ ├─────────────┤ │ factorial(3) │ ├─────────────┤ │ factorial(4) │ ├─────────────┤ │ main() │ ← BOTTOM (first call, will finish last) └─────────────┘
⚠️ Why This Matters in Interviews

When an interviewer asks "What's the space complexity?" for a recursive solution, they're asking: "How tall does this stack get?" The maximum simultaneous frames = the space complexity.

Section 4: The Two Phases — Winding & Unwinding

⬇️ WINDING Phase (Going Deeper)

What happens: • New frames are PUSHED onto stack • Each call SUSPENDS the caller • No computation happens yet • Stack GROWS Analogy: Like dominos being SET UP (none have fallen yet) Stack behavior: [main] [main][f(5)] [main][f(5)][f(4)] [main][f(5)][f(4)][f(3)] [main][f(5)][f(4)][f(3)][f(2)] [main][f(5)][f(4)][f(3)][f(2)][f(1)] ↑ PEAK MEMORY ↑

⬆️ UNWINDING Phase (Coming Back)

What happens: • Frames are POPPED from stack • Each return RESUMES the caller • Computation happens NOW • Stack SHRINKS Analogy: Like dominos FALLING (chain reaction of returns) Stack behavior: [main][f(5)][f(4)][f(3)][f(2)][f(1)] [main][f(5)][f(4)][f(3)][f(2)] ←ret 1 [main][f(5)][f(4)][f(3)] ←ret 2 [main][f(5)][f(4)] ←ret 6 [main][f(5)] ←ret 24 [main] ←ret 120 ↑ DONE ↑
💡 The Suspension Insight

During the winding phase, factorial(5) is frozen in time. It's sitting in memory with n=5, patiently waiting for factorial(4) to return. It cannot proceed. It cannot do anything. It just... waits. And factorial(4) is also frozen, waiting for factorial(3). All of them are suspended simultaneously. Only the BASE CASE actually executes and starts the chain reaction of returns.

Section 5: Head Recursion — Stack Behavior

function headPrint(n) { if (n === 0) return; // base case headPrint(n - 1); // recurse FIRST console.log(n); // work AFTER } headPrint(4); // Output: 1, 2, 3, 4

Observation

ALL frames exist simultaneously before ANY work happens. The printing only occurs during unwinding. This is why head recursion uses O(n) stack space with NO possibility of optimization — every frame has pending work.

Section 6: Tail Recursion — Stack Behavior

function tailPrint(n) { if (n === 0) return; // base case console.log(n); // work FIRST tailPrint(n - 1); // recurse LAST } tailPrint(4); // Output: 4, 3, 2, 1

💡 The Optimization Opportunity

Notice: when tailPrint(3) calls tailPrint(2), there's NOTHING left for tailPrint(3) to do. Its frame is dead weight. A smart compiler can reuse that frame instead of creating a new one → O(1) space instead of O(n).

With Tail Call Optimization (TCO)

WITHOUT TCO: WITH TCO: [tail(4)] prints 4 [tail(4)] prints 4 [tail(4)][tail(3)] prints 3 [tail(3)] prints 3 ← frame REUSED [4][3][tail(2)] prints 2 [tail(2)] prints 2 ← frame REUSED [4][3][2][tail(1)] prints 1 [tail(1)] prints 1 ← frame REUSED [4][3][2][1][tail(0)] ret [tail(0)] returns ← frame REUSED Stack depth: O(n) Stack depth: O(1) !!!

Section 7: Fibonacci — Branching Recursion Visualization

Fibonacci creates a tree of calls, not a linear chain. This is where visualization becomes critical.

function fib(n) { if (n <= 1) return n; return fib(n - 1) + fib(n - 2); }

Call Tree for fib(5)

fib(5) / \ fib(4) fib(3) / \ / \ fib(3) fib(2) fib(2) fib(1) / \ / \ / \ | fib(2) fib(1) fib(1) fib(0) fib(1) fib(0) → 1 / \ | | | | fib(1) fib(0) 1 1 0 1 | | 1 0 Total calls: 15 Unique subproblems: 6 (fib(0) through fib(5)) Redundant calls: 9 ← THIS is why naive fibonacci is O(2^n)
🚨 Critical Interview Point

Stack depth ≠ Total calls!
• Total calls = 15 (time complexity = O(2^n))
• Max stack depth = 5 (space complexity = O(n))

Why? Because the left subtree finishes and its frames are popped BEFORE the right subtree starts. The stack never holds all 15 frames simultaneously.

Stack at Different Points in Time

Time A: Deepest point (leftmost path) [main][fib(5)][fib(4)][fib(3)][fib(2)][fib(1)] ← depth 5 Time B: After left subtree of fib(3) done, starting right [main][fib(5)][fib(4)][fib(3)][fib(0)] ← depth 4 Time C: fib(4)'s left done, starting right subtree [main][fib(5)][fib(4)][fib(2)][fib(1)] ← depth 4 Maximum depth is always O(n) because one branch fully resolves before the sibling branch begins.

Section 8: Stack Overflow — When Recursion Kills

What Causes Stack Overflow?

Default stack sizes: • Java: ~512KB — ~1024 frames typically • Python: ~1000 frames (sys.getrecursionlimit()) • C/C++: ~1-8MB — ~10,000-100,000 frames • JavaScript: ~10,000-25,000 frames (engine dependent) If recursion depth > stack limit → CRASH

Example: Dangerous Recursion

// This WILL crash for large n function sum(n) { if (n === 0) return 0; return n + sum(n - 1); } sum(1000000); // 💥 Stack Overflow! // Safe iterative version function sum(n) { let total = 0; for (let i = 1; i <= n; i++) total += i; return total; }
⚠️ Interview Rule of Thumb

If the problem says n can be up to 10^5 or 10^6, and your recursive solution has depth O(n), mention the stack overflow risk to the interviewer. Then offer an iterative alternative or tail-recursive optimization. This shows maturity.

Detection Patterns

Section 9: Multiple Examples — See the Pattern

sum(4) = 4 + 3 + 2 + 1 = 10

WINDING: sum(4) → needs 4 + sum(3) [waiting] sum(3) → needs 3 + sum(2) [waiting] sum(2) → needs 2 + sum(1) [waiting] sum(1) → needs 1 + sum(0) [waiting] sum(0) → BASE CASE → returns 0 UNWINDING: sum(0) returns 0 sum(1): 1 + 0 = 1 → returns 1 sum(2): 2 + 1 = 3 → returns 3 sum(3): 3 + 3 = 6 → returns 6 sum(4): 4 + 6 = 10 → returns 10 ✓ Stack depth: 5 frames (including sum(0))

power(2, 4) = 2^4 = 16

Recursive logic: power(x, n) = x * power(x, n-1) WINDING: power(2,4) → needs 2 * power(2,3) [waiting] power(2,3) → needs 2 * power(2,2) [waiting] power(2,2) → needs 2 * power(2,1) [waiting] power(2,1) → needs 2 * power(2,0) [waiting] power(2,0) → BASE CASE → returns 1 UNWINDING: power(2,0) returns 1 power(2,1): 2 * 1 = 2 power(2,2): 2 * 2 = 4 power(2,3): 2 * 4 = 8 power(2,4): 2 * 8 = 16 ✓ Stack depth: 5 frames

reverse("hello") = "olleh"

Recursive logic: reverse(s) = reverse(s[1:]) + s[0] WINDING: reverse("hello") → reverse("ello") + "h" [waiting] reverse("ello") → reverse("llo") + "e" [waiting] reverse("llo") → reverse("lo") + "l" [waiting] reverse("lo") → reverse("o") + "l" [waiting] reverse("o") → BASE CASE (len≤1) → returns "o" UNWINDING: returns "o" reverse("lo"): "o" + "l" = "ol" reverse("llo"): "ol" + "l" = "oll" reverse("ello"): "oll" + "e" = "olle" reverse("hello"): "olle" + "h" = "olleh" ✓ Stack depth: 5 frames (length of string)

Section 10: Drawing Stack Diagrams — Your Interview Superpower

In interviews, drawing the call stack on the whiteboard is the fastest way to prove you understand recursion. Here's the technique:

The 4-Step Diagram Method

Step 1: Draw a vertical column (the stack) Step 2: Push frames top-to-bottom as calls happen Step 3: Write the WAITING expression in each frame Step 4: Fill in return values bottom-to-top Example for factorial(4): ┌──────────────────────────┐ │ factorial(4) │ ← CALLED FIRST │ waiting: 4 * f(3) = ? │ │ RETURNS: 4 * 6 = 24 │ ← RESOLVED LAST ├──────────────────────────┤ │ factorial(3) │ │ waiting: 3 * f(2) = ? │ │ RETURNS: 3 * 2 = 6 │ ├──────────────────────────┤ │ factorial(2) │ │ waiting: 2 * f(1) = ? │ │ RETURNS: 2 * 1 = 2 │ ├──────────────────────────┤ │ factorial(1) │ ← CALLED LAST │ BASE CASE │ │ RETURNS: 1 │ ← RESOLVED FIRST └──────────────────────────┘
Practice This

Take ANY recursive function. Before running it, draw the stack diagram on paper. Then verify by running the code with print statements. Do this 10 times and you'll never be confused by recursion again.

Section 11: Variable Scope — Each Frame is Isolated

A common misconception: "When factorial(3) sets n=3, doesn't that overwrite factorial(4)'s n=4?"

NO. Each frame has its own SEPARATE copy of every variable.

┌───────────────────────────────────────────────┐ │ factorial(1): n = 1 (its OWN n) │ ← TOP ├───────────────────────────────────────────────┤ │ factorial(2): n = 2 (its OWN n) │ ├───────────────────────────────────────────────┤ │ factorial(3): n = 3 (its OWN n) │ ├───────────────────────────────────────────────┤ │ factorial(4): n = 4 (its OWN n) │ ← BOTTOM └───────────────────────────────────────────────┘ These are FOUR different variables named "n", each living in their own isolated stack frame. They don't interfere. THIS IS WHY: When factorial(1) returns and its frame is popped, factorial(2)'s frame still has n=2 intact. Nothing was overwritten.
🚨 The Exception — Shared/Global State

If your recursive function modifies a global variable, an array passed by reference, or a class field, then ALL frames see the same data. This is how backtracking works (and why it needs careful undo operations). But local variables and parameters are always isolated per frame.

  • Side-by-side visualization
