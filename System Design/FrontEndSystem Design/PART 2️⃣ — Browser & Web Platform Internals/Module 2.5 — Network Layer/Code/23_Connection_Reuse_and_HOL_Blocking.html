🏎️ Why HTTP/3 / QUIC Matters

HTTP/2 flaw: Runs over TCP. If a packet is lost, TCP retransmits it before delivering any subsequent packets — blocking ALL streams in the connection. This is TCP-level HOL blocking.

QUIC solution: Runs over UDP. Each stream is independently flow-controlled. Packet loss on stream A doesn't block stream B. Critical for mobile users (packet loss ~5-8% on cellular).

Real impact: Google found QUIC improved YouTube rebuffering by 18% and Google Search by 3% — at their scale, this is billions of dollars of user experience improvement.

🔑 Key Insights for Interviews

HTTP/1.1 HOL: Application-level — a slow response blocks later responses in the pipelining queue per connection. Browsers work around it with 6 parallel connections per origin.
HTTP/2 HOL: Transport-level — multiplexing eliminates app HOL, but a lost TCP packet blocks ALL multiplexed streams until retransmitted.
HTTP/3 HOL: QUIC handles retransmission per-stream — lost packets on stream 2 don't block streams 1 or 3. True HOL elimination.

📉 Real-World Impact — SAP Context

SAP enterprise users on corporate VPNs (lossy networks) see 3–8% packet loss rates. Switching our API server to HTTP/3 reduced P95 load time by 340ms for these users.

For HTTP/2: we enable Connection: keep-alive (default in HTTP/1.1+) and preconnect to critical origins to amortise the TCP/TLS handshake cost across many requests.

💡 Connection Optimization Patterns

// 1. Preconnect — warm up TCP+TLS before you need it
<link rel="preconnect" href="https://api.yourapp.com">
<link rel="preconnect" href="https://fonts.googleapis.com" crossorigin>
// Saves: TCP 3-way handshake (50-150ms) + TLS negotiation (50-100ms)

// 2. DNS Prefetch — resolve hostname early (cheaper than preconnect)
<link rel="dns-prefetch" href="https://analytics.third-party.com">
// Use for third parties you'll eventually connect to but don't need immediately

// 3. Domain sharding — HTTP/1.1 only workaround (AVOID with HTTP/2!)
// HTTP/1.1: browsers limit to 6 connections per domain
// Sharding to static1.cdn.com + static2.cdn.com = 12 connections
// HTTP/2: NEVER shard — multiplexing is more efficient on 1 connection

// 4. Fetch priority hints — tell browser what matters most
<img src="hero.jpg" fetchpriority="high">  // key visual = high
<img src="below-fold.jpg" fetchpriority="low">  // defer bandwidth
<script src="analytics.js" fetchpriority="low" defer></script>

// 5. HTTP/2 server push alternative: 103 Early Hints
// Server sends critical resource hints BEFORE the main response
// HTTP/1.1 103:
// Link: </main.css>; rel=preload; as=style
// Link: </app.js>; rel=preload; as=script
// (Then continues processing the full response)

// 6. Keep-Alive header (HTTP/1.1) — persist TCP connection
// Default in HTTP/1.1, configure server idle timeout:
// Nginx: keepalive_timeout 65;  (seconds)
// Node.js HTTP server:
const server = http.createServer(app);
server.keepAliveTimeout = 65000; // 65 seconds
server.headersTimeout = 66000;   // must be > keepAliveTimeout

🔍 Connection Header Inspection — DevTools

// Check which protocol a request uses in DevTools → Network panel
// Protocol column shows: h2 (HTTP/2), h3 (HTTP/3), http/1.1

// Check via JavaScript (Navigation Timing API):
const nav = performance.getEntriesByType('navigation')[0];
console.log('Next Hop Protocol:', nav.nextHopProtocol);
// → 'h2' or 'h3'

// Resource Timing for each fetch:
const resources = performance.getEntriesByType('resource');
resources.forEach(r => {
  console.log(r.name, r.nextHopProtocol, `${r.duration.toFixed(0)}ms`);
});

// Check connection reuse (TCP reuse = connectEnd === connectStart)
resources.forEach(r => {
  const reusedConnection = r.connectStart === r.connectEnd;
  console.log(r.name, reusedConnection ? '♻️ reused' : '🆕 new connection');
});
