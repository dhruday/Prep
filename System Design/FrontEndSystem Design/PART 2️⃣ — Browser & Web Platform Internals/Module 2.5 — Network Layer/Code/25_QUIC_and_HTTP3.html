HTTP/1.1 vs HTTP/2 vs HTTP/3 — What each solved

FeatureHTTP/1.1 (TCP)HTTP/2 (TCP+TLS)HTTP/3 (QUIC+UDP)
Connection setup TCP 1.5 RTT + TLS 2 RTT TCP 1 RTT + TLS 1 RTT 1 RTT (or 0-RTT resume)
Multiplexing ❌ One request/connection ✅ Many streams per connection ✅ Many streams per connection
HOL Blocking (App) Yes — serial requests No — multiplexed No — multiplexed
HOL Blocking (Transport) Yes — TCP ordering Yes — TCP ordering blocks all streams No — per-stream delivery
Connection migration ❌ IP change = reconnect ❌ IP change = reconnect ✅ Connection ID survives IP change
TLS required Optional Mandatory (browsers enforce) TLS 1.3 built into protocol
Header compression ❌ Plain text headers HPACK (H2) QPACK (fixed HPACK issues)
Underlying transport TCP TCP UDP (QUIC manages reliability)

HTTP/1.1

• 6 parallel connections max
• Each needs its own handshake
• Head-of-line within each connection
• Domain sharding (hack)
• Concatenated bundles (hack)

HTTP/2

• 1 multiplexed connection
• App-level HOL solved ✅
• TCP HOL still present ❌
• HPACK header compression
• Server Push (largely unused)

HTTP/3 / QUIC

• Transport HOL solved ✅
• 0-RTT resumption ✅
• Connection migration ✅
• TLS 1.3 mandatory ✅
• QPACK header compression

Detect HTTP/3 in the browser (TypeScript)

// Check which protocol a resource actually used
function auditProtocols(): void {
  const nav = performance.getEntriesByType('navigation')[0] as PerformanceNavigationTiming;
  console.log(`Page: ${nav.nextHopProtocol}`); // 'h3' | 'h2' | 'http/1.1'

  performance.getEntriesByType('resource').forEach(entry => {
    const r = entry as PerformanceResourceTiming;
    const icon = r.nextHopProtocol === 'h3' ? '⚡'
               : r.nextHopProtocol === 'h2' ? '✅' : '⚠️';
    console.log(`${icon} [${r.nextHopProtocol}] ${r.name}`);
  });
}

// Server header to advertise HTTP/3:
// Alt-Svc: h3=":443"; ma=2592000

Transport-level Head-of-Line Blocking

HTTP/2 multiplexes streams above TCP. But TCP requires ordered delivery — if packet 5 drops, ALL HTTP/2 streams stall waiting for it. QUIC streams are independent: drop in stream 2 only stalls stream 2.

Drop at packet 4

Why TCP can't fix this

TCP is implemented in OS kernels. IETF has standardised improvements (MPTCP, etc.) but they require OS upgrades which take years — and corporate machines stay on old OSes for a decade.

Google's approach with QUIC: implement the transport in userspace as part of the browser. Ship updates via Chrome releases (every 6 weeks) without needing OS changes.

QUIC runs over UDP which most firewalls allow. QUIC's packet format is designed to be extensible without breaking older middleboxes.

0-RTT Resumption — How it works

FIRST VISIT (1-RTT)
1. ClientHello (QUIC Initial packet)
2. ServerHello + TLS cert + Session Ticket
3. Client: completes TLS, stores session ticket
4. First HTTP request → 1 RTT total
RETURNING VISIT (0-RTT)
1. Client: attaches session ticket to first packet
2. HTTP request piggybacks in same UDP datagram
3. Server can serve response immediately
⚠️ Only safe for GET (replay-attack risk for POST!)
0-RTT Security Warning: Session ticket encrypts with a pre-shared key → attacker who intercepts it can replay the 0-RTT data. Always limit 0-RTT to idempotent requests (GET, HEAD). Never accept 0-RTT for state-changing operations (POST/PUT/DELETE/payments).

Connection Migration Demo

TCP connections are a 4-tuple (src IP : src port → dest IP : dest port). Switch networks → IP changes → TCP connection dies. QUIC uses a Connection ID, abstracting over the 4-tuple.
