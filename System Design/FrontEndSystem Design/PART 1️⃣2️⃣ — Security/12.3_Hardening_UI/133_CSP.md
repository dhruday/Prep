# 133. CSP (Content Security Policy)

────────────────────────────────────
## 1. High-Level Explanation (Frontend Interview Level)
────────────────────────────────────

**Content Security Policy (CSP)** is a security standard that helps prevent cross-site scripting (XSS), clickjacking, and other code injection attacks by declaring which dynamic resources are allowed to load and execute on a web page.

### **What It Is:**
An HTTP header that defines a whitelist of trusted sources for:
- Scripts (JavaScript)
- Styles (CSS)
- Images, fonts, media
- iframe sources
- Form submission targets
- WebSocket/fetch destinations

### **Why It Exists:**
- **XSS Mitigation**: Primary defense against script injection
- **Defense-in-Depth**: Even if XSS exists, CSP limits damage
- **Reduced Attack Surface**: Blocks inline scripts, eval(), unsafe practices
- **Clickjacking Protection**: frame-ancestors directive
- **Data Exfiltration Prevention**: Restricts where data can be sent

### **When and Where Used:**
- Every production web application
- Single Page Applications (SPAs)
- Content Management Systems
- E-commerce platforms
- Banking/healthcare apps with sensitive data
- Sites handling user-generated content

### **Role in Large-Scale Applications:**
At FAANG scale, CSP is mandatory:
- Google enforces strict CSP on all properties
- Facebook uses CSP with nonces for inline scripts
- GitHub implements progressive CSP rollout
- One XSS vulnerability × 1B users = massive breach
- CSP reduces blast radius even when vulnerabilities exist

## 2. Deep-Dive Explanation (Senior / Staff Level)
────────────────────────────────────

### **A. CSP Directives**

#### **1. Script Sources**
```javascript
// Basic script-src
Content-Security-Policy: script-src 'self' https://cdn.example.com

// Breakdown:
// - 'self': Allow scripts from same origin
// - https://cdn.example.com: Allow from CDN
// - Blocks: inline scripts, eval(), inline event handlers
```

**Special Keywords:**
- `'self'`: Same origin (https://example.com)
- `'none'`: Block all sources
- `'unsafe-inline'`: Allow inline scripts (insecure, avoid)
- `'unsafe-eval'`: Allow eval(), Function() (insecure, avoid)
- `'strict-dynamic'`: Trust dynamically added scripts from allowed scripts
- `'nonce-abc123'`: Allow script with matching nonce attribute
- `'sha256-...'`: Allow script if hash matches

#### **2. Style Sources**
```javascript
Content-Security-Policy: style-src 'self' 'unsafe-inline' https://fonts.googleapis.com
```

**Why unsafe-inline for styles:**
Many frameworks inject styles dynamically (React styled-components, CSS-in-JS). Safer alternatives: nonces or hashes.

#### **3. Other Important Directives**

```javascript
Content-Security-Policy: 
  default-src 'self';  // Fallback for unspecified directives
  script-src 'self' https://cdn.example.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;  // Allow images from HTTPS + data URLs
  font-src 'self' https://fonts.gstatic.com;
  connect-src 'self' https://api.example.com;  // fetch/XHR/WebSocket
  frame-src 'none';  // Disallow iframes
  frame-ancestors 'none';  // Clickjacking protection
  base-uri 'self';  // Restrict <base> tag
  form-action 'self';  // Restrict form submissions
  upgrade-insecure-requests;  // Auto-upgrade HTTP to HTTPS
  block-all-mixed-content;  // Block HTTP resources on HTTPS page
```

### **B. Implementation Strategies**

#### **1. Report-Only Mode (Testing)**
```javascript
// Doesn't block, only reports violations
Content-Security-Policy-Report-Only: script-src 'self'; report-uri /csp-report

// Backend endpoint receives violation reports
app.post('/csp-report', (req, res) => {
  const report = req.body;
  console.log('CSP Violation:', JSON.stringify(report, null, 2));
  
  // Log to monitoring service
  sendToSentry('csp_violation', report);
  
  res.status(204).end();
});
```

**Violation Report Example:**
```json
{
  "csp-report": {
    "document-uri": "https://example.com/page",
    "violated-directive": "script-src",
    "blocked-uri": "https://evil.com/malicious.js",
    "line-number": 23,
    "column-number": 15,
    "source-file": "https://example.com/page",
    "status-code": 200
  }
}
```

#### **2. Progressive Rollout**
```javascript
// Phase 1: Report-Only on 10% of traffic
if (Math.random() < 0.1) {
  res.setHeader('Content-Security-Policy-Report-Only', policy);
}

// Phase 2: Analyze reports, fix violations

// Phase 3: Enforce on 10% traffic
if (Math.random() < 0.1) {
  res.setHeader('Content-Security-Policy', policy);
}

// Phase 4: Gradually increase to 100%
```

### **C. Handling Inline Scripts & Styles**

#### **1. Nonce-Based CSP (Recommended)**
```javascript
// Server-side: Generate nonce per request
const nonce = crypto.randomBytes(16).toString('base64');

res.setHeader(
  'Content-Security-Policy',
  `script-src 'self' 'nonce-${nonce}'`
);

// In HTML template
res.send(`
  <script nonce="${nonce}">
    console.log('This script is allowed');
  </script>
  
  <script>
    console.log('This script is BLOCKED - no nonce');
  </script>
`);
```

**React Example (Next.js):**
```javascript
// pages/_document.js
import { Html, Head, Main, NextScript } from 'next/document';
import crypto from 'crypto';

export default function Document() {
  const nonce = crypto.randomBytes(16).toString('base64');
  
  return (
    <Html>
      <Head nonce={nonce}>
        <script nonce={nonce} dangerouslySetInnerHTML={{
          __html: `window.config = ${JSON.stringify(config)};`
        }} />
      </Head>
      <body>
        <Main />
        <NextScript nonce={nonce} />
      </body>
    </Html>
  );
}

// Middleware to set CSP header with nonce
export function middleware(request) {
  const nonce = crypto.randomBytes(16).toString('base64');
  const csp = `script-src 'self' 'nonce-${nonce}' 'strict-dynamic'`;
  
  const response = NextResponse.next();
  response.headers.set('Content-Security-Policy', csp);
  
  return response;
}
```

#### **2. Hash-Based CSP**
```javascript
// For static inline scripts
const scriptContent = "console.log('Hello');";
const hash = crypto.createHash('sha256').update(scriptContent).digest('base64');

res.setHeader(
  'Content-Security-Policy',
  `script-src 'self' 'sha256-${hash}'`
);

// HTML
res.send(`
  <script>console.log('Hello');</script>  <!-- Allowed -->
  <script>console.log('World');</script>  <!-- BLOCKED -->
`);
```

#### **3. Strict Dynamic (Modern, Recommended)**
```javascript
Content-Security-Policy: script-src 'nonce-abc123' 'strict-dynamic'

// With strict-dynamic:
// - Scripts with nonce can dynamically create more scripts
// - Those created scripts are trusted automatically
// - Simplifies CSP for modern frameworks
```

**Example:**
```html
<script nonce="abc123">
  // This script is trusted (has nonce)
  const script = document.createElement('script');
  script.src = 'https://anywhere.com/script.js';  // Also trusted!
  document.head.appendChild(script);
</script>
```

### **D. Common CSP Patterns**

#### **1. Strict CSP (Google Recommended)**
```javascript
// Nonce-based with strict-dynamic
Content-Security-Policy:
  script-src 'nonce-{RANDOM}' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
```

**Benefits:**
- Blocks all inline scripts except those with nonce
- Allows dynamic script loading from trusted scripts
- Simple whitelist (just your nonce)
- No need to list CDN domains

#### **2. Moderate CSP (Practical for Existing Apps)**
```javascript
Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.example.com 'unsafe-inline';
  style-src 'self' 'unsafe-inline';
  img-src 'self' https: data:;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
```

**Trade-off:** Allows unsafe-inline (less secure) but easier to implement.

#### **3. Report-Only for Third-Party Scripts**
```javascript
// Allow your scripts, report on third-party
Content-Security-Policy:
  script-src 'self';
  report-uri /csp-report;

Content-Security-Policy-Report-Only:
  script-src 'self' https://analytics.com https://ads.com;
  report-uri /csp-report-testing;
```

### **E. CSP and Modern Frameworks**

#### **1. React / Create React App**
```javascript
// public/index.html
<meta http-equiv="Content-Security-Policy" content="
  default-src 'self';
  script-src 'self' 'unsafe-inline' 'unsafe-eval';
  style-src 'self' 'unsafe-inline';
">

// OR set via server (preferred)
// server.js
app.use((req, res, next) => {
  res.setHeader('Content-Security-Policy', 
    "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';"
  );
  next();
});
```

**Challenge:** CRA uses inline scripts during development. Production builds are cleaner.

#### **2. Next.js**
```javascript
// next.config.js
const ContentSecurityPolicy = `
  default-src 'self';
  script-src 'self' 'unsafe-eval' 'unsafe-inline';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  font-src 'self';
`;

module.exports = {
  async headers() {
    return [
      {
        source: '/(.*)',
        headers: [
          {
            key: 'Content-Security-Policy',
            value: ContentSecurityPolicy.replace(/\n/g, '')
          }
        ]
      }
    ];
  }
};
```

#### **3. Vue / Nuxt**
```javascript
// nuxt.config.js
export default {
  render: {
    csp: {
      hashAlgorithm: 'sha256',
      policies: {
        'default-src': ["'self'"],
        'script-src': ["'self'", "'unsafe-inline'"],
        'style-src': ["'self'", "'unsafe-inline'"]
      }
    }
  }
}
```

### **F. CSP Bypass Techniques (What Attackers Do)**

#### **1. JSONP Endpoints**
```javascript
// If CSP allows:
script-src 'self' https://trusted-site.com

// But trusted-site.com has JSONP endpoint:
<script src="https://trusted-site.com/jsonp?callback=alert(1)"></script>

// CSP allows it (whitelisted domain)
// But executes attacker's code
```

**Defense:** Don't whitelist domains with JSONP endpoints, or use strict-dynamic.

#### **2. AngularJS CSP Bypass**
```javascript
// Old AngularJS versions allowed:
<div ng-app ng-csp>
  {{constructor.constructor('alert(1)')()}}
</div>

// Even with CSP, this executes
```

**Defense:** Update framework versions, use CSP v3 with strict-dynamic.

#### **3. Base Tag Injection**
```html
<base href="https://attacker.com/">
<script src="/malicious.js"></script>  <!-- Loads from attacker.com -->
```

**Defense:** `base-uri 'self'` in CSP.

### **H. Performance Implications**

#### **1. Header Size**
```javascript
// Large CSP headers slow down every request
// BAD - 2KB CSP header
Content-Security-Policy: script-src 'self' https://cdn1.com https://cdn2.com https://cdn3.com ... (100 domains)

// GOOD - Small CSP with strict-dynamic
Content-Security-Policy: script-src 'nonce-abc123' 'strict-dynamic'
```

#### **2. Report Collection Overhead**
```javascript
// Millions of violation reports can overwhelm servers
// Solution: Sample reports
if (Math.random() < 0.01) { // 1% sampling
  res.setHeader('Content-Security-Policy', `...;report-uri /csp-report`);
}
```

---

### **I. Common Pitfalls**

#### **❌ Using unsafe-inline in Production**
```javascript
// INSECURE
Content-Security-Policy: script-src 'self' 'unsafe-inline'
// Defeats the purpose of CSP - allows XSS
```

#### **❌ Overly Permissive Whitelists**
```javascript
// WEAK
Content-Security-Policy: script-src 'self' https: data:
// Allows scripts from ANY HTTPS domain!
```

#### **❌ Forgetting frame-ancestors**
```javascript
// INCOMPLETE
Content-Security-Policy: script-src 'self'
// Still vulnerable to clickjacking!

// ADD:
Content-Security-Policy: script-src 'self'; frame-ancestors 'none'
```

#### **❌ Not Testing Before Enforcing**
```javascript
// DON'T go straight to enforcement
Content-Security-Policy: ... // Breaks production!

// DO use report-only first
Content-Security-Policy-Report-Only: ...
```

## 3. Clear Real-World Examples
────────────────────────────────────

### **Example 1: GitHub's CSP**
```javascript
Content-Security-Policy:
  default-src 'none';
  base-uri 'self';
  child-src github.com/assets-cdn;
  connect-src 'self' *.github.com;
  font-src github.githubassets.com;
  form-action 'self' github.com;
  frame-ancestors 'none';
  frame-src render.githubusercontent.com;
  img-src 'self' data: github.githubassets.com;
  script-src github.githubassets.com;
  style-src 'unsafe-inline' github.githubassets.com;
```

**Key points:**
- Very restrictive default-src 'none'
- Specific whitelists for each resource type
- frame-ancestors 'none' prevents clickjacking

### **Example 2: Google's Strict CSP**
```javascript
Content-Security-Policy:
  script-src 'nonce-random123' 'strict-dynamic' 'unsafe-inline';
  object-src 'none';
  base-uri 'self';
  report-uri https://csp.withgoogle.com/csp/...;
```

**Benefits:**
- Nonce-based (secure against XSS)
- strict-dynamic (framework-friendly)
- unsafe-inline ignored by modern browsers when nonce present

### **Example 3: Banking App**
```javascript
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-abc123';
  style-src 'self' 'nonce-abc123';
  img-src 'self' https://secure-cdn.bank.com;
  connect-src 'self' https://api.bank.com;
  frame-src 'none';
  frame-ancestors 'none';
  base-uri 'self';
  form-action 'self';

  block-all-mixed-content;
```

**Ultra-strict for financial data protection.**

## 4. Interview-Oriented Explanation
────────────────────────────────────

### **Sample Answer**

> *"CSP is an HTTP header that whitelists trusted sources for scripts, styles, and other resources. It's our primary defense against XSS—even if an attacker finds an injection point, CSP prevents their script from executing."*
>
> *"I'd implement CSP in phases. First, deploy in report-only mode to identify violations without breaking functionality. Analyze reports, fix issues, then enforce gradually. For modern apps, I'd use nonce-based CSP with strict-dynamic—this allows our framework to work while blocking inline scripts without nonces."*
>
> *"Key directives: script-src for JavaScript, style-src for CSS, frame-ancestors to prevent clickjacking, and connect-src to control API endpoints. I'd also add upgrade-insecure-requests to auto-upgrade HTTP to HTTPS."*
>
> *"The challenge is balancing security with developer experience. Frameworks like React often use inline styles. Solutions: nonces for inline scripts, 'unsafe-inline' for styles (less risky), or migrate to external stylesheets."*
>
> *"At scale, CSP violation reports can overwhelm servers. I'd sample reports (1-10%) and aggregate by violation type in a monitoring dashboard."*

### **Follow-Up Questions**

**Q: "What's the difference between nonce and hash?"**  
**A:** *"Both allow specific inline scripts. Nonces are random per request—the server generates a nonce, includes it in CSP header and script tags. Hashes are for static scripts—you compute SHA-256 hash of script content and add to CSP. Nonces are better for dynamic apps (each request has unique nonce). Hashes work for static sites where script content never changes."*

**Q: "How do you handle third-party scripts with CSP?"**  
**A:** *"Three approaches: 1) Whitelist the third-party domain in script-src. Risk: that domain could serve malicious scripts. 2) Use strict-dynamic—load third-party via your trusted script. 3) Proxy through your backend—fetch third-party script server-side, serve from your domain. I prefer #2 for flexibility, #3 for maximum security."*

## 6. Why & How Summary
────────────────────────────────────

### **Why It Matters**
- **XSS Mitigation**: Primary defense layer
- **Defense-in-Depth**: Limits damage even when vulnerabilities exist
- **Compliance**: Required by security standards (PCI-DSS)
- **Trust**: Shows commitment to security

### **How It Works**
1. **Whitelist**: Define trusted sources per resource type
2. **Block**: Browser refuses resources from untrusted sources
3. **Report**: Send violation reports to monitoring endpoint
4. **Iterate**: Analyze reports, refine policy
5. **Enforce**: Gradually roll out enforcement

**Key Principle:** Default deny, explicit allow
