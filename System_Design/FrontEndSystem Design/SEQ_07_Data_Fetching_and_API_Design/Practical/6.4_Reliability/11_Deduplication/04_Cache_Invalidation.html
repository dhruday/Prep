The Invalidation Problem

After a successful mutation (POST/PUT/DELETE), cached data becomes stale. Without invalidation, UI shows outdated information until the cache expires naturally.

"There are only two hard things in CS: cache invalidation, naming things, and off-by-one errors."

React Query Invalidation Flow

1. User clicks "Add Product"
2. useMutation fires POST /api/rest/products
3. onSuccess → queryClient.invalidateQueries(['products'])
4. All active observers of ['products'] refetch
5. UI updates with fresh data

staleTime Controls Freshness

staleTime: 0        → data immediately stale → refetch on every mount
staleTime: 30_000   → fresh for 30s → no refetch if recent
staleTime: Infinity  → never stale → only refetch on explicit invalidation

Higher staleTime = fewer requests, but more risk of showing outdated data.

Mutation with Invalidation

const mutation = useMutation({
  mutationFn: (newProduct) =>
    fetch('/api/rest/products', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(newProduct),
    }),

  onSuccess: () => {
    // Invalidate → marks cache stale → triggers refetch
    queryClient.invalidateQueries({ queryKey: ['products'] });
  },
});

Granular Invalidation Patterns

// Exact match — only ['products']
queryClient.invalidateQueries({
  queryKey: ['products'],
  exact: true,
});

// Prefix match — ['products'], ['products', 1], ['products', {page:2}]
queryClient.invalidateQueries({
  queryKey: ['products'],
});

// Predicate — custom logic
queryClient.invalidateQueries({
  predicate: (query) =>
    query.queryKey[0] === 'products' &&
    query.state.dataUpdatedAt < mutationTimestamp,
});

Optimistic Update + Invalidation

useMutation({
  mutationFn: updateProduct,
  onMutate: async (newData) => {
    await queryClient.cancelQueries(['products']);
    const prev = queryClient.getQueryData(['products']);
    queryClient.setQueryData(['products'], old =>
      old.map(p => p.id === newData.id ? newData : p)
    );
    return { prev };
  },
  onError: (err, vars, ctx) => {
    queryClient.setQueryData(['products'], ctx.prev); // rollback
  },
  onSettled: () => {
    queryClient.invalidateQueries(['products']); // refetch truth
  },
});

Invalidation Strategies

Strategy              │ When to Use
──────────────────────┼──────────────────────────────────
invalidateQueries     │ After mutations — simple & reliable
setQueryData          │ Optimistic UI — instant feedback
resetQueries          │ Logout/cleanup — wipe observer state
removeQueries         │ Destroy cache entry entirely
refetchQueries        │ Force refetch even if fresh

staleTime Guidelines

• 0 (default) — Good for frequently changing data (chat, feeds)
• 30s–5min — Good for user-generated content lists
• 10min–1hr — Good for reference data (categories, config)
• Infinity — Good for truly static data (countries, enums)

Common Mistakes

• Forgetting to invalidate related queries (e.g., invalidate ['products'] but not ['cart'])
• Setting staleTime too high, causing UI to show stale data after mutations
• Not using onSettled for invalidation — onSuccess misses error recovery
• Calling invalidateQueries with exact: true and missing parameterized variants
