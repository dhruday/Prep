Performance Comparison Theory

Offset Pagination

Page 1:   scan 10 rows
Page 10:  scan 100 rows
Page 100: scan 1,000 rows
Page 500: scan 5,000 rows

Time = O(page × limit)
Linear growth ↗

Cursor Pagination

Page 1:   seek + 10 rows
Page 10:  seek + 10 rows
Page 100: seek + 10 rows
Page 500: seek + 10 rows

Time = O(log N + limit)
Constant ━━━

The Speedup Factor

Speedup = offset_time / cursor_time

Page 1:    ~1x    (both fast)
Page 10:   ~3x    (offset getting slow)
Page 100:  ~20x   (offset noticeably slow)
Page 500:  ~80x   (offset painful)
Page 5000: ~500x  (offset unusable)
The deeper you go, the bigger the advantage of cursor pagination.

EXPLAIN — Offset at Page 500

EXPLAIN ANALYZE
SELECT * FROM items ORDER BY id LIMIT 10 OFFSET 4990;

Limit  (cost=524.75..525.80 rows=10)
  → Sort  (cost=524.75..549.75 rows=5000)
      Sort Key: id
      Sort Method: top-N heapsort  Memory: 450kB
      → Seq Scan on items  (cost=0.00..345.00 rows=5000)
            Rows Removed by Offset: 4990
            Actual time: 45.2ms

EXPLAIN — Cursor at Same Position

EXPLAIN ANALYZE
SELECT * FROM items WHERE id > 4990 ORDER BY id LIMIT 10;

Limit  (cost=0.29..0.65 rows=10)
  → Index Scan using items_pkey  (rows=10)
        Index Cond: (id > 4990)
        Actual time: 0.04ms
Offset: Seq Scan + 4990 rows discarded = 45ms
Cursor: Index Seek + 10 rows returned = 0.04ms
Speedup: ~1000x

Quick Decision Guide

📋 Admin/dashboard with page numbers → Offset
📱 Mobile feed with "load more" → Cursor
🔍 Search results (users view ≤5 pages) → Offset
📰 Social media feed (millions of posts) → Cursor
🛒 E-commerce catalog sorted by price → Keyset
📊 Analytics pagination → Offset (small aggregated sets)

Interview Key Points

🎯 Always discuss trade-offs — no single "best" approach
🎯 Mention ghost records for offset under concurrent writes
🎯 Explain B-tree index seek for cursor O(1) claim
🎯 Know that Google Search limits offset to ~30 pages as a practical cap
