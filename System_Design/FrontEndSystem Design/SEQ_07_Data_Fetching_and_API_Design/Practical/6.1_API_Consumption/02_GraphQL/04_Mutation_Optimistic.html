What Is Optimistic UI?

The UI updates immediately as if the mutation succeeded, then reconciles when the server responds.

User clicks Like → count increments instantly → server confirms (keep) or rejects (rollback).

❌ Without Optimistic — Feels Sluggish

// User clicks → spinner → wait 200-2000ms → update UI
async function likeMutation(postId) {
  setLoading(true);
  const res = await fetch(`/api/posts/${postId}/like`, { method: 'POST' });
  const data = await res.json();
  setLikes(data.likes); // delayed update
  setLoading(false);
}

✅ With Optimistic — Instant Feedback

async function likeMutationOptimistic(postId, currentLikes) {
  const previousLikes = currentLikes;
  setLikes(currentLikes + 1);  // optimistic update NOW

  try {
    const res = await fetch(`/api/posts/${postId}/like`, { method: 'POST' });
    const data = await res.json();
    setLikes(data.likes);      // reconcile with server truth
  } catch {
    setLikes(previousLikes);   // rollback on failure
    showError('Like failed');
  }
}

Mutation Code

// POST http://localhost:4001/api/posts/1/like
const mutation = {
  query: `mutation { likePost(id: 1) { id likes } }`,
  optimisticResponse: {
    likePost: { id: "1", likes: currentLikes + 1, __typename: "Post" }
  }
};

When to Use Optimistic Responses

✅ Good candidates: Likes, bookmarks, toggles, form submissions, cart updates — actions where the expected outcome is predictable.
⚠️ Bad candidates: Payment processing, inventory checks, complex calculations — actions where server validation is critical.

Risks & Mitigations

Risk 1: Race conditions
User clicks Like 3x fast → 3 optimistic +1 → server sees only 1
Fix: Debounce or queue mutations, use server count as source of truth

Risk 2: Rollback flicker
UI shows +1, then snaps back to 0 on failure
Fix: Show subtle toast on rollback, animate the change

Risk 3: Stale cache
Optimistic update writes to cache, but cache key is stale
Fix: Use normalized cache (Apollo) with __typename + id

Risk 4: Offline mutations
User is offline, optimistic update shows success
Fix: Queue mutations, replay on reconnect (Apollo link-retry)

Q1: What is an optimistic response in GraphQL?

A: An optimistic response predicts the server result and updates the cache immediately. Apollo's optimisticResponse option writes to the normalized cache before the network request completes. If the server returns a different result, the cache is reconciled automatically.

Q2: How do you handle optimistic rollback?

A: Store previous state before the optimistic write. On mutation error, restore the previous state. Apollo handles this automatically — if a mutation fails, the optimistic cache entry is removed and the original data is restored. For manual implementations, use a try/catch with explicit state rollback.

Q3: When should you NOT use optimistic UI?

A: Avoid optimistic UI for: (1) Payment/financial transactions — must confirm server success. (2) Uniqueness constraints — creating a username that might already exist. (3) Complex server-side validation — results are not predictable from client state. (4) Multi-step workflows — intermediate states may be invalid.

Q4: How do race conditions occur with optimistic updates?

A: Rapid clicks can fire multiple mutations. Each optimistic update assumes the previous one succeeded. If mutations resolve out of order, the final count can be wrong. Mitigate with: debouncing, mutation queuing, or using the server response as the final source of truth rather than incrementing locally.
