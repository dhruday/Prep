1. Event Loop Mechanics

// Both debounce and throttle use setTimeout internally
// Understanding the event loop is critical:

// Timer resolution in browsers:
// - Minimum: 4ms (setTimeout spec minimum after nested calls)
// - Background tabs: 1000ms minimum (Chrome/Firefox)
// - setTimeout(fn, 0) ≈ 4ms in practice
// - requestAnimationFrame: ~16.67ms (60fps)

// Timer phases in Node.js event loop:
// timers → pending → idle → poll → check → close
// setTimeout callbacks fire in "timers" phase
// Multiple expired timers batch in same phase

// Browser event loop:
// task (setTimeout) → microtasks (Promise) → render → task
// Debounced function fires as a macrotask
// If clearTimeout called before firing, timer removed from queue

2. Debounce — "Wait Until Calm"

// Timeline visualization (300ms delay):
// User types: H...e...l...l...o
//
// Time:  0   50  100 150 200 250 ... 500
// Input: H   e   l   l   o
// Timer: [---X---X---X---X-----------→] FIRE!
//
// Each keystroke RESETS the 300ms timer
// Only fires once after 300ms of silence
// Total calls: 5 keystrokes → 1 API call

// Leading edge debounce:
// Time:  0   50  100 150 200 250 ... 500
// Input: H   e   l   l   o
// Timer: FIRE![---------X---X-----------→]
//
// Fires IMMEDIATELY on first call, then waits
// Good for: button clicks (instant feedback)

3. Throttle — "Limit Frequency"

// Timeline visualization (200ms interval):
// User scrolls continuously for 1 second
//
// Time:    0    50   100  150  200  250  300  350  400...
// Events:  ↓    ↓    ↓    ↓    ↓    ↓    ↓    ↓    ↓
// Fires:   ✓                   ✓                   ✓
//
// Executes at most once per 200ms
// Event count: 9 scroll events → 3 handler calls

// Leading vs Trailing throttle:
// Leading (default): fires on first call, then every interval
// Trailing: fires at end of each interval
// Both: fires on first call AND at end of each interval

4. requestAnimationFrame as Throttle

// rAF naturally throttles to display refresh rate (60fps = 16.67ms)
// Perfect for visual updates: scroll position, resize, animations

let ticking = false;
window.addEventListener('scroll', () => {
  if (!ticking) {
    requestAnimationFrame(() => {
      updateScrollProgress();
      ticking = false;
    });
    ticking = true;
  }
});

// Why rAF over throttle for visual updates:
// 1. Syncs with browser paint cycle (no wasted computation)
// 2. Automatically pauses in background tabs
// 3. Adapts to display refresh rate (120Hz, 60Hz, etc.)
// 4. No arbitrary timing constant to choose

5. AbortController Integration

// Debounce alone isn't enough — previous requests may still be in-flight
// Combine debounce + AbortController for complete solution:

// Without abort:  H → [req1 pending] e → [req2 pending] l → [req3 fires]
//                 req1 returns AFTER req3 → stale results shown!

// With abort:     H → [req1 pending] e → [abort req1] l → [req3 fires]
//                 Only req3 returns → correct results

// Race condition timeline:
// t=0:    User types "he" → fetch("he") → server processes (200ms)
// t=50:   User types "hel" → fetch("hel") → server processes (50ms)
// t=100:  "hel" returns first (faster query)
// t=200:  "he" returns (slower query) → OVERWRITES correct result!
// Solution: abort "he" request when "hel" is sent

3. Resize Observer + Debounce Pattern

// ResizeObserver fires rapidly during window resize
// Debounce expensive layout recalculations

const useResizeDebounced = (ref, callback, delay = 150) => {
  useEffect(() => {
    const el = ref.current;
    if (!el) return;
    
    const debouncedCb = debounce((entry) => {
      callback({
        width: entry.contentRect.width,
        height: entry.contentRect.height,
      });
    }, delay);
    
    const observer = new ResizeObserver((entries) => {
      debouncedCb(entries[0]);
    });
    
    observer.observe(el);
    return () => {
      observer.disconnect();
      debouncedCb.cancel(); // prevent memory leak
    };
  }, [ref, callback, delay]);
};
Q1: Implement debounce from scratch. Explain every line.
See Code Walkthrough tab for full annotated implementation. Key points:
1. Closure captures timer ID
2. Each call clears previous timer (clearTimeout)
3. Sets new timer with delay
4. Uses apply() to preserve `this` context and arguments
5. Returns wrapper function (not the result)
6. Optional: .cancel() method, .flush() for immediate execution, leading edge option
Follow-up: What happens if debounce is called with delay=0?
setTimeout(fn, 0) still defers to next macrotask (~4ms). This means rapid calls still batch — only the last call fires. Useful for batching synchronous state updates into a single async callback. React's setState batching works similarly.
Q2: When would you use debounce vs throttle vs requestAnimationFrame?
Debounce: When you want the FINAL value after activity stops.
- Search input (fire after user stops typing)
- Window resize (recalculate layout once resizing ends)
- Form auto-save (save after user stops editing)

Throttle: When you want PERIODIC updates during activity.
- Scroll position tracking (update every 200ms during scroll)
- Rate-limiting API calls (max 5 calls/second)
- Drag events (update position regularly)

requestAnimationFrame: When updating VISUAL state.
- Scroll-linked animations
- Canvas/WebGL rendering
- Any DOM manipulation that should sync with paint
Follow-up: Can you use debounce with leading=true as a throttle substitute?
Leading debounce fires immediately then waits, but it only fires ONCE at the start and ONCE at the end (if trailing=true). Throttle fires periodically throughout. For continuous events like scroll, throttle gives regular updates while debounce would give just start + end.
Q3: How does Google Search implement its autocomplete? Walk through the architecture.
1. Debounce ~150ms: Short delay because Google optimizes for perceived speed
2. Prefetch: On input focus, prefetch trending/personalized suggestions
3. Client cache: Hash map of query→results. "hel" cached when user types "hello" then backspaces
4. Cancel previous: AbortController on each new request
5. Streaming response: Results arrive in chunks (partial rendering)
6. Prediction: Grey text completion (inline autocomplete) from most likely suggestion
7. Keyboard navigation: Arrow keys change highlighted suggestion without new request
8. Trie/prefix tree: Server-side data structure for O(L) prefix matching
9. Personalization: Recent searches weighted higher in results
10. Fallback: If API slow (>200ms), show cached/trending results as placeholder
Follow-up: Why 150ms and not 300ms?
Google's research shows 150ms feels "instant" while still saving ~70% of requests. They can afford shorter delays because their autocomplete API is optimized to respond in <50ms globally (edge servers + trie data structure). Less optimized APIs need 300ms+ to avoid overloading.
Q4: A search input has a race condition — sometimes old results overwrite new ones. Debug it.
Root cause: Debounce prevents rapid fire but doesn't cancel in-flight requests. Sequence:
1. User types "react" → debounce fires → fetch("react") starts (200ms response)
2. User types "react hooks" → debounce fires → fetch("react hooks") starts (50ms response)
3. "react hooks" returns FIRST (faster query)
4. "react" returns LATER → overwrites results!

Fixes (pick one or combine):
1. AbortController: abort previous fetch on new request
2. Request ID: track latest request ID, ignore stale responses
3. Timestamp: ignore response if older request
4. React Query: handles this automatically (queryKey changes cancel stale queries)
Follow-up: How does React Query handle this internally?
When queryKey changes, React Query marks the previous query as "stale." If a response arrives for a stale query, it's cached but NOT used as current data. The observer only subscribes to the latest queryKey. Internally uses a query hash + observer pattern.
Q5: How do debounce/throttle behave in background tabs?
Critical browser behavior:
1. Chrome/Firefox: setTimeout minimum delay = 1000ms in background tabs
2. 300ms debounce becomes 1000ms automatically in hidden tabs
3. rAF pauses completely in background tabs (no frames to render)
4. Web Workers: Timers are NOT throttled in workers

Implications:
- Auto-save with 5s debounce: still works (1s minimum < 5s)
- Polling with 500ms interval: slows to 1s (acceptable usually)
- 100ms throttle for scroll: becomes 1s (but tab isn't visible anyway)
- Real-time updates: use visibility API to pause/resume instead of relying on timers
Follow-up: How do you handle this in production?
document.addEventListener('visibilitychange', () => { if (document.hidden) { pause(); } else { resume(); flush(); } }). On resume, immediately sync state (flush pending debounced work, refetch stale data).

1. Debounce Implementation — Fully Annotated

function debounce(func, delay, options = {}) {
  let timerId = null;    // Closure: holds active timer
  let lastArgs = null;   // Last arguments for trailing call
  let lastThis = null;   // Last 'this' context
  let result;             // Return value for leading call
  const leading = options.leading || false;
  const trailing = options.trailing !== false; // default true
  
  function debounced(...args) {
    lastArgs = args;
    lastThis = this;
    
    const callNow = leading && !timerId;
    // ^ Leading: fire immediately if no active timer
    
    clearTimeout(timerId);
    // ^ Cancel any existing timer — THIS is the debounce magic
    // Every call resets the countdown
    
    timerId = setTimeout(() => {
      timerId = null;      // Timer expired, reset state
      if (trailing && lastArgs) {
        result = func.apply(lastThis, lastArgs);
        // ^ Trailing: fire with most recent args after delay
        lastArgs = lastThis = null;
      }
    }, delay);
    
    if (callNow) {
      result = func.apply(this, args);
      // ^ Leading: fire synchronously right now
    }
    
    return result;
  }
  
  debounced.cancel = () => {
    clearTimeout(timerId);
    timerId = lastArgs = lastThis = null;
    // ^ Clean up: prevent memory leak on unmount
  };
  
  debounced.flush = () => {
    if (timerId && lastArgs) {
      result = func.apply(lastThis, lastArgs);
      debounced.cancel();
    }
    return result;
    // ^ Force immediate execution (e.g., on form submit)
  };
  
  return debounced;
}

2. Throttle Implementation

function throttle(func, interval) {
  let lastTime = 0;       // Last execution timestamp
  let timerId = null;     // Trailing edge timer
  let lastArgs = null;
  
  function throttled(...args) {
    const now = Date.now();
    const remaining = interval - (now - lastTime);
    // ^ Time until next allowed execution
    
    lastArgs = args;
    
    if (remaining <= 0) {
      // Enough time elapsed — execute now (leading edge)
      clearTimeout(timerId);
      timerId = null;
      lastTime = now;
      func.apply(this, args);
    } else if (!timerId) {
      // Schedule trailing execution
      timerId = setTimeout(() => {
        lastTime = Date.now();
        timerId = null;
        func.apply(this, lastArgs);
      }, remaining);
    }
    // If timer exists, ignore (already scheduled)
  }
  
  throttled.cancel = () => {
    clearTimeout(timerId);
    lastTime = 0;
    timerId = lastArgs = null;
  };
  
  return throttled;
}

3. React useDebounce Hook

function useDebounce(value, delay) {
  const [debouncedValue, setDebouncedValue] = useState(value);
  
  useEffect(() => {
    const timer = setTimeout(() => {
      setDebouncedValue(value);
    }, delay);
    
    return () => clearTimeout(timer);
    // ^ Cleanup runs BEFORE next effect — cancels timer on re-render
    // This is the debounce: value changes → timer reset
  }, [value, delay]);
  
  return debouncedValue;
}

// Usage with React Query:
function SearchComponent() {
  const [query, setQuery] = useState('');
  const debouncedQuery = useDebounce(query, 300);
  
  const { data } = useQuery({
    queryKey: ['search', debouncedQuery],
    queryFn: ({ signal }) =>
      fetch(`/api/search?q=${debouncedQuery}`, { signal })
        .then(r => r.json()),
    enabled: debouncedQuery.length >= 2,
    // ^ React Query passes AbortSignal automatically
    // When queryKey changes, previous request is aborted
    staleTime: 5 * 60 * 1000, // Cache 5 min
    placeholderData: keepPreviousData,
  });
}

Common Delay Values

Search autocomplete:    150-300ms debounce
Form auto-save:         1000-2000ms debounce
Window resize:          150ms debounce

API rate limiting:      1000ms throttle
Analytics batching:     200ms throttle + 5s flush
Button click:           300ms debounce (leading edge)
Drag events:            rAF (no custom delay)

Decision Tree

Need FINAL value only? ──── Yes ──→ Debounce
         │ No                          (search, save, resize)
         ▼
Need PERIODIC updates? ──── Yes ──→ Throttle
         │ No                          (scroll, drag, tracking)
         ▼
Updating visual/DOM? ────── Yes ──→ requestAnimationFrame
         │ No                          (animations, paint-sync)
         ▼
Need instant + debounce? ── Yes ──→ Debounce(leading: true)
                                       (button clicks)
