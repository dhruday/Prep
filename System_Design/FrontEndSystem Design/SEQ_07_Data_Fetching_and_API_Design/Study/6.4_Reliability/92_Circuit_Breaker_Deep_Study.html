1. Three States of a Circuit Breaker

// Borrowed from electrical engineering (Michael Nygard's "Release It!")
//
// CLOSED ──(failure threshold exceeded)──→ OPEN
//   ↑                                         │
//   └──(probe succeeds)──── HALF-OPEN ←──(timeout expires)
//
// CLOSED:  Normal operation. Requests flow through. Failures counted.
// OPEN:    All requests FAIL IMMEDIATELY. No network calls.
//          User sees fallback content instead of loading spinners.
// HALF-OPEN: One probe request allowed. If succeeds → CLOSED.
//            If fails → back to OPEN for another timeout period.
//
// Why this matters for frontend:
// Without circuit breaker during a server outage:
//   Every user action → 30s timeout → error → user retries → loop
//   Users become inadvertent DDoS attackers
//
// With circuit breaker:
//   First few failures open the circuit → instant fallback
//   No network calls → server can recover
//   Periodic probes test if server is back

2. Failure Detection Strategies

// Strategy 1: Consecutive failure count
//   Open circuit after N consecutive failures (e.g., 5)
//   Simple but fragile — one success resets counter
//   A 90% failure rate with occasional success stays CLOSED

// Strategy 2: Error rate threshold ✅ (recommended)
//   Track failure rate over sliding window
//   Open when error rate > 50% AND volume > 10 requests
//   The volume threshold prevents 1-out-of-1 failure from opening

// Strategy 3: Latency-aware
//   Count slow responses (p95 > 5s) as partial failures
//   Open when slow+error rate exceeds threshold
//   Catches degraded services that technically respond but are unusable

// Strategy 4: Combined (production-grade)
//   Consecutive failures: 5 → OPEN (fast detection)
//   Error rate: 50% with min volume 10 → OPEN (statistical detection)
//   Slow responses: count as half-failures

4. What Happens in OPEN State?

// When circuit is OPEN, you DON'T just throw errors at the user
// Instead, trigger your degradation strategy:
//
// Option 1: Serve stale cached data
//   "Showing cached product list from 5 minutes ago"
//
// Option 2: Serve static fallback
//   Show pre-built "popular products" instead of personalized recs
//
// Option 3: Hide the section entirely
//   Optional features (recommendations, analytics) just disappear
//
// Option 4: Show transparent error with ETA
//   "This section is temporarily unavailable. Retrying in 25s."
//
// The CircuitOpenError should carry the retry time:
//   throw new CircuitOpenError("Circuit open", retryAfterMs: 25000)
//   UI shows countdown timer

1. Per-Service Circuit Breaker Registry

// In microservices, each backend service gets its own breaker
// Product service down shouldn't open the Auth breaker

class CircuitBreakerRegistry {
  breakers = new Map();

  get(serviceName, config) {
    if (!this.breakers.has(serviceName)) {
      this.breakers.set(serviceName, new CircuitBreaker(serviceName, config));
    }
    return this.breakers.get(serviceName);
  }

  getMetrics() {
    const metrics = {};
    this.breakers.forEach((breaker, name) => {
      metrics[name] = breaker.getMetrics();
    });
    return metrics;
  }
}

const registry = new CircuitBreakerRegistry();

// Each service independently managed:
const productBreaker = registry.get('products', { failureThreshold: 5 });
const authBreaker = registry.get('auth', { failureThreshold: 3 }); // more sensitive
const recsBreaker = registry.get('recommendations', { failureThreshold: 2 }); // fail fast

2. Multi-Tab Sync via BroadcastChannel

// Problem: Tab A discovers service is down, opens circuit
// Tab B doesn't know — fires requests that will also fail
// Solution: share circuit state across tabs

class SharedCircuitBreaker extends CircuitBreaker {
  constructor(name, config) {
    super(name, config);
    this.channel = new BroadcastChannel(`circuit-breaker-${name}`);

    // Listen for state changes from other tabs
    this.channel.onmessage = (event) => {
      const { state, openedAt } = event.data;
      if (state === 'OPEN' && this.state === 'CLOSED') {
        this.state = 'OPEN';
        this.openedAt = openedAt;
        console.log(`[${name}] Circuit opened by another tab`);
      }
      if (state === 'CLOSED' && this.state === 'OPEN') {
        this.reset();
        console.log(`[${name}] Circuit closed by another tab`);
      }
    };
  }

  transition(newState) {
    super.transition(newState);
    // Broadcast state change to all tabs
    this.channel.postMessage({
      state: newState,
      openedAt: this.openedAt,
    });
  }
}

3. Circuit Breaker + React Query Integration

// Wrap React Query fetcher with circuit breaker

function useCircuitBreakerQuery(queryKey, fetchFn, serviceName) {
  const breaker = registry.get(serviceName);

  return useQuery({
    queryKey,
    queryFn: () => breaker.call(fetchFn),
    retry: (failureCount, error) => {
      // Don't retry if circuit is open
      if (error.name === 'CircuitOpenError') return false;
      return failureCount < 2;
    },
    meta: {
      circuitState: breaker.getState(),
      fallbackData: getCachedFallback(queryKey),
    },
  });
}

// Component uses it naturally:
function ProductList() {
  const { data, error } = useCircuitBreakerQuery(
    ['products'],
    () => fetch('/api/products').then(r => r.json()),
    'products'
  );

  if (error?.name === 'CircuitOpenError') {
    return /* Show fallback UI with retry countdown */;
  }
  // ... normal render
}

FAANG Interview Questions

Q1: Explain the Circuit Breaker pattern and why it matters for frontend applications.
The Circuit Breaker prevents cascading failures when a backend service is down. It has three states: CLOSED (normal — requests flow through, failures counted), OPEN (fail-fast — no network calls, instant fallback), and HALF-OPEN (one probe request to test recovery). Without it, every user interaction during a backend outage results in a 30-second timeout, followed by the user retrying — effectively turning thousands of users into an inadvertent DDoS attack on a recovering server. With it, the first few failures open the circuit, all subsequent requests get instant fallback (cached data, static content, or "temporarily unavailable" message), and a single probe request periodically tests if the server has recovered. This protects both the user experience and the server's ability to recover.
Follow-up: How does it differ from retry with exponential backoff?
Q2: How would you implement circuit breaking in a frontend with multiple microservices?
I'd create a CircuitBreakerRegistry that manages one circuit breaker instance per service. The product service, auth service, and recommendation service each have independent breakers with different configurations — auth might have a lower failure threshold (more sensitive) while recommendations might open faster (fail fast is OK for optional features). This prevents the product service being down from accidentally opening the auth circuit. Each breaker is integrated into the API layer, wrapping the fetch calls. I'd also implement BroadcastChannel-based multi-tab sync so that if Tab A discovers the product service is down, Tab B immediately knows without making its own failing requests.
Follow-up: How would you handle partial failures — one endpoint fails but others on the same service work?
Q3: What's the difference between failure count vs error rate for triggering the circuit?
Failure count (consecutive failures ≥ 5 → OPEN) is simple but flawed: a single success in a stream of failures resets the counter, so a service with 90% error rate stays CLOSED. Error rate with volume threshold (error rate ≥ 50% AND total requests ≥ 10 → OPEN) is more robust. The volume threshold prevents one-out-of-one failure from opening the circuit — you need statistical significance. In practice, I use both: consecutive failures for fast detection (5 in a row catches a hard outage quickly) and error rate for statistical detection (catches a degraded service that fails intermittently). I also count slow responses (>5s) as half-failures to catch services that technically respond but are too slow to be useful.
Follow-up: How do you tune these thresholds in production?
Q4: How do you synchronize circuit breaker state across browser tabs?
BroadcastChannel API is the cleanest approach. Each CircuitBreaker instance creates a named channel (circuit-breaker-{serviceName}). When a breaker transitions to OPEN or CLOSED, it broadcasts the state change. Other tabs listen and update their local breaker state. This prevents Tab B from making the same failing requests that Tab A already detected. The key detail: only OPEN and CLOSED transitions are broadcast. HALF-OPEN is local — we don't want multiple tabs sending probe requests simultaneously. One tab probes, and if it succeeds (→ CLOSED), that gets broadcast. An alternative is storing state in localStorage with the storage event, but BroadcastChannel is more reliable and supports structured data.
Follow-up: What about SharedWorker as an alternative to BroadcastChannel?

Complete Circuit Breaker Implementation

class CircuitBreaker {
  constructor(name, config = {}) {
    this.name = name;
    this.state = 'CLOSED';
    this.failures = 0;
    this.successes = 0;
    this.totalRequests = 0;
    this.openedAt = 0;
    this.config = {
      failureThreshold: config.failureThreshold ?? 5,
      successThreshold: config.successThreshold ?? 2,
      timeout: config.timeout ?? 30000,
      volumeThreshold: config.volumeThreshold ?? 10,
      errorRateThreshold: config.errorRateThreshold ?? 0.5,
      onStateChange: config.onStateChange ?? (() => {}),
    };
  }

  async call(fn) {
    if (this.state === 'OPEN') {
      const elapsed = Date.now() - this.openedAt;
      if (elapsed < this.config.timeout) {
        const retryIn = Math.ceil((this.config.timeout - elapsed) / 1000);
        throw { name: 'CircuitOpenError', message: `Circuit ${this.name} OPEN`, retryIn };
      }
      this.transition('HALF_OPEN');
    }

    try {
      const result = await fn();
      this.onSuccess();
      return result;
    } catch (err) {
      this.onFailure();
      throw err;
    }
  }

  onSuccess() {
    this.totalRequests++;
    if (this.state === 'HALF_OPEN') {
      this.successes++;
      if (this.successes >= this.config.successThreshold) {
        this.reset();
        this.transition('CLOSED');
      }
    } else {
      this.failures = 0;
    }
  }

  onFailure() {
    this.failures++;
    this.totalRequests++;

    if (this.state === 'HALF_OPEN') {
      this.openedAt = Date.now();
      this.transition('OPEN');
      return;
    }

    const rateTriggered = this.totalRequests >= this.config.volumeThreshold
      && (this.failures / this.totalRequests) >= this.config.errorRateThreshold;
    const countTriggered = this.failures >= this.config.failureThreshold;

    if (rateTriggered || countTriggered) {
      this.openedAt = Date.now();
      this.transition('OPEN');
    }
  }

  transition(to) {
    const from = this.state;
    this.state = to;
    this.config.onStateChange(from, to);
  }

  reset() { this.failures = 0; this.successes = 0; this.totalRequests = 0; }

  getState() { return this.state; }
  getMetrics() {
    return {
      state: this.state, failures: this.failures,
      total: this.totalRequests,
      errorRate: this.totalRequests ? (this.failures / this.totalRequests * 100).toFixed(1) + '%' : '0%',
    };
  }
}

Production Checklist

✅ One circuit breaker per external service (not one global)
✅ Use error RATE, not just count (with volume threshold)
✅ Sync state across tabs (BroadcastChannel)
✅ OPEN state serves fallback (cache/static), not blank errors
✅ Log state transitions to monitoring dashboard
✅ Include retry countdown in UI when circuit is OPEN
✅ HALF-OPEN: only ONE probe at a time (not all tabs probing)
✅ Integrate with React Query (don't retry CircuitOpenError)
✅ Test with simulated failures (chaos engineering)
✅ Different configs for different services (auth ≠ analytics)
