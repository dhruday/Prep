1. Loading State Taxonomy

// Not all loading states are equal — treating them the same is a junior mistake
//
// INITIAL LOAD     → First ever fetch — show skeleton
// REFRESHING       → Has data, fetching update — show stale data + subtle indicator
// PAGINATING       → Loading next page — show existing + bottom loader
// BACKGROUND       → Silent refresh — no visible indicator at all
// SUBMITTING       → User action pending — disable UI + spinner on button
// ERROR            → Fetch failed — error state with retry option
//
// ❌ WRONG: if (isLoading) return <Spinner />
//   → This replaces existing content with spinner on refresh!
//   → User sees content disappear and reappear
//
// ✅ RIGHT: Show skeleton only on INITIAL load
//           Show existing data + subtle indicator on refresh
//           Show nothing on background refresh

2. Why Skeletons Beat Spinners

// Facebook's research: skeleton loaders improve perceived load time by 20%
// even when actual load time is IDENTICAL to spinner
//
// Why? Skeletons communicate:
// 1. WHAT is loading (text, image, avatar — not just "something")
// 2. WHERE it will appear (exact position in layout)
// 3. HOW MUCH is loading (rough content volume)
//
// Spinner says:  "Trust me bro, something is happening"
// Skeleton says: "Here's exactly what the page will look like in 200ms"
//
// When to use SPINNER instead of skeleton:
// - Button submission (small, localized action)
// - Modal loading (unknown content shape)
// - Full-page route transitions (brief flash)
//
// When to use NOTHING:
// - Background refresh of existing data (SWR)
// - Analytics/tracking calls
// - Prefetching future routes

// Reusable base skeleton
function Skeleton({ width = '100%', height = '1em', radius = '4px', circle }) {
  return <span
    className="skeleton"
    style={{
      display: 'block',
      width: circle ? height : width,
      height,
      borderRadius: circle ? '50%' : radius,

  />;
}

2. Smart Loading Decision Hook

function useLoadingUX(query) {
  const { data, isLoading, isFetching, isError, fetchStatus } = query;

  // First load — no data yet
  if (isLoading && !data) {
    return { state: 'skeleton', showSkeleton: true };
  }

  // Has data, fetching update in background
  if (data && isFetching) {
    return { state: 'refreshing', showStaleIndicator: true, data };
  }

  // Error with no previous data
  if (isError && !data) {
    return { state: 'error', showError: true };
  }

  // Error but has stale data
  if (isError && data) {
    return { state: 'stale-error', showStaleIndicator: true, data };
  }

  // Normal — has fresh data
  return { state: 'success', data };
}

// Usage in component:
function UserList() {
  const query = useQuery(['users'], fetchUsers);
  const { state, data, showSkeleton, showStaleIndicator, showError } = useLoadingUX(query);

  if (showSkeleton) return <UserListSkeleton count={5} />;
  if (showError) return <ErrorState onRetry={query.refetch} />;

  return (
    <div>
      {showStaleIndicator && <div className="stale-banner">Updating...</div>}
      {data.map(user => <UserCard key={user.id} user={user} />)}
    </div>
  );
}

3. Delayed Skeleton Pattern

// Don't show skeleton for fast loads (<200ms)
// Flashing a skeleton for 100ms is worse than showing nothing

function useDelayedLoading(isLoading, delayMs = 200) {
  const [showSkeleton, setShowSkeleton] = useState(false);

  useEffect(() => {
    if (!isLoading) {
      setShowSkeleton(false);
      return;
    }

    const timer = setTimeout(() => setShowSkeleton(true), delayMs);
    return () => clearTimeout(timer);
  }, [isLoading, delayMs]);

  return showSkeleton;
}

// Timeline for fast load (150ms):
// t=0:   Loading starts, showSkeleton = false (nothing visible)
// t=150: Data arrives → showSkeleton still false → no flash ✅

// Timeline for slow load (800ms):
// t=0:   Loading starts, showSkeleton = false
// t=200: Timer fires → showSkeleton = true → skeleton appears
// t=800: Data arrives → showSkeleton = false → content replaces skeleton

FAANG Interview Questions

Q1: How do you decide between a skeleton loader, spinner, and no loading indicator?
It depends on three factors: content predictability, duration, and user expectation. Skeleton loaders are best when you know the layout shape in advance (list of cards, profile page, feed) — they communicate what's coming and prevent CLS. Spinners are for unpredictable content (modal dialogs, search results with varying shapes) or short-lived actions (button clicks). No indicator at all is correct for background refreshes (SWR) where you already have stale data displayed, and for prefetching. The key principle: if the user already has content on screen, don't replace it with a loading state. Show a subtle "refreshing" indicator at most. Only show skeletons/spinners when the user would otherwise see a blank area.
Follow-up: What about the "delayed skeleton" pattern to prevent flash of skeleton for fast loads?
Q2: How do skeleton loaders impact CLS (Cumulative Layout Shift)?
Skeletons can either help or hurt CLS depending on implementation. Done right, they reserve exact space matching the real content — preventing the layout jump when content loads. The skeleton occupies the same width, height, and position as the final content. Done wrong, a skeleton with different dimensions causes TWO layout shifts: one when the skeleton appears, and another when it's replaced by content. My approach: every skeleton component has min-height matching its real counterpart. For images, I use aspect-ratio CSS on the container. For lists, the list skeleton renders N placeholder items matching real item height. I measure CLS using web-vitals library and set alerts for any page exceeding 0.1 CLS score.
Follow-up: How do you handle dynamic content where the final height is unknown?
Q3: How should loading states differ between initial load and data refresh?
This is a critical distinction many developers miss. On initial load (no data exists), show a skeleton that matches the expected content shape — the user needs visual feedback that something is happening. On refresh (data already exists), keep showing the existing data with a subtle indicator — a thin progress bar at the top, a small spinner in the header, or a "Last updated 2 min ago" badge. Never replace existing content with a skeleton on refresh. In React Query, I differentiate using isLoading (initial, no data) vs isFetching (any fetch activity). I built a useLoadingUX hook that returns the appropriate state: 'skeleton' for initial, 'refreshing' for background update, 'stale-error' for failed refresh with old data still available.
Follow-up: How does this work with React Suspense boundaries?
Q4: How do you make skeleton loaders accessible?
Three key accessibility concerns. First, skeletons must be hidden from screen readers with aria-hidden="true" — a screen reader user doesn't benefit from "gray rectangle" descriptions. Instead, the container should have aria-busy="true" and aria-label="Loading content" so screen readers announce "Loading content..." once. Second, respect prefers-reduced-motion — disable the shimmer animation and show a static gray placeholder instead, avoiding the continuous motion that can cause vestibular discomfort. Third, ensure keyboard focus doesn't land on skeleton elements. When content loads, focus should remain stable. If the user was tabbing through a list, their position shouldn't jump when an item transitions from skeleton to content.
Follow-up: Are there any WCAG guidelines specifically about loading indicators?

2. Complete useLoadingUX Hook

function useLoadingUX(query, options = {}) {
  const { delayMs = 200 } = options;
  const showDelayed = useDelayedLoading(query.isLoading, delayMs);

  // Initial load — no data yet
  if (query.isLoading && !query.data) {
    return {
      state: 'initial',
      showSkeleton: showDelayed,      // Delayed to avoid flash
      showContent: false,
      showError: false,
      data: null,
    };
  }

  // Has data + background refresh
  if (query.data && query.isFetching) {
    return {
      state: 'refreshing',
      showSkeleton: false,
      showContent: true,
      showRefreshIndicator: true,    // Thin progress bar
      data: query.data,
    };
  }

  // Error, no data
  if (query.isError && !query.data) {
    return {
      state: 'error',
      showSkeleton: false,
      showContent: false,
      showError: true,
      error: query.error,
    };
  }

  // Error, has stale data
  if (query.isError && query.data) {
    return {
      state: 'stale-error',
      showContent: true,
      showStaleBanner: true,
      data: query.data,
    };
  }

  // Success
  return {
    state: 'success',
    showContent: true,
    data: query.data,
  };
}

CLS Prevention Rules

1. Skeleton dimensions MUST match real content dimensions
2. Use min-height on container (not content)
3. Use aspect-ratio for images/media
4. Grid with fixed track sizes for card layouts
5. Never insert/remove elements above fold during load
6. Target: CLS < 0.1
