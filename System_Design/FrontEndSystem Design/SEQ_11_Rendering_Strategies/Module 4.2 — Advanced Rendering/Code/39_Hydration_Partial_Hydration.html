Full Hydration — the hidden cost of SSR

After SSR delivers HTML, the browser downloads the JS bundle and React "hydrates" — it walks the entire DOM tree, attaches event listeners, sets up state, and reconciles with the server-rendered HTML. This is expensive and delays TTI.

✔ FCP — fast (from SSR HTML) — user sees content
⚠ Hydrating — JS parsed + executed, component tree re-created, events attached
✔ TTI — AFTER hydration — page becomes interactive
⚡ The gap between FCP and TTI = "uncanny valley" — looks interactive but isn't
Hydration mismatch errors occur when server-rendered HTML differs from what client-side React would produce (e.g. Date.now(), window references). React must warn and re-render from scratch.

Partial Hydration strategies

Progressive Hydration
Delay hydration of below-fold / low-priority components. Hydrate as user scrolls. Reduces TBT on first load.
Islands Architecture
Only interactive "islands" are hydrated. Static content remains inert HTML. Used by Astro, Fresh.
React Server Components
Server components ship NO JS to client. Zero hydration for static parts. Client components hydrate normally.
Lazy / Deferred Hydration
Hydrate only when idle (requestIdleCallback) or on user interaction (click, hover). Qwik's resumability model.

Avoiding hydration mismatches (Next.js)

// Problem: SSR and client produce different HTML
function BadComponent() {
  // ❌ new Date() → different on server vs client
  return <p>{new Date().toLocaleString()}</p>;
}

// Fix 1: Use useEffect — output only on client
function GoodComponent() {
  const [time, setTime] = useState('');
  useEffect(() => setTime(new Date().toLocaleString()), []);
  return <p>{time}</p>;
}

// Fix 2: suppressHydrationWarning for time elements
function TimeStamp() {
  return (
    <time suppressHydrationWarning dateTime={new Date().toISOString()}>
      {new Date().toLocaleString()}
    </time>
  );
}

// Fix 3: dynamic import with ssr:false for browser-only code
const Chart = dynamic(() => import('./Chart'), { ssr: false });
