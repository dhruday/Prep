Screen Reader Testing

Topic 220 · Part 15 / Module 15.1 — Accessibility Basics · Hruday's Interview Prep

Why Screen Reader Testing?

Automated tools (axe, Lighthouse) catch 30-40% of accessibility issues. The remaining 60-70% require manual screen reader testing. Screen readers consume the Accessibility Tree, not the visual layout.

NVDA

Free · Windows · ~40% share

Open-source, most standards-compliant. Install key: Insert. Navigate: Tab + Arrows.

JAWS

Paid · Windows · ~30% share

Industry standard in enterprises. More forgiving of non-standard markup.

VoiceOver

Built-in · macOS/iOS · ~25% share

Cmd+F5 to activate. VO+Right Arrow to navigate. Rotor: VO+U.

Testing Protocol

  • Can I reach every interactive element with Tab?
  • Does each element announce its role and name?
  • Do form fields announce their labels?
  • Do error messages announce automatically (aria-live)?
  • Can I operate dropdowns, modals with keyboard only?
  • After SPA route change, where does focus go?
⚠️ Automated tools check markup syntax. Screen readers test the actual user experience. A button with aria-label passes axe but may announce nonsensically in NVDA.

Common Fixes

❌ Before: Custom dropdown

<div class="dropdown" onclick="toggle()">
  <span>High</span>
  <div class="menu">
    <div onclick="select('low')">Low</div>
  </div>
</div>
// SR announces: "clickable" — useless

✅ After: ARIA combobox

<div role="combobox" aria-expanded="false"
     aria-label="Priority" tabindex="0">
  <span>High</span>
  <ul role="listbox">
    <li role="option" aria-selected="true">High</li>
  </ul>
</div>
// SR announces: "Priority combobox, collapsed. High, 1 of 3"
