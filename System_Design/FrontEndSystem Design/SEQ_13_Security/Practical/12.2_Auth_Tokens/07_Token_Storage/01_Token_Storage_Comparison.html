Best Practice: Memory + HttpOnly Cookie

// THE RECOMMENDED PATTERN for SPAs:
// Access token → JavaScript memory (module-scoped variable)
// Refresh token → HttpOnly Secure SameSite=Strict cookie

// auth.js — token stored in closure (not accessible from console/XSS)
const createAuthManager = () => {
  let accessToken = null; // ← private, not on window/globalThis

  return {
    setToken: (token) => { accessToken = token; },
    getToken: () => accessToken,
    clearToken: () => { accessToken = null; },
    fetchWithAuth: async (url, options = {}) => {
      if (!accessToken) await refreshAccessToken(); // use refresh cookie
      return fetch(url, {
        ...options,
        headers: { ...options.headers, Authorization: `Bearer ${accessToken}` }
      });
    }
  };
};

const auth = createAuthManager();
// auth.getToken() works, but window.accessToken is undefined
// XSS can call auth.getToken() — but only during script execution
// On page reload, token is gone (must re-authenticate via refresh cookie)

Google Senior Frontend — Token Storage

Q: Your team stores JWT in localStorage. The security team flags it. What do you recommend?

Migration plan: Move access token to JavaScript memory (closure/module scope). Move refresh token to HttpOnly + Secure + SameSite=Strict cookie. Add a /api/refresh endpoint that reads the cookie and returns a new access token. On app load: call /api/refresh to get initial access token. On 401: automatically call /api/refresh and retry. Benefits: XSS can't steal persistent tokens (memory cleared on reload). CSRF can't hijack refresh (SameSite=Strict). Short-lived access token (15min) limits damage from memory-reading XSS. Trade-off: Slight complexity increase, but large security improvement.
