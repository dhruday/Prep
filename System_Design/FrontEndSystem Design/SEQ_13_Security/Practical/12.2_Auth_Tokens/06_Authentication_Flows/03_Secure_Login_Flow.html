Timing Attack Prevention

// VULNERABLE: Early return reveals whether user exists
async function login(username, password) {
  const user = db.getUser(username);
  if (!user) return false; // ← returns FAST (no hash check)
  return bcrypt.compare(password, user.hash); // ← returns SLOW
}
// An attacker can measure response time to enumerate valid usernames!

// SECURE: Always perform the hash comparison
async function login(username, password) {
  const user = db.getUser(username);
  const hash = user ? user.hash : '$2b$12$dummy...'; // dummy hash
  const valid = await bcrypt.compare(password, hash);
  if (!user || !valid) return false; // same timing regardless
  return true;
}

Google Senior Frontend — Login Security

Q: A user reports that login is slow. It takes 200ms per attempt. Is this a bug?

No, this is by design. Bcrypt with cost factor 12 takes ~200ms on purpose. This is the hashing time, making brute force attacks impractical (5 attempts/sec instead of millions). If you need faster login UX: (1) Show a loading spinner. (2) Use Argon2id which offers similar security with tunable parameters. (3) Consider WebAuthn/passkeys which don't need password hashing at all. Never reduce the cost factor just for speed — you're trading security. Google uses multi-layered auth that includes risk scoring, which adds latency but provides security.
