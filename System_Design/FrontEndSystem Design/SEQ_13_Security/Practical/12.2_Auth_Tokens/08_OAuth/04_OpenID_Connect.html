OAuth vs OIDC

// OAuth 2.0 = Authorization (what can you access?)
// OIDC = Authentication (who are you?) built on top of OAuth 2.0

// OAuth gives you: access_token (opaque, for API calls)
// OIDC adds: id_token (JWT, contains user identity claims)

// OIDC adds to OAuth:
// 1. id_token (JWT) — user identity information
// 2. /userinfo endpoint — additional user profile data
// 3. Standard claims: sub, name, email, picture, etc.
// 4. Discovery document: /.well-known/openid-configuration
// 5. Session management: how to detect user logout at IdP

// ID Token claims:
{
  "iss": "https://accounts.google.com",  // who issued
  "sub": "110169484474386276334",       // unique user ID
  "aud": "your-client-id.apps.google",  // intended audience
  "exp": 1678886400,                      // expiration
  "iat": 1678882800,                      // issued at
  "nonce": "abc123",                    // replay prevention
  "email": "alice@gmail.com",           // user email
  "name": "Alice Smith"                   // display name
}

ID Token Validation Checklist

// CRITICAL: Always validate BEFORE trusting the id_token

// 1. Verify signature (RS256 with IdP's public key)
const jwks = await fetch('https://accounts.google.com/.well-known/jwks.json');
// Use the kid (Key ID) from JWT header to find the right key

// 2. Check issuer (iss)
if (payload.iss !== 'https://accounts.google.com') throw 'Wrong issuer';

// 3. Check audience (aud)
if (payload.aud !== 'your-client-id') throw 'Wrong audience';

// 4. Check expiration (exp)
if (payload.exp * 1000 < Date.now()) throw 'Token expired';

// 5. Check nonce (if you sent one in the auth request)
if (payload.nonce !== storedNonce) throw 'Nonce mismatch (replay?)';

// 6. Check issued-at (iat) — not too old
const maxAge = 5 * 60 * 1000; // 5 minutes
if (Date.now() - payload.iat * 1000 > maxAge) throw 'Token too old';

// ⚠️ NEVER skip validation — forged tokens are trivial to create
// jwt.io lets anyone create a JWT with any claims

Google Senior Frontend — OIDC

Q: Should the frontend validate the ID token?

Depends on architecture. BFF pattern: No. The BFF (backend) validates the ID token and creates a session. The frontend only gets a session cookie. SPA calling IdP directly: Yes, validate in the frontend. But use a well-tested library (jose, oidc-client-ts) — don't implement JWT validation manually. The reason: You need to fetch the JWKS endpoint, verify RS256 signatures, check claims, handle key rotation. Getting any step wrong = vulnerability. At Google: Backend validates. The frontend receives pre-verified user claims through the BFF.
