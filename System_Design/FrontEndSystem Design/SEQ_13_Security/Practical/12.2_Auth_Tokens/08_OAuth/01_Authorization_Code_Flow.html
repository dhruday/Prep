Key security features:
• Code exchanged server-side (secret never in browser)
• State parameter prevents CSRF
• PKCE prevents code interception
• Tokens stored server-side (BFF pattern)

Google Senior Frontend — OAuth 2.0

Q: Why is the Implicit flow deprecated for SPAs?

The Implicit flow returns the access_token directly in the URL fragment (#access_token=xyz). Problems: (1) Token in URL → logged in browser history, referrer headers, server logs. (2) No refresh tokens — the SPA must redirect the user to re-authenticate. (3) No way to verify the token recipient (no code exchange). (4) PKCE can't be used. The replacement: Authorization Code + PKCE. This adds one extra round-trip (code → token exchange) but gains: tokens not in URLs, refresh tokens, PKCE protection, server-side secret for confidential clients.

Q: How does Google Sign-In handle the OAuth flow internally?

Google Sign-In (new version: "Sign In with Google" / GIS) uses the Authorization Code flow with PKCE by default for web. The GSI library handles state generation, PKCE, and redirect management. On success, it gives you an authorization code that your backend exchanges for tokens. For the one-tap UX: Google uses a popup or iframe with postMessage for the consent flow, avoiding full-page redirects. The ID token is returned as a JWT that can be verified client-side (using Google's public keys) or server-side.
