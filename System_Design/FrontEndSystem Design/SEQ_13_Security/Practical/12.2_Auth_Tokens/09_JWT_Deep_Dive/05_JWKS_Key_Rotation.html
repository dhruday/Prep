JWKS (JSON Web Key Set)

// JWKS endpoint: a well-known URL that publishes public keys
// Example: https://accounts.google.com/.well-known/jwks.json

{
  "keys": [
    {
      "kty": "RSA",          // Key type
      "kid": "key-2024-01",  // Key ID (matches JWT header)
      "use": "sig",          // Usage: signing
      "alg": "RS256",        // Algorithm
      "n": "0vx7agoebG...",  // RSA modulus (public)
      "e": "AQAB"            // RSA exponent (public)
    },
    {
      "kty": "RSA",
      "kid": "key-2024-02",  // NEW key (rotation)
      "use": "sig",
      "alg": "RS256",
      "n": "xqY2...",
      "e": "AQAB"
    }
  ]
}

// Flow:
// 1. JWT header has "kid": "key-2024-02"
// 2. Service fetches JWKS → finds key with matching kid
// 3. Verifies JWT signature with that public key
// 4. Caches JWKS (don't fetch on every request!)

JWKS Caching Best Practices

// Naive approach: fetch JWKS on every JWT verification
// ❌ Adds latency + DDoS risk to JWKS endpoint

// Recommended: Cache with smart invalidation
class JWKSClient {
  constructor(jwksUrl) {
    this.cache = new Map();
    this.cacheMaxAge = 10 * 60 * 1000; // 10 min TTL
    this.lastFetch = 0;
    this.minCooldown = 30 * 1000; // Min 30s between fetches
  }

  async getKey(kid) {
    // 1. Check cache
    if (this.cache.has(kid)) return this.cache.get(kid);

    // 2. Unknown kid → might be a new key. Refetch.
    // But rate-limit refetches (prevent JWKS DoS)
    if (Date.now() - this.lastFetch < this.minCooldown) {
      throw new Error('Unknown kid, cooldown active');
    }

    await this.refresh();
    return this.cache.get(kid) || null;
  }

  async refresh() {
    const resp = await fetch(this.jwksUrl);
    const jwks = await resp.json();
    this.cache.clear();
    jwks.keys.forEach(k => this.cache.set(k.kid, k));
    this.lastFetch = Date.now();
  }
}

// This pattern handles key rotation gracefully:
// - Cached keys serve most requests instantly
// - New kid triggers re-fetch (picks up new keys)
// - Rate limiting prevents cache-busting DoS

Google Senior Frontend — JWKS & Key Rotation

Q: How does Google handle key rotation for their OAuth/OIDC tokens?

Google's JWKS endpoint (googleapis.com/oauth2/v3/certs) typically has 2-3 keys: (1) The current signing key. (2) The previous key (for tokens not yet expired). (3) Sometimes a next key (pre-published for advance caching). Rotation occurs every ~6 hours. The HTTP response includes Cache-Control: max-age=N header. Libraries like google-auth-library-nodejs cache the JWKS and refetch based on this header. When they see a JWT with an unknown kid, they refetch the JWKS once. If still unknown → reject. This is why your services must NOT cache JWKS forever. Use a max TTL of 24h with re-fetch on unknown kid.
