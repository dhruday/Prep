Error Handling Architecture

// Global error handler (Express)
app.use((err, req, res, next) => {
  // 1. Log full error details server-side
  logger.error({
    message: err.message,
    stack: err.stack,
    url: req.url,
    userId: req.user?.id,
    requestId: req.id
  });

  // 2. Send sanitized response to client
  const statusCode = err.statusCode || 500;
  const isOperational = err.isOperational || false;

  res.status(statusCode).json({
    error: isOperational
      ? err.message        // known operational error
      : 'Internal server error', // unknown → generic
    code: err.code || 'INTERNAL_ERROR',
    requestId: req.id      // for support lookups
  });

  // 3. Alert on unknown errors
  if (!isOperational) {
    alertOps({ message: err.message, requestId: req.id });
  }
});

// Frontend: Map error codes to user messages

Google Senior Frontend — Error Security

Q: How do you prevent user enumeration in login/signup flows?

User enumeration: attacker discovers which emails are registered. Attacks: (1) Login: "Wrong password" vs "User not found." Fix: Always return "Invalid credentials" regardless. (2) Signup: "Email already taken." Fix: Return "Check your email for confirmation" for both new and existing emails. For existing: send "Someone tried to register with your email" instead. (3) Password reset: "Email sent" even if email doesn't exist. (4) Timing: checking if email exists (DB query) takes longer than immediate rejection. Fix: add artificial delay to normalize response times. await sleep(random(200, 500)). Google's approach: All auth endpoints return the same response structure and timing. Rate limit per IP. Monitor for enumeration patterns (sequential emails, high error rates).
