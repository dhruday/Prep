//   Simple but bursty (200 reqs at window boundary)

// 3. TOKEN BUCKET: burst-friendly

//   Allows bursts but caps sustained rate

// 4. EXPONENTIAL BACKOFF (client-side)
//   On 429: wait 1s, then 2s, 4s, 8s, max 60s
//   Add jitter to prevent thundering herd

Client-Side Throttle & Debounce

// THROTTLE: Max 1 call per interval
function throttle(fn, ms) {
  let last = 0;
  return (...args) => {
    if (Date.now() - last >= ms) {
      last = Date.now();
      return fn(...args);
    }
  };
}

// DEBOUNCE: Wait until user stops typing
function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}

// EXPONENTIAL BACKOFF with jitter
async function fetchWithBackoff(url, maxRetries = 5) {
  for (let i = 0; i < maxRetries; i++) {
    const resp = await fetch(url);
    if (resp.status !== 429) return resp;
    const base = Math.min(2 ** i * 1000, 60000);
    const jitter = Math.random() * base * 0.5;
    await new Promise(r => setTimeout(r, base + jitter));
  }
  throw new Error('Rate limited after max retries');
}

Q: How would you handle 429 responses gracefully in a React app?

Create a centralized fetch/axios interceptor that handles 429 globally: (1) Read Retry-After header from response. (2) Queue the failed request for retry. (3) Enable exponential backoff with jitter: delay = min(2^attempt * 1000, 60000) + random(0, 500). (4) Show a non-intrusive toast: "You're doing that too fast. Retrying in Xs." (5) For search/autocomplete: debounce input (300ms), throttle API calls (1/s). (6) Disable submit buttons during pending requests (prevent double-submit). (7) Use AbortController to cancel stale requests. (8) For batch operations: queue with concurrency limit (e.g., p-queue library, max 3 concurrent). If the 429 includes X-RateLimit-Reset, schedule the retry precisely. Never retry on 4xx other than 429 or 408.
