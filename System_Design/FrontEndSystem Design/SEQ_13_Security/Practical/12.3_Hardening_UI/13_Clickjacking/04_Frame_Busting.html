Frame-Busting Techniques

// ═══ Basic Frame-Busting ═══
if (top !== self) {
  top.location = self.location;  // break out of frame
}

// ═══ More Robust Version ═══
(function() {
  // Hide content if framed
  if (self !== top) {
    document.documentElement.style.display = 'none';
    top.location.replace(self.location.href);
  }
})();

// ═══ CSS-Based Defense ═══
// Start hidden, unhide only if NOT framed
<style>
  html { display: none !important; }
</style>
<script>
  if (self === top) {
    document.documentElement.style.display = 'block';
  } else {
    top.location = self.location;
  }
</script>

// ═══ Modern Detection ═══
if (window.frameElement !== null) {
  // We're in an iframe
  document.body.innerHTML = 'This page cannot be displayed in a frame.';
}

// ⚠️ JS frame-busting is UNRELIABLE as sole defense
// Always use HTTP headers as primary protection

Frame-Busting Bypasses

// ═══ Bypass 1: sandbox attribute ═══
<iframe src="http://victim.com"
  sandbox="allow-scripts allow-forms">
</iframe>
// Missing allow-top-navigation → top.location = ... is blocked!
// The frame-busting script silently fails

// ═══ Bypass 2: onbeforeunload ═══
window.onbeforeunload = function() {
  return "Leave this page?";  // user clicks "Stay"
};
// The navigation prompt interrupts frame-busting

// ═══ Bypass 3: 204 No Content ═══
// Attacker intercepts the navigation:
window.onbeforeunload = function() {
  window.location = "http://attacker.com/204"; // returns 204
  // Browser stays on current page
};

// ═══ Bypass 4: Double framing ═══
// if (top !== self) only checks immediate parent
// Attacker nests: attacker.com → proxy.com → victim.com

// ═══ Bypass 5: IE restricted zone ═══
// <iframe security="restricted"> disabled JS entirely
// (IE only, historical)

// CONCLUSION: JS frame-busting alone is NOT sufficient
// Use: X-Frame-Options + frame-ancestors + JS (defense in depth)

Q: Why is JavaScript frame-busting considered insufficient?

Three fundamental problems: (1) sandbox attribute: <iframe sandbox="allow-scripts"> (without allow-top-navigation) blocks all navigation attempts. The frame-busting script's top.location = ... throws a SecurityError silently. The attacker's iframe ALLOWS your scripts to run but BLOCKS them from breaking out. (2) Timing: Frame-busting runs after page load. During the gap, the user could click. CSS defense (start hidden) helps but isn't bulletproof. (3) Script blocking: CSP on the attacker's page can block inline scripts. Or the attacker serves your page through a proxy that strips scripts. HTTP headers (X-Frame-Options, frame-ancestors) work because: (a) Enforced by browser BEFORE rendering. (b) Cannot be bypassed by sandbox, CSP, or script manipulation. (c) Work even if JavaScript is disabled. Use JS frame-busting only as defense-in-depth, never as the primary control.
