Concurrent Refresh Race Conditions

// Scenario: Token expires, 5 requests fail with 401

// ❌ Naive approach: Each 401 triggers its own refresh
// Request A: 401 → refresh() → new_token_1
// Request B: 401 → refresh() → new_token_2 (token_1 invalidated!)
// Request C: 401 → refresh() → new_token_3
// Request D: 401 → refresh() → fails! (previous token already used)
// Request E: 401 → refresh() → fails!

// Problems:
// 1. Multiple refresh calls waste tokens (rotation = single use)
// 2. Later refreshes may fail (previous token invalidated)
// 3. Reuse detection triggers → ALL tokens revoked
// 4. User gets logged out unexpectedly

// ✅ Correct approach: Single refresh, queue all waiting requests
// Request A: 401 → starts refresh, others queue
// Request B: 401 → sees refresh in progress, queues
// Request C: 401 → queues
// Refresh completes → all queued requests retry with same new token

Request Queue Implementation

// Axios interceptor with refresh queue
let isRefreshing = false;
let failedQueue = [];

function processQueue(error, token) {
  failedQueue.forEach(({ resolve, reject }) => {
    error ? reject(error) : resolve(token);
  });
  failedQueue = [];
}

axios.interceptors.response.use(
  response => response,
  async error => {
    const originalRequest = error.config;
    
    if (error.response?.status === 401 && !originalRequest._retry) {
      if (isRefreshing) {
        // Queue this request — it'll retry when refresh completes
        return new Promise((resolve, reject) => {
          failedQueue.push({ resolve, reject });
        }).then(token => {
          originalRequest.headers['Authorization'] = `Bearer \${token}`;
          return axios(originalRequest);
        });
      }

      originalRequest._retry = true;
      isRefreshing = true;

      try {
        const { accessToken } = await refreshTokens();
        processQueue(null, accessToken);
        originalRequest.headers['Authorization'] = `Bearer \${accessToken}`;
        return axios(originalRequest);
      } catch (err) {
        processQueue(err, null);
        logout();
        return Promise.reject(err);
      } finally {
        isRefreshing = false;
      }
    }
    return Promise.reject(error);
  }
);

Google Senior Frontend — Race Conditions

Q: How do you handle multi-tab token refresh?

Problem: User has 3 tabs open. All need to refresh simultaneously. With rotation: first tab refreshes → invalidates token → other tabs' refreshes fail → users get logged out in 2 of 3 tabs. Solutions: (1) BroadcastChannel API: Tab that refreshes broadcasts new token to all tabs. Other tabs listen and update without calling refresh themselves. const bc = new BroadcastChannel('auth'); bc.onmessage = (e) => setToken(e.data.token). (2) localStorage event: Storage events fire cross-tab. localStorage.setItem('token', newToken) → other tabs get 'storage' event. (3) SharedWorker: Single SharedWorker manages all token refresh logic. All tabs connect to same worker. Worker deduplicates refreshes. (4) Leader election: Use Web Locks API or a library like tab-leader to elect one tab as the "auth leader." Only the leader refreshes; others follow. Google uses BroadcastChannel + leader election.
