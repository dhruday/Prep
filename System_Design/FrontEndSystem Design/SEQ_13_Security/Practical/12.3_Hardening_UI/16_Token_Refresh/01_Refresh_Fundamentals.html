Why Dual Tokens?

// Problem: Long-lived tokens = big security risk
// If stolen, attacker has access for days/weeks

// Solution: Short access token + long refresh token

// ACCESS TOKEN:
// - Short-lived: 5-15 minutes
// - Sent with every API request (Authorization header)
// - Stateless (JWT) — server doesn't track it
// - If stolen: limited damage window (minutes)

// REFRESH TOKEN:
// - Long-lived: days to weeks
// - Only sent to /token/refresh endpoint
// - Stored securely (HttpOnly cookie or secure storage)
// - Stateful — server tracks & can revoke
// - Used ONLY to get new access tokens

// If access token is stolen:
// Attacker has 5-15 minutes of access
// No way to get new tokens (no refresh token)

// If refresh token is stolen:
// Token rotation detects this (covered in Lab 02)
// Server can revoke the refresh token family

Refresh Flow Sequence

// 1. Login → Get both tokens
POST /auth/login { email, password }
→ { accessToken: "eyJ...", refreshToken: "eyJ..." }

// 2. API calls with access token
GET /api/data
Authorization: Bearer eyJ... (access token)
→ { data: [...] }

// 3. Access token expires (401 response)
GET /api/data
Authorization: Bearer eyJ... (expired)
→ 401 { error: "Token expired" }

// 4. Client detects 401, calls refresh
POST /auth/refresh
{ refreshToken: "eyJ..." }  // or from HttpOnly cookie
→ { accessToken: "NEW_eyJ...", refreshToken: "NEW_eyJ..." }

// 5. Retry original request with new access token
GET /api/data
Authorization: Bearer NEW_eyJ...
→ { data: [...] }

// This all happens transparently — user sees no interruption

Q: What's the optimal access token lifetime?

Trade-off: Security vs UX. Short tokens (5 min): More secure but more refresh requests. Adds latency if refresh is needed mid-request. Good for: banking, healthcare. Medium tokens (15 min): Google's sweet spot for most apps. Balances security with reasonable refresh frequency. Long tokens (1 hour): Fewer refreshes but longer attack window. Only for low-risk APIs. Factors: (1) Sensitivity of data (financial → short, blog → medium). (2) Network conditions (mobile users with poor connectivity → longer to avoid refresh failures). (3) User session length (if users work for hours, short tokens with reliable refresh). (4) Infrastructure: Stateless JWT means no server-side revocation during the token lifetime. The ONLY way to "revoke" a JWT is to wait for expiry or maintain a blacklist (which defeats statelessness). This is why access tokens MUST be short.
