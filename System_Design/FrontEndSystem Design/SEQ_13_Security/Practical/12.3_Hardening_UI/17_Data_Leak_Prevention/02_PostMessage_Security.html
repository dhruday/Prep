postMessage Vulnerabilities

// postMessage allows cross-origin window communication
// Used by: OAuth popups, payment widgets, chat embeds, analytics

// ❌ Vulnerability 1: No origin check on receiver
window.addEventListener('message', (event) => {
  // Accepting messages from ANY origin!
  const data = JSON.parse(event.data);
  document.getElementById('content').innerHTML = data.html;
  // XSS via postMessage! Attacker opens your page and sends:
  // victim.postMessage('{"html":"<img src=x onerror=steal()>"}', '*')
});

// ❌ Vulnerability 2: Wildcard target origin
targetWindow.postMessage(sensitiveData, '*');
// Any window can receive this message!
// If target window navigated to attacker.com → data leaked

// ❌ Vulnerability 3: Trusting message data
window.addEventListener('message', (event) => {
  if (event.origin === 'https://trusted.com') {
    eval(event.data.code);  // Even with origin check: eval is dangerous
  }
});

Safe postMessage Patterns

// ✅ Rule 1: Always validate origin
window.addEventListener('message', (event) => {
  const ALLOWED = ['https://trusted.com', 'https://partner.com'];
  if (!ALLOWED.includes(event.origin)) return;
  
  // Process message...
});

// ✅ Rule 2: Specify exact target origin
iframe.contentWindow.postMessage(data, 'https://specific-origin.com');
// NEVER use '*' with sensitive data

// ✅ Rule 3: Validate message structure
window.addEventListener('message', (event) => {
  if (event.origin !== 'https://trusted.com') return;
  if (typeof event.data !== 'object') return;
  if (!event.data.type || !event.data.payload) return;
  
  switch (event.data.type) {
    case 'RESIZE':
      if (typeof event.data.payload.height !== 'number') return;
      iframe.style.height = Math.min(event.data.payload.height, 1000) + 'px';
      break;
    // Explicit allowlist of message types
  }
});

// ✅ Rule 4: Use structured clone (no eval)
// postMessage already uses structured clone algorithm
// Never parse JSON manually or use eval on message data

Google Senior Frontend — postMessage

Q: How do you securely implement a payment widget using postMessage?

Architecture: (1) Parent page (merchant) embeds payment iframe from payment.stripe.com. (2) Communication: Parent → iframe: { type: 'INIT_PAYMENT', amount: 4999, currency: 'USD' }. Iframe → parent: { type: 'PAYMENT_SUCCESS', paymentId: 'pi_xxx' }. (3) Security: Parent sends to specific origin: iframe.postMessage(data, 'https://payment.stripe.com'). Iframe validates event.origin against merchant allowlist. Both sides validate message structure with TypeScript types. (4) Token passing: Never send full card data via postMessage. Payment iframe handles card input (PCI compliance). Only payment confirmation/error sent to parent. (5) CSP: frame-src https://payment.stripe.com. connect-src includes Stripe API. (6) Clickjacking: Payment iframe sets frame-ancestors to specific merchant origins. (7) Testing: E2E tests with Cypress/Playwright that test cross-origin iframe communication.
