Sensitive Data in URLs

// ❌ Data that should NEVER be in URLs:
/reset-password?token=abc123&email=alice@google.com
/api/users?apiKey=sk_live_xyz789
/dashboard?session=eyJhbGciOiJIUzI1NiJ9
/search?q=cancer+diagnosis+treatments
/checkout?card=4111111111111111

// Where URLs get exposed:
// 1. Referer header → sent to external sites
// 2. Browser history → accessible by anyone on same machine
// 3. Server access logs → stored in plaintext
// 4. Proxy/CDN logs → third-party has your URLs
// 5. Browser extensions → can read all URLs
// 6. Shoulder surfing → visible in address bar
// 7. Shared screenshots → URL visible in browser chrome
// 8. Bookmarks → synced across devices/accounts
// 9. Tab crash reports → browser sends URLs to vendor
// 10. ISP/DNS logs → can see hostnames (not HTTPS paths, but...)

// ✅ Use POST bodies, headers, or encrypted cookies instead

Referer Header Leaks

// Every link click, image load, and script fetch sends Referer

// Page: https://app.com/reset?token=SECRET
// This page loads Google Analytics script:
<script src="https://www.google-analytics.com/analytics.js"></script>
// → Referer sent: https://app.com/reset?token=SECRET
// Google now has the password reset token!

// Same with images:
<img src="https://cdn.tracking.com/pixel.gif">
// → Tracking company gets your full URL

// CSS fonts:
@font-face { src: url("https://fonts.google.com/font.woff"); }
// → Google Fonts gets your page URL

// Solution: Referrer-Policy header
Referrer-Policy: no-referrer // on sensitive pages
Referrer-Policy: strict-origin-when-cross-origin // global

// Per-element override:
<a href="https://external.com" referrerpolicy="no-referrer"></a>

Prevention Techniques

// 1. Never put sensitive data in URLs
//    Use POST bodies or Authorization headers

// 2. Set Referrer-Policy header
Referrer-Policy: strict-origin-when-cross-origin

// 3. Clean URLs after use
//    Password reset: consume token, redirect to clean URL
if (searchParams.has('token')) {
  await consumeResetToken(searchParams.get('token'));
  history.replaceState({}, '', '/reset-success');
}

// 4. Use fragment identifiers (not sent to server)
//    https://app.com/callback#access_token=xxx
//    The # fragment is client-side only
//    But: still in browser history & accessible by JS on page

// 5. Self-hosting critical resources
//    Host fonts, analytics locally
//    No external requests = no referer leaks

// 6. Use rel="noreferrer" on external links
<a href="https://external.com" rel="noreferrer noopener">

Google Senior Frontend — URL Data Leaks

Q: How would you implement a secure password reset flow?

Secure reset flow: (1) User requests reset → server generates one-time token (128+ bits, crypto random), stores hash (not plaintext) in DB with expiry (1 hour). (2) Email contains: https://app.com/reset?token=abc123. (3) Reset page loads: immediately extract token from URL. Use history.replaceState() to remove token from URL bar. Store token in memory/sessionStorage. (4) Set Referrer-Policy: no-referrer on the reset page. No external scripts (analytics, fonts) on this page — pure self-hosted. (5) User submits new password: POST /api/reset with {token, newPassword} in body (not URL). (6) Server: verify token hash, check expiry, update password, invalidate token. (7) Rate limit: max 3 reset attempts per token, max 5 reset requests per email per hour. (8) Don't reveal if email exists: "If this email is registered, you'll receive a reset link."
