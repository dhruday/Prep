1. OAuth 2.0 Roles

// Resource Owner  → The user (who owns the data)
// Client          → Your app (wants to access user's data)
// Authorization Server → Issues tokens (Auth0, Keycloak, Google)
// Resource Server      → Hosts protected data (your API)
//
// Key principle: DELEGATION
// "Let my app access your Google Drive files without giving me your password"
//
// OAuth is NOT authentication — it's authorization
// OAuth tells you: "User X allowed app Y to access scope Z"
// It does NOT tell you: "The user is X" (that's OpenID Connect)

3. Authorization Code Flow with PKCE

// Step 1: Generate PKCE challenge
const codeVerifier = generateRandom(128); // Random string
const codeChallenge = base64url(SHA256(codeVerifier));

// Step 2: Redirect user to authorization server
// GET https://auth.example.com/authorize?
//   response_type=code
//   &client_id=my-spa
//   &redirect_uri=https://app.com/callback
//   &scope=openid profile email
//   &state=random-csrf-nonce      ← prevents CSRF
//   &code_challenge=abc123...      ← PKCE challenge
//   &code_challenge_method=S256

// Step 3: User authenticates, consents, gets redirected back
// GET https://app.com/callback?code=AUTH_CODE&state=random-csrf-nonce

// Step 4: Exchange code for tokens (via BFF or directly)
// POST https://auth.example.com/token
//   grant_type=authorization_code
//   &code=AUTH_CODE
//   &redirect_uri=https://app.com/callback
//   &client_id=my-spa
//   &code_verifier=original_random_string  ← PKCE proof

// Step 5: Auth server verifies SHA256(code_verifier) === code_challenge
//   → returns: { access_token, refresh_token, id_token }
PKCE (Proof Key for Code Exchange) prevents authorization code interception attacks. Even if an attacker intercepts the auth code, they can't exchange it without the original code_verifier.

OAuth Attack Vectors

1. Authorization Code Interception (Why PKCE Exists)

// Without PKCE:
// 1. User starts OAuth flow
// 2. Auth server redirects: app.com/callback?code=SECRET_CODE
// 3. Attacker intercepts redirect (malicious app, browser history)
// 4. Attacker exchanges code for tokens → has full access
//
// With PKCE:
// Attacker has the code but NOT the code_verifier
// → Token exchange fails → attack blocked

2. State Parameter Forgery (Login CSRF)

// Without state parameter:
// 1. Attacker gets their own auth code for victim app
// 2. Tricks victim into visiting: app.com/callback?code=ATTACKER_CODE
// 3. Victim's app exchanges code → logs in as attacker(!)
// 4. Victim uploads data to attacker's account
//
// With state parameter:
// App sets state=random_nonce before redirect
// Checks state on callback → attacker can't forge it

3. Open Redirect via redirect_uri

// Lax redirect_uri validation on auth server:
// Attacker crafts: redirect_uri=https://app.com.evil.com/callback
// Auth server redirects code to evil domain
//
// Defense: exact match redirect_uri validation (no wildcards)
// Register exact URLs: https://app.example.com/callback

FAANG Interview Questions

Q1: Walk through the OAuth 2.0 Authorization Code flow with PKCE for an SPA.
The SPA generates a random code_verifier (128 chars) and computes code_challenge = base64url(SHA256(code_verifier)). It redirects the user to the authorization server with client_id, redirect_uri, scope (e.g., openid profile), state (CSRF nonce), and the code_challenge. The user authenticates and consents. The auth server redirects back to the SPA's callback URL with an authorization code and the state. The SPA verifies the state matches what it stored. Then it exchanges the code for tokens by sending to the token endpoint: the authorization code, client_id, redirect_uri, and the code_verifier. The auth server computes SHA256(code_verifier) and checks it matches the code_challenge from step 1. If valid, it returns an access token (JWT, 5-15 min), a refresh token (opaque, 7-30 days), and optionally an id_token (OpenID Connect). The SPA stores the access token in memory and the refresh token in an HttpOnly cookie (via BFF) or uses it directly for silent refresh.
Follow-up: Why was the Implicit flow deprecated, and how does PKCE replace it?
Q2: What's the difference between OAuth 2.0 and OpenID Connect?
OAuth 2.0 is an authorization framework — it lets a third-party app access user resources with scoped permissions (e.g., "read your Google Calendar"). It intentionally does NOT specify how to identify the user. The access token is an opaque string from the resource server's perspective. OpenID Connect (OIDC) is an identity layer on top of OAuth 2.0 — it adds authentication. It introduces: (1) The id_token — a JWT containing user claims (sub, email, name, picture). (2) The /userinfo endpoint — returns additional user profile data. (3) Standard scopes: openid, profile, email. (4) Discovery document — .well-known/openid-configuration for automated setup. In practice, if you need "Sign in with Google" (who is this user?), you use OIDC. If you need "Access this user's Google Drive" (what can this app do?), you use OAuth 2.0 access tokens. Most auth flows use both simultaneously.
Follow-up: Can you use the access token for authentication? What's the security risk?
Q3: How would you implement "Sign in with Google/GitHub" for a production app?
I'd use Auth Code + PKCE with a BFF. Flow: (1) User clicks "Sign in with Google." SPA redirects to Google's /authorize with client_id, redirect_uri pointing to BFF, scope (openid email profile), state (CSRF), and PKCE challenge. (2) User authenticates at Google. (3) Google redirects to BFF with auth code. (4) BFF exchanges code for tokens using client_secret (server-side, never exposed). (5) BFF creates an app session, stores tokens server-side, sets HttpOnly session cookie for the SPA. (6) BFF returns user info to SPA. For multi-provider: use a standardized OIDC library (node-openid-client). Map Google/GitHub users to internal accounts via sub + provider. Handle account linking: if same email exists from different provider, require verification before merge. Security: validate id_token signature (fetch Google's JWKS), check iss, aud, exp, nonce claims. Rate limit login attempts. Log all auth events for audit.
Follow-up: How do you handle the case where the user revokes access at Google?

1. PKCE Implementation

// Generate code verifier and challenge
function generateCodeVerifier() {
  const array = new Uint8Array(32);
  crypto.getRandomValues(array);
  return base64UrlEncode(array);
}

async function generateCodeChallenge(verifier) {
  const encoder = new TextEncoder();
  const data = encoder.encode(verifier);
  const hash = await crypto.subtle.digest('SHA-256', data);
  return base64UrlEncode(new Uint8Array(hash));
}

function base64UrlEncode(buffer) {
  return btoa(String.fromCharCode(...buffer))
    .replace(/\+/g, '-')
    .replace(/\//g, '_')
    .replace(/=+$/, '');
}

// Start OAuth flow
async function startLogin() {
  const verifier = generateCodeVerifier();
  const challenge = await generateCodeChallenge(verifier);
  const state = crypto.randomUUID();

  sessionStorage.setItem('pkce_verifier', verifier);
  sessionStorage.setItem('oauth_state', state);

  const params = new URLSearchParams({
    response_type: 'code',
    client_id: 'my-spa',
    redirect_uri: 'https://app.com/callback',
    scope: 'openid profile email',
    state,
    code_challenge: challenge,
    code_challenge_method: 'S256',
  });

  window.location.href = `https://auth.example.com/authorize?${params}`;
}

2. Callback Handler

async function handleCallback() {
  const params = new URLSearchParams(location.search);
  const code = params.get('code');
  const state = params.get('state');

  // Verify state (CSRF protection)
  if (state !== sessionStorage.getItem('oauth_state')) {
    throw new Error('State mismatch — possible CSRF attack');
  }

  const verifier = sessionStorage.getItem('pkce_verifier');
  sessionStorage.removeItem('pkce_verifier');
  sessionStorage.removeItem('oauth_state');

  // Exchange code for tokens
  const res = await fetch('https://auth.example.com/token', {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body: new URLSearchParams({
      grant_type: 'authorization_code',
      code,
      redirect_uri: 'https://app.com/callback',
      client_id: 'my-spa',
      code_verifier: verifier,
    }),
  });

  const tokens = await res.json();
  tokenManager.setToken(tokens.access_token, tokens.expires_in);
}

OAuth 2.0 Flow Selection Guide

Is a user involved?
  NO → Client Credentials (M2M)
  YES ↓

Is the client confidential (can keep a secret)?
  YES → Authorization Code (with client_secret)
  NO ↓

Is it a browser-based app (SPA)?
  YES → Authorization Code + PKCE
  NO ↓

Is it a native mobile app?
  YES → Authorization Code + PKCE + Custom URL Scheme
  NO ↓

Is it a device with no browser (TV, IoT)?
  YES → Device Authorization Grant

NEVER → Implicit Grant (deprecated)
NEVER → Resource Owner Password Grant (deprecated)

Security Checklist

✅ Always use PKCE (even for confidential clients — defense in depth)
✅ Validate state parameter on callback (CSRF protection)
✅ Exact match redirect_uri (no wildcards or query params)
✅ Use id_token only for authentication (validate signature, iss, aud, exp)
✅ Use access_token only for API authorization (don't trust claims blindly)
✅ Verify tokens via JWKS (public key from .well-known/jwks.json)
✅ Keep client_secret server-side (use BFF for confidential flows)
✅ Request minimal scopes (least privilege)
✅ Short access token lifetime (5-15 min)
✅ Rotate refresh tokens on use (detect theft via reuse)
✅ Implement proper logout (revoke tokens at IdP + clear local state)
✅ Handle token revocation webhooks from IdP
