1. How CSRF Works

// CSRF exploits the browser's automatic cookie attachment
//
// 1. User logs into bank.com → session cookie set
// 2. User visits evil.com (in same browser session)
// 3. evil.com has hidden form:
//    <form action="https://bank.com/transfer" method="POST">
//      <input name="to" value="attacker">
//      <input name="amount" value="10000">
//    </form>
//    <script>document.forms[0].submit()</script>
//
// 4. Browser sends POST to bank.com WITH the session cookie
// 5. Bank processes the transfer — it looks like a legit request
//
// Key insight: the attacker can't READ the response (SOP prevents it)
// But they don't NEED to — the side effect (transfer) already happened

2. Why Cookies Are the Problem

// Cookies are sent automatically on EVERY request to the domain
// Browser doesn't check if the request was initiated by the same site
//
// This is unique to cookies — other auth mechanisms are safe:
// ✅ Authorization: Bearer <token> → not sent automatically
// ✅ Custom headers (X-CSRF-Token) → not sent automatically
// ❌ Cookies → sent automatically → vulnerable to CSRF
//
// SPAs using JWT in localStorage + Authorization header = CSRF-immune
// But: JWT in cookie (HttpOnly for XSS protection) = CSRF-vulnerable
// This is the classic security trade-off:  XSS protection vs CSRF

Since Chrome 80 (2020), cookies default to SameSite=Lax. This is the single biggest CSRF mitigation in browser history — most CSRF attacks via POST are now blocked by default.

Defense 1: CSRF Token (Synchronizer Token Pattern)

// Server generates a random token, embeds in form/meta tag
// Client sends token with every state-changing request
// Server validates token matches the session's token
// Attacker can't read the token (SOP) → can't forge the request

// Server side:
app.use((req, res, next) => {
  if (!req.session.csrfToken) {
    req.session.csrfToken = crypto.randomUUID();
  }
  res.locals.csrfToken = req.session.csrfToken;
  next();
});

// Validation middleware for POST/PUT/DELETE:
app.use((req, res, next) => {
  if (['POST', 'PUT', 'DELETE'].includes(req.method)) {
    const token = req.headers['x-csrf-token'] ?? req.body._csrf;
    if (token !== req.session.csrfToken) {
      return res.status(403).json({ error: 'Invalid CSRF token' });
    }
  }
  next();
});

Defense 2: Double Submit Cookie

// Alternative when you can't use server-side sessions
// Set CSRF token in both a cookie AND a header/form field
// Server checks cookie value === header value
// Attacker can make browser send the cookie but can't READ it
// → can't set the matching header value

// Client fetches CSRF token from cookie:
function getCsrfToken() {
  return document.cookie
    .split('; ')
    .find(c => c.startsWith('csrf='))
    ?.split('=')[1];
}

// Send token in custom header with every mutation:
fetch('/api/transfer', {
  method: 'POST',
  headers: {
    'X-CSRF-Token': getCsrfToken(), // Must match cookie value
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({ to: 'alice', amount: 100 }),
});

Defense 3: SameSite + Custom Header

// Modern SPAs: Three-layer defense
//
// Layer 1: SameSite=Lax on all cookies (blocks cross-site POST)
// Layer 2: Custom header requirement (X-Requested-With: XMLHttpRequest)
//   Cross-origin forms can't set custom headers (CORS preflight blocks)
// Layer 3: Origin/Referer header validation
//   Verify Origin header matches your domain

app.use((req, res, next) => {
  if (['POST', 'PUT', 'DELETE'].includes(req.method)) {
    const origin = req.headers.origin || req.headers.referer;
    if (!origin || !allowedOrigins.includes(new URL(origin).origin)) {
      return res.status(403).json({ error: 'Invalid origin' });
    }
  }
  next();
});

FAANG Interview Questions

Q1: Explain CSRF and why SameSite=Lax doesn't fully solve it.
CSRF exploits automatic cookie attachment — a malicious site triggers a request to a victim site, and the browser includes the user's session cookie. SameSite=Lax blocks cookies on cross-site POST requests, which prevents the classic form-based CSRF attack. However, it doesn't protect against: GET-based state changes (which violate REST but exist in legacy APIs), same-site attacks (subdomain takeover where evil.sub.bank.com is "same-site"), or scenarios where SameSite=None is required (cross-origin iframes, SSO). Also, older browsers don't support SameSite. So Lax is a strong default but shouldn't be the only defense — I pair it with CSRF tokens for POST/PUT/DELETE and Origin validation.
Follow-up: How does CSRF differ in SPAs vs server-rendered apps?
Q2: Compare Synchronizer Token vs Double Submit Cookie patterns.
Synchronizer Token stores a CSRF token in the server session and embeds it in the page. Server validates the submitted token matches the session token. It's the gold standard because the token never leaves the server as a cookie — the attacker has no way to guess it. Requires server-side session storage. Double Submit Cookie stores the token in both a cookie and requires the client to send it as a header. Server checks cookie value === header value. Advantage: stateless (no server session needed). Disadvantage: if an attacker controls a subdomain, they can set cookies for the parent domain and know the value. For SPAs with JWT auth, I prefer the custom header approach — requiring X-CSRF-Token on all mutations. Since cross-origin requests can't set custom headers without CORS preflight, this is inherently CSRF-resistant.
Follow-up: How do you handle CSRF for file upload endpoints?
Q3: If your SPA uses JWT stored in localStorage, is it vulnerable to CSRF?
No. CSRF relies on the browser automatically attaching credentials (cookies). JWT in localStorage is sent manually via the Authorization header — a cross-origin form submission or image request won't include it. However, localStorage is vulnerable to XSS — any injected script can read it. This is the fundamental trade-off: cookies with HttpOnly+SameSite protect against XSS (script can't read them) but require CSRF defense. localStorage/sessionStorage is CSRF-immune but XSS-vulnerable. The recommended approach for most production apps: store the access token in memory (JavaScript variable), store the refresh token in an HttpOnly SameSite cookie, and use short-lived access tokens (5 min). This minimizes both attack surfaces.

1. SPA CSRF Protection with Axios Interceptor

// Automatically attach CSRF token to every mutation

const api = axios.create({ baseURL: '/api', withCredentials: true });

api.interceptors.request.use((config) => {
  if (['post', 'put', 'delete', 'patch'].includes(config.method)) {
    config.headers['X-CSRF-Token'] = getCsrfFromCookie();
  }
  return config;
});

// Or with fetch wrapper:
async function secureFetch(url, options = {}) {
  if (options.method && options.method !== 'GET') {
    options.headers = {
      ...options.headers,
      'X-CSRF-Token': getCsrfFromMeta(),
    };
  }
  return fetch(url, { ...options, credentials: 'same-origin' });
}

2. Express CSRF Middleware

function csrfProtection(options = {}) {
  const { cookieName = 'csrf', headerName = 'x-csrf-token' } = options;

  return (req, res, next) => {
    // Generate token on GET requests
    if (req.method === 'GET') {
      const token = crypto.randomUUID();
      res.cookie(cookieName, token, {
        httpOnly: false,  // JS must read it to send in header
        sameSite: 'strict',
        secure: process.env.NODE_ENV === 'production',
      });
      return next();
    }

    // Validate token on state-changing requests
    const cookieToken = req.cookies[cookieName];
    const headerToken = req.headers[headerName];

    if (!cookieToken || !headerToken || cookieToken !== headerToken) {
      return res.status(403).json({ error: 'CSRF validation failed' });
    }
    next();
  };
}

Production Checklist

✅ Set SameSite=Lax on all session cookies (default in modern browsers)
✅ Use CSRF tokens for all POST/PUT/DELETE endpoints
✅ Validate Origin/Referer header on state-changing requests
✅ Custom header requirement (X-CSRF-Token) for SPA APIs
✅ Never use GET for state-changing operations
✅ Rotate CSRF tokens on login (prevent fixation)
✅ Test with cross-origin form submission (should fail)
✅ For APIs: prefer Authorization header over cookies
✅ HttpOnly for session cookies (prevents XSS reading)
✅ Audit all cookies: which ones need SameSite=None?
