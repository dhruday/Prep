1. Three Types of XSS

// REFLECTED XSS — payload in URL, reflected by server
// Attacker crafts URL: https://shop.com/search?q=<script>steal()</script>
// Server renders: "Results for <script>steal()</script>"
// Script executes in victim's browser when they click the link
// Delivery: phishing email, social media link, ads

// STORED XSS — payload saved in database, served to all users
// Attacker posts comment: "Great product! <script>steal()</script>"
// Server stores it in DB, serves to every visitor of that page
// Most dangerous — affects ALL users, not just those who click a link
// Real world: TweetDeck XSS worm (2014), Samy worm on MySpace (2005)

// DOM-BASED XSS — payload never reaches server
// Vulnerable JS reads from location.hash / URL params and inserts into DOM
// Example: document.innerHTML = location.hash.slice(1)
// URL: https://site.com/#<img src=x onerror=steal()>
// Server logs show nothing — attack is entirely client-side

3. Browser's Same-Origin Context

// When XSS executes, the script runs with FULL privileges of the origin:
// ✓ Read/write all cookies (except HttpOnly)
// ✓ Access localStorage and sessionStorage
// ✓ Read DOM content (forms, hidden fields, tokens)
// ✓ Make fetch/XHR requests with the user's session
// ✓ Modify the page (phishing forms, fake login)
// ✓ Access webcam/mic if permission was previously granted
//
// This is why XSS is OWASP #1 — it's equivalent to full account takeover

Defense Layer 1: Output Encoding

// Context-aware encoding — different contexts need different encoding

// HTML context: encode < > & " '
function htmlEncode(str) {
  return str.replace(/&/g, '&amp;')
    .replace(/</g, '&lt;').replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;').replace(/'/g, '&#x27;');
}

// URL context: encode all special chars
const safeUrl = encodeURIComponent(userInput);

// JavaScript context: JSON.stringify (escapes quotes/special chars)
const safeJs = JSON.stringify(userInput);

// CSS context: escape or use CSS.escape()
const safeCss = CSS.escape(userInput);

Defense Layer 2: Content Security Policy (CSP)

// CSP is the strongest defense — browser-enforced allowlist

// Strict CSP with nonces:
Content-Security-Policy:
  script-src 'nonce-abc123' 'strict-dynamic';
  object-src 'none';
  base-uri 'self';

// Server generates a unique nonce per request:
<script nonce="abc123">
  // This runs — has the correct nonce
</script>

<script>
  // This is BLOCKED — no nonce, even if injected by XSS
</script>

// 'strict-dynamic' allows nonce'd scripts to load other scripts
// This enables modern bundlers (chunks loaded by main bundle)

Defense Layer 3: DOMPurify Sanitization

// When you MUST render user HTML (rich text editors, markdown)

import DOMPurify from 'dompurify';

// Clean dangerous elements and attributes
const clean = DOMPurify.sanitize(userHtml, {
  ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'a', 'p', 'ul', 'li'],
  ALLOWED_ATTR: ['href', 'title'],
  ALLOW_DATA_ATTR: false,
});

// What DOMPurify removes:
// <script> tags → removed entirely
// onerror, onclick, onload attributes → stripped
// javascript: URLs → removed
// <iframe>, <object>, <embed> → removed
// SVG with embedded scripts → sanitized

Defense Layer 4: Trusted Types API

// Trusted Types prevent DOM XSS at the browser level
// Enforced via CSP header:
Content-Security-Policy: require-trusted-types-for 'script';
  trusted-types myPolicy;

// Create a policy that validates all DOM writes:
const policy = trustedTypes.createPolicy('myPolicy', {
  createHTML: (input) => DOMPurify.sanitize(input),
  createScriptURL: (input) => {
    if (new URL(input).origin === location.origin) return input;
    throw new TypeError('Untrusted script URL');
  },
});

// Now innerHTML REQUIRES a TrustedHTML object:
element.innerHTML = policy.createHTML(userInput); // ✅ Works
element.innerHTML = userInput; // ❌ TypeError! Blocked by browser

FAANG Interview Questions

Q1: Explain the three types of XSS and which is most dangerous.
Reflected XSS embeds the payload in a URL — the server reflects untrusted input back in the response. It requires the victim to click a crafted link. Stored XSS persists the payload in the database — every user who views that content (a comment, profile, post) is affected. DOM-based XSS happens entirely client-side — JavaScript reads from an untrusted source (URL hash, postMessage) and writes to a dangerous sink (innerHTML). Stored XSS is most dangerous because it's persistent and affects all users of a page, not just those who click a specific link. The TweetDeck XSS worm in 2014 was stored XSS — a single malicious tweet auto-retweeted itself to all viewers, spreading exponentially.
Follow-up: How would you detect stored XSS in a large existing codebase?
Q2: How do modern frameworks like React prevent XSS?
React auto-escapes all expressions in JSX — {userInput} is treated as text, not HTML. Under the hood, React uses textContent/createTextNode, not innerHTML. This prevents reflected and stored XSS by default. However, React has explicit escape hatches: dangerouslySetInnerHTML bypasses escaping entirely. If you pass unsanitized user input through it, you're vulnerable. Also, href attributes accept javascript: URLs — <a href={userInput}> is exploitable if userInput is "javascript:alert(1)". React doesn't sanitize attribute values. My approach: never use dangerouslySetInnerHTML without DOMPurify, and validate all URLs against an allowlist of protocols (http:, https:, mailto:).
Follow-up: What about server-side rendering — does React's XSS protection work in SSR?
Q3: Design a defense-in-depth strategy against XSS for a social media platform.
Layer 1: Input validation — reject obviously malicious input at the API (script tags in a "name" field). This is not primary defense but catches low-effort attacks. Layer 2: Output encoding — context-aware encoding for all dynamic content. HTML context uses entity encoding, URL context uses encodeURIComponent, JavaScript context uses JSON.stringify. Layer 3: CSP with nonce — strict Content-Security-Policy that only allows scripts with a server-generated nonce. Even if XSS payload gets into the DOM, the browser blocks execution (no nonce). Layer 4: DOMPurify for rich text — user-generated content that requires HTML (posts, bios) is sanitized with DOMPurify with a strict allowlist. Layer 5: HttpOnly + Secure cookies — session tokens can't be stolen via document.cookie. Layer 6: Trusted Types — browser-level enforcement that all DOM writes go through a sanitization policy.
Follow-up: How does CSP reporting help you detect XSS attempts?
Q4: What is the Trusted Types API and why is it significant?
Trusted Types is a browser API (Chrome 83+) that prevents DOM XSS at the platform level. When enforced via CSP (require-trusted-types-for 'script'), the browser rejects raw strings passed to dangerous sinks like innerHTML, document.write, eval. Instead, you must pass a TrustedHTML/TrustedScript/TrustedScriptURL object created by a registered policy. This moves sanitization from "developer discipline" to "browser enforcement" — even if a developer forgets to sanitize, the browser blocks it. Google deployed Trusted Types internally and reduced DOM XSS vulnerabilities by 60% across their products. The significance: it's the first API that makes an entire class of vulnerability structurally impossible rather than relying on developers never making mistakes.
Follow-up: How do you handle third-party libraries that use innerHTML internally?

1. React XSS Prevention Patterns

// ✅ SAFE — React auto-escapes
function Comment({ text }) {
  return <p>{text}</p>;  // <script> becomes text, not HTML
}

// ❌ DANGEROUS — bypasses React's protection
function RichComment({ html }) {
  return <div dangerouslySetInnerHTML={{ __html: html }} />;
}

// ✅ SAFE — sanitize before dangerouslySetInnerHTML
function SafeRichComment({ html }) {
  const clean = DOMPurify.sanitize(html, {
    ALLOWED_TAGS: ['b', 'i', 'a', 'p', 'br'],
    ALLOWED_ATTR: ['href'],
  });
  return <div dangerouslySetInnerHTML={{ __html: clean }} />;
}

// ❌ DANGEROUS — javascript: URL in href
<a href={userUrl}>Click</a>

// ✅ SAFE — validate URL protocol
function SafeLink({ url, children }) {
  const safe = /^https?:\/\//.test(url) ? url : '#';
  return <a href={safe}>{children}</a>;
}

2. CSP Nonce Implementation (Express)

// Generate unique nonce per request
const crypto = require('crypto');

app.use((req, res, next) => {
  res.locals.nonce = crypto.randomBytes(16).toString('base64');
  res.setHeader('Content-Security-Policy',
    `script-src 'nonce-${res.locals.nonce}' 'strict-dynamic'; ` +
    `object-src 'none'; base-uri 'self';`
  );
  next();
});

// In HTML template:
<script nonce="<%= nonce %>">
  // App code runs — has valid nonce
</script>

// Injected by XSS (no nonce):
<script>alert('xss')</script>  // BLOCKED by browser

Production Checklist

✅ Use framework auto-escaping (React JSX, Angular templates)
✅ NEVER use innerHTML/dangerouslySetInnerHTML without DOMPurify
✅ Validate URL protocols (block javascript:, data:)
✅ Deploy strict CSP with nonces (not 'unsafe-inline')
✅ Set HttpOnly + Secure + SameSite on session cookies
✅ Enable Trusted Types for DOM XSS prevention
✅ Use CSP report-uri to detect XSS attempts
✅ Audit all uses of innerHTML, eval, document.write
✅ Sanitize user input on BOTH client and server
✅ Run automated XSS scanners in CI (e.g., OWASP ZAP)
