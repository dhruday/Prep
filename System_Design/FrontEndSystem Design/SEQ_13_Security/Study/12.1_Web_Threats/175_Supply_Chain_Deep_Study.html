1. The npm Supply Chain Problem

// Average React app: 1,000-2,000 dependencies (direct + transitive)
// Each dependency = code you trust to run in your app / user's browser
//
// Attack vectors:
// 1. Compromised maintainer account → push malicious update
//    (event-stream 2018: 1.5M weekly downloads, crypto wallet theft)
// 2. Typosquatting → register crossenv instead of cross-env
// 3. Dependency confusion → publish internal package name to npm public
// 4. Install scripts → "postinstall": "node steal-env.js"
// 5. Abandoned package takeover → request ownership transfer
//
// The trust model is fragile:
//   npm install lodash → trusts lodash + all its deps
//   → trusts all maintainers of those packages
//   → trusts npm's infrastructure wasn't compromised
//   → trusts the registry is serving the real package

3. SRI (Subresource Integrity)

// When loading scripts from CDN, verify file hasn't been tampered
// Browser computes hash of downloaded file, compares to expected hash

<script
  src="https://cdn.example.com/lib@3.0.0/dist/lib.min.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous">
</script>

// Generate hash: openssl dgst -sha384 -binary lib.min.js | base64
// If CDN is compromised and file changes → hash mismatch → script blocked
// Must include crossorigin="anonymous" for CORS-enabled resources

1. Dependency Confusion Attack (Deep Dive)

// Your company has private npm packages:
//   @company/auth-utils (private registry, version 1.2.0)
//
// Attack: publish "auth-utils" (no scope) to public npm at version 99.0.0
// If .npmrc is misconfigured, npm resolves: higher version wins
// → installs public malicious 99.0.0 instead of private 1.2.0
//
// Defense:
// 1. Always use scoped packages (@company/name)
// 2. Configure .npmrc to route scopes to private registry:
//    @company:registry=https://npm.company.com/
// 3. "Register" your private names on public npm as empty placeholders
// 4. Use package-lock.json (pins resolved URLs, not just versions)

FAANG Interview Questions

Q1: How would you design a secure dependency management pipeline for a frontend team?
Multi-layered approach: (1) Lockfiles committed and enforced — CI uses npm ci which fails if lock is stale, ensuring reproducible builds. (2) Pin exact versions in package.json (no ^ or ~) for sensitive packages. (3) npm audit in CI — configure audit-ci to fail the build on high/critical vulnerabilities. (4) Renovate/Dependabot for automated dependency updates with CI checks. (5) Ignore install scripts for untrusted packages (--ignore-scripts with explicit allow list). (6) Private registry proxy (Artifactory/Verdaccio) that caches packages and blocks known-malicious ones. (7) SRI hashes on all CDN-loaded scripts. (8) Socket.dev or Snyk integration that flags behavioral anomalies (new install scripts, env access, network calls) in PRs. (9) CODEOWNERS on package.json — require security team approval for new dependencies. (10) Regular dependency review: trim unused packages, audit transitive deps.
Follow-up: How do you handle the case where a critical vulnerability is found in a deep transitive dependency?
Q2: Explain the event-stream incident and its lessons.
event-stream was a popular npm package (1.5M weekly downloads). The original maintainer had lost interest and handed ownership to a contributor who asked for it. That new maintainer added a dependency (flatmap-stream) which contained obfuscated code targeting the Copay Bitcoin wallet app. The malicious code only activated in the Copay build environment and stole wallet credentials. Lessons: (1) The "trust chain problem" — you trust not just the package but all its maintainers, present and future. (2) Transitive dependency attacks are stealthy — the malicious code was one level deep, not in event-stream itself. (3) npm's social model (anyone can request transfer) is a vulnerability. (4) Targeted attacks are hard to detect — the payload only ran in one specific app. Mitigations inspired: npm 2FA enforcement for popular packages, GitHub's npm provenance, Socket.dev behavioral analysis.
Follow-up: How does npm provenance solve this? What are its limitations?
Q3: What is SRI and when would you NOT use it?
SRI (Subresource Integrity) lets you specify a cryptographic hash of the expected file content in the script/link tag. The browser downloads the resource, computes the hash, and blocks execution if it doesn't match. I use it for all CDN-loaded scripts — it protects against CDN compromise, MITM (if somehow TLS fails), and cache poisoning. When NOT to use: (1) When loading from first-party same-origin (SRI adds overhead for no security benefit). (2) When the resource URL is versioned AND immutable (e.g., npm CDN with exact version — the URL changes per version). (3) When using dynamic imports that frequently change — you'd need to update hashes in the HTML on every change. (4) Some analytics/widget scripts that are intentionally updated by the third party. In those cases, I prefer CSP with strict script-src instead of SRI.
Follow-up: Can SRI protect against a compromised build pipeline?

1. npm Configuration Hardening

// .npmrc — project level
engine-strict=true
ignore-scripts=true          // Block install scripts by default
audit=true                    // Audit on every install
fund=false
@company:registry=https://npm.company.com/  // Private scope routing

// Allow-list specific packages that need install scripts:
// .npmrc: (npm 9.4+)
// allow-scripts[esbuild]=true
// allow-scripts[sharp]=true

// package.json — pin versions
{
  "dependencies": {
    "react": "18.2.0",       // No ^ or ~
    "@company/auth": "2.1.0"  // Scoped for private
  }
}

2. CI Pipeline Supply Chain Checks

# GitHub Actions workflow
- name: Install (strict)
  run: npm ci --ignore-scripts

- name: Run allowed install scripts
  run: npx allow-scripts

- name: Security audit
  run: npx audit-ci --critical

- name: Check for new dependencies
  run: |
    git diff HEAD~1 package.json |
    grep '"dependencies"' &&
    echo "⚠️ New dependency added — requires security review"

- name: License check
  run: npx license-checker --failOn "GPL-3.0"

- name: SRI hash generation
  run: npx ssri $(cat dist/vendor.js) --algorithms sha384

✅ Commit lockfiles (package-lock.json / yarn.lock)
✅ Use npm ci in CI (not npm install)
✅ Pin exact versions for critical dependencies
✅ Run npm audit in CI pipeline (fail on high/critical)
✅ Use --ignore-scripts with explicit allow-list
✅ Scope private packages (@company/name)
✅ Route scoped packages to private registry in .npmrc

✅ Dependabot/Renovate for automated updates
✅ CODEOWNERS on package.json changes
