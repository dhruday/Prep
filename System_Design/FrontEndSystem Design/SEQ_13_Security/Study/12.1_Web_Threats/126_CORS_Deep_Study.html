1. Same-Origin Policy (SOP) — The Foundation

// SOP: a page from origin A can only read resources from origin A
// Origin = scheme + host + port
//   https://api.example.com:443  vs  http://api.example.com:80
//   ↑ different scheme = different origin
//
// SOP restricts:
//   ❌ fetch() / XMLHttpRequest reading cross-origin responses
//   ❌ JavaScript reading cross-origin iframe content
//   ❌ Reading cross-origin canvas data (tainted canvas)
//
// SOP does NOT restrict:
//   ✅ <img src="cross-origin">   → embeds, but JS can't read pixels
//   ✅ <script src="cross-origin"> → executes (JSONP exploit surface)
//   ✅ <link href="cross-origin">  → loads CSS
//   ✅ <form action="cross-origin"> → submits (CSRF exploit surface)
//
// CORS is the controlled relaxation of SOP

2. Simple vs Preflighted Requests

CriteriaSimple RequestPreflighted Request
MethodsGET, HEAD, POSTPUT, DELETE, PATCH, etc.
Content-Typetext/plain, multipart/form-data, application/x-www-form-urlencodedapplication/json, etc.
Custom HeadersNone (only CORS-safelisted)Any custom header (X-CSRF-Token, Authorization)
Browser BehaviorSends request directly, checks response headersSends OPTIONS first, then actual request if allowed
Preflight cached?N/AYes, via Access-Control-Max-Age
Key insight: Most real API calls (JSON body, Authorization header) trigger a preflight. The browser sends an OPTIONS request BEFORE the actual request. If your server doesn't handle OPTIONS correctly, the actual request is never sent.

3. CORS Headers Explained

// Response headers the server must set:

Access-Control-Allow-Origin: https://app.example.com
  // Which origin(s) can read the response
  // Can be specific origin or * (but NOT with credentials)

Access-Control-Allow-Methods: GET, POST, PUT, DELETE
  // Which methods are allowed (preflight response)

Access-Control-Allow-Headers: Authorization, X-CSRF-Token, Content-Type
  // Which custom headers client can send

Access-Control-Allow-Credentials: true
  // Allow cookies/auth headers. If true:
  //   - Allow-Origin cannot be * (must be specific origin)
  //   - Client must set: fetch(url, { credentials: 'include' })

Access-Control-Expose-Headers: X-Total-Count, X-Request-Id
  // Which response headers JS can read (defaults: Cache-Control,
  //   Content-Language, Content-Type, Expires, Last-Modified, Pragma)

Access-Control-Max-Age: 86400
  // How long (seconds) to cache preflight result
  // Chrome caps at 7200 (2hrs); Firefox at 86400 (24hrs)

CORS Misconfigurations (Attack Vectors)

1. Reflecting Origin (Wildcard with Credentials)

// DANGEROUS: Server reflects whatever Origin header was sent
app.use((req, res, next) => {
  res.setHeader('Access-Control-Allow-Origin', req.headers.origin);
  res.setHeader('Access-Control-Allow-Credentials', 'true');
  next();
});
// ❌ Any origin can now read authenticated responses
// evil.com can steal user data from your API

2. Null Origin Allowance

// DANGEROUS: Some servers allow Origin: null
// Null origin comes from: sandboxed iframes, local files, redirects
// An attacker can craft: <iframe sandbox="allow-scripts"...
// → browser sends Origin: null → server allows it
// ❌ Never allow 'null' as a trusted origin

3. Regex Bypass

// DANGEROUS: Loose regex for origin validation
const allowed = /example\.com$/;
// Attacker registers: attackerexample.com → matches!

// FIX: Anchor your regex properly
const allowed = /^https:\/\/(app|api)\.example\.com$/;

FAANG Interview Questions

Q1: Walk through what happens when a browser makes a cross-origin fetch with JSON body and Authorization header.
Since the request has a custom Authorization header and Content-Type: application/json, it's not a "simple" request — the browser sends a preflight. Step 1: Browser sends OPTIONS to the URL with headers: Origin (the requesting page's origin), Access-Control-Request-Method (POST), Access-Control-Request-Headers (Authorization, Content-Type). Step 2: Server responds with CORS headers: Allow-Origin, Allow-Methods, Allow-Headers, Max-Age. If Allow-Credentials: true, Allow-Origin must be the specific origin (not *). Step 3: Browser checks if the actual method and headers are in the allowed list. If yes, browser sends the real POST. If credentials are involved, the client must have { credentials: 'include' }. Step 4: Browser checks the actual response's Allow-Origin header again before exposing the response body to JS. If any check fails, JS gets a NetworkError with no details (to prevent information leakage).
Follow-up: Why doesn't the browser tell you which CORS check failed?
Q2: Why can't you use Access-Control-Allow-Origin: * with credentials?
If the server says "any origin can read my responses with cookies attached," any malicious site could make authenticated requests and read the responses. The browser enforces a spec rule: when Allow-Credentials is true, Allow-Origin must be a specific origin, not wildcard. This forces the server to explicitly declare which origin is trusted to receive credentialed responses. In practice, the server reads the Origin header, validates it against a whitelist, and echoes it back. The key distinction from the "reflecting origin" vulnerability is that a proper implementation has an actual whitelist — it doesn't just echo any origin.
Follow-up: How does this interact with CDN caching? What's the Vary: Origin header for?
Q3: How do you optimize CORS preflight performance?
Preflights add latency — an extra RTT before every API call. Optimization: (1) Access-Control-Max-Age — cache preflight results. Set to 7200s for Chrome (its internal max is 2hrs). (2) Keep requests "simple" where possible — using form-urlencoded instead of JSON avoids preflight (though rarely practical). (3) Use a proxy or BFF — if app.example.com proxies to api.example.com, the browser sees same-origin and skips CORS entirely. (4) Consolidate API calls to reduce total preflight count. (5) For CDN/static assets, use crossorigin attribute on <link> and <script> tags so the browser caches CORS-enabled responses properly. In production, I typically set Max-Age to the browser max and use a BFF to avoid CORS for most API calls.
Follow-up: What's the Private Network Access spec, and how does it change CORS for localhost?

1. Express CORS Middleware (Production-Grade)

const allowedOrigins = new Set([
  'https://app.example.com',
  'https://staging.example.com',
]);

function corsMiddleware(req, res, next) {
  const origin = req.headers.origin;

  if (origin && allowedOrigins.has(origin)) {
    res.setHeader('Access-Control-Allow-Origin', origin);
    res.setHeader('Access-Control-Allow-Credentials', 'true');
    res.setHeader('Vary', 'Origin'); // Critical for CDN caching
  }

  if (req.method === 'OPTIONS') {
    res.setHeader('Access-Control-Allow-Methods', 'GET,POST,PUT,DELETE');
    res.setHeader('Access-Control-Allow-Headers',
      'Authorization,Content-Type,X-CSRF-Token');
    res.setHeader('Access-Control-Max-Age', '7200');
    return res.sendStatus(204); // No body needed
  }
  next();
}

2. Vite/Webpack Dev Proxy (Avoid CORS in Development)

// vite.config.js — proxy API calls to avoid CORS entirely
export default {
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:3000',
        changeOrigin: true,
      },
    },
  },
};
// Browser sees same-origin → no CORS headers needed in dev
// In production, nginx/BFF handles the same proxying

Common Mistakes

❌ Reflecting Origin without whitelist
❌ Allow-Origin: * with Allow-Credentials: true (browser rejects)
❌ Forgetting Vary: Origin (CDN serves wrong origin's response)
❌ Not handling OPTIONS → 404/405 → preflight fails
❌ Regex without anchors: /example\.com$/ matches evil-example.com
❌ Allowing Origin: null
❌ Not setting Expose-Headers → can't read X-Total-Count pagination
❌ Forgetting CORS on error responses (4xx/5xx) → opaque error in JS
