1. What Is SRI?

// Subresource Integrity: browser verifies file content matches expected hash
// Before executing a script or applying a stylesheet, browser:
//   1. Downloads the resource
//   2. Computes SHA hash of the content
//   3. Compares to the hash in the integrity attribute
//   4. If mismatch → BLOCKS execution
//
// Protects against:
// ✅ CDN compromise (attacker modifies hosted file)
// ✅ MITM (if TLS somehow fails, modified file detected)
// ✅ Cache poisoning (proxy/CDN serves wrong content)
// ✅ Supply chain attacks via CDN

<script
  src="https://cdn.example.com/react@18.2.0/umd/react.production.min.js"
  integrity="sha384-FjROGhGDq6bfzGpK3mREbJQIyJcMa..."
  crossorigin="anonymous">
</script>

// crossorigin="anonymous" is REQUIRED for cross-origin SRI
// Without it, browser can't access content for hashing

2. How SRI Hashes Work

// Generate hash:
// openssl dgst -sha384 -binary file.js | openssl base64 -A
// Or: shasum -b -a 384 file.js | xxd -r -p | base64
//
// Format: {algorithm}-{base64-hash}
// Supported: sha256, sha384, sha512
// sha384 is the recommended default (balance of speed + security)
//
// Multiple hashes for migration/fallback:
// integrity="sha384-abc... sha512-xyz..."
// Browser uses the strongest supported algorithm
// Match ANY hash → resource allowed
//
// Works with: <script> and <link rel="stylesheet">
// Does NOT work with: <img>, <video>, fetch(), <iframe>

3. SRI + CSP Integration

// CSP can REQUIRE SRI for all scripts/styles:
Content-Security-Policy: require-sri-for script style

// With this directive:
// <script src="..."> → BLOCKED (no integrity attribute)
// <script src="..." integrity="sha384-..."> → ALLOWED
//
// This enforces that EVERY external resource has an SRI hash
// Catches: developer forgetting to add integrity on new script
//
// ⚠️ require-sri-for is not widely supported yet
// Chrome removed it; Firefox supports it behind flag
// Alternative: use a strict CSP with nonces instead
For maximum security, combine SRI (verifies CDN content) with CSP nonces (controls which scripts execute). They protect against different threats and are complementary.

CDN Compromise Scenario

// Without SRI:
// 1. Your app loads jQuery from cdn.jsdelivr.net
// 2. Attacker compromises jsdelivr's infrastructure
// 3. Attacker replaces jquery.min.js with malicious version
//    (includes keylogger, crypto miner, data exfiltration)
// 4. Every site loading from jsdelivr serves the malicious script
// 5. Your users are compromised
//
// With SRI:
// 1-3. Same attack happens
// 4. Browser downloads the modified jquery.min.js
// 5. Computes SHA-384 hash → doesn't match integrity attribute
// 6. Browser REFUSES to execute the script
// 7. Console error: "Subresource Integrity: resource integrity mismatch"
// 8. Your app may break (missing jQuery) but users are SAFE
//
// Real incident: cdnjs (2021) had RCE vulnerability
// Attacker could have modified any hosted library
// Sites with SRI would have been protected

SRI Challenges

// 1. Dynamic resources (hash changes on every deployment)
//    → Use build tool to auto-generate hashes
//    → Or self-host and use nonces instead
//
// 2. Third-party scripts that auto-update (analytics, widgets)
//    → Can't use SRI (hash changes without warning)
//    → Alternative: self-host a pinned version
//    → Or use CSP + nonces for these
//
// 3. Content negotiation (server returns different encoding)
//    → gzip vs brotli → different bytes → different hash!
//    → SRI is computed on the DECOMPRESSED content (browser handles this)
//
// 4. CDN edge processing (minification, optimization)
//    → CDN must NOT modify the file content
//    → Disable CDN transformations for SRI-protected resources

FAANG Interview Questions

Q1: What is SRI and when would you use it in production?
SRI (Subresource Integrity) is a W3C standard that lets you specify a cryptographic hash of expected file content in script and link tags. The browser downloads the resource, computes the hash, and blocks execution if it doesn't match. I use SRI for all CDN-loaded scripts and stylesheets — it protects against CDN compromise, supply chain attacks, and cache poisoning. The integrity attribute uses SHA-384 (recommended) format: integrity="sha384-{base64 hash}", and requires crossorigin="anonymous" for cross-origin resources. When NOT to use: first-party resources on same origin (no added security), dynamically-updating third-party scripts where the hash changes without warning (like analytics snippets), or resources loaded via JS (SRI only works on script/link tags). For dynamic third-party scripts, I prefer self-hosting a pinned version with SRI, or using strict CSP with nonces instead. SRI and CSP nonces are complementary — SRI verifies content integrity, nonces control script execution authorization.
Follow-up: How do you automate SRI hash generation in a CI/CD pipeline?
Q2: How does SRI interact with CDN caching and content negotiation?
SRI hashes are computed on the decompressed content, so gzip/brotli encoding doesn't affect hashing — the browser decompresses first, then hashes. However, CDN edge processing can break SRI: if the CDN minifies, optimizes, or modifies file content, the hash will mismatch. You must disable CDN transformations for SRI-protected resources (Cloudflare: disable Auto Minify). For CDN caching: the integrity attribute is an additional validation on top of cache. Even if the CDN serves a cached file, the browser verifies the hash before execution. Cache poisoning that substitutes a different file is caught by SRI. For versioned CDN URLs (e.g., react@18.2.0), the hash is stable per version — generate once, use forever. For content-addressed URLs (hash in filename like vendor.abc123.js), SRI is redundant since the URL itself guarantees content (but it's still defense-in-depth). I recommend always including SRI for cross-origin resources regardless of URL structure.
Follow-up: What happens to users if a CDN-hosted file fails SRI check? How do you handle the fallback?

1. Build Tool Integration (Webpack)

// webpack.config.js
const SriPlugin = require('webpack-subresource-integrity');

module.exports = {
  output: {
    crossOriginLoading: 'anonymous', // Required for SRI
  },
  plugins: [
    new SriPlugin({
      hashFuncNames: ['sha384'],
      enabled: process.env.NODE_ENV === 'production',
    }),
  ],
};

// Webpack automatically:
// 1. Computes SHA-384 of each output chunk
// 2. Adds integrity attribute to script/link tags in HTML
// 3. Adds crossorigin="anonymous" attribute

2. Manual SRI Hash Generation

// Command line:
openssl dgst -sha384 -binary file.js | openssl base64 -A
// Output: oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQl...

// Node.js script:
const crypto = require('crypto');
const fs = require('fs');

function generateSRI(filePath) {
  const content = fs.readFileSync(filePath);
  const hash = crypto
    .createHash('sha384')
    .update(content)
    .digest('base64');
  return `sha384-${hash}`;
}

console.log(generateSRI('./dist/vendor.js'));
// sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/...

// HTML output:
// <script src="vendor.js" integrity="sha384-oqVu..." crossorigin="anonymous"></script>

3. SRI with Fallback

<!-- Load from CDN with SRI -->
<script
  src="https://cdn.jsdelivr.net/npm/react@18.2.0/umd/react.production.min.js"
  integrity="sha384-xxx..."
  crossorigin="anonymous"
  onerror="loadFallback(this)">
</script>

<script>
// If CDN fails or SRI mismatch → load from own server
function loadFallback(failedScript) {
  const fallback = document.createElement('script');
  fallback.src = '/vendor/react.production.min.js'; // Self-hosted copy
  fallback.integrity = 'sha384-xxx...'; // Same hash
  document.head.appendChild(fallback);
}
</script>

SRI Implementation Checklist

✅ Add integrity attribute to all CDN <script> and <link> tags
✅ Use sha384 as the hash algorithm (recommended standard)
✅ Always add crossorigin="anonymous" for cross-origin resources
✅ Automate hash generation in build pipeline (webpack/vite plugin)
✅ Self-host fallback copies of critical CDN resources
✅ Disable CDN content transformations (auto-minify, image optimization)
✅ Verify SRI works: modify a hash → script should be blocked
✅ Combine with CSP nonces for maximum protection
✅ Pin CDN URLs to specific versions (not @latest)
✅ Monitor CSP/SRI violations in your reporting endpoint
✅ Update SRI hashes when upgrading library versions

SRI vs Other Protections

ThreatSRICSPHTTPS
CDN compromise✅ Blocks modified files⚠️ Allows if domain whitelisted❌ No protection
Injected inline script❌ Only for external resources✅ Nonces block unauthorized inline❌ No protection
MITM (modified in transit)✅ Detects modification❌ Domain still matches✅ Encrypts transport
Unauthorized script source❌ Content-based, not source-based✅ Blocks unauthorized sources❌ No protection
Cache poisoning✅ Verifies cached content❌ Cache serves allowed domain❌ No protection
SRI and CSP protect against different threats. SRI verifies "is this the right content?". CSP controls "is this an allowed source?". Use both together for defense in depth.
