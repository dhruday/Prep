Long Tasks — the threshold and why it matters

The browser defines a Long Task as any main-thread task taking ≥ 50 ms. Why 50 ms? To maintain 60 fps you have a 16 ms budget per frame. 50 ms is the threshold beyond which users perceive UI as "slow to respond" (RAIL model). Long Tasks directly degrade INP (Interaction to Next Paint) and TTI.

Common Long Task culprits
  • 📦 Synchronous JS module evaluation
  • 🔄 Unvirtualized list renders
  • 🧮 Heavy JSON parsing / serialisation
  • 🎨 Forced synchronous layouts
  • 📊 Complex reselect computations
Detection APIs
  • PerformanceObserver (longTask)
  • Chrome DevTools Performance panel
  • Lighthouse "Minimize main-thread work"
  • web-vitals.js onINP callback
  • scheduler.yield() (Chrome 115+)

At SAP: SAP Fiori order management dashboard had an 800ms long task on initial data load — caused by synchronous normalisation of a 5 000-item dataset. Split into 100-item chunks with setTimeout → reduced to 8 × 50ms tasks → TTI improved from 5.2 s → 1.8 s.

Three yielding strategies

setTimeout(fn, 0)
Classic macrotask yield. Guaranteed to let the browser respond to inputs and paint before calling fn. Problem: task priority is the same as timers — analytics events may execute before user-visible work. 
items.forEach((item, i) => {
  if (i % chunkSize === 0) setTimeout(() => process(item), 0);
  else process(item);
});
MessageChannel (faster yield)
MessageChannel.postMessage() schedules a microtask-adjacent, slightly higher priority macrotask than setTimeout. Used by React's scheduler internally because setTimeout min delay is clamped to 4ms in nested calls.
scheduler.yield() (Chrome 115+)
New API: await scheduler.yield() yields the current task at user-blocking priority, resuming before background timers. The cleanest ergonomics: just await in async functions. Polyfillable with MessageChannel. 
async function processAll(items: Item[]) {
  for (const [i, item] of items.entries()) {
    if (i % 10 === 0) await scheduler.yield();
    process(item);
  }
}

Long task detection + chunking utility

// ─── Detect long tasks ───
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.warn(`Long Task detected: ${entry.duration.toFixed(0)}ms`, entry);
    // Send to analytics for RUM baseline
    trackEvent('long_task', { duration: entry.duration, page: window.location.pathname });
  }
});
observer.observe({ type: 'longtask', buffered: true });

// ─── Reusable chunked processor ───
function yieldToMain(): Promise<void> {
  // scheduler.yield() with fallback
  if ('scheduler' in self && 'yield' in scheduler)
    return (scheduler as any).yield();
  return new Promise(resolve => setTimeout(resolve, 0));
}

async function chunkProcess<T>(
  items: T[], work: (item: T) => void, chunkSize = 20
): Promise<void> {
  for (let i = 0; i < items.length; i++) {
    work(items[i]);
    if ((i + 1) % chunkSize === 0) await yieldToMain();
  }
}

// Usage: SAP order normalisation
await chunkProcess(rawOrders, (o) => dispatch(addOrder(normalise(o))));
