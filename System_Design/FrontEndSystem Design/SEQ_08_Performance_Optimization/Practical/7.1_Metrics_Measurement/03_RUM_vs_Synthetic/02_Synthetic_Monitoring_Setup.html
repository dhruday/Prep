Synthetic vs RUM Monitoring

Practical 7.1 · Understanding when to use each monitoring approach

Comparison Matrix

Data sourceLab environment, controlledReal users, real devices
When to measurePre-deploy (CI/CD), scheduledPost-deploy, continuous
ConsistencyReproducible (same device/network)Varies by user conditions
CoverageOnly tested pages/flowsAll pages users actually visit

Regression detectionImmediate (in PR check)After deployment (needs traffic)
CostInfrastructure cost (CI runners)Beacon storage + analytics

Decision Framework

Use Synthetic when:
✓ Catching regressions before deploy (CI gate)
✓ A/B testing build configurations
✓ Benchmarking against competitors
✓ Testing specific user journeys (checkout flow)
✓ You need reproducible, blame-able numbers

Use RUM when:
✓ Understanding real user experience (p75, p95)
✓ Measuring INP (requires real interactions)
✓ Segmenting by device/network/geography
✓ Correlating perf with business KPIs (conversion)
✓ Monitoring long-tail pages you can't test synthetically

Best practice: Use BOTH
Synthetic = front door guard (prevents regressions)
RUM = security camera (monitors real experience)

Typical Setup

// PR pipeline (Synthetic):
// 1. Build app
// 2. Deploy to preview URL
// 3. Run Lighthouse CI against preview
// 4. Assert budgets → fail PR if exceeded
// 5. Post results as PR comment

// Production (RUM):
// 1. Include web-vitals in app bundle
import { onLCP, onINP, onCLS } from 'web-vitals';

onLCP(sendToAnalytics);
onINP(sendToAnalytics);
onCLS(sendToAnalytics);

function sendToAnalytics(metric) {
  // Send to your backend/analytics
  navigator.sendBeacon('/api/vitals', JSON.stringify({
    name: metric.name,     // 'LCP', 'INP', 'CLS'
    value: metric.value,   // ms or score
    rating: metric.rating, // 'good', 'needs-improvement', 'poor'
    url: location.pathname,
    id: metric.id,
  }));
}

// Dashboard: aggregate p75 per page per day
// Alert: if p75 LCP crosses 2.5s for any key page
