1. What Is a Long Task?

// Chrome defines a "Long Task" as any task > 50ms on the main thread
//
// Why 50ms? Because:
// - Frame budget is ~16ms (60fps)
// - RAIL model: Response within 100ms
// - 50ms task + input delay + rendering ≈ 100ms total
// - So 50ms is the max "safe" JS execution time
//
// Common sources of long tasks:
// 1. JavaScript parsing & compilation (large bundles)
// 2. Large React/Angular renders (100+ components)
// 3. Data processing (filtering, sorting 10K+ items)
// 4. JSON parsing (large API responses)
// 5. Third-party scripts (analytics, ads)
// 6. DOM manipulation (adding 1000+ nodes)
// 7. Synchronous XHR (never do this)
//
// Detecting long tasks:
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.warn(
      `Long Task: ${entry.duration}ms`,
      entry.attribution[0]?.containerSrc // which script
    );
  }
});
observer.observe({ type: 'longtask', buffered: true });

Pattern 1: Time-Sliced Processing

// Process items in chunks, yielding between chunks
async function processInChunks(items, chunkSize = 100) {
  const results = [];

  for (let i = 0; i < items.length; i += chunkSize) {
    const chunk = items.slice(i, i + chunkSize);
    const chunkResults = chunk.map(item => processItem(item));
    results.push(...chunkResults);

    // Yield to main thread
    await yieldToMain();
  }

  return results;
}

function yieldToMain() {
  return new Promise(resolve => {
    const ch = new MessageChannel();
    ch.port1.onmessage = resolve;
    ch.port2.postMessage(undefined);
  });
}

Pattern 2: Deadline-Based Yielding

// Use isInputPending (Chrome 87+) to yield only when needed
async function processWithDeadline(items) {
  let deadline = performance.now() + 50; // 50ms budget
  let i = 0;

  while (i < items.length) {
    // Check: should we yield?
    if (
      navigator.scheduling?.isInputPending?.() ||  // User waiting?
      performance.now() >= deadline                // Time's up?
    ) {
      await yieldToMain();
      deadline = performance.now() + 50; // Reset budget
    }

    processItem(items[i++]);
  }
}

// Pattern 3: scheduler.yield() (Chrome 129+, experimental)
// The simplest yielding API — built into the platform
async function processWithYield(items) {
  for (let i = 0; i < items.length; i++) {
    processItem(items[i]);
    if (i % 100 === 0) {
      await scheduler.yield(); // Yield, keep priority
    }
  }
}
// Unlike setTimeout, scheduler.yield() keeps your task priority
// So your continuation runs BEFORE lower-priority tasks

Web Workers: Move Work Off Main Thread

// Web Workers run JavaScript on a SEPARATE thread
// They can NOT access the DOM
// Communication via postMessage (structured clone)

// main.js:
const worker = new Worker('/sort-worker.js');

worker.postMessage({ items: largeArray, sortKey: 'price' });

worker.onmessage = (e) => {
  const sorted = e.data;
  renderList(sorted); // Back on main thread for DOM update
};

// sort-worker.js:
self.onmessage = (e) => {
  const { items, sortKey } = e.data;
  const sorted = items.sort((a, b) => a[sortKey] - b[sortKey]);
  self.postMessage(sorted);
};

// Comlink: Library that makes workers feel like async functions
// worker.js:
import { expose } from 'comlink';
const api = {
  async sortItems(items, key) {
    return items.sort((a, b) => a[key] - b[key]);
  }
};
expose(api);

// main.js:
import { wrap } from 'comlink';
const api = wrap(new Worker('/worker.js'));
const sorted = await api.sortItems(items, 'price');
// Looks like a regular async call!

FAANG Interview Questions

Q1: You have to sort and filter 100K records client-side. How do you keep the UI responsive?
Three-tier approach: (1) Move the heavy work to a Web Worker. Sorting/filtering is pure computation with no DOM dependency — perfect for a worker. Main thread stays fully free for user interactions. Use Comlink to simplify the API. Transfer the data using Transferable objects (ArrayBuffer) to avoid structured clone overhead for large datasets. (2) If the data changes frequently, add a debounce — don't re-sort on every keystroke, wait 150ms after the user stops typing, then send the filter criteria to the worker. (3) For the results, virtualize the list — only render ~50 visible items regardless of how many match. Combined: user types → debounce 150ms → worker sorts/filters → postMessage results → virtualized list renders ~50 items. The main thread never does heavy computation, and rendering is O(visible items) not O(total items). If Web Workers aren't viable (legacy codebase), fall back to time-sliced processing: process items in chunks of 1000, yield to main thread between chunks via MessageChannel.

Q2: What is scheduler.yield() and how does it differ from setTimeout(fn, 0)?
Both yield to the main thread, but with a critical difference in task priority. setTimeout(fn, 0) pushes your continuation to the back of the task queue. If 10 other tasks are queued (analytics scripts, timers), your continuation waits behind all of them. This can cause your yielded work to take much longer to resume, which is why Google calls it the "yield tax." scheduler.yield() (Chrome 129+) yields but KEEPS your current task priority. Your continuation runs before lower-priority pending tasks, not after them. It's like saying "I'm pausing to let higher-priority things (user clicks) through, but I'll resume before background tasks." This is exactly what you want for UI-critical work that just needs to be chunked. Additionally, setTimeout has a 4ms minimum delay after 5 nested calls (HTML spec), while scheduler.yield() has no such clamping. For now, scheduler.yield() has limited browser support — use it with a fallback to MessageChannel or setTimeout.

Decision Tree

Is the work > 50ms?
├── No → Run synchronously, no optimization needed
└── Yes → Does it need DOM access?
    ├── No → Use Web Worker
    │   ├── Large data? → Use Transferable objects
    │   └── Complex API? → Use Comlink
    └── Yes → Break into chunks + yield
        ├── scheduler.yield() available? → Use it
        ├── Need priority control? → scheduler.postTask()
        ├── Need idle-only? → requestIdleCallback
        └── Fallback → MessageChannel or setTimeout(fn, 0)
