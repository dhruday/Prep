1. Lazy Loading Taxonomy

// Lazy loading = defer loading of resources until they're actually needed
//
// Three categories:
//
// 1. Component Lazy Loading (React.lazy)
//    Load JS modules on demand → reduces initial bundle
//    Trigger: route navigation, user interaction, visibility
//
// 2. Image Lazy Loading (loading="lazy")
//    Defer offscreen image downloads → reduces initial bandwidth
//    Trigger: scroll into viewport (IntersectionObserver internally)
//
// 3. Data Lazy Loading (pagination, infinite scroll)
//    Fetch data incrementally → reduces initial API payload
//    Trigger: scroll, button click, page change
//
// Why it matters at FAANG scale:
// - Facebook: 5000+ components, users see ~50 per session
// - Loading everything upfront = 10MB+ of JS
// - Lazy loading achieves ~200KB initial load

2. React.lazy & Suspense Internals

// React.lazy() creates a "lazy component" that wraps dynamic import()
//
// Internal implementation (simplified):
function lazy(loader) {
  let status = 'pending';
  let result;
  const promise = loader().then(
    (mod) => { status = 'resolved'; result = mod; },
    (err) => { status = 'rejected'; result = err; },
  );

  return {
    $$typeof: REACT_LAZY_TYPE,
    _init() {
      if (status === 'pending') throw promise;  // ← Suspense catches this
      if (status === 'rejected') throw result;
      return result.default;
    }
  };
}

// How Suspense works:
// 1. React tries to render the lazy component
// 2. Lazy component throws a Promise (not an error)
// 3. Suspense boundary catches the thrown Promise
// 4. Suspense renders fallback UI while Promise is pending
// 5. When Promise resolves, React re-renders with the loaded component
// 6. If Promise rejects, error propagates to nearest ErrorBoundary
//
// KEY: React.lazy only supports DEFAULT exports
// For named exports, re-export as default in a wrapper module

Pattern 1: Route-Level Lazy Loading

import { lazy, Suspense } from 'react';
import { Routes, Route } from 'react-router-dom';
import PageSkeleton from './PageSkeleton';

// Named chunk for better debugging
const Home = lazy(() => import(/* webpackChunkName: "home" */ './pages/Home'));
const Products = lazy(() => import(/* webpackChunkName: "products" */ './pages/Products'));
const Checkout = lazy(() => import(/* webpackChunkName: "checkout" */ './pages/Checkout'));

function App() {
  return (
    <ErrorBoundary fallback={<ErrorPage />}>
      <Suspense fallback={<PageSkeleton />}>
        <Routes>
          <Route path="/" element={<Home />} />
          <Route path="/products/*" element={<Products />} />
          <Route path="/checkout" element={<Checkout />} />
        </Routes>
      </Suspense>
    </ErrorBoundary>
  );
}

Pattern 2: Interaction-Based Lazy Loading

// Load component only when user interacts
function ProductActions() {
  const [ShowReview, setShowReview] = useState(null);

  const handleWriteReview = async () => {
    const { ReviewEditor } = await import('./ReviewEditor');
    setShowReview(() => ReviewEditor);
  };

  return (
    <>
      <button onClick={handleWriteReview}>Write Review</button>
      {ShowReview && <ShowReview />}
    </>
  );
}

// Visibility-based with IntersectionObserver
function useInView(options) {
  const [inView, setInView] = useState(false);
  const ref = useRef();

  useEffect(() => {
    const observer = new IntersectionObserver(
      ([entry]) => { if (entry.isIntersecting) { setInView(true); observer.disconnect(); } },
      { rootMargin: '200px', ...options }  // Start loading 200px before visible
    );
    if (ref.current) observer.observe(ref.current);
    return () => observer.disconnect();
  }, []);

  return [ref, inView];
}

const LazyChart = lazy(() => import('./Chart'));

function AnalyticsDashboard() {
  const [ref, inView] = useInView();
  return (
    <div ref={ref} style={{ minHeight: 400 }}>
      {inView && (
        <Suspense fallback={<ChartSkeleton />}>
          <LazyChart />
        </Suspense>
      )}
    </div>
  );
}

Image Lazy Loading

// Native lazy loading (Chrome, Firefox, Safari 15.4+)
<img src="photo.webp" loading="lazy" width="800" height="600" alt="Photo">

// How it works internally:
// Chrome uses IntersectionObserver with threshold based on:
// - Connection speed (3G: loads ~3000px below viewport)
// - Effective connection type (4G: loads ~1250px below viewport)
// - Data saver mode
//
// IMPORTANT: Never lazy load the LCP image!
// LCP image should have: loading="eager" (default) + fetchpriority="high"
// Only lazy load below-the-fold images

// <iframe> lazy loading
<iframe src="https://youtube.com/embed/123" loading="lazy"></iframe>

// Custom IntersectionObserver for more control:
const observer = new IntersectionObserver((entries) => {
  entries.forEach(entry => {
    if (entry.isIntersecting) {
      const img = entry.target;
      img.src = img.dataset.src;  // Swap data-src → src
      img.removeAttribute('data-src');
      observer.unobserve(img);
    }
  });
}, { rootMargin: '200px 0px' });

document.querySelectorAll('img[data-src]').forEach(img => observer.observe(img));

Next.js Image Optimization

import Image from 'next/image';

// Above the fold — eager load, high priority
<Image src="/hero.jpg" priority width={1200} height={600} alt="Hero" />

// Below the fold — lazy loaded automatically
<Image src="/product.jpg" width={400} height={400} alt="Product" />

// Next.js Image does:
// ✓ Automatic WebP/AVIF conversion
// ✓ Responsive srcset generation
// ✓ Lazy loading by default (loading="lazy")
// ✓ Blur placeholder (prevents CLS)
// ✓ priority prop → adds preload + fetchpriority="high"
// ✓ On-demand optimization (server resizes on request, caches)

FAANG Interview Questions

Q1: How does React.lazy work internally? What happens when the component loads?
React.lazy wraps a dynamic import() call and creates a special component type. When React tries to render it for the first time, the lazy component throws a Promise (the import() promise). The nearest Suspense boundary catches this thrown Promise, renders its fallback prop, and subscribes to the Promise. When the import resolves, React re-renders the subtree with the loaded component — the Suspense boundary unmounts the fallback and renders the actual component. If the import rejects (network error, 404), the error propagates to the nearest ErrorBoundary. Important: React.lazy only works with default exports. For named exports, create an intermediate module that re-exports as default. Also, the lazily loaded module is cached after first load — subsequent renders don't trigger another import.
Follow-up: How does Suspense for data fetching differ from Suspense for lazy components?
Q2: When should you NOT lazy load something?
Several critical cases: (1) The LCP element — never lazy load the hero image or the component that renders it. Lazy loading delays discovery and download, directly increasing LCP. Use priority/fetchpriority="high" instead. (2) Above-the-fold components — anything visible on initial render should be in the main bundle. Lazy loading it adds a round-trip delay before content appears. (3) Very small components (under 5KB) — the overhead of a separate HTTP request exceeds the savings from splitting. (4) Components needed for interaction (e.g., event handlers) — if a user can interact with something immediately, the handler code must be loaded. (5) Critical path dependencies — auth guards, layout wrappers, error boundaries should be in the main bundle. Rule: lazy load what's below the fold, behind user interaction, or on different routes.
Follow-up: How would you handle a slow network where lazy-loaded chunks take 5+ seconds?

Lazy Loading Decision Tree

Is it above the fold?
├── Yes → DON'T lazy load. Include in main bundle.
│         Is it the LCP element?
│         └── Yes → Add fetchpriority="high" + preload
└── No → Is it > 10KB?
    ├── Yes → LAZY LOAD
    │   ├── Route-level: React.lazy + Suspense
    │   ├── Interaction-based: Load on click/hover
    │   └── Visibility-based: IntersectionObserver
    └── No → Probably not worth splitting (HTTP overhead)

Production Checklist

✅ Route-level lazy loading for all non-initial routes
✅ Heavy components lazy loaded (charts, editors, modals)
✅ Suspense boundaries with meaningful skeleton fallbacks
✅ ErrorBoundary wrapping all Suspense boundaries
✅ LCP image: loading="eager" + fetchpriority="high" + preload
✅ Below-fold images: loading="lazy" + width/height set
✅ Prefetch likely-next routes on hover
✅ IntersectionObserver for viewport-triggered loading
✅ Skeleton dimensions match final content (prevent CLS)
✅ Network error handling with retry mechanism
