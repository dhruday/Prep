2. When to Use Each

// Use SYNTHETIC when:
// ✓ Catching regressions in CI/CD (before deploy)
// ✓ Debugging specific performance issues (reproducible trace)
// ✓ Benchmarking against competitors
// ✓ Testing pages with no traffic yet (staging)
// ✓ Establishing baselines for new features
//
// Use RUM when:
// ✓ Understanding actual user experience
// ✓ Segmenting by device, geography, connection
// ✓ Measuring INP (requires real interactions)
// ✓ Tracking business impact (correlate metrics with conversion)
// ✓ Monitoring CWV for Google ranking (CrUX data)
// ✓ Detecting issues on specific devices/browsers
//
// Use BOTH when:
// ✓ You're serious about performance (all FAANG companies do)
// ✓ Synthetic catches regressions pre-deploy
// ✓ RUM validates that fixes actually improved user experience
// ✓ Discrepancies between lab/field reveal real-world factors
//   (third-party scripts, browser extensions, slow devices)

3. CrUX — Chrome UX Report

// CrUX is Google's RUM dataset — aggregated from Chrome users who opted in
//
// How data flows:
// Chrome browser → anonymous performance data → Google servers
// → Aggregated over 28-day rolling window
// → Published monthly in BigQuery + API
//
// Available at two levels:
// 1. Origin level: https://example.com (entire site)
// 2. URL level: https://example.com/products (specific page)
//    URL-level only available if page has enough traffic
//
// Metrics in CrUX:
// LCP, INP, CLS, FCP, TTFB
// + navigation types, form factors, effective connection types
//
// Tools powered by CrUX:
// - PageSpeed Insights (field data section)
// - Search Console (Core Web Vitals report)
// - CrUX Dashboard (Data Studio template)
// - BigQuery (raw SQL queries)
// - CrUX API (programmatic access)

RUM Implementation with web-vitals

// Production RUM setup — collect from all users, sample 10%
import { onLCP, onINP, onCLS, onFCP, onTTFB } from 'web-vitals/attribution';

// Sampling — don't overwhelm analytics endpoint
const SAMPLE_RATE = 0.1; // 10% of users
const shouldSample = Math.random() < SAMPLE_RATE;

if (shouldSample) {
  const queue = [];

  function addToQueue(metric) {
    queue.push({
      name: metric.name,
      value: metric.value,
      rating: metric.rating,
      delta: metric.delta,
      id: metric.id,
      attribution: getAttribution(metric),
      page: location.pathname,
      deviceType: getDeviceType(),
      connection: navigator.connection?.effectiveType ?? 'unknown',
      country: getCountryFromCDN(), // Cloudflare/Fastly header
      timestamp: Date.now(),
      sessionId: getSessionId(),
      deployVersion: __DEPLOY_VERSION__,
    });
  }

  function getAttribution(metric) {
    switch (metric.name) {
      case 'LCP':
        return {
          element: metric.attribution.element,
          url: metric.attribution.url,
          ttfb: metric.attribution.timeToFirstByte,
          loadDelay: metric.attribution.resourceLoadDelay,
          loadTime: metric.attribution.resourceLoadTime,
          renderDelay: metric.attribution.elementRenderDelay,
        };
      case 'INP':
        return {
          eventTarget: metric.attribution.eventTarget,
          eventType: metric.attribution.eventType,
          inputDelay: metric.attribution.inputDelay,
          processingDuration: metric.attribution.processingDuration,
          presentationDelay: metric.attribution.presentationDelay,
        };
      case 'CLS':
        return {
          largestShiftTarget: metric.attribution.largestShiftTarget,
          largestShiftValue: metric.attribution.largestShiftValue,
        };
      default: return {};
    }
  }

  onLCP(addToQueue);
  onINP(addToQueue);
  onCLS(addToQueue);
  onFCP(addToQueue);
  onTTFB(addToQueue);

  // Flush on page hide (user navigates away)
  document.addEventListener('visibilitychange', () => {
    if (document.visibilityState === 'hidden' && queue.length) {
      navigator.sendBeacon('/api/rum', JSON.stringify(queue));
      queue.length = 0;
    }
  });
}

// Lighthouse programmatic API
const lighthouse = require('lighthouse');
const chromeLauncher = require('chrome-launcher');

async function runLighthouse(url) {
  const chrome = await chromeLauncher.launch({ chromeFlags: ['--headless'] });
  const result = await lighthouse(url, {
    port: chrome.port,
    output: 'json',
    onlyCategories: ['performance'],
  });
  await chrome.kill();
  return result.lhr;
}

FAANG Interview Questions

Q1: Explain the difference between RUM and Synthetic monitoring. When would you use each?
Synthetic monitoring runs automated tests in controlled environments — fixed device, network, and location. It's reproducible and great for CI/CD regression detection, debugging, and benchmarking. RUM (Real User Monitoring) collects performance data from actual user sessions in production — real devices, real networks, real-world conditions. It captures what users actually experience, including INP (which requires real interactions). Key insight: Lighthouse (synthetic) doesn't affect Google ranking — only CrUX (field/RUM data) does. I use both: synthetic in CI to catch regressions before deploy, and RUM in production to validate that fixes improved real user experience. Common trap: a page scores 98 on Lighthouse but fails CWV because real users on budget Android phones with 3G have a completely different experience than Lighthouse's simulated mobile profile.
Follow-up: How do you handle the data volume of RUM at 100M monthly users?
Q2: How does CrUX work and why does Google use 75th percentile?
CrUX (Chrome UX Report) collects anonymous performance data from Chrome users who've opted into usage statistics sharing. Data is aggregated over a 28-day rolling window and published at origin-level and URL-level. Google uses the 75th percentile because it balances capturing the majority experience without being skewed by extreme outliers. If your p75 LCP is 2.4s, that means 75% of your users see LCP under 2.4s. The remaining 25% might be on very slow networks — acceptable. But if p75 is 4s, a significant chunk of users (25-50%) have a poor experience. Google chose 75th over median (p50) because the median can hide a bimodal distribution — half the users might be fine, but the other half terrible. The p75 catches this.
Follow-up: Can you access CrUX data programmatically? How would you use it?
