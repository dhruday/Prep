1. What Is Lighthouse CI?

// Lighthouse CI (LHCI) runs Lighthouse audits in your CI/CD pipeline
// It catches performance regressions BEFORE they reach production
//
// Architecture:
// ┌──────────┐     ┌──────────────┐     ┌──────────────┐
// │ PR Push  │ ──▶ │ CI Pipeline  │ ──▶ │ LHCI Server  │
// │ (GitHub) │     │ (Run Lighthouse)│   │ (Store/Compare)│
// └──────────┘     └──────────────┘     └──────────────┘
//                        │
//                  ┌─────┴─────┐
//                  │  Pass/Fail │ ──▶ GitHub Status Check
//                  └───────────┘
//
// Three components:
// 1. @lhci/cli — CLI that collects Lighthouse runs
// 2. LHCI Server — stores results, compares against baselines
// 3. GitHub App — posts status checks on PRs
//
// Key concept: Run Lighthouse 3-5 times per URL (reduce variance)
// LHCI uses median of runs for assertions

2. Performance Budgets — Theory

// A performance budget is a set of limits on metrics that should not be exceeded
//
// Types of budgets:
// 1. Quantity-based: max bundle size, max number of requests, max image weight
// 2. Milestone-based: max LCP, max FCP, max TTI
// 3. Rule-based: min Lighthouse score, no violations of specific audits
//
// Why budgets work at FAANG scale:
// - Without budgets, performance degrades incrementally ("boiling frog")
// - Each developer adds "just 10KB" → death by a thousand cuts
// - Budgets make the invisible visible — CI fails when limits exceeded
// - Creates a culture of performance ownership
//
// Google's budget philosophy:
// - Start with competitor analysis (what's the p75 LCP of top 5 competitors?)
// - Set budget 20% better than the best competitor
// - Assign "budget owners" for each page/feature team
// - Budget violations block merges (hard gate, not advisory)

3. Lighthouse Internals

// Lighthouse internally does:
// 1. Launches headless Chrome (via chrome-launcher)
// 2. Connects via Chrome DevTools Protocol (CDP)
// 3. Navigates to URL
// 4. Collects artifacts:
//    - Network requests (HAR-like)
//    - DOM snapshot
//    - Trace (Chrome Trace format)
//    - Console messages, JS coverage
// 5. Runs audits against artifacts (200+ audits)
// 6. Scores each category (Performance, A11y, Best Practices, SEO, PWA)
//
// Performance score calculation:
// Weighted average of 6 metrics:
// FCP:          10%
// Speed Index:  10%
// LCP:          25%
// TBT:          30%  (lab proxy for INP)
// CLS:          25%
//
// Each metric score is mapped via a log-normal distribution
// (not linear — diminishing returns at extremes)

Lighthouse CI Setup — GitHub Actions

# .github/workflows/lighthouse.yml
name: Lighthouse CI
on: [pull_request]

jobs:
  lighthouse:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Install & Build
        run: |
          npm ci
          npm run build

      - name: Start server
        run: npm run start &

      - name: Run Lighthouse CI
        run: |
          npm install -g @lhci/cli
          lhci autorun
        env:
          LHCI_GITHUB_APP_TOKEN: ${{ secrets.LHCI_GITHUB_APP_TOKEN }}

lighthouserc.js — Configuration

// lighthouserc.js
module.exports = {
  ci: {
    collect: {
      url: [
        'http://localhost:3000/',
        'http://localhost:3000/products',
        'http://localhost:3000/checkout',
      ],
      numberOfRuns: 5,  // Reduce variance
      settings: {
        preset: 'desktop',  // or 'mobile' (4x CPU throttle, slow 4G)
        chromeFlags: '--no-sandbox',
      },
    },
    assert: {
      assertions: {
        // Metric-based budgets
        'first-contentful-paint': ['error', { maxNumericValue: 2000 }],
        'largest-contentful-paint': ['error', { maxNumericValue: 2500 }],
        'cumulative-layout-shift': ['error', { maxNumericValue: 0.1 }],
        'total-blocking-time': ['error', { maxNumericValue: 300 }],

        // Score-based budgets
        'categories:performance': ['error', { minScore: 0.9 }],
        'categories:accessibility': ['error', { minScore: 0.95 }],

        // Resource budgets
        'resource-summary:script:size': ['error', { maxNumericValue: 300000 }],
        'resource-summary:total:size': ['error', { maxNumericValue: 500000 }],

        // Specific audit checks
        'uses-responsive-images': 'error',
        'render-blocking-resources': 'warn',
        'unused-javascript': 'warn',
      },
    },
    upload: {
      target: 'lhci',
      serverBaseUrl: 'https://lhci.mycompany.com',
      // Or use temporary public storage:
      // target: 'temporary-public-storage',
    },
  },
};

Bundle Size Budget — webpack

// webpack.config.js — Built-in performance hints
module.exports = {
  performance: {
    maxAssetSize: 250000,      // 250KB per asset
    maxEntrypointSize: 300000, // 300KB per entrypoint
    hints: 'error',             // 'warning' | 'error' | false
  },
};

// bundlesize (npm package) — more granular
// package.json
{
  "bundlesize": [
    { "path": "dist/main.*.js", "maxSize": "150 kB" },
    { "path": "dist/vendor.*.js", "maxSize": "100 kB" },
    { "path": "dist/*.css", "maxSize": "30 kB" }
  ]
}

// size-limit (more accurate — accounts for gzip + parse time)
// .size-limit.json
[
  { "path": "dist/main.js", "limit": "50 kB", "gzip": true },
  { "path": "dist/main.js", "limit": "100 ms", "running": true }
]

FAANG Interview Questions

Q1: How would you implement performance budgets in a CI/CD pipeline?
I'd use a two-layer approach. Layer 1: Bundle size budgets using size-limit or bundlesize in the build step — these are fast (no browser needed) and catch JavaScript/CSS growth immediately. Each PR shows a size diff. Layer 2: Lighthouse CI running against a staging deployment — this catches metric regressions (LCP, CLS, TBT) that bundle size alone can't detect (e.g., render-blocking CSS order change). Configuration: 5 Lighthouse runs per URL (median reduces variance), assertions for LCP < 2.5s, CLS < 0.1, TBT < 300ms as hard errors that block merge. Results upload to LHCI Server for trend analysis. GitHub status check shows pass/fail with a link to the detailed report. For a mature team: add custom Lighthouse audits — for example, check that hero images have fetchpriority="high", or that no third-party script exceeds 50KB.
Follow-up: How do you handle Lighthouse score variance in CI?
Q2: Lighthouse gives your page a 65 performance score. Walk through your optimization process.
Step 1: Look at the "Metrics" section — identify which metrics are red. Usually LCP or TBT. Step 2: Check "Opportunities" — Lighthouse prioritizes fixes by estimated savings. Common findings: unused JavaScript (code splitting needed), unoptimized images (modern formats, responsive), render-blocking resources (defer/async). Step 3: Check "Diagnostics" — DOM size, main thread work breakdown, critical request chains. Step 4: Use the Treemap view to visualize bundle composition — often one large dependency (moment.js, lodash) dominates. Step 5: Implement fixes in priority order: largest-impact-first. Typically: add image optimization (5-15 points), implement code splitting (5-10 points), inline critical CSS (3-5 points), defer third-party scripts (3-8 points). Step 6: Re-run Lighthouse after each change to verify improvement. Target: 90+ score, which typically means CWV are all "good."
Follow-up: Why might a page score 95 on Lighthouse but still have poor CrUX data?

Complete Lighthouse CI Configuration

// Advanced lighthouserc.js with custom budgets per URL
module.exports = {
  ci: {
    collect: {
      url: [
        'http://localhost:3000/',
        'http://localhost:3000/search?q=shoes',
        'http://localhost:3000/product/123',
      ],
      numberOfRuns: 5,
      settings: {
        // Simulate real mobile conditions
        formFactor: 'mobile',
        throttling: {
          rttMs: 150,           // Round-trip time
          throughputKbps: 1638,   // ~1.6 Mbps (slow 4G)
          cpuSlowdownMultiplier: 4, // 4x CPU throttle
        },
        screenEmulation: {
          mobile: true,
          width: 412,
          height: 823,
          deviceScaleFactor: 1.75,
        },
      },
    },
    assert: {
      assertMatrix: [
        {
          matchingUrlPattern: '.*/$',  // Homepage — strictest
          assertions: {
            'largest-contentful-paint': ['error', { maxNumericValue: 2000 }],
            'cumulative-layout-shift': ['error', { maxNumericValue: 0.05 }],
            'categories:performance': ['error', { minScore: 0.92 }],
          },
        },
        {
          matchingUrlPattern: '.*/product/.*',  // Product pages — images heavy
          assertions: {
            'largest-contentful-paint': ['error', { maxNumericValue: 2500 }],
            'uses-responsive-images': 'error',
            'categories:performance': ['error', { minScore: 0.85 }],
          },
        },
      ],
    },
  },
};

Production Checklist

✅ Lighthouse CI runs on every PR with 5 runs per URL
✅ Hard gates: LCP < 2.5s, CLS < 0.1, TBT < 300ms
✅ Bundle size limits per chunk (size-limit in CI)
✅ LHCI Server stores historical data for trend analysis
✅ GitHub status check blocks merge on budget violation
✅ Per-page budgets (homepage stricter than deep pages)
✅ Mobile throttling enabled (4x CPU, slow 4G)
✅ Custom audits for project-specific rules
✅ Weekly review of LHCI trends dashboard
✅ Budget owners assigned per feature team
