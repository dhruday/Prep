Short Polling — ask repeatedly on a fixed interval

Short polling sends a request every N seconds regardless of whether the server has new data. Simple to implement over plain HTTP. Used when real-time is not critical. Generates a lot of unnecessary traffic. At SAP, simple dashboard refresh (every 30s) works fine with short polling.

→ GET /status← 304 (no change)→ GET /status← 304 (no change)→ GET /status← 200 new data!

Wasted requests while data unchanged

Long Polling — hold the connection open until data is ready

Long polling sends a request. The server holds the connection open (without responding) until it has new data or a timeout occurs. When data arrives, the server responds, and the client immediately sends a new request. Zero wasted requests — every response contains real data. More complex to implement. Used in SAP Intelligent RPA for job status notifications.

→ GET /status… server holds 28s …← 200 new data!→ GET /status immediately

Every response carries useful data

Short polling + long polling implementations

// ─── Short polling ───
function startShortPoll(interval = 5000) {
  return setInterval(async () => {
    const res = await fetch('/api/job-status');
    const data = await res.json();
    if (data.status === 'done') clearInterval(timerId);
    updateUI(data);
  }, interval);
}

// ─── Long polling (recursive) ───
async function longPoll(signal: AbortSignal) {
  while (!signal.aborted) {
    try {
      const res = await fetch('/api/events?timeout=30', { signal });
      const data = await res.json();
      processEvent(data);
      // immediately re-request
    } catch (e) {
      if (signal.aborted) break;
      await sleep(1000); // backoff on error
    }
  }
}
