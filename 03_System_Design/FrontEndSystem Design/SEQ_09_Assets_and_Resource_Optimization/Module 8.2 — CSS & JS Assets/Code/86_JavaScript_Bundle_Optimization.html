JS bundle size — the biggest parse/execute bottleneck

Unlike images (decoded once), JavaScript must be downloaded, parsed, compiled, and executed on every page load. 1 MB of JS ≈ 8 s parse + execute on a low-end mobile device. At SAP, a legacy jQuery + Angular hybrid app had a 2.8 MB initial bundle — code splitting + deferred Angular routes cut it to 280 KB initial.

Bundle bloat sources
  • 🔁 Duplicate dependencies (lodash × 3 versions)
  • 📦 Importing whole library (import _ from 'lodash')
  • ⚡ No code splitting (all routes in one chunk)
  • 🔧 Dev dependencies leaked to production
  • 🌐 Polyfills for browsers you don't support
Optimisation levers
  • ✂️ Code splitting (route + component level)
  • 🌳 Tree shaking (ESM + sideEffects: false)
  • 🔎 Bundle analysis (webpack-bundle-analyzer)
  • 🏷️ Module federation (share chunks across MFEs)
  • 📊 Import cost VSCode extension

Bundle optimization config patterns

// ─── webpack splitChunks config ───
module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'all',
      cacheGroups: {
        vendor: {
          test: /node_modules/,
          name: (module) => {
            const pkg = module.context.match(/node_modules\/(.*?)(?:\/|$)/)[1];
            return `vendor.${pkg}`;  // per-package chunk for better caching
          },
        },
      },
    },
  },
};

// ─── Vite manual chunks ───
build({
  rollupOptions: {
    output: {
      manualChunks: {
        react: ['react', 'react-dom'],
        router: ['react-router-dom'],
        charts: ['recharts'],
      },
    },
  },
});

// ─── Angular lazy route (deferred chunk) ───
const routes: Routes = [
  {
    path: 'orders',
    loadChildren: () => import('./orders/orders.module')
      .then(m => m.OrdersModule)
  }
];

// ─── Named import (tree-shakeable) ───
import { debounce } from 'lodash-es'; // 2KB
// NOT: import _ from 'lodash';        // 72KB
