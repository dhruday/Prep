Error Taxonomy

Transient — temporary failures (500, 503, 429, network). Safe to retry.
Permanent — client bugs or missing resources (400, 401, 404). Retrying won't help.

Key rule: retry transient errors with backoff; surface permanent errors to the user immediately.

Classification Table

Status │ Type       │ Retryable │ Why
───────┼────────────┼───────────┼──────────────────────
400    │ Permanent  │ No        │ Bad request / invalid payload
404    │ Permanent  │ No        │ Resource does not exist
429    │ Transient  │ Yes       │ Rate-limited, wait & retry
500    │ Transient  │ Yes       │ Server crash, may recover
Network│ Transient  │ Yes       │ Connectivity issue
Timeout│ Transient  │ Yes       │ Server too slow

How the Browser Surfaces Errors

• HTTP errors (4xx/5xx) still resolve the fetch() promise — check response.ok.
• Network failures (DNS, no connection) reject the promise with a TypeError.
• AbortController timeouts reject with AbortError (DOMException).

Chrome DevTools → Network tab shows failed requests in red. Status 0 = CORS or network failure.

Fetch Error Flow

try {
  const res = await fetch(url, { signal });
  if (!res.ok) // HTTP error — promise resolved
    classify(res.status);
} catch (e) {
  if (e.name === 'AbortError') // timeout
  else // network failure
}

Q: Which HTTP errors should be retried automatically?

Transient server-side errors (500, 502, 503, 504) and 429 (rate-limited) are retryable. Client errors (400, 401, 403, 404) are permanent — retrying won't fix bad input or missing auth.

Q: How do you distinguish a network error from a server error in fetch?

Network errors reject the fetch promise (TypeError). Server errors resolve the promise with response.ok === false. You must check both paths.

Q: Why is 429 special among 4xx errors?

Unlike other 4xx codes, 429 is transient — the request is valid but rate-limited. Clients should read the Retry-After header and wait before retrying.
