Idempotency Keys

A client-generated UUID sent with a POST. The server stores {key → response}. On retry with the same key, the server replays the cached response without re-executing.

Stripe, PayPal, and AWS all use idempotency keys for safe payment retries.

Protocol Flow

── Request 1 (new key) ──
POST /orders  X-Idempotency-Key: abc-123
→ 201 Created  { id: 42 }

── Request 2 (same key) ──
POST /orders  X-Idempotency-Key: abc-123
→ 200 OK  { id: 42 }  X-Idempotent-Replay: true

Send & Retry POST

Click Send New to POST with a fresh key. Then Retry Same Key to replay. Watch for the X-Idempotent-Replay header.

Implementation Internals

• Key generation: crypto.randomUUID() — supported in all modern browsers.
• Server hashes the key and stores the response for a TTL (e.g. 24 h).
• If the key collides with a different payload, the server must return 422 Unprocessable Entity.

Why UUID v4?

122 bits of entropy → collision probability < 10⁻¹⁸ for billions of keys. No coordination needed between clients.

Q: Why can't you just use a request ID for idempotency?

Request IDs are server-generated for tracing, not dedup. Idempotency keys are client-generated before the request so the same key can be sent on retry.

Q: What happens if the first request times out?

The client doesn't know if the server executed. Retry with the same idempotency key — if processed, the server returns the cached result; if not, it processes normally.

Q: How long should idempotency keys be stored?

Typically 24–48 hours. Short enough to bound storage, long enough to cover all reasonable retry windows.
