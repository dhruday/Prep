Key Takeaways

Why Cross-Tab Dedup?

Promise maps and React Query only work within a single page. If a user opens your app in two browser tabs, each tab independently fetches the same data. A Service Worker sits between all tabs and the network — it can intercept identical requests and serve a single cached response.

Architecture

Browser Tab A ──┐                         ┌── Network
Browser Tab B ──┼── Service Worker (SW) ──┤
Browser Tab C ──┘   ├ inflight map        └── (1 request)
                    ├ Cache API
                    └ respondWith()
The SW's fetch event fires for every network request from every controlled tab.

Dedup Flow

1. Tab A requests /api/rest/products → SW sees no inflight → starts fetch, stores promise
2. Tab B requests /api/rest/products → SW finds inflight promise → clones & returns
3. Network response arrives → both tabs receive data → SW caches response → clears inflight entry

sw-dedup.js (Service Worker)

const inflight = new Map();

self.addEventListener('fetch', (event) => {
  const url = event.request.url;

  // Only dedup GET API requests
  if (event.request.method !== 'GET') return;
  if (!url.includes('/api/')) return;

  if (inflight.has(url)) {
    // Clone the inflight response for this tab
    event.respondWith(
      inflight.get(url).then(r => r.clone())
    );
    return;
  }

  const promise = fetch(event.request)
    .then(response => {
      // Cache for future tabs/navigations
      const cache = await caches.open('api-v1');
      cache.put(url, response.clone());
      return response;
    })
    .finally(() => inflight.delete(url));

  inflight.set(url, promise);
  event.respondWith(promise.then(r => r.clone()));
});

Registration (main page)

if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw-dedup.js');
}

Benefits

• True cross-tab dedup — no shared state needed in app code
• Works with any framework or vanilla JS
• Can combine with Cache API for offline + dedup
• Transparent to the application layer

Challenges

• Response cloning — each respondWith needs a separate clone (readable stream consumed once)
• SW lifecycle — install/activate/update adds complexity
• POST/PUT dedup — risky; only safe for idempotent reads
• Cache invalidation — stale SW cache can serve outdated data

Scope Comparison

Layer              │ Dedup Scope    │ Persistence
───────────────────┼────────────────┼──────────────
Promise Map        │ Single page    │ RAM only
React Query        │ Single page    │ RAM (gc'd)
Service Worker     │ All tabs       │ Cache API
HTTP Cache (disk)  │ All tabs       │ Disk
