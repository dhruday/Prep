Per-Endpoint Strategy

Not all endpoints have the same cost. Search APIs are expensive (DB full-text) while data reads are cheap. Assign separate buckets per route.
  • /api/search — 5 tokens, refills 1 token every 2 seconds (strict)
  • /api/data — 30 tokens, refills 1 token every 2 seconds (relaxed)
  • Each endpoint has its own independent token bucket
  • Exhausting one bucket doesn't affect the other

Implementation

const endpointConfigs = {
  '/api/search': { capacity: 5,  refillMs: 2000 },
  '/api/data':   { capacity: 30, refillMs: 2000 },
};

class EndpointBucket {
  constructor({ capacity, refillMs }) {
    this.cap = capacity;
    this.tokens = capacity;
    this.interval = setInterval(
      () => this.refill(), refillMs);
  }
  refill() {
    this.tokens = Math.min(this.cap,
      this.tokens + 1);
  }
  tryConsume() {
    if (this.tokens >= 1) {
      this.tokens--; return true;
    }
    return false;
  }
}

// Create a bucket map
const buckets = {};
for (const [ep, cfg] of Object.entries(endpointConfigs)) {
  buckets[ep] = new EndpointBucket(cfg);
}

Key Takeaways

Granular rate limits protect expensive endpoints without penalizing cheap ones.
  • Costly endpoints (search, write) get stricter limits
  • Read-heavy endpoints can be more generous
  • Buckets are independent — no cross-contamination
  • Config-driven: easy to tune without code changes
  • Pattern used by GitHub API, Shopify, Cloudflare
