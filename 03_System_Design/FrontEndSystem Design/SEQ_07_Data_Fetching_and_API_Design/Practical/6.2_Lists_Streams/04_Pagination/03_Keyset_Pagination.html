Multi-Column Keyset Pagination

When results are sorted by a non-unique column (e.g., price), you need a composite key (price, id) to guarantee uniqueness.

-- Simple cursor (single column, unique):
WHERE id > 1050 ORDER BY id LIMIT 10

-- Keyset (multi-column, sorted by price):
WHERE (price, id) > (29.99, 1050)
ORDER BY price, id
LIMIT 10

-- Equivalent expanded form (SQL standard):
WHERE price > 29.99
   OR (price = 29.99 AND id > 1050)
ORDER BY price ASC, id ASC
LIMIT 10

Why a Composite Key?

-- Problem: multiple items share the same price
price │ id
──────┼─────
 9.99 │ 101
 9.99 │ 204   ← same price! WHERE price > 9.99 skips #204
 9.99 │ 317
14.99 │ 102

-- Solution: (price, id) guarantees unique ordering
-- "Give me items AFTER (9.99, 204)" → starts at (9.99, 317)
The tie-breaker column (usually id) must be unique to prevent skipping rows.

Compound Index for Keyset Queries

-- Create a compound index matching the sort order:
CREATE INDEX idx_items_price_id
ON items (price ASC, id ASC);

-- The keyset query uses this index directly:
EXPLAIN ANALYZE
SELECT * FROM items
WHERE (price, id) > (29.99, 1050)
ORDER BY price, id LIMIT 10;

-- → Index Scan using idx_items_price_id
--   Index Cond: ROW(price, id) > ROW(29.99, 1050)
--   Rows: 10
--   Time: 0.06ms

Index Structure Visualization

Compound B-Tree: (price, id)

         [(19.99, 500)]
        /              \
 [(9.99, 101)]    [(29.99, 300)]
   /      \          /       \
[9.99,101] [9.99,317] [29.99,300] [49.99,150]
[9.99,204] [14.99,102] [29.99,1050] [49.99,420]

Seek to (29.99, 1050): navigate tree → O(log N)
Then scan forward 10 leaves → O(limit)
Total: O(log N + limit) ≈ O(1)
The compound index order must match the ORDER BY clause exactly.

Keyset Limitations

  • No jump to page N — you can only go forward/backward from current position
  • Sort order is fixed — changing sort requires a different keyset/index
  • Complex WHERE expansion — 3+ columns become verbose SQL
  • Descending sort — requires (price, id) < (X, Y) and reversed index

Multi-Column Complexity

-- 2 columns: manageable
WHERE price > X OR (price = X AND id > Y)

-- 3 columns: getting verbose
WHERE category > A
   OR (category = A AND price > X)
   OR (category = A AND price = X AND id > Y)

-- 4+ columns: use ROW() syntax or framework support
WHERE ROW(cat, price, date, id) > ROW(A, X, D, Y)

Interview Key Points

✅ O(1) seek with compound index — perfect for sorted feeds
✅ No ghost records — stable position across inserts/deletes
❌ Cannot show "Page 5 of 20" — no total count or page jump
❌ Each sort order needs its own compound index
🎯 FAANG: "Paginate e-commerce search sorted by price" → Keyset (price, id)
