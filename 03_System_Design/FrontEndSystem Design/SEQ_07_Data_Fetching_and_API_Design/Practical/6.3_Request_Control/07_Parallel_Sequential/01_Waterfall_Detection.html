What Is a Request Waterfall?

A waterfall occurs when requests are chained sequentially — each waits for the previous one to finish before starting. This is the #1 performance anti-pattern in data fetching.

Total time = sum of all request durations (sequential) vs max of all durations (parallel).

Sequential (Waterfall)

// Each await blocks the next request
const products   = await fetch('/api/rest/products');
const categories = await fetch('/api/rest/categories');
const posts      = await fetch('/api/posts');
const dashboard  = await fetch('/api/dashboard');

Parallel (Promise.all)

// All requests fire simultaneously
const [products, categories, posts, dashboard] = await Promise.all([
  fetch('/api/rest/products'),
  fetch('/api/rest/categories'),
  fetch('/api/posts'),
  fetch('/api/dashboard'),
]);

Network Waterfall in DevTools

Open DevTools → Network tab. Sequential requests appear as stair-step bars; parallel requests start at the same vertical line.

Chrome DevTools colors: blue = DNS, orange = connecting, green = TTFB, blue bar = content download.

How the Browser Executes Fetch

1. fetch() creates a network task on the network thread.
2. DNS resolution → TCP handshake → TLS negotiation (connection reuse skips these).
3. HTTP request sent → server processes → response streams back.
4. The promise resolves on the microtask queue of the main thread.

Why Sequential Is Slow

Each await pauses the async function. The next fetch() call only enters the network thread after the previous promise resolves and the microtask runs. The network sits idle between requests.

With 4 requests each taking 200ms: sequential = ~800ms, parallel = ~200ms. That's a 4× difference.

Q: What is a request waterfall and why is it bad?

A: A waterfall is when network requests are chained sequentially — each starts only after the previous completes. It multiplies latency because total time equals the sum of all request times instead of the maximum. Fix: use Promise.all for independent requests.

Q: How do you detect waterfalls?

A: 1) DevTools Network tab — look for stair-step pattern. 2) Performance tab timeline. 3) Lighthouse "Avoid chaining critical requests" audit. 4) Code review: consecutive awaits on independent fetches.

Q: When is sequential fetching actually correct?

A: When requests have true data dependencies — e.g., fetch user ID first, then fetch that user's posts. If request B needs data from response A, they must be sequential. The goal is to parallelize independent requests.

Q: How does React Suspense / RSC help with waterfalls?

A: React Server Components can fetch data on the server in parallel before streaming HTML. Suspense boundaries let independent subtrees fetch concurrently without waterfall chains created by parent→child render dependencies.
