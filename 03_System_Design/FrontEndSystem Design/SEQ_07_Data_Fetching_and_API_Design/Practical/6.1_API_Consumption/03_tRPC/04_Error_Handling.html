TRPCError — Built-in Error Codes

import { TRPCError } from '@trpc/server';

// tRPC maps its codes to HTTP status codes automatically
throw new TRPCError({
  code: 'NOT_FOUND',          // → HTTP 404
  message: 'User not found',
  cause: originalError,       // optional — wraps the original error
});

// Available codes:
'BAD_REQUEST'       // 400 — invalid input
'UNAUTHORIZED'      // 401 — not logged in
'FORBIDDEN'         // 403 — insufficient permissions
'NOT_FOUND'         // 404 — resource doesn't exist
'CONFLICT'          // 409 — duplicate resource
'TOO_MANY_REQUESTS' // 429 — rate limited
'INTERNAL_SERVER_ERROR' // 500 — unexpected failure

Server-Side Error Throwing

const appRouter = t.router({
  getUser: t.procedure
    .input(z.object({ id: z.string().uuid() }))
    .query(async ({ input, ctx }) => {
      if (!ctx.session) {
        throw new TRPCError({ code: 'UNAUTHORIZED' });
      }

      const user = await db.users.findById(input.id);
      if (!user) {
        throw new TRPCError({
          code: 'NOT_FOUND',
          message: `User ${input.id} not found`,
        });
      }

      if (user.id !== ctx.session.userId && ctx.session.role !== 'admin') {
        throw new TRPCError({ code: 'FORBIDDEN' });
      }

      return user;
    }),
});

Client-Side Error Handling

import { TRPCClientError } from '@trpc/client';

try {
  const user = await trpc.getUser.query({ id });
} catch (err) {
  if (err instanceof TRPCClientError) {
    // Discriminated union on error.data.code
    switch (err.data?.code) {
      case 'NOT_FOUND':    showNotFound(); break;
      case 'UNAUTHORIZED': redirectToLogin(); break;
      case 'FORBIDDEN':    showForbidden(); break;
      case 'BAD_REQUEST':  showValidationErrors(err.data); break;
      default:            showGenericError(); break;
    }
  }
}

Error Formatter — Customizing Error Shape

const t = initTRPC.context<Context>().create({
  errorFormatter({ shape, error }) {
    return {
      ...shape,
      data: {
        ...shape.data,
        // Add Zod validation errors to the response
        zodError: error.cause instanceof ZodError
          ? error.cause.flatten()
          : null,
        // Add request ID for debugging
        requestId: crypto.randomUUID(),
      },
    };
  },
});

Q1: How does tRPC handle errors differently from REST?

A: tRPC provides typed error codes as a discriminated union. Instead of checking HTTP status codes (which vary by API), you check error.data.code — a finite set of string literals like 'NOT_FOUND', 'UNAUTHORIZED'. TypeScript can exhaustively check these in a switch statement. The error formatter lets you attach custom data (Zod errors, request IDs) to every error response.

Q2: How do you handle Zod validation errors on the client?

A: When Zod validation fails in a tRPC procedure, tRPC throws a BAD_REQUEST error with the Zod error as the cause. Use a custom error formatter to include zodError: error.cause.flatten() in the response. On the client, check error.data.code === 'BAD_REQUEST' and read error.data.zodError.fieldErrors to show per-field validation messages in the form.

Q3: What is the error formatter and when should you customize it?

A: The error formatter is a function passed to initTRPC.create() that shapes every error response. Customize it to: (1) Include Zod validation details for form errors. (2) Add request IDs for debugging. (3) Strip stack traces in production. (4) Add i18n error messages. The formatter receives the original error shape and the TRPCError instance, and returns the modified shape.

Q4: Design error codes for a production API

A: Use tRPC's built-in codes for standard cases. For domain-specific errors, use BAD_REQUEST with custom data in the error formatter: { code: 'BAD_REQUEST', domainCode: 'INSUFFICIENT_BALANCE', field: 'amount' }. Keep the error contract explicit — document which procedures can throw which codes. On the client, create a centralized error handler that maps codes to UI states (toast, redirect, inline error).
