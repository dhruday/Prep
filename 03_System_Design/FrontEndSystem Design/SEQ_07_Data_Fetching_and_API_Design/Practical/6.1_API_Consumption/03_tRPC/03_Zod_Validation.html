Zod: Schema = Runtime Validator + TypeScript Type

Define once, get both runtime validation and a TypeScript type via z.infer. No duplication.

Single source of truth: schema validates at runtime AND provides compile-time types.

Defining Schemas

import { z } from 'zod';

const CreateUserSchema = z.object({
  name:     z.string().min(2).max(50),
  email:    z.string().email(),
  age:      z.number().int().min(13).max(120).optional(),
  role:     z.enum(['user', 'admin']).default('user'),
  tags:     z.array(z.string()).max(5).default([]),
  metadata: z.record(z.string()).optional(),
});

// Derive TypeScript type — zero duplication!
type CreateUser = z.infer<typeof CreateUserSchema>;
// = { name: string; email: string; age?: number; role: 'user'|'admin'; ... }

In tRPC — Schema as Input Validator

const appRouter = t.router({
  createUser: t.procedure
    .input(CreateUserSchema)   // runtime validation + type inference
    .mutation(({ input }) => {
      // input is fully typed as CreateUser
      // AND validated at runtime — invalid data never reaches here
      return db.users.create(input);
    }),
});

z.infer Under the Hood

z.infer<typeof schema> is a purely compile-time operation. It recursively walks the Zod schema's TypeScript type to extract the output type. At runtime, z.infer doesn't exist — it's erased during compilation. This means zero runtime cost for type derivation.

Q1: Why use Zod instead of manual validation?

A: Zod provides: (1) Type inference — z.infer derives TypeScript types from the schema, eliminating duplication between runtime checks and compile-time types. (2) Composability — schemas are objects you can extend, merge, pick, and omit. (3) Structured errors — ZodError provides path-aware errors for nested objects. (4) Ecosystem integration — native support in tRPC, React Hook Form, and Astro. Manual validation lacks all of these.

Q2: .parse() vs .safeParse() — when to use which?

A: .parse() throws a ZodError on invalid input — use it when invalid data should halt execution (tRPC input validation, API handlers). .safeParse() returns { success: boolean, data?, error? } — use it for form validation, user input, or when you want to handle errors gracefully without try/catch. In tRPC, .parse() is used internally; the framework catches the error and returns a typed error response.

Q3: How does Zod compare to Joi for TypeScript projects?

A: Zod was designed TypeScript-first. Joi was built for JavaScript (Hapi ecosystem) and added TypeScript types later. Key differences: (1) Zod's z.infer gives perfect type inference; Joi requires manual type definitions. (2) Zod is 13KB vs Joi's 150KB. (3) Zod integrates natively with tRPC; Joi needs an adapter. Choose Zod for modern TS stacks, Joi for existing Express/Hapi codebases.

Q4: Can Zod validate at the boundary only?

A: Yes — and it should. Validate at system boundaries (API input, form submission, external data) and use TypeScript's type system internally. Once data passes Zod validation, you have a typed value. There's no need to re-validate in business logic. This is the "parse, don't validate" principle: transform unknown data into typed data at the boundary, then trust the types throughout.
