Error Classification

Network Error   — TypeError: Failed to fetch (no connectivity, DNS, CORS)
HTTP Error      — 4xx (client fault), 5xx (server fault)
Business Error  — 200 OK but { success: false, errors: [...] }
Timeout Error   — AbortError after signal deadline exceeded

Error Types in the Browser

TypeError        — Network failure, CORS block, invalid URL
AbortError       — AbortController.abort() or AbortSignal.timeout()
DOMException     — Parent class of AbortError
SyntaxError      — response.json() on non-JSON body

Browser Error Event vs Fetch Rejection

The global window.onerror and unhandledrejection events catch uncaught errors. A fetch rejection (TypeError) becomes an unhandled promise rejection if not caught. HTTP errors (4xx/5xx) never trigger these events because fetch resolves normally.

Q: Why does fetch() not reject on 404/500?

By design, fetch() treats the network layer and HTTP layer separately. A 404 means the server responded — the network succeeded. Only true network failures (DNS, connectivity, CORS) cause rejection. This gives developers explicit control over HTTP error handling rather than conflating network and application errors.

Q: How do you distinguish transient vs permanent errors?

Transient (retryable): 5xx (server overload), 429 (rate limit), network errors, timeouts. Permanent (non-retryable): 4xx — 400 bad request, 401 unauthorized, 403 forbidden, 404 not found. These won't succeed on retry without changing the request.

Q: How should mutations handle errors differently from queries?

Queries are idempotent — safe to retry automatically. Mutations (POST/PUT/DELETE) are not idempotent by default, so blind retries risk duplicates. Use idempotency keys for mutations, and only auto-retry if the server confirms no side effect occurred (e.g., network error before server processed the request).

Q: How does error transformation improve observability?

Typed errors enable: (1) Structured logging with error categories for dashboards. (2) Automatic retry decisions based on retryable flag. (3) User-friendly messages mapped from error types. (4) Alerting rules that distinguish transient spikes from persistent failures.
