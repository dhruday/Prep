Why Abstract fetch()?

At Google/Microsoft scale, raw fetch() calls scattered across components create maintenance nightmares. A layered API client provides: centralized error handling, automatic auth headers, request/response logging, caching, and type safety — all in one place.

UI Components ↓ Custom Hooks ↓ API Service Layer ↓ HTTP Client (fetch/axios) ↓ Backend REST API

❌ Anti-Pattern: Raw fetch() in Components

// Repeated in EVERY component — no caching, no retry, no cancellation
function ProductList() {
  const [products, setProducts] = useState([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState(null);

  useEffect(() => {
    setLoading(true);
    fetch('/api/products')               // ❌ No base URL config
      .then(r => r.json())                // ❌ No status code check
      .then(setProducts)                  // ❌ No error transformation
      .catch(setError)                    // ❌ No retry logic
      .finally(() => setLoading(false)); // ❌ No cancellation on unmount
  }, []);
}

✅ Production Pattern: Typed API Client

// Single source of truth — used by ALL components via hooks
class ApiClient {
  constructor(baseURL, options = {}) {
    this.baseURL = baseURL;
    this.interceptors = { request: [], response: [] };
    this.defaultHeaders = { 'Content-Type': 'application/json' };
  }

  async request(endpoint, options = {}) {
    const url = `${this.baseURL}${endpoint}`;
    const config = {
      ...options,
      headers: { ...this.defaultHeaders, ...options.headers },
    };

    // Run request interceptors (auth, logging, etc.)
    for (const fn of this.interceptors.request) config = await fn(config);

    const response = await fetch(url, config);

    // Transform errors into typed domain errors
    if (!response.ok) throw await this.transformError(response);

    return response.json();
  }
}

🔬 How the Browser Processes fetch()

1. Call Stack: fetch() is called from JS. The browser creates a Promise and hands off the HTTP request to the Network Task Queue (off the main thread).

2. DNS + TCP + TLS: For the first request, the browser resolves DNS, establishes TCP connection (3-way handshake), and TLS handshake. Subsequent requests reuse the connection (HTTP keep-alive).

3. HTTP/1.1 Connection Pool: Browsers limit to 6 parallel connections per origin. If you fire 10 fetches, 4 will queue. This is why domain sharding existed pre-HTTP/2.

4. Response Parsing: When the response arrives, the browser puts the callback in the Microtask Queue (Promise resolution). The event loop picks it up after the current synchronous code finishes.

5. JSON Parsing: response.json() is also async — it reads the body stream and parses JSON in a separate step. For large payloads (>1MB), this can block the main thread for 50-100ms.

Connection Pooling — HTTP/1.1 vs HTTP/2

// HTTP/1.1: 6 parallel connections per origin
// If all 6 are busy, requests QUEUE (head-of-line blocking)
fetch('/api/products');   // → Connection 1
fetch('/api/users');      // → Connection 2
fetch('/api/comments');   // → Connection 3
fetch('/api/tags');        // → Connection 4
fetch('/api/categories');  // → Connection 5
fetch('/api/stats');       // → Connection 6
fetch('/api/config');      // ⏳ QUEUED — waits for a slot

// HTTP/2: Multiplexed streams over ONE connection
// ALL 7 requests fire simultaneously — no queue
// This is why HTTP/2 makes domain sharding an anti-pattern

Google/Microsoft Senior Frontend — API Layer Questions

Q: Why not just use fetch() directly in components?

Direct fetch creates duplication: every component repeats error handling, auth header injection, loading states, and retry logic. At scale with 200+ components, a single API change (like adding a CSRF header) requires touching every file. An abstraction layer provides a single point of change, centralized error transformation, and enables request deduplication and caching transparently.

Q: What layers should an API client have at Google scale?

Four layers: (1) HTTP Transport — raw fetch/axios with timeout, retry, AbortController; (2) API Service Layer — typed endpoints, base URL config, auth interceptors, error transformation; (3) Data Hooks — React Query/SWR for caching, deduplication, background refetch; (4) UI Components — only consume hooks, never know about HTTP. This separation means you can swap transport (fetch→axios), swap caching (React Query→SWR), or add new interceptors without touching any component.

Q: How do interceptors work in a fetch-based client?

Interceptors are middleware functions that run before/after every request. Request interceptors modify config (inject auth tokens, add correlation IDs, log request start). Response interceptors transform the response (unwrap data envelope, refresh expired tokens, log timing). They compose as a pipeline: request → [...requestInterceptors] → fetch → [...responseInterceptors] → result. This is the same pattern as Express middleware but on the client side.

Q: When would you NOT use an abstraction layer?

For prototypes, hackathons, or apps with fewer than 5 API calls, direct fetch is fine — YAGNI applies. Also, if the team is using a framework like Next.js server components where data fetching is colocated with rendering and deduplication is built-in, you might skip a custom client. The abstraction adds value at scale (50+ endpoints, multiple teams, evolving auth patterns).
