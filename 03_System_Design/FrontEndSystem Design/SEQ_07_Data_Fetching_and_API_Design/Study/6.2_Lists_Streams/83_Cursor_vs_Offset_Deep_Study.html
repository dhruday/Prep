1. Database Query Execution — The Real Cost

-- OFFSET: What actually happens in PostgreSQL
EXPLAIN ANALYZE
  SELECT * FROM products ORDER BY id LIMIT 20 OFFSET 100000;

-- Execution plan:
-- Limit  (rows=20) (actual time=245.123..245.130)
--   → Index Scan using products_pkey (rows=100020)
--     Rows Removed by Offset: 100000 ← THE PROBLEM
-- Planning Time: 0.08ms
-- Execution Time: 245.15ms ← Slow!

-- CURSOR: Same dataset
EXPLAIN ANALYZE
  SELECT * FROM products WHERE id > 100000 ORDER BY id LIMIT 20;

-- Execution plan:
-- Limit  (rows=20) (actual time=0.032..0.045)
--   → Index Scan using products_pkey (rows=20)
--     Index Cond: (id > 100000)
-- Planning Time: 0.07ms
-- Execution Time: 0.06ms ← 4000x faster!
The key insight: OFFSET forces a sequential scan through N rows even with an index. The WHERE clause in cursor pagination allows the B-tree to seek directly to the start position.

2. B-Tree Index Behavior

// B-Tree structure (simplified):
//           [500]              ← root node
//          /     \
//     [250]       [750]        ← internal nodes
//    /    \      /    \
//  [1-249] [251-499] [501-749] [751-1000]  ← leaf nodes

// OFFSET 500, LIMIT 20:
// 1. Start at leftmost leaf [1]
// 2. Scan 500 entries sequentially through leaves
// 3. Return entries 501-520
// Cost: O(500) leaf traversals

// WHERE id > 500 LIMIT 20:
// 1. B-Tree seek: root → [750] → [501-749] leaf
// 2. Start at id=501, read 20 entries
// Cost: O(log N) seek + O(20) reads = O(log N)

3. Consistency Model Comparison

// Scenario: 1000 items sorted by created_at DESC
// User is viewing page 5 (items 81-100)
// 3 new items are inserted at the top

// ═══ OFFSET Pagination ═══
// Before insert: page 5 = items 81-100
// After insert:  page 5 = items 78-97 (items shifted by 3)
// Result: User sees items 78-80 AGAIN (duplicates from page 4)
//         Items 98-100 are MISSED (pushed to page 6)

// ═══ Cursor Pagination ═══
// Cursor = "created_at < '2024-01-15T10:30:00Z'"
// Before insert: next 20 items after cursor
// After insert:  SAME 20 items after cursor (unaffected)
// Result: Perfectly consistent — inserts above cursor are invisible

// ═══ What about DELETIONS? ═══
// Offset: If item 85 deleted, item 86 shifts to position 85
//         User might miss item that shifted up from next page
// Cursor: Deleted items simply don't appear. No gaps, no duplicates.

4. Performance Degradation Curve

// Benchmark: PostgreSQL, 1M rows, indexed on id
// Query time by page number (pageSize = 20):

// Page      Offset Time    Cursor Time    Speedup
// ────────  ──────────     ──────────     ───────
// 1         0.05ms         0.05ms         1x
// 10        0.08ms         0.05ms         1.6x
// 100       0.5ms          0.05ms         10x
// 1,000     5ms            0.06ms         83x
// 10,000    50ms           0.06ms         833x
// 50,000    245ms          0.06ms         4,083x

// Offset: LINEAR degradation O(N)
// Cursor: CONSTANT time O(1) after index seek
// Crossover point: ~page 50 offset starts feeling slow
At Google/Facebook scale (billions of rows, sharded), offset pagination is completely impractical. Even page 2 might hit different shards and the offset calculation becomes distributed — adding network round trips per shard.

5. Distributed Systems Implications

// Sharded database with OFFSET:
// Query: SELECT * FROM products ORDER BY price LIMIT 20 OFFSET 100
//
// Shard A: OFFSET 100, LIMIT 120 → return 120 rows (need extras!)
// Shard B: OFFSET 100, LIMIT 120 → return 120 rows
// Shard C: OFFSET 100, LIMIT 120 → return 120 rows
// Router: merge-sort 360 rows, skip 100, take 20
// Problem: each shard returns MORE than needed (scatter-gather)

// Sharded database with CURSOR (price > 29.99, id > 5432):
// Shard A: WHERE (price,id) > (29.99,5432) LIMIT 20
// Shard B: WHERE (price,id) > (29.99,5432) LIMIT 20
// Shard C: WHERE (price,id) > (29.99,5432) LIMIT 20
// Router: merge-sort 60 rows, take top 20
// Each shard returns exactly what's needed — minimal data transfer

1. Hybrid Pagination Strategy

// Pattern: Offset for first N pages, cursor thereafter
// Why: Users on page 1-5 want page numbers (bookmarkable)
//      Users scrolling past page 5 are in "browse" mode

class HybridPaginator {
  private OFFSET_THRESHOLD = 5; // pages
  
  getPage(params) {
    if (params.cursor) {
      return this.cursorPaginate(params.cursor, params.limit);
    }
    if (params.page <= this.OFFSET_THRESHOLD) {
      return this.offsetPaginate(params.page, params.limit);
    }
    // Page > threshold: convert to cursor
    throw new Error('Use cursor for deep pagination');
  }
}

// API response includes both:
{
  "data": [...],
  "pagination": {
    "page": 3,           // for pages 1-5
    "totalPages": 5,     // only show first 5
    "nextCursor": "abc", // always available
    "hasMore": true
  }
}

2. Cursor with Encrypted Context

// Problem: Plain Base64 cursors can be decoded and tampered
// Solution: Encrypt cursor payload with server-side key

import { createCipheriv, createDecipheriv } from 'crypto';

const CURSOR_KEY = process.env.CURSOR_SECRET; // 32 bytes

function encodeCursor(data) {
  const iv = randomBytes(16);
  const cipher = createCipheriv('aes-256-gcm', CURSOR_KEY, iv);
  const encrypted = Buffer.concat([
    cipher.update(JSON.stringify(data)),
    cipher.final()
  ]);
  const tag = cipher.getAuthTag();
  return Buffer.concat([iv, tag, encrypted]).toString('base64url');
}

// Benefits:
// 1. Client cannot modify cursor values
// 2. Prevents SQL injection via cursor
// 3. Hides internal column names/types
// 4. Can include expiry timestamp

3. Cache Architecture Differences

// OFFSET — Deterministic cache keys:
Cache key: "products:page=3:size=20:sort=price"
// ✅ Can prefetch page 4 before user gets there
// ✅ Any user gets same page (CDN cacheable)
// ❌ Insert invalidates ALL page caches (shift)

// CURSOR — Position-dependent cache keys:
Cache key: "products:after=eyJ...:size=20"
// ❌ Cannot prefetch (don't know next cursor)
// ❌ Each user has different cursor (not CDN cacheable)
// ✅ Insert doesn't invalidate existing cached pages

// Production strategy:
// 1. Cache page 1 aggressively (most visited)
// 2. Use stale-while-revalidate for subsequent pages
// 3. Client-side: React Query caches everything per session
// 4. Server-side: Cache only if cursor maps to known position

// Pattern D: Link headers (GitHub API style)
Link: </api/products?page=4>; rel="next",

Q1: You're building a product listing page for an e-commerce site with 5M products. Walk me through pagination strategy.
Answer: Use a hybrid approach:
1. Search results: Cursor pagination. Search queries change frequently and dataset is filtered, so consistency matters. Cursor = last item's relevance_score + id.
2. Category browsing: First 5 pages offset (users want "page 3 of 50"), then cursor after page 5.
3. Sort by price: Keyset pagination with composite (price, id) index. Price is non-unique, need tiebreaker.
4. Total count: Cached counter per category, updated async on product CRUD. Show "~5,000 products" not exact.
5. API: /products?category=shoes&sort=price&after=cursor&limit=24. Response includes pageInfo with hasNextPage.
6. Frontend: useInfiniteQuery for mobile (scroll), offset useQuery for desktop (page numbers).
Follow-up: How do you handle it when someone sorts by "Newest" then switches to "Price: Low to High" mid-pagination?
Reset pagination entirely. The cursor from sort-by-newest is meaningless for sort-by-price. Clear React Query cache for that key, fetch page 1 with new sort params. Show loading state during transition. Preserve scroll position only if sort didn't change.
Q2: How does GitHub implement pagination for their REST API and why?
GitHub uses Link header pagination:
- Response includes Link header: <url>; rel="next", <url>; rel="prev", <url>; rel="first", <url>; rel="last"
- Offset-based under the hood (?page=N&per_page=30)
- Limited to 1000 results (hard cap on deep pagination)

Why offset? GitHub repos rarely have millions of items in a single list. Issues, PRs, commits per repo are manageable. The 1000 limit prevents the performance problem.

For their GraphQL API (v4), they use cursor-based with Relay Connection spec — different choice for different API style.
Follow-up: What would you change about GitHub's pagination design?
Add cursor support to REST for repositories with 100K+ issues (e.g., kubernetes/kubernetes). Add total_count to response headers for UI without extra request. Consider ETags for page-level caching.
Q3: A user reports seeing duplicate items when scrolling through their feed. Diagnose and fix.
Diagnosis: Almost certainly offset pagination with concurrent writes.
1. User loaded page 5 (offset 80)
2. New item inserted (pushed item 80 to position 81)
3. User loads page 6 (offset 100) — item that was at 80 is now at 81, appears again

Fix: Switch to cursor-based pagination.
1. Change API to accept cursor (last item's timestamp + id)
2. WHERE (created_at, id) < (:ts, :id) ORDER BY created_at DESC, id DESC
3. Return endCursor in response
4. Frontend: useInfiniteQuery with getNextPageParam returning endCursor

Quick fix (if can't change backend): Client-side deduplication with Set of seen item IDs. But this masks the real problem.
Follow-up: What if the product requirement says "users must see page numbers"?
Compromise: show page numbers for first 10 pages only (most users don't go further). After page 10, switch to "Load More" with cursor. Or: snapshot pagination — take a snapshot ID on first page load, all subsequent pages read from that consistent snapshot using MVCC.
Q4: Compare the three approaches from a frontend developer's perspective. Framework-level integration.
Offset + React Query:
- useQuery(['items', { page }]) — one query per page
- Easy prefetching: queryClient.prefetchQuery(['items', { page: page + 1 }])
- Page state in URL: /items?page=3 — bookmarkable
- placeholderData: keepPreviousData — smooth page transitions

Cursor + React Query:
- useInfiniteQuery(['items']) — single query, multiple pages
- data.pages.flatMap(p => p.data) — flatten for rendering
- Cannot prefetch (no cursor for unmade requests)
- getNextPageParam: (last) => last.cursor — auto-pagination
- maxPages: 10 — memory management

Keyset + SWR:
- useSWRInfinite(getKey, fetcher) — index-based key function
- getKey: (i, prev) => prev?.nextKey ? `/api?...` : null
- Similar to cursor but key is server-provided composite
Q5: How would you implement bidirectional cursor pagination (forward and backward)?
Relay approach:
- Forward: first: 20, after: "cursor" → WHERE id > :cursor ORDER BY id ASC LIMIT 21
- Backward: last: 20, before: "cursor" → WHERE id < :cursor ORDER BY id DESC LIMIT 21, then REVERSE result

Implementation details:
1. Backward query reverses ORDER BY, then reverses result to maintain display order
2. pageInfo returns both hasPreviousPage and hasNextPage
3. Response includes both startCursor and endCursor
4. Client stores cursors per page for back-navigation

Edge case: first page has no "before" cursor — client knows to show "beginning of list." Last page has hasNextPage=false.
Follow-up: How does this work with composite sort keys?
Forward: WHERE (price, id) > (:p, :id) ORDER BY price ASC, id ASC. Backward: WHERE (price, id) < (:p, :id) ORDER BY price DESC, id DESC, then reverse. Both need composite index. The cursor encodes both price and id.
Q6: At what dataset size does cursor pagination become necessary? How do you decide?
Rule of thumb:
- <1K items: Offset fine, even without index optimization
- 1K-10K: Offset OK if indexed, but cursor recommended for write-heavy
- 10K-100K: Cursor strongly recommended, offset has visible latency on deep pages
- 100K+: Cursor required, offset is broken (seconds of latency)
- 1M+: Keyset/cursor only, consider query result caching

Other factors forcing cursor:
1. Frequent writes (social feed) → offset consistency broken
2. Public API → clients shouldn't depend on total count
3. Sharded data → offset scatter-gather is expensive
4. Real-time data → items appearing/disappearing constantly

1. Benchmark: Offset vs Cursor Performance

// Express endpoint that benchmarks both approaches
app.get('/api/benchmark', async (req, res) => {
  const page = parseInt(req.query.page) || 100;
  const limit = 20;
  
  // Benchmark OFFSET
  const offsetStart = performance.now();
  const offsetResult = await db.query(
    `SELECT * FROM products ORDER BY id LIMIT ? OFFSET ?`,
    [limit, (page - 1) * limit]
  );
  const offsetTime = performance.now() - offsetStart;
  
  // Benchmark CURSOR (simulate: use last ID from offset result as cursor)
  const cursorId = (page - 1) * limit; // approximation
  const cursorStart = performance.now();
  const cursorResult = await db.query(
    `SELECT * FROM products WHERE id > ? ORDER BY id LIMIT ?`,
    [cursorId, limit]
  );
  const cursorTime = performance.now() - cursorStart;
  
  res.json({
    page,
    offset: { time: `${offsetTime.toFixed(2)}ms`, rows: offsetResult.length },
    cursor: { time: `${cursorTime.toFixed(2)}ms`, rows: cursorResult.length },
    speedup: `${(offsetTime / cursorTime).toFixed(1)}x`
  });
});

2. React: Offset Pagination with Prefetching

function OffsetProductList() {
  const [page, setPage] = useState(1);
  const queryClient = useQueryClient();
  
  const { data, isPlaceholderData } = useQuery({
    queryKey: ['products', { page }],
    queryFn: () => fetch(`/api/products?page=${page}&limit=20`)
      .then(r => r.json()),
    placeholderData: keepPreviousData,
    // ^ Show previous page data while next page loads
    // Prevents flash of empty state
  });
  
  // Prefetch next page on hover or when current page renders
  useEffect(() => {
    if (data?.meta.hasNext) {
      queryClient.prefetchQuery({
        queryKey: ['products', { page: page + 1 }],
        queryFn: () => fetch(`/api/products?page=${page + 1}&limit=20`)
          .then(r => r.json()),
      });
    }
  }, [page, data]);
  
  return (
    <div style={{ opacity: isPlaceholderData ? 0.7 : 1 }}>
      {data?.data.map(item => <ProductCard key={item.id} {...item} />)}
      <Pagination
        page={page} total={data?.meta.totalPages}
        onChange={setPage}
      />
    </div>
  );
}

3. React: Cursor Pagination with Infinite Query

function CursorProductList() {
  const {
    data, fetchNextPage, hasNextPage,
    isFetchingNextPage, status
  } = useInfiniteQuery({
    queryKey: ['products', 'cursor'],
    queryFn: async ({ pageParam }) => {
      const url = pageParam
        ? `/api/products/cursor?after=${pageParam}&limit=20`
        : `/api/products/cursor?limit=20`;
      return fetch(url).then(r => r.json());
    },
    initialPageParam: null,
    getNextPageParam: (lastPage) =>
      lastPage.pageInfo.hasNextPage
        ? lastPage.pageInfo.endCursor
        : undefined, // undefined = no more pages
    maxPages: 10, // Evict oldest pages beyond 10
  });
  
  // Flatten all pages into single array
  const allProducts = data?.pages.flatMap(
    page => page.edges.map(e => e.node)
  ) ?? [];
  
  return (
    <div>
      {allProducts.map(item => <ProductCard key={item.id} {...item} />)}
      <LoadMoreButton
        hasMore={hasNextPage}
        loading={isFetchingNextPage}
        onClick={fetchNextPage}
      />
    </div>
  );
}

Quick Decision Guide

Need page numbers?          → Offset (with cached count)
Write-heavy + consistency?  → Cursor
Sort by non-unique column?  → Keyset (composite index)
Mobile infinite scroll?     → Cursor + useInfiniteQuery
SEO / shareable URLs?       → Offset (first 10 pages)
Public API?                 → Cursor (Relay Connection)
Admin dashboard?            → Offset (familiar UX)
1M+ rows?                   → NEVER offset for deep pages
Real-time feed?             → Cursor (immune to inserts)
E-commerce product list?    → Hybrid (offset first 5 pages + cursor)

SQL Quick Reference

-- Offset (page 50 of 20-item pages)
SELECT * FROM t ORDER BY id LIMIT 20 OFFSET 980;

-- Cursor (after ID 980)
SELECT * FROM t WHERE id > 980 ORDER BY id LIMIT 21;

-- Keyset (after price=29.99, id=5432)
SELECT * FROM t WHERE (price,id) > (29.99,5432)
  ORDER BY price,id LIMIT 21;

-- Backward cursor (before ID 500)
(SELECT * FROM t WHERE id < 500 ORDER BY id DESC LIMIT 21)
  ORDER BY id ASC; -- reverse back to display order

-- Required indexes:
CREATE INDEX idx_id ON t(id);
CREATE INDEX idx_price_id ON t(price, id);
CREATE INDEX idx_created_id ON t(created_at DESC, id DESC);
