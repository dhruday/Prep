1. Offset Pagination — SQL Internals

The query SELECT * FROM products ORDER BY id LIMIT 20 OFFSET 10000 forces the database to:

-- Execution plan for OFFSET pagination:
1. Perform full index scan or table scan with ORDER BY
2. Read and sort ALL qualifying rows (potentially millions)
3. Skip first 10,000 rows (still reads them from disk!)
4. Return next 20 rows
5. Discard the rest

-- B-tree traversal: O(offset + limit) rows read
-- At page 500 with pageSize=20: reads 10,020 rows, returns 20
-- Memory: holds sorted result set until offset reached
PostgreSQL's OFFSET clause is syntactic sugar — the engine physically scans past rows, holding locks briefly on each. At 1M+ rows, this causes measurable I/O and CPU spikes.

2. Cursor-Based Pagination — Seek Method

Instead of skipping N rows, we use a WHERE clause that leverages the B-tree index directly:

-- Cursor pagination (basic single-column):
SELECT * FROM products
WHERE id > 10000   -- cursor = last seen ID
ORDER BY id ASC
LIMIT 20;

-- B-tree traversal: O(log N) to find start position
-- Then sequential read of exactly 20 rows
-- No wasted I/O regardless of page number
-- Performance: O(log N + limit) vs O(offset + limit)

Cursor Encoding

-- Raw cursor: { id: 10000 }
-- Base64 encoded: eyJpZCI6MTAwMDB9
-- Client receives opaque string, cannot tamper with internals
-- Server decodes, validates, and uses as WHERE condition
-- Relay spec: cursor is per-edge, not per-page

3. Keyset Pagination — Composite Sort Keys

When sorting by non-unique columns (price, name), a tiebreaker column (id) is required:

-- Keyset with composite key (price + id):
SELECT * FROM products
WHERE (price, id) > (29.99, 5432)
ORDER BY price ASC, id ASC
LIMIT 20;

-- SQL row-value comparison: tuple comparison
-- Equivalent to: (price > 29.99) OR (price = 29.99 AND id > 5432)
-- Requires composite index: CREATE INDEX idx ON products(price, id)
-- B-tree traversal: O(log N) seek on composite index
Not all databases support row-value comparisons equally. PostgreSQL handles them natively with index seek. MySQL may need the expanded OR form for index utilization.

4. The Total Count Problem

-- COUNT(*) is expensive on large InnoDB tables:
SELECT COUNT(*) FROM products; -- 500ms+ on 10M rows

-- Solutions at scale:
1. Cached count: Store in Redis/memcached, update on write (eventual consistency)
2. Approximate count: pg_class.reltuples (PostgreSQL) or TABLE_ROWS (MySQL INFORMATION_SCHEMA)
3. HyperLogLog: Probabilistic count with ~2% error (Redis PFCOUNT)
4. Eliminate count: "Load More" UI doesn't need total
5. Count estimate: EXPLAIN output row estimate for filtered queries

5. Consistency During Concurrent Writes

-- Offset pagination consistency problem:
-- User on page 3 (offset=40, limit=20)
-- Another user inserts a row at position 15
-- Page 3 now shifts: row 40 becomes row 41
-- User sees a DUPLICATE from page 2, MISSES a row

-- Cursor pagination: immune to this!
-- WHERE id > 60 always returns the same next batch
-- Inserts before id=60 don't affect future pages
-- Inserts after id=60 naturally appear in correct position

1. Strategy Pattern — Pagination Service

// Abstract pagination strategy
interface PaginationStrategy<T> {
  paginate(query: QueryBuilder, params: PaginationParams): Promise<PaginatedResult<T>>;
}

// Offset implementation
class OffsetStrategy implements PaginationStrategy {
  paginate(query, { page, pageSize }) {
    const offset = (page - 1) * pageSize;
    return query.offset(offset).limit(pageSize).execute();
  }
}

// Cursor implementation
class CursorStrategy implements PaginationStrategy {
  paginate(query, { cursor, limit }) {
    const decoded = cursor ? decodeCursor(cursor) : null;
    if (decoded) query = query.where('id', '>', decoded.id);
    return query.orderBy('id').limit(limit + 1).execute();
    // Fetch limit+1 to determine hasNextPage
  }
}

// Service uses strategy based on use case
class PaginationService {
  constructor(private strategy: PaginationStrategy) {}
  getPage(params) { return this.strategy.paginate(...params); }
}

Q1: Why does offset pagination degrade at scale? What's the exact database behavior?
With OFFSET 10000 LIMIT 20, the database must:
1. Perform an index scan or table scan with ORDER BY
2. Materialize and sort all qualifying rows into a temporary result set
3. Iterate through the first 10,000 rows, reading each from disk/buffer pool
4. Return only rows 10,001-10,020
5. Discard the rest

This is O(offset + limit) I/O. At page 500 (offset=10,000): ~10x slower than page 1. At page 50,000 (offset=1M): potentially seconds of scan time. The CPU cost of sorting is also proportional to the full result set, not just the page.
Follow-up: How would you prove this with EXPLAIN ANALYZE?
Run EXPLAIN ANALYZE and observe: (1) "Seq Scan" or "Index Scan" rows=10020 at high offset; (2) "Sort" node with sort method: external merge for large sets; (3) Actual time increases linearly with offset. Compare page 1 vs page 1000 execution times.
Q2: Design pagination for a social media feed with 100M posts. Which approach and why?
Cursor-based (keyset) pagination with created_at + id composite cursor:
1. Feed is chronological — natural cursor on (created_at DESC, id DESC)
2. New posts appear at top — offset would cause duplicates on refresh
3. No total count needed — infinite scroll UX with "Load More"
4. Composite index on (created_at, id) ensures O(log N) seek
5. Cursor: base64({ts: "2024-01-15T10:30:00Z", id: "abc123"})
6. Follow-up requests: WHERE (created_at, id) < (:ts, :id) ORDER BY created_at DESC, id DESC LIMIT 20
7. Cache each page response with cursor as cache key
8. For "new posts" indicator: separate polling endpoint returning count since last cursor
Follow-up: How do you handle deletions between page loads?
Cursor pagination is naturally resilient — deleted rows simply won't appear. However, if a row is deleted from a previously loaded page, the client's local cache becomes stale. Solution: each page response includes a version/etag; on mutation, invalidate affected page caches.
Q3: How does cursor encoding work in the Relay Connection specification?
Relay cursors are opaque strings — the spec intentionally hides implementation:
1. Server encodes position data (e.g., {id: 100, sort: "price:29.99"}) as Base64
2. Client treats cursor as an opaque token — never parses or modifies it
3. Each edge has its own cursor (not per-page)
4. pageInfo provides startCursor and endCursor for the current page
5. Client passes cursor via "after" (forward) or "before" (backward) argument
6. Enables bidirectional navigation: first/after for forward, last/before for backward
7. The encoding can change between versions without breaking clients
Follow-up: Why is the cursor per-edge rather than per-page?
Per-edge cursors allow jumping to any position in the list, not just page boundaries. If you want to load items after a specific item (e.g., "show me what comes after this post"), you use that edge's cursor. It also enables efficient list manipulation — insert/delete near a known cursor position.
Q4: Explain keyset pagination with composite sort keys. What's the WHERE clause?
For sorting by (price ASC, id ASC): WHERE (price, id) > (:lastPrice, :lastId)

This uses SQL row-value comparison (tuple comparison), which expands to:
(price > :lastPrice) OR (price = :lastPrice AND id > :lastId)

Critical requirements:
1. Tiebreaker column (id) MUST be unique — ensures deterministic ordering
2. Composite index CREATE INDEX idx_price_id ON products(price, id) required
3. Sort direction must match index direction (ASC,ASC or DESC,DESC)
4. PostgreSQL optimizes tuple comparison to index seek natively
5. MySQL may need the expanded OR form for proper index utilization
Follow-up: What if you need DESC sort on price but ASC on id?
Mixed sort directions make tuple comparison harder. You need: (price < :lastPrice) OR (price = :lastPrice AND id > :lastId). Some ORMs don't support this cleanly. PostgreSQL: CREATE INDEX ... (price DESC, id ASC). MySQL: supported since 8.0.
Q5: How would you display total count without expensive COUNT(*)?
Five approaches by accuracy/cost:
1. Cached count: Redis counter, increment/decrement on writes. O(1) read, eventually consistent.
2. Table statistics: PostgreSQL pg_class.reltuples, MySQL TABLE_ROWS. Free but ~10% inaccurate.
3. Materialized count: Background job updates count every N minutes. Consistent with known staleness.
4. HyperLogLog: Redis PFCOUNT for approximate distinct counts. ~0.81% error, 12KB memory.
5. Eliminate: Change UX to "Showing results" without total. Google Search doesn't show exact total anymore for this reason.
Follow-up: What does Google Search actually do?
Google shows "About X results" — this is an estimate from the index, not a precise count. They stopped showing exact page numbers years ago, switched to "More results" button. Most users never go past page 2.
Q6: Compare offset vs cursor vs keyset — when would you choose each?
Offset: Admin dashboards, data tables with page numbers, small datasets (<10K), when users need "jump to page 47".
Cursor: Social feeds, infinite scroll, real-time data, mobile apps, any list with frequent writes. Most common at scale.
Keyset: When cursor-based but sorting by non-unique columns. Analytics dashboards sorted by metrics. Time-series data. High-performance reporting.

Decision matrix: frequent writes → cursor. Jump-to-page needed → offset. Custom sort + scale → keyset. Public API → cursor (Relay spec).
Follow-up: Can you combine approaches?
Yes. Common pattern: cursor for primary navigation + estimated total for UI ("~1,234 results"). Or: first page uses offset (for "page 1 of ~50"), then switches to cursor for subsequent pages. Slack does this for search results.

1. Offset Pagination — Express + SQL

// GET /api/products?page=3&pageSize=20&sort=price&order=asc
app.get('/api/products', async (req, res) => {
  const page = Math.max(1, parseInt(req.query.page) || 1);
  const pageSize = Math.min(100, Math.max(1, parseInt(req.query.pageSize) || 20));
  // ^ Clamp pageSize between 1-100 to prevent abuse
  
  const offset = (page - 1) * pageSize;
  // ^ Page 1 → offset 0, Page 3 → offset 40
  
  const allowedSorts = ['id', 'name', 'price', 'created_at'];
  const sort = allowedSorts.includes(req.query.sort) ? req.query.sort : 'id';
  // ^ Whitelist sort columns to prevent SQL injection
  
  const [rows, [{ total }]] = await Promise.all([
    db.query(`SELECT * FROM products ORDER BY ${sort} LIMIT ? OFFSET ?`, [pageSize, offset]),
    db.query('SELECT COUNT(*) as total FROM products')
    // ^ Two queries: data + count (consider caching count)
  ]);
  
  res.json({
    data: rows,
    meta: {
      page, pageSize, total,
      totalPages: Math.ceil(total / pageSize),
      hasNext: offset + pageSize < total,
      hasPrev: page > 1
    }
  });
});

2. Cursor Pagination — Base64 Encoded

// GET /api/products/cursor?after=eyJpZCI6MTAwfQ==&limit=20
app.get('/api/products/cursor', async (req, res) => {
  const limit = Math.min(100, parseInt(req.query.limit) || 20);
  let cursor = null;
  
  if (req.query.after) {
    try {
      cursor = JSON.parse(Buffer.from(req.query.after, 'base64').toString());
      // ^ Decode: "eyJpZCI6MTAwfQ==" → { id: 100 }
    } catch {
      return res.status(400).json({ error: 'Invalid cursor' });
    }
  }
  
  const rows = await db.query(
    cursor
      ? 'SELECT * FROM products WHERE id > ? ORDER BY id LIMIT ?'
      : 'SELECT * FROM products ORDER BY id LIMIT ?',
    cursor ? [cursor.id, limit + 1] : [limit + 1]
    // ^ Fetch limit+1 to determine hasNextPage without COUNT
  );
  
  const hasNext = rows.length > limit;
  if (hasNext) rows.pop(); // Remove extra row
  
  const encodeCursor = (row) =>
    Buffer.from(JSON.stringify({ id: row.id })).toString('base64');
  
  res.json({
    edges: rows.map(row => ({
      cursor: encodeCursor(row),
      node: row
    })),
    pageInfo: {
      hasNextPage: hasNext,
      endCursor: rows.length ? encodeCursor(rows[rows.length - 1]) : null
    }
  });
});

3. Keyset Pagination — Composite Key

// GET /api/products/keyset?afterPrice=29.99&afterId=5432&limit=20
app.get('/api/products/keyset', async (req, res) => {
  const limit = Math.min(100, parseInt(req.query.limit) || 20);
  const afterPrice = parseFloat(req.query.afterPrice);
  const afterId = parseInt(req.query.afterId);
  
  let query, params;
  if (!isNaN(afterPrice) && !isNaN(afterId)) {
    // Tuple comparison for composite keyset
    query = `SELECT * FROM products
             WHERE (price, id) > (?, ?)
             ORDER BY price ASC, id ASC
             LIMIT ?`;
    params = [afterPrice, afterId, limit + 1];
  } else {
    query = 'SELECT * FROM products ORDER BY price ASC, id ASC LIMIT ?';
    params = [limit + 1];
  }
  
  const rows = await db.query(query, params);
  const hasNext = rows.length > limit;
  if (hasNext) rows.pop();
  
  const last = rows[rows.length - 1];
  res.json({
    data: rows,
    meta: {
      hasNext,
      nextKey: last ? { price: last.price, id: last.id } : null
    }
  });
});

4. React Query useInfiniteQuery

function useProducts() {
  return useInfiniteQuery({
    queryKey: ['products'],
    queryFn: async ({ pageParam }) => {
      const url = pageParam
        ? `/api/products/cursor?after=${pageParam}&limit=20`
        : '/api/products/cursor?limit=20';
      const res = await fetch(url);
      return res.json();
    },
    initialPageParam: null,
    getNextPageParam: (lastPage) =>
      lastPage.pageInfo.hasNextPage ? lastPage.pageInfo.endCursor : undefined,
    // ^ Return undefined to signal no more pages
    // React Query calls this after each page fetch
    // If undefined returned, hasNextPage becomes false
  });
}

Quick SQL Reference

-- Offset
SELECT * FROM t ORDER BY id LIMIT 20 OFFSET 40;

-- Cursor (single key)
SELECT * FROM t WHERE id > :cursor ORDER BY id LIMIT 21;

-- Keyset (composite)
SELECT * FROM t WHERE (price,id) > (:p,:id) ORDER BY price,id LIMIT 21;

-- Required indexes:
CREATE INDEX idx_id ON t(id);                  -- cursor
CREATE INDEX idx_price_id ON t(price, id);     -- keyset
CREATE INDEX idx_created_id ON t(created_at, id); -- feed

Decision Tree

Need "Page 1 of N" UI? ──── Yes ──→ Offset (+ cached total count)
         │ No
         ▼
Dataset > 10K rows? ──────── No ───→ Offset (simple, fast enough)
         │ Yes
         ▼
Sort by unique column? ───── Yes ──→ Cursor (simplest at scale)
         │ No
         ▼
Sort by non-unique + ID? ── Yes ──→ Keyset (composite index)
         │ No
         ▼
Multiple sort options? ───── Yes ──→ Cursor with encoded sort key
