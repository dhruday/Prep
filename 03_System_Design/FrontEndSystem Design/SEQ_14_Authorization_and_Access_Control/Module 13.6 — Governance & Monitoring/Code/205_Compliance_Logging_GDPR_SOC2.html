GDPR vs SOC 2: The Core Tension

GDPR says minimize what you collect. SOC 2 says prove who did what. The engineering resolution: pseudonymize PII at write time. Logs contain enough to satisfy SOC 2 evidence requirements, but not enough to identify the person without the separately-stored mapping table.

GDPR

Data Protection Regulation (EU)

  • Art. 5(1)(c) — Data minimisation
  • Art. 5(1)(e) — Storage limitation (retain only as long as necessary)
  • Art. 17 — Right to erasure ("Right to be forgotten")
  • Art. 25 — Privacy by design (pseudonymization default)
  • Art. 30 — Records of processing activities
  • Fines up to 4% global annual revenue
SOC 2

Trust Service Criteria (US SaaS)

  • CC6.1 — Logical access restrictions
  • CC6.2 — Access provisioning log
  • CC6.3 — Access revocation/offboarding log
  • CC6.7 — Data transmission / export audit
  • CC7.2 — Anomaly monitoring evidence
  • Type II covers 6–12 month window

WORM (Write Once Read Many) Storage Options

AWS

S3 Object Lock — Compliance Mode

Once in compliance mode, no one (including AWS root) can delete or modify objects before the retention date expires. Strongest tamper-evidence guarantee.

Azure

Immutable Blob Storage

Time-based retention policies at container level. Locked policies cannot be shortened. Meets SEC Rule 17a-4 WORM requirements.

Self-hosted

Hash Chaining

Each log entry stores SHA-256(previousHash + currentContent). Modification of any entry breaks all subsequent hashes — proving tampering without special storage.

⚠️ GDPR + Audit Log Conflict: You cannot delete an audit log entry (that breaks tamper-evidence). You also cannot refuse a valid erasure request. Resolution: only store pseudonymous IDs. Deleting the mapping satisfies erasure. The log entry no longer contains personal data.

Code Patterns

GDPR-Compliant Pseudonymization

import { createHash } from 'crypto';

// HMAC-based pseudonymization — stable (same input = same output) but not reversible
function pseudonymize(value: string, tenantId: string): string {
  return createHash('sha256')
    .update(`${tenantId}:${value}:${process.env.PSEUDONYM_SALT}`)
    .digest('hex')
    .slice(0, 16);
}

function maskIp(ip: string): string {
  // IPv4: keep first 2 octets; IPv6: keep first 4 groups
  if (ip.includes(':')) return ip.split(':').slice(0,4).join(':') + ::x:x:x:x';
  return ip.split('.').slice(0,2).join('.') + '.x.x';
}

// GDPR erasure: delete mapping → log entries anonymized, not deleted
async function processErasureRequest(userId: string, tenantId: string): Promise<void> {
  const pseudoId = pseudonymize(userId, tenantId);
  // Step 1: Delete mapping table entry (GDPR erasure satisfied)
  await db.query('DELETE FROM pseudonym_mapping WHERE pseudo_id = $1 AND tenant_id = $2', [pseudoId, tenantId]);
  // Step 2: Audit log entries still exist — now anonymized (no longer personal data)
  // Step 3: Log the erasure request itself (meta-compliance record)
  await metaAudit.write({ action: 'gdpr:erasure_processed', pseudoId, tenantId });
}

SOC 2 Evidence Query Service

// Provides structured evidence for SOC 2 auditor evidence requests
export class Soc2EvidenceService {
  // CC6.2 — Access provisioning log (auditor: "who was granted access in Q1?")
  async getProvisioningLog(from: Date, to: Date, tenantId: string) {
    return this.repo.query({
      tenantId,
      action: { in: ['user:grant_role', 'permission:create', 'access:provision'] },
      timestamp: { gte: from, lte: to }
    });
  }

  // CC6.3 — Access revocation log (auditor: "who was offboarded and when?")
  async getRevocationLog(from: Date, to: Date, tenantId: string) {
    return this.repo.query({
      tenantId,
      action: { in: ['user:revoke_role', 'access:revoke', 'user:offboard'] },
      timestamp: { gte: from, lte: to }
    });
  }

  // CC7.2 — Anomaly evidence (auditor: "how do you detect suspicious access?")
  async getHighDenyUsers(from: Date, to: Date, tenantId: string) {
    return this.repo.aggregateByUser({ tenantId, decision: 'deny', timestamp: { gte: from, lte: to }, havingCount: { gte: 100 } });
  }
}

// Multi-framework retention enforcer
const RETENTION_POLICIES = [
  { category: 'security_event', days: 90,   /* GDPR */   coldDays: 365  },
  { category: 'role_change',    days: 365,  /* SOC 2 */  coldDays: 730  },
  { category: 'financial_op',   days: 365,  /* SOX */    coldDays: 2555 },
  { category: 'pii_access',     days: 180,  /* GDPR+SOC2 */ coldDays: 730 },
];

async function runRetentionCycle(): Promise<void> {
  for (const p of RETENTION_POLICIES) {
    const hotCutoff  = new Date(Date.now() - p.days     * 86400000);
    const coldCutoff = new Date(Date.now() - p.coldDays  * 86400000);
    await archiver.moveToGlacier({ category: p.category, olderThan: hotCutoff });
    await archiver.verifyGlacierIntegrity({ category: p.category, olderThan: coldCutoff });
    // Note: we never DELETE — only archive to WORM storage
  }
}
Key Interviewer Points:
(1) HMAC pseudonymization — deterministic, not reversible without the PSEUDONYM_SALT env var
(2) Erasure = delete mapping table, not the log
(3) SOC2EvidenceService wraps auditor evidence queries — compliance team, not devops, uses this
(4) Retention enforcer uses WORM archive (never DELETE) with per-category policies
