Cheat Sheet

1. Why Short-Lived Tokens + Refresh?

// Long-lived access tokens = large attack window
// If stolen, attacker has access for hours/days
// JWT can't be revoked without server-side blacklist
//
// Solution: Access Token (5-15 min) + Refresh Token (7-30 days)
//
// Access Token: short-lived JWT, used for API authorization
//   → If stolen: attacker has only a few minutes
//   → Stateless verification (no server lookup needed)
//
// Refresh Token: long-lived opaque string, used only to get new access tokens
//   → Stored server-side: CAN be revoked instantly
//   → Sent only to /auth/refresh (narrow attack surface)
//   → Rotated on each use (reuse = theft detection)
//
// The "silent refresh" UX:
// User never sees a login screen during their session
// Access token expires → app silently requests new one → continues

2. Refresh Token Rotation

// Single-use refresh tokens: each token is used exactly once
// When exchanged, server issues a NEW refresh token
//
// Token Family: server tracks a "family" of related refresh tokens
//   RT1 → issues AT2 + RT2   (RT1 marked used)
//   RT2 → issues AT3 + RT3   (RT2 marked used)
//
// Theft Detection:
//   If attacker stole RT2 and uses it AFTER the legitimate user:
//   RT2 was already used → server detects reuse
//   → Revoke ALL tokens in the family (RT3, RT4, etc.)
//   → Force re-authentication for user AND attacker
//
// If attacker uses RT2 BEFORE the legitimate user:
//   User tries RT2 → already used → family revoked
//   User sees login screen → re-authenticates → safe
//   Attacker's stolen RT3 is revoked too
Token rotation with family tracking means token theft is always detected within one refresh cycle. The attacker can never maintain persistent access.

Race Conditions & Edge Cases

1. Parallel API Calls During Refresh

// Problem: Access token expires during multiple concurrent API calls
// All get 401 → all try to refresh → multiple refresh requests
// If refresh token is single-use: only first succeeds
//
// Solution: Request Queue Pattern
// 1. First 401 triggers refresh
// 2. Subsequent 401s are queued (not retried immediately)
// 3. After refresh completes → retry all queued requests
// 4. Single refresh promise shared across all waiting requests

2. Multi-Tab Refresh Conflict

// Problem: User has 5 tabs open, token expires
// All 5 tabs try to refresh simultaneously
// With rotation: only first tab gets new refresh token
// Other 4 tabs try to use old (now-invalidated) refresh token → fail
//
// Solutions:
// A. BroadcastChannel: one tab refreshes, broadcasts to others
// B. Refresh token reuse grace period (10 seconds)
//    → Same refresh token accepted within 10s window
//    → Returns SAME new tokens to all tabs
// C. Leader election: only one tab handles refresh
//    → Lock in SharedWorker or IndexedDB

3. Offline → Online Transition

// User's access token (and possibly refresh token) expired while offline
// App comes online → try refresh → may fail
//
// Solution: listen for 'online' event → attempt refresh
// If refresh fails → queue offline actions → show login
// After login → replay queued actions

FAANG Interview Questions

Q1: Design a robust token refresh system for a multi-tab SPA.
Three components: (1) Request queue — when a 401 is received, the first interceptor call triggers a refresh. All subsequent 401s during the refresh are queued. The refresh promise is shared (deduplication). Once refresh succeeds, all queued requests are retried with the new token. If refresh fails, all queued promises are rejected and user redirected to login. (2) Multi-tab coordination — use BroadcastChannel. The tab that refreshes first broadcasts the new access token to all other tabs. Other tabs listen and update their in-memory token. For logout: broadcast 'LOGOUT' to all tabs. To prevent races: use a lock (navigator.locks.request or IndexedDB-based) so only one tab refreshes at a time. (3) Proactive refresh — decode the JWT exp claim. Schedule a timer to refresh at 80% of token lifetime. Also refresh on visibilitychange (tab regains focus after idle). Combine with on-401 as fallback for clock skew. Server-side: implement token family tracking — rotate refresh tokens on every use, revoke the entire family if reuse is detected.
Follow-up: How do you handle the case where the BroadcastChannel message is lost?
Q2: How does refresh token rotation detect theft?
Each refresh token belongs to a "family" (linked by a family ID). When a refresh token is used, the server issues a new access + refresh token and marks the old refresh token as used. If someone tries to use an already-used refresh token, the server detects reuse and immediately revokes ALL tokens in that family. This works because of the timeline: either the attacker or the legitimate user will use the stolen token second. Whoever uses it second triggers the reuse detection. Scenario 1: Attacker uses stolen RT first → gets new tokens. Legitimate user tries the same RT → reuse detected → entire family revoked → both attacker and user must re-authenticate. Scenario 2: Legitimate user uses RT first (normal). Attacker tries later → reuse detected → family revoked → attacker loses access, user re-authenticates. The key insight: the attacker can never maintain persistent access — theft is detected within one refresh cycle (5-15 minutes).
Follow-up: What if the attacker uses the refresh token in a very short window before the user?

1. Complete Refresh System

class TokenRefreshManager {
  #accessToken = null;
  #refreshPromise = null;
  #channel = new BroadcastChannel('auth-refresh');

  constructor() {
    this.#channel.addEventListener('message', (e) => {
      if (e.data.type === 'TOKEN') this.#accessToken = e.data.token;
      if (e.data.type === 'LOGOUT') this.handleLogout();
    });
    // Refresh on tab focus after idle
    document.addEventListener('visibilitychange', () => {
      if (!document.hidden && this.isExpiringSoon()) this.refresh();
    });
  }

  isExpiringSoon() {
    if (!this.#accessToken) return true;
    const { exp } = decodeJwt(this.#accessToken);
    return Date.now() > (exp * 1000) - 60000; // 1 min before expiry
  }

  async getToken() {
    if (this.#accessToken && !this.isExpiringSoon()) return this.#accessToken;
    return this.refresh();
  }

  async refresh() {
    // Deduplicate: reuse in-flight refresh
    if (this.#refreshPromise) return this.#refreshPromise;

    this.#refreshPromise = fetch('/auth/refresh', {
      method: 'POST',
      credentials: 'include',
    })
    .then(async (res) => {
      if (!res.ok) throw new Error('Refresh failed');
      const { accessToken } = await res.json();
      this.#accessToken = accessToken;
      this.#channel.postMessage({ type: 'TOKEN', token: accessToken });
      return accessToken;
    })
    .catch((err) => {
      this.handleLogout();
      throw err;
    })
    .finally(() => { this.#refreshPromise = null; });

    return this.#refreshPromise;
  }

  handleLogout() {
    this.#accessToken = null;
    this.#channel.postMessage({ type: 'LOGOUT' });
    window.location.href = '/login';
  }
}

Refresh Architecture Checklist

✅ Access token: 5-15 min, JWT, stored in memory
✅ Refresh token: 7-30 days, opaque, HttpOnly SameSite cookie
✅ Rotate refresh token on every use (single-use)
✅ Token family tracking: revoke all on reuse detection
✅ Deduplicate concurrent refresh requests (shared promise)
✅ Request queue: hold 401'd requests, retry after refresh
✅ BroadcastChannel: sync token across tabs
✅ Proactive refresh: timer at 80% of token lifetime
✅ Visibility-based refresh: refresh on tab focus after idle
✅ 401 fallback: handle clock skew and missed proactive refresh
✅ Graceful logout: clear all tokens, broadcast to all tabs
✅ Rate-limit /auth/refresh endpoint (prevent brute force)
