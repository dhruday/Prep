1. JWT Structure

// JWT = Header.Payload.Signature (3 base64url-encoded parts)

// HEADER:
{
  "alg": "RS256",     // Signing algorithm
  "typ": "JWT",       // Token type
  "kid": "key-id-1"   // Key ID (for JWKS rotation)
}

// PAYLOAD (Claims):
{
  "sub": "user_123",           // Subject (user ID)
  "iss": "https://auth.example.com", // Issuer
  "aud": "https://api.example.com",  // Audience
  "exp": 1700000000,           // Expiration (Unix timestamp)
  "iat": 1699999100,           // Issued at
  "scope": "read write",       // Permissions
  "role": "admin"              // Custom claim
}

// SIGNATURE:
// RS256: RSA-SHA256(base64url(header) + "." + base64url(payload), privateKey)
// HS256: HMAC-SHA256(base64url(header) + "." + base64url(payload), secret)
//
// JWT is NOT encrypted — anyone can decode the payload (base64)
// Signature only ensures integrity (hasn't been tampered with)
// For encrypted tokens → use JWE (JSON Web Encryption)

2. HS256 vs RS256

AspectHS256 (Symmetric)RS256 (Asymmetric)
KeyShared secretPrivate key (sign) / Public key (verify)
Who can sign?Anyone with the secretOnly the auth server (private key)
Who can verify?Anyone with the secretAnyone (public key via JWKS)
MicroservicesBad: all services have the secret = all can forge tokensGood: services only need public key
Key rotationHard: update all servicesEasy: publish new public key to JWKS

Always use RS256 in production with microservices. JWKS (JSON Web Key Set) endpoint makes key distribution and rotation automatic. Services fetch /.well-known/jwks.json and cache the public keys.

JWT Attack Vectors

1. Algorithm Confusion (alg: none)

// Attack: Change header to {"alg": "none"}
// Remove signature → server skips verification
//
// Defense: NEVER accept alg: none. Whitelist allowed algorithms:
jwt.verify(token, key, { algorithms: ['RS256'] }); // Explicit!

2. HS256/RS256 Confusion

// Attack: Server configured for RS256
// Attacker changes header to {"alg": "HS256"}
// Signs with the PUBLIC key (which is known) as HMAC secret
// Vulnerable library: "oh, HS256? let me verify with the key I have"
// Uses PUBLIC key as HMAC secret → signature matches!
//
// Defense: Explicitly set algorithm in verify, not from token header
// Modern libraries: separate functions for symmetric vs asymmetric

3. JKU/X5U Header Injection

// Attack: Token header has {"jku": "https://evil.com/jwks.json"}
// Server fetches attacker's JWKS → validates with attacker's key
//
// Defense: Never fetch keys from the token's jku/x5u claims
// Whitelist your IdP's JWKS URL in server configuration

4. Missing Claim Validation

// DANGEROUS: Only checking signature, not claims
// Token could be expired, wrong audience, wrong issuer
//
// Always validate: exp, iss, aud at minimum
jwt.verify(token, publicKey, {
  algorithms: ['RS256'],
  issuer: 'https://auth.example.com',
  audience: 'https://api.example.com',
  clockTolerance: 30, // 30 seconds for clock skew
});

FAANG Interview Questions

Q1: Explain how JWT works and why it's useful for microservices.
A JWT is a signed JSON payload with three base64url-encoded parts: header (algorithm + key ID), payload (claims like user ID, role, expiry), and signature. The auth server signs the JWT with its private key (RS256). Any microservice can verify the JWT using the public key from the JWKS endpoint — without calling the auth server. This is the key benefit for microservices: stateless verification. Each service independently validates the token by checking the signature, expiration, issuer, and audience. No shared session store, no inter-service auth calls. The trade-off: you can't revoke a JWT instantly because there's no central check. Solutions: short expiry (5 min) so stolen tokens expire quickly, or a lightweight token blacklist (Redis set of jti values) that services check — this re-introduces state but only for revoked tokens, which is a small set.
Follow-up: How do you handle JWT revocation at scale?
Q2: What are the top JWT security pitfalls?
Five critical ones: (1) Algorithm confusion — accepting 'alg: none' or letting the token header dictate the verification algorithm. Fix: whitelist algorithms explicitly. (2) Not validating claims — checking signature but ignoring exp, iss, aud. A valid signature from the wrong issuer or an expired token should be rejected. (3) Storing sensitive data in payload — JWT payload is simply base64 encoded, not encrypted. Anyone can decode it. Never put passwords, SSNs, or secrets in JWT claims. Use JWE if you need encrypted claims. (4) Using HS256 in microservices — the shared secret means every service can forge tokens. Use RS256 so only the auth server can sign. (5) Infinite token lifetime — long-lived JWTs without refresh token rotation give attackers a large window. Use short-lived access tokens (5-15 min) with refresh token rotation.
Follow-up: How does the kid header prevent key rotation downtime?
Q3: How does JWKS work and why is it important?
JWKS (JSON Web Key Set) is a JSON document published at a well-known URL (/.well-known/jwks.json) by the authorization server. It contains an array of public keys, each with a kid (key ID), kty (key type), algorithm, and the key material (n and e for RSA). When a service receives a JWT, it reads the kid from the JWT header, fetches the JWKS (cached with TTL), finds the matching key, and verifies the signature. This enables zero-downtime key rotation: the auth server starts signing with a new key (kid-2), publishes both kid-1 and kid-2 in JWKS, services start using kid-2 for new tokens while still validating kid-1 for existing tokens. After old tokens expire, remove kid-1 from JWKS. Services should cache JWKS with a reasonable TTL (e.g., 1 hour) and refetch when they encounter an unknown kid — this handles rotation without manual intervention.
Follow-up: What happens if the JWKS endpoint is down?

1. JWT Verification (Node.js)

import jwt from 'jsonwebtoken';
import jwksClient from 'jwks-rsa';

const client = jwksClient({
  jwksUri: 'https://auth.example.com/.well-known/jwks.json',
  cache: true,
  cacheMaxAge: 3600000, // 1 hour
});

function getKey(header, callback) {
  client.getSigningKey(header.kid, (err, key) => {
    if (err) return callback(err);
    callback(null, key.getPublicKey());
  });
}

function verifyToken(token) {
  return new Promise((resolve, reject) => {
    jwt.verify(token, getKey, {
      algorithms: ['RS256'],
      issuer: 'https://auth.example.com',
      audience: 'https://api.example.com',
      clockTolerance: 30,
    }, (err, decoded) => {
      if (err) return reject(err);
      resolve(decoded);
    });
  });
}

2. Client-Side JWT Decode (No Verification)

// Decode payload for display purposes (NOT security)
// Never trust decoded claims without server verification

function decodeJwt(token) {
  const [, payload] = token.split('.');
  const json = atob(payload.replace(/-/g, '+').replace(/_/g, '/'));
  return JSON.parse(json);
}

function isExpired(token) {
  const { exp } = decodeJwt(token);
  return Date.now() >= exp * 1000;
}

// Usage: show user profile from token claims
const claims = decodeJwt(accessToken);
// { sub: "user_123", email: "...", role: "admin" }

JWT Validation Checklist

✅ Whitelist algorithms: { algorithms: ['RS256'] }
✅ Validate issuer (iss) matches your auth server
✅ Validate audience (aud) matches your API
✅ Check expiration (exp) with clock tolerance (30s)
✅ Use RS256 for microservices (not HS256)
✅ Fetch keys from cached JWKS (not token's jku header)
✅ Never accept alg: "none"
✅ Never store secrets in JWT payload
✅ Short expiry: 5-15 minutes for access tokens
✅ Include jti for replay prevention (optional)
✅ Rotate signing keys via JWKS with kid overlap period
