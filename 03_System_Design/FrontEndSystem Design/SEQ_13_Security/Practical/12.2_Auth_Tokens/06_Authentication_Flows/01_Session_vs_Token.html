Architecture Flows

// SESSION FLOW:
// 1. Client → POST /login {user, pass}
// 2. Server: create session in Redis, set Set-Cookie: sid=abc123; HttpOnly; Secure
// 3. Client → GET /api/data (Cookie: sid=abc123 auto-attached)
// 4. Server: lookup session in Redis → return data

// TOKEN FLOW:
// 1. Client → POST /login {user, pass}
// 2. Server: create JWT, return { token: "eyJ..." }
// 3. Client stores token (memory/cookie/localStorage)
// 4. Client → GET /api/data (Authorization: Bearer eyJ...)
// 5. Server: verify JWT signature → return data

// HYBRID (Best practice for SPAs):
// Short-lived JWT (15min) + Refresh token in HttpOnly cookie
// Access token in memory (XSS-safe), refresh in cookie (CSRF-safe with SameSite)

Google Senior Frontend — Authentication

Q: You're building a new SPA. Sessions or tokens? Justify your choice.

For a modern SPA: Hybrid approach. Access token (JWT, 15min TTL) stored in JavaScript memory (closure or module-scoped variable — not localStorage). Refresh token in HttpOnly, Secure, SameSite=Strict cookie. Why: Memory storage is immune to XSS persistence (cleared on page reload). HttpOnly cookie is immune to XSS theft. SameSite=Strict prevents CSRF. Short access token limits damage window. This is what Google uses for many of their SPAs.

Q: How does Google handle session management at scale?

Google uses a layered approach: (1) SID cookie for google.com domain (session identifier). (2) SSID/HSID cookies for secure-only sessions. (3) Server-side session store (Spanner/Bigtable) with the actual session data. (4) Anti-session-fixation: session ID rotates on privilege changes. (5) Device fingerprinting for anomaly detection. (6) 2FA challenges on suspicious activity. The key insight: Google treats cookies as opaque identifiers, with all the intelligence server-side.
