OAuth Attack Surface

// 1. OPEN REDIRECT via redirect_uri
// If auth server doesn't strictly validate redirect_uri:
/authorize?redirect_uri=https://evil.com/steal // ← token sent to attacker
// Fix: Exact match of pre-registered redirect URIs. No wildcards.

// 2. CSRF on OAuth Callback
// Attacker initiates OAuth with THEIR account
// Tricks victim into completing the callback
// Victim's app is now linked to attacker's account!
// Fix: State parameter. Always verify state on callback.

// 3. Authorization Code Injection
// Attacker steals a code and replays it in their own session
// Fix: PKCE binds code to the original requester.

// 4. Token Leakage via Referrer
// Implicit flow: token in URL fragment
// If page has external links/images → token leaks in Referer header
// Fix: Use Auth Code flow. Set Referrer-Policy: no-referrer.

// 5. Insufficient Scope Validation
// App requests 'read' scope but server grants 'read write'
// Fix: Validate returned scope against requested scope.

// 6. Token Substitution (Confused Deputy)
// Attacker gets access_token from one resource
// Uses it on another resource that accepts the same token
// Fix: Validate token audience (aud claim).

Defense Checklist

// OAuth Implementation Security Checklist:

✅ 1. Exact redirect_uri validation (no wildcards, no substrings)
✅ 2. State parameter for CSRF protection
✅ 3. PKCE for code exchange protection
✅ 4. Short-lived authorization codes (10 min, single-use)
✅ 5. Token exchange server-side (client_secret never in browser)
✅ 6. Validate id_token: iss, aud, exp, nonce
✅ 7. Minimum necessary scopes
✅ 8. Referrer-Policy: no-referrer (prevent token leakage)
✅ 9. Token audience validation
✅ 10. Secure token storage (in-memory or HttpOnly cookie)
✅ 11. Token revocation on logout
✅ 12. Rate limit token endpoint

Google Senior Frontend — OAuth Vulnerabilities

Q: You're reviewing an OAuth integration that uses redirect_uri=https://app.com/*. What's the risk?

Critical risk: Any path on app.com can receive the authorization code. If there's an open redirect on any endpoint (e.g., /redirect?url=evil.com), an attacker chains: (1) Start OAuth with redirect_uri=https://app.com/redirect?url=https://evil.com, (2) Auth server allows it (matches wildcard), (3) Code is sent to app.com/redirect which forwards to evil.com with the code in the URL. Fix: Register exact redirect URIs only (https://app.com/oauth/callback). Even path-prefix matching (/oauth/*) is risky — a single unrelated endpoint under that path could be exploited.
