navigator.credentials.create() — Full Breakdown

const credential = await navigator.credentials.create({
  publicKey: {
    // Random challenge from server (prevents replay)
    challenge: serverChallenge,

    // Relying Party — your website
    rp: {
      id: "example.com",     // Domain (or registrable suffix)
      name: "My App"           // Display name
    },

    // User info — stored in authenticator
    user: {
      id: userIdBytes,              // Unique, random, NOT email
      name: "alice@example.com", // For display in chooser
      displayName: "Alice"        // Friendly name
    },

    // Acceptable algorithms (server preference order)
    pubKeyCredParams: [
      { alg: -7, type: "public-key" },   // ES256 (preferred)
      { alg: -257, type: "public-key" }  // RS256 (fallback)
    ],

    // Authenticator requirements
    authenticatorSelection: {
      authenticatorAttachment: "platform",  // built-in only
      residentKey: "required",             // discoverable
      userVerification: "required"          // must verify user
    },

    // Prevent duplicate registrations
    excludeCredentials: existingCredentials,

    timeout: 120000,        // 2 minutes
    attestation: "none"     // don't need hardware proof
  }
});

Registration Response Structure

// credential (PublicKeyCredential) contains:

credential.id          // Base64URL credential ID
credential.rawId       // ArrayBuffer credential ID
credential.type        // Always "public-key"
credential.response    // AuthenticatorAttestationResponse

// credential.response contains:
.clientDataJSON        // { type, challenge, origin, crossOrigin }
.attestationObject     // CBOR-encoded: { fmt, attStmt, authData }

// authData breakdown (binary):
// [32 bytes] rpIdHash — SHA-256 of RP ID
// [1 byte]   flags — UP, UV, AT, ED bits
// [4 bytes]  signCount — replay counter
// [variable] attestedCredData — AAGUID + credentialId + publicKey

// Server must verify:
// 1. challenge matches what was issued
// 2. origin matches expected (phishing protection!)
// 3. rpIdHash is SHA-256 of expected RP ID
// 4. User Present (UP) flag is set
// 5. User Verified (UV) flag matches requirements
// 6. Extract and store public key + credential ID

Q: Why does user.id need to be random bytes, not the email?

The user.id (user handle) is stored in the authenticator and returned during authentication. If you use email: (1) Privacy — the authenticator reveals the user's email on every authentication. (2) Immutability — if user changes email, you need to update all their credentials. (3) Spec compliance — user.id is a byte sequence, max 64 bytes. Use a random UUID or database ID encoded as bytes. The user.name (email) is only for display in the credential chooser — it's not used for verification. Google generates a random 16-byte user handle per account.
