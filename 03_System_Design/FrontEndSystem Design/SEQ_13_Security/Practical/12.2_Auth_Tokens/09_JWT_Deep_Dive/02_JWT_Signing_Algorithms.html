Why Asymmetric > Symmetric for Microservices

// HS256 (Symmetric): Same key signs AND verifies
// Problem: Every microservice that verifies needs the secret
// If ANY service is compromised → attacker can forge tokens

// RS256/ES256 (Asymmetric): Different keys for sign vs verify
// Auth service: has private key (signs tokens)
// Other services: have public key (verify only)
// If a service is compromised → they can verify but NOT forge

// Key distribution:
// JWKS endpoint: https://auth.myapp.com/.well-known/jwks.json
// Services fetch public keys from here. No secret sharing needed.

The "alg: none" Attack

// CVE-2015-9235 — one of the most famous JWT attacks

// Legitimate token:
{"alg": "RS256"}.{payload}.{valid signature}

// Attacker modifies:
{"alg": "none"}.{payload with role: "admin"}.

// Vulnerable library sees alg:none → skips verification!
// Attacker can set any claims without signing.

// DEFENSE:
const decoded = jwt.verify(token, publicKey, {
  algorithms: ['RS256'], // ← WHITELIST allowed algorithms
  // NEVER let the token dictate which algorithm to use
});

// Another variant: Algorithm Confusion Attack
// Server expects RS256 (asymmetric)
// Attacker sends: alg: "HS256" with public key as HMAC secret
// Public key is… public! Attacker can compute valid HMAC.
// Fix: Always whitelist algorithms. Never accept HS* on RS* server.

Q: Your team is debating HS256 vs RS256 for a microservices architecture. What's your recommendation?

RS256 (or better, ES256). Reasoning: (1) Key distribution — with HS256, every service needs the shared secret. That's N copies of a critical secret. One breach = total compromise. With RS256, only the auth service has the private key. Others get the public key via JWKS endpoint. (2) Key rotation — with JWKS + kid (Key ID in header), you can rotate keys without downtime. Services cache the JWKS and refetch when they see an unknown kid. (3) Performance — RS256 verification is slower than HS256, but ES256 is comparable to HS256 for verification while being asymmetric. (4) Zero trust — in a zero-trust architecture, services shouldn't be able to forge tokens for other services. Asymmetric signing enforces this.
