Three Parts of a JWT

// A JWT is three Base64URL-encoded sections separated by dots:
// HEADER.PAYLOAD.SIGNATURE

// 1. HEADER — algorithm & token type
{
  "alg": "RS256",     // signing algorithm
  "typ": "JWT",       // token type
  "kid": "abc123"     // key ID (for key rotation)
}

// 2. PAYLOAD — claims (data)
{
  "sub": "user123",       // subject (who)
  "iss": "myapp.com",     // issuer (who created)
  "aud": "api.myapp.com", // audience (intended for)
  "exp": 1678886400,       // expiration (Unix timestamp)
  "iat": 1678882800,       // issued at
  "role": "admin"         // custom claim
}

// 3. SIGNATURE — integrity proof
// HMAC-SHA256 or RSA-SHA256 of:
//   base64url(header) + "." + base64url(payload)
// Anyone can READ a JWT. Only the signer can CREATE a valid one.

// ⚠️ JWT is NOT encrypted — it's just base64 encoded!
// Anyone can decode it. Never put secrets in the payload.

Registered Claims (RFC 7519)

// Registered claims have defined semantics:

"iss" // Issuer — who created the token
       // Verify: matches expected issuer

"sub" // Subject — who the token is about
       // Usually a user ID. NEVER use email (can change).

"aud" // Audience — who should accept this token
       // Prevents token reuse across different APIs
       // Can be string or array: ["api.myapp.com", "admin.myapp.com"]

"exp" // Expiration — when token becomes invalid
       // Unix timestamp. Typical: 15 min for access, 7 days for refresh

"nbf" // Not Before — token not valid before this time
       // Use for scheduled activation

"iat" // Issued At — when token was created
       // Useful for detecting old tokens

"jti" // JWT ID — unique identifier for this token
       // Use for revocation tracking and replay prevention

// Custom claims — your app-specific data:
"role", "permissions", "org_id", "tenant"
// Keep minimal — every claim adds to token size

Google Senior Frontend — JWT

Q: Why shouldn't you put sensitive data in a JWT payload?

JWTs are signed, not encrypted. The payload is just Base64URL-encoded — anyone can decode it with atob(). If a JWT leaks (via logs, URL, referrer, XSS), all claims are readable. Never include: passwords, SSNs, credit card numbers, API keys, internal IDs that reveal architecture. If you need encrypted tokens, use JWE (JSON Web Encryption), but it adds complexity and size. Better approach: Keep JWTs minimal (sub, exp, role). Look up sensitive data server-side using the sub claim.

Q: JWT vs opaque session token — when to use which?

JWT: Stateless, self-contained. Good for: microservices (no shared session store), serverless, API-to-API. Tradeoffs: Can't revoke instantly (until expiry), larger payload (1KB+ vs 32 bytes), claims are visible. Opaque token: Random string that maps to server-side session. Good for: monoliths, when you need instant revocation, when claims change frequently. Tradeoffs: Requires session store (Redis), every request needs a lookup. Google's approach: Short-lived JWTs (5 min) + server-side session for revocation. The JWT carries role/permissions for microservices, but the session store is the source of truth for revocation.
