Multi-Tab Auth Challenges

// Problem: User has multiple tabs of your app open

// Challenge 1: Token refresh
// Tab A refreshes → new token. Tab B has old token → 401
// With rotation: Tab B's refresh uses invalidated token → FAIL

// Challenge 2: Logout
// User logs out in Tab A. Tab B still shows authenticated UI.
// User thinks they're logged out but Tab B can still make requests.

// Challenge 3: Login as different user
// User switches accounts in Tab A.
// Tab B still shows old user's data → confusion + privacy issue.

// Solutions:
// 1. BroadcastChannel API — purpose-built for cross-tab comms
// 2. localStorage 'storage' event — fires cross-tab
// 3. SharedWorker — shared process across tabs
// 4. Service Worker — intercepts all fetches

BroadcastChannel Implementation

// Create a shared auth channel
const authChannel = new BroadcastChannel('auth');

// Tab that performs refresh:
async function refreshAndBroadcast() {
  const { accessToken } = await refreshTokens();
  // Broadcast to ALL other tabs
  authChannel.postMessage({
    type: 'TOKEN_REFRESHED',
    accessToken,
    timestamp: Date.now()
  });
}

// Tab that logs out:
function logoutAndBroadcast() {
  clearTokens();
  authChannel.postMessage({ type: 'LOGOUT' });
}

// ALL tabs listen:
authChannel.onmessage = (event) => {
  switch (event.data.type) {
    case 'TOKEN_REFRESHED':
      setAccessToken(event.data.accessToken);
      // Don't refresh ourselves — use the broadcasted token
      break;
    case 'LOGOUT':
      clearTokens();
      redirectToLogin();
      break;
    case 'USER_CHANGED':
      window.location.reload(); // reload with new user
      break;
  }
};

// Cleanup on tab close:
window.addEventListener('beforeunload', () => authChannel.close());

Google Senior Frontend — Multi-Tab Auth

Q: Design a complete multi-tab authentication system.

Architecture: (1) Auth State Manager — singleton per tab. Holds current access token in memory (not localStorage — XSS safe). (2) BroadcastChannel — cross-tab event bus. Events: TOKEN_REFRESHED, LOGOUT, USER_CHANGED. (3) Leader Election — only one tab refreshes tokens. Use Web Locks API: navigator.locks.request('auth-refresh', {ifAvailable: true}, ...). The tab that acquires the lock is the leader. Leader refreshes and broadcasts. Followers just listen. (4) Token Storage: Access token — JavaScript memory only. Refresh token — HttpOnly Secure cookie (server manages). Token metadata — sessionStorage for per-tab state. (5) Failure handling: If leader tab closes, next tab to need refresh becomes new leader. If BroadcastChannel not supported: fallback to localStorage events. If all else fails: each tab refreshes independently with grace period on server. (6) Testing: Puppeteer with multiple browser contexts to simulate tabs.
