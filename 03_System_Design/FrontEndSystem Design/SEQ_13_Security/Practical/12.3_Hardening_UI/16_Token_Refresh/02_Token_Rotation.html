Refresh Token Rotation

// Rotation: Every refresh gives a NEW refresh token
// The old refresh token is immediately invalidated

// Without rotation:
// Login → refresh_token_A
// Refresh → new access_token (same refresh_token_A)
// Refresh → new access_token (same refresh_token_A)
// Problem: stolen refresh_token_A works forever

// With rotation:
// Login  → access_1 + refresh_1 (family_id: F1)
// Refresh → access_2 + refresh_2 (refresh_1 invalidated)
// Refresh → access_3 + refresh_3 (refresh_2 invalidated)
// Each refresh token is single-use!

// Server tracks token families:
{
  familyId: "F1",
  tokens: [
    { id: "refresh_1", used: true,  revoked: false },
    { id: "refresh_2", used: true,  revoked: false },
    { id: "refresh_3", used: false, revoked: false } // current
  ]
}

Theft Detection via Reuse

// How rotation detects theft:

// Normal flow:
// User has refresh_2 → uses it → gets refresh_3
// refresh_2 is marked "used"

// Attack scenario:
// 1. Attacker steals refresh_2 (before user uses it)
// 2. User uses refresh_2 → gets refresh_3
//    (refresh_2 marked "used")
// 3. Attacker tries refresh_2 → SERVER DETECTS REUSE!
//    "refresh_2 was already used → THEFT DETECTED"

// Server response to reuse detection:
if (token.used) {
  // THEFT DETECTED!
  // Revoke ENTIRE token family
  await revokeTokenFamily(token.familyId);
  // Both user and attacker must re-authenticate
  // Alert security team
  await alertSecurityTeam(token.userId);
  return res.status(401).json({
    error: 'Refresh token reuse detected'
  });
}

// The "damage" of family revocation:
// User gets logged out → minor inconvenience
// Attacker gets locked out → mission accomplished

Q: What happens if the client crashes after refreshing but before storing the new token?

This is the "lost response" problem. The server issued new tokens and invalidated the old one, but the client never received them. Solutions: (1) Grace period: Don't immediately invalidate the old refresh token. Allow a small window (30-60 seconds) where both old and new tokens work. After grace period, old token is fully revoked. (2) Idempotent refresh: If same refresh token is sent within grace period, return the same new tokens (don't generate another pair). Requires server to cache the response. (3) Transactional rotation: Use database transactions — only mark old token as used after the response is sent successfully. If response fails, rollback. (4) Client-side: Persist tokens before making the refresh request. Use localStorage.setItem as a receipt. If crash during refresh: retry on next load. Google and Auth0 use grace periods (typically 30 seconds).
