CDN Compromise Attack Vectors

// How CDNs get compromised:

// 1. Account hijacking
//    Attacker compromises CDN admin account
//    Replaces files at source

// 2. DNS hijacking
//    Redirect cdn.example.com to attacker's server
//    Serve malicious files from lookalike domain

// 3. BGP hijacking
//    Route CDN's IP traffic through attacker's network
//    MITM at network layer

// 4. Supply chain compromise
//    npm publish of malicious version
//    CDN auto-syncs latest version
//    unpkg, jsdelivr serve from npm registry

// 5. Edge server compromise
//    Individual CDN PoP (Point of Presence) hacked
//    Only users routed to that PoP affected

// Impact without SRI:
//    ❌ Crypto mining in users' browsers
//    ❌ Credential theft (form hijacking)
//    ❌ Credit card skimming (Magecart attacks)
//    ❌ Malware distribution
//    ❌ SEO spam injection

// With SRI:
//    ✅ Browser blocks the modified file
//    ✅ CSP reports the violation
//    ✅ Fallback to self-hosted copy

SRI with Popular CDNs

// ═══ React from cdnjs ═══
<script
  src="https://cdnjs.cloudflare.com/ajax/libs/react/18.2.0/umd/react.production.min.js"
  integrity="sha384-COMPUTED_HASH_HERE"
  crossorigin="anonymous"
></script>

// ═══ Bootstrap from jsdelivr ═══
<link
  rel="stylesheet"
  href="https://cdn.jsdelivr.net/npm/bootstrap@5.3.0/dist/css/bootstrap.min.css"
  integrity="sha384-COMPUTED_HASH_HERE"
  crossorigin="anonymous"
>

// ═══ jQuery from Google CDN ═══
<script
  src="https://ajax.googleapis.com/ajax/libs/jquery/3.7.0/jquery.min.js"
  integrity="sha384-COMPUTED_HASH_HERE"
  crossorigin="anonymous"
></script>

// Important notes:
// 1. Use exact version URLs (not /latest or unversioned)
// 2. crossorigin="anonymous" is REQUIRED for cross-origin SRI
// 3. CDN must serve proper CORS headers (Access-Control-Allow-Origin: *)
// 4. Hash MUST match the exact bytes served (including gzip differences)
//    Note: SRI hashes the decompressed content. Gzip is transparent

CDN Fallback Pattern

// If SRI fails → CDN compromised or down
// Fallback to self-hosted copy:

// Pattern 1: onerror fallback
<script
  src="https://cdn.example.com/lib.js"
  integrity="sha384-HASH"
  crossorigin="anonymous"
  onerror="loadFallback(this, '/static/lib.js')"
></script>

<script>
function loadFallback(el, fallbackSrc) {
  console.warn('CDN failed, loading fallback:', fallbackSrc);
  const script = document.createElement('script');
  script.src = fallbackSrc;
  // No crossorigin needed for same-origin
  // Can add SRI for self-hosted too (defense-in-depth)
  el.parentNode.insertBefore(script, el.nextSibling);
}
</script>

// Pattern 2: Feature detection
<script src="https://cdn/jquery.min.js" integrity="sha384-..." crossorigin="anonymous"></script>
<script>
if (!window.jQuery) {
  document.write('<script src="/fallback/jquery.min.js"><\/script>');
}
</script>

// Pattern 3: Dynamic loader with retry
async function loadWithFallback(primary, fallback) {
  try {
    await loadScript(primary);
  } catch (e) {
    console.warn('Primary failed, trying fallback');
    await loadScript(fallback);
  }
}

Google Senior Frontend — CDN Integrity

Q: How would you design a CDN strategy that balances performance and security?

Layered approach: (1) Self-host critical resources: Your own app bundle, authentication logic, payment forms. No CDN dependency for security-critical code. (2) CDN for libraries with SRI: React, lodash, etc. Versioned URLs + SRI hashes. (3) Fallback chain: CDN → self-hosted copy → graceful degradation. Feature-detect library availability. (4) CSP enforcement: script-src 'self' cdn.jsdelivr.net 'sha384-...'. Restrict which CDNs can serve scripts. (5) CDN monitoring: Automated checks comparing CDN-served content against known hashes. Alert on hash mismatch before users are affected. (6) Version pinning: Never use @latest URLs. Pin to exact versions.Lock file generates SRI manifest. (7) Multi-CDN: Primary and secondary CDN. If Cloudflare is down, fallback to Fastly. (8) Preconnect for performance: . DNS prefetch + TLS handshake happen early. (9) HTTP/2 push: Self-hosted resources can use server push. CDN resources benefit from shared browser cache.
