Secure Fetch Patterns

// ✅ Secure fetch wrapper
async function secureFetch(url, options = {}) {
  const controller = new AbortController();
  const timeout = setTimeout(() => controller.abort(), 10000);

  try {
    const response = await fetch(url, {
      ...options,
      signal: controller.signal,
      credentials: 'same-origin',   // ← not 'include' by default
      headers: {
        'Content-Type': 'application/json',
        'X-Requested-With': 'XMLHttpRequest', // CSRF signal
        ...options.headers
      }
    });

    // Check Content-Type before parsing
    const ct = response.headers.get('content-type');
    if (!ct?.includes('application/json')) {
      throw new Error('Unexpected content type');
    }

    if (!response.ok) {
      const error = await response.json().catch(() => ({}));
      throw { status: response.status, ...error };
    }

    return await response.json();
  } finally {
    clearTimeout(timeout);
  }
}

Safe Error Handling

// ❌ Bad: Expose error details to user
catch (error) {

// ✅ Good: User-friendly messages, detailed server-side logging
catch (error) {
  if (error.name === 'AbortError') {
    showToast('Request timed out. Please try again.');
  } else if (error.status === 401) {
    redirectToLogin();
  } else if (error.status === 403) {
    showToast('You don\'t have permission for this action.');
  } else if (error.status === 429) {
    showToast('Too many requests. Please wait.');
  } else {
    showToast('Something went wrong. Please try again.');
    logToServer({ error: error.message, url, timestamp: Date.now() });
  }
}

Q: Why is credentials: 'include' dangerous by default?

credentials: 'include' sends cookies with cross-origin requests. This means: (1) If your app makes requests to api.example.com, cookies for api.example.com are sent — even from an attacker's page. This is how CSRF works. (2) It requires the server to set Access-Control-Allow-Credentials: true, which weakens CORS (can't use wildcard origins). (3) Best practice: Use credentials: 'same-origin' (default) — only sends cookies to your own origin. For cross-origin APIs: use Authorization header with a bearer token instead of cookies. This is immune to CSRF because the attacker can't read your token.
