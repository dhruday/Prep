Why Lockfiles Matter for Security

// package.json says: "express": "^4.18.0"
// This means: any version >= 4.18.0 and < 5.0.0
// Today npm install gives you 4.18.2
// Tomorrow npm install might give you 4.19.0 (potentially compromised)

// package-lock.json PINS the exact version + integrity hash:
{
  "packages": {
    "node_modules/express": {
      "version": "4.18.2",
      "resolved": "https://registry.npmjs.org/express/-/express-4.18.2.tgz",
      "integrity": "sha512-5/PsL6iGPdfQ/lKM1UuielYgv3BUoJfz1aUwU9vHZ+J7gyvwdQXFEBIEIAxeGf0GIcreATNyBExtalisDbuMqQ=="
    }
  }
}

// npm ci (not npm install!) uses the lockfile EXACTLY
// If integrity hash doesn't match → install FAILS
// This prevents silent package substitution attacks

🧪 Tamper Detection

npm install vs npm ci

npm install:
  • Reads package.json
  • Resolves versions from registry (may get newer versions)
  • Updates package-lock.json if versions changed
  • ⚠️ Can introduce unexpected changes

npm ci (clean install):
  • Reads package-lock.json ONLY
  • Installs exact versions specified
  • Verifies integrity hashes
  • Deletes node_modules first (clean slate)
  • Fails if lock doesn't match package.json
  • ✅ Deterministic, secure, 2-3x faster

Rule: npm ci in CI/CD, npm install only for local development

CI/CD Security Checks

# GitHub Actions — supply chain security pipeline
name: Security Audit
on: [push, pull_request]

jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      # 1. Check lockfile is committed
      - name: Verify lockfile exists
        run: test -f package-lock.json

      # 2. Install with integrity verification
      - name: Clean install
        run: npm ci --ignore-scripts

      # 3. Run security audit
      - name: npm audit
        run: npm audit --audit-level=high

      # 4. Check for known vulnerabilities
      - name: Snyk test
        run: npx snyk test

      # 5. Verify no lockfile changes (detect dependency confusion)
      - name: Check for lockfile drift
        run: |
          git diff --exit-code package-lock.json || \
          (echo "Lockfile was modified during install!" && exit 1)

      # 6. Check for install scripts in new deps
      - name: Check install scripts
        run: |
          npm ls --json | jq '.dependencies | to_entries[] |
          select(.value.scripts.postinstall != null) | .key'

Google Senior Frontend — Lockfiles

Q: A developer commits a lockfile change with 200+ updated packages. How do you review this?

Red flags: (1) Check if resolved URLs changed registries. (2) Look for version jumps >1 major version. (3) Check for new postinstall scripts. (4) Verify integrity hashes are present for all entries. Tools: npm-diff (compare package versions), lockfile-lint (validate lockfile policies), socket.dev (real-time package intelligence). Automate: CI check that compares lockfile changes against an allowlist of expected updates. At Google: dependency updates go through an automated security review bot that checks for new capabilities (network access, file system, child_process) in updated packages.
