Common CORS Error Messages & Fixes

// Error 1: "No 'Access-Control-Allow-Origin' header is present"
Fix: Server must add ACAO header with the requesting origin or *

// Error 2: "The value of the ACAO header must not be the wildcard '*'"
Fix: With credentials:include, use exact origin instead of *

// Error 3: "Request header field X is not allowed by ACAH"
Fix: Add the header to Access-Control-Allow-Headers in preflight response

// Error 4: "Method PUT is not allowed by Access-Control-Allow-Methods"
Fix: Add method to Access-Control-Allow-Methods in preflight

// Error 5: "Response to preflight request doesn't pass access control check"
Fix: OPTIONS handler must return 200/204 with correct CORS headers

// Error 6: "Redirect is not allowed for a preflight request"
Fix: OPTIONS handler must not redirect (301/302). Return 204 directly.

DevTools CORS Debugging Steps

// Step 1: Open Network tab, enable "Preserve log"
// Step 2: Reproduce the CORS error
// Step 3: Look for the OPTIONS request (preflight)
//   - If missing → it's a simple request, check response headers
//   - If present → check its response headers AND status code

// Step 4: In the OPTIONS response, check:
//   Access-Control-Allow-Origin: matches your origin?
//   Access-Control-Allow-Methods: includes your method?
//   Access-Control-Allow-Headers: includes your custom headers?
//   Status: 200 or 204? (not 301, 404, 500)

// Step 5: In the actual response, check:
//   Access-Control-Allow-Origin: still present?
//   Access-Control-Allow-Credentials: true (if using credentials)?

// Pro tip: Use curl to bypass browser CORS and test server directly:
curl -v -X OPTIONS https://api.example.com/endpoint \
  -H "Origin: https://myapp.com" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: Content-Type, Authorization"

Google Senior Frontend — CORS Debugging

Q: A developer says "I fixed CORS by adding a proxy." Is this acceptable?

For local development: yes, webpack-dev-server proxy or Vite proxy is fine for DX. For production: it depends. If you're proxying through your own BFF or API Gateway — great, that's eliminating CORS by design. If using a third-party "CORS proxy" service — absolutely not. It sends your auth tokens through an unknown server, creating a MITM vulnerability. The correct production fix is always: configure CORS properly on the server, or use same-origin architecture.

Q: How would you debug intermittent CORS failures that only happen on some browser versions?

Check: (1) Safari has stricter SameSite handling than Chrome, (2) Older browsers don't support Access-Control-Allow-Headers: * — list headers explicitly, (3) Check if Vary: Origin is set — CDN may cache wrong ACAO, (4) Chrome's "Private Network Access" (PNA) blocks requests from public to private networks — new preflight added in Chrome 104. Use web-platform-tests to verify CORS behavior across engines.
