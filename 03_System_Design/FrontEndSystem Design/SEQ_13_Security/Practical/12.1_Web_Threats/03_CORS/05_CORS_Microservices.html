The CORS Problem in Microservices

In a microservices architecture, the frontend may call 10+ different services. Each service being a different origin creates a CORS nightmare:

Frontend (app.com) → user-service.internal:3001 Frontend (app.com) → order-service.internal:3002 Frontend (app.com) → payment-service.internal:3003 Frontend (app.com) → notification-service.internal:3004 ❌ Each needs CORS config ❌ Preflight for every service = 10+ extra round-trips ❌ Each service must know about frontend origins ❌ Inconsistent CORS policies across teams

Solution: API Gateway

Frontend (app.com) → API Gateway (api.app.com) → backend services ✅ CORS handled once at the gateway ✅ Backend services don't need CORS headers ✅ Single preflight cache for all API calls ✅ Centralized security policy ✅ Can rate-limit, authenticate, and log at the edge

Pattern 1: Same-Origin Proxy (Best)

// Frontend: app.com
// API calls: app.com/api/* → proxied to internal services

// No CORS needed! Same origin = no restrictions
// Next.js example:
// next.config.js
module.exports = {
  async rewrites() {
    return [
      { source: '/api/:path*', destination: 'http://gateway:3000/:path*' }
    ];
  }
};

Pattern 2: API Gateway CORS (Common)

// Gateway handles ALL CORS — backend services don't touch it
// AWS API Gateway / Kong / Nginx / Envoy

// Nginx example:
location /api/ {
  if ($request_method = 'OPTIONS') {
    add_header 'Access-Control-Allow-Origin' $allowed_origin;
    add_header 'Access-Control-Allow-Methods' 'GET, POST, PUT, DELETE';
    add_header 'Access-Control-Allow-Headers' 'Content-Type, Authorization';
    add_header 'Access-Control-Max-Age' 86400;
    return 204;
  }
  proxy_pass http://backend;
  add_header 'Access-Control-Allow-Origin' $allowed_origin always;
}

Pattern 3: BFF (Backend for Frontend)

// Each frontend has its own backend that handles CORS
// Web BFF: handles CORS for web app
// Mobile BFF: no CORS needed (native apps don't have SOP)
// Admin BFF: different CORS policy for admin origins

// This isolates CORS policy per consumer
// Google uses this pattern: YouTube Web BFF, YouTube Mobile BFF, etc.

Google Senior Frontend — CORS Architecture

Q: Design the CORS strategy for a new Google Cloud service with web console + API + mobile app.

Web console (console.cloud.google.com): Same-origin proxy via the web server — all API calls go through /api/* prefix, proxied to internal services. No CORS needed. Public API (developers.google.com/cloud): Requires CORS for browser-based clients. Use API Gateway with per-project origin allowlist stored in config. OAuth token-based auth (no cookies) simplifies CORS. Mobile: No SOP, no CORS needed — direct API access with Bearer tokens.

Q: A microservices team accidentally deployed a service with ACAO:* and credentials:true. What's the blast radius?

Blast radius: If the service handles any authenticated requests, any website can make credentialed requests and read responses — stealing user data. Mitigation: (1) Browser actually blocks ACAO:* with credentials:true, so it's broken, not exploitable. But if they "fixed" it by echoing Origin → then it IS exploitable. (2) This is why CORS should be at the gateway, not per-service. (3) Add an infrastructure-level check: reject any response from backend services that contains CORS headers (the gateway adds them).
