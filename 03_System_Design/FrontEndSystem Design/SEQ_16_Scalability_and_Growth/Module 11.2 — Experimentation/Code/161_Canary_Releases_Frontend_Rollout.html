Canary releases — progressive traffic shifting

A canary release routes a small percentage of users (1%, 5%, 10%) to the new version before full rollout. Named after "canary in a coal mine" — if the canary dies (errors spike), you roll back before all users are affected. For frontend, this means serving different JS/CSS bundles or enabling different feature flags to different user segments.

Frontend canary mechanisms
  • CDN routing: Cloudflare Worker routes % of requests to v2 origin
  • Feature flags: LaunchDarkly/Unleash toggles at component level
  • A/B cookie: Server sets variant cookie at edge; JS reads it
  • User cohort: hash(userId) % 100 < rolloutPercent
  • Browser strategy: different <script> src based on header
Rollout phases (typical)
0% → internal only (employees)
1% → canary cohort (opt-in beta)
5% → ring 1 (stable early adopters)
25% → ring 2 (monitor error rate)
50% → ring 3 (compare metrics)
100% → ship to all users
❌ error spike → immediate rollback

Feature flag implementation + user cohort routing

// Deterministic user cohort (same user always gets same variant)
function getUserVariant(userId: string, featureKey: string, rolloutPct: number): 'control' | 'treatment' {
  const hash = cyrb53(`${userId}:${featureKey}`);  // stable hash
  return (hash % 100) < rolloutPct ? 'treatment' : 'control';
}

// React hook that reads from feature flag service
function useFeatureFlag(key: string): boolean {
  const { userId } = useUser();
  return useMemo(() => {
    const flags = window.__FEATURE_FLAGS__ || {};     // injected at edge
    if (flags[key] === undefined) return false;    // default off
    if (typeof flags[key] === 'boolean') return flags[key];
    // percentage rollout
    return getUserVariant(userId, key, flags[key]) === 'treatment';
  }, [key, userId]);
}

// Usage
function ProductPage() {
  const showNewCheckout = useFeatureFlag('new-checkout-v2');
  return showNewCheckout ? <CheckoutV2 /> : <CheckoutV1 />;
}
