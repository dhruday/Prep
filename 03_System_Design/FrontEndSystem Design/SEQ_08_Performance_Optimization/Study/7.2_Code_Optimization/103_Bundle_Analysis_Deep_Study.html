1. Why Bundle Analysis Matters

// The #1 reason apps are slow: too much JavaScript
//
// Typical React app sends 300-800KB of JS (gzipped: 80-250KB)
// Problem: developers ADD code but never AUDIT what's already there
//
// Common discoveries from bundle analysis:
// - moment.js: 300KB (includes ALL locales, you need 1)
// - lodash: 70KB (you use 3 functions, 6KB needed)
// - Entire icons library: 200KB (you use 10 icons)
// - Debug/dev code in production build
// - Duplicate dependencies (react-dom + preact-compat)
// - Polyfills for features all your users' browsers support
//
// Real impact at scale:
// - Each 1KB of JS costs ~1ms of main thread time on mobile
// - 200KB reduction → 200ms faster TTI
// - Walmart: 100ms improvement = +1% revenue
// - Pinterest: 40% less JS → 15% more search traffic

2. What Bundle Analyzers Show

// Bundle analyzers visualize a TREEMAP of your output:
//
// ┌─────────────────────────────────────────────────┐
// │                 main.js (250KB)                  │
// │  ┌──────────────┐ ┌───────────┐ ┌────────────┐  │
// │  │  react-dom    │ │  lodash   │ │  your code │  │
// │  │  (120KB)      │ │  (70KB)   │ │  (60KB)    │  │
// │  └──────────────┘ └───────────┘ └────────────┘  │
// └─────────────────────────────────────────────────┘
//
// Three size metrics:
// 1. Stat size:    Raw output size (before minification)
// 2. Parsed size:  After minification (what the browser parses)
// 3. Gzipped size: Over-the-wire size (what user downloads)
//
// Always optimize for PARSED size (parse cost is the bottleneck)
// Gzip is for network transfer, but CPU still parses full file

3. Three Sizes of JavaScript

Size TypeWhat It IsWhy It Matters
Transfer Size (gzip/brotli)Compressed bytes over networkAffects download time, data usage
Parsed Size (uncompressed)Raw bytes browser must parseAffects parse/compile time (CPU)
Execution CostTime to run module codeAffects TTI, blocks main thread
A 100KB gzipped file might be 400KB parsed. On a budget phone, parsing 400KB takes ~400ms. This is why reducing parsed size matters more than just reducing transfer size.

Tool 1: webpack-bundle-analyzer

// Installation
npm install --save-dev webpack-bundle-analyzer

// webpack.config.js
const { BundleAnalyzerPlugin } = require('webpack-bundle-analyzer');

module.exports = {
  plugins: [
    new BundleAnalyzerPlugin({
      analyzerMode: 'static',  // Generates HTML report
      reportFilename: 'bundle-report.html',
      openAnalyzer: false,
      defaultSizes: 'parsed',  // Show parsed size by default
    }),
  ],
};

// Or run ad-hoc:
npx webpack --profile --json=stats.json
npx webpack-bundle-analyzer stats.json

FAANG Interview Questions

Q1: How would you reduce the JavaScript bundle size of a large React application?
Systematic approach: First, analyze — run webpack-bundle-analyzer to visualize what's in the bundle. Common wins: (1) Replace heavy libraries — moment.js (300KB) → date-fns or dayjs (2KB per function). Lodash → lodash-es with tree shaking, or per-function imports. (2) Code splitting — React.lazy for route-level splitting, dynamic import for heavy components (charts, editors). Target: initial bundle under 170KB gzipped. (3) Tree shaking — ensure all deps have ESM builds, add "sideEffects": false, avoid barrel file re-exports. (4) Purge unused CSS — Tailwind's purge, PurgeCSS. (5) Modern targets — set browserslist targets to modern browsers, avoid shipping polyfills for features all target browsers support. (6) Compression — Brotli (10-20% smaller than gzip) for static assets. (7) CI enforcement — size-limit checks on every PR to prevent regression. At Google, a 50KB reduction in JS bundle on a high-traffic page can save terabytes of monthly bandwidth.
Follow-up: How do you handle the tradeoff between bundle size and number of HTTP requests?
Q2: Explain the difference between gzipped size and parsed size. Which matters more for performance?
Gzipped size is the compressed transfer size — what downloads over the network. A 400KB JS file might compress to 100KB with gzip or 80KB with Brotli. This affects download time. Parsed size is the uncompressed bytes that the JavaScript engine must parse and compile into bytecode. The browser decompresses 80KB back to 400KB, then V8 must parse all 400KB. On a flagship phone, parsing is ~1MB/sec. On a budget Android, it's ~200KB/sec. So 400KB parsed takes 2 seconds on a budget phone. For performance, PARSED size matters more because: (1) download usually finishes first (during HTML parsing), but parsing blocks the main thread; (2) you can improve download with CDN/HTTP2, but parsing hits CPU limits on the device; (3) execution cost compounds — more code = more to parse, compile, AND execute. The optimization focus should be: reduce what ships, not just how it's compressed.
Follow-up: How does V8's code caching optimization affect this analysis?

Bundle Analysis Checklist

✅ webpack-bundle-analyzer report generated on each build
✅ size-limit checks in CI (block PR if budget exceeded)
✅ Initial JS bundle < 170KB gzipped
✅ Vendor chunk separated (react-dom, router)
✅ No duplicate packages (run: npm ls --all)
✅ All heavy libraries have ESM alternatives
✅ Tree shaking verified (search for unused exports in output)
✅ Dynamic imports for routes and heavy components
✅ Source maps uploaded to Sentry, not served publicly
✅ Brotli compression enabled on CDN/server
