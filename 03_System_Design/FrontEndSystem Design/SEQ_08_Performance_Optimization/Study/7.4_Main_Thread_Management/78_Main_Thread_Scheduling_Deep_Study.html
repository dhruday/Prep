1. Why the Main Thread Is the Bottleneck

// The browser's main thread handles EVERYTHING:
//
// 1. JavaScript execution (your code)
// 2. Style recalculation
// 3. Layout (reflow)
// 4. Paint + Composite
// 5. DOM parsing
// 6. Event handling (click, input, scroll)
// 7. Garbage collection
//
// All on ONE thread. If JS runs for 200ms:
// → No clicks processed for 200ms
// → No animations for 200ms
// → User sees "frozen" UI
//
// Frame budget at 60fps: 16.67ms per frame
// Frame budget at 120fps: 8.33ms per frame
//
// Layout of one frame (ideal):
// ┌──────────────────── 16.67ms ────────────────────┐
// │ JS │ Style │ Layout │ Paint │ Composite │ IDLE  │
// │ 5ms│ 1ms   │ 2ms    │ 2ms   │ 1ms       │ 5.67ms│
// └────┴───────┴────────┴───────┴───────────┴───────┘
//
// Reality with heavy JS:
// ┌──────────────── 16.67ms ─────────┐
// │      JavaScript (50ms)           │← Frame dropped!
// │ ████████████████████████████████████████████████│
// └──────────────────────────────────────────────────┘

2. The Event Loop Model

// Simplified event loop algorithm:
//
// while (true) {
//   1. Pick ONE task from the task queue (macrotask)
//      Sources: setTimeout, setInterval, I/O, UI events, MessageChannel
//
//   2. Execute it to completion (cannot be interrupted!)
//
//   3. Run ALL microtasks until the microtask queue is empty
//      Sources: Promise.then, queueMicrotask, MutationObserver
//      ⚠️ Microtasks can enqueue more microtasks → starvation risk!
//
//   4. If it's time to render (~16.67ms since last):
//      a. Run requestAnimationFrame callbacks
//      b. Recalculate styles
//      c. Layout
//      d. Paint
//      e. Composite
//
//   5. If idle, run requestIdleCallback
// }
//
// KEY INSIGHT: Tasks run to completion
// A 200ms task BLOCKS everything for 200ms
// The browser CANNOT interrupt your JavaScript
// Only YOU can yield back to the event loop

Task Queue Priority

// Modern browsers have MULTIPLE task queues with priorities:
//
// Priority (high → low):
//
// 1. MICROTASKS (not really a "task queue" — runs between tasks)
//    Promise.then, queueMicrotask, MutationObserver
//    Always drain completely before next task
//
// 2. USER INTERACTION tasks
//    Click, keydown, input events
//    Browsers prioritize these for responsiveness
//
// 3. RENDERING tasks
//    requestAnimationFrame callbacks
//    Style/layout/paint
//
// 4. DEFAULT tasks
//    setTimeout(fn, 0), setInterval
//    MessageChannel.port1.onmessage
//    fetch callbacks
//
// 5. IDLE tasks
//    requestIdleCallback
//    Only runs when browser is idle
//
// 6. BACKGROUND tasks
//    scheduler.postTask({ priority: 'background' })
//    Lowest priority, yields to everything

// Practical impact:
// If you start heavy work with setTimeout(heavyWork, 0)
// and the user clicks a button at the same time,
// the click handler runs FIRST (higher priority queue)

Yielding Strategies

// Strategy 1: setTimeout(fn, 0) — yield to task queue
async function processItems(items) {
  for (let i = 0; i < items.length; i++) {
    processItem(items[i]);
    if (i % 100 === 0) {
      await new Promise(r => setTimeout(r, 0));
      // Yields: browser can handle events, render, etc.
    }
  }
}

// Strategy 2: MessageChannel — faster yield (no 4ms clamp)
function yieldToMain() {
  return new Promise(resolve => {
    const ch = new MessageChannel();
    ch.port1.onmessage = resolve;
    ch.port2.postMessage(undefined);
  });
}
// React's scheduler uses this internally

// Strategy 3: requestIdleCallback — run when idle
function processInIdle(items) {
  let i = 0;
  function work(deadline) {
    while (i < items.length && deadline.timeRemaining() > 1) {
      processItem(items[i++]);
    }
    if (i < items.length) requestIdleCallback(work);
  }
  requestIdleCallback(work);
}

// Strategy 4: scheduler.postTask (Chrome 94+)
await scheduler.postTask(() => heavyWork(), {
  priority: 'background',
  signal: AbortSignal.timeout(5000),
});

FAANG Interview Questions

Q1: Explain the browser event loop and how it affects UI responsiveness.
The browser's main thread runs a single-threaded event loop that processes tasks sequentially. Each iteration: (1) dequeue one macrotask (setTimeout, event handler, I/O callback), (2) execute it to completion — JavaScript cannot be preempted, (3) drain all microtasks (Promise.then, queueMicrotask), (4) if ~16.67ms has passed, run requestAnimationFrame callbacks, recalculate styles, layout, paint, composite. The critical insight: if a JavaScript task runs for 200ms, the browser cannot handle user input, run animations, or update the screen for that entire duration. The user sees a "frozen" UI. This is why long tasks (>50ms per Chrome's definition) directly impact INP (Interaction to Next Paint). The fix is to break long tasks into smaller chunks and yield back to the event loop between chunks, allowing the browser to process pending user events and render frames. Yielding strategies include setTimeout(fn, 0), MessageChannel (no 4ms clamp), requestIdleCallback (for non-urgent work), and scheduler.postTask (for priority-based scheduling).
Follow-up: What's the difference between setTimeout(fn, 0) and queueMicrotask(fn)?
Q2: Why does React use MessageChannel instead of setTimeout for scheduling?
Browsers clamp nested setTimeout calls to a minimum of 4ms after the 5th nesting level (HTML spec). React's concurrent mode needs to yield frequently (every 5ms work slice), so a 4ms yield delay would double the overhead. MessageChannel posts a task to the macrotask queue with no minimum delay — the callback runs as soon as the current task completes and any pending higher-priority tasks are processed. This gives React near-zero yield cost while still allowing the browser to handle user interactions and rendering between work slices. React's scheduler creates a MessageChannel, calls port2.postMessage() to schedule the next work slice, and port1.onmessage picks it up. This is also why React can't use microtasks — microtasks (Promise.then) run before the browser can render, so using them to schedule work would still block the rendering pipeline.

Quick Reference

Event Loop Order per iteration:
1. Dequeue ONE macrotask → execute to completion
2. Drain ALL microtasks (Promise, queueMicrotask)
3. requestAnimationFrame callbacks (if render needed)
4. Style → Layout → Paint → Composite
5. requestIdleCallback (if idle time left)

Yielding Methods (fastest → most deferring):
┌─────────────────────┬─────────┬──────────────────────┐
│ Method              │ Latency │ Use Case             │
├─────────────────────┼─────────┼──────────────────────┤
│ queueMicrotask      │ ~0ms    │ ⚠ No yield to render │
│ MessageChannel      │ ~0.1ms  │ Framework schedulers │
│ setTimeout(fn, 0)   │ ~1-4ms  │ General yielding     │
│ requestAnimFrame    │ ~16ms   │ Animation sync       │
│ requestIdleCallback │ varies  │ Non-urgent work      │
│ scheduler.postTask  │ varies  │ Priority-based       │
└─────────────────────┴─────────┴──────────────────────┘
