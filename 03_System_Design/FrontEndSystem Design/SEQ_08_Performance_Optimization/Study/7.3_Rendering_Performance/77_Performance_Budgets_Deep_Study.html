1. What Is a Performance Budget?

// A performance budget is a quantitative LIMIT on a metric
// that a page or app must not exceed.
//
// It's the performance equivalent of a test suite:
// if the budget is broken → the build FAILS / PR is blocked
//
// Why budgets matter:
// ✓ Prevent slow death by 1000 small regressions
//   (each +5KB "doesn't matter" until you're 2MB)
// ✓ Make performance a first-class team concern
// ✓ Shift-left: catch regressions at build time, not in production
// ✓ Align engineering with business (Amazon: +100ms → –1% revenue)
//
// Three budget categories:
//
// 1. QUANTITY budgets
//    - Max JS bundle: 170KB gzipped (Google recommendation)
//    - Max total page weight: 500KB transferred
//    - Max images per page: 1MB
//    - Max third-party scripts: 50KB
//
// 2. TIMING budgets
//    - LCP < 2.5s (Core Web Vital)
//    - INP < 200ms (Core Web Vital)
//    - CLS < 0.1 (Core Web Vital)
//    - TTI < 5s on 3G mobile
//
// 3. RULE budgets
//    - Lighthouse Performance ≥ 90
//    - No render-blocking resources > 1
//    - No images without width/height

2. Setting Budgets: The Science

// Step 1: Baseline measurement
// Run Lighthouse on 3G throttled, mid-tier device
// Use WebPageTest for real device data
//
// Step 2: Competitive analysis
// Measure your top 5 competitors
// Budget should be 20% FASTER than the fastest competitor
// (Tim Kadlec's recommendation)
//
// Step 3: Target device/network
// Google's guidance: budget for a $200 Android phone on 3G
// CPU: ~4x slower than MacBook Pro
// Network: 1.6Mbps, 150ms RTT (Slow 3G)
//
// The ~170KB JS budget comes from:
// - 5s TTI budget on 3G mobile
// - ~1.5s network transfer (170KB gzipped ≈ 500KB parsed)
// - ~3.5s parse + compile + execute on slow CPU
// - Total: ~5s to interactive
//
// Budget allocation for a typical SPA:
//   Framework: 45KB  (React ~42KB gzipped)
//   App code:  50KB  (your features)
//   Libraries: 30KB  (routing, state, utils)
//   Polyfills: 15KB  (modern: near zero)
//   3rd party: 30KB  (analytics, etc.)
//   TOTAL:    170KB  gzipped

Webpack Performance Budget

// webpack.config.js
module.exports = {
  performance: {
    maxAssetSize: 250000,          // 250KB per asset
    maxEntrypointSize: 300000,     // 300KB for entry chunk
    hints: 'error',               // 'warning' | 'error' | false
    assetFilter: (file) =>
      file.endsWith('.js') || file.endsWith('.css'),
  },
};

FAANG Interview Questions

Q1: How would you implement a performance budget system for a large-scale frontend application?
I'd implement a three-layer budget system: (1) Build-time: webpack/Vite performance hints fail the build if any chunk exceeds the budget. bundlesize or size-limit in CI check individual bundles against limits and post PR comments showing delta. (2) Synthetic: Lighthouse CI runs against staging on every PR. Assert on LCP < 2.5s, INP < 200ms, CLS < 0.1, and performance score ≥ 90. This runs on consistent infrastructure (no real-user variance). (3) RUM-based: In production, track p75 and p95 of Core Web Vitals via web-vitals library + analytics. Set alerting thresholds — if p75 LCP crosses 2.5s, page the on-call. For governance: store historical budgets in a config file checked into the repo. Require tech lead approval to increase any budget. Provide an "escape hatch" — if a feature genuinely needs more JS, the team must offset it by removing something else (budget trade-off). For dashboard: display trends over time so the team sees drift before it becomes a crisis.
Follow-up: How do you handle third-party script budgets when marketing wants to add more analytics tags?
Q2: The team keeps breaking performance budgets. How do you create a perf-aware culture?
Three approaches: (1) Visibility: set up a performance dashboard on a TV in the office (or a Slack channel with weekly reports). Show Core Web Vitals trends, bundle size trends, and the budget line. Make it impossible to ignore. (2) Guardrails: integrate bundlesize into PR checks — the PR literally cannot merge if it breaks the budget. This removes "I'll fix it later." Add Lighthouse CI as a required check. (3) Ownership: assign a "perf champion" per team rotation who reviews the weekly report, investigates regressions, and presents findings. At Google, each team has a performance SLO owner. Also: celebrate wins! When someone reduces bundle size by 20KB, highlight it in standup. When LCP improves by 200ms, show the business impact (higher conversion). Culture change is about making performance visible, actionable, and rewarded.

Complete CI Pipeline Example

# .github/workflows/perf-budget.yml
name: Performance Budget
on: [pull_request]

jobs:
  bundle-size:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
      - run: npm ci && npm run build
      - name: Check bundle size
        run: npx size-limit
      - uses: andresz1/size-limit-action@v1
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
  
  lighthouse:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
      - run: npm ci && npm run build
      - name: Lighthouse CI
        run: |
          npm i -g @lhci/cli
          lhci autorun
        env:
          LHCI_GITHUB_APP_TOKEN: ${{ secrets.LHCI_TOKEN }}
