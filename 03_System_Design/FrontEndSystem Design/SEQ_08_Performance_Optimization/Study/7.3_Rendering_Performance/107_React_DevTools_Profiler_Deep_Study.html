1. What the Profiler Measures

// React DevTools Profiler records COMMIT information
//
// A COMMIT = one batch of updates applied to the DOM
//
// For each commit, the profiler captures:
//
// 1. Which components RENDERED (called their render function)
// 2. WHY each component rendered:
//    - "Props changed"
//    - "State changed"
//    - "Context changed"
//    - "Parent rendered" (the most common wasted render)
//    - "Hooks changed"
//
// 3. How LONG each component took to render (in ms)
//    - Self time: just this component's render
//    - Total time: this component + all descendants
//
// 4. How many times each component rendered across all commits
//
// IMPORTANT: Profiler measures RENDER time, not commit time
// Render = "what should change?" (virtual DOM diff)
// Commit = "apply changes to real DOM" (not measured by profiler)
//
// Enable: DevTools Settings → Profiler → "Record why each component rendered"

2. The Profiler API (Programmatic)

// React.Profiler: Built-in component for measuring render cost
// Works in production builds too (with profiling bundle)

import { Profiler } from 'react';

function onRenderCallback(
  id,           // "ProductList" — the profiler's id prop
  phase,        // "mount" | "update" | "nested-update"
  actualDuration, // Time spent rendering this commit (ms)
  baseDuration,   // Estimated time without memoization (ms)
  startTime,      // When React started rendering this commit
  commitTime      // When React committed this update
) {
  // Send to analytics / performance monitoring
  if (actualDuration > 16) { // Over 1 frame budget
    sendToAnalytics({
      component: id,
      phase,
      duration: actualDuration,
      wasted: baseDuration - actualDuration, // Time saved by memo
    });
  }
}

<Profiler id="ProductList" onRender={onRenderCallback}>
  <ProductList items={items} />
</Profiler>

// Nest profilers for granular measurement:
<Profiler id="App" onRender={onRender}>
  <Header />
  <Profiler id="Main" onRender={onRender}>
    <ProductList />
  </Profiler>
</Profiler>

Reading the Flame Graph

// Flame Graph view: each bar = one component
// Width = render time (wider = slower)
// Color: yellow/orange = rendered, gray = did not render
//
// Example flame graph for a commit:
//
// ┌─────────────── App (4.2ms) ───────────────────┐
// │ ┌─ Header (0.1ms) ─┐ ┌── Main (3.8ms) ──────┐│
// │ │ Logo   NavBar     │ │ ┌ ProductList (3.5ms)┐││
// │ │ (gray) (0.1ms)    │ │ │ Item Item Item ... │││
// │ └──────────────────┘ │ └────────────────────┘││
// │                       └──────────────────────┘│
// └───────────────────────────────────────────────┘
//
// Reading this: App took 4.2ms total
// ProductList is the bottleneck at 3.5ms
// Logo was gray = it used React.memo and didn't re-render
//
// Ranked View: sorts components by render time (descending)
// → Immediately shows your slowest components
//
// Interactions View (deprecated in React 18+)
// → Use User Timing API or React's startTransition instead

Common Patterns to Spot

// Pattern 1: "Waterfall of yellow"
// Every component in the tree is yellow (rendered)
// Diagnosis: state too high in tree, no memoization
// Fix: state colocation, React.memo on children
//
// Pattern 2: "One fat bar"
// One component takes 50ms+ to render
// Diagnosis: expensive computation in render
// Fix: useMemo for computation, virtualization for lists
//
// Pattern 3: "Many identical commits"
// 30+ commits in quick succession, same components
// Diagnosis: high-frequency state updates (mouse, scroll, resize)
// Fix: throttle/debounce, useTransition, requestAnimationFrame
//
// Pattern 4: "Gray parent, yellow child"
// Parent didn't render but child did
// Diagnosis: child has its own state or context subscription
// This is usually CORRECT behavior
//
// Pattern 5: actualDuration ≈ baseDuration
// Memoization isn't helping (props always change)
// Diagnosis: unstable references defeating React.memo
// Fix: useCallback/useMemo for props

Chrome Performance Tab + React

// React adds User Timing marks in development mode
// Visible in Chrome DevTools → Performance → Timings lane
//
// Marks you'll see:
//   ⏱ "⚛️ App [mount]"  — component mounting
//   ⏱ "⚛️ App [update]" — component updating
//
// Combining React Profiler + Chrome Performance Tab:
//
// 1. Open Chrome Performance tab
// 2. Click Record
// 3. Interact with the app
// 4. Stop recording
// 5. Look at the "Timings" lane for React marks
// 6. Correlate with Main thread → shows actual JS execution
//
// This tells you:
// - Which React renders caused long tasks
// - Whether the bottleneck is render or commit
// - Whether layout/paint is the real issue

// Custom performance marks for production:
performance.mark('productList-render-start');
// ... render logic
performance.mark('productList-render-end');
performance.measure(
  'ProductList render',
  'productList-render-start',
  'productList-render-end'
);

FAANG Interview Questions

Q1: Walk me through how you'd use React DevTools Profiler to debug a slow interaction.
Step 1: Open React DevTools → Profiler tab. Enable "Record why each component rendered." Click the record button, then perform the slow interaction (e.g., clicking a button, typing). Stop recording. Step 2: Look at the commit list on the right. Each bar represents one commit — taller bars took longer. Click the tallest bar. Step 3: In the flame graph, identify the widest bars — these are the slowest components. Check: is one component taking 50ms+? Or are 100 small components rendering unnecessarily? Step 4: Click a slow component. Check "Why did this render?" If it says "Parent rendered" and the component's output didn't change, wrap it in React.memo. If it says "Props changed," check whether the parent is creating new object/function references — fix with useMemo/useCallback. Step 5: Switch to Ranked view to see all components sorted by render time. The top 3-5 are your optimization targets. Step 6: Apply fixes, re-profile, compare actualDuration before and after.
Follow-up: How would you measure render performance in production where DevTools aren't available?
Q2: What's the difference between actualDuration and baseDuration in the Profiler?
actualDuration is the real wall-clock time React spent rendering the component and its descendants for this specific commit. It accounts for memoization — if some children were skipped via React.memo, their time isn't included. baseDuration is the estimated time to render the entire subtree without any memoization — as if every component re-rendered from scratch. The gap between them tells you how effective your memoization is. If actualDuration ≈ baseDuration, memoization isn't helping (either you have none, or props always change). If actualDuration << baseDuration, memo is working well. Example: baseDuration=50ms, actualDuration=5ms means memo saved 45ms. If you see baseDuration=50ms, actualDuration=48ms in a memo'd component, the memo is being defeated — likely by unstable prop references.

Profiler Quick Reference

React DevTools Profiler Workflow:
1. Settings → Enable "Record why each component rendered"
2. Click Record → Interact → Stop
3. Check commit bars (right side) — tall = slow
4. Flame graph → widest bar = bottleneck
5. Click component → check "Why did this render?"
6. Ranked view → sort by render time

Key metrics per component:
• Self time: just this component
• Total time: this + descendants
• Render count: across all commits

Common fixes by "why rendered" reason:
• "Parent rendered" → React.memo
• "Props changed" → useMemo/useCallback in parent
• "State changed" → state colocation
• "Context changed" → split context

Production profiling:
• React.Profiler component + onRender callback
• React profiling build: react-dom/profiling
• Custom performance.mark() / performance.measure()
• web-vitals library for CWV
