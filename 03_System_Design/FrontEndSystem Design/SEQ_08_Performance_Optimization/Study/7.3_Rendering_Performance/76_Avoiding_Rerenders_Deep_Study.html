Cheat Sheet

1. Three Reasons a React Component Re-Renders

// A component re-renders when:
//
// 1. Its STATE changes (useState, useReducer)
//    setState(newValue) → React schedules re-render
//    Note: setState(sameValue) does NOT re-render (with primitives)
//    BUT: setState({...obj}) ALWAYS re-renders (new reference)
//
// 2. Its PARENT re-renders
//    Parent re-renders → ALL children re-render
//    Even if the child's PROPS haven't changed!
//    This is the #1 source of wasted renders
//
// 3. CONTEXT it consumes changes
//    useContext(MyContext) → re-renders when context value changes
//    Even if you only use 1 field and a DIFFERENT field changed!
//    This is the #2 source of wasted renders
//
// DOES NOT re-render when:
// ✗ Props change (props change BECAUSE parent re-rendered)
// ✗ useRef changes (ref mutations don't trigger renders)
// ✗ Direct DOM manipulation (React doesn't know about it)

2. The Cascade Problem

// One state change at root → entire tree re-renders
//
// App (state: theme) ← setState triggers re-render
// ├── Header        ← re-renders (parent changed)
// │   ├── Logo      ← re-renders (parent changed)
// │   └── NavBar    ← re-renders (parent changed)
// │       ├── Link  ← re-renders (parent changed)
// │       └── Link  ← re-renders (parent changed)
// ├── Main          ← re-renders (parent changed)
// │   ├── ProductList (100 items) ← all 100 re-render!
// │   └── Sidebar   ← re-renders
// └── Footer        ← re-renders
//
// A single theme toggle → 105+ component re-renders
// Most are WASTED — their output is identical
//
// React still reconciles (diffs) everything
// Finding "nothing changed" still costs CPU time
// With 100+ components, this can take 50-200ms

3. Detecting Wasted Renders

// Tool 1: React DevTools Profiler
// Settings → "Highlight updates when component renders"
// Blue border = re-rendered. Yellow/red = expensive render.
//
// Tool 2: React DevTools Profiler (record mode)
// Click Record → interact → Stop
// See flame graph: which components rendered and why
// "Why did this render?": Shows state change, props change, or parent
//
// Tool 3: Custom hook for development
function useRenderCount(name) {
  const count = useRef(0);
  count.current++;
  if (process.env.NODE_ENV === 'development') {
    console.log(`[${name}] renders: ${count.current}`);
  }
}

// Tool 4: React.Profiler component
<React.Profiler id="ProductList" onRender={(id, phase, duration) => {
  if (duration > 16) console.warn(`${id}: ${duration}ms (${phase})`);
}}>
  <ProductList />
</React.Profiler>

Pattern 1: State Colocation (Move State Down)

// ❌ BEFORE: State at root → entire tree re-renders
function App() {
  const [search, setSearch] = useState('');
  return (
    <div>
      <input value={search} onChange={e => setSearch(e.target.value)} />
      <ExpensiveComponent /> {/* Re-renders on every keystroke! */}
      <AnotherExpensive />   {/* Also re-renders! */}
    </div>
  );
}

// ✅ AFTER: Extract state into its own component
function SearchInput() {
  const [search, setSearch] = useState('');
  return <input value={search} onChange={e => setSearch(e.target.value)} />;
}

function App() {
  return (
    <div>
      <SearchInput />         {/* Only this re-renders on keystroke */}
      <ExpensiveComponent />  {/* Unaffected! */}
      <AnotherExpensive />    {/* Unaffected! */}
    </div>
  );
}

Pattern 2: Children as Props (Composition)

// ❌ BEFORE: Scrolling state re-renders children
function ScrollTracker() {
  const [scrollY, setScrollY] = useState(0);
  useEffect(() => {
    const handler = () => setScrollY(window.scrollY);
    window.addEventListener('scroll', handler);
    return () => window.removeEventListener('scroll', handler);
  }, []);
  return (
    <div>
      <ScrollIndicator y={scrollY} />
      <ExpensiveContent />  {/* Re-renders on scroll! */}
    </div>
  );
}

// ✅ AFTER: Accept children as props
function ScrollTracker({ children }) {
  const [scrollY, setScrollY] = useState(0);
  useEffect(() => {
    const handler = () => setScrollY(window.scrollY);
    window.addEventListener('scroll', handler);
    return () => window.removeEventListener('scroll', handler);
  }, []);
  return (
    <div>
      <ScrollIndicator y={scrollY} />
      {children}  {/* children was created by PARENT — doesn't re-render! */}
    </div>
  );
}

// Usage:
<ScrollTracker>
  <ExpensiveContent />  {/* Created in parent scope → stable reference */}
</ScrollTracker>

Pattern 3: React.memo + Stable References

// React.memo skips re-render if props are shallowly equal
// But only works if props are actually STABLE

// ❌ Memo defeated by inline objects/functions:
function Parent() {
  const [count, setCount] = useState(0);
  return (
    <MemoChild
      style={{ color: 'red' }}     {/* New object every render! */}
      onClick={() => doSomething()} {/* New function every render! */}
      items={[1, 2, 3]}             {/* New array every render! */}
    />
  );
}

// ✅ Stable references with useMemo/useCallback:
function Parent() {
  const [count, setCount] = useState(0);
  const style = useMemo(() => ({ color: 'red' }), []);
  const handleClick = useCallback(() => doSomething(), []);
  const items = useMemo(() => [1, 2, 3], []);
  return <MemoChild style={style} onClick={handleClick} items={items} />;
}

Context Optimization Strategies

// Problem: Context changes re-render ALL consumers
// Even if they only use a part of the context that didn't change

// ❌ Monolithic context — everything in one:
const AppContext = createContext({ user: null, theme: 'light', cart: [] });
// Changing cart re-renders components that only need theme!

// ✅ Strategy 1: Split contexts by update frequency
const UserContext = createContext(null);    // Rarely changes
const ThemeContext = createContext('light'); // Changes on toggle
const CartContext = createContext([]);       // Changes often

// ✅ Strategy 2: Memoize context value
function CartProvider({ children }) {
  const [items, setItems] = useState([]);
  const value = useMemo(() => ({ items, setItems }), [items]);
  return <CartContext.Provider value={value}>{children}</CartContext.Provider>;
}

// ✅ Strategy 3: Selector pattern with useSyncExternalStore
function useCartItemCount() {
  const { items } = useContext(CartContext);
  return items.length; // Component still re-renders when items change
}
// For true selectors: use Zustand, Jotai, or useSyncExternalStore

FAANG Interview Questions

Q1: A React app feels sluggish when typing in a search input. How do you diagnose and fix it?
Step 1: Open React DevTools Profiler, enable "Highlight updates when components render." Type in the search input and observe which components flash (re-render). If the entire page lights up on each keystroke, the search state is too high in the tree. Step 2: Check where the state lives. If search state is in a parent that also renders expensive children, those children re-render on every keystroke. Fix: move the search state into a dedicated SearchInput component (state colocation). Step 3: If search results need to be below, use composition — keep the search input as a self-contained component, and use debounced callback to update parent state only after the user stops typing (300ms). Step 4: For the results list, use React.memo + startTransition to mark the filtering as a non-urgent update — React will keep the input responsive and defer the expensive list re-render. Step 5: If the list is large, add virtualization. This combination gives instant input feedback + deferred filtered results + minimal re-renders.
Follow-up: How does React 18's automatic batching help here?
Q2: Explain state colocation vs React.memo. When do you prefer one over the other?
State colocation means moving state closer to where it's used — extract the stateful part into its own component so only that component re-renders. It's a structural change, zero runtime overhead, and it's the preferred approach. React.memo wraps a component to skip re-rendering when props haven't changed — it adds runtime overhead (shallow comparison every render) but doesn't require restructuring. Prefer colocation when: the state is only relevant to one part of the UI (search input, hover state, toggle). The component boundaries naturally separate concerns. Prefer memo when: you can't restructure (state genuinely needed at parent level), a child is expensive and receives stable-ish props, or you're in a list with many items. Best practice: try colocation first (it's free), then composition (children as props), and only then reach for React.memo as a last resort.
Follow-up: How does the React Compiler eliminate the need for manual memoization?

Anti-Render Checklist

✅ State colocated (as low in tree as possible)
✅ Composition pattern for stateful wrappers (children as props)
✅ React.memo on list items and expensive components
✅ Stable references via useMemo/useCallback for memo'd children
✅ Context split by update frequency (auth vs theme vs cart)
✅ Context values memoized with useMemo
✅ startTransition for non-urgent state updates
✅ React DevTools Profiler used to verify optimizations
✅ No inline objects/arrays/functions passed to memo'd children
✅ Consider Zustand/Jotai for granular subscriptions over Context
