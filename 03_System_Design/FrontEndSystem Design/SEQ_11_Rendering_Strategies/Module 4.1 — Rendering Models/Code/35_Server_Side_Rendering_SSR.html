SSR Request Lifecycle

1
Browser requests URL → Request hits server (Node.js / Edge)
2
Server fetches data from DB/API (server-to-server, low latency)
3
Server renders HTML with real data — React's renderToString / renderToPipeableStream
4
Full HTML delivered → browser paints immediately — excellent FCP & LCP
5
JS bundle downloaded & hydration — React attaches event listeners to server HTML (TTFB + TTI gap)
Key insight: FCP comes from the server, making SSR ideal for SEO-critical public pages. But each request triggers a server round-trip — the TTFB is higher if the server is slow.

SSR Pros & Cons

✅ Advantages
Fast FCP and LCP
Full HTML for SEO crawlers
Good on slow client devices
Social media preview cards work
Personalised content per request
❌ Disadvantages
Higher TTFB if server is slow
Server cost scales with traffic
Session/cookie complexity
Hydration mismatch bugs
Hard to cache dynamic pages

SAP context

SAP public-facing product pages (sap.com store, SAP Help Portal) use SSR for SEO. At SAP Labs, Hruday evaluated Next.js App Router SSR for the procurement portal where product pages needed to rank on Google.

Next.js App Router — SSR per-request

// app/products/[id]/page.tsx — runs on server every request
export default async function ProductPage({
  params,
}: {
  params: { id: string };
}) {
  // Direct DB/API call — no useEffect, no client fetch
  const product = await fetchProduct(params.id); // server-side

  return (
    <main>
      <h1>{product.name}</h1>
      <p>{product.description}</p>
      <AddToCartButton id={product.id} /> {/* client component */}
    </main>
  );
}

// Force dynamic (SSR) — no caching
export const dynamic = 'force-dynamic';

// generateMetadata for SEO <head> tags
export async function generateMetadata({ params }) {
  const product = await fetchProduct(params.id);
  return { title: product.name, description: product.summary };
}
