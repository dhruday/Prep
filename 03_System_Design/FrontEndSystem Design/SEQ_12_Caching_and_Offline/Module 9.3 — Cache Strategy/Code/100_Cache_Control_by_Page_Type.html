One caching policy doesn't fit all — tailor by page/resource type

A blanket "cache everything for 1 hour" approach breaks: the login page returns cached credentials, a product page shows sold-out stock as available, and a hashed JS bundle gets double-validated. At SAP, the procurement portal uses distinct cache policies for the HTML shell, API responses, user-data pages, and hashed static assets.

✅ Aggressively cacheable
  • 📦 Hashed JS/CSS bundles → immutable
  • 🖼️ Images/fonts with hash → 1 year
  • 📚 Static documentation pages
  • 🔧 Service worker script
❌ Cannot cache or short TTL
  • 🔐 Auth / profile pages → no-store
  • 💰 Pricing data → 5–30s
  • 🛒 Cart / checkout → no-cache
  • 📄 HTML document → no-cache

Express / Next.js per-route cache headers

// ─── Express: cache headers by route ───
app.get('/api/catalog', (req, res) => {
  res.set('Cache-Control', 'public, max-age=300, stale-while-revalidate=600');
  res.json(catalog);
});
app.get('/api/orders', authenticate, (req, res) => {
  res.set('Cache-Control', 'private, no-cache');
  res.json(orders);
});
app.get('/api/auth/*', (req, res) => {
  res.set('Cache-Control', 'no-store');
  next();
});

// ─── Next.js headers config ───
// next.config.js
