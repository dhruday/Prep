Stale data: cached data that no longer reflects server truth

Stale data is the inevitable result of caching. The challenge is finding the right balance: too aggressive = many network calls (defeats caching), too permissive = users act on wrong data. At SAP, an order status shown as "Processing" after it was already shipped is a critical stale data problem — the field sales team might call a customer about a delivery already received.

Always fresh
no-cache / no-store. Every request validated. Correct data, maximum latency. Use for: PII, real-time prices, auth state.
Stale-then-revalidate
Return cached instantly, revalidate in background. Next render shows fresh. Use for: catalogs, dashboards, feeds.
Accept staleness
Cache long TTL. Use for: static content, avatars, rarely-changing config. Mark with immutable.

SWR / React Query stale management + focus/online revalidation

// ─── React Query staleness config ───
useQuery({
  queryKey: ['order', orderId],
  queryFn: fetchOrder,
  staleTime: 60_000,      // fresh for 60s, no refetch
  gcTime: 300_000,         // keep in cache for 5min
  refetchOnWindowFocus: true,  // revalidate when tab gains focus
  refetchOnReconnect: true,    // revalidate after network back
  refetchInterval: 30_000,    // poll every 30s for real-time data
});

// ─── SWR (Next.js) ───
useSWR('/api/catalogue', fetcher, {
  refreshInterval: 3600_000,   // 1 hour for catalogue
  revalidateOnFocus: false,
  dedupingInterval: 300_000,   // dedupe within 5 mins
});

// ─── Stale indicator pattern ───
function OrderPanel() {
  const { data, isStale, isFetching } = useQuery({ staleTime: 30_000, ... });
  return (
    <div>
      {isStale && <Badge color="amber">Refreshing...</Badge>}
      {isFetching && <Spinner />}
      <OrderData data={data} />
    </div>
  );
}
