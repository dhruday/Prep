🏗️ High-Level Design (HLD)

Answers "WHAT will the system look like?" — boxes and arrows, bird's-eye view. Click each layer to expand.

1. User / Client Layer
Who uses the system? Browser/mobile/desktop? Authenticated vs anonymous? This shapes every other decision. Example: "10M DAU, primarily mobile web, 60% on slow 3G."
2. Data Flow Architecture
How does data move? Client fetches from REST/GraphQL? Websocket for realtime? SSE for server push? Diagram the arrows. Where is the source of truth?
3. Rendering Strategy
CSR / SSR / SSG / ISR? Hybrid? Decision should be driven by SEO requirements, TTI budget, and content freshness needs — not framework preference.
4. Deployment & CDN
Static assets on CDN (S3+CloudFront), API behind a load balancer, edge computing for personalisation? Geographic distribution strategy.
5. Cross-Cutting Concerns
Auth (OAuth/JWT), logging & monitoring, feature flags, error boundaries, A/B experimentation framework. These belong in HLD — they affect the whole system.
At Microsoft: After presenting HLD, pause and ask "Does this overall direction make sense before I dive deeper?" — signals you think collaboratively.

🔬 Low-Level Design (LLD)

Answers "HOW will we build it?" — actual components, APIs, state shape, algorithms. Click each layer to expand.

1. Component Hierarchy
Break the UI into named components. Which are smart (data-aware) vs dumb (presentational)? What are the props/events contracts? How does composition work?
2. State Shape & Management
What lives in global state vs local? Draw the state interface. Context API vs Redux vs Zustand — justified by complexity of sharing. Derived state vs stored state distinction.
3. API Contract / Interface
Define the REST endpoints or GraphQL queries you need. Request/response shape, pagination strategy (cursor vs offset), error schema, retry logic.
4. Performance Optimisations
Virtualisation for long lists, memoisation boundaries, code-splitting strategy, image lazy-loading, critical CSS extraction. Applied at the component level.
5. Error & Loading States
Every async operation needs three states: loading skeleton, success, error with retry. Optimistic UI design. How do you handle partial failures in parallel requests?
At Adobe: They'll ask about the specific component API you chose. Be ready to show TypeScript interface definitions for your major state shapes.

📖 Worked Example: Design A Twitter-like Feed

HLD ↔ LLD Boundary
HLD Decisions for Feed
  • 📦 CDN: Static React bundle served via CloudFront. Media via separate media CDN.
  • 🔄 Data flow: Initial SSR for first ~20 tweets (SEO + LCP). Then CSR for infinite scroll pagination.
  • 🔌 Realtime: WebSocket for live like count updates; SSE for new tweet notifications.
  • 🔐 Auth: JWT in httpOnly cookie. Refresh via silent iframe or service worker.
  • 📊 Observability: Sentry for errors, DataDog RUM for Core Web Vitals.
LLD Decisions for Feed
  • 🧩 Components: FeedContainer → TweetList (virtualised) → TweetCard → TweetActions
  • 📐 State: {`{ tweets: Map<id,Tweet>, cursor: string, hasMore: boolean, optimisticLikes: Map<id,number> }`}
  • 🌐 API: GET /feed?cursor=<cursor>&limit=20 returning {`{ data: Tweet[], nextCursor: string }`}
  • ⚡ Perf: react-window for list virtualisation. useMemo on tweet selector. React.memo on TweetCard.
  • ❌ Errors: Error boundary per TweetCard. Failed tweets show placeholder. Like failures show toast with undo.
Belongs in HLD
  • • Rendering strategy (SSR vs CSR)
  • • CDN topology
  • • Authentication mechanism
  • • Realtime protocol choice
  • • Micro-frontend vs monolith
  • • Overall data flow direction
⟺
Belongs in LLD
  • • Component tree structure
  • • State interface typings
  • • API endpoint shape
  • • Virtualisation library choice
  • • Error boundary placement
  • • Memoisation strategy
