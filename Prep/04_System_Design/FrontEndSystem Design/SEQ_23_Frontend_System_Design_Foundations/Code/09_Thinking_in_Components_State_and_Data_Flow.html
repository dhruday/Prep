🔍 Component Contract Inspector

← Click any highlighted component to inspect its contract
AppShell Smart
Top-level container. Owns global navigation state, authentication context, and routing.
State currentRoute: string — active route for highlighting nav items
State theme: 'light' | 'dark' — passed via Context to all children
Provides (Context) ThemeContext, AuthContext
AppShell is the context provider boundary. Everything below it can read theme and auth without prop-drilling.
Header Presentational
Renders the top navigation bar. Reads theme from context, receives active route as prop.
Props activeRoute: string — determines which NavItem is highlighted
Props user: User | null — shows avatar or login button
Emits onLogout: () => void — bubbled to AppShell for auth state update
No local state. Header is a pure function of props — easy to test, easy to reuse.
NavItem Dumb
Props label: string
Props href: string
Props isActive: boolean — controls highlight style
Zero state, zero side effects. The simplest possible component. Always start here and add complexity only when needed.
FeedContainer Smart
Data-fetching boundary. Fetches paginated posts, manages cursor, handles loading/error/empty states.
State posts: Post[] — current page of posts
State cursor: string | null — for infinite scroll pagination
State isLoading: boolean
State error: Error | null
Passes down (Props) posts[] to TweetList component
Container pattern: FeedContainer owns ALL data concerns. PostCard knows nothing about fetching — it just renders. This separation makes PostCard 100% testable without mocking APIs.
PostCard Presentational
Props post: Post — {`{ id, author, content, likeCount, replyCount }`}
Props isLiked: boolean — determined by parent, not local state
Emits onLike: (postId: string) => void
Emits onReply: (postId: string) => void
Like state is NOT local — it comes from the parent (or global store). This enables optimistic updates to be rolled back correctly if the API fails.
PostActions Dumb
Props likeCount: number
Props replyCount: number
Props retweetCount: number
Props isLiked: boolean
Emits onLike: () => void — forwarded up to PostCard
The deepest leaf component. Zero state, just renders numbers and fires events. Testable with a single render + click assert.

🏆 State Placement Decision Rule

// Ask these questions in order:
// 1. Is this state needed by only ONE component?
//    → Keep it LOCAL with useState/useReducer

// 2. Is it needed by a small subtree of 2-4 components?
//    → Lift to nearest common ancestor (prop drilling OK)

// 3. Is it needed across many unrelated components?
//    → React Context (if simple) or Zustand/Redux (if complex)

// 4. Is it server/async data?
//    → React Query / TanStack Query (NOT global store)

// Examples from feed app:
// isDropdownOpen   → LOCAL (Header only)
// currentUser      → CONTEXT (many components need it)
// likedPostIds     → GLOBAL STORE (optimistic + server sync)
// posts[]          → REACT QUERY (server state)

📐 Component Decomposition Checklist

☐ Single Responsibility: Does each component do exactly one thing?
☐ Smart vs Dumb: Have you separated data-fetching from rendering?
☐ Props contract: Can you write a TypeScript interface for every component's props?
☐ State ownership: Is each piece of state owned by exactly one place?
☐ Event flow: Does data flow DOWN and events flow UP?
☐ Error boundaries: Where can a component fail without crashing the whole page?
☐ Testability: Can you test each component in isolation?
