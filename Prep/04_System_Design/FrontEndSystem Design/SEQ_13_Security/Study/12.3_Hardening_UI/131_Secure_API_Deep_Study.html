1. HTTPS / TLS Fundamentals

// HTTPS = HTTP over TLS (Transport Layer Security)
// TLS provides: Confidentiality + Integrity + Authentication
//
// TLS Handshake (simplified):
// 1. Client Hello → supported cipher suites, random value
// 2. Server Hello → chosen cipher suite, certificate, random value
// 3. Client verifies certificate chain (CA trust)
// 4. Key exchange → both sides derive session keys
// 5. All subsequent data encrypted with symmetric key (AES-256-GCM)
//
// TLS 1.3 improvements:
// - 1-RTT handshake (vs 2-RTT in TLS 1.2)
// - 0-RTT resumption (fast reconnection)
// - Removed insecure cipher suites (RC4, SHA-1, CBC)
// - Forward secrecy mandatory (ECDHE)

2. HSTS (HTTP Strict Transport Security)

// Problem: First visit to http://bank.com → redirect to https://
// That first HTTP request is vulnerable to MITM (SSL stripping)
//
// HSTS tells browser: "ALWAYS use HTTPS for this domain"
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

// max-age: how long (seconds) to enforce HTTPS (1 year)
// includeSubDomains: apply to all subdomains too
// preload: opt-in to browser's built-in HSTS list
//   → browser enforces HTTPS even on FIRST EVER visit
//   → submit to: hstspreload.org
//
// After HSTS: browser automatically upgrades http:// → https://
// Even if user types http://bank.com → browser sends https://

API Attack Vectors

1. MITM (Man-in-the-Middle) — SSL Stripping

// Attacker intercepts HTTP → HTTPS redirect
// User connects to attacker's HTTP proxy
// Attacker connects to bank via HTTPS
// User sees HTTP, thinks it's secure
//
// Defense: HSTS + preload → browser never makes HTTP request
// Defense: HSTS preload list → works even on first visit

2. Broken Object-Level Authorization (BOLA/IDOR)

// GET /api/users/123/profile → returns user 123's data
// Attacker changes to: GET /api/users/456/profile
// If server doesn't check: "Is the authenticated user allowed to see user 456?"
// → Data breach
//
// OWASP API Security Top 1 risk
// Defense: always verify resource ownership server-side
app.get('/api/users/:id/profile', (req, res) => {
  if (req.params.id !== req.user.id && !req.user.isAdmin) {
    return res.status(403).json({ error: 'Forbidden' });
  }
  // ... return profile
});

3. Mass Assignment

// User sends: { name: "Alice", role: "admin" }
// Server does: Object.assign(user, req.body)
// → user.role is now "admin"!
//
// Defense: whitelist allowed fields
const { name, email } = req.body; // Destructure only allowed fields

FAANG Interview Questions

Q1: How do you secure API communication between a frontend and backend?
Layered approach: Transport — TLS 1.3 with HSTS (max-age=1 year, includeSubDomains, preload). Never serve anything over HTTP. Authentication — OAuth 2.0 with PKCE for user auth, short-lived JWTs for API access. CSRF protection via SameSite cookies + custom headers. Authorization — server validates every request: does this user own this resource? Role-based access control via JWT claims + server-side checks. Never trust frontend-sent role/permission data. Input validation — Zod schemas on every endpoint. Parameterized queries for database access. Rate limiting — per-user and per-endpoint. Sliding window with 429 responses that include Retry-After header. Response security — don't over-fetch (GraphQL: use field-level authorization). Set proper CORS headers (explicit origin whitelist, not *). Cache-Control: no-store for sensitive responses. Logging — structured audit logs for all auth events and data access.
Follow-up: How do you handle API versioning securely?
Q2: Explain Certificate Pinning and why it's controversial for web apps.
Certificate Pinning hardcodes the expected certificate (or public key hash) into the client. If the server presents a different certificate, the connection is rejected — even if it's from a trusted CA. This prevents attacks where a compromised or rogue CA issues a fake certificate for your domain. For mobile apps, pinning is common and recommended (e.g., TrustKit for iOS, OkHttp CertificatePinner). For web apps, it's been deprecated: the HPKP (HTTP Public Key Pins) header was removed from browsers because it was too dangerous — a misconfiguration or key loss could permanently brick your site for users. Modern alternative: Certificate Transparency (CT) logs. Browsers require certificates to be logged in public CT logs, making rogue certificates detectable. Plus HSTS with preload ensures HTTPS. The combination of CT + HSTS provides similar protection without the bricking risk.
Follow-up: What about Certificate Transparency monitoring for your domain?
Q3: What's BOLA/IDOR and how do you test for it?
BOLA (Broken Object-Level Authorization), formerly called IDOR (Insecure Direct Object Reference), is the #1 API security risk per OWASP. It happens when the API uses user-supplied IDs to access resources without verifying the authenticated user has permission. Example: GET /api/orders/12345 — does the server check that the requesting user owns order 12345? Testing: (1) Create two test users A and B. (2) User A creates resources. (3) User B tries to access/modify A's resources by guessing or incrementing IDs. (4) Automate with Burp Suite intruder: swap authorization headers while keeping the same resource IDs. Prevention: always validate resource ownership in the data layer (not just middleware). Use UUIDs instead of sequential IDs to make guessing harder (but this is NOT a security control — just obscurity). For GraphQL: field-level authorization resolvers that check ownership.

1. Secure Fetch Wrapper

const API_BASE = 'https://api.example.com';

async function secureFetch(path, options = {}) {
  const token = await tokenManager.getToken();

  const response = await fetch(`${API_BASE}${path}`, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${token}`,
      'X-Request-ID': crypto.randomUUID(),
      ...options.headers,
    },
  });

  // Handle common security scenarios
  if (response.status === 401) {
    const newToken = await refreshAccessToken();
    return secureFetch(path, {
      ...options,
      headers: { ...options.headers, Authorization: `Bearer ${newToken}` },
    });
  }

  if (response.status === 429) {
    const retryAfter = response.headers.get('Retry-After') || 5;
    await new Promise(r => setTimeout(r, retryAfter * 1000));
    return secureFetch(path, options);
  }

  return response;
}

2. Input Validation (Zod)

import { z } from 'zod';

const UpdateProfileSchema = z.object({
  name: z.string().min(1).max(100),
  email: z.string().email(),
  // Explicitly NO 'role' or 'isAdmin' fields → mass assignment prevented
});

app.put('/api/profile', (req, res) => {
  const result = UpdateProfileSchema.safeParse(req.body);
  if (!result.success) {
    return res.status(400).json({ errors: result.error.issues });
  }
  // result.data contains only { name, email } — safe
  db.updateProfile(req.user.id, result.data);
});

API Security Checklist

✅ TLS 1.3 everywhere (no HTTP fallback)
✅ HSTS with preload (max-age=31536000; includeSubDomains; preload)
✅ Authentication on every endpoint (except public routes)
✅ Authorization: verify resource ownership (prevent BOLA/IDOR)
✅ Input validation: Zod/Joi schemas on all endpoints
✅ Rate limiting: per-user, per-endpoint, per-IP
✅ CORS: explicit origin whitelist, Vary: Origin
✅ Request IDs: X-Request-ID for tracing
✅ Prevent mass assignment: whitelist allowed fields
✅ Parameterized queries (never string concat SQL)
✅ Audit logging: who accessed what, when
✅ Error responses: don't leak stack traces or internal details
