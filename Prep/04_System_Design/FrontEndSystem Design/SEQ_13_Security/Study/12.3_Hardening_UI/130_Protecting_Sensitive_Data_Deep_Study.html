2. Where Sensitive Data Leaks in the Browser

// 1. URL / Query Parameters
//    https://app.com/reset?token=SECRET
//    → Logged in: server logs, proxy logs, browser history, Referer header
//    FIX: Use POST body or hash fragment (not sent to server)

// 2. Console Logging
//    console.log('User data:', user); // includes SSN in dev
//    → Persists in browser tools, crash reports
//    FIX: Strip console.log in production build; redact sensitive fields

// 3. Error Tracking (Sentry, LogRocket)
//    → Stack traces may include variable values with PII
//    FIX: Configure beforeSend to scrub sensitive fields

// 4. Network Tab / DevTools
//    → API responses visible in clear text
//    → No fix for the user's own browser, but don't over-fetch

// 5. Autocomplete / Form Data
//    → Browser stores form values for autofill
//    FIX: autocomplete="off" for sensitive fields, or autocomplete="new-password"

// 6. Clipboard
//    → User copies sensitive data, malicious page reads clipboard
//    FIX: Disable copy on sensitive fields; warn users

// 7. Screenshots / Screen Recording
//    → Sensitive data visible on screen
//    FIX: Mask by default, reveal on click

3. Web Crypto API

// Browser has built-in cryptography — no libraries needed

// Generate AES key:
const key = await crypto.subtle.generateKey(
  { name: 'AES-GCM', length: 256 },
  true,
  ['encrypt', 'decrypt']
);

// Encrypt:
const iv = crypto.getRandomValues(new Uint8Array(12));
const encrypted = await crypto.subtle.encrypt(
  { name: 'AES-GCM', iv },
  key,
  new TextEncoder().encode('sensitive data')
);

// Decrypt:
const decrypted = await crypto.subtle.decrypt(
  { name: 'AES-GCM', iv },
  key,
  encrypted
);
const text = new TextDecoder().decode(decrypted);

// Note: key is in browser memory — not a complete defense against XSS
// But useful for: encrypting data before storing in IndexedDB/localStorage

Practical Defense Patterns

1. Data Masking in UI

function maskSSN(ssn) {
  return '***-**-' + ssn.slice(-4);
}
function maskEmail(email) {
  const [user, domain] = email.split('@');
  return user[0] + '***' + '@' + domain;
}
function maskCard(number) {
  return '**** **** **** ' + number.slice(-4);
}

// React component with reveal toggle:
function SensitiveField({ value, maskFn }) {
  const [revealed, setRevealed] = useState(false);
  return (
    <span>
      {revealed ? value : maskFn(value)}
      <button onClick={() => setRevealed(!revealed)}>
        {revealed ? 'Hide' : 'Show'}
      </button>
    </span>
  );
}

2. Scrub PII from Error Tracking

Sentry.init({
  beforeSend(event) {
    // Scrub sensitive data from breadcrumbs
    if (event.breadcrumbs) {
      event.breadcrumbs = event.breadcrumbs.map(b => ({
        ...b,
        data: redactSensitive(b.data),
      }));
    }
    // Scrub request data
    if (event.request?.data) {
      event.request.data = redactSensitive(event.request.data);
    }
    return event;
  },
});

FAANG Interview Questions

Q1: How do you prevent sensitive data exposure in a frontend application?
Multi-layered approach: (1) API design — server should never send more data than needed. Rather than sending full SSN and masking on the client, send only the last 4 digits. This is the most important defense. (2) UI masking — display sensitive fields masked by default with explicit reveal action. Log the reveal event for audit. (3) URL hygiene — never put tokens, PII, or sensitive data in URLs or query params (leaks via Referer, logs, browser history). Use POST body or hash fragments. (4) Memory management — clear sensitive variables after use; avoid storing in global state. (5) Error tracking — configure Sentry/DataDog beforeSend hooks to scrub PII from stack traces and breadcrumbs. (6) Prevent caching — use Cache-Control: no-store on sensitive API responses. Set autocomplete="off" on sensitive form fields. (7) Copy protection — disable text selection on sensitive display fields if business-appropriate. (8) Reference: OWASP recommends "data minimization" — only collect, process, and display what's absolutely necessary.
Follow-up: How do you audit what sensitive data is being sent to the frontend?
Q2: How would you handle payment card data securely on the frontend?
Never let card data touch your servers — use PCI DSS-compliant third-party elements. Stripe Elements or Braintree Hosted Fields render the card input in an iframe from their domain. Your JavaScript can't access the card number because it's cross-origin (Same-Origin Policy). The card data goes directly from the iframe to Stripe's servers, which return a tokenized reference (tok_xxx). Your frontend sends only the token to your backend. This keeps you in PCI SAQ-A scope (minimal compliance burden). If you must collect card data directly (rare), you need PCI DSS Level 1 compliance — annual audits, network segmentation, encryption at rest and in transit, quarterly vulnerability scans. For display: only show last 4 digits from the API. Never store full card numbers in any browser storage. Use input masking during entry (show dots as user types). Disable autocomplete on card fields.
Follow-up: What happens if a user takes a screenshot of the card details?
Q3: What's the Referrer-Policy header and when do you need it?
The Referer header (yes, the misspelling is intentional — historical typo in the HTTP spec) tells the destination page which URL the user came from. This leaks sensitive URL data: tokens in query params, internal paths, user IDs. Referrer-Policy controls what's sent. I use 'strict-origin-when-cross-origin' (the modern default): same-origin requests get the full URL, cross-origin requests get only the origin (scheme+host+port), and downgrades from HTTPS to HTTP send nothing. For pages with sensitive URLs, use 'no-referrer' to send nothing at all. This prevents: password reset tokens leaking to external analytics, internal page structure leaking to third-party scripts, and user IDs in URLs leaking via outbound links. Set it as both an HTTP header and a meta tag for comprehensive coverage.
Follow-up: How does this interact with analytics and attribution tracking?

1. Secure Form Handling

// Prevent sensitive data from browser autofill and history

<form autocomplete="off">
  <input
    type="password"
    autocomplete="new-password"
    name=crypto.randomUUID()  // Randomize name to prevent autofill
  />
  <input
    type="text"
    autocomplete="off"
    inputmode="numeric"
    pattern="[0-9]*"
    placeholder="SSN"
  />
</form>

// Clear sensitive fields on component unmount (React):
useEffect(() => {
  return () => {
    // Clear the input values from memory
    setSsn('');
    setCardNumber('');
  };
}, []);

2. Secure API Response Headers

// Server headers for sensitive endpoints
Cache-Control: no-store, no-cache, must-revalidate
Pragma: no-cache
Referrer-Policy: no-referrer
X-Content-Type-Options: nosniff

// Express middleware:
app.use('/api/sensitive', (req, res, next) => {
  res.set({
    'Cache-Control': 'no-store',
    'Referrer-Policy': 'no-referrer',
    'X-Content-Type-Options': 'nosniff',
  });
  next();
});

Data Protection Checklist

✅ Data minimization: API sends only what UI needs
✅ Mask sensitive fields by default, reveal on explicit action
✅ Never put sensitive data in URLs or query parameters
✅ Set Cache-Control: no-store on sensitive API responses
✅ Configure Referrer-Policy: strict-origin-when-cross-origin
✅ Scrub PII from error tracking (Sentry beforeSend)
✅ autocomplete="off" on sensitive form fields
✅ Strip console.log in production builds
✅ Use Stripe Elements / hosted fields for payment data
✅ Clear sensitive state on component unmount / logout
✅ Log access to sensitive data for audit trail
