1. What Are Passkeys?

// Passkeys = WebAuthn credentials synced across devices
// The password replacement from FIDO Alliance + W3C
//
// Traditional:  user types password → server verifies hash
// Passkeys:     user authenticates locally (biometric/PIN)
//               → device signs a challenge with private key
//               → server verifies with stored public key
//
// Key properties:
// ✅ Phishing-resistant (origin-bound — only works on correct domain)
// ✅ No shared secret (server stores only public key)
// ✅ No password to steal, leak, or reuse
// ✅ Built-in MFA (device possession + biometric/PIN)
// ✅ Synced via iCloud Keychain / Google Password Manager
//
// Adoption: Apple, Google, Microsoft since 2022-2023
// Sites: GitHub, Google, PayPal, Amazon, Shopify

2. WebAuthn Protocol Flow

// REGISTRATION (creating a passkey):
// 1. Server sends: challenge (random), user info, relying party (RP) info
// 2. Browser calls: navigator.credentials.create({publicKey: options})
// 3. Device authenticates user (Face ID, Touch ID, PIN)
// 4. Authenticator generates key pair (private stays on device)
// 5. Browser returns: credential ID + public key + signed attestation
// 6. Server stores: credential ID + public key (linked to user account)
//
// AUTHENTICATION (using a passkey):
// 1. Server sends: challenge (random) + allowed credential IDs
// 2. Browser calls: navigator.credentials.get({publicKey: options})
// 3. Device authenticates user (biometric/PIN)
// 4. Authenticator signs challenge with private key
// 5. Browser returns: credential ID + signed assertion
// 6. Server verifies signature with stored public key → authenticated
//
// Origin binding: the authenticator includes the origin in the signed data
// → a phishing site (evil.com) can't forge a valid assertion for bank.com

Why Passkeys Are Phishing-Proof

// TOTP phishing attack (still possible):
// 1. Attacker creates fake-bank.com (looks identical to bank.com)
// 2. User enters password + TOTP code on fake-bank.com
// 3. Attacker relays credentials to real bank.com in real-time
// 4. TOTP is valid for 30 seconds → attacker authenticates
//
// Passkey phishing attempt:
// 1. Attacker creates fake-bank.com
// 2. Browser calls navigator.credentials.get()
// 3. Authenticator checks RP ID (relying party) = fake-bank.com
// 4. No passkey exists for fake-bank.com → authentication fails
// 5. Even if attacker proxies the challenge from bank.com:
//    The authenticator signs: origin=fake-bank.com
//    Server checks: origin should be bank.com → rejects
//
// The origin check is the fundamental difference:
// Passwords/TOTP: user decides which site gets the credential
// Passkeys: the browser/OS enforces domain matching

FAANG Interview Questions

Q1: How do passkeys eliminate phishing, and what makes them different from TOTP?
Passkeys are origin-bound — the authenticator (browser + device) includes the website's origin in the signed assertion. If the user is on fake-bank.com, the authenticator signs with origin=fake-bank.com. The real bank.com server sees the wrong origin and rejects it. Even if the attacker sets up a transparent proxy (relay phishing), the signed data includes the wrong origin. TOTP codes are just 6-digit numbers — they carry no origin information. An attacker who proxies the TOTP in real-time (within the 30-second window) can use it on the real site. Passkeys also eliminate credential databases on the server — only public keys are stored. A server breach leaks public keys, which are useless to attackers. With TOTP, the shared TOTP seed is stored server-side, and if leaked, all codes can be generated offline. Passkeys also provide implicit MFA: device possession (something you have) + biometric/PIN (something you are/know).

Q2: How would you implement passkey authentication in a production web app?
I'd use a server library like @simplewebauthn/server (Node.js). Registration: After the user logs in with their existing method, check if their device supports platform authenticators via PublicKeyCredential.isUserVerifyingPlatformAuthenticatorAvailable(). If yes, show a "Set up passkey" prompt. Call the server to generate registration options (challenge, RP info, user info, preferred algorithms). Call navigator.credentials.create() with the options. Send the credential response to the server, which verifies the attestation and stores the credential ID + public key. Authentication: On the login page, offer "Sign in with passkey." Server sends authentication options (challenge + allowed credential IDs). Call navigator.credentials.get(). Send the assertion to the server for verification. Key implementation details: set userVerification to 'preferred' (don't force if unavailable), use residentKey: 'required' for discoverable credentials (user doesn't need to type username), implement conditional UI (autofill-style passkey suggestion in the username field).
Follow-up: What's conditional UI and how does it improve UX?
Q3: What are the limitations of passkeys today?
Several real-world challenges: (1) Ecosystem lock-in — iCloud Keychain passkeys are hard to use on Android and vice versa. Cross-device auth (QR + Bluetooth) works but has friction. (2) Account recovery — if a user loses all devices and hasn't set up cloud sync, they're locked out. Must maintain fallback auth methods. (3) Shared devices — passkeys on a public computer are risky (others can use them). Platform authenticators shouldn't be offered on shared devices. (4) Enterprise — IT admins need to manage which authenticators are allowed (attestation policies). (5) Browser support — full support in Chrome, Safari, Edge, but partial in Firefox. Conditional UI is even more limited. (6) Developer complexity — WebAuthn is a complex protocol. Libraries help but the mental model is harder than password auth. (7) User education — many users don't understand passkeys yet. The term isn't universally known. Best approach: offer passkeys as an upgrade path, don't force, keep password as fallback for now.

1. Passkey Registration (Client)

async function registerPasskey() {
  // 1. Get options from server
  const optionsRes = await fetch('/auth/webauthn/register-options', {
    method: 'POST',
    credentials: 'include',
  });
  const options = await optionsRes.json();

  // 2. Convert base64 to ArrayBuffer
  options.challenge = base64ToBuffer(options.challenge);
  options.user.id = base64ToBuffer(options.user.id);

  // 3. Create credential (triggers biometric prompt)
  const credential = await navigator.credentials.create({
    publicKey: {
      ...options,
      authenticatorSelection: {
        authenticatorAttachment: 'platform', // Built-in (Face ID)
        residentKey: 'required',        // Discoverable
        userVerification: 'preferred',   // Biometric or PIN
      },
      pubKeyCredParams: [
        { type: 'public-key', alg: -7 },   // ES256
        { type: 'public-key', alg: -257 }, // RS256
      ],
    },
  });

  // 4. Send credential to server for storage
  await fetch('/auth/webauthn/register-verify', {
    method: 'POST',
    credentials: 'include',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      id: credential.id,
      rawId: bufferToBase64(credential.rawId),
      response: {
        attestationObject: bufferToBase64(credential.response.attestationObject),
        clientDataJSON: bufferToBase64(credential.response.clientDataJSON),
      },
      type: credential.type,
    }),
  });
}

2. Passkey Authentication (Client)

async function loginWithPasskey() {
  // 1. Get challenge from server
  const optionsRes = await fetch('/auth/webauthn/login-options');
  const options = await optionsRes.json();
  options.challenge = base64ToBuffer(options.challenge);

  // 2. Get assertion (triggers biometric prompt)
  const assertion = await navigator.credentials.get({
    publicKey: options,
  });

  // 3. Send assertion to server for verification
  const res = await fetch('/auth/webauthn/login-verify', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      id: assertion.id,
      rawId: bufferToBase64(assertion.rawId),
      response: {
        authenticatorData: bufferToBase64(assertion.response.authenticatorData),
        clientDataJSON: bufferToBase64(assertion.response.clientDataJSON),
        signature: bufferToBase64(assertion.response.signature),
      },
      type: assertion.type,
    }),
  });
  // Server verified → returns session/token
}

Passkey Implementation Checklist

✅ Check device support: PublicKeyCredential available?
✅ Check platform authenticator: isUserVerifyingPlatformAuthenticatorAvailable()
✅ Use residentKey: 'required' for discoverable credentials
✅ Use userVerification: 'preferred' (don't block if unavailable)
✅ Generate cryptographic challenges server-side (min 16 bytes)
✅ Validate origin in clientDataJSON on server
✅ Store credential ID + public key (NOT private key — that's on device)
✅ Support multiple passkeys per account (phone + laptop)
✅ Implement fallback auth (email magic link, password)
✅ Offer conditional UI (autocomplete="webauthn") for seamless UX
✅ Handle cross-device flow (QR + Bluetooth)
✅ Rate-limit authentication attempts
