Same-Origin Policy (SOP)

The browser's fundamental security model. JavaScript on origin A cannot read responses from origin B. An "origin" = scheme + host + port.

What SOP Blocks vs Allows

// SOP BLOCKS JavaScript from READING cross-origin responses:
await fetch('https://api.other.com/data'); // request IS sent, but
// response.json() throws TypeError — JS can't read it

// SOP ALLOWS cross-origin EMBEDDING:
// <img src="https://other.com/pic.jpg">      ← allowed
// <script src="https://cdn.com/lib.js">       ← allowed
// <link href="https://cdn.com/style.css">     ← allowed
// <iframe src="https://other.com">            ← allowed (can't read content)

// SOP ALLOWS cross-origin WRITES (form submissions):
// <form action="https://other.com/submit">   ← allowed (CSRF!)

Google Senior Frontend — CORS Questions

Q: Explain CORS to a junior developer who says "CORS blocks my requests."

CORS doesn't block requests — it blocks JavaScript from reading responses. The request is still sent and the server still processes it. CORS is NOT a security feature for the server; it's the server giving PERMISSION to another origin's JavaScript to read the response. If you're getting CORS errors, the server needs to include the proper Access-Control-Allow-Origin header. Don't "fix" CORS by adding a proxy — understand why the server should (or shouldn't) allow it.

Q: When should you use Access-Control-Allow-Origin: * vs specific origins?

Use * only for truly public APIs with no auth (public data, CDN assets). For any API that uses cookies or auth, you MUST use specific origins. The wildcard is incompatible with credentials (browser enforces this). At Google: API Gateway validates the Origin header against a per-service allowlist, dynamically sets the ACAO header to the matching origin.

🔬 How CORS Works in the Browser Engine

1. Request Classification: Before sending, the browser classifies the request as "simple" or "preflighted" based on method, headers, and content-type.

2. Simple Request Flow: Request is sent immediately. Browser adds Origin header. Server responds with Access-Control-Allow-Origin. Browser checks if the response's ACAO header includes the requestor's origin. If no match → JS gets a TypeError and can't read the response body. Note: the request WAS sent and processed — the server-side effect occurred.

3. Preflight Flow: Browser sends OPTIONS first with Access-Control-Request-Method and Access-Control-Request-Headers. If server approves, the actual request follows. If denied, the actual request is NEVER sent.

4. Credential Mode: fetch with credentials: 'include' sends cookies. Server MUST respond with specific origin (not *) and Access-Control-Allow-Credentials: true. Without this, the browser blocks the response AND doesn't send cookies.

Google Senior Frontend — CORS Questions

Q: Why can <img> and <script> load cross-origin but fetch can't?

Historical web compat. <img>, <script>, <link> predate SOP and are "opaque" — JS can't read the response content (you can't read pixel data from a cross-origin image on canvas without CORS). fetch/XHR are programmable APIs that give JS full access to response data, so they enforce SOP. CORS is the opt-in mechanism for servers to permit this.

Q: How would you configure CORS for a microservices architecture at Google?

Centralize CORS at the API gateway/load balancer, not in individual services. Maintain an allowlist of trusted origins (from config, not hardcoded). Never reflect the Origin header dynamically without validation. Return Vary: Origin to prevent CDN cache poisoning. Set Access-Control-Max-Age to reduce preflight overhead. For internal service-to-service: no CORS needed (server-to-server bypasses CORS), use mTLS authentication instead.
