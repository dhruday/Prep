Secure Frontend CI/CD Pipeline

# Stage 1: INSTALL (Secure Dependencies)
npm ci --ignore-scripts          # Lockfile-only, no scripts
npm run allowed-scripts          # Run only whitelisted scripts
lockfile-lint --type npm --path . --validate-https --allowed-hosts npm
                                 # Verify all URLs are HTTPS

# Stage 2: AUDIT (Security Checks)
npm audit --audit-level=high     # Block on high+ vulnerabilities
npx snyk test                    # Deep vulnerability scan
npx eslint . --config .eslintrc-security.json  # Security-focused lint rules

# Stage 3: BUILD (Isolated Environment)
NODE_ENV=production npm run build  # Production build
# Verify no secrets in build output:
grep -r "API_KEY\|SECRET\|PASSWORD" dist/ && exit 1

# Stage 4: TEST (Security Tests)
npm run test:security             # XSS, CSRF, injection tests
npx lighthouse --chrome-flags="--headless" --only-categories=best-practices

# Stage 5: SIGN & PUBLISH
# Sign build artifacts with Sigstore/cosign
cosign sign-blob --output-signature dist.sig dist/
# Generate SBOM
npx @cyclonedx/cyclonedx-npm --output-file sbom.json

# Stage 6: DEPLOY (Secure Delivery)
# Deploy to CDN with SRI hashes
# Enable CSP headers, HSTS, etc.

Secret Management in CI/CD

// ❌ NEVER: Hardcode secrets
const API_KEY = 'sk-abc123...'; // NEVER!
const DB_PASS = 'password123';  // NEVER!

// ❌ NEVER: Put secrets in .env committed to git
//   .env should be in .gitignore

// ✅ Use environment variables from CI/CD secrets:
//   GitHub: Settings → Secrets → Actions
//   GitLab: Settings → CI/CD → Variables (masked + protected)

// ✅ For client-side: ONLY use NEXT_PUBLIC_ / VITE_ prefixed vars
//   These ARE visible to users — only use for public API keys

Google Senior Frontend — CI/CD Security

Q: Design a CI/CD pipeline for a frontend app that handles financial data (like Google Pay).

Build isolation: Docker containers with pinned base images (no latest tag). Dep management: npm ci with lockfile + integrity verification. Object.freeze(Object.prototype) in the app entrypoint. Static analysis: ESLint security rules + CodeQL for taint analysis (user input → dangerous sinks). Dynamic testing: Headless browser tests that attempt XSS/CSRF injections. Build signing: Sigstore/cosign for artifact provenance. CSP: Strict nonce-based CSP generated at build time. Deployment: Blue-green with automatic rollback on security metric regression. Monitoring: Real-time CSP violation reporting, SRI checking, anomaly detection on API call patterns. Google's approach: Binary Authorization — only signed, policy-checked builds can be deployed to production.
