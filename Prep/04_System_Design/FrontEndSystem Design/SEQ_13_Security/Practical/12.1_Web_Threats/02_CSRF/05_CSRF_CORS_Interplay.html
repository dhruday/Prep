Key insight: Forms and images bypass CORS entirely. Only fetch/XHR with non-simple headers/content-types trigger CORS preflight, which can block the request if the server doesn't allow the origin.

What is a "Simple Request" (no preflight)?

// A request is "simple" (no preflight) if ALL of these are true:
// 1. Method is GET, HEAD, or POST
// 2. Content-Type is one of:
//    - application/x-www-form-urlencoded
//    - multipart/form-data
//    - text/plain
// 3. No custom headers (only Accept, Accept-Language, Content-Language,
//    Content-Type, Range)
//
// Simple requests are sent IMMEDIATELY — the server processes them
// before the CORS check. CORS only affects whether the RESPONSE is
// readable by the attacker's JS.
//
// This means: CORS does NOT prevent the side effect!
// The money is already transferred — attacker just can't read the response.

CORS Preflight — Step by Step

// Step 1: Browser detects non-simple request (custom header or JSON content-type)
// Step 2: Browser sends OPTIONS preflight:
OPTIONS /api/transfer HTTP/1.1
Origin: https://evil.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Content-Type, X-Custom-Header

// Step 3: Server responds with allowed origins:
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://myapp.com
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: Content-Type, X-Custom-Header
Access-Control-Max-Age: 86400

// Step 4: Browser checks: evil.com ≠ myapp.com → BLOCK!
// The actual POST is NEVER sent. No side effect occurs.

// Contrast with simple request:
// POST is sent immediately → server processes it → side effect occurs
// Browser checks CORS on the response → blocks JS from reading it
// But the damage is already done!

Google Senior Frontend — CSRF + CORS

Q: A colleague says "our API only accepts JSON, so CORS protects us from CSRF." Is this correct?

Partially. If the server strictly rejects non-JSON content-types AND the CORS policy doesn't allow untrusted origins, then yes — the preflight will block cross-origin JSON requests. But this relies on TWO things being correct: Content-Type check + CORS config. If either is misconfigured (e.g., Access-Control-Allow-Origin: *), CSRF is possible. Defense-in-depth with explicit CSRF tokens or SameSite cookies is more robust.

Q: What's the security implication of Access-Control-Allow-Origin: *?

It allows ANY origin to read the response. But: the wildcard doesn't work with credentials (the browser blocks it). If you also set Access-Control-Allow-Credentials: true, you MUST specify exact origins. The real danger is when server dynamically echoes the Origin header back as Access-Control-Allow-Origin without validation — this is "CORS misconfiguration" and enables cross-origin data theft.
