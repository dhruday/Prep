Three CSRF Prevention Patterns

PatternHow It WorksProsCons
Synchronizer Token Server generates random token, stores in session. Client sends in hidden form field or header. Most secure, battle-tested Requires server-side session state
Double-Submit Cookie Server sets CSRF token in cookie AND expects it in request header. Attacker can't read the cookie to copy it. Stateless, scales well Vulnerable if attacker can set cookies (subdomain XSS)
Origin/Referer Check Server checks Origin or Referer header matches expected domain. No token management Referer can be stripped; Origin not sent on some requests

Modern SPA Pattern: Custom Header

// SPAs that use fetch/XHR can use a simpler approach:
// Cross-origin requests with custom headers trigger CORS preflight.
// Evil.com CANNOT add custom headers via form submission.

const res = await fetch('/api/transfer', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',  // triggers preflight
    'X-Requested-With': 'XMLHttpRequest'  // custom header = CSRF protection
  },
  body: JSON.stringify({ to: 'friend', amount: 50 })
});

// Server-side: reject requests without the custom header
if (!req.headers['x-requested-with']) {
  return res.status(403).json({ error: 'Missing custom header' });
}

Server Implementation (Express.js)

// Synchronizer Token Pattern
const crypto = require('crypto');
const tokens = new Map(); // session_id → csrf_token

app.get('/api/csrf/token', (req, res) => {
  const token = crypto.randomBytes(32).toString('hex');
  tokens.set(req.sessionId, token);
  res.json({ csrfToken: token });
});

app.post('/api/transfer', (req, res) => {
  const expected = tokens.get(req.sessionId);
  const received = req.headers['x-csrf-token'];
  if (!expected || expected !== received) {
    return res.status(403).json({ error: 'Invalid CSRF token' });
  }
  tokens.delete(req.sessionId); // one-time use
  // process transfer...
});

// Double-Submit Cookie Pattern
app.use((req, res, next) => {
  if (['POST','PUT','DELETE'].includes(req.method)) {
    const cookieToken = req.cookies['csrf-token'];
    const headerToken = req.headers['x-csrf-token'];
    if (!cookieToken || cookieToken !== headerToken) {
      return res.status(403).json({ error: 'CSRF mismatch' });
    }
  }
  next();
});

Google Senior Frontend — CSRF Patterns

Q: For a new Google-scale app, which CSRF pattern would you choose?

For an SPA: Custom header check (X-Requested-With) + SameSite=Lax cookies. This is the simplest and most scalable. The custom header forces a CORS preflight, which cross-origin forms can't do. For SSR pages with forms: synchronizer tokens stored in the session. Double-submit as fallback for stateless microservices. Always layer with SameSite cookies.

Q: How does SameSite=Lax interact with CSRF in real scenarios?

Lax sends cookies on top-level navigations (GET) but NOT on cross-origin POST form submissions. This blocks classic CSRF. But: (1) GET-based state changes are still vulnerable, (2) Two-minute POST window on new cookies in Chrome, (3) doesn't protect against subdomain attacks. Always pair SameSite with explicit CSRF tokens for defense-in-depth.
