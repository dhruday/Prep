Are JSON APIs Immune to CSRF?

Myth: "If my API only accepts application/json, it's safe from CSRF."

Reality: Partially true. HTML forms can only send three content types (application/x-www-form-urlencoded, multipart/form-data, text/plain). They CANNOT send application/json. BUT:

1. text/plain trick: Attacker can use <form enctype="text/plain"> to send data that LOOKS like JSON

2. Flash/Java applets: (Legacy) Could send arbitrary Content-Types

3. Misconfigured CORS: If server sends Access-Control-Allow-Origin: *, attacker's JS can send JSON via fetch

4. Proper defense: Check Content-Type header strictly AND require a custom header

The text/plain CSRF Trick — Detailed

// Attacker's page (evil.com):
<form action="https://api.bank.com/transfer"
      method="POST"
      enctype="text/plain"
      id="f">
  <input name='{"to":"attacker","amount":"10000","x":"'
         value='ignore"}' type="hidden">
</form>
<script>document.getElementById('f').submit();</script>

// This sends body:
{"to":"attacker","amount":"10000","x":"=ignore"}

// If server blindly parses JSON from text/plain body → CSRF works!
// Defense: reject requests where Content-Type ≠ application/json

Why Custom Headers Work

// HTML forms CANNOT set custom headers.
// Cross-origin fetch with custom headers triggers CORS preflight.
// If server doesn't allow evil.com in CORS → preflight fails → request blocked.

// The defense:
// 1. Require X-Requested-With: XMLHttpRequest on all mutations
// 2. Forms can't set this → CSRF from forms is blocked
// 3. Cross-origin XHR needs CORS permission → CSRF from scripts is blocked
// 4. Only same-origin scripts can set custom headers without preflight

Google Senior Frontend — SPA CSRF

Q: Design the CSRF protection for a React SPA at Google scale.

Layer 1: SameSite=Lax on all auth cookies (blocks cross-site form POST). Layer 2: Require Content-Type: application/json (blocks plain form submissions). Layer 3: Custom header (X-Fetch-Mode: 'api') checked by API gateway — forms can't set headers, cross-origin needs CORS approval. Layer 4: For critical actions (money transfer, account deletion), require re-authentication or a synchronizer token. This approach is stateless, scales across microservices, and provides defense-in-depth.

Q: What about CSRF with JWTs in localStorage?

If JWT is in localStorage and sent via Authorization header, CSRF is inherently prevented because: (1) cross-origin scripts can't read localStorage, (2) custom headers require CORS permission. But localStorage JWTs are vulnerable to XSS — one XSS and the token is stolen. The trade-off: HTTP-only cookies are XSS-safe but need CSRF protection; localStorage tokens are CSRF-safe but need XSS protection.
