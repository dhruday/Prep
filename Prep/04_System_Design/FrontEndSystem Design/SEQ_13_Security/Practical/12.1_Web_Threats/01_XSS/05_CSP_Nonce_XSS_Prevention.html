CSP as XSS Defense-in-Depth

Content Security Policy (CSP) is a defense-in-depth layer. Even if XSS payload reaches the DOM, CSP blocks its execution. The nonce-based approach allows only scripts with the correct server-generated nonce to execute.

// Server sends this header with EVERY response:
Content-Security-Policy: script-src 'nonce-abc123randomvalue' 'strict-dynamic'

// Legitimate scripts have the nonce:
<script nonce="abc123randomvalue">console.log('allowed')</script>

// Injected XSS scripts don't know the nonce:
<script>alert('blocked by CSP!')</script>  ← blocked

// Event handlers are also blocked:
<img src=x onerror=alert(1)>  ← blocked (inline event handlers)

🔬 How CSP Nonce Works Internally

1. Response Processing: Browser parses the CSP header BEFORE parsing HTML. It stores the allowed nonces, hashes, and sources in a policy object.

2. Script Discovery: When the HTML parser encounters a <script> tag, before executing it, the browser checks the element's nonce attribute against the stored policy.

3. Inline Event Handlers: CSP also blocks inline event handlers (onclick, onerror) because they have no way to carry a nonce. This is why CSP is effective against <img onerror=...> even though innerHTML doesn't need <script> tags.

4. strict-dynamic: When a trusted script (with valid nonce) dynamically creates a new script via document.createElement('script'), that child script is also trusted — it inherits trust from its parent. This enables SPAs to load modules dynamically.

5. Violation Reporting: You can set report-uri or report-to to receive violation reports as JSON POSTs, allowing monitoring without blocking.

Google Senior Frontend — CSP Questions

Q: How would you implement CSP in a React SPA?

For SSR (Next.js): Generate a nonce per request on the server, inject it into the CSP header and all <script nonce="..."> tags. For pure CSR: Use hash-based CSP since you know the script hashes at build time. Always use 'strict-dynamic' so dynamically-loaded chunks work. Avoid 'unsafe-inline' — React's JSX doesn't need it since it uses addEventListener, not inline handlers.

Q: What's the difference between CSP Level 2 and Level 3?

Level 2 added nonces and hashes. Level 3 added 'strict-dynamic' (trust propagation), 'report-sample' (include violating code in reports), and the navigate-to directive. Google's recommendation is nonce + strict-dynamic, which works even if you have legacy 'unsafe-inline' in older directives — strict-dynamic takes precedence.

Q: Can CSP completely prevent XSS?

Almost, but not quite. CSP cannot prevent: (1) Script gadgets — where existing trusted scripts are tricked into executing attacker data, (2) Dangling markup injection, (3) CSS-based data exfiltration. CSP is a safety net, not a silver bullet — always combine with output encoding/sanitization.
