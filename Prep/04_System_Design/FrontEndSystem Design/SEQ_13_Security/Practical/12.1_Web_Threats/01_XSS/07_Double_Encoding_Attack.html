Double Encoding Attack

When a server decodes input once for validation (finds it safe) but the downstream component decodes it AGAIN, the payload activates. The key insight: encoding is not sanitization.

// Original payload:
<script>alert(1)</script>

// Single URL-encoded (caught by naive filter):
%3Cscript%3Ealert(1)%3C%2Fscript%3E

// DOUBLE URL-encoded (bypasses naive filter):
%253Cscript%253Ealert(1)%253C%252Fscript%253E

// What happens:
// 1. Server decodes once: %253C → %3C  (filter sees %3C, not <, says "safe")
// 2. Downstream decodes again: %3C → <  (now it's a script tag!)

Google Senior Frontend — Filter Bypass Questions

Q: Why do blocklist-based XSS filters always fail?

Blocklists fail because HTML has too many parsing contexts and edge cases. Browsers are extremely permissive in parsing malformed HTML — they recover from errors in unpredictable ways. There are 100+ HTML event handlers, multiple encoding schemes (URL, HTML entity, Unicode, base64), and browser-specific quirks. The only reliable approach is to use a parser-based sanitizer (DOMPurify) that understands the exact HTML parsing rules, or output encoding that addresses the root cause.

Q: What is mXSS (mutation XSS)?

mXSS exploits the difference between how the HTML is parsed during sanitization vs how the browser re-serializes and re-parses it. For example, when you read innerHTML, the browser serializes the DOM back to HTML — but the serialization can introduce changes that create valid XSS when re-parsed. DOMPurify v3 mitigates this by calling the parser twice and comparing results.

Q: How do you test for XSS filter bypass in a code review?

Don't test the filter — reject the approach. If you see regex-based filtering (replace, match for script/alert/eval), flag it as insecure by design. The correct fix is output encoding (for text contexts) or DOMPurify (for HTML contexts), not filter improvement. In a Google code review: NACK any regex-based XSS filter, link to go/safe-html.
