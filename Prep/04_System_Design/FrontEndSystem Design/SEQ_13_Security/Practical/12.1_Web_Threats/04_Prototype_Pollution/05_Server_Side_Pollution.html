Server-Side Impact

On the server (Node.js), prototype pollution is more dangerous because it can lead to Remote Code Execution (RCE). The server is a single long-lived process — pollution persists across ALL requests for ALL users.

// Express body parser + unsafe merge → global pollution:
app.post('/api/config', (req, res) => {
  merge(appConfig, req.body);  // req.body from JSON.parse
  // { "__proto__": { "isAdmin": true } } → ALL objects polluted!
});

// Later, in auth middleware:
if (user.isAdmin) {  // user.isAdmin is true (from prototype!)
  return next(); // ← auth bypass for ALL users!
}

// RCE via EJS template engine:
// Pollute: __proto__.outputFunctionName = "x;process.mainModule.require('child_process').execSync('whoami')//"
// When EJS renders a template → executes the shell command

// Detection: npm audit, Snyk, GitHub Dependabot
// Prevention: Object.freeze(Object.prototype) in app startup

Google Senior Frontend — Server-Side PP

Q: You discover a Node.js service in production has prototype pollution via Lodash merge. What's your incident response?

Immediate: (1) Add Object.freeze(Object.prototype) to the process entrypoint — prevents exploitation NOW. (2) Deploy hotfix with lodash 4.17.21+. (3) Check logs for suspicious __proto__ patterns in request bodies. (4) Restart all instances to clear any existing pollution. (5) Run npm audit across all services. Medium-term: (6) Add input validation middleware that rejects __proto__ in all JSON bodies. (7) Add ESLint rule to ban for...in, _.merge with user data. Long-term: (8) Migrate to structured schemas (Protobuf, Zod) that inherently prevent unknown keys.
