Pollution → XSS via Gadgets

A "gadget" is a piece of existing code that uses a property from an object without checking if it's an own property. If that property is polluted, the gadget becomes a vector for XSS.

// Example gadget in a template engine:
function render(template, data) {
  let html = template;
  for (let key in data) {  // ← 'in' operator walks prototype chain!
    html = html.replace(`{{${key}}}`, data[key]);
  }
  element.innerHTML = html; // ← dangerous sink
}

// Attacker pollutes Object.prototype:
Object.prototype['innerHTML'] = '<img src=x onerror=alert(1)>';

// Now any code that reads obj.innerHTML from the prototype gets XSS

Google Senior Frontend — Prototype Pollution to XSS

Q: In a security review, you find a library using for...in without hasOwnProperty. How critical is this?

Severity depends on: (1) Can user input reach Object.prototype? (any merge/extend of user data), (2) What does the for...in loop write to? (innerHTML = Critical, style property = Medium, log message = Low). If both conditions are met (user-controlled merge + for...in writing to DOM), it's a Critical XSS via prototype pollution gadget. Flag it and require: switch to Object.keys() or Object.entries(), or add hasOwnProperty check.

Q: How does Object.freeze(Object.prototype) interact with third-party libraries?

Object.freeze prevents any modification to Object.prototype — no new properties, no changes, no deletions. Most well-written libraries work fine because they don't extend Object.prototype. But some polyfills (e.g., for Array.flat, String.padStart in old environments) add methods to prototypes and would break. Test thoroughly. At Google, this is used in security-critical applications like Google Pay where prototype pollution would be catastrophic.
