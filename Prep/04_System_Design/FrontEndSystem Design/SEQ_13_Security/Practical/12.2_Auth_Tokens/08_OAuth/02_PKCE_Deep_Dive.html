PKCE Mechanism

// PKCE prevents authorization code interception attacks
// Required by OAuth 2.1 for ALL client types

// Step 1: Generate verifier (random string, 43-128 chars)
const verifier = generateRandomString(128);
// e.g., "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"

// Step 2: Create challenge (SHA-256 hash of verifier)
const challenge = base64url(SHA256(verifier));
// e.g., "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM"

// Step 3: Send challenge with auth request
// GET /authorize?...&code_challenge=E9Mel...&code_challenge_method=S256

// Step 4: Send verifier with token exchange
// POST /token { code, code_verifier: "dBjftJeZ4CVP..." }

// Step 5: Auth server verifies: SHA256(verifier) === stored challenge
// If match → issue tokens. If not → reject.

// Why it works:
// Attacker intercepts code but doesn't have the verifier
// Challenge was sent earlier and is a ONE-WAY hash
// Attacker can't derive verifier from challenge (SHA-256)

Q: Is PKCE necessary for confidential clients (those with a client_secret)?

Yes, per OAuth 2.1 (draft) PKCE is required for ALL clients. Even confidential clients benefit: (1) Defense in depth — if client_secret is compromised, PKCE still protects. (2) Prevents authorization code injection (attacker replays a stolen code). (3) Simplifies security analysis — one flow for all client types. Google's OAuth requires PKCE for all new client registrations. Auth0, Okta, and Azure AD all recommend PKCE universally.

Q: What's the difference between plain and S256 code_challenge_method?

plain: challenge = verifier (no hashing). Vulnerable if the authorization request is intercepted (attacker gets the verifier directly). S256: challenge = SHA-256(verifier). Even if intercepted, attacker can't reverse the hash. ALWAYS use S256. The spec allows plain as a fallback for environments without SHA-256, but in practice every modern browser and server supports S256.
