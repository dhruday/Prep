Why In-Memory?

// Problem: Every persistent storage is vulnerable
// localStorage → XSS reads it directly
// sessionStorage → XSS reads it directly
// Cookie without HttpOnly → XSS reads it
// Cookie with HttpOnly → CSRF sends it automatically

// Solution: Store access token ONLY in JavaScript memory
// Benefits:
// ✅ Not in any persistent storage → survives XSS theft (attacker
//    can read it during execution, but can't exfiltrate for later)
// ✅ Cleared on page reload → limits exposure
// ✅ Not auto-sent → no CSRF
// ✅ Not visible in DevTools storage panels

// Trade-off: Token lost on refresh → need silent refresh via cookie
// Flow: Page load → fetch /api/refresh (sends HttpOnly cookie)
//       → server returns new access token → store in memory

Full Implementation

// authManager.ts — Singleton auth manager using closure

interface AuthManager {
  login(username: string, password: string): Promise<boolean>;
  logout(): Promise<void>;
  getToken(): string | null;
  fetchWithAuth(url: string, options?: RequestInit): Promise<Response>;
}

function createAuthManager(): AuthManager {
  let accessToken: string | null = null;
  let refreshTimer: NodeJS.Timeout | null = null;

  const scheduleRefresh = (expiresIn: number) => {
    if (refreshTimer) clearTimeout(refreshTimer);
    // Refresh 1 minute before expiration
    refreshTimer = setTimeout(silentRefresh, (expiresIn - 60) * 1000);
  };

  const silentRefresh = async () => {
    const res = await fetch('/api/auth/refresh', {
      method: 'POST',
      credentials: 'include' // sends HttpOnly refresh cookie
    });
    if (res.ok) {
      const { token, expiresIn } = await res.json();
      accessToken = token;
      scheduleRefresh(expiresIn);
    } else {
      accessToken = null;
      // Redirect to login
    }
  };

  return {
    async login(username, password) { /* ... */ },
    async logout() { accessToken = null; },
    getToken: () => accessToken,
    async fetchWithAuth(url, options = {}) {
      if (!accessToken) await silentRefresh();
      let res = await fetch(url, {
        ...options,
        headers: { ...options.headers, Authorization: `Bearer ${accessToken}` }
      });
      if (res.status === 401) { // token expired mid-request
        await silentRefresh();
        res = await fetch(url, {
          ...options,
          headers: { ...options.headers, Authorization: `Bearer ${accessToken}` }
        });
      }
      return res;
    }
  };
}

export const auth = createAuthManager();

Q: If XSS can still call auth.getToken() during execution, isn't memory storage just security theater?

No, it's defense in depth. Key differences: (1) No persistence: XSS that runs once (e.g., reflected XSS) can't steal a token that's gone after page reload. (2) No offline access: Attacker can't browse DevTools → Storage → copy token at leisure. (3) Reduces blast radius: Stored XSS in localStorage means the attacker's payload runs on EVERY page load and always has the token. In memory, the token must be present at the exact moment the XSS executes. (4) Combined with short TTL (15min), even if stolen, the window is tiny. It's not perfect — but it's significantly better than localStorage.
