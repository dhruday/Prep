WebAuthn / Passkeys Architecture

// WebAuthn = W3C standard for passwordless authentication
// Passkeys = consumer-friendly name for discoverable WebAuthn credentials

// Three entities:
// 1. Relying Party (RP) — your web application
// 2. Authenticator — biometric, security key, or platform authenticator
// 3. Browser — mediates between RP and authenticator via WebAuthn API

// Key concept: Public-key cryptography
// Registration: Authenticator creates a key pair
//   Private key → stored in authenticator (never leaves device)
//   Public key → sent to server (stored in DB)
// Authentication: Server sends challenge → authenticator signs it
//   Server verifies signature with stored public key

// Why passkeys are better than passwords:
// ✅ Phishing-resistant (bound to origin)
// ✅ No shared secrets (nothing to steal from server DB)
// ✅ No password reuse across sites
// ✅ No brute-force attacks possible
// ✅ Built-in multi-factor (possession + biometric)

Passkey Types

// 1. Platform authenticator (built-in)
//    - Touch ID / Face ID (Apple)
//    - Windows Hello
//    - Android biometrics
//    Synced via cloud: iCloud Keychain, Google Password Manager

// 2. Roaming authenticator (external)
//    - YubiKey, Titan Security Key
//    - USB, NFC, or Bluetooth
//    Not synced — physical device required

// 3. Cross-device (hybrid)
//    - Use phone as authenticator for desktop login
//    - QR code + Bluetooth proximity check

Authentication Ceremony

// Step 1: Server generates challenge
const options = {
  challenge: crypto.getRandomValues(new Uint8Array(32)),
  rpId: "myapp.com",
  allowCredentials: [{  // optional for discoverable creds
    id: storedCredentialId,
    type: "public-key",
    transports: ["internal", "hybrid"]
  }],
  userVerification: "preferred",
  timeout: 60000
};

// Step 2: Browser prompts user (biometric/PIN)
const assertion = await navigator.credentials.get({
  publicKey: options
});

// Step 3: Send assertion to server
// assertion contains:
//   - authenticatorData (rpIdHash, flags, counter)
//   - clientDataJSON (type, challenge, origin)
//   - signature (signed by private key)

// Step 4: Server verifies
//   - Challenge matches what was issued
//   - Origin matches expected origin
//   - rpIdHash matches expected RP ID
//   - Signature valid with stored public key
//   - Counter increased (cloning detection)

Q: How are passkeys phishing-resistant?

The browser enforces origin binding at the protocol level. When creating a passkey, the credential is bound to the RP ID (e.g., "google.com"). During authentication, the browser checks: (1) The requesting origin matches the RP ID. (2) The challenge was received over a secure connection from that origin. If an attacker creates a phishing page at "g00gle.com", the browser won't find any credentials for that RP ID. Even if the user is tricked into clicking "Sign in," there are simply no passkeys available. The authenticator won't produce a valid signature because the rpIdHash in the clientDataJSON won't match. This is fundamentally different from passwords — where the user types the password into whatever form is shown.
