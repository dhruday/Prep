JWT Security Best Practices

// ═══════ SIGNING ═══════
✅ Use asymmetric signing (RS256 or ES256) for microservices
✅ Whitelist algorithms: { algorithms: ['RS256'] }
✅ Never accept alg: "none"
✅ Use 256-bit minimum secrets for HS256
✅ Implement key rotation via JWKS with kid header

// ═══════ CLAIMS ═══════
✅ Set short expiration: 5-15 min for access tokens
✅ Always include: iss, sub, aud, exp, iat
✅ Use jti for replay prevention (critical operations)
✅ Validate aud per service (prevent cross-service confusion)
✅ Minimize claims (don't duplicate DB data)
❌ Never put sensitive data in payload (not encrypted!)

// ═══════ STORAGE ═══════
✅ In-memory (JavaScript variable) for SPAs
✅ HttpOnly cookie via BFF pattern
❌ Never localStorage (XSS accessible)
❌ Never sessionStorage for long-lived tokens

// ═══════ TRANSPORT ═══════
✅ HTTPS only (TLS 1.3)
✅ Authorization: Bearer <token> header
✅ Set Referrer-Policy: no-referrer
❌ Never put tokens in URLs or query strings

// ═══════ REVOCATION ═══════
✅ Short-lived access + refresh token rotation
✅ Token blacklist for immediate revocation (Redis)
✅ token_version for "sign out from all devices"

Common JWT Anti-Patterns

// ❌ 1. Using JWT as a session replacement
// JWTs are for authorization, not session management.
// If you need server-side state anyway (for revocation),
// a session token is simpler and more secure.

// ❌ 2. Huge JWTs (putting everything in claims)
// JWT sent with EVERY request. 1KB → 10KB = huge bandwidth waste.
// Keep it under 1KB. Store data server-side, not in the token.

// ❌ 3. Using JWTs for CSRF tokens
// CSRF tokens should be unpredictable and tied to the session.
// JWTs are predictable (same token for the session lifetime).

// ❌ 4. Trusting JWT without verification
// NEVER decode a JWT and trust the claims without verifying.
// Always: jwt.verify() not jwt.decode().

// ❌ 5. Long-lived JWTs (days/weeks)
// The longer a JWT lives, the longer a stolen token is useful.
// Max 15 min for access tokens. Use refresh tokens for longevity.

// ❌ 6. Accepting tokens for any audience
// If service-A accepts tokens meant for service-B,
// a compromised service-A token works everywhere.

Google Senior Frontend — JWT Best Practices

Q: Walk me through how you'd implement JWT-based auth in a new microservices architecture.

Architecture: (1) Auth Service — sole issuer, has private key (ES256). Handles login, token issuance, refresh. Exposes /.well-known/jwks.json. (2) API Gateway — validates every JWT using cached JWKS public key. Checks exp, aud (gateway-specific), iss. Attaches decoded claims to request headers. (3) Microservices — receive pre-validated claims from gateway. Can optionally re-validate for zero-trust. Each service has its own aud value. (4) Tokens — Access: JWT, 5 min, in-memory. Refresh: opaque, HttpOnly cookie, 14 days, stored in Redis with rotation. jti for audit trail. (5) Revocation — Redis blacklist for access tokens (TTL = 5 min). Refresh token deletion for logout. token_version for "logout all." (6) Key rotation — ECDSA P-256, rotate monthly, dual-key JWKS during transition. (7) Monitoring — log all auth events, alert on unusual jti patterns, track token refresh rates.
