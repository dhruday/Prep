Blob URL Security

// Blob URLs: browser-local references to binary data
const blob = new Blob([sensitiveData], { type: 'text/plain' });
const url = URL.createObjectURL(blob);
// url = "blob:https://app.com/1a2b3c4d-5e6f-..."

// ⚠️ Blob URL risks:
// 1. Blob URLs persist until page unload OR explicit revoke
//    Forgetting to revoke = memory leak + data exposure

// 2. Blob URLs are accessible by any script on the page
//    XSS can enumerate and read blob URLs

// 3. Downloaded files from blob URLs can be recovered
//    Browser downloads directory, temp files

// ✅ Always revoke when done:
const url = URL.createObjectURL(blob);
// ... use the URL ...
URL.revokeObjectURL(url); // immediately after use

// For downloads:
const a = document.createElement('a');
a.href = url;
a.download = 'report.pdf';
a.click();
setTimeout(() => URL.revokeObjectURL(url), 100); // revoke after download starts

History API Data Exposure

// history.pushState/replaceState can store data
history.pushState({ token: 'secret123' }, '', '/page');

// ⚠️ Risks:
// 1. history.state is readable by ANY script on the page
console.log(history.state); // { token: 'secret123' }
// XSS can access it

// 2. State persists through navigation
// Back/forward buttons restore the state object
// Includes sensitive data you stored

// 3. Browser may serialize to disk (session restore)
// After crash/restart: state is restored from disk

// ✅ Safe patterns:
// Never store sensitive data in history state
history.pushState({ page: 'dashboard', tab: 'overview' }, '', '/dashboard');

// Clean up sensitive data from URLs:
if (location.search.includes('token')) {
  const token = new URLSearchParams(location.search).get('token');
  processToken(token);
  history.replaceState({}, '', location.pathname); // clean URL
}

Browser Cache Data Leaks

// Browsers cache responses for performance
// Cached data is readable by anyone with disk access

// ⚠️ What gets cached:
// 1. HTTP responses (images, HTML, JSON, files)
// 2. Service Worker Cache API entries
// 3. localStorage / sessionStorage
// 4. IndexedDB databases
// 5. Back/forward cache (bfcache)

// Prevent caching sensitive responses:
Cache-Control: no-store, no-cache, must-revalidate, private
Pragma: no-cache
Expires: 0

// Express.js:
app.get('/api/sensitive/*', (req, res, next) => {
  res.set({
    'Cache-Control': 'no-store, no-cache, must-revalidate, private',
    'Pragma': 'no-cache',
    'Expires': '0',
  });
  next();
});

// For Service Worker caches:
// Don't cache API responses containing PII
// Clear caches on logout:
caches.keys().then(names =>
  Promise.all(names.map(n => caches.delete(n)))
);

Google Senior Frontend — Data Leak Prevention

Q: A user reports seeing another user's data after logout/login. What happened?

Most likely causes: (1) Browser cache: API responses were cached. New user's requests served from cache with old user's data. Fix: Cache-Control: no-store on all authenticated endpoints. (2) Service Worker cache: SW cached responses without checking the user context. Clear SW caches on logout. (3) In-memory state: React/Redux store not cleared between sessions. Fix: Reset store on logout: dispatch({type: 'RESET'}). (4) localStorage: Previous user's data in localStorage. Fix: Clear on login: localStorage.clear() before setting new user data. Namespace by user ID. (5) Back/forward cache (bfcache): User hits back button → sees cached page with old user's data. Fix: Listen for pageshow event: window.addEventListener('pageshow', (e) => { if(e.persisted) location.reload() }). (6) CDN cache: Response cached without Vary: Authorization. Debugging: Check Network tab for 'disk cache' indicator. Inspect Application tab for stale entries.
