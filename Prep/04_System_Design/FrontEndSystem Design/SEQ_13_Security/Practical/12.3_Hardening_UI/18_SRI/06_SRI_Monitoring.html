SRI Failure Monitoring

// SRI failures indicate either:
// 1. CDN compromise (critical security event)
// 2. Deploy issue (stale hash in HTML)
// 3. CDN cache inconsistency

// ═══ Method 1: CSP report-uri ═══
Content-Security-Policy: require-sri-for script style; report-uri /csp-report

// SRI failures generate CSP violation reports
// Server receives JSON with violated directive details

// ═══ Method 2: Script error handlers ═══
const scripts = document.querySelectorAll('script[integrity]');
scripts.forEach(script => {
  script.addEventListener('error', (e) => {
    // Could be SRI failure, network error, or 404
    reportSRIFailure({
      src: script.src,
      integrity: script.integrity,
      timestamp: Date.now(),
      userAgent: navigator.userAgent,
    });
  });
});

// ═══ Method 3: Performance Observer ═══
const observer = new PerformanceObserver((list) => {
  list.getEntries().forEach(entry => {
    if (entry.transferSize === 0 && entry.decodedBodySize === 0) {
      // Resource blocked — potential SRI failure
      console.warn('Blocked resource:', entry.name);
    }
  });
});
observer.observe({ type: 'resource' });

// ═══ Method 4: RUM (Real User Monitoring) ═══
// Track SRI failure rate in production dashboards
// Alert if failure rate exceeds threshold (e.g., >0.1%)
// Correlate with deploy events to distinguish from attacks

SRI Best Practices Checklist

// ═══ MUST DO ═══
☐ SRI on ALL cross-origin <script> and <link> tags
☐ crossorigin="anonymous" on every SRI element
☐ Use SHA-384 (not SHA-256)
☐ Pin exact CDN versions (no @latest)
☐ Automate hash generation in build pipeline
☐ Monitor SRI failures in production

// ═══ SHOULD DO ═══
☐ Fallback to self-hosted copy on SRI failure
☐ SRI on self-hosted assets too (defense-in-depth)
☐ CI check: verify all CDN resources have integrity
☐ CSP: require-sri-for script style
☐ Test SRI in staging before production
☐ Document SRI process for team

// ═══ AVOID ═══
☒ SRI on resources that change frequently (analytics, widgets)
☒ SRI without fallback (site breaks if CDN changes)
☒ Manual hash management (always automate)
☒ Deploying HTML before assets (hash mismatch window)

// ═══ COMPLETE SECURITY HEADER SET ═══
Content-Security-Policy: default-src 'self'; script-src 'self' cdn.example.com;
  require-sri-for script style; report-uri /csp-report
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()

Google Senior Frontend — SRI Mastery

Q: Walk us through securing a production app from supply chain attacks.

Multi-layer supply chain defense: (1) Package management: Lock files (package-lock.json) committed. npm audit in CI. Renovate/Dependabot for automated updates with review. No wildcard versions (^, ~). Consider using npm overrides for transitive dependency control. (2) Build integrity: Reproducible builds — same input → same output. Store build hashes. SRI generated at build time, verified in CI. CSP with strict script-src. (3) CDN layer: SRI on all CDN-loaded resources. Fallback to self-hosted copies. Monitor CDN content hash via automated probes. Pin CDN versions. Use multiple CDNs with failover. (4) Runtime protection: CSP prevents unauthorized script execution. Trusted Types blocks DOM XSS. Service Worker verifies resource integrity. (5) Monitoring: CSP violation reports → real-time alerting. SRI failure dashboard. npm advisory monitoring. GitHub Dependabot security alerts. (6) Incident response: Playbook for supply chain compromise. Ability to switch from CDN → self-hosted within minutes. Kill switch to block compromised script. Post-incident: audit all affected user sessions.
