Complete Defense Strategy

// Layer 1: HTTP Headers (PRIMARY)
X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'none'

// Layer 2: SameSite Cookies
Set-Cookie: session=abc; SameSite=Strict; Secure; HttpOnly
// Even if framed, cookies won't be sent → unauthenticated

// Layer 3: JavaScript Detection (SUPPLEMENT)
if (self !== top) {
  document.documentElement.style.display = 'none';
}

// Layer 4: UI Confirmation Patterns
// For dangerous actions: require explicit confirmation
// - Type "DELETE" to confirm
// - CAPTCHA before irreversible actions
// - Re-authentication for sensitive operations
// - Random confirmation codes

// Layer 5: Timing Defenses
// Delay enabling dangerous buttons (500ms after page load)
// Require mouse movement before allowing clicks
// Detect rapid double-clicks on sensitive buttons

// Layer 6: Visibility Detection
// IntersectionObserver to check if page is visible
// document.visibilityState check
// Disable forms if page is within an iframe

Google Senior Frontend — UI Redressing

Q: How do you protect sensitive actions beyond frame protection headers?

Defense in depth for dangerous operations: (1) Interaction confirmation: "Type DELETE to confirm" — cannot be clickjacked because it requires keyboard input. Google uses this for account deletion. (2) Re-authentication: Require password/OTP before sensitive actions (change email, download data, delete account). Even if session is valid, re-verify the human. (3) CSRF tokens: One-time tokens for state-changing operations. The hidden iframe can trigger clicks but can't read the CSRF token from the page (same-origin policy). (4) Rate limiting on actions: Even if clickjacked, limit damage. One delete per user per minute. (5) Audit logging: Log all sensitive actions with timestamp, IP, user-agent. Automated patterns (many actions in seconds) trigger alerts. (6) Undo mechanisms: "Account scheduled for deletion. 30-day grace period." The clickjacking damage is reversible.
