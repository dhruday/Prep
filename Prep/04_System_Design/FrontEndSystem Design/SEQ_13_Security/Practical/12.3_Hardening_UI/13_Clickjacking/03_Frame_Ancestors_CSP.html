CSP frame-ancestors Directive

// frame-ancestors: controls WHO can embed your page
// (The opposite of frame-src, which controls what YOU embed)

Content-Security-Policy: frame-ancestors 'none'
// No one can frame this page (equivalent to X-Frame-Options: DENY)

Content-Security-Policy: frame-ancestors 'self'
// Only same origin can frame (equiv to SAMEORIGIN)

Content-Security-Policy: frame-ancestors 'self' https://partner.com
// Same origin + specific partner

Content-Security-Policy: frame-ancestors *.trusted.com
// Any subdomain of trusted.com

// IMPORTANT distinctions:
// frame-ancestors → WHO can embed ME (clickjacking defense)
// frame-src      → WHAT can I embed (what iframes I load)
// child-src      → Legacy, use frame-src + worker-src instead

// Express.js:
app.use((req, res, next) => {
  res.setHeader('Content-Security-Policy',
    "frame-ancestors 'self' https://partner.com");
  next();
});

Configuration Scenarios

// ═══ Scenario 1: Banking App ═══
// Never allow framing
Content-Security-Policy: frame-ancestors 'none'

// ═══ Scenario 2: SaaS Dashboard ═══
// Only frame within own app
Content-Security-Policy: frame-ancestors 'self'

// ═══ Scenario 3: Embeddable Widget ═══
// Payment form embedded by approved merchants
Content-Security-Policy: frame-ancestors
  https://merchant1.com
  https://merchant2.com
  https://*.bigretailer.com

// ═══ Scenario 4: OAuth Popup ═══
// Consent page in popup, not iframe
Content-Security-Policy: frame-ancestors 'none'
// Use window.open() for OAuth, not iframes

// ═══ Anti-pattern: Too permissive ═══
Content-Security-Policy: frame-ancestors *
// ❌ Anyone can embed your page = NO clickjacking protection

frame-ancestors vs X-Frame-Options

Feature             | X-Frame-Options | frame-ancestors
─────────────────────┼─────────────────┼────────────────
Multiple origins     | ❌              | ✅
Wildcard subdomains  | ❌              | ✅
Browser support      | All (legacy)    | All modern
Priority when both   | Lower           | Higher (wins)
Meta tag support     | ❌              | ❌
Report-only mode     | ❌              | ✅ (via CSP)

// Key insight: frame-ancestors CANNOT be set via <meta> tag
// It MUST be set as an HTTP header
// This is by design — if it were in meta, an attacker
// could inject a meta tag to override it via XSS

// When both are present:
// Modern browsers use frame-ancestors and IGNORE X-Frame-Options
// Old browsers (IE11) use X-Frame-Options

// Best practice: Set BOTH
X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'none'

Google Senior Frontend — frame-ancestors

Q: Your app needs to be embedded by partners. How do you securely configure frame-ancestors?

(1) Maintain an allowlist of partner origins in server config (not hardcoded). (2) Set frame-ancestors dynamically per request: check Referer/Origin header against allowlist, set CSP header with matching origins. (3) Use report-uri to monitor embedding: Content-Security-Policy-Report-Only to test before enforcing. (4) For embeddable widgets: serve from a separate subdomain (widget.yourapp.com) with its own relaxed CSP. The main app (app.yourapp.com) keeps strict frame-ancestors 'none'. (5) Communication between parent and iframe: window.postMessage with strict origin validation. Never use '*' as target origin. (6) Consider: iframes from different origins don't get cookies with SameSite=Strict. Use token-based auth for embedded content. (7) Regular audits: who is embedding your content? CSP reports + server logs.
