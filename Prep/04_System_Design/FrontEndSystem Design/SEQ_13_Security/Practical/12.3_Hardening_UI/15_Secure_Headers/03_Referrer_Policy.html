Referrer-Policy Values

// The Referer header tells the destination where you came from
// Page: https://app.com/user/123?token=secret
// Click link to external site → Referer sent!

// Referrer-Policy values (most → least restrictive):

no-referrer
// Never send Referer. Safest but breaks analytics.

no-referrer-when-downgrade
// Send Referer for HTTPS→HTTPS, not HTTPS→HTTP (browser default)

origin
// Send only origin: https://app.com (no path/query)

origin-when-cross-origin
// Same origin: full URL. Cross-origin: just origin.

same-origin
// Send full Referer to same origin, nothing to cross-origin

strict-origin
// Send origin only (no path), but not on HTTPS→HTTP downgrade

strict-origin-when-cross-origin ← RECOMMENDED
// Same origin: full URL. Cross-origin: origin only. No downgrade.

unsafe-url
// Always send full URL including path and query. DANGEROUS.

Information Leak via Referer

// ═══ What leaks without Referrer-Policy ═══

// Page URL: https://app.com/messages/inbox?user=alice&token=abc123
// User clicks external link → Referer header sent:
Referer: https://app.com/messages/inbox?user=alice&token=abc123

// Leaked: username, auth token, URL structure

// ═══ Real-world leaks ═══

// 1. Password reset links
//    URL: /reset?token=abc123
//    If page has external resources (images, analytics)
//    → Reset token leaked to third parties

// 2. Search queries
//    /search?q=medical+condition
//    → Third-party ads see health searches

// 3. Internal URLs
//    /admin/users/edit/42
//    → Reveals admin paths, user IDs

// 4. OAuth state parameters
//    /callback?code=auth_code&state=csrf_token
//    → OAuth codes leaked before exchange

// Defense: Use strict-origin-when-cross-origin
// Cross-origin requests only send: https://app.com
// No path, no query, no sensitive data

Setting Referrer-Policy

// Method 1: HTTP header (recommended)
Referrer-Policy: strict-origin-when-cross-origin

// Method 2: Meta tag
<meta name="referrer" content="strict-origin-when-cross-origin">

// Method 3: Per-link
<a href="https://external.com" referrerpolicy="no-referrer">Link</a>

// Method 4: Per-element (img, script, iframe)
<img src="https://cdn.com/img.png" referrerpolicy="no-referrer">

// Method 5: fetch API
fetch(url, { referrerPolicy: 'no-referrer' });

// Express.js:
app.use((req, res, next) => {
  res.setHeader('Referrer-Policy', 'strict-origin-when-cross-origin');
  next();
});

// Per-page override for sensitive pages:
app.get('/reset-password', (req, res) => {
  res.setHeader('Referrer-Policy', 'no-referrer');
  res.render('reset');
});

Google Senior Frontend — Referrer-Policy

Q: How does Referrer-Policy interact with analytics and attribution?

Tension: Analytics wants full URLs for traffic attribution. Security wants minimal referrer. Balance: strict-origin-when-cross-origin is the sweet spot. Same-site analytics (Google Analytics on your domain): Gets full URL including path — internal navigation tracking works. Cross-site: Only gets origin (https://yourapp.com) — enough for traffic source attribution but no path/query leak. Override per link: External links that need full referrer (affiliate tracking): <a referrerpolicy="no-referrer-when-downgrade">. Sensitive pages override to no-referrer. For Google Tag Manager: Works with strict-origin-when-cross-origin because it's loaded same-origin. URL parameters: Never put tokens, PII, or sensitive data in URLs. Use POST bodies, headers, or session storage. Even with strict referrer policy, URLs appear in browser history, server logs, and shared screenshots.
