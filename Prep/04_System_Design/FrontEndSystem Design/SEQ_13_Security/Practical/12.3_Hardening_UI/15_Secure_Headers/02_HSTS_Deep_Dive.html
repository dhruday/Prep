How HSTS Works

// HSTS header (sent ONLY over HTTPS):
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload

// Behavior after receiving HSTS:
// 1. Browser stores: "example.com uses HSTS until [date]"
// 2. Any HTTP request to example.com → auto-upgraded to HTTPS
// 3. If HTTPS certificate is invalid → HARD FAIL (no bypass)
//    Normal: "Your connection is not private" with "Proceed anyway"
//    HSTS: No "Proceed" option. Connection blocked.

// Parameters:
// max-age=63072000  → 2 years (seconds)
// includeSubDomains → Applies to all *.example.com
// preload           → Eligible for browser preload list

// Rollout strategy:
// Week 1: max-age=300 (5 minutes) — test
// Week 2: max-age=86400 (1 day)
// Week 3: max-age=604800 (1 week)
// Month 2: max-age=63072000 (2 years) + preload
// Gradual increase prevents lockout if cert issues arise

SSL Stripping Attack

// Without HSTS:
// 1. User types "example.com" in browser
// 2. Browser sends HTTP request (not HTTPS)
// 3. MITM intercepts HTTP request
// 4. MITM connects to example.com via HTTPS
// 5. MITM relays content to user via HTTP
// 6. User sees content but connection is NOT encrypted
// 7. MITM can read/modify all traffic

//    User ←─ HTTP ─→ Attacker ←─ HTTPS ─→ Server
//    (no padlock)      (reads everything)   (thinks it's secure)

// With HSTS:
// 1. User types "example.com"
// 2. Browser internal redirect: "I know this is HSTS → HTTPS"
// 3. HTTP request NEVER sent
// 4. MITM has nothing to intercept

// HSTS weakness: First visit
// First visit has no HSTS cached → HTTP sent → interceptable
// Solution: HSTS Preload List (next tab)

HSTS Preload List

// Preload = Hardcoded HSTS in browser source code
// Even FIRST visit uses HTTPS (no TOFU problem)

// Requirements for preload:
// 1. Valid HTTPS certificate
// 2. Redirect HTTP → HTTPS on same host
// 3. HSTS header on HTTPS response
// 4. max-age ≥ 63072000 (2 years)
// 5. includeSubDomains directive
// 6. preload directive

// Submit at: https://hstspreload.org

// ⚠️ WARNING: Preload is HARD TO UNDO
// Removal takes months (browser release cycles)
// If you lose your cert or need HTTP: users can't access your site
// Make sure ALL subdomains support HTTPS before submitting

// Query: Check if domain has HSTS
// Delete: Remove HSTS for testing

// Notable preloaded domains:
// google.com, facebook.com, twitter.com, github.com

Google Senior Frontend — HSTS

Q: What's the risk of setting includeSubDomains on HSTS?

includeSubDomains forces HTTPS on ALL subdomains: *.example.com. Risks: (1) If ANY subdomain doesn't support HTTPS (legacy internal tool at internal.example.com), it becomes inaccessible. (2) Development/staging subdomains without valid certs are blocked. (3) If a subdomain's cert expires, no user bypass is possible (HSTS prevents "proceed anyway"). (4) Third-party services on your subdomains may not support HTTPS. Mitigation: (1) Audit ALL subdomains before enabling. Use Certificate Transparency logs: crt.sh/?q=%.example.com. (2) Start without includeSubDomains, add it after confirming all subdomains work. (3) Use short max-age during testing (300 seconds). (4) Wildcard certs cover all subdomains easily. For preload: includeSubDomains is REQUIRED. The .dev and .app TLDs are entirely preloaded — every domain under them forces HTTPS.
