1. What Is an API Contract?

// An API contract is the formal agreement between frontend and backend:
// - What endpoints exist and what methods they support
// - What request parameters/body shapes are expected
// - What response shapes come back (fields, types, required/optional)
// - What error shapes look like
// - What status codes mean what

// Without explicit contracts:
// Backend renames "user_name" → "userName" → frontend silently breaks
// Backend makes optional field required → frontend sends null → 500 error
// Backend removes deprecated field → frontend shows "undefined" to user

// Contract mechanisms (from weakest to strongest):
// 1. Documentation (Confluence/Wiki)    → often stale, not machine-checked
// 2. OpenAPI/Swagger spec              → machine-readable, generates code
// 3. Zod/Yup runtime validation        → catches violations at runtime
// 4. TypeScript SDK generation          → compile-time type safety
// 5. Consumer-driven contract tests     → CI fails if contract breaks
// 6. tRPC / GraphQL codegen             → end-to-end type-safe, zero drift

2. OpenAPI → TypeScript Generation

// OpenAPI spec (source of truth, lives in backend repo):
// openapi.yaml
// paths:
//   /products/{id}:
//     get:
//       responses:
//         '200':
//           content:

//               schema:
//                 $ref: '#/components/schemas/Product'
//
// components:
//   schemas:
//     Product:
//       type: object
//       required: [id, name, price]
//       properties:
//         id: { type: string, format: uuid }
//         name: { type: string }
//         price: { type: number }

// Generate TypeScript types at build time:
// npx openapi-typescript ./api/openapi.yaml --output ./src/api/types.ts
// → If backend removes 'price', TypeScript compilation fails
// → CI catches it before deployment

3. Zod as Runtime Contract Validator

// TypeScript types disappear at runtime — they can't catch
// a backend change that deployed without updating the spec
// Zod validates at runtime: catches contract violations in production

const ProductSchema = z.object({
  id: z.string().uuid(),
  name: z.string(),
  price: z.number().nonnegative(),
  description: z.string().optional(),
});

async function fetchProduct(id) {
  const raw = await fetch(`/api/products/${id}`).then(r => r.json());
  const result = ProductSchema.safeParse(raw);

  if (!result.success) {
    // Log to Sentry/Datadog — backend changed without telling us
    reportContractViolation({
      endpoint: `/api/products/${id}`,
      errors: result.error.flatten(),
      rawResponse: raw,
    });
    throw new Error('API contract violation');
  }

  return result.data;
}

2. Consumer-Driven Contract Testing (Pact)

// Frontend (consumer) defines what it EXPECTS from the API
// Backend (provider) verifies it DELIVERS what consumer expects

// Frontend writes a Pact test:
// "When I call GET /api/products/123,
//  I expect { id: string, name: string, price: number }"
//
// This generates a "pact file" (JSON contract)
// Pact file is shared with backend team (via Pact Broker)
//
// Backend runs pact verification:
// "Does my API actually return { id, name, price } for GET /products/123?"
// If no → CI fails → backend can't deploy a breaking change

// This is the ONLY approach that catches breaking changes
// where backend and frontend release independently

3. Defensive Deserialization Pattern

// Never trust API responses — validate and transform at the boundary

function createApiParser(schema) {
  return async function(response) {
    const raw = await response.json();
    const result = schema.safeParse(raw);

    if (result.success) return result.data;

    // Strategy: partial parse — use what's valid, default the rest
    const partial = {};
    for (const [key, value] of Object.entries(raw)) {
      const fieldResult = schema.shape[key]?.safeParse(value);
      if (fieldResult?.success) partial[key] = fieldResult.data;
    }

    // Log what failed for monitoring
    logContractDrift({
      expected: Object.keys(schema.shape),
      received: Object.keys(raw),
      errors: result.error.issues,
    });

    return partial; // Graceful degradation — show what we can
  };
}

FAANG Interview Questions

Q1: How do you ensure frontend-backend API compatibility in a microservices architecture?
I'd implement a contract-first approach with three layers. First, every service publishes an OpenAPI spec as the single source of truth. We generate TypeScript types from these specs at build time using openapi-typescript — if a backend changes a response shape, our TypeScript compilation fails in CI before deployment. Second, I add Zod runtime validation at the API boundary as a safety net — if a backend team deploys without updating the spec, our monitoring catches the contract violation in production. Third, for critical paths (checkout, auth), I'd use consumer-driven contract tests with Pact — frontend defines what it expects, and the backend's CI verifies it still delivers those shapes. This gives us both compile-time safety and runtime resilience.
Follow-up: What happens when you need to support two API versions simultaneously during migration?
Q2: URL versioning vs header versioning — which do you prefer and why?
For most teams, I recommend URL path versioning (/api/v1/products). It's explicit — you can see the version in browser DevTools, API logs, and monitoring dashboards without inspecting headers. It's cache-friendly — CDNs and browsers cache /v1/products and /v2/products separately without custom Vary headers. The main argument against it (URL pollution) doesn't matter in practice because you rarely have more than 2-3 active versions. Header-based versioning (like Stripe's date-based API-Version) is elegant for large public APIs with many consumers who pin to specific versions. But for internal APIs or B2B, URL versioning wins for simplicity and debuggability.
Follow-up: How do you deprecate and sunset old API versions?
Q3: How would you handle a backend deploying a breaking change without warning?
This is where runtime validation saves you. If I have Zod schemas at the API boundary, the contract violation is caught immediately and logged to our error monitoring (Sentry/Datadog) with the exact field differences. The frontend gracefully degrades — showing cached data or partial results rather than crashing. Longer-term prevention: I'd establish a contract review process where any schema change requires updating the OpenAPI spec, which triggers a compatibility check against consumer expectations. If using Pact, the backend's CI literally cannot deploy a breaking change because the consumer contract test will fail. The key principle: trust but verify at the boundary.
Follow-up: How does this work with GraphQL where the schema is self-documenting?
Q4: What's the difference between frontend and backend contract validation?
Backend validation is authoritative — it enforces business rules and data integrity (a price must be positive, an email must be unique). If backend validation fails, it's a hard error. Frontend validation is defensive — it protects against unexpected response shapes and provides fast user feedback. Frontend validates outgoing requests (form inputs) to prevent unnecessary round-trips, and incoming responses (Zod parsing) to prevent rendering crashes. The critical insight: frontend validation is never a substitute for backend validation. A malicious user can bypass any frontend check. Frontend validation exists for UX and resilience, not security.
Follow-up: Should frontend and backend share validation schemas? How?

1. Complete API Client with Contract Validation

class TypeSafeApiClient {
  constructor(baseUrl) {
    this.baseUrl = baseUrl;
    this.schemas = new Map();
  }

  register(endpoint, responseSchema) {
    this.schemas.set(endpoint, responseSchema);
    return this;
  }

  async get(endpoint, params = {}) {
    const url = new URL(endpoint, this.baseUrl);
    Object.entries(params).forEach(([k, v]) => url.searchParams.set(k, v));

    const response = await fetch(url);
    if (!response.ok) throw new ApiError(response.statusText, response.status);

    const raw = await response.json();
    const schema = this.schemas.get(endpoint);

    if (schema) {
      const result = schema.safeParse(raw);
      if (!result.success) {
        console.error('Contract violation:', endpoint, result.error.issues);
        // Report but don't crash — return raw data as fallback
        reportContractViolation(endpoint, result.error);
      } else {
        return result.data;
      }
    }
    return raw;
  }
}

// Usage:
const api = new TypeSafeApiClient('https://api.example.com')
  .register('/products', z.array(ProductSchema))
  .register('/users/me', UserSchema);

const products = await api.get('/products', { page: '1' });

2. Version Migration Helper

// Adapter pattern for supporting multiple API versions during migration

const productAdapters = {
  v1: (raw) => ({
    id: raw.product_id,       // v1 used product_id
    name: raw.product_name,   // v1 used product_name
    price: raw.price_cents / 100, // v1 sent cents
  }),
  v2: (raw) => ({
    id: raw.id,               // v2 uses id
    name: raw.name,           // v2 uses name
    price: raw.price,         // v2 sends decimal
  }),
};

function parseProduct(raw, apiVersion) {
  const adapter = productAdapters[apiVersion] ?? productAdapters.v2;
  return adapter(raw);
}

// Feature flag controls which version we use
const API_VERSION = featureFlags.get('products-api-version') ?? 'v1';

Versioning Strategy Decision

Is it a public API with external consumers?
├── Yes → Header versioning (date-based, like Stripe)
└── No (internal)
    ├── Microservices with independent deploy?
    │   ├── Yes → URL versioning (/api/v2/) + contract tests
    │   └── No → Zod validation + feature flags for migration
    └── Full-stack TypeScript?
        └── Use tRPC — zero contract drift by design

Production Checklist

✅ Every API has an OpenAPI spec or GraphQL schema
✅ TypeScript types generated from spec (not hand-written)
✅ Zod validation at API boundary for critical endpoints
✅ CI breaks if spec changes don't match implementation
✅ New API fields are ALWAYS optional (additive-only changes)
✅ Removing a field requires deprecation notice + migration window
✅ Error response shapes are part of the contract (not just success)
✅ Monitor contract violations in production (Sentry/Datadog)
✅ Version sunset policy defined (e.g., support N-1 for 6 months)
✅ Adapters isolate version differences from business logic
