1. GraphQL Execution Pipeline — Parse → Validate → Execute → Serialize

Every GraphQL request passes through a deterministic four-phase pipeline defined in the spec (June 2018+). Understanding each phase is critical for debugging, performance tuning, and security hardening.

// The four phases inside graphql-js execute()
Phase 1 — Parse
  Source text → AST (DocumentNode)
  Lexer tokenises the raw string, parser builds the tree.
  Errors here = SyntaxError (malformed query).
  Cost: O(n) where n = query length. Cached via persisted queries.

Phase 2 — Validate
  AST + Schema → validation errors[]
  Runs ~30 built-in rules (FieldsOnCorrectType, KnownFragmentNames,
  NoUnusedVariables, UniqueOperationNames, etc.)
  Custom rules inject here: depth-limiting, complexity analysis.
  Cost: O(fields × rules). Run ONCE per unique query.

Phase 3 — Execute
  AST + Schema + Resolvers + rootValue + context → data | errors
  Walks the AST depth-first. For each field:
    1. Resolve field value (call resolver or use default)
    2. Complete value (coerce scalars, recurse objects, iterate lists)
  Mutations execute root fields SERIALLY (spec §6.3.1).
  Queries execute root fields in PARALLEL (implementation-dependent).

Phase 4 — Serialize
  Result map → JSON string
  Custom scalars call serialize(). Errors get positions attached.
  Extensions field (tracing, cache hints) appended here.
💡 At Meta, the parse + validate phases are entirely eliminated in production through Relay's persisted queries. The server receives only a query ID + variables, looks up a pre-validated AST, and jumps directly to execute.

2. Resolver Tree Traversal — Depth-First Execution Model

GraphQL resolvers form an implicit tree that mirrors the query shape. The execution engine walks this tree depth-first, resolving parent fields before children. This creates the N+1 problem and motivates DataLoader.

// Query
query {
  users {          ← resolver: Query.users → User[]
    name           ← resolver: User.name (default)
    posts {        ← resolver: User.posts → Post[] (N calls!)
      title        ← resolver: Post.title (default)
      comments {   ← resolver: Post.comments → Comment[] (N×M calls!!)
        body
      }
    }
  }
}

Execution order:
1. Query.users()          → [User1, User2, ..., UserN]
2. User.posts(User1)      → [Post1a, Post1b]    ← called N times
   User.posts(User2)      → [Post2a]
   ...
3. Post.comments(Post1a)  → [Comment1, ...]      ← called Σ(posts) times
   Post.comments(Post1b)  → [...]
   ...

Without DataLoader: 1 + N + N*M database calls
With DataLoader:    1 + 1 + 1 = 3 batched calls (one per level)

3. DataLoader — Tick-Coalescing Batch Strategy

DataLoader collects all `.load(key)` calls within a single tick of the event loop, then dispatches a single batch function. This is the standard solution to the N+1 problem in GraphQL servers.

// How DataLoader coalesces within one event loop tick

Microtask queue view:
┌─────────────────────────────────────────────────────┐
│ Tick 1: Resolvers call loader.load(id) for N users  │
│   load(1) → enqueue key 1                          │
│   load(2) → enqueue key 2                          │
│   load(5) → enqueue key 5                          │
│                                                     │
│ End of tick: process.nextTick / Promise.resolve()   │
│   → batchFn([1, 2, 5]) fires ONCE                  │
│   → SQL: SELECT * FROM posts WHERE user_id IN(1,2,5)│
│   → Results mapped back to individual promises      │
└─────────────────────────────────────────────────────┘

Key implementation details:
• Scheduling uses process.nextTick (Node) or Promise.resolve().then()
• Keys are de-duplicated by identity (Map) — load(1) twice = 1 batch key
• Cache is per-request (new DataLoader per context) to avoid stale data
• maxBatchSize splits large batches (default: Infinity)
• Results array MUST match keys array 1:1 in length and order
💡 DataLoader was created at Facebook specifically for GraphQL. It's language-agnostic in concept — Java has java-dataloader, Go has dataloaden. The pattern: collect keys → batch fetch → distribute results.

4. Type System Deep Dive — Scalars, Enums, Interfaces, Unions, Input Types, Directives

Scalar Types — Leaf nodes. Built-in: Int, Float, String, Boolean, ID
  Custom: scalar DateTime — must define serialize/parseValue/parseLiteral
  Used for: dates, JSON blobs, URLs, email validation

Enum Types — Finite set of allowed values
  enum Role { ADMIN EDITOR VIEWER }
  Serialised as strings in JSON. Internal values can differ (mapper).

Interface Types — Abstract types with guaranteed fields
  interface Node { id: ID! }
  Implementing types MUST define all interface fields.
  Resolved via __resolveType or isTypeOf.
  Critical for Relay's Global Object Identification pattern.

Union Types — "one of" without shared fields
  union SearchResult = User | Post | Comment
  Queried via inline fragments: ... on User { name }
  Must have __resolveType. Cannot have fields of their own.

Input Types — Structured arguments
  input CreateUserInput { name: String! email: String! }
  Cannot have fields that return object types (no cycles).
  Validated at the validate phase before resolvers run.

Directives — Metadata annotations
  Built-in: @skip(if: Boolean!), @include(if: Boolean!), @deprecated
  Custom: @auth(requires: Role), @cacheControl(maxAge: Int)
  Schema directives transform the schema at build time (SchemaTransformer).
  Query directives modify execution at runtime.

5. Subscription WebSocket Protocol — graphql-ws

Protocol: graphql-transport-ws (newer) vs subscriptions-transport-ws (legacy)

// Connection lifecycle (graphql-transport-ws)
Client → Server: { type: "connection_init", payload: { authToken } }
Server → Client: { type: "connection_ack" }    // within connectionInitWaitTimeout

Client → Server: { id: "1", type: "subscribe", payload: { query, variables } }
Server → Client: { id: "1", type: "next", payload: { data: {...} } }  // repeated
Server → Client: { id: "1", type: "complete" }  // stream ended

Client → Server: { id: "1", type: "complete" }  // client unsubscribes

Key differences from legacy protocol:
• Single WebSocket per client (multiplexed via id)
• Proper acknowledgement flow — no race conditions
• Server can send "error" per subscription (not connection-level)
• Lazy connections: WS opens only on first subscribe
• Supports keep-alive via ping/pong frames (not GQL messages)

6. Persisted Queries & Automatic Persisted Queries (APQ)

Persisted Queries (Relay-style)
  Build time: compiler extracts all queries → generates ID (SHA256 hash)
  Deployed: server has allowlist map { queryId → AST }
  Runtime: client sends { id: "abc123", variables: {} }
  Benefits: no parse/validate, smaller payload, query allowlisting (security)

Automatic Persisted Queries (Apollo APQ)
  No build step required. Uses a negotiate protocol:
  1. Client sends: { extensions: { persistedQuery: { sha256Hash: "abc" } } }
  2. Server checks cache:
     → HIT:  execute cached query
     → MISS: respond PersistedQueryNotFound
  3. Client retries with full query text + hash
  4. Server stores hash → query, executes
  5. Subsequent requests use hash only

Trade-offs:
  Persisted: max security (allowlist), max perf, requires build pipeline
  APQ: zero config, gradual, but no allowlisting on first request

7. Query Complexity & Depth Limiting — Security

Depth Limiting
  Rejects queries exceeding a max nesting depth.
  Implementation: walk AST, track depth counter on SelectionSet entry.
  Typical limit: depth ≤ 10 (GitHub API uses 10).

Query Complexity Analysis
  Assigns cost to each field, sums total, rejects if over budget.

  type Query {
    users(first: Int!): [User!]! @cost(complexity: 2, multipliers: ["first"])
  }

  Example: users(first: 50) { posts(first: 20) { title } }
  Complexity = 2*50 + 1*50*20 = 100 + 1000 = 1100
  Budget: 1000 → REJECTED

Additional protections:
  • Query allowlisting (persisted queries only)
  • Timeout per resolver (resolve-level cancellation)
  • Rate limiting (token bucket per client + per complexity score)
  • Disable introspection in production
  • Batch attack prevention: limit concurrent operations in a document

1. Apollo Normalized Cache — __typename + id → __ref

Apollo Client's InMemoryCache stores a flat, normalized lookup table. Every entity with __typename and id (or a custom keyFields) gets a unique cache key. References replace nested objects.

// Query result
{
  "data": {
    "user": {
      "__typename": "User",
      "id": "42",
      "name": "Alice",
      "posts": [
        { "__typename": "Post", "id": "100", "title": "GraphQL at Scale" },
        { "__typename": "Post", "id": "101", "title": "Federation Deep Dive" }
      ]
    }
  }
}

// Normalized cache store
{
  "User:42": {
    "__typename": "User",
    "id": "42",
    "name": "Alice",
    "posts": [
      { "__ref": "Post:100" },
      { "__ref": "Post:101" }
    ]
  },
  "Post:100": {
    "__typename": "Post",
    "id": "100",
    "title": "GraphQL at Scale"
  },
  "Post:101": {
    "__typename": "Post",
    "id": "101",
    "title": "Federation Deep Dive"
  },
  "ROOT_QUERY": {
    "user": { "__ref": "User:42" }
  }
}

Why this matters:
• Updating Post:100 title in ANY query automatically updates ALL queries
  referencing that post — single source of truth.
• Avoids data duplication across dozens of queries.
• Enables optimistic UI: write to cache → render → await server confirm.

2. Cache Policies — Choosing the Right Fetch Strategy

cache-first (default)
  Check cache → if complete, return cached data (no network).
  If cache miss or incomplete → fetch from network → write to cache.
  Best for: relatively static data (user profiles, config).

network-only
  Always fetch from network. Still writes to cache for future reads.
  Best for: real-time data (notifications, live feeds).

cache-and-network
  Return cached data immediately (fast paint), THEN fetch from network.
  If server data differs, re-render with updated data.
  Best for: lists that need fast UX but should show fresh data.

no-cache
  Always fetch from network. Does NOT write result to cache.
  Best for: sensitive data, one-off lookups, search results.

cache-only
  Read from cache ONLY. Errors if data not in cache.
  Best for: offline mode, reading data written by another query.

Decision heuristic:
  "How stale can this data be?"
    → 0 seconds: network-only
    → seconds–minutes: cache-and-network
    → minutes–hours: cache-first
    → never fetched independently: cache-only
    → must not be cached at all: no-cache

3. Fragment Colocation — Components Own Their Data

// Each component declares EXACTLY what data it needs

// UserAvatar.tsx
export const USER_AVATAR_FRAGMENT = gql`
  fragment UserAvatarFields on User {
    id
    avatarUrl
    displayName
  }
`;

// UserBio.tsx
export const USER_BIO_FRAGMENT = gql`
  fragment UserBioFields on User {
    id
    bio
    joinedDate
  }
`;

// UserProfile.tsx — parent composes fragments
const USER_PROFILE_QUERY = gql`
  query UserProfile($id: ID!) {
    user(id: $id) {
      ...UserAvatarFields
      ...UserBioFields
    }
  }
  ${USER_AVATAR_FRAGMENT}
  ${USER_BIO_FRAGMENT}
`;

Benefits:
1. Adding a field to UserAvatar automatically includes it in the query.
2. Removing UserAvatar component → its fragment unused → tree-shaken.
3. Each component can derive TypeScript types from its own fragment.
4. No over-fetching: the query is the union of all active fragments.
5. Relay enforces this pattern via its compiler — it's not optional.
💡 At Meta, fragment colocation is mandatory. The Relay compiler statically validates that every component reads only from its declared fragment. This guarantee enables safe, automated query optimizations across thousands of components.

4. Federation vs Schema Stitching

Schema Stitching (Legacy)
  Gateway merges schemas from multiple services using type merging.
  Gateway knows about ALL schemas — single point of coupling.
  Resolvers delegated via delegateToSchema().
  Problem: gateway grows complex, hard to version independently.

Apollo Federation (v2)
  Each service ("subgraph") owns its types and extends shared entities.
  The gateway ("router") composes subgraphs into a supergraph.
  Services are independently deployable.

  // Users subgraph
  type User @key(fields: "id") {
    id: ID!
    name: String!
    email: String!
  }

  // Posts subgraph — extends User
  type User @key(fields: "id") {
    id: ID!
    posts: [Post!]!       ← added by Posts service
  }

  type Post @key(fields: "id") {
    id: ID!
    title: String!
    author: User!
  }

Query plan (federation):
  query { user(id: "42") { name posts { title } } }

  1. Router → Users subgraph: Fetch { name } for User:42
  2. Router → Posts subgraph: Fetch { posts { title } } for User:42
  3. Router merges results and returns unified response

Federation v2 improvements:
  • @shareable — multiple subgraphs can resolve the same field
  • @override — migrate fields between subgraphs incrementally
  • @inaccessible — hide fields from the public API
  • @tag — metadata for schema governance tooling

5. Gateway Architecture — Routing, Query Planning, Error Handling

Apollo Router (Rust-based, Federation v2)

┌──────────┐     ┌──────────────────────────────┐
│  Client   │────▶│        Apollo Router          │
└──────────┘     │  1. Parse + Validate           │
                 │  2. Query Plan (from supergraph)│
                 │  3. Parallel subgraph fetches   │
                 │  4. Merge results               │
                 │  5. Serialize response           │
                 └──────┬──────┬──────┬────────────┘
                        │      │      │
                   ┌────▼─┐ ┌─▼───┐ ┌▼─────┐
                   │Users │ │Posts│ │Notif │  ← Subgraphs
                   └──────┘ └─────┘ └──────┘

Query Planning:
  Supergraph SDL is composed at build time (rover compose).
  Router generates a query plan = DAG of fetches to subgraphs.
  Parallel fetches when subgraphs are independent.
  Sequential when data dependencies exist (entity references).

Error handling:
  Partial data: if Posts subgraph fails, user.name still returned.
  Errors array contains per-subgraph errors with path information.
  Router-level: timeout, retry, circuit breaker per subgraph.

Performance:
  Apollo Router is ~10x faster than Node.js gateway (no GC pauses).
  Supports response caching, query deduplication, coprocessors.

FAANG GraphQL Interview — 6 Deep Q&A

Q1: What is the N+1 problem in GraphQL and how does DataLoader solve it?
In GraphQL, resolvers are executed per-field. When a list query returns N parent items, each parent triggers its own child resolver — producing 1 (parent) + N (children) database queries. DataLoader solves this by collecting all `.load(key)` calls enqueued during a single tick of the Node.js event loop, deduplicating keys, and dispatching a single batch function. The batch function issues one query (e.g., `WHERE id IN (...)`) and maps results back to the individual promises in key order. A fresh DataLoader instance is created per request to prevent cross-request cache pollution.
Follow-up: What happens if you forget to create a new DataLoader per request?
The DataLoader's internal memoization cache persists across requests, meaning User A could see User B's data from a previous request's cached result. This is both a correctness bug and a security vulnerability. Always scope DataLoader to the request context object.
Follow-up: Can DataLoader batch across different resolvers at the same depth?
Yes. DataLoader batches by event loop tick, not by resolver identity. If `User.posts` and `User.comments` both call `postLoader.load(id)` in the same tick, their keys are combined into one batch. The key insight: batching is temporal (same tick), not structural (same resolver).
Q2: Explain how Apollo's normalized cache works. Why is normalization important?
Apollo's InMemoryCache stores entities in a flat lookup table keyed by `__typename:id` (e.g., `User:42`). When a query result contains nested objects with `__typename` and `id`, Apollo replaces them with `__ref` pointers. This creates a single source of truth — if a Post's title is updated via any query or mutation, every component displaying that Post sees the update without refetching. Without normalization, Apollo would store raw query shapes, causing data duplication and stale reads when the same entity appears in multiple queries.
Follow-up: How do you handle entities without an `id` field?
Configure `typePolicies` with custom `keyFields`. For example, a `Coordinate` type might use `keyFields: ["latitude", "longitude"]`, producing cache key `Coordinate:{"latitude":40.7,"longitude":-74.0}`. If an entity truly has no identity, it's stored inline (not normalized) — but this means updates won't propagate.
Follow-up: What's the difference between cache.modify and cache.writeFragment?
`writeFragment` writes a fragment-shaped object and triggers normalization (it can create new cache entries). `cache.modify` directly mutates existing cache fields using modifier functions — it's lower-level, bypasses merge functions, and cannot create new entities. Use `modify` for surgical updates (removing items from lists), `writeFragment` for upserting entities.
Q3: When should a team choose GraphQL over REST? When should REST be preferred?
Choose GraphQL when: multiple consumer platforms need different data shapes (mobile vs web vs TV), UI is component-driven with deep nesting, product iteration is rapid (schema evolves without endpoint proliferation), and the team can invest in schema governance and tooling. Choose REST when: caching requirements are simple (HTTP cache headers work well), the API surface is simple with 1:1 resource mapping, the team is small without GraphQL expertise, file uploads are a primary concern, or the workload is primarily CRUD with no complex data relationships.
Follow-up: Can GraphQL and REST coexist? How?
Absolutely. A common pattern is a GraphQL gateway that wraps existing REST services using RESTDataSource. The gateway provides a unified graph to clients while REST services remain unchanged. This is the "GraphQL as a BFF (Backend for Frontend)" pattern — clients speak GraphQL, the gateway speaks REST to backends.
Q4: How do you implement field-level authorization in GraphQL?
There are three primary approaches: 1) Resolver-level guards — check permissions in each resolver, return null or throw for unauthorized access. Simplest but scatters auth logic. 2) Schema directive (@auth) — declare `@auth(requires: ADMIN)` on fields; a directive transformer wraps the resolver with a permission check. Declarative and auditable. 3) Middleware/plugin layer — intercept field resolution in Apollo's `willResolveField` plugin hook. Centralised but can be opaque. Best practice: implement authorization in the business/data layer (not the GraphQL layer) so it's enforced regardless of access path — GraphQL resolvers delegate to service methods that enforce auth.
Follow-up: How does field-level auth interact with introspection?
Introspection exposes the full schema including protected fields. Options: disable introspection in production, run a schema-level transform that strips @auth fields from the introspection result, or accept that discoverability ≠ accessibility (knowing a field exists doesn't mean you can read it). GitHub's API takes the latter approach.
Q5: How do you prevent abuse through expensive GraphQL queries in production?
Layered defense: 1) Depth limiting — reject queries nested beyond N levels (typically 10). 2) Complexity analysis — assign costs to fields (with multipliers for lists), compute total cost, reject queries over budget. 3) Persisted queries / allowlisting — only accept known query hashes. 4) Timeout — per-resolver and per-request timeouts. 5) Rate limiting — combine traditional rate limiting (requests/sec) with complexity-weighted rate limiting (total complexity/minute). 6) Disable introspection — prevents attackers from mapping the schema.
Follow-up: How does GitHub implement complexity analysis on their public GraphQL API?
GitHub assigns a point cost per node (1 point) and per connection, with `first`/`last` arguments as multipliers. Total budget: 5,000 points per query. They expose `rateLimit { cost remaining }` in every response so clients can self-adjust. The formula is recursive: a connection with `first: 100` containing a sub-connection with `first: 50` costs 100 + 100*50 = 5,100 (over budget).
Q6: What is fragment colocation and why is it critical at scale?
Fragment colocation places a GraphQL fragment definition next to the component that consumes its data. The parent page query composes all child fragments using the spread operator. Benefits: 1) Data contract — each component declares exactly what it needs. 2) Safety — adding/removing a field in a component automatically updates the query. 3) Type safety — TypeScript types are generated per-fragment, not per-query. 4) Refactoring — delete a component, its fragment goes with it. 5) Perf — Relay's compiler can optimize fragments (e.g., @defer a slow fragment). At Meta scale (100K+ components), colocation is the only way to prevent over-fetching and maintain the data layer.
Follow-up: How does Relay enforce colocation differently from Apollo?
Relay's compiler makes colocation mandatory — it forbids reading fragment data outside the component that declared it (`useFragment` enforces this). Apollo is permissive — fragments are opt-in sugar and any component can read any cached data. Relay's strictness enables compiler-level optimisations: automatic query flattening, @defer insertion, and dead-field elimination — none of which Apollo can do because it can't guarantee ownership.

1. Apollo Client Link Chain — Auth → Retry → Error → HTTP

import { ApolloClient, InMemoryCache, from, HttpLink } from '@apollo/client';
import { setContext } from '@apollo/client/link/context';
import { RetryLink } from '@apollo/client/link/retry';
import { onError } from '@apollo/client/link/error';

// 1. Auth link — injects token into every request
const authLink = setContext(async (_, { headers }) => {
  const token = await getAccessToken(); // async token refresh
  return {
    headers: {
      ...headers,
      authorization: token ? `Bearer ${token}` : '',
    },
  };
});

// 2. Retry link — exponential backoff on network errors
const retryLink = new RetryLink({
  delay: { initial: 300, max: 5000, jitter: true },
  attempts: {
    max: 3,
    retryIf: (error) => !!error && error.statusCode !== 401,
  },
});

// 3. Error link — global error handling + token refresh
const errorLink = onError(({ graphQLErrors, networkError, operation, forward }) => {
  if (graphQLErrors) {
    for (const err of graphQLErrors) {
      if (err.extensions?.code === 'UNAUTHENTICATED') {
        // Refresh token and retry the failed operation
        return refreshToken().flatMap(() => forward(operation));
      }
      console.error(`[GraphQL Error]`, err.message, err.path);
    }
  }
  if (networkError) {
    console.error(`[Network Error]`, networkError);
  }
});

// 4. HTTP link — the terminating link
const httpLink = new HttpLink({
  uri: 'https://api.example.com/graphql',
  credentials: 'include',
});

// Compose: auth → retry → error → http
const client = new ApolloClient({
  link: from([authLink, retryLink, errorLink, httpLink]),
  cache: new InMemoryCache(),
});
💡 Links form a chain like Express middleware. Each link can modify the operation (e.g., add headers), handle errors, retry, or pass to the next link via `forward(operation)`. The HttpLink is always last (terminating link).

3. Cache Update After Mutation — cache.modify & writeFragment

// Scenario: user creates a new post, we need to add it to the cached list

const [createPost] = useMutation(CREATE_POST_MUTATION, {
  // Option A: cache.modify — surgical update to an existing entity
  update(cache, { data: { createPost: newPost } }) {
    cache.modify({
      id: cache.identify({ __typename: 'User', id: newPost.authorId }),
      fields: {
        posts(existingPostRefs = [], { toReference }) {
          const newPostRef = toReference({
            __typename: 'Post',
            id: newPost.id,
          });
          return [newPostRef, ...existingPostRefs];
        },
      },
    });
  },
});

// Option B: writeFragment — write the post entity + update the list
const [createPost2] = useMutation(CREATE_POST_MUTATION, {
  update(cache, { data: { createPost: newPost } }) {
    // Step 1: Write the new post into the cache
    cache.writeFragment({
      fragment: gql`
        fragment NewPost on Post { id title createdAt author { id } }
      `,
      data: newPost,
    });

    // Step 2: Read the existing list, append, and write back
    const existing = cache.readQuery({ query: GET_USER_POSTS, variables: { userId } });
    if (existing) {
      cache.writeQuery({
        query: GET_USER_POSTS,
        variables: { userId },
        data: { userPosts: [newPost, ...existing.userPosts] },
      });
    }
  },
});

4. Optimistic Response with Rollback

// Optimistic UI: update the cache BEFORE the server responds
// If the mutation fails, Apollo automatically rolls back

const [toggleLike] = useMutation(TOGGLE_LIKE_MUTATION, {
  // optimisticResponse provides a "fake" result immediately
  optimisticResponse: {
    __typename: 'Mutation',
    toggleLike: {
      __typename: 'Post',
      id: postId,
      likeCount: isLiked ? currentLikes - 1 : currentLikes + 1,
      isLikedByViewer: !isLiked,
    },
  },
  // update runs TWICE:
  //   1. Immediately with optimisticResponse data
  //   2. Again with actual server response (replacing optimistic)
  update(cache, { data: { toggleLike: post } }) {
    cache.modify({
      id: cache.identify(post),
      fields: {
        likeCount() { return post.likeCount; },
        isLikedByViewer() { return post.isLikedByViewer; },
      },
    });
  },
  // onError: Apollo automatically removes optimistic data
  // and restores the cache to its pre-optimistic state
  onError(err) {
    console.error('Like toggle failed, rolled back', err);
    showToast('Action failed. Please try again.');
  },
});

Rollback mechanism:
  1. Apollo snapshots the cache before applying optimistic data
  2. Optimistic data is layered ON TOP as a separate "optimistic layer"
  3. On success: optimistic layer replaced with real data (usually identical)
  4. On failure: optimistic layer removed, cache reverts to snapshot
  5. Multiple optimistic updates stack as independent layers

N+1 Problem Checklist

☐ Identified: Every list field with a child resolver is a potential N+1
☐ DataLoader per resource: userLoader, postLoader, commentLoader
☐ DataLoader per request: new DataLoader() in context factory
☐ Batch function returns: results.length === keys.length (same order)
☐ Database query uses: WHERE id IN (...) or equivalent batch fetch
☐ Caching: DataLoader deduplicates keys within a request automatically
☐ Monitoring: log batch sizes — if always 1, DataLoader isn't batching
☐ Max batch size: set maxBatchSize if DB has IN clause limits (e.g., 1000)
☐ Nested N+1: DataLoaders needed at EVERY depth level, not just the first

Security Checklist

☐ Depth limiting: max depth ≤ 10 (configurable)
☐ Complexity analysis: field costs × list multipliers, budget enforced
☐ Persisted queries: in prod, only allow known query hashes
☐ Introspection: DISABLED in production
☐ Rate limiting: per-client AND per-complexity (weighted)
☐ Timeouts: per-resolver (5s) and per-request (30s)
☐ Input validation: max string lengths, list size limits (first/last ≤ 100)
☐ Authorization: enforced in business layer, not just GraphQL resolvers
☐ Batching attacks: limit operations per document to 1 (or small number)
☐ Error masking: never leak stack traces or internal details in errors[]
☐ CORS: restrict allowed origins for the GraphQL endpoint
☐ CSRF: use custom header requirement (e.g., X-GraphQL-Operation)
