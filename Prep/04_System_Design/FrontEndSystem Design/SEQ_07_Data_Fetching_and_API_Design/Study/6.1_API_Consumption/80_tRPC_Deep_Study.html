1. TypeScript Inference Chain — The Core Mechanism

tRPC's magic lies in a single insight: TypeScript's structural type system can infer types across module boundaries without any code generation step. The chain works as follows:

// 1. Server defines a procedure with a Zod schema
const userRouter = t.router({
  getById: t.procedure
    .input(z.object({ id: z.string().uuid() }))  // ← Zod schema
    .query(({ input }) => {
      // input is inferred as { id: string }
      return db.user.findUnique({ where: { id: input.id } });
      // return type inferred as User | null
    }),
});

// 2. AppRouter type is exported (TYPE ONLY — no runtime import)
export type AppRouter = typeof appRouter;

// 3. Client creates a typed proxy from the AppRouter type
const trpc = createTRPCReact<AppRouter>();

// 4. Usage — full autocomplete, input validation, return type known
const { data } = trpc.user.getById.useQuery({ id: "abc-123" });
// data is User | null — inferred end-to-end
Key insight: The AppRouter type is a purely compile-time construct. It carries the full shape of every procedure's input and output types. The client proxy uses TypeScript's Proxy at runtime and mapped types at compile time to reconstruct the router shape on the client side.

2. Eliminating Schema Drift — No Codegen, No OpenAPI

Traditional API approaches suffer from schema drift — the API contract diverges from client expectations:

ApproachDrift RiskHow It's Mitigated
REST + OpenAPIHighManual spec maintenance, codegen on change
GraphQLMediumSchema-first, but codegen needed for typed clients
gRPCMediumProtobuf compilation step
tRPCZeroTypes flow directly — change server, client breaks at compile time

tRPC achieves zero drift because there is no intermediate representation. The TypeScript compiler is the single source of truth. If a server procedure changes its return type, every client callsite that depends on the old shape produces a compile error instantly.

3. Zod — Runtime Validation + Compile-Time Type Derivation

Zod serves a dual purpose in tRPC:

import { z } from 'zod';

// 1. Define a schema — this is RUNTIME code
const CreatePostInput = z.object({
  title: z.string().min(1).max(200),
  body: z.string().min(10),
  tags: z.array(z.string()).max(5).optional(),
});

// 2. Derive TypeScript type — this is COMPILE-TIME only
type CreatePostInput = z.infer<typeof CreatePostInput>;
// { title: string; body: string; tags?: string[] | undefined }

// 3. tRPC uses the schema for BOTH
t.procedure
  .input(CreatePostInput)   // runtime validation via .parse()
  .mutation(({ input }) => {
    // input: CreatePostInput (compile-time type)
    // At runtime, malformed data throws ZodError before this runs
  });
Why Zod over io-ts or Yup? Zod was purpose-built for TypeScript-first validation. Its z.infer provides the cleanest type derivation. tRPC v11 also supports any validator that implements the StandardSchemaV1 interface (ArkType, Valibot, etc).

5. Middleware Chain — Execution Order & Context Injection

Middlewares execute in declaration order (top → bottom) before the procedure resolver. Each middleware can:

  • Short-circuit by throwing a TRPCError
  • Augment the context via next({ ctx: { ...ctx, newProp } })
  • Measure timing (wrap next() in a timer)
// Execution flow: createContext → middleware1 → middleware2 → resolver

const isAuthed = t.middleware(({ ctx, next }) => {
  if (!ctx.session?.user) {
    throw new TRPCError({ code: 'UNAUTHORIZED' });
  }
  return next({ ctx: { ...ctx, user: ctx.session.user } });
  // downstream procedures now have ctx.user guaranteed
});

const isAdmin = t.middleware(({ ctx, next }) => {
  if (ctx.user.role !== 'ADMIN') {
    throw new TRPCError({ code: 'FORBIDDEN' });
  }
  return next();
});

// Compose: publicProcedure → protectedProcedure → adminProcedure
const protectedProcedure = t.procedure.use(isAuthed);
const adminProcedure = protectedProcedure.use(isAdmin);

6. Context Creation & Injection

Context is created per request via a createContext function passed to the adapter. This is where you parse cookies, verify JWTs, and inject database clients.

// createContext runs BEFORE any middleware or procedure
export const createContext = async (opts: CreateNextContextOptions) => {
  const session = await getServerSession(opts.req, opts.res);
  return {
    session,       // nullable — may not be authenticated
    db: prisma,    // database client
    req: opts.req, // raw request (for IP, headers, etc.)
  };
};

type Context = Awaited<ReturnType<typeof createContext>>;
// All procedures receive this as ctx — type-safe throughout

8. Links — HTTP Batch Link & WebSocket Link

tRPC uses a link chain (inspired by Apollo Client's link concept) to control how requests flow from client to server:

import { httpBatchLink } from '@trpc/client';
import { createWSClient, wsLink } from '@trpc/client';
import { splitLink } from '@trpc/client';

const trpcClient = createTRPCClient<AppRouter>({
  links: [
    splitLink({
      // Route subscriptions over WebSocket, everything else over HTTP
      condition: (op) => op.type === 'subscription',
      true: wsLink({ client: wsClient }),
      false: httpBatchLink({
        url: 'https://api.example.com/trpc',
        maxURLLength: 2048,  // switch to POST if URL too long
        headers: () => ({ Authorization: `Bearer ${token}` }),
      }),
    }),
  ],
});
httpBatchLink: Collects all procedures called within a single React render tick and sends them as a single HTTP request. The server responds with an array of results. This dramatically reduces network overhead. Each procedure in the batch is identified by its path (e.g., user.getById) and input.

9. SuperJSON Transformer — Serializing Rich Types

JSON cannot natively represent Date, Map, Set, BigInt, undefined, RegExp, or Error. SuperJSON solves this:

// Server: configure transformer
import superjson from 'superjson';

const t = initTRPC.context<Context>().create({
  transformer: superjson,  // serialize/deserialize automatically
});

// Now this works seamlessly:
getUser: t.procedure.query(() => ({
  name: "Ada",
  createdAt: new Date(),      // ← preserved as Date on client
  skills: new Set(["TS"]),   // ← preserved as Set on client
  metadata: new Map([["k", "v"]]), // ← preserved as Map
}));

// Wire format: { json: {...}, meta: { values: { createdAt: ["Date"], ... } } }
// Client automatically reconstructs native types from meta

1. Monorepo Shared Types Pattern

The canonical tRPC architecture uses a monorepo (Turborepo/Nx) with shared type exports:

packages/
├── api/                  ← tRPC server package
│   ├── src/
│   │   ├── root.ts        ← initTRPC, createContext
│   │   ├── routers/
│   │   │   ├── user.ts    ← userRouter
│   │   │   ├── post.ts    ← postRouter
│   │   │   └── index.ts   ← appRouter = mergeRouters(user, post)
│   │   └── trpc.ts        ← t.procedure, t.middleware
│   └── package.json
├── web/                  ← Next.js frontend
│   ├── src/utils/trpc.ts  ← createTRPCReact<AppRouter>()
│   └── package.json
└── db/                   ← Prisma schema + client
    └── package.json

// packages/api/src/routers/index.ts
import { userRouter } from './user';
import { postRouter } from './post';

export const appRouter = t.router({
  user: userRouter,
  post: postRouter,
});

export type AppRouter = typeof appRouter;
// ↑ This is the ONLY thing the client imports from the server
Critical constraint: The client must ONLY import the AppRouter type. Importing runtime code from the server package would bundle server logic into the client, leaking secrets and breaking separation.

5. Batching — Multiple Procedures in a Single HTTP Request

When using httpBatchLink, tRPC collects all procedure calls triggered in the same microtask and sends them as one request:

// Client calls 3 procedures in a single component render:
const user  = trpc.user.getById.useQuery({ id });
const posts = trpc.post.listByUser.useQuery({ userId: id });
const stats = trpc.analytics.userStats.useQuery({ userId: id });

// HTTP request (single!):
// GET /api/trpc/user.getById,post.listByUser,analytics.userStats
//   ?batch=1
//   &input={"0":{"id":"..."},"1":{"userId":"..."},"2":{"userId":"..."}}

// HTTP response (array of results):
// [
//   { result: { data: { name: "Ada", ... } } },
//   { result: { data: [{ title: "Post 1" }, ...] } },
//   { result: { data: { views: 1234, ... } } }
// ]
Performance impact: Batching reduces HTTP connections from N to 1 per render cycle. On HTTP/1.1 this is critical (6 connection limit). On HTTP/2 the latency benefit is smaller but still meaningful due to reduced header overhead and server-side processing.

6. Server-Side Caller Pattern (RSC / Server Components)

In Next.js App Router with React Server Components, you don't need HTTP round-trips — call procedures directly on the server:

// packages/api/src/root.ts
export const createCaller = createCallerFactory(appRouter);

// app/users/[id]/page.tsx (React Server Component)
import { createCaller } from '@acme/api';
import { createContext } from '@acme/api/context';

export default async function UserPage({ params }: Props) {
  const ctx = await createContext();    // create context manually
  const caller = createCaller(ctx);     // get a typed caller
  const user = await caller.user.getById({ id: params.id });

  // No HTTP call — procedure runs in the same process
  // Full type safety preserved
  return <UserProfile user={user} />;
}

tRPC's React integration wraps @tanstack/react-query. Understanding this mapping is critical:

// Optimistic update pattern using tRPC utils
const utils = trpc.useUtils();

const updatePost = trpc.post.update.useMutation({
  async onMutate(newData) {
    await utils.post.getById.cancel({ id: newData.id });
    const prev = utils.post.getById.getData({ id: newData.id });
    utils.post.getById.setData({ id: newData.id }, (old) =>
      old ? { ...old, ...newData } : old
    );
    return { prev };
  },
  onError(err, newData, context) {
    utils.post.getById.setData({ id: newData.id }, context?.prev);
  },
  onSettled() {
    utils.post.getById.invalidate();
  },
});

Q1: How does tRPC achieve type safety without code generation?

Explain the mechanism end-to-end.
tRPC exploits TypeScript's structural type inference across module boundaries. The server defines procedures with Zod input schemas and TypeScript return types. The router type (type AppRouter = typeof appRouter) captures the entire API surface as a single recursive type. The client imports only this type (zero runtime import) and passes it as a generic to createTRPCReact<AppRouter>(). The client library uses TypeScript's mapped types and conditional types to reconstruct the router shape, giving each procedure the correct input and output types. At runtime, the client uses a Proxy object that dynamically builds procedure paths (e.g., user.getById) and maps them to HTTP calls. Because the type flows directly from server to client through TypeScript's compiler — with no intermediate schema, no generated files, and no build step — any server-side change is immediately reflected as a compile error on the client.
Follow-up: "What happens if the server and client are in separate repos?" → Type safety breaks. You'd need to publish the AppRouter type as an npm package or use a shared monorepo. Without the type, you lose all compile-time guarantees and tRPC devolves to an untyped fetch wrapper.
Follow-up: "How is this different from GraphQL codegen?" → GraphQL requires a schema file (.graphql), a codegen tool (graphql-codegen), and a regeneration step whenever the schema changes. tRPC skips all of this — TypeScript IS the schema. The tradeoff is that tRPC only works when both client and server are TypeScript.

Q2: Compare tRPC vs GraphQL for a greenfield TypeScript fullstack project.

When would you choose one over the other?
Choose tRPC when: Both client and server are TypeScript, the team is small-to-medium, you want maximum velocity with zero boilerplate, and the API is consumed by a single frontend (or a small set of known TS clients). tRPC has near-zero setup, no schema language to learn, and changes propagate instantly at compile time.

Choose GraphQL when: Multiple clients in different languages need the API (iOS/Swift, Android/Kotlin, third-party), you need fine-grained field selection to reduce over-fetching across diverse clients, or you need a public API with strong documentation and introspection. GraphQL's schema serves as a language-agnostic contract.

Key differences: GraphQL solves the multi-client, multi-language problem with a universal schema. tRPC solves the TypeScript fullstack DX problem by eliminating the schema altogether. They're optimizing for different constraints.
Follow-up: "Can you use both together?" → Yes. A common pattern is tRPC for internal BFF (Backend-for-Frontend) communication and GraphQL or REST for public/external APIs. The BFF pattern lets the tRPC layer aggregate data from multiple downstream services.

Q3: When is tRPC NOT appropriate?

What are the hard constraints and limitations?
1. Multi-language clients: tRPC's type safety is TypeScript-only. If you need a Swift iOS app or a Python data pipeline to consume the API, tRPC provides no contract for them. You'd either need to expose a REST/GraphQL layer alongside tRPC or abandon tRPC.

2. Public APIs: tRPC has no built-in schema documentation, no equivalent to Swagger UI or GraphQL Playground. Public APIs need discoverability — OpenAPI/Swagger or GraphQL introspection serve this purpose. (Note: trpc-openapi can generate OpenAPI from tRPC routers, but it adds friction.)

3. Separate repos without shared types: If frontend and backend live in different repositories without a shared type package, tRPC's core advantage — compile-time type flow — disappears entirely.

4. Very large organizations: When API producers and consumers are different teams with different release cycles, a formal contract (OpenAPI spec, GraphQL schema) provides better governance than implicit TypeScript types.
Follow-up: "What about performance at scale?" → tRPC itself adds negligible overhead — it's a thin layer over HTTP. The batching link can actually improve performance vs. GraphQL by eliminating query parsing and AST validation. The bottleneck is always the database, not the API framework.

Q4: tRPC middleware vs Express middleware — what's the difference?

Compare execution model, type safety, and composability.
Express middleware: Operates on raw (req, res, next). Types are loose (req.body: any). Middleware modifies the mutable request/response objects. Ordering is implicit (registration order). Error handling is via next(err) — easy to forget and causes silent failures.

tRPC middleware: Operates on ({ ctx, next, input, type }). Context is fully typed — each middleware can extend it via next({ ctx: { ...ctx, newProp } }), and downstream procedures see the augmented type. Composition is explicit: protectedProcedure = t.procedure.use(isAuthed).use(isAdmin). Error handling uses throw new TRPCError(), which is caught and formatted by the error handler — no silent swallowing.

Key advantage: tRPC middleware is type-narrowing. After isAuthed middleware runs, the context type changes from { session: Session | null } to { session: Session; user: User }. This is impossible with Express because middleware types don't compose.
Follow-up: "Can tRPC middleware access raw request headers?" → Yes, through context. The createContext function receives the raw request and can inject any header, cookie, or IP into the context. Middleware then accesses these via ctx.

Q5: How does tRPC batching work over HTTP?

Explain the mechanism, wire format, and performance implications.
When using httpBatchLink, the client collects all procedure calls made during a single JavaScript microtask (i.e., one React render cycle) and batches them into a single HTTP request.

Wire format (GET):
GET /api/trpc/user.getById,post.list?batch=1&input={"0":{"id":"x"},"1":{"limit":10}}

The procedure paths are comma-separated in the URL path. Inputs are keyed by their position index. The server processes each procedure in parallel (using Promise.all) and returns a JSON array of results, one per procedure, in the same order.

POST fallback: If the URL exceeds maxURLLength (default 2048), the batch automatically switches to a POST request with the input in the body. This handles large inputs gracefully.

Performance: Reduces N HTTP round-trips to 1. On HTTP/1.1 this bypasses the 6 concurrent connection limit. On HTTP/2, it reduces header overhead and allows the server to process all procedures in a single event loop entry. However, one slow procedure delays the entire batch response.
Follow-up: "How can you mitigate a slow procedure blocking the batch?" → Use httpBatchStreamLink (v11) instead of httpBatchLink. It streams responses as they complete using newline-delimited JSON, so fast procedures resolve immediately while slow ones arrive later.

Q6: Explain the tRPC + React Query integration.

How does tRPC wrap React Query, and what does this give you?
@trpc/react-query is a thin, type-safe wrapper around @tanstack/react-query. It provides:

1. Typed hooks: trpc.user.getById.useQuery({ id }) → calls useQuery with pre-configured queryKey (derived from procedure path + input) and queryFn (the tRPC HTTP call). Return type is inferred from the server procedure.

2. Automatic query keys: tRPC constructs structured query keys like [['user', 'getById'], { input: { id: 'x' }, type: 'query' }]. This enables precise cache invalidation — utils.user.getById.invalidate() invalidates only that procedure, while utils.user.invalidate() invalidates all user procedures.

3. Utils (useUtils): The trpc.useUtils() hook returns a typed utility object that wraps QueryClient methods: getData, setData, invalidate, cancel, prefetch. All are scoped to specific procedures with full type inference.

4. SSR/SSG hydration: On the server (getServerSideProps / RSC), you can prefetch data into the query cache, dehydrate it, and pass it to the client. React Query rehydrates the cache so the client renders immediately without a loading state.
Follow-up: "Can you use tRPC without React Query?" → Yes. The vanilla @trpc/client provides a proxy client that returns promises directly: const user = await trpc.user.getById.query({ id }). This works in any JS/TS environment — Node.js scripts, Vue apps, Svelte, etc.

Full tRPC v11 Server — Annotated

// ──────────────────────────────────────────────
// FILE: packages/api/src/trpc.ts
// Core tRPC initialization — procedures, middleware, context
// ──────────────────────────────────────────────

import { initTRPC, TRPCError } from '@trpc/server';
import superjson from 'superjson';
import { ZodError } from 'zod';
import type { Context } from './context';

// Initialize tRPC — this is called ONCE per application
// .context<Context>() sets the base context type for all procedures
const t = initTRPC.context<Context>().create({
  // superjson preserves Date, Map, Set, BigInt in transit
  transformer: superjson,

  // Custom error formatter — expose Zod validation details
  errorFormatter({ shape, error }) {
    return {
      ...shape,
      data: {
        ...shape.data,
        zodError:
          error.cause instanceof ZodError
            ? error.cause.flatten()
            : null,
      },
    };
  },
});

// ─── Exported helpers ────────────────────────
export const createRouter = t.router;
export const createCallerFactory = t.createCallerFactory;
export const publicProcedure = t.procedure;

// ─── Auth middleware: narrows ctx to include `user` ──
const enforceAuth = t.middleware(({ ctx, next }) => {
  // ctx.session comes from createContext (nullable)
  if (!ctx.session?.user) {
    throw new TRPCError({
      code: 'UNAUTHORIZED',
      message: 'You must be logged in',
    });
  }
  // Pass narrowed context downstream
  // After this, ctx.user is `User` (not User | undefined)
  return next({
    ctx: {
      ...ctx,
      user: ctx.session.user, // ← guaranteed non-null
    },
  });
});

// Protected procedure — requires authentication
export const protectedProcedure = t.procedure.use(enforceAuth);

// ─── Timing middleware (logging) ─────────────
const withTiming = t.middleware(async ({ path, type, next }) => {
  const start = performance.now();
  const result = await next();
  const ms = (performance.now() - start).toFixed(2);
  console.log(`[tRPC] ${type} ${path} — ${ms}ms`);
  return result;
});

Router with Zod Schemas

// ──────────────────────────────────────────────
// FILE: packages/api/src/routers/post.ts
// Post domain router — queries, mutations, error handling
// ──────────────────────────────────────────────

import { z } from 'zod';
import { TRPCError } from '@trpc/server';
import { createRouter, publicProcedure, protectedProcedure } from '../trpc';

// ─── Input schemas (Zod) ─────────────────────
const CreatePostInput = z.object({
  title: z.string().min(1).max(200),
  body: z.string().min(10),
  tags: z.array(z.string()).max(5).optional(),
});

const UpdatePostInput = z.object({
  id: z.string().uuid(),
  title: z.string().min(1).max(200).optional(),
  body: z.string().min(10).optional(),
});

const PaginationInput = z.object({
  cursor: z.string().uuid().optional(), // cursor for keyset pagination
  limit: z.number().min(1).max(100).default(20),
});

// ─── Router definition ───────────────────────
export const postRouter = createRouter({

  // PUBLIC — anyone can list posts
  list: publicProcedure
    .input(PaginationInput)
    .query(async ({ ctx, input }) => {
      const posts = await ctx.db.post.findMany({
        take: input.limit + 1, // fetch one extra to detect hasMore
        cursor: input.cursor ? { id: input.cursor } : undefined,
        orderBy: { createdAt: 'desc' },
        include: { author: { select: { name: true, image: true } } },
      });

      let nextCursor: string | undefined;
      if (posts.length > input.limit) {
        const extra = posts.pop()!;
        nextCursor = extra.id; // cursor for next page
      }

      return { posts, nextCursor };
    }),

  // PUBLIC — get single post by ID
  getById: publicProcedure
    .input(z.object({ id: z.string().uuid() }))
    .query(async ({ ctx, input }) => {
      const post = await ctx.db.post.findUnique({
        where: { id: input.id },
        include: { author: true, comments: true },
      });
      if (!post) {
        throw new TRPCError({
          code: 'NOT_FOUND',
          message: `Post ${input.id} not found`,
        });
      }
      return post;
    }),

  // PROTECTED — must be logged in to create
  create: protectedProcedure
    .input(CreatePostInput)
    .mutation(async ({ ctx, input }) => {
      // ctx.user is guaranteed by enforceAuth middleware
      return ctx.db.post.create({
        data: {
          ...input,
          authorId: ctx.user.id,
        },
      });
    }),

  // PROTECTED — only author can update their post
  update: protectedProcedure
    .input(UpdatePostInput)
    .mutation(async ({ ctx, input }) => {
      const existing = await ctx.db.post.findUnique({
        where: { id: input.id },
      });
      if (!existing) {
        throw new TRPCError({ code: 'NOT_FOUND' });
      }
      if (existing.authorId !== ctx.user.id) {
        throw new TRPCError({
          code: 'FORBIDDEN',
          message: 'You can only edit your own posts',
        });
      }
      return ctx.db.post.update({
        where: { id: input.id },
        data: input,
      });
    }),

  // PROTECTED — only author can delete
  delete: protectedProcedure
    .input(z.object({ id: z.string().uuid() }))
    .mutation(async ({ ctx, input }) => {
      const post = await ctx.db.post.findUnique({
        where: { id: input.id },
      });
      if (post?.authorId !== ctx.user.id) {
        throw new TRPCError({ code: 'FORBIDDEN' });
      }
      return ctx.db.post.delete({ where: { id: input.id } });
    }),
});

export function TRPCProvider({ children }: { children: React.ReactNode }) {
  const [queryClient] = useState(() => new QueryClient());
  const [trpcClient] = useState(() =>
    trpc.createClient({
      links: [
        httpBatchLink({
          url: '/api/trpc',
          transformer: superjson,
          headers: () => {
            const token = getAuthToken();
            return token ? { Authorization: `Bearer ${token}` } : {};
          },
        }),
      ],
    })
  );

  return (
    <trpc.Provider client={trpcClient} queryClient={queryClient}>
      <QueryClientProvider client={queryClient}>
        {children}
      </QueryClientProvider>
    </trpc.Provider>
  );
}

// ──────────────────────────────────────────────
// FILE: packages/web/src/components/PostList.tsx
// Consuming tRPC with useQuery + useMutation
// ──────────────────────────────────────────────

'use client';
import { trpc } from '../utils/trpc';

export function PostList() {
  // ─── Read: useQuery ───────────────────────
  const {
    data,       // { posts: Post[], nextCursor?: string } — fully typed
    isLoading,  // boolean
    error,      // TRPCClientError | null
  } = trpc.post.list.useQuery({ limit: 10 });

  // ─── Write: useMutation ──────────────────
  const utils = trpc.useUtils();

  const createPost = trpc.post.create.useMutation({
    onSuccess() {
      // Invalidate the list cache so it refetches
      utils.post.list.invalidate();
    },
    onError(err) {
      // Access Zod validation errors if available
      if (err.data?.zodError) {
        const fieldErrors = err.data.zodError.fieldErrors;
        console.error('Validation failed:', fieldErrors);
      }
    },
  });

  // ─── Delete with optimistic update ───────
  const deletePost = trpc.post.delete.useMutation({
    async onMutate({ id }) {
      await utils.post.list.cancel();
      const prev = utils.post.list.getData({ limit: 10 });
      utils.post.list.setData({ limit: 10 }, (old) =>
        old ? { ...old, posts: old.posts.filter((p) => p.id !== id) } : old
      );
      return { prev };
    },
    onError(_, __, context) {
      if (context?.prev) {
        utils.post.list.setData({ limit: 10 }, context.prev);
      }
    },
    onSettled() {
      utils.post.list.invalidate();
    },
  });

  if (isLoading) return <div>Loading...</div>;
  if (error) return <div>Error: {error.message}</div>;

  return (
    <ul>
      {data.posts.map((post) => (
        <li key={post.id}>
          {post.title}
          <button onClick={() => deletePost.mutate({ id: post.id })}>
            Delete
          </button>
        </li>
      ))}
    </ul>
  );
}

Senior Interview Talking Points — One-Liners

  • Type safety: "tRPC uses TypeScript's structural type system — the AppRouter type IS the API contract."
  • No codegen: "Unlike GraphQL, there's no build step between server change and client type error."
  • Limitation: "tRPC only works when both ends are TypeScript — it's not for public or multi-language APIs."
  • Batching: "httpBatchLink collects all calls in a render tick and sends one HTTP request."
  • Middleware: "tRPC middleware narrows context types — after auth middleware, ctx.user is guaranteed."
  • React Query: "tRPC wraps React Query — every useQuery gets automatic cache keys from procedure path + input."
  • RSC pattern: "Use createCallerFactory to call procedures directly in Server Components — no HTTP."
  • Monorepo: "Client imports only the AppRouter type — zero runtime code from the server package."
