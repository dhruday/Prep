1. Browser Connection Limits

// HTTP/1.1: Max 6 connections per origin (Chrome/Firefox)
// 7th request QUEUES until a connection frees up

// Timeline with 10 parallel requests on HTTP/1.1:
// Batch 1 (connections 1-6): ████████ simultaneous
// Batch 2 (connections 7-10): ....████ queued, start after batch 1
// Total time ≈ 2x single request time

// HTTP/2: Multiplexed streams on SINGLE connection
// All 10 requests share one TCP connection
// No head-of-line blocking at HTTP level
// Chrome limits ~100 concurrent streams per connection

// HTTP/3 (QUIC): Independent streams
// No TCP head-of-line blocking (stream-level loss recovery)
// Even better for parallel requests

// Why this matters for request orchestration:
// On HTTP/1.1: Limit parallel requests to 6 per origin
// On HTTP/2: Can fire many parallel requests efficiently
// Check: window.performance.getEntries() → see protocol field

2. Promise Combinators Deep Dive

// Promise.all — ALL succeed or first rejection
// Behavior: Waits for all. Rejects on FIRST failure.
// Use: Independent requests where ALL are required
Promise.all([fetchA(), fetchB(), fetchC()])
// If B fails: A and C results DISCARDED (but requests complete)
// A and C are NOT aborted! They run to completion wastefully.

// Promise.allSettled — Wait for ALL, never rejects
// Returns: [{status:'fulfilled',value}, {status:'rejected',reason}]
// Use: Dashboard widgets — show what succeeded, error what failed
Promise.allSettled([fetchA(), fetchB(), fetchC()])
// Always resolves. No short-circuit.

// Promise.race — First to settle (resolve OR reject)
// Use: Timeout pattern, fastest mirror selection
Promise.race([fetchA(), timeout(5000)])
// If timeout resolves first → treat as timeout error

// Promise.any — First to RESOLVE (ignores rejections)
// Rejects only if ALL reject (AggregateError)
// Use: Redundant servers, CDN fallback
Promise.any([fetchFromCDN1(), fetchFromCDN2(), fetchFromCDN3()])

3. Waterfall vs Parallel — Impact on LCP

// Sequential (waterfall) — 3 dependent requests:
// [user 200ms] → [posts 300ms] → [comments 150ms]
// Total: 200 + 300 + 150 = 650ms

// Parallel (independent) — 3 independent requests:
// [user 200ms    ]
// [posts 300ms       ]
// [comments 150ms]
// Total: max(200, 300, 150) = 300ms ← 2.2x faster!

// Mixed — some dependent, some not:
// [user 200ms] → [user-posts 300ms]
// [config 100ms]   (independent, parallel with user)
// Total: 200 + 300 = 500ms (config hidden during user fetch)

// LCP impact: Every 100ms of data fetching delay
// adds ~100ms to Largest Contentful Paint
// Google: LCP should be < 2.5s for "Good" rating

4. Concurrency Control — Why Unlimited Parallel Is Bad

// Problem: Dashboard with 20 widget APIs
// Promise.all(widgets.map(w => fetch(w.url)))
// This fires ALL 20 simultaneously!

// Issues:
// 1. HTTP/1.1: Only 6 connections → 14 queue → waterfall
// 2. Server overload: 20 requests from one client
// 3. Memory: 20 response bodies buffered simultaneously
// 4. Mobile: Network contention with other tabs/apps

// Solution: Concurrency limiter (pool pattern)
// Process max N requests at a time
// When one completes, start the next queued request

// Common limits:
// HTTP/1.1: concurrency = 4-6
// HTTP/2: concurrency = 10-20
// Image loading: concurrency = 3
// API batch processing: concurrency = 5

// Model requests as a DAG (Directed Acyclic Graph):

      ┌──── auth ────┐
      │              │
      ▼              ▼
    user          config
      │              │
      ├──────┬───────┘
      ▼      ▼
    posts  preferences
      │
      ▼

// Level 0: auth (must be first)

// Level 2: [posts, preferences] (parallel, different deps)
// Level 3: comments (depends on posts)

// Optimal execution:
// auth → [user || config] → [posts || preferences] → comments
// Each level runs in parallel where dependencies allow

2. Suspense Waterfall Prevention

// React Suspense creates UNINTENTIONAL waterfalls:

// ❌ BAD: Each component suspends independently
function Page() {
  return (
    <Suspense fallback={<Spinner/>}>
      <UserProfile />   // suspends → fetches user
      <UserPosts />     // WAITS for UserProfile to resolve!
    </Suspense>         // Sequential waterfall!
  );
}

// ✅ GOOD: Prefetch all data before render
function Page() {
  // Both queries start simultaneously
  const userQuery = useSuspenseQuery({queryKey: ['user']});
  const postsQuery = useSuspenseQuery({queryKey: ['posts']});
  // React Query batches: since both fire before first suspend,
  // they run in parallel! Component suspends once for both.
}

// ✅ ALSO GOOD: Nested Suspense boundaries
<Suspense>
  <UserProfile />
  <Suspense><UserPosts /></Suspense> // Independent boundary
</Suspense>

3. Request Queue with Priority

// Priority queue for mixed-criticality requests:

class PriorityRequestQueue {
  // Priority levels:
  // CRITICAL: auth, core data (process immediately)
  // HIGH: above-the-fold content
  // NORMAL: interactive features
  // LOW: analytics, prefetch, below-fold images
  
  // Architecture:
  // ┌─────────────┐
  // │ CRITICAL [■] │ → immediate (no queue)
  // │ HIGH [■■■]   │ → concurrency: 4
  // │ NORMAL [■■]  │ → concurrency: 2 (after HIGH)
  // │ LOW [■■■■■]  │ → concurrency: 1 (idle only)
  // └─────────────┘
  
  // When a HIGH request completes:
  // 1. Check HIGH queue first
  // 2. If empty, promote from NORMAL
  // 3. If empty, promote from LOW
}

4. Batching Pattern

// Instead of N individual requests, batch into 1:

// ❌ N+1 problem:
posts.forEach(post => fetch(`/api/users/${post.authorId}`));
// 100 posts = 100 HTTP requests to /api/users/!

// ✅ Batch request:
const uniqueIds = [...new Set(posts.map(p => p.authorId))];
fetch(`/api/users/batch?ids=${uniqueIds.join(',')}`);
// 1 HTTP request for all authors!

// DataLoader pattern (auto-batching):
// Collects all load(id) calls in current tick
// Then fires single batch request in next microtask
const userLoader = new DataLoader(async (ids) => {
  const users = await fetch(`/api/users/batch?ids=${ids}`);
  return ids.map(id => users.find(u => u.id === id));
});
// Multiple components call: userLoader.load(authorId)
// All calls in same tick batched into ONE request
Q1: Implement a concurrency limiter for Promise-based operations. Max N at a time.
See Code Walkthrough for full implementation. Key design:
1. Maintain running count and waiting queue
2. When add(task) called: if running < limit, execute immediately; else queue
3. When task completes: decrement running, dequeue and start next
4. Use Promise chaining to return original task's result
5. Handle rejections without stopping the queue
Time complexity: O(1) per enqueue/dequeue. Space: O(queue size).
Follow-up: How would you add priority to this?
Replace FIFO queue with a priority queue (min-heap or sorted array). Each task has a priority. On dequeue, pop highest priority task. For equal priorities, maintain insertion order (FIFO within priority level).
Q2: Your dashboard loads 15 widgets. Some users see partial data. Diagnose.
Likely cause: Promise.all fails fast on first rejection, discarding all other results.

Fix: Switch to Promise.allSettled:
1. All 15 requests complete regardless of individual failures
2. Map results: fulfilled → render widget, rejected → show error per widget
3. Individual error boundaries per widget component
4. Retry option per failed widget

Additional improvements:
- Concurrency limit of 6 (HTTP/1.1 friendly)
- Priority: critical widgets first (revenue, active users), enrichment widgets last
- Timeouts per widget: fast timeout (3s) for quick APIs, long timeout (10s) for analytics
- Progressive rendering: show each widget as it resolves
Follow-up: How do you show progress as widgets load?
Track resolution count: const resolved = ref(0). On each promise settlement, increment and update progress bar (resolved/total). With allSettled, you can even show "12/15 loaded, 2 failed, 1 loading" in real-time.
Q3: Promise.all vs Promise.allSettled vs Promise.race vs Promise.any — when each?
Promise.all: Login flow (auth → token → user). If ANY fails, entire flow is invalid. Fast-fail is desired.
Promise.allSettled: Dashboard. Show what works, error what doesn't. Analytics batch (some events may fail). Feature flag fetching.
Promise.race: Request timeout (race against setTimeout). Fastest CDN selection. "Show loading spinner after 200ms" pattern.
Promise.any: Redundant API calls to multiple regions. CDN fallback (try CDN1, CDN2, origin — first success wins). Cache layers (try memory → disk → network).
Follow-up: What happens to the "losing" promises in Promise.race?
They continue executing! Race doesn't cancel losers. Critical: use AbortController to cancel losing requests. Otherwise you waste bandwidth and server resources. Pattern: store AbortControllers, abort all on first resolution.
Q4: How would you fetch data for a page that needs user profile, recent posts, notifications, and recommendations?
Dependency analysis:
- user profile: no dependency (auth token only)
- recent posts: depends on user.id
- notifications: no dependency (auth token only)
- recommendations: depends on user.id + user.preferences

Optimal execution:
Level 1: [user, notifications] (parallel — both independent)
Level 2: [posts, recommendations] (parallel — both need user, but independent of each other)

Code:
const [user, notifications] = await Promise.all([fetchUser(), fetchNotifications()]);
const [posts, recs] = await Promise.all([fetchPosts(user.id), fetchRecs(user.id)]);

Total time: max(user, notif) + max(posts, recs) instead of sum of all four.
Follow-up: What if recommendations is slow (2s) but not critical?
Don't block render on it. Render page with user + posts + notifications immediately. Load recommendations lazily with Suspense boundary or loading skeleton. Or: use Promise.race with timeout — show "recommendations coming soon" after 500ms, load in background.
Q5: Explain the request waterfall problem in React and how to solve it.
Problem: Component tree creates waterfall:
Parent renders → fetches data → Child renders → fetches data → Grandchild...
Each level waits for parent to render before starting its own fetch.

Solutions:
1. Hoist fetches: Parent fetches all data, passes to children
2. Parallel queries: useQueries([query1, query2, query3]) at top level
3. Prefetch: queryClient.prefetchQuery on route navigation (before component mounts)
4. React Router loaders: loader() functions fetch before component renders
5. Server Components: Fetch on server, send rendered HTML (no client waterfall)
6. GraphQL: Single query returns all needed data (no component-level fetches)

1. Concurrency Limiter

function createPool(concurrency) {
  let running = 0;
  const queue = [];
  
  function next() {
    while (running < concurrency && queue.length) {
      const { task, resolve, reject } = queue.shift();
      running++;
      task()
        .then(resolve, reject)
        .finally(() => {
          running--;
          next(); // Process next queued task
        });
    }
  }
  
  return {
    add(task) {
      return new Promise((resolve, reject) => {
        queue.push({ task, resolve, reject });
        next();
      });
    },
    get size() { return queue.length; },
    get active() { return running; }
  };
}

// Usage:
const pool = createPool(5); // Max 5 concurrent
const results = await Promise.all(
  urls.map(url => pool.add(() => fetch(url)))
);

2. Dependency-Aware Parallel Fetcher

// Execute requests respecting dependency graph
async function fetchWithDeps(tasks) {
  // tasks = [
  //   { id: 'user', fn: fetchUser, deps: [] },
  //   { id: 'posts', fn: (results) => fetchPosts(results.user.id), deps: ['user'] },
  //   { id: 'config', fn: fetchConfig, deps: [] },
  // ]
  
  const results = {};
  const completed = new Set();
  const pending = new Map(tasks.map(t => [t.id, t]));
  
  while (pending.size > 0) {
    // Find tasks whose dependencies are ALL completed
    const ready = [...pending.values()].filter(
      t => t.deps.every(d => completed.has(d))
    );
    
    if (ready.length === 0) throw new Error('Circular dependency');
    
    // Execute all ready tasks in parallel
    const batch = await Promise.allSettled(
      ready.map(async (t) => {
        results[t.id] = await t.fn(results);
        completed.add(t.id);
        pending.delete(t.id);
      })
    );
  }
  
  return results;
}

3. React useQueries for Parallel Fetching

// React Query: parallel independent queries
function Dashboard() {
  const results = useQueries({
    queries: [
      { queryKey: ['revenue'], queryFn: fetchRevenue },
      { queryKey: ['users'], queryFn: fetchActiveUsers },
      { queryKey: ['orders'], queryFn: fetchRecentOrders },
      { queryKey: ['alerts'], queryFn: fetchAlerts },
    ],
  });
  // All 4 fire simultaneously on mount!
  // Each has independent loading/error state
  
  return (
    <div>
      {results.map((result, i) => (
        <Widget
          key={i}
          isLoading={result.isLoading}
          error={result.error}
          data={result.data}
        />
      ))}
    </div>
  );
}

// For dependent queries — use enabled option:
const user = useQuery({ queryKey: ['user'], queryFn: fetchUser });
const posts = useQuery({
  queryKey: ['posts', user.data?.id],
  queryFn: () => fetchPosts(user.data.id),
  enabled: !!user.data?.id, // Only fetch after user loads
});

CombinatorSettles whenResultUse case
Promise.allAll fulfill OR first rejectArray of valuesDependent batch, login flow

Orchestration Decision Tree

Requests independent? ──── No ──→ Sequential (await in order)
         │ Yes
         ▼
All must succeed? ─────── Yes ──→ Promise.all
         │ No
         ▼
Show partial results? ─── Yes ──→ Promise.allSettled
         │ No
         ▼
Need fastest only? ─────── Yes ──→ Promise.any or Promise.race
         │
         ▼
Many requests (>6)? ────── Yes ──→ Concurrency limiter (pool)
         │ No
         ▼
Mixed dependencies? ─────── Yes ──→ Dependency graph executor
