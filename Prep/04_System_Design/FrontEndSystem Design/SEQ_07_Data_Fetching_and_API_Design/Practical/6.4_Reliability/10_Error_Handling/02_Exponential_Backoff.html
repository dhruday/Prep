Exponential Backoff + Jitter

On transient failure, wait min(base × 2^attempt + jitter, cap) before retrying. This avoids thundering-herd stampedes when many clients retry simultaneously.

Jitter adds randomness (0–baseDelay) to each wait so retries don't synchronize across clients.

Why Jitter Matters

Without jitter, N clients all failing at t=0 will all retry at t=1s, t=2s, etc. — the "thundering herd." Jitter desynchronizes retries, spreading load evenly. Full jitter: wait = rand(0, base × 2^attempt).

Browser Constraints

• setTimeout minimum ~4 ms (nested > 5 levels).
• Background tabs may throttle timers to 1 s minimum.
• Use AbortController to cancel in-flight retries on navigation.

Q: Why exponential instead of fixed-interval retry?

Fixed intervals keep hammering the server at the same rate. Exponential backoff gives the server progressively more breathing room to recover, reducing load during outages.

Q: What is the "thundering herd" problem?

When many clients retry simultaneously after a failure, they flood the server at the same moment. Jitter randomizes retry timing to spread the load.

Q: Should you retry POST requests?

Only if the operation is idempotent (via idempotency keys). Non-idempotent POSTs risk duplicate side-effects on retry.
