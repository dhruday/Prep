Why Promise.allSettled?

A dashboard has multiple independent widgets. Promise.all rejects on the first failure — cascading one widget's error to crash the entire page.

Promise.allSettled waits for ALL promises and returns each result as {status:'fulfilled',value} or {status:'rejected',reason}. You render each widget independently.

Promise.all vs Promise.allSettled

Promise.all
One failure = entire dashboard blank
All-or-nothing — bad for independent data
Promise.allSettled
Each widget handles its own failure
Partial rendering — graceful degradation

Dashboard Loader with allSettled

async function loadDashboard() {
  const widgets = [
    { id: 'revenue',  url: `${API}/api/dashboard` },
    { id: 'users',    url: `${API}/api/dashboard` },
    { id: 'activity', url: `${API}/api/unreliable/flaky` },
    { id: 'alerts',   url: `${API}/api/unreliable/flaky` },
  ];

  const results = await Promise.allSettled(
    widgets.map(w => fetch(w.url).then(r => r.json()))
  );

  results.forEach((result, i) => {
    const el = document.getElementById(widgets[i].id);
    if (result.status === 'fulfilled') {
      renderWidget(el, result.value);
    } else {
      renderFallback(el, widgets[i].id);
    }
  });
}

Key Points

• Use Promise.allSettled for independent parallel fetches — never Promise.all

• Each widget handles its own error: show stale data, default, or error state

• The page always renders — partial data beats no data

• Track per-widget success/failure rates for reliability monitoring

• Combine with fallback chain: allSettled catches failures, chain provides fallback data

Interview tip: "We use Promise.allSettled so a flaky activity feed never crashes the revenue dashboard."
