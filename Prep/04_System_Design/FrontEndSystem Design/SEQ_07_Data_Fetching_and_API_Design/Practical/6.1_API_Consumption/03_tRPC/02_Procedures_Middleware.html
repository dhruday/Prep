Defining Procedure Types

const t = initTRPC.context<Context>().create();

// Base middleware — logging
const logger = t.middleware(async ({ next, path }) => {
  const start = Date.now();
  const result = await next();
  console.log(`${path} took ${Date.now() - start}ms`);
  return result;
});

// Auth middleware — adds user to context
const isAuthed = t.middleware(({ ctx, next }) => {
  if (!ctx.session?.user) throw new TRPCError({ code: 'UNAUTHORIZED' });
  return next({ ctx: { user: ctx.session.user } });
});

// Admin middleware — checks role
const isAdmin = isAuthed.unstable_pipe(({ ctx, next }) => {
  if (ctx.user.role !== 'admin') throw new TRPCError({ code: 'FORBIDDEN' });
  return next();
});

// Three procedure types
const publicProcedure   = t.procedure.use(logger);
const protectedProcedure = t.procedure.use(logger).use(isAuthed);
const adminProcedure     = t.procedure.use(logger).use(isAdmin);

Using Procedures in Router

export const appRouter = t.router({
  // Anyone can call this
  healthCheck: publicProcedure.query(() => 'ok'),

  // Must be logged in
  getProfile: protectedProcedure.query(({ ctx }) => {
    return db.users.findById(ctx.user.id);
    // ctx.user is typed! TypeScript knows it exists.
  }),

  // Must be admin
  deleteUser: adminProcedure
    .input(z.object({ userId: z.string() }))
    .mutation(({ input }) => db.users.delete(input.userId)),
});

Context Narrowing Through Middleware

// Each middleware NARROWS the context type

publicProcedure:
  ctx: { session: Session | null }

protectedProcedure (after isAuthed):
  ctx: { session: Session; user: User }
  // TypeScript KNOWS user exists — no optional chaining needed

adminProcedure (after isAdmin):
  ctx: { session: Session; user: User & { role: 'admin' } }
  // TypeScript KNOWS role is 'admin' — enum narrowed

Middleware vs Guards Comparison

─────────────────             ─────────────────

Performance Impact

Middleware runs synchronously in sequence. Each next() call awaits the downstream chain. A 3-middleware stack adds ~0.01ms overhead — negligible compared to DB queries. The real cost is in what the middleware does (JWT verification, DB lookups), not the chain itself.

Q1: How does tRPC middleware differ from Express middleware?

A: tRPC middleware is type-safe and composable through the procedure builder pattern (.use(mw1).use(mw2)). Each middleware can narrow the context type, so downstream middleware and handlers get stronger types. Express middleware mutates req/res without type safety — you need manual type assertions. tRPC middleware also uses the next() pattern to pass modified context, while Express uses next() only for flow control.

Q2: How do you compose middleware in tRPC?

A: Two ways: (1) Chain with .use() on procedures: t.procedure.use(logger).use(auth). Each .use() wraps the previous. (2) Pipe middlewares: isAuthed.unstable_pipe(isAdmin) creates a single middleware from two. You then create named procedure helpers: const adminProcedure = t.procedure.use(combinedMiddleware). The router uses these as building blocks.

Q3: How does context narrowing work?

A: When middleware calls next({ ctx: { user: session.user } }), tRPC's type system merges the new context with the existing one. Downstream handlers see the narrowed type. This means protectedProcedure handlers can access ctx.user without optional chaining — TypeScript guarantees it exists because the middleware would have thrown before reaching the handler.

Q4: Public vs protected vs admin — how to organize?

A: Define reusable procedure helpers at the tRPC initialization level. Each level adds one middleware layer. Group related procedures into sub-routers. Use publicProcedure for health checks, landing page data. protectedProcedure for user-specific data. adminProcedure for destructive operations. This pattern is self-documenting: the procedure type name tells you the access level at a glance.
