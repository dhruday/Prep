How tRPC Achieves End-to-End Types

tRPC uses TypeScript's type inference — the server defines procedures with input/output types, and the client infers them through the AppRouter type export. No code generation step is needed.

Server types → TypeScript compiler → Client autocomplete. Change server → client breaks at compile time.

Server: Define the Router

// server/router.ts
import { initTRPC } from '@trpc/server';
import { z } from 'zod';

const t = initTRPC.create();

export const appRouter = t.router({
  getUser: t.procedure
    .input(z.object({ id: z.string() }))
    .query(async ({ input }) => {
      // input is typed as { id: string }
      return { id: input.id, name: 'Alice', role: 'admin' };
      // Return type inferred: { id: string; name: string; role: string }
    }),
});

// Export the type — this is the magic link
export type AppRouter = typeof appRouter;

Client: Types Flow Automatically

// client/trpc.ts
import { createTRPCProxyClient, httpBatchLink } from '@trpc/client';
import type { AppRouter } from '../server/router';

const trpc = createTRPCProxyClient<AppRouter>({
  links: [httpBatchLink({ url: 'http://localhost:3000/trpc' })],
});

// Full autocomplete — no codegen needed!
const user = await trpc.getUser.query({ id: '123' });
// user is typed as { id: string; name: string; role: string }

trpc.getUser.query({ id: 42 });
// TS Error: Type 'number' is not assignable to type 'string'

The Type Chain

Server Router Definition
    ↓ export type AppRouter = typeof appRouter
TypeScript Compiler (type-only import)
    ↓ import type { AppRouter } from '../server/router'
Client Proxy
    ↓ createTRPCProxyClient<AppRouter>
Full autocomplete + compile-time errors
    ↓ trpc.getUser.query({ id: '123' }) → typed result

📝 What Happens at Runtime?

tRPC sends a plain HTTP request under the hood — the types exist only at compile time. The wire format is just JSON over HTTP.
// What tRPC actually sends:
GET /trpc/getUser?input=%7B%22id%22%3A%22123%22%7D

// Decoded: /trpc/getUser?input={"id":"123"}
// Response: {"result":{"data":{"id":"123","name":"Alice","role":"admin"}}}

tRPC Wire Protocol

Query (GET request):
  GET /trpc/getUser?input={"id":"123"}
  → Cacheable by browser, CDN, reverse proxy

Mutation (POST request):
  POST /trpc/createUser
  Body: {"id":"123","name":"Bob"}

Batch (single round-trip):
  GET /trpc/getUser,getPosts?batch=1&input={"0":{"id":"1"},"1":{}}
  → Multiple procedures in one HTTP request

Type Erasure at Compile Time

TypeScript types are erased during compilation. tRPC's magic is that import type { AppRouter } imports zero runtime bytes — it only exists for the TS compiler. The compiled JS has no type information.
// TypeScript source:
import type { AppRouter } from '../server/router';
const trpc = createTRPCProxyClient<AppRouter>({...});

// Compiled JavaScript (types gone):
const trpc = createTRPCProxyClient({...});
// No import, no type info — just a plain function call

Monorepo Requirement

tRPC requires the server and client to share types via import type. This means they must be in the same TypeScript project or monorepo. For separate repos, you'd need GraphQL or OpenAPI codegen instead.

Q1: How does tRPC achieve type safety without codegen?

A: tRPC leverages TypeScript's structural type system and type inference. The server defines procedures as TypeScript functions with typed inputs and outputs. The client imports the router type (not the runtime code) using import type. TypeScript's compiler then infers the exact input/output types for each procedure call. No codegen step, no schema file — just TypeScript's built-in type inference across a shared type boundary.

Q2: tRPC vs GraphQL codegen — when to use which?

tRPC                           GraphQL
─────────────────────           ─────────────────────
Same repo (monorepo)            Separate repos / teams
TypeScript only                 Language-agnostic
Zero codegen                    Requires codegen step
No schema file                  Schema-first (SDL)
Direct function call feel       Query language (GQL)
Simpler for full-stack TS       Better for public APIs
No introspection                Built-in introspection
Tight coupling (by design)      Loose coupling

Q3: What is `import type` and why does tRPC use it?

A: import type is a TypeScript-only import that is completely erased at compile time. It imports zero runtime bytes — no module loading, no bundled code. tRPC uses it so the client can reference the server's router type for autocomplete and type checking without actually importing the server code into the client bundle. This keeps the client lightweight while maintaining full type safety.

Q4: Can tRPC work across separate repositories?

A: Not natively. tRPC relies on import type from the server package, which requires a shared TypeScript compilation context (monorepo or published npm package with types). For cross-repo scenarios, alternatives include: (1) Publish the server as an npm package with its types. (2) Use GraphQL with codegen. (3) Use OpenAPI with generated TypeScript clients. tRPC is intentionally designed for the monorepo use case.
