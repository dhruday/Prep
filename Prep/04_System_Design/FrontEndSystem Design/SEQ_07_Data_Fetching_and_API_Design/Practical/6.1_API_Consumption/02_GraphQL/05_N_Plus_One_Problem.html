What Is the N+1 Problem?

When resolving a list of N items plus a related field, a naive resolver fires 1 query for the list + N queries for each related item = N+1 total queries.

Fetching 10 posts + each author = 11 HTTP requests instead of 2.

❌ Naive Resolver — N+1 Queries

// GraphQL resolver
Post: {
  author: async (post) => {
    // Called ONCE PER POST — N times!
    return await db.query(`SELECT * FROM users WHERE id = ${post.authorId}`);
  }
}

// Query: { posts { title author { name } } }
// 1 query for posts + 10 queries for authors = 11 queries!

✅ DataLoader — Batched to 2 Queries

const authorLoader = new DataLoader(async (authorIds) => {
  // Called ONCE with all collected IDs
  const authors = await db.query(
    `SELECT * FROM users WHERE id IN (${authorIds.join(',')})`
  );
  // Return in same order as input IDs
  return authorIds.map(id => authors.find(a => a.id === id));
});

Post: {
  author: (post) => authorLoader.load(post.authorId)
  // DataLoader defers & batches all .load() calls in one tick
}

DataLoader Batching — How It Works

Event Loop Tick Batching:

  Tick 1 (microtask):
    resolver post1.author → loader.load(1)  // queued
    resolver post2.author → loader.load(2)  // queued
    resolver post3.author → loader.load(5)  // queued

  Tick 2 (next microtask via process.nextTick / Promise.resolve):
    DataLoader dispatches: batchFn([1, 2, 5])
    → Single SQL: SELECT * FROM users WHERE id IN (1, 2, 5)

Key insight: DataLoader uses process.nextTick() to defer the
batch function until all synchronous .load() calls in the current
event loop tick have been collected.

Per-Request Caching

// DataLoader caches within a single request
loader.load(1) // → hits DB
loader.load(1) // → returns cached Promise (no DB hit)

Browser Connection Limits

Browsers allow only 6 concurrent connections per origin (HTTP/1.1). 11 requests means 5 are queued, adding latency. Batching to 2 requests avoids this bottleneck entirely.

Q1: Explain the N+1 problem in GraphQL

A: In GraphQL, each field has its own resolver. When resolving a list of N items with a related field, the related resolver is called N times — once per item. Combined with the initial list query, that's N+1 database calls. For example, fetching 100 posts with their authors triggers 101 queries. The fix is DataLoader, which batches all individual loads from a single event loop tick into one bulk query.

Q2: How does DataLoader achieve batching?

A: DataLoader collects all .load(key) calls made synchronously within one event loop tick. It then uses process.nextTick() (or a microtask) to invoke the batch function with all collected keys at once. Each .load() returns a Promise that resolves when the batch completes. It also caches results per request to avoid duplicate loads for the same key.

Q3: Why create a new DataLoader per request?

A: DataLoader's built-in cache is a simple memoization Map. If shared across requests, User A could see User B's data from cache (security leak), or stale data persists after mutations. Creating a fresh DataLoader per request ensures isolation and correctness. The per-request cost is negligible compared to the N+1 savings.

Q4: N+1 problem on the frontend — does it exist?

A: Yes. If a React component fetches data for each list item individually (e.g., useEffect per card), you get N+1 on the client. Solutions: (1) Fetch all data in the parent and pass down as props. (2) Use a client-side DataLoader pattern. (3) Design the API to return nested data in one call. (4) Use GraphQL fragments to co-locate data needs and fetch in one query.
