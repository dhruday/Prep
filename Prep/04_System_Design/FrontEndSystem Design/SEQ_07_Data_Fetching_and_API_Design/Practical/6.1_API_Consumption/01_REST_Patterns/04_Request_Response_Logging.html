Why Log Every API Call?

  • Debugging: Quickly trace failures to a specific request
  • Performance monitoring: Identify slow endpoints before users complain
  • Correlation: Link frontend requests to backend traces via shared IDs

console.time vs Performance API

console.time()/console.timeEnd() are convenient but imprecise (milliseconds, no programmatic access). The Performance API uses DOMHighResTimeStamp (microsecond precision) and entries are queryable for dashboards and analytics.

Q: How do you implement distributed tracing in the frontend?

Generate a unique correlation ID (UUID) per request. Pass it as X-Request-ID header. The backend propagates it through microservice calls. Additionally, use W3C Trace Context headers (traceparent, tracestate) and baggage headers for OpenTelemetry-compatible traces.

Q: What's the performance cost of logging every request?

Minimal if async: buffering logs in memory and flushing in batches to a collector (e.g., beacon API) has negligible overhead. Dangerous if synchronous: console.log with large payloads in production blocks the main thread. In production, use log levels (ERROR only) and strip verbose logs at build time via tree-shaking or babel plugins.

Q: How do you strip logs in production?

(1) Build-time removal: Babel plugin transform-remove-console or Terser's drop_console. (2) Log levels: A logger utility that checks LOG_LEVEL env var and no-ops below threshold. (3) Conditional compilation: if (process.env.NODE_ENV !== 'production') — dead-code eliminated by bundlers.
