HTTP Caching Headers

Cache-Control: max-age=60              // Fresh for 60s
Cache-Control: stale-while-revalidate=30 // Serve stale 30s while refetching
Cache-Control: no-cache                  // Always revalidate (NOT "don't cache")
Cache-Control: no-store                  // Never cache at all
ETag: "abc123"                           // Content hash for validation
If-None-Match: "abc123"                   // Client sends to validate

304 Not Modified

When the client sends If-None-Match: "etag" and the resource hasn't changed, the server returns 304 Not Modified with no body — the browser uses its cached copy. This saves bandwidth while ensuring freshness.

Browser Cache Layers

Memory Cache→ Disk Cache→ Service Worker Cache→ Network
Memory cache: Very fast, cleared on tab close. Used for resources loaded in the same page load (preloaded images, scripts).
Disk cache: Persists across sessions. Respects Cache-Control headers. Slower than memory but larger capacity.

Cache-Control → Storage Duration

max-age=3600       → disk cache for 1 hour, no revalidation
no-cache            → stored in disk cache but MUST revalidate every time
no-store            → never written to any cache layer
private             → only in browser cache, not CDN/proxy
public, max-age=0  → cacheable by CDN but always revalidate

Cache Partitioning (Chrome)

Since Chrome 86, the HTTP cache is partitioned by top-level site. A resource cached under siteA.com cannot be reused when embedded in siteB.com — even if it's the same URL. This prevents cross-site tracking via cache timing attacks.

Q: What's the difference between no-cache and no-store?

no-cache = the browser CAN store the response but MUST revalidate with the server before using it (sends If-None-Match/If-Modified-Since). no-store = the browser must NOT store the response at all — not in memory, not on disk. Use no-store for sensitive data (banking, PII).

Q: When would you use ETag vs Last-Modified?

ETag is more precise — it's a content hash, so it detects any change regardless of timestamp. Last-Modified has 1-second granularity and can't detect sub-second changes. ETags also work for dynamically generated content where timestamps are meaningless. Use both for maximum compatibility.

Q: How does stale-while-revalidate improve perceived performance?

The browser serves the stale cached response immediately (0ms latency) while firing a background revalidation request. The user sees instant data, and the next request gets fresh data. This is the core UX pattern behind SWR/React Query's staleTime concept.

Q: How do you bust cache when deploying new API versions?

(1) URL versioning: /api/v2/products. (2) Query param: ?v=2.1 (fragile, some CDNs ignore query strings). (3) Content-based ETags: Server generates new ETag on code deploy, 304 stops matching. (4) Short max-age + stale-while-revalidate: Cached data refreshes within seconds of deploy.
