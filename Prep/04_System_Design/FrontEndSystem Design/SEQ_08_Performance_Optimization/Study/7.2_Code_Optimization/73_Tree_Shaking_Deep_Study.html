1. What Is Tree Shaking?

// Tree shaking = removing unused exports from the final bundle
// Named after "shaking a tree to remove dead leaves"
//
// Example: lodash is 70KB minified
// You only use: import { debounce } from 'lodash'
// Without tree shaking: 70KB in bundle
// With tree shaking: ~2KB in bundle (only debounce + its deps)
//
// REQUIREMENT: Only works with ES Modules (import/export)
// Does NOT work with CommonJS (require/module.exports)
//
// Why ES Modules?
// - Static structure: imports/exports known at compile time
// - No conditional imports: always at top level
// - Bundler can statically analyze dependency graph
//
// Why NOT CommonJS?
// - Dynamic: require() can be called conditionally
// - module.exports can be reassigned at runtime
// - Bundler can't determine what's used without executing code

2. How Bundlers Tree Shake

// Step 1: Build dependency graph
// Start from entry point, follow all import statements
// Create a graph of modules and their exports
//
// Step 2: Mark used exports
// Starting from entry, mark every import as "used"
// Follow the chain: entry → imports A.foo → A.foo imports B.bar
// Everything not marked = dead code
//
// Step 3: Remove unused exports
// Terser/SWC minifier removes code marked as unused
// Only in production mode (development keeps everything for debugging)
//
// Example:
// utils.js
export function used() { return 'I stay'; }
export function unused() { return 'I get removed'; }

// app.js
import { used } from './utils';
console.log(used());

// After tree shaking: unused() is removed from bundle
// Minifier also removes the export statement itself

// Webpack marks unused exports with a comment:
// /* unused harmony export unused */
// Terser sees this and removes the dead code

3. ESM vs CommonJS — Tree Shaking Impact

FeatureES Modules (ESM)CommonJS (CJS)
Syntaximport / exportrequire() / module.exports
AnalysisStatic (compile-time)Dynamic (runtime)
Tree Shakeable✅ Yes❌ No
Conditional Import❌ Not at top level✅ require() anywhere

Browser SupportAll modern browsersNode.js only
Always check if a library has an ESM build. Use lodash-es instead of lodash. Use date-fns instead of moment. The ESM version enables tree shaking — the CJS version bundles everything.

Side Effects — The Tree Shaking Killer

// A "side effect" is code that does something besides export a value
// If a module has side effects, bundler CAN'T safely remove it
//
// Side effects include:
// - Modifying global state: window.myGlobal = 42;
// - Polyfills: import 'core-js/features/promise';
// - CSS imports: import './styles.css';
// - Class with static initializers that mutate globals
// - Module-level console.log, fetch, DOM manipulation
//
// Examples:

// ❌ HAS side effects — can't be tree-shaken:
import './polyfill'; // No specific import — runs module body

// ❌ HAS side effects — the class expression mutates prototype:
export class MyClass {
  static instances = [];
  constructor() { MyClass.instances.push(this); }
}
// Even if MyClass is never imported elsewhere, the static field
// initializer runs when the module is loaded → side effect

// ✅ NO side effects — pure export, safe to tree shake:
export function add(a, b) { return a + b; }
export function multiply(a, b) { return a * b; }

The sideEffects Field in package.json

// Tell the bundler which files are safe to tree shake

// package.json — ALL files are side-effect free:
{
  "name": "my-utils",
  "sideEffects": false
}
// → Bundler can safely remove ANY unused export

// package.json — Only CSS has side effects:
{
  "sideEffects": ["*.css", "*.scss", "./src/polyfills.js"]
}
// → CSS is kept, polyfills are kept, everything else is tree-shakeable

// HOW IT WORKS:
// 1. When sideEffects: false, webpack skips entire modules
//    if none of their exports are used
// 2. Without the flag, webpack must keep the module body
//    "just in case" it has side effects
// 3. This is why lodash (CJS, no flag) bundles 70KB
//    but lodash-es (ESM + sideEffects: false) tree-shakes to 2KB

// PURE annotations for function calls:
const result = /*#__PURE__*/ createHelper();
// Tells minifier: this call has no side effects
// If result is unused, the call can be removed entirely

FAANG Interview Questions

Q1: Explain tree shaking. Why does it only work with ES Modules?
Tree shaking is a dead code elimination technique where bundlers remove unused exports from the final bundle. It only works with ES Modules because ESM has static structure — all imports and exports are declared at the top level and known at compile time. The bundler can build a complete dependency graph and determine which exports are actually referenced. CommonJS uses require() which can be called conditionally, inside functions, or with dynamic paths — the bundler can't statically determine what's used without executing the code. Example: lodash uses CJS, so importing { debounce } from 'lodash' still includes all 70KB. Switching to lodash-es (ESM version) allows the bundler to include only debounce and its internal dependencies (~2KB).
Follow-up: What are "side effects" in the context of tree shaking?
Q2: A library you depend on is 200KB but you only use two functions. How do you reduce its bundle impact?
Layered approach: (1) Check if an ESM build exists — many libraries publish both CJS and ESM. Look for "module" or "exports" field in package.json, or a separate -es variant (lodash-es, rxjs). (2) Check if the library supports deep imports — import debounce from 'lodash/debounce' instead of import { debounce } from 'lodash'. This bypasses tree shaking issues by importing only the specific file. (3) Check sideEffects flag — if the library's package.json doesn't have "sideEffects": false, the bundler may include dead code. You can add module overrides in your webpack config. (4) Use babel-plugin-transform-imports to auto-convert named imports to deep imports. (5) Last resort: find a smaller alternative — replace moment (300KB) with date-fns (tree-shakeable, ~2KB per function) or dayjs (2KB total). Use bundle analysis tools to verify the impact.
Follow-up: How would you audit your entire bundle for tree-shaking opportunities?
Q3: Why might tree shaking fail even with ES Modules?
Several gotchas: (1) Side effects — if a module modifies globals, registers polyfills, or has top-level code that runs on import, the bundler keeps the entire module. Mark with "sideEffects": false if safe. (2) Re-exports through barrel files — exporting everything from an index.ts means the bundler must analyze ALL re-exported modules. Deep import paths are sometimes faster. (3) Class declarations — some bundlers treat class creation as potentially having side effects (static properties, decorators). The /*#__PURE__*/ annotation helps. (4) Transpiler output — Babel/TypeScript can produce code patterns that look like side effects to the bundler (IIFE wrappers, Object.defineProperty for enums). Using TypeScript const enums or targeting ESNext avoids this. (5) Dynamic property access — export const utils = { foo, bar }; then using utils[key] prevents tree shaking because the bundler doesn't know which properties are used at runtime.
Follow-up: How do barrel files (index.ts re-exports) affect tree shaking performance?

webpack Tree Shaking Config

// webpack.config.js
module.exports = {
  mode: 'production', // Required for tree shaking!
  optimization: {
    usedExports: true,  // Mark unused exports
    minimize: true,     // Terser removes marked code
    sideEffects: true,  // Respect package.json sideEffects
    concatenateModules: true, // Scope hoisting (more efficient)
  },
};

// Verify tree shaking is working:
// 1. Build with --stats
//    webpack --mode production --stats detailed
// 2. Look for "harmony export" markers in output
// 3. Check unused exports: "unused harmony export foo"
// 4. Use webpack-bundle-analyzer to visualize

✅ All internal modules use ESM (import/export)
✅ package.json has "sideEffects": false (or explicit array)
✅ Libraries have ESM builds (check "module" field)
✅ webpack mode: 'production' enabled
✅ No barrel files re-exporting unused modules (when possible)
✅ Large libraries use deep imports (lodash/debounce)
✅ /*#__PURE__*/ annotation on factory functions
✅ TypeScript targets ESNext or ES2020 (preserves ESM)
✅ Bundle analyzer verifies dead code removal
