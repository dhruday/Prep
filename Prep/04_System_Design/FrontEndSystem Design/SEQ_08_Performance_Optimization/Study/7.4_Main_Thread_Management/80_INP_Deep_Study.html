1. INP Replaces FID (March 2024)

// FID (First Input Delay):
// - Only measured the FIRST interaction
// - Only measured INPUT DELAY (time before handler runs)
// - Ignored processing time and presentation delay
// - A page could have great FID but terrible responsiveness thereafter
//
// INP (Interaction to Next Paint):
// - Measures ALL interactions throughout the page lifecycle
// - Reports the worst (or near-worst) interaction
// - Measures the FULL duration: input delay + processing + paint
// - This is what users ACTUALLY experience
//
// Which interactions count?
// ✓ Click / Tap
// ✓ Key press (keydown → keyup)
// ✗ Scroll (handled by compositor, not main thread)
// ✗ Hover (not a discrete interaction)
//
// Thresholds:
// ┌──────────┬──────────────┬──────────────┐
// │ Good     │ Needs Work   │ Poor         │
// │ ≤ 200ms  │ 200-500ms    │ > 500ms      │
// └──────────┴──────────────┴──────────────┘
//
// Google uses p75 (75th percentile) of real user data
// for CrUX / Search ranking signals

2. How INP Is Calculated

// During a page session, ALL interactions are recorded
// INP = the interaction with the highest latency
// (with a correction for pages with many interactions)
//
// For pages with < 50 interactions:
//   INP = worst interaction
//
// For pages with ≥ 50 interactions:
//   INP = 98th percentile (ignores 1 outlier per 50)
//   This prevents a single fluke from dominating
//
// Example: User has 100 interactions on a page
// Latencies: [30, 40, 50, 80, ..., 150, 400ms]
// 100 interactions → ignore 2 worst → INP = 3rd worst = 150ms
//
// Measuring INP:
import { onINP } from 'web-vitals';

onINP((metric) => {
  console.log(`INP: ${metric.value}ms`);
  console.log(`Element: ${metric.attribution.interactionTarget}`);
  console.log(`Type: ${metric.attribution.interactionType}`); // click/keydown
  console.log(`Input delay: ${metric.attribution.inputDelay}ms`);
  console.log(`Processing: ${metric.attribution.processingDuration}ms`);
  console.log(`Paint delay: ${metric.attribution.presentationDelay}ms`);
});

Three Phases of an Interaction

// Total INP = Input Delay + Processing Time + Presentation Delay
//
// ┌──────────────────────────── INP ─────────────────────────────┐
// │                                                              │
// │  Input Delay  │  Processing Time  │  Presentation Delay      │
// │               │                   │                          │
// │  User clicks  │  Event handler    │  Style → Layout → Paint  │
// │  waiting for  │  runs             │  → Composite → Pixel     │
// │  main thread  │  (your code)      │  on screen               │
// │               │                   │                          │
// └───────────────┴───────────────────┴──────────────────────────┘
//
// Phase 1: INPUT DELAY (time before handler starts)
// Cause: main thread is busy (long task running)
// Fix: break long tasks into chunks, yield to main thread
//
// Phase 2: PROCESSING TIME (handler execution)
// Cause: expensive event handler (heavy computation, large re-render)
// Fix: defer non-essential work, use startTransition, Web Worker
//
// Phase 3: PRESENTATION DELAY (render after handler)
// Cause: large DOM updates, layout thrashing, forced reflows
// Fix: minimize DOM changes, avoid layout thrashing, use CSS containment
//
// Real-world example:
// User clicks "Add to Cart" button
// Input Delay: 80ms (third-party analytics script running)
// Processing: 40ms (state update + re-render cart badge)
// Presentation: 30ms (layout shift for cart animation)
// Total INP: 150ms (Good ✅)

Optimization by Phase

// PHASE 1: Reduce Input Delay
// ─────────────────────────────

// a) Break long tasks during page load
// Before: one 300ms hydration task
// After: three 100ms tasks with yields

// b) Defer third-party scripts
<script src="analytics.js" defer></script>
// Or load after interaction:
button.addEventListener('click', () => {
  import('./heavy-module.js').then(m => m.init());
}, { once: true });

// PHASE 2: Reduce Processing Time
// ─────────────────────────────────

// a) Use React startTransition for non-urgent updates
function handleSearch(query) {
  // Urgent: update input value immediately
  setInputValue(query);

  // Non-urgent: filter results can wait
  startTransition(() => {
    setFilteredResults(filterItems(query));
  });
}

// b) Move computation to Web Worker
// See Long Tasks study for details

// PHASE 3: Reduce Presentation Delay
// ────────────────────────────────────

// a) Use content-visibility: auto for off-screen content
// Skips rendering of non-visible elements
.offscreen-section {
  content-visibility: auto;
  contain-intrinsic-size: 0 500px;
}

// b) Use CSS containment
.card {
  contain: layout style paint;
  /* Browser knows changes inside don't affect outside */
}

FAANG Interview Questions

Q1: What is INP, and how does it differ from FID?
INP (Interaction to Next Paint) replaced FID as a Core Web Vital in March 2024. Three key differences: (1) Scope — FID only measured the first interaction; INP measures all interactions throughout the page lifecycle and reports the worst (or near-worst for high-interaction pages). (2) What's measured — FID only measured input delay (the gap before your event handler runs, caused by main thread being busy). INP measures the full interaction lifecycle: input delay + processing time (event handler) + presentation delay (rendering the visual update). (3) Representativeness — FID could give a false "all clear" if the page was idle when the user first clicked, even if subsequent interactions were terrible. INP captures the actual user experience across the entire session. INP thresholds: ≤200ms is Good, 200-500ms Needs Improvement, >500ms is Poor. Measured at p75 in CrUX data.
Follow-up: How does INP affect SEO and Core Web Vitals ranking?
Q2: An e-commerce page has INP of 450ms. Walk through your debugging and optimization process.
Step 1: Identify which interaction is the INP culprit. Use web-vitals attribution build: onINP() gives me the target element, interaction type, and the three-phase breakdown (input delay, processing, presentation). Step 2: Open Chrome DevTools Performance tab, record the slow interaction. Look at the Main thread: is there a long task before the click (input delay)? Is the event handler itself slow (processing)? Is there a large layout/paint after (presentation)? Step 3: Fix by phase. If input delay is the issue (e.g., 300ms from a third-party script), defer or lazy-load that script, break up long initialization tasks. If processing time is the problem (e.g., re-rendering 500 product cards), use startTransition to defer the heavy render, virtualize the list, or move filtering logic to a Web Worker. If presentation delay is large (e.g., 200ms for layout), check for layout thrashing, add CSS containment, use content-visibility: auto for off-screen sections. Step 4: Validate — re-record in DevTools, check that the interaction is now <200ms. Deploy and monitor p75 INP in RUM.

┌────────────────────┬─────────────────────────────────────┐
