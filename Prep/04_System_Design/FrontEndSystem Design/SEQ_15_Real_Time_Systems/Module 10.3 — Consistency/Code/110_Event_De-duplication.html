Duplicate events are inevitable — build dedup logic into the client

Duplicates happen when: (1) the client reconnects and replays missed events, (2) at-least-once delivery guarantees from message brokers, (3) network retries fire the same event twice. Without dedup, an "Order Shipped" notification appears twice, a counter increments double, or a list item appears twice. At SAP, reconnect-replay combined with event ID tracking ensured exactly-once UI updates on reconnect.

❌ Without dedup
  • Event received → process immediately
  • Duplicate event → processed again
  • Notification shown twice
  • Counter: 2 instead of 1
✅ With ID-based dedup
  • Each event has unique eventId
  • Seen-IDs set checked before processing
  • Duplicate → silently dropped
  • Counter: exactly 1

EventID dedup with TTL eviction

// ─── Client-side event deduplication ───
class EventDeduplicator {
  private seen = new Map<string, number>(); // id → timestamp
  private TTL = 60_000; // 60s window
  isDuplicate(eventId: string): boolean {
    this.evict();
    if (this.seen.has(eventId)) return true;
    this.seen.set(eventId, Date.now());
    return false;
  }
  private evict() {
    const cutoff = Date.now() - this.TTL;
    for (const [id, ts] of this.seen) {
      if (ts < cutoff) this.seen.delete(id);
    }
  }
}
const dedup = new EventDeduplicator();
ws.onmessage = (e) => {
  const event = JSON.parse(e.data);
  if (dedup.isDuplicate(event.eventId)) return; // drop
  processEvent(event);
};
