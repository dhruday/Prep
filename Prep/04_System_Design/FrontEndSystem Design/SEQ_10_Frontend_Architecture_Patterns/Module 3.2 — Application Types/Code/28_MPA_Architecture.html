MPA Request Model

Every navigation requires a full server round-trip. Server renders HTML and sends it. Browser discards current page and loads new one. State is lost between pages (session/cookie bridges it).

User clicks link
→ Browser makes GET /orders (full HTTP request)
→ Server: query DB, render HTML template
→ Server: sends complete HTML page (~50KB)
→ Browser: parses full HTML, discards old DOM
→ Page visible (all content in HTML — great for SEO)
→ Repeat for every navigation — no persistent state

✅ MPA Strengths

Excellent SEO (HTML on first byte)
Works without JavaScript
Each page independently cacheable
Simpler mental model
No JS bundle size problem
Back-button works natively

❌ MPA Weaknesses

Full page reload flicker
Shared header/footer re-fetched
Server must render everything
No client-side state persistence
Harder to build rich interactions

Modern MPA with Next.js (best of both worlds)

// Next.js App Router — each route is server-rendered HTML
// but client-side navigation uses prefetch for SPA-like speed

// app/orders/page.tsx — Server Component (MPA model)
export default async function OrdersPage() {
  // Runs on server — no JS bundle for this data fetching
  const orders = await fetch('/api/orders').then(r => r.json());
  
  return (
    <div>
      <h1>Orders</h1>
      {orders.map((order: Order) => (
        <OrderCard key={order.id} {...order} />
      ))}
    </div>
  );
}

// SEO: Google gets fully rendered HTML
// Performance: zero client-side JS for this page
// Client navigation: Next.js prefetches chunks → SPA-like speed
The modern answer: Most production apps use hybrid rendering — server renders HTML for SEO/performance, then hydrates for interactivity. Next.js App Router, Nuxt 3, SvelteKit all do this.
