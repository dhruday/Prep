💡 Why GPU Composite-Only Wins

The compositor thread runs completely independently from the main JavaScript thread. If your JavaScript is executing a 50ms task (blocking the main thread), a GPU-composited animation continues at 60fps. A layout-triggering animation would jank during that 50ms block. This is why transform + opacity are the gold standard for animations.

🔬 When Does Chrome Auto-Promote?

Without explicit will-change, Chrome auto-promotes elements with: active CSS transform/opacity animation, position: fixed, video/canvas/iframe elements, CSS filter. Auto-promotion happens ON the first animation frame — causing a single-frame composition stutter. will-change prevents this by promoting beforehand.

📋 Correct Pattern — Apply & Remove

// ✅ CORRECT: Apply will-change before animation, remove after
function animateElement(el) {
  el.style.willChange = 'transform, opacity';
  
  // Start animation
  el.classList.add('animating');
  
  el.addEventListener('transitionend', () => {
    el.style.willChange = 'auto'; // Free VRAM!
  }, { once: true });
}

// ❌ WRONG: Always-on will-change wastes VRAM
.every-card {
  will-change: transform; /* Applied to all 100 cards = 100 GPU layers */
}

// ❌ WRONG: will-change: all — meaningless, hurts performance
.comp { will-change: all; }
❌
Anti-pattern: Static will-change on all cards
Applying to every list item creates hundreds of GPU layers, exhausting VRAM on mobile. Common in CSS frameworks that add it blindly.
/* WRONG — 50 card components × 1 GPU layer each = VRAM exhausted */
.card { will-change: transform; }
/* CORRECT — only when needed, via JS */
card.addEventListener('mouseenter', () => {
  card.style.willChange = 'transform';
});
card.addEventListener('mouseleave', () => {
  card.style.willChange = 'auto';
});
❌
Anti-pattern: Animating layout-triggering properties
Still common in codebases. Every frame triggers a full browser reflow.
/* WRONG — animates a layout property */
@keyframes slide { from { top: -100px; } to { top: 0; } }

/* WRONG — width animation triggers reflow on every frame */
.expand { animation: expand .3s; }
@keyframes expand { from { width: 0; } to { width: 200px; } }
/* CORRECT — use transform instead */
@keyframes slide { from { transform: translateY(-100px); } to { transform: translateY(0); } }
@keyframes expand { from { transform: scaleX(0); } to { transform: scaleX(1); } }
❌
Anti-pattern: Reading and writing layout properties in a loop
Forces browser to recalculate layout after every write. Known as "layout thrashing".
// WRONG — read → write → read forces layout every iteration
elements.forEach(el => {
  const width = el.offsetWidth; // forces layout recalc
  el.style.width = (width + 10) + 'px'; // invalidates layout
});
// CORRECT — batch reads, then batch writes
const widths = elements.map(el => el.offsetWidth); // reads
elements.forEach((el, i) => {
  el.style.width = (widths[i] + 10) + 'px'; // writes
});
✅
Best practice: IntersectionObserver + will-change for entry animations
const observer = new IntersectionObserver(entries => {
  entries.forEach(entry => {
    if (entry.isIntersecting) {
      const el = entry.target;
      el.style.willChange = 'transform, opacity';
      el.classList.add('animate-in');
      el.addEventListener('animationend', () => {
        el.style.willChange = 'auto'; // cleanup
        observer.unobserve(el);
      }, { once: true });
    }
  });
}, { rootMargin: '50px' });
