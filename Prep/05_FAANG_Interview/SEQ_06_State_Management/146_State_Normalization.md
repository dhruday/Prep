# 146. State Normalization
**Phase:** State & Data | **Sequence:** SEQ 06 | **Company:** Microsoft, Adobe, Salesforce, Cisco

---

## 🎯 1. Interview Opening Answer

State normalization is the practice of storing entities in a flat, deduplicated structure indexed by ID — separate `ids` array and `entities` dictionary — rather than as nested arrays. It mirrors database normalization: one source of truth per entity, related entities referenced by ID rather than embedded. The problem it solves: with nested/duplicated state, updating a user who appears in 10 different lists requires finding and updating all 10 occurrences. With normalized state, the user exists once in `entities['user_123']` — one update propagates everywhere. Redux Toolkit's `createEntityAdapter` generates this structure automatically along with selectors. The performance benefit for large datasets: O(1) lookup by ID instead of O(n) array traversal.

## 🔍 2. Deep Dive — Senior/Staff Level

### The Problem: Nested State

```typescript
// ❌ Denormalized (nested) state — common initial structure
interface DenormalizedState {
  posts: Array<{
    id: string;
    title: string;
    author: {        // ← author embedded — duplicated across all their posts
      id: string;
      name: string;
      avatar: string;
    };
    comments: Array<{   // ← comments embedded — can't be addressed independently
      id: string;
      text: string;
      author: {       // ← author duplicated again inside comment
        id: string;
        name: string;
        avatar: string;
      };
    }>;
  }>;
}

// Problem 1: Update author name
// Must find: all posts by this author, all comments by this author (O(n * m))
// Miss one → stale data shown in some places

// Problem 2: Add a comment to post
// Must find the post in the array (O(n)), find its comments array, append
// Redux: requires structural cloning of the entire nested tree

// Problem 3: Delete a comment
// Must find the post, find the comment, splice (mutation) or filter (O(m)) 
```

### Normalized Shape

```typescript
// ✅ Normalized state — each entity type stored flat, referenced by ID
interface NormalizedState {
  posts: {
    ids: string[];               // ['post_1', 'post_2', 'post_3']
    entities: Record<string, Post>;  // { post_1: {...}, post_2: {...} }
  };
  users: {
    ids: string[];
    entities: Record<string, User>;
  };
  comments: {
    ids: string[];
    entities: Record<string, Comment>;
  };
}

interface Post {
  id: string;
  title: string;
  authorId: string;               // ← reference, not embedded object
  commentIds: string[];           // ← references, not embedded objects
}

interface Comment {
  id: string;
  text: string;
  authorId: string;               // ← reference
  postId: string;                 // ← back-reference for O(1) parent lookup
}

// Problems solved:
// Update author name: users.entities[authorId].name = '...' → one update, consistent everywhere
// Add comment: comments.entities[id] = newComment; posts.entities[postId].commentIds.push(id)
// Delete comment: delete comments.entities[id]; filter from posts.entities[postId].commentIds
// Lookup by ID: comments.entities[commentId] — O(1) always
```

### Redux Toolkit `createEntityAdapter`

```typescript
import { createEntityAdapter, createSlice, createSelector, PayloadAction } from '@reduxjs/toolkit';

interface Product {
  id: string;
  name: string;
  price: number;
  categoryId: string;
  inStock: boolean;
}

// createEntityAdapter generates:
// - initialState with { ids: [], entities: {} }
// - CRUD reducers: addOne, addMany, setOne, setMany, setAll, updateOne, updateMany, upsertOne, upsertMany, removeOne, removeMany
// - Selectors: selectAll, selectById, selectIds, selectEntities, selectTotal
const productsAdapter = createEntityAdapter<Product>({
  // Optional: custom ID selector (default: entity.id)
  selectId: (product) => product.id,

  // Optional: sort order for selectAll output
  sortComparer: (a, b) => a.name.localeCompare(b.name),
});

const productsSlice = createSlice({
  name: 'products',
  initialState: productsAdapter.getInitialState({
    // Extend initial state with additional fields
    loading: false as boolean,
    error: null as string | null,
    lastFetched: null as number | null,
  }),
  reducers: {
    // ✅ All CRUD operations pre-generated by the adapter
    productAdded: productsAdapter.addOne,
    productsAdded: productsAdapter.addMany,
    productUpdated: productsAdapter.updateOne,
    productUpserted: productsAdapter.upsertOne,
    productRemoved: productsAdapter.removeOne,
    productsReceivedFromAPI: productsAdapter.setAll,

    // Custom reducer for toggle
    productToggleStock: (state, action: PayloadAction<string>) => {
      const product = state.entities[action.payload];
      if (product) product.inStock = !product.inStock;  // ← Immer makes mutation safe
    },
  },

  extraReducers: (builder) => {
    builder
      .addCase(fetchProducts.pending, (state) => { state.loading = true; })
      .addCase(fetchProducts.fulfilled, (state, action) => {
        state.loading = false;
        state.lastFetched = Date.now();
        productsAdapter.setAll(state, action.payload);  // ← replace all
      })
      .addCase(fetchProducts.rejected, (state, action) => {
        state.loading = false;
        state.error = action.error.message ?? 'Unknown error';
      });
  },
});
```

### Selectors — Denormalize for Display

```typescript
// createEntityAdapter generates base selectors
const productSelectors = productsAdapter.getSelectors<RootState>(
  state => state.products
);

// Usage:
productSelectors.selectAll(state)        // → Product[] (sorted by sortComparer)
productSelectors.selectById(state, id)  // → Product | undefined
productSelectors.selectIds(state)        // → string[]
productSelectors.selectTotal(state)      // → number

// Derived selectors — join normalized entities
const selectProductsWithCategory = createSelector(
  [productSelectors.selectAll, (state: RootState) => state.categories.entities],
  (products, categoryEntities) =>
    products.map(product => ({
      ...product,
      category: categoryEntities[product.categoryId],  // O(1) lookup
    }))
);

// Filter by category
const selectProductsByCategory = createSelector(
  [
    productSelectors.selectAll,
    (_state: RootState, categoryId: string) => categoryId,
  ],
  (products, categoryId) =>
    products.filter(p => p.categoryId === categoryId)
);

// Compute stats
const selectProductStats = createSelector(
  [productSelectors.selectAll],
  (products) => ({
    total: products.length,
    inStock: products.filter(p => p.inStock).length,
    avgPrice: products.reduce((sum, p) => sum + p.price, 0) / (products.length || 1),
  })
);
```

### Manual Normalization (without RTK)

```typescript
// normalize utility — flatten nested API response
function normalizeProducts(apiResponse: ApiProduct[]): NormalizedState['products'] {
  return apiResponse.reduce(
    (acc, product) => {
      acc.ids.push(product.id);
      acc.entities[product.id] = {
        id: product.id,
        name: product.name,
        price: product.price,
        categoryId: product.category.id,  // keep reference, drop embedded object
      };
      return acc;
    },
    { ids: [] as string[], entities: {} as Record<string, Product> }
  );
}

// Denormalize for display (in selector or component)
function denormalizeProduct(
  productId: string,
  products: Record<string, Product>,
  categories: Record<string, Category>
): ProductWithCategory | undefined {
  const product = products[productId];
  if (!product) return undefined;
  return { ...product, category: categories[product.categoryId] };
}
```

### When Normalization Is Appropriate

```typescript
// ✅ Normalize when:
// - Same entity appears in multiple lists (post author + comment author)
// - Entities are frequently updated individually (real-time updates via WebSocket)
// - Need O(1) lookup by ID frequently (routing: /posts/:id)
// - 500+ total entities in memory
// - Pagination with overlapping items (page 1 and page 2 may share trending posts)

// ❌ Do NOT normalize when:
// - Small, static datasets (<50 items that never update)
// - Entities are display-only, never individually addressed
// - Server state managed by TanStack Query (TQ has its own caching by query key)
// - Data is only ever shown in one place

// The TanStack Query distinction:
// If you use TanStack Query for products, the cache IS the normalized store.
// queryClient.getQueryData(['products', id]) gives you O(1) lookup by id.
// Don't normalize + RTK + TanStack Query for the same entities — that's three caches.
```

### Immutable Updates on Normalized State

```typescript
// Without Immer (RTK uses Immer internally)
function addCommentToPost(
  state: NormalizedState,
  comment: Comment
): NormalizedState {
  return {
    ...state,
    comments: {
      ids: [...state.comments.ids, comment.id],
      entities: { ...state.comments.entities, [comment.id]: comment },
    },
    posts: {
      ...state.posts,
      entities: {
        ...state.posts.entities,
        [comment.postId]: {
          ...state.posts.entities[comment.postId],
          commentIds: [
            ...(state.posts.entities[comment.postId]?.commentIds ?? []),
            comment.id,
          ],
        },
      },
    },
  };
}

// With Immer (RTK slices + createEntityAdapter) — much cleaner:
reducers: {
  commentAdded: (state, action: PayloadAction<Comment>) => {
    const comment = action.payload;
    commentsAdapter.addOne(state.comments, comment);
    const post = state.posts.entities[comment.postId];
    if (post) post.commentIds.push(comment.id);  // Immer handles immutability
  },
}
```

### ⚠️ Anti-Patterns

- **Double-normalizing server state** — if TanStack Query caches `['products', id]`, don't ALSO put products in Redux with `createEntityAdapter`; you get two separate caches that can diverge
- **Normalizing too eagerly** — a static dropdown list of 20 countries does not need normalization; overhead costs: boilerplate, selector complexity, mental model
- **Denormalizing in reducers** — reducers should store the normalized structure; denormalize in selectors only; reducers that embed full objects waste memory and create stale-data bugs
- **`ids` array out of sync with `entities`** — if you manually delete from `entities` without removing from `ids`, `selectAll` returns undefined entries; always use adapter methods that keep both in sync

## 🏭 3. Real-World Examples

**At Hruday's level:**
At SAP, the supplier management view had a supplier list page AND a supplier detail panel — both needed to render the same supplier. The list used embedded supplier objects in a `suppliers[]` array; the detail panel fetched separately. When a manager updated a supplier's address live, the list showed the old address while the detail panel showed the new — classic denormalized inconsistency. Migrated to `createEntityAdapter` with `suppliers.entities[id]` as the single source. Both list and panel read from the same entity — update propagated everywhere in one dispatch.

**FAANG scale:**
- **Microsoft:** Outlook web — email threads are normalized; the email entity appears in the inbox list, the sent folder, the search results, and the open thread simultaneously; one entity, consistent everywhere
- **Adobe:** Experience Manager — thousands of assets across multiple collections; normalization by `assetId` enables the "used in" feature (show all collections an asset belongs to) as a reverse-lookup from the normalized state
- **Salesforce:** Activity timeline — same lead appears in multiple deal pipelines; normalized leads with `leadId` references in pipeline records; single `leads.entities[id]` update from WebSocket event updates all pipeline views simultaneously
- **Cisco:** Device inventory — 50K+ devices; normalized by `deviceId`; filtering, sorting, grouping all operate on the `ids` array without copying entities; memory footprint reduced by 60% vs duplicating device objects in each view

## 💬 4. Interview Execution

### Sample Answer

> "Normalization is about having one source of truth per entity. Without it, the same user might exist in 20 places in your state tree — the post author object embedded in post 1, post 2, etc., and the comment author objects. When that user updates their name, you need to find and update all 20 copies. Miss one, and some part of your UI shows the old name. With normalization, the user exists once in `users.entities[userId]` — one update, consistent everywhere.
>
> Redux Toolkit's `createEntityAdapter` is the production tool for this. It generates the `{ ids: [], entities: {} }` structure and all the CRUD methods — `addOne`, `updateOne`, `setAll`, `removeOne` — plus base selectors. You add domain selectors on top using `createSelector`, which lets you denormalize for display (join the user into the product without storing them embedded).
>
> The performance case: O(1) vs O(n). `state.entities[id]` is O(1). `state.entities.find(e => e.id === id)` is O(n). At 10K items, that's the difference between a 12ms and 500ms click response.
>
> Important caveat: if I'm using TanStack Query, the TQ cache IS a normalized store by query key. Layering `createEntityAdapter` on top of TanStack Query for the same data creates two caches that can disagree — that's an anti-pattern I always flag in code review."

### Likely Follow-up Questions
1. "What's the difference between `setAll` and `upsertMany`?" → `setAll` replaces all entities (wipes and reloads from API response); `upsertMany` merges — adds new + updates existing, leaves entities not in the payload untouched
2. "How do you handle circular references in normalized state?" → Use IDs on both sides: `post` has `commentIds: string[]`, `comment` has `postId: string` — the reference circle is broken because both are just IDs, not embedded objects
3. "How do you handle pagination with normalized state?" → Keep entities in the adapter; store pagination metadata separately: `pages: Record<number, string[]>` mapping page number to array of entity IDs for that page
4. "`createEntityAdapter` sets `sortComparer` — when would you change the sort at runtime?" → Don't put dynamic sort in `sortComparer` (it runs on every insert/update); compute sorted order in a `createSelector` that takes the sort direction as a parameter instead
5. "Is normalization always better?" → No — for small, static, display-only data it adds unnecessary complexity; normalize when entities are shared across views and updated independently

## 💻 5. Code Example

```typescript
// Real-world: Normalized chat state — messages, users, channels

// Entities
interface User { id: string; name: string; avatar: string; status: 'online' | 'offline'; }
interface Channel { id: string; name: string; memberIds: string[]; lastMessageId: string | null; }
interface Message { id: string; text: string; authorId: string; channelId: string; timestamp: number; }

// Adapters
const usersAdapter = createEntityAdapter<User>();
const channelsAdapter = createEntityAdapter<Channel>();
const messagesAdapter = createEntityAdapter<Message>({
  sortComparer: (a, b) => a.timestamp - b.timestamp,
});

// Slice
const chatSlice = createSlice({
  name: 'chat',
  initialState: {
    users: usersAdapter.getInitialState(),
    channels: channelsAdapter.getInitialState(),
    messages: messagesAdapter.getInitialState(),
    activeChannelId: null as string | null,
  },
  reducers: {
    usersReceived: (state, action: PayloadAction<User[]>) => {
      usersAdapter.setAll(state.users, action.payload);
    },
    channelsReceived: (state, action: PayloadAction<Channel[]>) => {
      channelsAdapter.setAll(state.channels, action.payload);
    },
    messageReceived: (state, action: PayloadAction<Message>) => {
      const msg = action.payload;
      messagesAdapter.addOne(state.messages, msg);

      // Also update channel's lastMessageId
      const channel = state.channels.entities[msg.channelId];
      if (channel) channel.lastMessageId = msg.id;  // Immer mutation
    },
    userStatusUpdated: (state, action: PayloadAction<{ id: string; status: User['status'] }>) => {
      usersAdapter.updateOne(state.users, {
        id: action.payload.id,
        changes: { status: action.payload.status },
      });
    },
    channelSelected: (state, action: PayloadAction<string>) => {
      state.activeChannelId = action.payload;
    },
  },
});

// Selectors
const userSelectors = usersAdapter.getSelectors((s: RootState) => s.chat.users);
const channelSelectors = channelsAdapter.getSelectors((s: RootState) => s.chat.channels);
const messageSelectors = messagesAdapter.getSelectors((s: RootState) => s.chat.messages);

// Derived: messages for active channel with author objects joined in
const selectActiveChannelMessages = createSelector(
  [
    (state: RootState) => state.chat.activeChannelId,
    messageSelectors.selectAll,
    userSelectors.selectEntities,
  ],
  (activeChannelId, allMessages, userEntities) => {
    if (!activeChannelId) return [];
    return allMessages
      .filter(m => m.channelId === activeChannelId)
      .map(m => ({ ...m, author: userEntities[m.authorId] }));
  }
);

// Derived: channels with unread count (if we tracked read cursors)
const selectChannelsWithMeta = createSelector(
  [channelSelectors.selectAll, messageSelectors.selectAll, userSelectors.selectEntities],
  (channels, messages, users) =>
    channels.map(channel => {
      const lastMsg = channel.lastMessageId
        ? messages.find(m => m.id === channel.lastMessageId)
        : null;
      return {
        ...channel,
        lastMessage: lastMsg ? { ...lastMsg, author: users[lastMsg.authorId] } : null,
        memberCount: channel.memberIds.length,
      };
    })
);

export {
  chatSlice,
  selectActiveChannelMessages,
  selectChannelsWithMeta,
  userSelectors,
  channelSelectors,
};
```

## 🧠 6. Memory Aid

**FORD — why normalize:**
- **F**lat — one copy per entity, no nesting
- **O**ne — single source of truth per ID  
- **R**eference — link by ID, not embedding
- **D**iscoverable — O(1) lookup by ID via dictionary

**`createEntityAdapter` methods — SARUR:**
- **S**etAll — replace all
- **A**ddOne/addMany — insert new
- **R**emoveOne/removeMany — delete
- **U**pdateOne/updateMany — partial update (id + changes)
- **R**ead (selectAll, selectById, selectIds, selectTotal) — selectors

## ✅ 7. Why & How Summary

**Why it matters:**
→ The real-time update scenario is the killer use case — at SAP, a WebSocket event updates a user entity once in `entities[userId]`; without normalization, you'd need to scan every array in state to find all occurrences and update them (likely missing some); with normalization, one dispatch via `updateOne` propagates to every component that reads that entity through its selector
→ O(1) vs O(n) lookup is an interview talking point that shows algorithmic awareness — `selectById` is a dictionary lookup (O(1)); `state.posts.find(p => p.id === id)` is array scan (O(n)); at 10K entities the difference is perceptible latency in click handlers
→ The TanStack Query / normalization boundary question separates mid-level from senior candidates — TanStack Query normalizes by query key (server state); Redux `createEntityAdapter` normalizes by entity ID (client-side derived state); they serve different purposes and should not be used for the same entities simultaneously

**How it works (2 sentences):**
`createEntityAdapter` stores entities as two parallel structures: an `ids` string array (preserves insertion/sort order for iteration → `selectAll`) and an `entities` object keyed by ID (enables O(1) lookup → `selectById`) — all adapter CRUD methods keep these two structures in sync as an atomic operation via Immer, eliminating the class of bugs where `ids` and `entities` diverge.
`createSelector`'s memoization makes the denormalization cost pay-once — the join between `messages.selectAll` and `userSelectors.selectEntities` runs only when either the messages or users change, not on every render; between updates, the selector returns the exact same array reference, so `React.memo`-wrapped components that receive this as a prop skip re-rendering entirely.
